# ADR-0001：飞书为操作账本，本地为分析账本

- 状态：`proposed`
- 日期：2026-09-16
- 决策者：Owner（周健）
- 影响：数据架构、同步方向、所有后续工具的实现方式

## 背景

业务侧已经用飞书多维表格在管理内容合规数据（广告文案明细 291 条、规则库 21 条、
改写建议库 52 条、正负样本若干）。我们需要的却是另一个东西：

1. **可复算** —— 「这个数字是从哪一版数据算出来的」必须能回答；
2. **可版本化** —— 「上周和这周规则变了什么」必须能 diff；
3. **可离线** —— Agent 判定不能依赖飞书在线；
4. **可回放** —— 一次审查跑完，要能重放当时的规则与输入。

飞书多维表格**做不到** 1/2/4：它没有内容指纹、没有内容级 diff、没有回放包。

但反过来，让业务改到本地 Markdown 里工作也**不可行**：飞书是他们唯一的协作面，
强行迁移等于让项目在第一周就没人用。

**这是一个真实的取舍，不能两边都要。**

## 决策

采用**双账本**，并明确划走各自的权威范围：

| | 操作账本（Operational） | 分析账本（Analytical） |
|---|---|---|
| **载体** | 飞书多维表格 | 本地 git 仓库 |
| **权威对象** | **人的动作** —— 谁判的、改了什么、状态流转 | **规则的语义** —— 规则内容、版本、证据 |
| **谁写** | 业务同事（人） | 我们的工具（程序） |
| **谁读** | 人 + Agent | 我们的工具 |
| **冲突时** | 人的记录优先 | 程序生成物以本地为准 |

**同步方向**：

```
飞书 ──(单向拉取，只读)──▶ 本地快照 ──▶ 分析/规则生成 ──▶ Agent
  ▲                                                        │
  └──────────(人工确认后，显式回写建议字段)◀────────────────┘
```

- **拉取是单向的、自动的、只读的** —— 工具永不直接改飞书业务字段。
- **回写是显式的、经人确认的** —— 只写「建议」类字段，不覆盖人工判定。
- 每次拉取产出**内容指纹（sha256）**，写入 `research/live/LATEST.json`。

## 为什么不选另外两种

**方案 B：飞书为唯一权威，本地不存副本**
- ❌ 无法复算：飞书 API 没有「历史版本」能力，改了就查不到
- ❌ 无法离线：守衡断网即失效
- ❌ 无法回放：没有输入快照，receipt 无意义

**方案 C：本地为唯一权威，飞书只做展示**
- ❌ 业务同事无法维护（他们不会用 git）
- ❌ 与「不额外增加工作量」的会议要求直接冲突
- ❌ 291 条记录已经在飞书里，迁移成本无人承担

## 后果

**正面**
- 「我们分析的是哪一版数据」变成可验证事实（有 sha256）
- 规则变更有 diff、有历史、可回滚
- 守衡可离线工作
- 业务同事的工作方式**完全不变**

**负面 / 必须接受的代价**
- **存在同步延迟** —— 飞书改了，本地要等下次拉取。必须显式记录「拉取时间」
- **必须处理漂移** —— 本地生成物与飞书现状可能不一致，需要 `drift` 检查
- **两套字段名** —— 飞书用中文列名，本地用英文字段。需要一层映射表并版本化

**必须现在就定的硬规则**
1. 任何进入分析的数字，**必须能指回一个快照指纹**；指不回的数字不得写进任何报告。
2. 飞书表结构变更（增删列、改类型）→ 必须同步更新映射表，且映射表本身进 git。
3. 拉取失败**不得静默继续** —— 用旧快照继续算，必须显式标注「用的是旧快照」。

## 待 Owner 确认的问题

1. 是否接受「单向自动拉取 + 显式回写」这个方向？
2. 回写允许的字段范围：只允许写「建议」类字段，还是也允许写状态？
3. 首次全量拉取的授权范围：除已知 6 张表外，是否还有应纳入的表？
