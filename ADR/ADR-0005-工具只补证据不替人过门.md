# ADR-0005：Agent 只补证据，不替人通过判定

- 状态：`proposed`
- 日期：2026-09-16
- 决策者：Owner（周健）
- 依赖：ADR-0002（溯源）

## 背景

09-15 规划会上，这一点被讲得非常明确（原话，出自智能纪要）：

> 「它其实不承担任何给真正的决策和下判断的一个动作」
> 「我不要挑战人性」

会议定的 agent 定位：
> **仅承担风险筛查、问题标注、流程分流职责，不做最终决策判断**，目标可覆盖 90% 的已知风险

这条原则在会议上已经达成共识。**本 ADR 把它固化成可执行的约束，
因为「不做决策」这句话如果不翻译成代码规则，实现时一定会漂移。**

### 实测证据：人工判定里有大量规则表装不下的东西

291 条记录中 130 条有 `命中原因`（自然语言），平均 **118 字**，最长 **299 字**：

> 「H07 疼痛功效承诺（pain-free/no pain/without pain/pain relief/less pain/缓解疼痛等；
> 吸奶疼痛因人而异，只可讲 comfort/gentle 舒适与缓解胀满不适 discomfort）」

这段文字里包含三种规则表**没有**的信息：
1. **裁量理由** —— 「吸奶疼痛因人而异」（为什么这条是红线）
2. **合规替代方案** —— 「只可讲 comfort/gentle」
3. **适用边界** —— 「缓解胀满不适 discomfort 可以」

规则表 12 个字段里，没有一个字段能装这三样。

**结论：真正的判定逻辑，一部分在规则里，一部分在人脑里，还有一部分在这 130 段自由文本里。
Agent 可以学会前两部分，第三部分只能由人来。**

## 决策

把「不做决策」翻译成**五条可测试的代码约束**：

### 约束 1：Agent 的输出是「分流建议」，不是「判定结论」

```yaml
# Agent 输出（结构固定）
suggestion: 直接发布 | 转人工 | 需修改     # 建议，不是决定
matched_rules: [H07, M03]                  # 命中了什么
evidence:                                   # 凭什么
  - rule: H07
    fragment: "sans douleur"                # 原文片段，不可改写
    source_sha256: 2a1a219a7e76…
confidence: low | medium | high              # 置信度必须给
unknowns:                                   # ★ 必须显式列出「我判断不了什么」
  - "该表达在法语市场是否属于行业惯用语，规则库未覆盖"
```

`unknowns` **不允许为空数组**。如果 Agent 认为没有不确定项，必须显式写
`unknowns: ["无 —— 但本判定未覆盖图片/视频部分"]`，逼它说明覆盖边界。

### 约束 2：Agent 永远不能写「已通过」

- Agent **不能**把记录状态改成 `无需处理`
- Agent **不能**关闭任何待复核项
- Agent 只能**新增**字段：`agent_suggestion`、`agent_evidence`、`agent_unknowns`
- 人的字段（`处理状态`、`检查人`、`修改建议`）**Agent 只读**

> 这条直接对应会议原话「增设负责人上线确认环节」——
> 绕过人的动作在系统层面不存在，不依赖自觉。

### 约束 3：规则未命中 ≠ 合规

对应设计文档 §5.1。规则表**是白名单，不做判险**。
因此：
- Agent 说「未命中任何规则」时，**分流建议不得是「直接发布」**
- 只能是「转人工」，且 `unknowns` 必须写明「规则库对本品线/本语种覆盖率不足」

### 约束 4：证据必须逐字可核

- `fragment` 必须是**原文的连续子串**，不允许概括、翻译、改写
- 判定时必须能 `assert fragment in original_text`
- 核验失败 → 该条判定直接作废，不得降级使用

> 依据：昨天审计发现的真实事故 —— 一处引文问题不是编造，
> 而是**折行被拼平**（`规范-审核规则库完整设计.md` 附录 C.3）。
> 逐字核验是唯一能挡住这类问题的机制。

### 约束 5：每一次判定产出可回放的 receipt

```yaml
run_id: RUN-BP-20260916-001
input_sha256: 0927fd58b0f8…        # 送审内容的指纹
rule_snapshot_sha256: 2a1a219a7e76… # 规则库的指纹
agent_version: shouheng@<commit>
model: deepseek-flash
outputs: [...]                      # 逐条输出
```

**没有 receipt 的判定不算发生过。**

## 为什么这些约束要写进 ADR 而不是代码注释

因为它们是**权责边界**，不是实现细节。
它们会在这些时刻被挑战：
- 「Agent 都 95% 准了，能不能让它直接过？」
- 「每次都转人工，我要 Agent 干什么？」
- 「这个不用查原文了，Agent 说是就是吧」

**ADR 的价值就是在这些时刻提供一个已经想清楚的答案，且不需要重新争论。**

## 后果

**正面**
- Agent 的输出天然可审计
- 不会出现「Agent 判错了但没人知道为什么」
- 与会议共识一致，不需要额外说服

**负面 / 必须接受的代价**
- **Agent 的"直接发布"建议数量会显著少于预期**（因为未命中一律转人工）
  → 这是刻意的：第一阶段目标是「不放过」，不是「少叫人」
- `unknowns` 会经常很长，看起来像 Agent 在推卸
  → 缓解：这是诚实，不是推卸。要的是可核验的边界，不是好看
- 人工复核工作量在第一阶段**不会下降**（甚至略升）

## 待 Owner 确认的问题

1. **是否接受「未命中规则时必须转人工，不能直接发布」？**
   这会让第一阶段 Agent 的"自动化率"数字很难看，但能避免漏放。
2. `unknowns` 不允许为空 —— 是否接受？
3. 人工复核工作量在 P0 阶段不下降，是否可向业务侧交代？
4. 约束 2 中「Agent 不能改人的字段」，是否需要在飞书侧用**字段级权限**强制
   （而不是靠工具层自觉）？
