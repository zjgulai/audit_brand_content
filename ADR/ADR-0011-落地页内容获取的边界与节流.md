# ADR-0011：落地页内容获取的边界与节流 —— 「持续监测」不能建立在朴素爬取之上

- 状态：`proposed`（开发者执行中确立，待 Owner 确认是否纳入常态化监测）
- 日期：2026-09-16
- 决策者：开发者（获取边界、节流参数、存储口径）；Owner（是否常态化）
- 依赖：ADR-0001（双账本）· ADR-0002（记录级溯源与内容指纹）· ADR-0005（工具只补证据）
- 触发：批次 C「落地页内容获取实测」

## 一、决策

1. **只读**。不发 POST/PUT、不带 cookie、不登录、不提交任何表单。
2. **robots 逐条判定**。抓取前先取该域名 `robots.txt`，被 `Disallow` 的 URL
   记为 `robots_disallowed` 且**不发请求**。本批 92 个 URL 实测被禁 0 条。
3. **三层自适应节流**：全局请求间隔 · 同域名间隔 · 429 后的指数惩罚（尊重 `Retry-After`）。
   三层缺一不可，理由见 §二。
4. **熔断**。连续 N 个 URL 失败即退出并落盘，**不把抓取变成压测**。
   未尝试的 URL 记为「未尝试」，**不记为失败** —— 这两件事在报告里必须分开。
5. **内容寻址存储**。原始响应按 `sha256` 命名 gzip 落 `_evidence/`，
   报告只引用可复核片段 + 指纹（ADR-0002）。增量落盘，长任务被中断不丢已抓部分。
6. **本批次只做获取与提取，不做判定**（ADR-0005）。
   提取出的 `claims` 是「页面上出现了哪些声明性表述」的**清单**，
   不是「这些声明是否合规」的结论。
7. **内容指纹建立在「提取后的正文」上，不建立在原始响应上。**
   这条是对 ADR-0002 的实现口径补充，依据见 §二之三。

## 二、节流参数是测出来的，不是拍的

第一次抓取只做了「同域名间隔 1.2s」。结果：

| 观察 | 读数 |
|---|---|
| 前 27 个 URL | 全部 200 成功 |
| 第 28 个 URL 起 | **全部 429**，返回 Cloudflare 的 `Verifying your connection...` 机器人验证页 |
| 最终分档 | 成功 **28** / 被拦 **63** / HTTP 500 **1**（共 92） |

**根因**：限制是**按来源 IP** 施加的，而「同域名间隔」在跨域名时形同虚设 ——
`au` / `ca` / `de` / `es` / `fr` / `uk` 各自等 1.2s，出门却是同一个 IP，
实际速率是域名数的倍数。约 40 次请求后触发防护。

**续抓（全局 6s 节流 + 快速失败）**：同一批 64 个 URL，**64/64 全部成功**。
于是整批 92 个 URL 的最终结果是 **92/92 成功**。

> **同一个站点、同一批 URL、同一份 User-Agent，成功率从 30.4% 变成 100%，
> 唯一变量是节流策略。**
> 这是本批次最重要的一条结论：**「内容获取成功率」不是站点属性，是获取策略的属性。**
> 任何把它当站点属性汇报的数字都是错的。

**一处被这轮推翻的判断（留档，因为它差点进了报告）**：
续抓途中观察到 `es.momcozy.com` 的产品页返回 HTTP 500、`.js` 端点返回 429 挑战，
一度判断为「与速率无关的持续错误」。续抓完成后该域名产品页**全部 200**。
**500 也是限流的副作用**，不是站点故障。
教训：**在限流未完全冷却时观察到的「站点错误」，先假定是自己的问题。**

## 三、内容指纹：不能建在原始响应上（ADR-0002 的实现口径）

验收器 V4 抽检重抓时，**3/3 的页面原始 HTML 指纹都变了**。查清原因后是新发现的坑：

| 差异内容 | 形态 |
|---|---|
| Shopify 内嵌的每次请求唯一 `reqid` | `<script id="__st">var __st={…,"reqid":"339c19df-…-1789545921",…` |
| 埋点/事件监听脚本 | `<script data-source-attribution="shopify.event_observer.bootstrap">` |

每个页面只有 9–14 行不同，字节数几乎不变（990,837 → 990,837）。
**页面内容没变，变的是每次请求都不同的追踪标识。**

**对照实验：**

| 指纹建立在 | 结果 |
|---|---|
| 原始 HTML 的 sha256 | **3/3 变化** —— 不可用 |
| **提取后正文**的 sha256 | **3/3 逐字节一致** —— 可用 |

**决策**：本项目所有「内容指纹」一律对**提取后的正文**计算。
理由不只是「更稳」—— 对原始响应做哈希会让 ADR-0002 想回答的那个问题
（「上周读到的这条，现在还是不是同一条」）**永远答不了**，
因为所有页面每次看都显示「变了」。

**这个坑不测就发现不了**，所以它被固化成验收项：
`tools/verify_landing.py` 的 V4 同时测两种指纹并分别报告。

## 四、这条 ADR 真正想固定的事
法务文档 §（一）2 把「已发布内容自动监测」定义为：

> 系统定期执行 + 法务通过【内容扫描】入口按需发起 …… 识别新增/修改内容，进行风险检查

本次实测给出的硬约束是：

> **在 92 个页面的量级上，朴素 HTML 抓取就已经会被防护拦住。**
> 那么「定期自动巡检整个官网 + 多地区站」不可能建立在朴素爬取之上。

三条可选路径，必须在承诺「持续监测」之前选定（本 ADR 不选，登记为遗留）：

| 路径 | 说明 | 代价 |
|---|---|---|
| **放慢** | 全局间隔提到安全水位 | 92 页 ≈ 十几分钟；全站 × 多地区站不可行 |
| **浏览器渲染** | 真实浏览器过 JS 挑战 | 资源重、慢、需维护；但能过挑战 |
| **结构化来源** | Shopify 商品端点（`/products/<handle>.js`）等 | 覆盖不到博客/集合页/营销页；仍需授权与合作 |

本次实测的一个副产品支持第三条：**结构化端点 32KB / 293ms，
HTML 1.6MB / 1795ms —— 体积差约 50×，耗时差约 6×**。
但它同时**也被同一套防护拦**（`es.momcozy.com` 的 `.js` 拿到 429 挑战），
所以它降低的是带宽与解析成本，**不自动解决访问权问题**。

## 五、边界（本 ADR 明确不覆盖）

1. **不做定时监测**。本 ADR 只固定「抓取行为本身」的边界，不含调度、告警、变更检测。
2. **不定义判定**。拿到内容之后判什么、怎么判，属于批次 A/B。
3. **不含 Amazon**。样本里那 1 条 `www.amazon.de` 照抓照报，但 Amazon 需要另一套策略，
   不在本 ADR 的适用范围内。
4. **不承诺覆盖率**。本 ADR 不主张「抓到的就是全部对外内容」。

## 六、遗留（待决）

1. **「持续监测」走哪条路径** —— 放慢 / 浏览器 / 结构化来源，需 Owner 与法务共同决定。
2. **节流参数是否足够保守** —— 当前 6s/请求是通过值，但它是在「已被拦过一次、
   随后冷却」之后测的，**稳健水位可能更高**；本批次无法回答「多久会被再次拦住」，
   因为只跑了一轮。要回答它需要一次**跨小时的持续速率实验**，那不该拿生产站点做。
3. **`www.amazon.de` 那 1 条**仍走不通朴路径，需单独评估 —— 但它在本批 92 个 URL 里
   占 1 条，不影响主结论。
