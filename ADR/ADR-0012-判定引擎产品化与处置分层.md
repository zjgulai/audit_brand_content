## 一、决策

1. **`judge(text, product_line=…)` 是判定引擎对外的唯一稳定入口。**
   返回固定契约：判定 / 命中规则编号 / **位置** / 原文片段 / 降级或放行证据 /
   规则与词表版本 / 边界声明 / 处置层 / 回执。
   `Engine.assess()` 保持为内部实现，不再是产品接口。

2. **每次判定都留回执**（ADR-0005 约束 5）。回执**不含原文与片段** —— 见 §三之三。

3. **规则与词表版本由制品内容指纹派生，不由人填写。**
   `engine-manifest.json` 记录四个判定制品的 `sha256`，`engine_version` 是它们的确定性折叠。
   制品变了而版本没变，在结构上不可能。
   **代码另算一个 `code_version`** —— ADR-0005 约束 5 把回执字段列成
   `rule_snapshot_sha256` **与** `agent_version` 两项，不是一项（见 §三之四）。

4. **豁免带的方向由规则自己声明。** `downgrade_band.effect` 的箭头右侧就是落点：
   落 `auto_pass` → 从放行带取词；落 `manual_review` → 从降级带取词。
   代码不再硬编码任何一条 `effect` 字符串。
   ★ **2026-09-16（D9）细化到逐词**：`keyword_effect_overrides` 允许给带内**单个词**
   另写 effect —— 因为同一个带里的词强度可以不同（`FDA cleared` 是器械层状态，
   `FDA registered` 是企业层注册）。原则没变（方向仍由规则里的字符串声明），
   只是粒度由「每条规则一个」细到「每个词一个」。两个带同现时**降级优先**（保守）。

5. **命中位置与原文片段是契约的一部分，不是可选装饰。**
   `matched_text` 恒为原文连续子串，且 `source_text[start:end] == matched_text` 可断言
   （ADR-0008 §四 的「逐字可核」）。

6. **处置层映射是一张**数据表**，所有权在法务。**
   `disposition-layers-v1.json` 定义四层与落点；引擎读表，不内建语义。
   改表即改处置，不发版。
   ★ **2026-09-16 修正两处**（D5 / D8）：层级由 4 个变为 **5 个**（新增 `DP0 不可判`），
   ID 由 `L1–L4` 改为 `DP1–DP4`；并新增 `preconditions`（前置条件先于落点与升级）
   与 `mapping.*.outbound`（结论的**出口**：谁要知道、怎么写、能不能申诉）。
   ★ 但**表级 `status` 不再替每一行背书**：每个 mapping 行 / 层级 / 前置条件都必须写
   `$decision` 点名一条台账决定，表级 `ratification_scope` 把「法务确认的」与
   「Owner 决定的」分开列，由 V24 逐项核对。原因见 §4.5 开头。

7. **匹配原语只有一份实现。** `matcher.py` 是唯一入口；`score.py` 与 `judge.py`
   都消费它，不各自实现。

8. **结论必须带出口**（D6 / D10）。
   每个 disposition 的 `mapping` 行可声明 `outbound`：`must_reach`、通知模板、
   禁用语、以及（拦截方向）完整的申诉块（入口 / 责任人 / 时限 / 撤销依据 / 升级对象）。
   `judge()` 在 `verdict.layer.outbound` 与 `receipt.obligations` **两处**输出 ——
   判定结果是一次性的返回体，回执才是长期留存的账。
   ★ 这条补的是 D1 授权里唯一没付的那笔账：`human_must_see=false` 说的是
   「拦截生效前不需要人看」，**不是**「提交人不会知道」。而今天两者事实上等价。
   ★ 没有出口声明就返回 `None`，**不合成一个默认出口** —— 合成的默认出口会让
   「没人负责通知」看起来像「已经通知了」。

9. **无文案输入走独立通道**（D5）。
   `preconditions` 在落点与升级**之前**判：文本去空白后为空 → `DP0`，
   不进空白清单、不占审查产能、不一定升 DP4。
   ★ 这一步在升级之前判是必须的：一段没有文本的输入不属于任何主题，
   谈不上「跨主题共现」。顺序反过来，无文案记录会先被升级规则捞走，
   于是 59 条空记录会顶着一条它们不满足的升级理由进法务终审。

## 二、决策 4 的理由：修的不是「没接上」，是「谁决定方向」

盘点实测的原状：

| 事实 | 位置 |
|---|---|
| `vocab.py` 提供 `pass_of()` | `vocab.py:64-65` |
| **全仓无消费者**（只有定义、组装、一处打印、一处体检） | `grep pass_of` |
| `Engine.assess` 只调 `downgrade_of()` | `score.py:127` |
| 3 条 `target=auto_pass` 的规则**降级带全空** | `T6.1` / `T2.2.quiet` / `T2.2.suction` |
| 那两条 `→ auto_pass` 分支因此不可达 | `score.py:197-200` |
| 而 `main()` 仍打印「放行带 8 词次」 | `score.py:439` |

**看到「放行带 8 词次」极易以为放行在生效。** 这是本缺陷真实危害：不是崩溃，是让人以为一切正常。

第一版修法我写的是「把 `pass_of` 接到 `assess` 里」。**这是错的** —— 它把方向判断留在了代码里。
正确的修法是问：**谁有权决定这条规则的落点？** 答案在 ADR-0008 §三 的分工表里：

> 「降级后的处置等级 ✅ 法务 定义 | ❌ 开发者」

而方向**已经写在规则文件里了**：`downgrade_band.effect` 的箭头右侧。
`"auto_reject → auto_pass"` 这个字符串就是法务的声明。代码要做的是**读它**，不是复述它。

所以 `band_hits()` 按 `band_target(rule)` 选带，`assess()` 按 `band_target(rule)` 定落点。
副作用：**法务改一个字符串就能改处置等级，不需要开发者改代码。** 这与决策 6 是同一件事的两个面。

## 三、三项技术取舍，及其代价

### 3.1 位置：算得出，但可能**不敢报**

`_find_literal` 一直在算 `(start, end)`，只是被丢掉了。恢复它有一个陷阱：

```
tl = text.lower()          # 用来匹配
text[start:end]            # 用来切原文
```

`'İ'.lower()` 是 **2 个字符**。此时小写串的下标与原文下标不再一一对应 ——
用小写串的偏移去切原文会**静默切错位置**，不抛异常，只给一个看起来合理的错片段。

**决策**：`matcher.lower_offsets_align()` 先判等长。等长走恒等映射（99.99% 的情况）；
不等长则回原文重新搜（`re.escape` + `IGNORECASE`）；**再失败就报 `position: null` 并给出成因**。
宁可少报位置，不可错报位置 —— 一个错位置比没有位置更坏，因为它看起来是对的。

### 3.2 词干 ≠ 原文：这个差值必须显式暴露

前缀匹配下，规则里的词干常常不是原文的写法：

```
原文   Painlessly pump with high efficiency
词干   painlessly / painless
```

旧实现只回词干。下游拿 `painless` 回原文搜，**搜不到** —— 而它不会知道自己搜错了。
新契约两样都给，并且在顶层写明二者可能不同。实测 355 处命中，**0 处片段不变量违反**。

### 3.3 回执不落原文：一个必须说清的代价

ADR-0008 决策 2 已定「RSA 完整素材不落库」。回执是**长期留存**的审计日志，
往里面写广告原文，等于用另一条路径把已决定不落库的东西落库了。

**决策**：回执只存 `input_sha256` + 版本 + `verdict_digest`。

**代价（必须说清）**：**光看回执无法还原当时判了什么。** 要复核必须同时持有原文。
这是「不落库」决策的直接代价，不是实现疏漏。

`verdict_digest` 是本 ADR 新增的：只记输入的回执**无法证明当时判出了什么** ——
同一个输入在不同版本的规则下会得出不同结论，而回执必须能钉住结论本身。

### 3.4 数据版本与代码版本必须分开 —— 这是 ADR-0005 自己漏掉的一半

第一版只做了数据指纹：`engine_version` = 规则 + 词表 + 主题树的哈希。
**改一行 `judge.py`，`engine_version` 纹丝不动。** 而契约字段的形状、聚合的次序、
边界声明的措辞全在代码里 —— 代码变了，「同一条判定」的含义就变了。

回执因此只答得了「哪版规则」，答不了「哪版代码」。ADR-0005 约束 5 列的字段清单
本来就把两者分开写了：

```
run_id / input_sha256 / rule_snapshot_sha256 / agent_version / model
                                     ↑ 数据            ↑ 代码
```

**决策**：`engine_version`（数据）与 `code_version`（6 个 .py 文件的哈希）分离，
两者都进回执，**不合并成一个数** —— 合并之后就再也分不出「是规则变了还是代码变了」。

实测（验收 V1d/V1e）：`engine_version = f516c14c1a2284fb` · `code_version = 392ed34e34f86ad8`。
改一行契约代码 → 只有 `code_version` 变；加一个规则词 → 只有 `engine_version` 变。

### 3.5 审计日志必须分得出「测试」与「真判定」

实施过程中踩到的：开发期的验证调用把三条记录写进了正式账本，
**而账本当时没有任何字段能把它们标出来**。事后才发现，说明字段本来就不够。

**决策**：回执带 `origin`（`cli` / `batch` / `shouheng` / 其他）。
已写入的三条开发期记录**保留并补记 `origin=dev-batchA`**，不删除 ——
删审计记录比留一条标注过的更坏。补记本身也在记录里写明是事后补的。

### 4.1 处置层映射（`disposition-layers-v1.json`）

**五层**（2026-09-16 · D8 把 ID 从 `L1–L4` 改为 `DP1–DP4` 并新增 `DP0`）：

| disposition | 落层 | 机器可终结 | 存量 291 条实测 |
|---|---|---|---|
| （无文案输入，PRE-001） | **DP0 不可判（无文案格式）** | ❌ **机器不得终结** | **59 条（20.3%）** |
| `auto_reject` | DP2 工具预审（**拦截**） | ✅ 仅在拦截方向 | 67 条 |
| `manual_review` | DP3 人工复核 | ❌ | 31 条 |
| `auto_pass_with_note` | DP2 工具预审（附注放行） | ✅ | 3 条 |
| `auto_pass` | DP1 业务自审（退回提交人） | ❌ | 0 条 |
| `catch_all`（零命中，**有文案**） | DP3 人工复核 | ❌ | **100 条（34.4%）** |
| 升级 ESC-002（`manual_only` 规则） | **DP4 法务终审** | ❌ | **31 条（10.7%）** |

**实测处置层落点**：DP0 = 59（20.3%）· DP1 = 0 · DP2 = 70（24.1%）·
DP3 = 131（45.0%）· **DP4 = 31（10.7%）**。逐项见 §5.3.2。

★ **ID 为什么不能叫 `L`（D8）**：同一份判定结果里同时出现两个「L」命名空间 ——
`verdict.severity = "L4"`（规则风险等级）与 `verdict.layer.id = "L2"`（处置层），
而两者**语义相反**：severity=L4 是「这条规则最危险」，layer=L2 是「机器可以自己拦」，
且一条 severity=L4 的红线规则产出的正是 layer=L2。字段都叫 L、数字还不一样，
任何按字符串匹配的下游都可能取错，取错的后果是双向的。
`DP` 前缀实测零占用；风险等级 `L0–L5` **一字未动**（它来自 §4.2.1 的六档校准并写进 26 条规则，
改它才是贵的那个）。V16e 断言两个命名空间前缀不同。

★ **最需要法务注意的一条**：`machine_may_finalize` 的方向是**单向**的 ——
机器可以独立**拦截**（错了只是少发一条广告），不能独立**放行**（错了是违规上线）。
这不是实现偏好，是 ADR-0005 约束 2 的直接后果。
DP0 上这条同样成立且更硬：**机器不得判「这条不可判」** —— 否则它获得了一条把内容
移出审查的通道，而那正是约束 2 要防的绕过，只是换了个名字。

**★ 2026-09-16 更新：法务已确认 D1–D4，本表 `status=ratified`。**
但表级 `status` **不再替每一行背书** —— 第二批之后改成逐项记账，见 §4.5 开头。

★★ **Q7 的原前提是假的，而且假得结构性。** 原写法说 `T9.objective-parameter` 的
`evaluability=manual_only`「一旦命中就会被 ESC-002 升到 DP4」，今天 0 命中所以无人察觉。
实测：T9 的 `match.keywords` 与 `match.patterns` **都是空数组**、`topic_only: true`、
`is_modifier: true`（22 个白名单词已按 ADR-0008/0009 迁到 `whitelist-v1.json`）；
`Engine.__init__` 把 modifier 放进 `self.modifiers`、**不进 `self.rules`**，而命中只由 `self.rules` 产生；
ESC-002 的判据是 `hit.evaluability`。**没有命中就没有 evaluability —— 这条路径对 T9 不可达**，
不是「今天恰好 0 次」。★ 真正的风险在覆盖面，不在 T9：
**DP4 的 31 条 100% 来自 ESC-002**（`T7.1` 16 / `T3.2` 14 / `T7.2` 2），
其中 **13 条原生 `auto_reject`** —— 升级把它们从 DP2（机器可独立拦截）挪到了 DP4，
等于**暂停了自动拦截**。关掉 ESC-002 的反事实：DP4 31 → 2，DP3 131 → 149，DP2 70 → 81。
重写后的 Q7 与实测数字见台账 `$decision_queue`。

**Q1 的量化后果（法务已知悉并接受）**：存量 291 条中 **67 条（23.0%）会被机器独立拦下**
（另有 13 条同判 `auto_reject` 但被 ESC-002 升到 DP4）；按本档规则级 precision 0.970 计，
**约 2 条/批是误拦**。

### 4.2 放行带的杀伤力：需要法务确认语义

**存量 291 条上，放行带触发 0 次**（没有一条同时含判险词与放行词）。
但构造用例证明它会响：

| 输入 | 结果 |
|---|---|
| `FDA approved and FDA cleared breast pump` | `T6.1` `auto_reject` → **`auto_pass`** |
| `Whisper quiet motor, with a quiet mode` | `T2.2.quiet` `manual_review` → **`auto_pass`** |

★ 需要裁定的是第一个：**「FDA approved」本身是错误宣称，即便同一段文字里也出现了正确的
「FDA cleared」。** 规则现在声明的 `effect` 是 `auto_reject → auto_pass`，本 ADR 按声明执行。
若法务认为不正确，改法是把该规则的 `effect` 改成 `auto_reject → manual_review`（一次字符串修改，无需发版）。

**★ 2026-09-16 裁定：放行（维持原语义）。** 规则与带的落点未改。附带做了两件事：

1. **引用复核**：`21 CFR 807.97` 的原文是「依 510(k) 提交并获实质性等同认定，
   **不表示**官方对该器械的批准」，且任何造成「因符合上市前通知要求而获官方批准」印象的表述属误导
   （[eCFR §807.97](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-H/part-807/subpart-E/section-807.97)）。
   这条支持的正是本规则的方向：`cleared` 与 `approved` 是两个不同的法定状态，
   把 cleared 说成 approved 才是违规。**引用成立。**

2. **把「同现即放行」的字面后果写进规则文件**（`T6.1` 的 `$decision`），因为它是**文本级**的：
   带词出现在同段文本的**任何位置**即生效，与距离无关。下列三行今天全部判 `auto_pass`：

   ```
   FDA approved breast pump. FDA cleared.                          → auto_pass
   FDA approved. Our factory holds FDA registration (FDA 注册).    → auto_pass
   FDA registered facility. FDA approved device.                    → auto_pass
   ```

   `FDA approved and FDA cleared` 与 `FDA approved. Also, our factory is FDA cleared.`
   在今天的实现里**结果完全相同**。记下来不是异议，是为了让这个后果有具体形状 ——
   否则「同现即放行」听起来像「两句话说清楚时才放行」。
   若法务认为不可接受，改法是加**邻近窗口**（带词须靠近命中词才放行），不是改词表。

**★ 由此新增一个待决问题 Q6**：`FDA registered` / `FDA 注册` 与 `FDA cleared` 是否应同处一个放行带？
FDA 自己的表述是注册（establishment registration）**不表示**批准、许可或授权，
而 `cleared` 是**器械层**的状态 —— 两者强度不同，今天却同为放行词。
D2 问的是 `cleared`，D3 问的是登记位置，**这一格是回答前两个问题时没覆盖到的**。
三个可选方案（维持 / 单独降为人工 / 加邻近窗口）写在台账 `Q6`。

### 4.4 品线维度：法务不裁定，转产品（D4）

**问题**：哪些规则**只对特定品线**成立？（需要给规则加 `product_lines: [...]`）
**法务回答**：「**不知道，这个要看产品本身**」。

这个拒答是对的，且理由值得记下：法务定义**表达的风险**，产品知道**这个品线上会不会出现这个表达**。
「这条规则在婴儿车上会不会触发」不是法务能单独回答的问题。

**Owner 由法务改为产品。** 机制保持「已就绪、数据未填」，未擅自填入任何取值。

**三个拦路的事实**（都在动手前先量了）：

1. **存量语料是单品的**：291 条里 289 条品线=吸奶器、2 条为空。
   所以「按品线过滤」这个能力**在现有语料上无法被验证，也无法被证伪**。
2. **公司里没有一份权威品线表**：9 张业务表各有一套取值（吸奶器 / 婴幼儿 / 喂养 / 喂养电器 /
   家纺 / 服纺 / 功能性服纺 / 家居 / 护肤 / 多品线），且同一件事三种编码
   （标量 `"家纺"`、数组 `["家居","家纺"]`、占位符 `"无法归结到品线"`）。
3. **因此今天填 `product_lines` 是有下行风险、没有上行收益的**：对 289 条吸奶器零影响，
   却可能因一个错字**静默删掉一条规则**（见下）。

**★ 加的两道硬防护**（`product-lines-v1.json` · `$unknown_value_policy`，验收 V23b–V23e）：

| 情形 | 行为 | 为什么 |
|---|---|---|
| 调用方传入不在取值域内的品线（如 `"吸奶器s"`） | **不过滤**，并在边界声明里点名 | 按未知值过滤会让**所有**声明了品线的规则静默消失 —— 拼写错误变成一次没有提示的漏报 |
| 规则声明了不在取值域内的值 | 判定里逐条点名「漏报成因」，验收器红 | 这是收窄时的错字，后果是该规则在预期品线上不生效 |

★ 第一版这一项写的是「传了品线 = 判得更准」的文案，那等于把「支持但没填」包装成能力。
现在边界声明逐字写明**到底滤没滤、为什么没滤**。

**★ 证据：法务说不裁定的那一格，是可以先量一遍的。**

- *构造演示*（机制上确实会发生同形异义）：`超强吸水，柔软亲肤的四件套`（家纺）
  → 判 `T2.2.suction-claim`（**吸力夸大**），命中词 `超强`。同型：家居「超强承重」、
  婴幼儿「极致呵护」、护肤「超强补水」、家居「静音风扇」→ 噪音主张。
- *代理语料实测*（`tools/measure_cross_line_homographs.py`，1914 条真实文章标题/关键词）：
  **5 条规则在「其他品线」文本上产生命中** —— `T7.1`（`新生儿`，64 处）、
  `T1.1`（`treat`→`Treatment`，36 处）、`T2.1.2`（3 处）、`T5.1`（1 处）、`T3.2.lactation-consultant`（1 处）。

**猜出来的风险点与量出来的风险点不是同一批**：构造演示里最像问题的是 `超强`/`静音`，
而真实语料里一次都没命中它们；真实发生的是 `新生儿` / `treat` / `pain relief`。

**★ 一个必须对产品说清的代价：品线收窄不减少人工量。**
家纺的「超强吸水」被收窄后，不再判「吸力夸大」，而是落进 CATCH-ALL → **仍是 L3 人工复核**
（标签从「误报」变成「疑似规则空白」）。变的是**标签的语义正确性**，不是工作量。
若目标是减少人工，该做的是 `B 规则补宾语`（`超强` → `超强吸力`），而那是法务改词。

**★ 归属只有一个书写位置。** 品线归属写在 `product-lines-v1.json` 的 `assignments`，
**不写在 `rules-v1.json`**：规则语义的 Owner 是法务，品线归属的 Owner 是产品，
让两个 Owner 改同一个 1269 行的文件就是在制造第 4 次「两处真相」
（前三次：`安全词` 与 `检测关键词` 同字段、匹配原语两份实现、白名单两条导入路径）。
引擎在装载时把 `assignments` 灌进规则对象；若在规则文件里发现 `product_lines`，
**直接硬失败**并指出该写在哪 —— 而不是让其中一处默默生效（那样两个人都以为自己的改动生效了）。
验收 V23h 用构造的越界写法证明这道硬挡确实会响。

**交给产品的产出**：`research/governance/品线维度-待产品确认.md`
（问题 + 机制 + 证据 + 三种做法的代价）+ `品线确认表.csv`（**只问有证据的 7 条规则 × 10 条品线 = 70 格**）。
★ 没有生成 26×10=260 格的全矩阵：没有证据支撑的格子交出去不是问题，是作业，
而且**填错比不填更坏**。

### 4.5 第二批：D5–D11（2026-09-16，Owner）

**先说为什么第二批要单独立一节，而不是接着 §4.1–4.4 往下写。**

第一批落地时，本表用**一个表级 `status`** 承载全部权威性：`ratified` 表示「法务确认过」，
并且写了一句规矩 ——「之后任何一次改动都会让 status 退回 proposed」。

这句话在实现上**做不到**：表里没有任何代码能判断「改了没有」，只有人记得。
而一个靠人记得的规则，在第一次忘记时就开始撒谎。第二批让它立刻暴露了：

| 这次改的东西 | 谁定的 | 若按「一律退回 proposed」 |
|---|---|---|
| 层级 ID 拼写（`L`→`DP`） | Owner | 法务对 D1 的授权**一起作废** |
| 新增 DP0 与出口字段 | Owner | 同上 |
| 不改 | — | 等于拿法务的名义背书法务没看过的内容 |

**两种结果都是假话。** 一个是把已授权的映射说成草案，另一个是把 Owner 的决定说成法务的。

所以改成**逐项记账**：表级 `status` 只说「本表处于已确认状态」，
每一行 / 每一层 / 每条前置条件各自写 `$decision` 点名台账里的一条决定，
表级 `ratification_scope` 分列 `legal_confirmed` / `owner_decided` / `pending_legal_review`。
**「这一行谁定的」从此可以逐行查出来**，由 V24a–V24c 机检（点名不得悬空、归属不得串台）。

| **D23** | 站点侧**只记录、不送达**（Q17 选 D）：地址按决定留空，「（未定）」的语义从待办改成决定 | 0 条（只改「送不送」，不改「判没判」） | V41a–V41d（判据未改，含义已变） |
| **D24** | `www.amazon.de` 归独立站侧 Rikka（Q18 选 B）：全表 10 行首次全部有主 | 0 条（只改路由目标，判定一字未变） | V43a–V43b |

**这八条里有六条在存量语料上不可见。** 这不是巧合，是这批决定的性质：
它们修的是 DP1 出口、DP0 路由、法务产能、命名冲突、申诉通道 —— 全是**结构与出口**，
而存量语料只反映**判定结果**。所以每一组验收都配了构造正对照，
其中四组还配了**反向对照**（把配置抽掉，断言必须变红），用来证明这些检查不是恒真的：

- V25d：删掉 `auto_pass.outbound` → 出口真的变 `None`（不是凭空合成一个默认出口）
- V25e：往通知里注入「本判定已通过」→ 禁用语检查真的会红
- V27c：打开 ESC-003 → 同一条多主题文案真的从 DP2 变 DP4（开关是活的）
- V29e：删掉 `keyword_effect_overrides` → `FDA registered` 真的回到 `auto_pass`

★ 只断言「现在是绿的」，等于什么都没断言。**一个永远为真的检查，与没有检查的区别，只在于它让人以为检查过了。**

#### 4.5.2 DP0：59 条不属于任何审查队列的记录

D5 里最值得单独写下来的一条，不是拆分本身，而是**拆出来的那 59 条是什么**：

| 事实 | 值 |
|---|---|
| 文本为空的记录 | **59 条 / 291（20.3%）** |
| 广告类型 | **全部是 Google `产品广告`（PLA / 商品 Feed 广告）** —— 结构上不含 Primary Text / Headline |
| 其余 7 种广告类型 | 0 条空文本 |
| 近 7 天花费 | **$15,747** |
| 仍 ENABLED | 57 条 |
| 今天被记成 | `风险等级=合规·绿` / `处理状态=无需处理` |

三件事因此成立：

1. **「catch_all = 规则空白」这个等式不成立。** 159 条里有 37% 是「没有东西可以覆盖」，
   不是「规则没覆盖」。真实的规则缺口压力是 **100/291 = 34.4%**，不是 54.6% ——
   把它算进缺口率，分母虚高、缺口率被系统性低估。
2. **把 159 条压给 DP4 是错的，而且错得看不出来。** 法务单量会从 31 涨到 190（6.1 倍），
   而其中 59 条没有文案可读。这批单的正确答案不是「要建规则」，是「这类格式文本引擎判不了」。
3. **`合规·绿` 的语义重载在这一格上有了具体形状。** 设计文档 §4.2 早已点名这个字段
   同时表示「确认合规」与「规则没覆盖到」；这里是它的第三种含义：**「没有文本可判」**。
   三种含义落成一个值，后果是这 59 条**花了 $15,747、57 条还在跑，而它们在账上是绿的**。

★ 但 DP0 **不是**「机器判它合规」。它 `can_finalize=false`：机器不得终结本层。
若允许机器自己判「这条不可判」，它就获得了一条把内容移出审查的通道 ——
那正是 ADR-0005 约束 2 要防的绕过，只是换了个名字。
出口通知的禁用语里因此特别加了**「合规」**二字。

#### 4.5.3 D9 与 D3 的关系：两个 diff 都对

D3（同一天）把 `FDA 注册` 从守卫表迁入白名单表，理由是它 `status=misrouted`、声明了却取不到。
D9 让它**回到降级通道**。看起来像 D9 撤销了 D3。**不是。**

- D3 修的是「**登记在哪张表**」（登记错了）；
- D9 定的是「**它该在哪个通道**」（语义归属）。

叠加后的状态：词**仍在白名单表**（可独立复核为真 —— 注册号可查），但它的**通道是降级**。
这正是白名单不变量 W3 早就写明的边界 ——「放行与降级是两个通道，不是一件事」。

★ 必须同时留在词表与规则两处，不能只留一处：**只看 D3 的 diff 会以为这个词被放行了；
只看 D9 的 diff 会以为 D3 被撤销了。两个 diff 都对，合起来才是完整语义。**

这次改动同时暴露了两个**假红**，都属同一个错：**判据跟着通道走，而通道有两个**。
`lint_whitelist` 的 W5a 与 W2 原来只看放行带，于是 `FDA registered` 一移入降级带就被报成
「死声明」和「没有受益人」。**假红比不检更坏：它训练人忽略这个检查。** 两项都已改为双通道判据。

#### 4.5.4 顺带发现的五处问题（不在原问题清单里）

1. **同步工具跑第二次会整表翻倍。** `migrate_vocab_to_lark.py` 用 `batch_create`
   无条件追加 —— 跑一次是对的，跑两次每次输出全是 ✅，而表里每行都有两份。
   实测后果：守卫表 174 行（85 词）、白名单表 56 行（30 词）。
   已在写入侧加闸门：**非空表拒绝写入**，重建必须显式 `--force`。
2. **验证工具比的是集合，所以看不见重复。** `verify_vocab_lark.py` 用
   `{词: 字段 for r in fetch(...)}` 建索引，同一个词的第二行被静默覆盖；
   它当时报的是「飞书 89 条 / 字段不符 0」，而真实行数是 174。
   **两条缺陷叠起来，「同步成功」在第二次运行时无法被自己的工具证伪。**
   现在它数行数、报重复、并让重复导致验证失败。（本次已 `--force` 重建为 85/30/4 并回读通过。）
3. **`judge.py --json` 曾不是合法 JSON**（人类可读输出混进 stdout）。已修。
4. **`lint_whitelist` 印出的数字与它自己算出的不一致**（写死的「14 词」vs 算出的 16 词）。
   最小的那种假账。已修。
5. **★ 我写下的「`T9.objective-parameter` 埋着一个升级通道」是错的，这里更正。**
   原写法：它的 `evaluability=manual_only`，一旦命中就会被 ESC-002 升到 DP4，今天 0 命中所以无人察觉。
   实测：T9 的 `keywords` 与 `patterns` **都是空数组**、`topic_only: true`、`is_modifier: true`；
   modifier 不进 `Engine.rules`，**永不产生命中**；ESC-002 读的是 `hit.evaluability`。
   所以那不是「埋着的坑」，是**一条不可达的死路**。
   ★ 值得记下的是它的形状：**一个写在制品里、语气确定、却从未被执行到的风险描述。**
   它与「跑一次对、跑两次错」是同一种病 —— 描述与事实之间没有检查。
   沿这条线测下去才看见真正的问题：ESC-002 的**覆盖面**比任何人事先以为的都大
   （DP4 的 31 条 100% 来自它，其中 13 条原本机器可拦）。已重写为 Q7。

## 五、后果

### 5.1 得到什么

- 任何新文案现在可以一句话判定，输出带位置、带证据、带版本、带边界。
- 「这条判定是哪版规则算出来的」今天答得了：`engine_version` + `rule_version` + `vocab_version`。
- 「谁把红线改成放行」查得出来：`disposition_declared` 与 `disposition` 的差值逐条留痕。
- 「本可降级但因守卫未接线而成了红线」以**具名词条 + 缺口成因**的形式出现在判定结果里。
- 守衡多了第 10 个工具 `judge_copy`（只读），群内可直接判定。

### 5.2 明确**没有**得到什么

- **品线维度：机制已就绪，规则数据未填。** 26 条规则里没有一条声明 `product_lines`，
  所以今天传任何品线都不产生过滤。**但这不是「不支持」** —— `Engine.rules_for()`
  已经会按声明过滤，法务给一条规则加上 `product_lines: ["吸奶器"]`，过滤立刻生效
  （验收 V17c/V17d 用注入声明证明了机制是活的）。
  规则侧口径：不写或写空数组 = 适用全部品线（默认，向后兼容）。
  ★ 这个区分是刻意的：「机制不存在」与「机制存在但你没填」长得一样，
  但前者永远不可能生效，后者只差一次数据录入。让调用方看得见区别，是本条的要点。
- **未接入批次 C 的落地页正文。** 能力已产出，通路未建 —— 落到谁、改哪边仍是未决的（**Q15**），
  但两侧责任人已经有了：文案侧 Roxie、页面侧 Rikka（`_data/site-owners.csv`）。
- **未覆盖图片 / 视频 / A+ 详情页。**
- **`evaluability=manual_only` 的 5 条规则仍然报出命中**，只是被升级到 L4。机器在这 5 条上不可采信。
- **零命中的三种成因（新表达 / 新语种 / 规则边界不清）仍不区分。** CATCH-ALL 只答「未覆盖」。

### 5.3 存量语料上的影响：**零**

改造前后 291 条的混淆矩阵**逐项一致**：P 0.970 / R 0.962 / F1 0.966 / CATCH-ALL 159 (54.6%)。

这不是「没改」——是**缺陷在存量语料上不触发**：

| 改动 | 存量语料上的触发次数 |
|---|---|
| 匹配原语重构（7275 次比对） | 差分 **0** |
| 放行带接线 | **0**（无一条同时含判险词与放行词） |
| 位置与片段补齐 | 355 处命中全部可核 |
| 未接线守卫提示 | **0**（43 条未接线守卫里只有 2 条在本语料出现，且目标规则均未命中） |

**所以「验收全绿」不能替代正对照。** 一个只在存量数据上验证过的修复，
与一个从没生效过的修复，在存量数据上**长得一模一样**。
三条正对照（放行带、near-miss 守卫、聚合取最严）都是构造用例，不是存量记录。

## 六、遗留

### 6.0 已修（2026-09-16）：分层表不在版本指纹里

原状：`disposition-layers-v1.json` 决定 `verdict.layer`，却**不在** `engine_version` 的任何一项里。
理由写的是「改表不用发版」—— 那句没错，但漏了一半：

```
法务按 Q2 把 catch_all 从 L3 改到 L4
  → 结论变了（verdict_digest 变）· 版本号不变（回执照样解析到「同一份配置」）
  → digest 证明「结论不同」，版本证明不了「为什么不同」
```

法务刚刚接管这张表、且它上面还挂着 4 个 open 问题 —— 这个漏洞正好落在最会被改的文件上。
已修：`disposition_layers` 进 `ARTIFACTS` 并单独给出 `layers_version`（进 `versions()` 与回执）。
「改表不用改代码」的性质不变：法务照旧直接编辑 JSON。

★ 顺带修掉一处**反方向的假话**：`judge.py` 里 `$table_note` 原先写死为
「在法务确认前不得作为业务承诺引用」。D1 确认之后这句话就反了 ——
把一份**已授权**的处置映射说成草案，同样是在骗读它的人。
现在它随 `status` 变（V21c 检查这个一致性）。

### 6.1 仍然遗留：`downgrade_band` 这个名字仍然骗人

决策 4 让代码**读**声明而不是复述声明，但字段名没改：

```
"downgrade_band": { "effect": "auto_reject → auto_pass" }
     ↑ 这个名字说它装的是「降级词」
       —— 而它同时装着放行词（T6.1 / T2.2.quiet / T2.2.suction 三条规则的词全在里面）
```

`rules-v1.json` 的 ADR 索引里这条被记为「第三处同病未解：把通道藏在字符串里」。
决策 4 解决了**行为**（方向不再由代码猜），没解决**命名**。

**没有现在改的理由**：改字段名要动 `rules-v1.json`（26 条）+ `vocab.py` +
`wire_whitelist.py` + `wire_context_guards.py` + `build_context_guards.py` +
`lint_whitelist.py`，且会让 `engine_version` 变化 ——
所有已发出的回执会指向一份不再存在的规则集。这是一次需要计划的迁移，不是顺手改的。

★ **这一条在 2026-09-16 之后不再那么可怕了**：`engine_manifest.py` 现在会在每次
`--write` 时把**正要被覆盖的** manifest 追加到 `_data/manifest-history.jsonl`，
并提供 `resolve_version()` 按 `engine_version` 反查历史。实测：现存 5 条回执
（全部指向 `f516c14c1a2284fb`）在四次重新固化之后**仍可逐条解析**。
「指向一份不存在的规则集」已经变成「指向历史里的一次快照」。
所以下一次迁移的公告成本从「回执作废」降为「回执指向历史」，可以做了。

**建议的迁移形态**（留给下一批）：字段拆成两个显式命名，`effect` 改为结构化两字段：

```json
"exemption_band": { "from": "auto_reject", "to": "auto_pass", "words_from": "whitelist" }
```

`words_from` 显式写明词从哪张表来 —— 这样「方向」和「词源」都是结构，不再是字符串。
迁移必须与一次 `engine_version` 冻结同时做，并公告回执的代际边界。

★ **2026-09-16 第二批之后，这一条的紧迫性又降了一档，但也多了一个新理由：**
D9 引入了 `keyword_effect_overrides` —— 通道落点现在是**三级**的（规则 → 词 → 表），
而承载它的字段仍然叫 `downgrade_band`。也就是说，**这个字段名比昨天更不准了**：
它现在同时装着放行词、降级词、以及逐词覆盖后的混合体。
建议迁移时一并把 `keyword_effect_overrides` 的键从「词」改为「词 + 通道」的结构，
避免出现「同一个词在两个通道里各有一条覆盖」这种只能靠代码次序决定的情形。

## 七、异议留档

1. **我不认为「`auto_reject` 允许机器独立拦截」应当由开发者写进默认表。**
   实测规则级 precision 0.970，即**约 3% 误报会被自动拦下**。误拦的代价是少发广告，
   漏放的代价是违规上线 —— 两者不可比，但也不该由我替业务选。已写进 §4.1，标 `proposed`。

2. **我不认为「四层」这个名字是确定的。** §4.1 的四层是开发者提议的，
   依据是 PRD 的「AI Agent 初筛 + 北美人工复核」两段 + R8-W3 §3.2.4 的权限分配表。
   若法务现有流程叫法不同，**请直接改 JSON 里的字符串**，代码会跟随。

3. **`verdict_digest` 不进 ADR-0005 约束 5 的原始字段清单，是我加的。**
   理由见 §3.3。若认为回执不应超出原清单，删掉它即可 —— 但那样回执就只能证明
   「我在某个时刻判过一段文本」，不能证明「我判出了什么」。

### 2026-09-16 追加（法务四项决定之后）

4. **`auto_reject` 已获授权独立拦截，但「可申诉」这项义务没有主人。**
   67 条/批会被机器拦下，约 2 条是误拦（按 0.970 规则级 precision 估），
   而这 2 条今天**没有任何通道回到人眼前**。我在台账里把它记成 `unmet` + `owner=待定`，
   而没有顺手做一个「申诉按钮」—— 申诉入口是流程与责任人的决定，
   开发擅自造一个只会制造一个没人负责的入口。**这是本次唯一没付的账。**

5. **`FDA registered` / `FDA 注册` 与 `FDA cleared` 同处一个放行带，我认为值得再问一次（Q6）。**
   FDA 自己的表述是注册**不表示**批准、许可或授权；`cleared` 是器械层状态，`registered`
   是企业层登记。两者强度不同却同为放行词，于是 `FDA registered facility. FDA approved device.`
   判 `auto_pass`。**这不是对 D2/D3 的异议** —— D2 问的是 `cleared`，D3 问的是登记位置，
   这一格是回答那两个问题时没覆盖到的。

6. **词干匹配对英文的成本还没有被承认过。**
   `matcher.py` 用前缀匹配（`treat` 命中 `Treatment`、`heal` 命中 `healthy`），
   理由写得很扎实（德语变格 `schmerzfreies`、法语阴性 `hospitalière` 会漏）。
   但代价全落在英文：在 1914 条其他品线真实文本上，`treat`→`Treatment` 命中 36 处，
   其中大多是**科普文章标题里的话题名词**，不是功效主张。T1.1 是 `auto_reject` + L4。
   **存量 291 条广告语料上这个成本实测为 0**（无一处靠后缀命中）——
   所以它不是存量缺陷，是**未来文案上的定向风险**，而恰好落在 D1 新授权的自动拦截方向上。
   若哪天真出现，修法是给关键词加"是否允许后缀"的开关，而不是取消前缀匹配。

    这份文件会被当成「有没有真的发过」的证据，**它若与真实送达混在一起，等于伪造一次送达** ——
    而本项目刚花一整轮在治「把声明当成事实」。V39g 断言它带标记、且与生产已推送记录无交集。

21. **两路派发不是「把报告拆成两个 CSV」，分界线选在「要不要先判」上。**
    D20 之后，C 批的发现变成两份带收件人的待办。分界不是严重程度，而是：
    **同一产品在不同地区站自报不同 mmHg/dB（甚至 de 写 CE、fr 写 FDA），无论以谁为准，
    至少有一个站是错的** —— 这一路不需要法务先判，可以直接核实；
    而「广告写了、页面没写」两种解释都成立（页面漏写 / 文案夸大），**改错方向会把对的改错**，
    所以先判再改。
    ★ 判据没有重写：两类问题的判据都直接读 `一致性分析.json`。在第二个地方重算同一个判据，
    就是本项目已经出过三次事的那种「两处真相」——V41a 因此断言两路与来源**逐条一致**。
    ★ 还有一处必须写下来：那 9 个跨 locale 产品里有 5 个**未检出**不一致。
    这是「未发现」，不是「已核实一致」（本批只比了 mmHg / dB / 认证词三类），
    这句话写进了路由 JSON 的 `$其余产品`，免得下一个人把「没报」读成「没事」。

### 2026-09-16 追加（第六批 D22 之后）

22. **Owner 给的是姓名 —— 而姓名不是地址；更要紧的是，我差点用一个恒真的扫描把它说成「查无此人」。**
    Q16 问的是 Rikka 的投递地址，回来的是一行「她的名字是：林建纯」。名字我已经有了，

    文档全文检索只能搜到「正文提到她」而没有实体 id —— 到这里都还是常规排查。
    ★ 真正该写下来的是下一步：我扫了全库 6000+ 条记录的 `created_by` / `last_modified_by`，
    报「零命中」。**报完才想起做阳性对照** —— 那两个字段在 list records 响应里**恒为 null**，
    扫描根本没有输入。「零命中」什么也没证明，而我当时已经准备把它写进结论了。

    ★ 顺带暴露的第二个缺口：`www.amazon.de`（`/dp/B0G1MW5TB6`，1 条 URL）那一行责任人写的是

24. **「暂不填」是一个决定，不是没做完 —— 而它必须长得像决定。**
    Q17 给了四条路（拉进群 / 她发一句话 / 授权通讯录只读 / 暂不填），Owner 选了 D。
    执行时最要紧的不是「不改表」，而是**改语义**：`（未定）` 原来是「等一个人填」，
    现在是「已经决定不填」。这两者在文件里长得一模一样，差别只在下一个读它的人会不会去催。
    所以三处一起改：`site-owners.csv` 的 10 行备注、`整改路由-页面侧.csv` 那 4 行的
    「★ 不可送达（**已决定，非待办**）」、以及 `整改路由.json` 新增的 `$delivery_mode`。
    ★ 最后一处是这轮最值钱的一小段：**两路的送达状态根本不一样** —— 法务侧经 Owner 转达（可送达 33 条）、
    站点侧只记录（不送达 4 条）。不写这一节，「站点侧没收到」会被读成遗漏；写了，
    它就是一个可核对的事实。**判据一字未改**（V41b 仍要求地址不可用时逐行写出「不可送达」），
    变的是它的含义 —— 这也是为什么这轮不需要动任何验收判据。

25. **代价要写在决定旁边，而不是等一个月后有人来问。**
    选 D 的实际后果是：那 4 条跨 locale 不一致（`momcozy-mobile-flow-…` 的 dB 在 ca/de/eu/uk 写 42、
    momcozy.com 写 48；`momcozy-wellness-1-…` 的认证词 de/es/uk 写 CE、fr 与主站写 FDA）
    **不会被任何人收到**。它们的价值只剩「记录在案、谁查都有」，而没有「有人被通知到」。
    ★ 这句话写进了 D23 的 `$what_this_costs`，而不是留在对话里 —— 一个只在会话里说过的代价，
    等于没有代价。同时写明 `$reversible`：把地址填进那一列就自动恢复，
    `deliverable` 判据只看地址形状，不需要改代码、也不需要新决定。
    **一个能便宜地反悔的决定，才敢被放心地做。**

26. **「（未定）」如果没指向任何未决项，它不是「等决定」，是没人接又没人登记。**
    `www.amazon.de` 那一行就是这样：D19 定了「广告账号 → Roxie、独立站 → Rikka」，而亚马逊站内商品页
    两边都不完全对口，于是当时写了「（未定）」。写出来是对的（比留空强），但它**没有指向任何题** ——
    于是它在表里安静地待着，直到这轮穷举时被我翻出来，才成了 Q18，Owner 选 B 归独立站侧（D24）。
    ★ 落地时顺手把地址列已有的那条纪律（V40b：地址要么可用、要么显式「（未定）」**并指向题**）
    原样搬到**责任人口径**上：V43a 要求每一行要么有主，要么这个空缺是可决策的未决项（指针必须真实存在）。
    反向对照做了两个方向（留空 / 悬空指针），并且**把该行临时还原成 D24 之前的样子真跑了一次** ——
    V43a 当场红了（`www.amazon.de: 责任人「（未定）」却没指向任何未决项`），恢复后立刻变绿。
    ★ 为什么要费这个劲：一条**为现状定制**的检查，和一条**当时就会红**的检查，
    外观完全一样 —— 差别只在有没有人让它红过一次。这是本项目第 7 次碰到同一个形状
    （前六次见第 16、17、22 条），也是第一次在**加检查的同时**就把历史状态复现出来。

27. **队列清空不等于没事可做 —— 它是这一轮结束、下一轮开始的分界。**
    Q1–Q18 全部 answered（D1–D24），0 项 open。按 D12 的约定，未决项只有一个书写位置，
    而这一次那个位置**是空的** —— 这是好事，也是唯一一次可以这么说的时刻：
    站点侧送不送达、亚马逊页归谁，都已经有明确答案，而不是悬着。
    下一批作答（比如法务对那 33 条给出判定）会带来新的未决项。**未决项随作答而增加，是机制在正常工作。**
28. **反向对照只在「有未决项」时才跑得动 —— 而队列清空是个好状态。**
    D24 之后 Q1–Q18 全部结案，验收当场崩了：V30e 用
    `next(q for q in _mut if q.get("status") == "open")` 取样本，队列一空就 `StopIteration`。
    换句话说，**这条守着 V30a 不是恒真的检查，自己是有前提的** —— 而那个前提在最好的状态下不成立。
    ★ 修法不是加个 `if` 跳过（「没问题时就不检查」正是本项目一直在治的病），
    而是让对照**自带样本**：拿任意一条带选项的（已答的也行）复制成 `open` 的变体再抽。
    现在它印出 `样本=Q7（当前 open 项 0 条）` —— 队列空着也照样证明判据会红。
    ★ 这是同一个形状的第 8 次（前七次见第 16、17、22、26 条）：**检查自身也有前提，
    而前提往往在「一切正常」时失效。** 区别是这一次它在唯一一次「队列清空」的好消息里露了头 ——
    如果当时我选择「先跳过这条，回头再修」，它就成功地把一个好消息变成了一个永久的盲区。
