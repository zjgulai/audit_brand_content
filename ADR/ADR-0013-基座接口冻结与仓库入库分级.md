# ADR-0013：基座接口冻结与仓库入库分级

- 状态：`accepted`（Owner 于 2026-09-17 经九道选择题逐条决定；**接受只代表设计决策已定，不代表已实现、已验收或可上生产** —— 见 `ADR/README.md` 规则 4）
- 日期：2026-09-17
- 决策者：Owner（ADR13-D1–ADR13-D9 全部由 Owner 选择，九条均采纳开发者推荐选项）
  开发者（分级的判据设计、`ContentUnit` 字段形状、同步契约的冲突语义）
- 依赖：ADR-0001（数据权威与双账本）· ADR-0002（记录级溯源与版本化）·
  ADR-0003（敏感样本分级准入，**`proposed`**）· ADR-0005（工具只补证据不替人过门）·
  ADR-0009（语境守卫独立成表 / 所有权分离）· ADR-0011（落地页内容获取的边界与节流）·
  ADR-0012（判定引擎产品化与处置分层）
- 触发：Owner 提出「先搭基座、等业务给 PRD 再做前后端联通」，并要求覆盖
  **多内容格式解析 / 需求文档治理 / 知识库 / skill** 四项。据此做了一次只读盘点。

> ★ 盘点过程中确认了一件**与规划无关、但改变排序**的事：
> **本目录不是 git 仓库**（`git rev-parse --show-toplevel` → `not a git repository`；
> `.git` 不存在，上级目录也没有；根目录无 README / 构建清单）。
> 也就是说 —— 14 个 ADR、161 项验收、291 条差分 0、四份验收脚本，
> **全部没有版本历史**。今天任何一次误改都不可回滚，
> 而「记录级溯源」正是 ADR-0002 的第一条地基。
>
> ★ 另一件在动手时才发现的事：**`git init` 这一刀本身会撞出安全问题**。
> 目录里同时存在真实凭据与浏览器会话数据（见 §三）。所以 ADR13-D7/ADR13-D8 不是「顺手加个
> `.gitignore`」，而是一条需要 Owner 单独拍板的入库规则。

## 一、决策

### ADR13-D1 · 第一刀 = 建版本控制 + 冻结两个接口

顺序不是偏好问题。**基座里只有两处「不做完就会在 PRD 到来时返工」**，
其余三处已经立好，PRD 到位后只做装配：

| 面 | 契约 | 今天 | 会不会返工 |
|---|---|---|---|
| ① 进 | `ContentUnit` + 解析器 | 文本已通；落地页有抓取提取但**未接引擎**；图片/视频 0 | **会** —— `assess(text: str)` 的签名容不下三种新形态 |
| ② 判 | `judge(unit) → Verdict` | **已建成**（ADR-0012） | 不会，只差一层适配 |
| ③ 供 | 权威源 + 版本 + 4 类知识库 | 品线维度机制就绪但**零条规则声明**；规则为本地手工 JSON；4 类知识库只有 1 类有料 | **会** —— PRD 到来后业务与法务要改规则 |
| ④ 出 | 处置五层 DP0–DP4 + 回执 | **已建成**（ADR-0012） | 不会 |
| ⑤ 证 | 版本控制 + 验收 + 度量 | 4 份验收脚本齐备 | **会** —— 无版本历史则不可回溯 |

因此 B0 只做两件事：**立版本**、**冻结①②③三面里会返工的两处**。

### ADR13-D2 · 飞书 Base 是规则与词表的唯一权威源，本地 JSON 是只读投影

- 方向**单向**：飞书 → 本地。本地不得回写权威源。
- 同步必须带**内容指纹**；指纹不一致而记录 id 相同 ⇒ **报错退出**，不静默合并、不取「较新者」。
- 依据：ADR-0001 已实测「飞书 API 无内容指纹、无 diff、无回放能力」，ADR-0009 已把
  「人写规则主 Base（app 只读）」与「app 维护机器词表 Base」分开。
- **本决定不新建 Base**：权威源已经存在 —— `_evidence/rulelib-live.json` 就是从飞书拉下的
  逐字快照（21 条规则，带 `record_id` 与全部字段）。B0 做的是把这次性拉取**固化成契约**。
- **投影仍入历史**（见 §三 L1）：正因为飞书没有 diff 与回放，
  本地副本的版本历史才是唯一能回答「上周那次判定用的是哪版规则」的地方。
  这不是冗余，是 ADR-0001 双账本在本层的具体含义。

### ADR13-D3 · 图片与视频先只做「文本化」，不作语义判定

- 图片：OCR 取图内文字 + 合成人像标记检测；视频：字幕/ASR 转写 + 关键帧 OCR。
- 产出统一进 `ContentUnit.verdict_text`，**复用现有 21 条规则**，不新增判定机制。
- 理由：今天**没有图片/视频的标注集**，多模态直接判定的精度无法度量 ——
  那会把「判不了」伪装成结论，正是本项目从第一天起拒绝做的事。
- 代价已写进 §四：图内**非文字**的违规（画面暗示、构图）本决定覆盖不到。

### ADR13-D4 · 4 类知识库从「措辞表达库」开始实例化

- 依据：存量 291 条里已现成提取出 60 个真实片段（`PMO/内容合规-阶段性复盘-20260916.md` §3.2），
  是四类中**唯一「今天就有料 + 直接提升引擎覆盖」**的一类。
- 其余三类（外部标准库 / 内部正负样本库 / 产品描述库）排在 ADR13-D4 之后，不阻塞 B0/B1。

### ADR13-D5 · 需求知识库的三条未决按「先记录不阻塞」收口

| 未决 | 处置 |
|---|---|
| `资源账号管理`（含密码，11 条） | **整体排除**（与 `research/kb/需求知识库-建设方案.md` 默认一致），理由写明：无脱敏方案前不纳管 |
| E/F/G/H 四条材料链接失效 | 记为**外部依赖**，不阻塞台账；等 Owner 补链接后单独补录 |
| 台账刷新节奏 | 定**定时**，且**排在谷时**（DeepSeek 官方线路峰时 ×2，见成本扫描结论） |

三条一律写进 `legal-decisions-v1.json · $decision_queue` 的书写位置，
不散落在方案文档里（该位置由 ADR-0012 · D12 收拢，本次沿用）。

### ADR13-D6 · skill 做成 DSH 技能包，任何 agent 可按规程调用

- 不采用「只扩守衡工具集」两条腿：那会让规程散在两处，
  而「同一判据写两处就会漂移」正是本项目已复发三次的病（ADR-0007 → 0008 → 0009）。
- 技能包与守衡共用**同一条验收命令**，不共用两份实现。

### ADR13-D7 · 仓库分三层，判据是「会不会被人改」，不是「大不大」

| 层 | 判据 | 处置 |
|---|---|---|
| **L1 入历史** | **人写的、会被改的、改了要能回滚的**；以及「权威源无 diff/无回放」时，唯一能答版本问题的本地投影 | `git add` |
| **L2 入盘不入历史** | **机器生成的、可复算的、内容寻址的、别人管的** | `.gitignore`，文件保留在盘 |
| **L3 永不入盘** | **凭据**与**会话数据** | 移出项目目录 |

→ 逐条清单见 §三。

### ADR13-D8 · 凭据移出项目目录

`PMO/腾讯云-周健-SecretKey.csv`（92 字节，真实凭据）→ `~/.dsh/credentials/`（与既有
`shouheng-lark.json` 同处，目录权限 `700`、文件 `600`）。
**移出工作区，而不只是加 `.gitignore`** —— 工作目录本身可能被同步、备份、打包或分享。

### ADR13-D9 · `ContentUnit` 采用双指纹

| 指纹 | 答什么问题 | 依据 |
|---|---|---|
| `raw_sha256` | 这条判定看的是**哪份原件** | 溯源需要；落地页会变 |
| `text_sha256` | **重跑能不能得到一样的结果** | ADR-0011 实测：原始 HTML 指纹 3/3 变化，提取后正文 3/3 一致 |

两者都要：前者是 ADR-0002 的记录级溯源要求，后者是 ADR-0005「没有 receipt 的判定不算发生过」的复现前提。

## 二、落地分期（B0 / B1 / B2）

| 期 | 内容 | Done（可验收） | 依赖 PRD |
|---|---|---|---|
| **B0 · 1 周** | 立版本 + 冻结 `ContentUnit` / `judge(unit)` + 规则单向同步 + `verify_base.py` | 五面各一条自证命令全绿；`git log` 有历史；任意文案与任意 URL 都能变成 unit 进 judge | 否 |
| **B1 · 2–3 周** | 文本 → 落地页 HTML → 图片 → 视频，逐个接进管道；每形态按法务口径各测三个指标 | 四种形态各有「获取成功率 / 识别完整度 / 处理耗时」三个数字 | 否 |
| **B2 · 2–3 周** | 4 类知识库实例化 + 需求治理三条未决收口 + skill 化 + 一次模拟端到端送审 | 10 条黄金问题全部可答；任意 agent 能按规程调起审查 | 否 |
| **之后** | **装配层**：卡片状态机 / 状态落多维表格 / 回调 / 审批 / 任务 | 才需要 PRD | **是** |

**范围边界（明确不做）**：不做前端（等 PRD）；不做「贴进来就告诉你能不能投」的机器人
（54.6% 落 CATCH-ALL，会把「不知道」说成「没问题」）；不让业务在卡片里直接改规则
（规则变更必须有单一权威实现）。

**周期账**：会议定 3 个月，当前第 1 周。B0+B1+B2 ≈ 6–7 周，余下 5–6 周给 PRD 到位后的
装配与真实试跑。B0 若拖成 3 周，后面余量即被吃掉。

### L3 · 永不入盘

| 内容 | 为什么 |
|---|---|
| `PMO/腾讯云-周健-SecretKey.csv` | 真实凭据 → **移出**（ADR13-D8） |
| `research/governance/_evidence/R4/_cfprof_fetch`(22M) · `_cfprof_headful`(49M) · `_cfprof_headless=new`(11M) · `_chromeprof`(7.4M) · `_chromeprof_cdp`(139M) | **浏览器会话数据**（含 `Trust Tokens` / `Trust Tokens-journal` 等）。虽已被 L2 覆盖，此处**显式列出**，防止日后有人把 `_evidence` 整体提进 L1 |

**预计仓库规模：< 50 MB**（对照：全量入库 2 GB+）。

> **落地时的一处澄清（不是改决定）**：`research/landing/要素提取.json`（10.3 MB）虽落在 L1
> 「`research/landing/*.json`」的字面范围内，但它是 `lp_extract.py` 对 L2 证据的机器产物、

> 「生成脚本 + 输入指纹」，就说明它被分错了层。

## 四、后果

### 4.1 得到什么

1. **可回滚**：14 个 ADR、161 项验收、四份验收脚本首次拥有版本历史。
2. **接口冻结**：B1/B2 的每一项能力都有确定的插入位置；PRD 到位后接的是装配层，不是重做。
3. **权威源单向**：业务与法务改规则不必经手开发者，且每次同步可被指纹检出漂移。
4. **凭据离开工作区**：目录被同步/备份/打包不再泄露。

### 4.2 **没有**得到什么（必须说清，否则会被当成已解决）

1. **L1/L2 分级不解决素材保密。** 它解决的是**体积**与**凭据/会话数据**。
   291 条真实广告文案与费用数据**仍会进历史** —— 因为它们就在 `PRD/内容治理需求文档.md`
   的「广告文案明细」表里，而该文档属于 L1。
   素材保密是 **ADR-0003（敏感样本分级准入，`proposed`）** 的事，本 ADR 不动它。
   ⇒ **推论：本仓库本轮不设远端。**设远端等于「开放外部输入」，依 `ADR/README.md` 规则 3
   须由 Owner 重新确认，且必须先结清 ADR-0003。
2. **ADR13-D3 的文本化覆盖不到图内非文字违规**（画面暗示、构图、品牌调性），
   也不覆盖视频的音调、节奏、字幕与画面对不上的情形。
3. **`account-owners.csv` / `site-owners.csv` / `lark-visible-people.csv` 含真人 open_id。**
   本地无虞；**加远端前必须重估**（与第 1 条同批处理）。
4. **本地投影入历史 ≠ 权威源被版本化。** 飞书侧的改动历史仍然不可查；
   本地历史只能证明「某次同步时它长什么样」。
5. **飞书 `app_token` / `file_token`（Base 与文档的内部标识）会进历史。**
   实测：`tools/live_snapshot.py`（6 处）、`tools/kb_materials_lark.py`（15 处材料 token）、
   `tools/migrate_whitelist_to_lark.py`、`tools/migrate_vocab_to_lark.py`、
   `research/live/snapshot-*.json`（9 处）均含此类标识。
   它们**不是凭据**（token 本体在 `~/.dsh/credentials/`，已在项目外；拿不到
   `tenant_access_token` 就访问不了），且大部分已随飞书链接出现在 `PRD/内容治理需求文档.md`（同为 L1）。
   但它们是**内部资源标识**，与第 1 条同批处理：**设远端前必须一并重估**。
   ★ 提交前已跑内容级扫描：暂存区**无硬编码凭据** —— `SecretKey` / `api_key` / `password`
   的全部命中均可解释（minified JS 的库字符串、API 路径、或讨论凭据的说明性文字）。

## 七、落地时发现：`.md` 文件被企业 DLP 透明加密加长 4096 字节（2026-09-17 · 已定位）

**发现方式**：执行 ADR13-D1（`git init` 前的内容核对）时，`read` 工具拒绝两处合法 UTF-8 文件，
报 `binary file`。追查到底后确认：**不是文件内容坏了，也不是那个工具有 bug。**

### 7.1 最小复现（决定性的那一个）

同一目录、同一时刻、逐字节相同的内容，**只改扩展名**：

| 文件 | `st_size` | 实际读到 | 磁盘分配 | 差 |
|---|---:|---:|---:|---:|
| `/tmp/_repro.md` | 8118 | 4022 | 8192 | **+4096** |
| `/tmp/_repro.bin` | 4022 | 4022 | 4096 | 0 |
| `/tmp/_repro.txt` | 4022 | 4022 | 4096 | 0 |

**差值只跟扩展名有关 —— 与目录、内容、时刻都无关。** 这一条推翻了本节初稿的判断。

### 7.2 读数的分裂

| 取数方式 | 读数 | 为什么 |
|---|---:|---|
| `/usr/bin/stat` · `ls -l` | 真实 **+4096** | 直接读 `st_size` |
| `wc -c < 文件` · `dd if=文件` | 真实 **+4096** | 对普通文件走 `fstat`，**不实际读取** |
| `cat 文件 \| wc -c` · `python` · `mmap` · `cp` · `git blob` | **真实** | 真正读字节 |

多出的 4096 字节**确实被分配了**（`blocks` 由 8 涨到 16，即 8192 字节），
在全新文件上读出来是**全零**。

### 7.3 它会自己回来

- **原子替换可以临时修好**：读干净数据流 → 写临时文件 → `os.replace`。
  修完立即复验：271/271 全部一致，inode 已更换。
- **但 30 秒后复发，且 inode 再次更换。**
  受控实验（5 个文件，全程记录 inode）：

  | 时点 | `st_size` | 真实数据 | inode |
  |---|---:|---:|---:|
  | 修复前 | 19136 | 15040 | 11201472 |
  | 修复后立刻 | 15040 | 15040 | 11205660 |
  | **+30 秒** | **19136** | 15040 | **11205677** |

- ⇒ **不是一次性损坏，是一层介入在持续维护这个状态。**

### 7.4 影响

| 对象 | 是否受影响 |
|---|---|
| **文件内容** | **否** —— 所有真读字节的路径都得到完整、合法 UTF-8、语义完整的内容 |
| **git 仓库** | **否** —— `git add` 存入干净版本；提交后 `git status` **为空** |
| **判定引擎** | **否** —— 161/161 验收通过，读的就是这些文件 |
| **`read` 工具** | **是** —— 它按 `st_size` 读，读到 4096 字节尾部，遂判 `binary`。**它没有错。** |
| 任何按 `st_size` 预分配的消费者 | 是 |

**★ 更正本节初稿的一处过强判断。** 初稿把范围写成「只限本目录」，
并称之为「一条磁盘健康信号」。**这是错的** —— 7.1 的最小复现证明：
它在 `/tmp` 下同样成立，且只跟扩展名有关，与本目录、与磁盘健康都无关。
这段更正**保留在正文里而不删掉**，因为「先写下判断、再被自己的实验推翻」
这件事本身值得留痕 —— 它正是 B0.5「自证」要防的那类错误。

### 7.5 处置与遗留

- **修复无意义，已停手**：原子替换会在 30 秒内被撤销，且每次替换都换 inode。
  继续做只会制造 inode 抖动。已修复的 271 个文件**内容零改动**（逐文件 md5 前后对照，271/271 相同）。
- **不阻塞 B0**：内容、git、引擎三条都不受影响。
- **★ 给后来者的处置（B3.0 补记）**：受影响的是**按 `st_size` 读取的消费者**，而
  `read` 工具正是其中之一 —— 于是在本机读 `.md` 会得到 `binary file`，而文件内容
  完好。**不要去找这个"bug"**（它没有 bug，见 7.4 那一行）。
  绕法：用真读字节的路径 —— `python3 -c "print(open(p,encoding='utf-8').read())"`、
  `sed`、`cat`、`cp`。B3.0 整轮的 `.md` 读写都走这条路，未受影响。
  **先例**：我这一轮先是怀疑「`read` 工具的二进制判定写错了」，查了实现
  （`readWholeText`：首 N 字节含 `\0` 即判 binary）又回来对上了 7.2 的读数分裂 ——
  两个解释都自洽，而正确的那个是**已经写在这里的**这个。
- **实际代价只有一条**：`read` / `edit` 工具在受影响的 `.md` 上会失败。
  绕行方式已验证可行 —— 用 `python3` 经 bash 读写（`read` 工具的判断依据是 `st_size`）。
### 7.6 这层介入是什么 —— **已定位（2026-09-17）**

**不是磁盘问题，是企业的数据防泄漏（DLP）透明加密。** 实测证据：

| 证据 | 值 |
|---|---|
| 已加载内核扩展 | **`com.tipray.trldKext (5.02)`** —— 天锐绿盾（TipRay） |
| 常驻进程 | `/usr/local/.trld/bin/tr_daemon`（多实例）、`TrTrayForMac.app`、`TrFinderSync.appex` |
| LaunchDaemons | `com.trld.tr_daemon` · `com.trld.tr_kext` · `com.trld.tr_userdog` |
| 端点安全系统扩展 | `com.kaspersky.kav.sysext`（Kaspersky，亦为活跃端点安全扩展） |
| 类型相关性 | 同一测试中 `.md` +4096、`.txt`/`.bin` +0 —— 与 DLP 按文档类型分类加密的行为一致 |

**机制**：DLP 对「文档类」文件做透明加密，加密元数据块占 4096 字节。
读文件时内核扩展对**被授权的进程**透明解密，于是：
`st_size` 显示密文长度（真实 +4096），而 `cat`/`python`/`git` 读到的是解密后的原文。

**这把本节的四条结论全部解释了**，且**推翻了「磁盘健康」这个初稿判断 —— 它已彻底撤回。**

### 7.7 对项目本身的三个后果

1. **ADR13-D7「本轮不设远端」多了一条独立理由。** 原先的理由是 ADR-0003（敏感样本分级准入）未结清；
   现在多一条：**该目录处于企业 DLP 管控之下，向外部远端推送可能被策略阻断或构成数据外泄**。
   设远端前必须同时过这两关。
2. **`read` / `edit` 工具在本仓的 `.md` 上不可靠**（凡 `st_size` > 4096 者）。
   已验证的绕行：用 `python3` 经 bash 读写。**这不是工具 bug，不要报给它。**
3. **透明解密依赖进程被 DLP 授权。** 今天 `git`、`python`、引擎都在授权范围内（161/161 通过）。
   若日后换用户、换终端或换进程身份，**可能出现「同一命令昨天能读、今天读不了」** ——
   这类故障会伪装成「文件损坏」，届时先查 DLP 策略，不要先查文件。

### 9.1 这一层存在的理由：引擎的边界声明里有一句话变成了假话

`skeleton/judge.py:220` 的 `unknowns` 里写死着一句（同一句还以机器可读形式出现在
`boundary_statement.not_covered_carriers`）：

> **未覆盖的载体**：本判定只看文本。图片、视频、**落地页正文**、A+ 详情页均不在输入内。
> 批次 C 已产出落地页正文的获取能力，但**尚未接入本引擎**。

在一个 `landing_page` unit 进判定时，**它逐字是假的** —— 那份判定的输入就是落地页正文。
而 `judge.py` 自己的 `_layer_note()` 已经立过「一句写死的免责声明迟早会变成假话」这条原则。

⇒ **ADR13-D27 · 边界订正在适配层做，不在引擎里做。** 改 `judge.py` 是改引擎，且 161 项验收盯着它；
而 unit 知道自己是哪种载体，也只有它知道。订正动作进 `boundary_statement.$corrections`，
**留痕不静默**。订正**按载体分**：对广告文案引擎那句仍为真，**不动**。

实测对照（`python3 base/judge_adapter.py --boundary-report`）：

| | |
|---|---|
| 订正前 | 「…落地页正文…**尚未接入本引擎**」 |
| 订正后 | 「**载体：落地页正文——已接入，但只覆盖到文字那一层。**…**不含画面语义**，也抓不到 JS 运行时渲染出来的内容」 |
| `not_covered_carriers` | `['图片','视频','落地页正文','A+ 详情页']` → `['图片','视频','A+ 详情页']` |

### 9.2 `judge()` 的回执答不了「哪份原件」

引擎回执只存 `input_sha256`。这对广告够用（正文就是原件），对落地页不够 ——
同一段正文可以来自无数份 HTML（§8.1 三：raw 变 4/4 而正文变 0/4）。

**ADR13-D28 · 适配层的回执加一个 `unit` 块**（双指纹 / 载体 / uri / 两个档位名 / 文本化边界），
**仍不含原文与片段**。实现上刻意**不重写** `obligations` —— 那是法务所有的契约字段，
抄第二份实现迟早不一致；改为让 `judge()` 照常生成完整回执（写临时路径），
本层补 `unit` 块后再经**生产闸门** `append_receipt()`（origin 检查 + 前缀哈希链）落账。

### 9.3 一条自证断言，与它抓到的一句假话

**J2 · 正文原样到达引擎**：`result["input"]["text_sha256"] == unit.fingerprint.text_sha256`，
且 `chars` 相等。引擎自己也算了一遍 `sha256`，**两个独立实现算出同一个数** ——
这是「unit 的正文没有被中间任何一层改写」的证明。427/427 通过。

**本层自己制造过一句假话**（记下来，因为它是本节最有价值的产出）：
第一版对「正文为空」只判 `not has_text`，于是它对**那 59 条 PLA 广告**也说
「本条落 DP0 的原因与 PLA 那 59 条不同」—— 而它自己就是其中一条。
**为了订正一句假话而写出的新句子，第一版就是假的。**
被本文件自己的断言抓到（[J3]「59 条 PLA 空文案不被告知『你与 PLA 那 59 条不同』」）。

修正后按**载体**分：`landing_page`/`structured_json`/`image`/`video` 的空正文是**取不到**；
`free_text` 是**调用方给的就是空的**；`ad_text` 是**结构上没有**（PLA）。
三者都走 DP0，性质与处置都不同 —— 而 ADR13-D5 那条通知若只说「没有文本」，收件人无法行动。

### 10.3 冲突语义（ADR13-D2 原文：不静默合并、不取「较新者」）

| | 本地多出来 | 权威/飞书多出来 |
|---|---|---|
| `pull`（飞书权威） | **✗ 本地成了第二个源**（ADR13-D2 明令禁止） | ⚠ 待同步 |
| `push`（本地权威） | ⚠ 待发布 | **✗ 有人手改了发布面** —— 下一次推送会**静默覆盖**它 |

### 10.4 `--probe` 第一次跑就撞出自己检查里的一个洞

首跑报告「广告文案明细 291 条 / `records.json` 289 条 —— ✓ 条目集合一致」。
**「✓」是假的**：两侧各有 2 条记录 `外部广告ID` 为空，被两侧**一起**从分母里剔掉了。

本仓已经吃过一次同形的教训（「把读不到的 10 条从分母里剔掉之后，
『收集了 15 条』看起来像成功，实际可用 5 条」）。已改为：
报告必须写出**分母是多少、少的那些是谁**，且「无标识」单列为一等公民。

**那 2 条的真身**（实测，不是猜测）：飞书 `recvuNu8mWXyYp` / `recvuNE6m1MyjQ`

### 10.5 一处「文案说未通过、退出码说 0」

### 11.2 异议一：那条检查**做不到全覆盖**，而原因必须先说清

异议一原文要求「L2 的每个关键产物都能在 L1 里找到它的生成脚本 + 输入指纹」。

**做不到 —— 因为 L2 不是一个性质，是五个。** 本模块把 `class` 做成必填字段：

| 类 | 组数 | 异议一那条判据 |
|---|---|---|
| `derived` 可复算 | 5 | **适用**：必须有 git 跟踪的生成脚本 + 可追溯的输入 |
| `addressed` 内容寻址 | 4 | **不适用**：文件名即指纹，它自己证明自己 |
| `primary` 本身是账本 | 3 | ★ **不适用，且必须写清为什么** |
| `runtime` 运行态 | 2 | 不适用 |
| `vendored` 别人管的 | 10 | 不适用 |
| `forbidden` 结构性防线 | 7 | 不适用 |

**`primary` 这一类是本检查最该说清的地方。** §三 L2 把 `receipts.jsonl` 判为 L2，
理由写的是「**追加型账本**：只会增长，不需要 diff 与回滚」—— **不是**「可复算」。
一条回执记录的是「当时判了什么」，**L1 里没有第二份**，所以它不可复算、
**也不该被要求可复算**。异议一那条检查只对 L2 的**第一类理由**成立。

⇒ **异议一不需要重议，但它的措辞需要收窄**：把「L2 的每个关键产物」改为
「L2 里**以『可复算』为由**入库的每个产物」。**这不是给检查放水，是把判据说准** ——
如果笼统要求全部可复算，结果只会是给不可复算的东西编一个假的生成脚本。
**ADR13-D7 因此不必重议**：它排除 `records.json` 的理由正是「可复算」，而那条已逐项查过（`derived` 5 组全绿）。

**★ 分母口径的两处刻意处理：**

   而不是从「已经取到过 HTML 的那 92 个页面」里抽。**这一条不写，那个 100% 会被当成能力。**

### 12.3 ★ 我提出的核心假设**没有被证实**

**假设**：alt 文本看着像覆盖（90.2% 的图有 alt），但它是商品名目录（中位 17 字符），
声明是画在图里的 —— 所以 OCR 应当读到 alt 里没有的声明。

**实测：不成立。**

```
alt 非空、而 OCR 读到 alt 之外的新声明        0 / 30   (0.0%)
OCR 命中声明性表述                          1 / 59   (1.7%)
```

**而且原因比假设本身更有用**，它有两层：

- **声明词表是英文的，图片文字不是。** 本批样本抽到大量 es/de 站，
  OCR 读出的是 `~70% indico un reflejo de bajada de la leche mas temprano*`、
  `Masaje sincronizado con la succion para un vaciado mas rapido y eficaz` ——
  这些是**西语的功效表述**，任何英文词表都盖不住。
  （这不是新问题：`judge.py` 的边界声明早就写了「de/fr/es/pl 只有零星词条」。）
- **图片里的表述是视觉化的**：`~70%`、`más rápido`、对比图上的 `50avs Battery Life`。
  它们不是词表能枚举的**词**，是**版式**。

**⇒ 于是换了一个与语言无关的问法：OCR 读到的实词，页面正文里有没有？**

```
有 OCR 文本 38 张 · 实词覆盖率 中位 78% · 最低 0% · 最高 100%
低覆盖（<50%，字只存在于像素里）11 张
```

**★★ 而这 11 张里，多数是 OCR 噪声，不是隐藏的声明**：

```
momcooy | momor | treasl purp coetra          ← 花体 logo 被读错
R | 02:18 | 0-0.25 oz | 7 | + | LCR | Finish  ← 视频播放器与对比控件的碎片
```

**把噪声当成「新发现」是这类测量的典型误读。**
真正的像素独占内容确实存在 —— `Images are for illustrative purposes only.` 这类免责声明、
`*Segun los datos de mercado disponibles a fecha de noviembre de 2025` 这类**来源脚注** ——
但在本批样本里数量很少，**不足以支撑「OCR 是图片审查的主要通道」这个结论**。

⇒ **ADR13-D30 · 图片这一档的定位下调。** ADR13-D3 说「图片先做文本化」，本模块照做了；
但实测表明：**在落地页这个载体上，图内文字与页面正文高度重叠**（中位 78%），
OCR 的**净增量很小、且噪声占多数**。所以图片 OCR 应当定位为
**① 覆盖 alt 为空的图（15/29 有文本，这条是实的）② 抓免责声明与来源脚注这类
「小字」内容** —— 而**不是**当作「图片已审」。

### 12.4 ★★ 顺带抓到一个真缺陷：声明词表里有两个词**永远匹配不上**

`tools/lp_extract.py` 的 `CLAIM_PATTERNS["absolute"]` 原式：

```python
r"\b(100%|never|always|guaranteed|best|#1|number one|no\.?\s?1|ultimate|perfect)\b"
```

末尾那个 `\b` 让 **`100%` 与 `#1` 永远匹配不上** —— `%` 与 `#` 都是非单词字符，
它们后面紧跟空格时**不存在单词边界**。实测 `'100% safe'` → 不命中，`'#1 brand'` → 不命中。

**影响面（实测，不是估计）：**

| | 修正前 | 修正后 |
|---|---|---|
| 21,424 条 alt 里的命中数 | 87 | **94**（漏 7） |
| 92 个页面正文里含 `100%`/`#1` 却抽不出的 | **3 个页面** | 0 |
| **批次 C「广告 vs 落地页」一致性：至少一项声明未出现的广告数** | 33 | **35** |
| 同上 · 其中广告本身已命中规则的 | 29 | **31** |
| 同上 · 未在落地页出现的声明计数 | 29 | **30** |

**★ 这个缺陷一直在静默压掉跨载体不一致** —— 新增的两条正是
`{"广告中的表述": "#1", "类型": "absolute", "落地页是否出现": false}`。
一个广告说了 `#1`、落地页上没有，这正是批次 C 存在的全部理由，而它被一个 `\b` 挡住了。

**修法与守卫**：把「以符号结尾」的备选从 `\b` 里拿出来
（`(?<![\w%])100\s?%` / `(?<![\w#])#\s?1\b`），并在 `base/media.py --selftest` 里
加了一条**词形自洽检查**：**6 类 30 个声明词，每一个都必须命中它自己。**

> **这条守卫的缺席，就是那个缺陷能活下来的原因。** 词形清单写了、
> 文档写了、调用也接上了 —— 但**没有一条检查问过「它匹配得上自己列的词吗」**。
> 这与 ADR-0012 §二 记的「能力写好了、调用没接上」是同一类病的新变种：
> **词写了，但它匹配不上。**
>
> 因这个修正，批次 C 的制品需要重跑（`python3 tools/lp_consistency.py`）——
> 已在本轮执行，`一致性分析.json` 已更新。

### 12.5 视频：**49 条视频广告，0 个视频文件**

**第一版我写的是「全仓 0 个视频素材」—— 那句话误导。** 它说的是文件数（确实 0），
读起来却像「没有视频这回事」。实盘：

| | |
|---|---|
| 视频广告条数 | **49**（视频需求开发广告 31 · 自适应视频广告 6 · 名称含「视频」另 12） |
| 其中带落地页 URL | 37 |
| 近 7 天费用 | **$5,110** |

**⇒ 准确的说法是：这 49 条的「文案」已在覆盖范围内**（在 291 条 → 427 个 unit 里，已进判定），

  外部服务会引入数据出域，**须先过 ADR-0003**）③ 抽帧 ④ 人工标注真值。
- **契约已备好**：`contract.from_media(kind="video")` 可用，`covers`/`does_not_cover` 必填。

## 十三、B2 落地：文本两组的三指标 · 常驻 OCR · 无偏重抽 · 指纹复现性（2026-09-17）

**交付物**：`base/text_stage.py`（文本两组的三个指标）· `base/media.py`（常驻 OCR · 无偏抽样 ·
退化占位图分类）· `base/ocr_vision.m`（`--serve`）· `tools/lp_stability.py`（指纹复现性实测）。
`base/verify_base.py` 的 A 面从 3 个模块扩到 **5 个**。自证：`text_stage` 19 项 · `media` 26 项 ·
基座六面全绿。

### 13.1 文本这一类一直没有自己的三个数字，而它被认为「已经通了、不用量」

ADR-0013 ADR13-D3 要求打样覆盖**文字、图片、视频**三类。B1 交了图片，视频如实报「没有数字」，
**文字这一类一直空着** —— 理由是它「已经通了」。这个理由本身就是要防的形态：

> **跑得通 ≠ 量过了。** 「通了」说的是管道没断，不是「拿到多少、认得多少、要多久」。

而且「文字」不是**一个**载体，是**两组来源完全不同**的语料，实测下来它们的「获取」根本不是同一件事：

| 组 | 来源 | 分母 | 「获取」是什么意思 |
|---|---|---|---|
| **A 广告文案** | 存量记录表（内部导出） | **291 条记录** | 把表读成 unit —— **不是抓取** |
| **B 落地页 HTML** | 批次 C 联网抓取 | **92 个 URL** | 从站点取回内容 —— **是抓取** |

**把两组混成一个「文字类」百分比是错的**：A 的失败原因是「字段本来就没有」，
B 的失败原因是「站点不给你」。**处置完全不同，混读会同时掩盖两边的真问题。**

### 13.2 A 组：那个 100% 是本轮最像样的一个假数字

```
跳① 广告平台 → 存量记录表 ：不可测（表是给定的，仓里没有任何关于这一跳的记录）
跳② 存量记录表 → unit      ：291 / 291 = 100%
```

**把跳②的 100% 报成「内容获取成功率」，是本档最容易犯的错。** 它只说明**表读得动**。
真相是 **59 条记录（20.3%）的正文是空的**，一个字都没有。所以 `text_stage` 报的第一个数是：

> **内容获取成功率 79.7%（232/291）** —— 判据是「记录里有可判正文」，不是「记录读进来了没有」。

**空文案的构成必须说得出**（否则「59 条没有文案」读起来像抓取失败）：`产品广告 55 + 广告类型为空 4`。
产品广告（Google PLA / Shopping）的标题与卖点由平台按商品 feed 拼装，**结构上就没有
`Primary Text` / `Headline` 这两个字段** —— 它们的文案在图片与商品标题里。
⇒ **这 59 条要去看图片档，不是记成「无内容」。**

**识别完整度 0.825**（25 个字段达成率均值，分母 291）。均值会被 21 个几乎全满的采集段字段抬起来，
所以**三段剖面比均值有用**：

| 段 | 字段数 | 覆盖率区间 | 零填充字段 |
|---|---:|---|---|
| 采集段 | 5 | 99.0 – 100.0% | — |
| 维度段 | 4 | 90.0% | — |
| 正文段 | 3 | 70.1 – 79.7% | — |
| 分析段 | 4 | 44.7 – 45.4% | — |
| **治理段** | **1** | **0.0%** | **`检查人`（0/291）** |

**断崖的位置比任何一个单点数值有信息量**：采集段几乎全满，走到「谁负责」这一格停下了。
（首测见 `04-内部证据-字段可用性与平台抽样偏差.md`；本模块**每次从记录重算**，不抄那份文档。）

**处理耗时**（`--timing`，实测而非读常数）：

| 环节 | p50 | p90 |
|---|---:|---:|
| 建 unit（291 条） | **0.025 ms** | 0.061 ms |
| 判定（有正文的 232 条） | **2.847 ms** | 3.621 ms |

⇒ **判定是建 unit 的 114 倍。** 「一次判定要多久」这个问题，答案由引擎决定，不由信封决定 ——
这一条不测，很容易被「291 条跑完不到 1 秒」这种整体读数盖过去。

### 13.3 B 组：落地页的 100% 与 30.4% 必须成对读，这一条**编进了指标本身**

批次 C 早已量出这个成对关系，但它留在**报告正文**里，没进「三指标」这个口径 ——
于是一份只抄三个数字的表会把 100% 单独带走。本模块把它编成指标的**字段**：

```
值 100.0%（92/92）  ←→  成对读数：首轮 30.4%（28/92，全局间隔 0.0s） → 终值 100%
「同一个站点、同一批 URL、同一份 UA，唯一变量是节流策略」
```

**★ 读数不重算。** 三个数的唯一产地是 `tools/lp_metrics.py`（批次 C）。
在第二个地方重算同一个判据，就是本项目已出过三次事的「两处真相」。
`text_stage` 只做 `lp_metrics.py` 没做的两件事：① 整成与 A 组／图片档同一形状；
② 补上「复现性」（见 13.6）。自证里有一条守着它：**B 组的值必须与制品逐字相等**。

### 13.4 遗留 19 关闭：批次 C 三件制品全部复查，**其中一件真的变了**

`CLAIM_PATTERNS["absolute"]` 末尾那个 `\b` 让 `100%` / `#1` 永远匹配不上（B1 §12.4）。
遗留 19 记的是「需重跑批次 C 制品」，B1 只跑了 `lp_consistency.py`。本轮把三件全部复查：

| 制品 | 重跑结果 | 结论 |
|---|---|---|
| `指标.json` | **逐字段无差异** | 那 3 个页面本来就另有其它声明，`claims` 这一类没翻档 |
| `一致性分析.json` | **无差异** | B1 已跑过，此处确认幂等 |
| **`整改路由.json` / `-待法务判定.csv`** | **33 → 35 条** | ★ **真的变了** |

新增的 2 条**全部**来自同一个词形 `absolute:#1`：

```
recvuJYdObTUXT  自适应搜索广告-Jolla-Sale-Search-US   规则 U01
recvuJYeGRHN3g  自适应搜索广告-Jolla-Sale-Search-US   规则 M03,U01
```

**这两条正是「批次 C 的存在理由」那一类发现：广告里写了 `#1`、落地页上没有。**
一个 `\b` 把它们挡在门外 —— 而**没有任何东西会告诉你有东西被挡住了**：
词形清单写了、文档写了、调用也接上了，只是那个正则匹配不上自己列的词。

> **这一条的意义不在 2 这个数字，在于「重跑制品」这件事本身。**
> 一个已经交付给法务的 CSV，在里面悄悄少两条、并且行序也变了 ——
> 如果没有人复查，它和「一切正常」长得完全一样。

### 13.5 常驻 OCR：省的是启动开销，**结果必须逐字节相同**

B1 实测「Vision 自报 p50 169ms、本模块墙钟 p50 3573ms」，差值里有一大块与图片无关。
`ocr_vision.m` 加了 `--serve`：逐行读路径、逐行回一行 JSON、每行 flush。

| | 一次一进程 | 常驻 |
|---|---:|---:|
| 单次 Vision 时间（第 2 张起的中位） | 142–173 ms | **26–59 ms** |
| 进程启动 | 每张一次 | **整批一次** |
| 原始识别行 | — | **逐字节相同** |

**★ 这条优化必须由一条检查来证明，而不是由注释来声明**（`media.py` 自证 `[6b]`）：

```
✓ 常驻模式可用，且两种模式的**原始识别行逐字节相同**   （比的是 lines，不是加工后的 text）
✓ 必红对照：杀掉常驻进程后，下一次请求自动重启并仍给出结果
```

**比 `lines` 而不是 `text`** 是刻意的：拿加工结果比，会让「两条路的字段补齐不一致」
伪装成「OCR 结果不一致」，排查方向会被带偏。

> **★ 本轮实测到的一件事：命名的坑会伪装成结果的坑。**
> `srv.ocr()` 第一版不补 `text`/`chars`，于是自证报「两种模式文本不一致」——
> 而 OCR 本身一个字都没差。**把它当成 OCR 问题查，会查很久。**

### 13.6 无偏重抽：B1 那个 64.4% 有一半是**样本的构造方式**

B1 的抽样是**病例对照设计**，不是概率样本：

```python
with_alt.sort(key=lambda i: -len(i.get("alt") or ""))   # 每页取 alt 最长的
sel = with_alt[:half] + without[:per_page - half]       # 再配一半 alt 为空的
```

它的**目的**（「找内容图而不是 logo」）达到了，**代价是任何百分比都不能读**。
本轮的 `uniform` 设计是两阶段等概率（先等概率抽页面、再在页内等概率抽位图），
每张图带 `w = 1/π`。

**偏差量 —— 「重抽了无偏样本」这句话必须带数**：

| | alt 非空率 | alt 长度中位 | n |
|---|---:|---:|---:|
| **总体真值**（13,834 张位图，从盘上直接算，不需联网） | **91.2%** | **20** | 13,834 |
| B1 `alt-biased` | 50.8% | 92 | 59 |
| **B2 `uniform`** | **91.7%** | **17** | 120 |
| 偏差 | **−40.4 个百分点** | **4.6 倍** | |

> **`uniform` 在总体真值上校准到 0.5 个百分点以内** —— 这就是「无偏」这句话的**验证**，
> 而不是**声称**。而 `alt-biased` 把 alt 长度中位抬到 4.6 倍、把非空率压到一半。
> **在这份样本上算出来的「识别完整度」，量的是样本的构造方式。**

**重抽后的三个数字（120 张 / 20 个页面，样本 2026-09-17）**：

| 指标 | 值 | 加权（全部 13,834 张位图口径） |
|---|---:|---:|
| 内容获取成功率 | 100.0%（120/120） | 100.0% |
| 识别完整度（有 OCR 文本） | **40.0%**（48/120） | **41.8%** |
| OCR 命中声明性表述 | 4.2%（5/120） | — |
| **★ alt 非空、而 OCR 读到 alt 之外的新声明** | **3.7%**（4/109） | **4.8%** |
| 退化占位图（1×1，单列一档） | 1.7%（2/120） | — |

**B1 报的是 64.4%（38/59）。真实量级是 40%。** 差出来的 24 个百分点，
来自「B1 专挑了 alt 最长的那批图」——而那批图恰好就是**图上真有字**的内容图。

**★ 报价口径的两处刻意处理**：

1. **加权与未加权并排给，不取其一。** 未加权回答「**随便挑一张图**会怎样」，
   加权回答「**全部 13,834 张位图**会怎样」。两者差多少，就是「页均」与「图均」这两个问题差多少。
2. **识别完整度的分母含退化占位图与 OCR 失败**（120 张），不是只取「OCR 跑通了的」（118 张）。
   后者会把失败挪出分母 —— **本项目已立规矩不许这么干**。剔除后的 40.7% 并列给出，
   因为「占位图算不算素材」是个**口径问题，不该由本模块替法务决定**。

### 13.7 ★★ 无偏样本推翻了 B1 的说法，并给出了更强的版本：**alt 与「图里有字」是负相关的**

B1 §12.3 的结论是定性的：「有 alt 不等于图里的字被读到了」。**那个样本证明不了这句话** ——
要证明「alt 不预测图内文字」，必须在一个**概率样本**上比两个条件概率。实测：

| | 有 OCR 文本 | 加权 | n |
|---|---:|---:|---:|
| **有 alt** | **37.6%** | 39.9% | 109 |
| **无 alt** | **77.8%** | 79.1% | 9 |
| `alt 长度` 与 `OCR 字数` 的相关系数 | **r = 0.139** | | 118 |

**不是「无关」，是方向相反。** 直觉是「有描述的图内容更丰富」；实测是反的 ——
有描述性 alt 的多是**商品缩略图与分类瓷片**（`Bottle Sterilizers`、`Labor Hospital Bag`
这类干净产品图，图上没有字），而 `alt=""` 的多是**横幅与信息图**，
文案画在图里、开发者留空 alt。

⇒ **「23,745 张图里 90.2% 有 alt」这句话，不但回答不了「图里的字读到了没有」，
它指向的方向是错的：alt 覆盖越好的那部分，图内文字反而越少。**

**同时，OCR 的净增量在无偏样本上确实仍然很小**（4/109 = 3.7%，加权 4.8%），
所以 B1「净增量小」这个**定性**结论成立 —— 但它的一个读数被纠正了：

```
B1（alt-biased）：1 / 30
B2（uniform）    ：4 / 109
```

而且这 4 条里有伪增量：奖章徽标上的 `TIME BEST INVENTIONS 2025`
被抽成 `absolute: best` —— **第三方奖项图形上的 BEST，与品牌自己写的「最好的」不是一回事。**
真正的像素独占发现也有（`IBCLC`：`Trusted by lactation experts` 画在图里），
但**数量级不足以支撑「OCR 是图片审查的主要通道」**。

### 13.8 ★★ 第三个数缺的那一问：**重跑能不能得到一样的数**（`tools/lp_stability.py`）

法务表第二层问的是「工具能否**稳定**获取并处理」。「稳定」两个字必须由某一个数字回答。
在此之前**没有任何数字回答它** —— 于是 100% 与 0.996 会被读成「这个数明天还是这个数」。

**ADR-0011 的对照实验是在「同一时刻」做的**：V4 抽检重抓，raw 变 3/3、**提取后正文 3/3 一致**。
推理没错，结论「指纹建在提取后正文上」也没错。但它接着推出了一句话：

> 「对原始响应做哈希会让『上周读到的这条，现在还是不是同一条』**永远答不了**。」
> ⇒ 建成正文指纹之后，**这个问题就答得了了**。

**B2 把同一件事放到「隔一天」这个尺度上重做，答案是：答不了。**

#### 13.8.1 实测（快照 2026-09-16 → 2026-09-17）

| 指纹建立在 | 一致 |
|---|---|
| 原始 HTML 的 sha256 | **0 / 40** |
| **提取后正文的 sha256** | **12 / 40 = 30.0%** |

> ★★ **订正（§14.2 / §14.7）：上表的「两轮共 40 个 URL」是重复计数得来的** ——
> 累计读数把**当前这一轮**又算了一遍，盘上当时只有一轮 20 条观测。
> 修复后补跑，盘上真实是 **4 轮 / 80 次观测**（有效独立样本仍是 20 个 URL），
> 读数为 **0/80** 与 **24/80 = 30.0%**。
> **两个百分比一个都没变** —— 变的只是它们有多少证据托底。
> 本节的推理与结论不因此改写；被改写的只是「这些数是从几次观测里来的」。

> **★ 这不是「指纹算错了」。** 原始 HTML 一致率 0% 说明 ADR-0011 的判断完全正确 ——
> 正文指纹**确实**比原始 HTML 稳（0% → 30%）。错的是**它被赋予的期望**：
> 「30% 可复现」不足以回答「上周读到的这条，现在还是不是同一条」。
>
> **ADR-0011 的实验时间尺度（同一时刻）与它想回答的问题的时间尺度（隔周）不是一回事。**
> 这不是推理错误，是**结论被外推到了没有测过的尺度上**。

#### 13.8.2 变了什么 —— 三问，第一版只报了「变了多少」，那不可执行

**① 变化长什么样？**（最小变更段：共同前缀／后缀一剪即得；再逐词取差集）

```
数字/计数  20 处   例：Rated 4.6 out of 5 stars  1,834 → 1,835
文本片段    4 处   例：−Up to 25% Off / Shop …   +Made for Efficiency, Rooted in …
价格        2 处   例：$199.99 → $169.99
评论数      2 处
```

**② 我的假设「都是评论数那种小计数器」—— 被否。**

```
掩掉「评论数 / 库存 / 倒计时」后再比指纹：一致 12/40（未掩码也是 12/40）
（同一结论在修复后的账上复现：24/80，仍与未掩码完全相同）
```

**一个也没救回来。**

**③ 那是不是「页面被重排了、内容没变」？** —— 也不是。看跨度：

```
① 跨度 ≤30 字（局部替换）                        1 处
② 跨度 31–500 字                                1 处
③ 跨度 >500 字（**页面重排，diff 无法表达**）     12 处
```

其中一处在 Δ 只有 −301 字的情况下跨度是 **17,585 字符**。
**那不是「改动很大」，是首尾分歧之间夹着大量根本没变的内容。**
⇒ 正确的读法不是「改得多」，而是「**改动无法被表达成一个小 diff**」。
想在界面上给法务指「这里变了」，做不到 —— 要标 17,585 个字符。

#### 13.8.3 ★★ 所以到底变的是什么：**提问方式换一次，结论就翻了**

第一版的判据是「**变更段里含不含**合规词形」。它**几乎恒为真** ——
最小变更段可能长达一万七千字符，段里的 `45dB` / `FSA` 在**新旧两版里都出现**。
**那是一个会天天报假警的判据。**

改成在**完整两版正文**上各抽一次声明集合、再取差集之后，得到的是可执行的答案：

> **40 次观测里，10 次（25%）的「合规相关声明集合」真的变了。**
> （修复后：**80 次观测里 20 次 = 25%**，率完全相同；四轮的逐轮读数都一模一样）

而且变得很实：**`ca.momcozy.com/collections/electric-breast-pump`**

```
消失：hospital-grade（医疗）· perfect（绝对化）· 45db（性能）· vs（比较性）
新增：fsa / hsa（认证）· guaranteed（绝对化）· award-winning / unlike（比较性）
```

另外 4 个 M5 产品页**同时新增**了 `20 hours`（性能）。

> **⇒ 结论与「这些都是噪声」相反：两天之间，四分之一的页面发生了真实的合规相关变化。**
>
> 这条发现**只有在先问「变的是什么」之后才能得到**。如果停在「正文变化 70%，不可复现」，
> 得到的结论会是「指纹有缺陷」—— 而真相是**变更检测这件事本身有价值，只是判据用错了**。

**静态暴露面**（另一件事，不许与实测率混读）：**92 个页面里 75 个（81.5%）含有会随时间变的片段**。
最多的是评论数（68 页）与价格（59 页）。

> **两个数不许互相冒充**：`正文可复现率` 是**实测**（分母 = 本轮可判的 URL 数）；
> `静态暴露面` 是**有多少页面处于风险下**（分母 92）。把后者当前者，
> 会得出「八成以上的页面不可复现」这种**没有测过**的结论。

### 13.9 这一条对项目意味着什么（**需要 Owner 裁定，不是开发者能定的**）

**契约层的事实**：`ContentUnit.content_key` 的文档写着「只吃正文指纹 —— **页面重渲染后它不变**」。
实测：**两次观测相隔一天，约 70% 的页面会得到一个不同的 `content_key`。**
而 `content_key` 要回答的是「**这两次看到的是不是同一个东西**」。

**这不是「指纹算错了」，是一个从未被实测过的断言。** 修法有三条，本轮实测已经把其中两条的代价量出来了：

| | 做法 | 代价 | 本轮实测对它的判断 |
|---|---|---|---|
| **A** | 把「变更检测」的判据从「指纹变了」改成「**声明集合变了**」 | 不动契约；`content_key` 的语义要改措辞（它答的是「哪一版正文」，不是「同一个东西」） | **✅ 有直接证据**：每轮 20 条里它挑出 5 条真变化，滤掉另外 9 条无声明变化（§14.8）。取差集的结果**人一眼能看完**（几个词） |
| **B** | 加第三个指纹：对**掩码后的正文**取哈希 | 掩码清单要定版；价格与促销幅度不能掩（`SAVE 20%` 本身可能是被判定的表述） | **❌ 实测削弱**：只掩小计数器**一个也没救回来**（30.0% → 30.0%） |
| **C** | 不动，把「定期重抓并 diff」整个降级为**人工复核的辅助材料** | 承认「已发布内容自动监测」（法务文档 §（一）2 的原文）在本机能力下**做不到自动判变** | 本轮实测说明这条**过于悲观**：变更检测有效，只是判据要换 |

**开发者的建议是 A**，理由不再是推理，是 13.8.3 的量：

- 它用**已有的**声明词表（`lp_extract.CLAIM_RE`，唯一词形来源），不加新组件；
- 它把「变没变」这个问题交给**法务口径的判据**，而不是交给一个哈希；
- 它**当天就能验证** —— 本轮的取差集逻辑就是它；
- 它同时解决了 13.8.2 那个「diff 无法表达」的问题：**能给人看的是 4 个词，不是 17,585 个字符。**

> **但这一条必须 Owner 裁定**：它改的是 `content_key` 的语义，而那是**冻结契约**的一部分
> （ADR-0013 ADR13-D1）。开发者不单方面改契约。

### 13.10 本轮我自己犯的三个错（记下来，它们的形态是一样的）

| # | 错 | 后果 | 为什么值得记 |
|---|---|---|---|
| 1 | 抽样权重的字段名用了 `w` | `image_row` 用 `row["w"]` 存「HTML 声明宽度」，**把它覆盖了**；10 行 `w=None`，加权判据静默为假 | **表照常打印，只是不再加权，一个字都不说** —— 本项目最怕的形态 |
| 2 | 「变更段里含合规词形」当判据 | 几乎恒为真（词形在两版里都在） | **一个恒为真的判据比没有判据坏**：它会天天报假警，然后被忽略 |
| 3 | `size_class()` 对字符数写了 `len()` | 在第一轮 20 个样本**跑完之后**才抛 `TypeError`，166 秒联网白做 | 教训不是「小心 `len`」，是**聚合阶段不该在抓取之后才第一次被执行** |

第 1 条的修法值得说：权重是**重算**补回的 —— `build_sample` 是确定性的，
重建的 120 行与盘上样本 `(page_key, src)` 序列**逐一相同**，
`media.py --reattach-weights` **先逐行断言再写盘**，不一致就拒绝写。
**猜参数会让权重错得很安静**，所以参数必须显式传或从 payload 读。

### 13.11 一处被修掉的检查盲区：**自证写了 ≠ 自证被跑**

`media.py` 是 B1 交付的，`--selftest` 有 20 项。
但 `verify_base.py` 的 A 面只列了三个模块 —— **没有任何东西会去跑那 20 项**。
B1 报告「基座自证全绿（六面）」也是真的：绿的是那六面，而 `media.py` 不在其中。
**漏掉的后果是静默的：模块回归了没人知道，因为没人在跑。**

**已修**：A 面从 3 个模块扩到 5 个（`media.py` / `text_stage.py` 进列）。
**但这条修正本身还是靠人维护清单** —— 没有任何检查在问
「`base/` 下每个有 `--selftest` 的模块，是不是都被 A 面调用了」。
这条**已进 §五 遗留**。

## 十四、B2·A 落地：Owner 裁定 A（2026-09-17）

**裁定**：§十三.9 的三条修法里选 **A** —— 把「变更检测」的判据从
「**指纹变了**」改成「**声明集合变了**」。

一句话概括 A 改了什么、没改什么：

> **`content_key` 的算法一个字没改，改的是「它答哪一问」。**
> 它答「这是哪一版正文」，不再被当成「这两次看到的是不是同一个东西」。
> 「变没变」交给一个具名判据（`claim-set-v1`），而不是交给一个哈希。

| # | 落地物 | 位置 | 它守的是什么 |
|---|---|---|---|
| 1 | 具名判据 `claim-set-v1` | `base/change_detect.py`（新增，16 项自证 / 4 条必红） | 「变没变」有了唯一的判据，且判据名与词形指纹**随结论一起**返回 |
| 2 | `content_key` 措辞订正 + 守住它的断言 | `base/contract.py`、`schema`、`base/README.md` | 措辞是被人读、被代码照着写的 —— 所以由断言守住，不由文档自觉 |
| 3 | A 面从「人维护清单」改成「自动发现 + 双向对照」 | `base/verify_base.py` | **关掉遗留 24**：`base/` 下任何写了 `--selftest` 却没被跑的模块，当场红 |
| 4 | 证据补强：两版正文落盘（内容寻址）+ 判据名 + 逐条摘要 | `tools/lp_stability.py` | 让「判据改了不必重抓」第一次成为可执行的，而不是一句口号 |
| 5 | **判据的集成面**：`verify_landing.py` 的 V4 换问法 | `tools/verify_landing.py` | 裁定之后，任何仍用旧判据判红的地方**从那一刻起就是错的**（见 §14.6） |

### 14.2 ★★ 落地时先抓到的是一件别的事：「40 次观测」是**重复计数**

在动 `content_key` 之前先复核了 §十三.8 引用的那两个数，于是发现累计读数的算法有一个缺陷：

```python
d["runs"] = (prev.get("runs") or []) + [cur]   # runs 的末尾已经是 cur
agg = _aggregate(d["runs"] + [cur])            # ← 又把 cur 算了一遍
```

**一轮 20 个观测被算成了两轮 40 个。** 盘上只有一条观测账，
而 `累计` 写着「轮数 2 / 可判合计 40 / 变更触及合规 10」—— §十三.8 与 `base/README.md`
引用的正是这个 40 与这个 10。

**为什么它比前三个错更值得记**（§13.10 那三条，形态都是「检查静默失效」）：

> **前三个错让检查变得没用；这一个错让证据变得更多。**
> 「40 次观测里 10 次真变化」听起来比「20 次里 5 次」可信得多 —— 而它是同一个数。
> 百分比没被它带偏（两轮分母相同，30.0% 与 30.0% 都对），
> **被带偏的恰恰是「这个结论有多少证据托底」**，而那正是这个脚本存在的全部理由。
>
> 而它长什么样？**一份完全正常的 JSON、一张完全正常的表、退出码 0。**

**修法（三处，且不靠「调用点写对」）**：

1. 调用点改成 `_aggregate(d["runs"])`；
2. `_aggregate` **自己拒绝**把同一轮算两遍（`measured_at` 重复即抛错）——
   本项目的教训是**断言要能在下游独立成立**：一条只在调用点写对时才成立的检查，
   下一次有人复制那行 `+ [cur]` 就又没了；
3. `lp_stability.py --selftest` 把「同一轮喂两次 → 必须拒绝合并」做成**必红对照**。

外加两处同形态的修补（都是「少一个数而屏幕不说」）：
`main()` 里读不动历史时原本是静默 `d["runs"] = []`（累计分母悄悄缩水），改成**出声并说明后果**；
每轮入账前跑 `round_account_problems()`，**缺一个数就不许入账**。

> **盘上那条旧账还缺 `本轮 URL`**（字段是后来才加的）。补它用的是
> `--repair-ledger`：先断言「该条账的 `measured_at` 与顶层逐条相同 ⇒ 同属一轮」，
> 再断言 `可判` 与 `正文一致` 两个数逐一相符，**任何一项对不上就拒绝写盘**。
> 沿用 `media.py --reattach-weights` 的做法：**猜参数会让账错得很安静。**

### 14.3 判据：`claim-set-v1`

`base/change_detect.py`。三值结论 —— **中间那一档才是 A 买来的东西**：

```
① 同一版正文              正文逐字节相同
② 换了版正文 · 声明未变   ★ 把约 70% 的噪声滤掉的就是这一档
③ 换了版正文 · 声明已变   ★ 这一档才要报给人，且差集是「几个词」，不是 17,585 个字符
```

两条设计上的硬要求：

- **词形只有一份。** 判据从 `tools/lp_extract.py` 取 `CLAIM_RE`，不另写一份；
  自证里有一条断言「本模块抽出来的声明集合与直接查 `CLAIM_RE` **逐条相同**」——
  防的是「悄悄加了一层加工」。
- **恒为真与恒为假的判据都不许存在。** 自证里有两条必红：
  两版词形完全一致时**不许**报变化（旧判据在这里恒为真）；
  **空词形表必须被拒绝**（否则每一对正文都判成「声明未变」，
  而它长得和「今天什么都没变」一模一样）。

`base/contract.py --selftest` 新增 `[4c]` 组，把 A 的措辞变成**可执行的**：

```
✓ 同一个载体、两份正文 ⇒ 两个 content_key（key 是版本标识，不是页面标识）
✓ 同一个正文、两个不同载体 ⇒ 同一个 content_key（key 里没有 uri）
✓ unit_id 同样不含 uri：同一段文字、两个载体 ⇒ 同一个 unit_id
✓ 盘上 3 组折叠，全部折叠的是同一个 target（不是两个地址撞成一个观测）
✓ 必红：盘上确有 37 组「同 content_key、不同载体」
```

> ★ 其中**第三条是这一轮我自己抓到自己的一处**：我原本断言「unit_id 随载体变」，
> 实测**不随** —— `unit_id = f(kind, raw_sha256, text_sha256)`，**不含 uri**。
> 我错在照着自己写的文档措辞（「这一次观测是哪一次」）去断言，而没有去看实现。
> 由此浮出一个**真实边界**：两个**不同地址**若逐字节相同，会被折叠成一次观测。
> 本项目语料里没发生过，但它是可发生的 —— 所以第四条把它变成一条**会被看见**的检查
> （盘上 3 组折叠，全部是同 target）；真出现跨地址碰撞，它会红。

### 14.4 遗留 24 关闭：A 面改成「自动发现 + 双向对照」

原状：A 面的模块清单靠人维护。B1 交付 `media.py`（20 项自证）而清单里没有它 ——
那 20 项**没有任何东西会去跑**，模块回归了也没人知道。

只把 `change_detect.py` 加进清单是不够的：**那是把同一个洞留在原地等下一次。**
现在 A 面自己扫 `base/*.py` 找声明了 `--selftest` 的模块，与清单**双向**对照：

```
✗ 有 --selftest 却没被 A 面调用：…      → 后果是静默的：模块回归了没人知道
✗ A 面登记的模块里，这些没有 --selftest：…
✓ 清单与自动发现一致（6 个模块，双向无差）
```

外加一条**给探测本身**的断言：自动发现找到的模块 < 2 个即红 ——
否则探测坏掉时，上面两条差集会**假绿**。

### 14.5 证据补强：让「判据改了不必重抓」第一次成为可执行的

§13.8.2 已经把 `summarize()` 从 `refetch()` 里抽出来，理由是「判据改了不必重抓」。
**但这一轮要重算判据时才发现它做不到**：盘上的逐条里只有旧判据的**结论**，
**没有两版正文** —— `--analyze-only` 能重算计数，不能重算判据。

而词表**已经改过一次**（§12.4：两个词永远匹配不上，导致批次 C 一整批制品要重跑）。

三处补强（从下一轮起生效）：

| 补强 | 做法 | 为什么是这个做法 |
|---|---|---|
| 两版正文落盘 | 内容寻址 + gzip，文件名就是正文指纹（沿 ADR-0011 §一.5） | 跨轮去重免费；「这份正文是哪一份」由文件名自证 |
| 读回时**当场重算指纹** | 与指针不符即拒绝读回 | 不核指纹的读回等于相信文件名 |
| 判据名与词形指纹进逐条 | 每行 `合规相关性.判据` | 一个结论离开它的判据就没有意义 |
| 轮次账加 `逐条摘要` | 每轮记 url_key × 正文一致 × 触及合规 | 只有总数的话，「两轮都是 6/20」并不说明两轮**判的是同一批** |

新增 `--recompute`（不联网，用当前判据重算盘上每一行）；
改写证据必须是显式动作（`--write-back`），且会把**原判据名**记进 `判据变更历史`。

### 14.6 判据的**集成**面：`verify_landing.py` 的 V4 也必须换问法

A 改的是判据，而**任何还在用旧判据的地方，从裁定那一刻起就是错的**。
盘上正好有一处：`tools/verify_landing.py` 的 **V4** 原本问
「重抓时提取后正文的指纹一致吗」，不一致就判 ❌。

按 §13.8 的实测，那一问在隔日尺度上**约七成会红** ——
**一个按构造必然报红的检查，等于一个会被学会忽略的检查**
（这正是 §13.10 第 2 条那个「恒为真的判据」的镜像：一个是恒真，一个是恒假）。

V4 已拆成两件事：

| | 问什么 | 红了代表什么 |
|---|---|---|
| 指纹一致率 | 原始 HTML / 正文各自一致几个 | **不再判红** —— 它是观测值，隔日尺度上的期望就是约三成 |
| 判据面 | 每一条正文变化是否都被 `claim-set-v1` 接住，且「声明已变」必须列出差集词 | 判据跑不起来 / 词表为空 / **判为已变却说不清变了哪几个词** |

最后那一条是关键：**「说不清变了哪几个词」与旧判据是同一种病**（不可执行）。
判据给出「已变」却给不出差集，等于又要人去看那一万七千个字符。

`--recheck 3` 的实跑（3 条，`tools/verify_landing.py`）：

```
· 观测：原始 HTML 一致 0/3 · 提取后正文一致 2/3 = 66.7%
  （隔日尺度上的期望就是约三成；这一行是**观测**，不是合格线）
✅ 判据 claim-set-v1 判完全部 3 条：同一版 2 · 换了版未变 0 · **声明已变 1**
    ★ 声明已变的那几条（这是**发现**，不是缺陷）：
      au.momcozy.com/products/m5-smart-wearable-breast-pump-upgraded
         消失 {} / 新增 {"performance": ["20 hours"]}
```

★ 判据**每一行都判**（不只是变了的）：否则「判了几条」与「变了几条」会被混成一个数
（第一版就是这样，屏幕上写着「接住了全部 3 条变化」，而真正变化的只有 1 条）。
这与 §14.5 里 `lp_stability` 的修正是同一条：**判据要覆盖全部输入，不只覆盖异常输入。**

> ★ 顺带一个观察：这 3 条里正文一致率是 2/3 = 66.7%，而 20 条样本的率是 30.0%。
> **3 个样本说不出率** —— 抽检只回答「通道通不通、判据接不接得住」，
> 要说率就去跑 `lp_stability.py`。这也是 V4 把「一致率」降级为观测值的原因之一。

### 14.7 实测：修复后盘上的真实账

**四个百分比一个都没变** —— 变的只有它们**有多少证据托底**：

| | §13.8 引用的读数 | 修复后盘上的真实读数 |
|---|---|---|
| 轮数 | 「2」 | **4** |
| 观测次数 | 「40」 | **80** |
| 有效独立样本 | （当时没有这个概念） | **20** |
| 原始 HTML 一致 | 「0 / 40」 | 0 / 80 |
| 提取后正文一致 | 「12 / 40 = **30.0%**」 | 24 / 80 = **30.0%** |
| 变更触及合规 | 「10（**25%**）」 | 20（**25%**） |

> **这正是 14.2 那个缺陷危险的地方：它不影响结论的方向，它让结论看起来比实际更硬。**
> 如果不去复核那两个数，「40 次观测」会一直被当作已经攒下的证据量。

四轮的**逐轮**读数完全相同（每轮都是 6/20 一致、5/20 触及合规）——
所以「约三成」与「四分之一」这两个率是稳的；不稳的从来只是**账**。

### 14.8 ★★ 判定可复现 100%，而指纹可复现 30%

第 3、4 两轮的轮次账里都记了 `逐条摘要`（url_key × 正文一致 × 触及合规），
于是第一次可以**逐项**对照两轮：

| 问的是哪一层 | 两轮之间一致 |
|---|---|
| 原始 HTML 的 sha256 | **0 / 80 = 0%** |
| 提取后正文的 sha256 | **24 / 80 = 30.0%** |
| **判据给出的逐项结论** | **20 / 20 = 100%** |

> **「重跑能不能得到一样的数」这个问题，在指纹那一层是 30%，在判定那一层是 100%。**
>
> 这就是 A 的要点本身：**哈希答不了「变没变」，判据答得了。**
> 30% 不是「指纹有缺陷」，是**问错了对象** —— 一个逐字节的哈希必然会被
> 评论数、价格、促销横幅推动；而「合规相关声明变了没有」在这两轮之间**一个都没变**。

**重算验证**（`--recompute`，不联网，吃的是落盘的两版正文）：

```
逐条 20 行 · 可重算 20 · 不可重算 0
用当前判据重算 → 逐项一致 20 / 20
带判据名的行 20 / 20
```

**两个判据并排**（同一批 20 条观测）：

```
旧判据（指纹变了）        14 / 20
新判据（声明集合变了）     5 / 20
★ 新判据多滤掉的           9 / 20
```

被滤掉的 9 处不是「没变」—— 是**变了，但变的东西与合规判定的输入无关**。
两者的处置完全相反：前者要人去看，后者不该进人的待办。

## 十五、B3.0 落地：需求文档治理 —— 让文档里的数字重新变成算出来的（2026-09-17）

> **编号说明**：§二那张表里的 B1/B2 是**流水线**分期（形态接入 → 指标）。
> 本轮起 `B` 号按**交付线**走：B1=图片、B2=文本两组指标与判据、**B3=需求知识库**。
> §二 表里原 B2 的「4 类知识库实例化 + 需求治理未决收口」正是 B3 的内容，与
> 「流水线 B2」不是同一件事 —— 这个双轨在 §五 遗留里已有编号（遗留 25），此处是它第二次咬人。

### 15.1 起因：先复核 B3 自己的验收门

B3 的 Done 条件写在 §二：**「10 条黄金问题全部可答」**。动手做 P2 之前先跑了一遍
`python3 tools/verify_kb.py` —— 全绿。但同一份输出里，`Q7` 明明白白印着
「❌ **GAP：无法回答**」。**门是绿的，门后面的东西是缺的。** 于是查门。

### 15.2 ★★ 那条检查的输入里根本没有变量

```python
c.add("D2", "缺口显式声明", True,
      f"声明 GAP 的：{gaps}（声明出来就不是欺骗，静默略过才是）")
#                        ↑ 这个 True 是字面量，不是任何一个算出来的东西
```

`D2` **永远绿**：无论有没有缺口、缺口有没有落点、落点里写的是不是真的。
它的立场是对的（「声明出来就不是欺骗」），但它守不住那个立场 —— 一个不接受
任何输入的判据等价于没有判据，而**比没有判据更坏**：它让
「10 条黄金问题全部可答」这句话看起来有机器背书。

**这是那条纪律的又一个实例**（见 §14.2 与 `PMU/内容合规-阶段性复盘` 里那句
「废检查（恒真）比没有检查更坏」）：**不影响结论的方向，只让结论看起来更硬。**

### 15.3 手册里那条「可复现命令」复现不出手册里的数

`Q2` 的基准日原本是 `load.today()`。于是：

| | 逾期条数 | 基准日 |
|---|---:|---|
| 盘上 `查询手册.md`（09-16 生成） | **30** | 2026-09-16 |
| 09-17 重跑同一条命令 | **33** | 2026-09-17 |

**手册里写着「`python3 tools/kb_query.py 2`」，而这条命令给出的是另一个数。**
`D3` 只检查「手册里有 ≥10 节」，所以没有任何东西会发现它 —— 每过一天这句话
就更假一点，而它**不会自愈**。

修法不是「记得重生成」，是**把基准日钉在数据上**：
`load.basis_date()` 取快照 MANIFEST 的 `taken_at_utc` 按 Asia/Shanghai 落日。

> **逾期是数据的属性，不是提问时刻的属性。** 想知道今天的逾期，就重新拉快照。
> 这与 §一「v1 不做实时同步」是同一条取舍，只是过去没有贯彻到判据上。

### 15.4 同一个数在两处自相矛盾，而代码就在旁边

| 位置 | 写的 | 实际 |
|---|---|---|
| `research/kb/README.md` §四.4 | 「材料 15 条里只有 **5** 条能读」 | **4** |

`main()` 每次都打印「材料可读性：可读 4 / 不可读 11」，而同一份文件的散文里写着 5。
**代码在算，散文在猜，谁也没红。**

### 15.5 「已登记」这四个字当时没有任何落点

`Q7` 的结论里有一句：`→ 已登记为对源系统的数据需求：状态变更需留痕。`
全仓搜「状态变更」：只有 `查询手册.md` 与 `README.md` 两处散文，以及 README 表格
里的一行字。**「已登记」= 我写下了这句话。** 与本 ADR 反复出现的那族
「声明了没实现」是同一条。

**修法：让那句话变成读出来的，而不是写出来的。**

- 新增 `research/kb/缺口-v1.json`（生成物，`tools/kb_gaps.py`）：**8 条缺口 / 五类**
  （data / access / classification / evidence / schema），每条带编号、影响哪条黄金问题、
  **量**、责任人、状态、复算命令与提出方式；
- `Q7` 不再打印散文，改为 `_gap_lines("D1")` —— 登记表里没有这一条就打「**未登记**」；
- 每个缺口的「量」必须能在 `tools/kb_facts.py` 里重算对上；算不出来的必须显式写
  `量_unrecomputable` 并说明理由（现 2 条：D7 样例判读、D8 制品未建）。

**顺带纠正了 `Q7` 原来的理由**：它说「源系统没有状态变更时间戳」——对；但它隐含
「所以没有任何时间字段」。实测需求类表里有**四个**名字带「开始」的字段，且在跑记录里
填得不少（seo 48/48、创意支持 22/41、视频 18/22）。它们是**实际开始**还是**计划开始**
未确认（【平面】那张表干脆叫「计划开始时间」）→ 记为〔缺口:KB-GAP-2〕，
**语义未确认前不得进判据**，否则会把「排期没到」算成「卡住了」。
缺口因此从「什么都没有」变成「有四个候选，差一次语义确认」——判据没变宽，理由变准了。

## 十七、B0.1 遗留：`engine_version` 冻结台账的漂移（2026-09-17）

制品后被改，提交发生在漂移之后。逐条核对也支持这个读法：manifest 的 `engine_version`
**按它自己存的 sha256 重算完全自洽**（`30f10be717c09e9c`），即它是一份**真实历史状态**的快照，
不是被手改坏的台账。

**它为什么没被任何一套验收抓到。** 本轮实跑：七套验收脚本（`base/verify_base.py` · `tools/verify_engine_contract.py` · `verify_external` · `verify_kb` · `verify_landing` · `verify_skill` · `verify_vocab_lark`）与六个 `--check` 工具，在漂移期间**都是绿的** —— 因为其中没有一条问过「真目录的 manifest 对不对」。
直接原因是 `tools/verify_engine_contract.py` 的 V11a–V11c
**全部在临时副本里跑**（`cwd=tmp`，`shutil.copytree(SKEL, tmp)`）—— 副本是拷出来的，
拷贝那一刻真目录是什么状态，门就只测什么状态。**它在原理上就看不见真目录的漂移。**

### 17.2 V11b 在那一天是一道假绿

V11b 原文判据：`ck.returncode == 1 and "sha256 不符" in ck.stderr`。

实测（2026-09-17，真目录漂移期间）：把 `SKEL` 拷成副本后**不做任何改动**，`--check` 已经是
exit=1 —— 判据在「什么都不做」时即已满足。也就是说这道门**恰好在它最该起作用的时候失效**：
它分不清「抓到了我这一改」与「副本拷出来本来就坏」。

**修法**：先 `--write` 固化副本并断言基线为 0，再改动。现在输出 `基线=0 改动后=1`，
红才是这一改造成的。

### 17.3 同族第二处：`code_version` 只写不校

`check()` 原先只比 `artifacts[].sha256` 与 `engine_version`，**从不比 `code_version`**。

而 ADR-0012 §166 决定分离 `engine_version`（数据）与 `code_version`（代码），理由逐字是
「改一行 `judge.py`，`engine_version` 纹丝不动」。**分离做了，校验只做了数据那一半。**

代价可复现：改 `engine_manifest.py`（本文件自己就是 6 个 `CODE_FILES` 之一）之后
`--check` 照旧 exit 0，manifest 于是把「哪版代码判的」（回执字段 `agent_version`）
记成假话，且没有任何东西会红。

**已补**：`check()` 现在也比 `code_version`，并点名是哪个文件变了。
反向对照是本轮天然发生的 —— 我改完 `engine_manifest.py` 后 `--check` 立刻红：

```
code_version 不符 manifest=c95b42d9f0e58ebb disk=a45ef12ba540c87d（变了的：engine_manifest.py）
```

重新固化后转绿，且 `engine_version` 不变（数据没动）、`code_version` 变 —— 分离正确。

### 17.4 那句把人劝退的错误提示

`engine_manifest.py` 的 `--check` 失败提示原文：

> ★ 重新固化会让所有引用旧 engine_version 的回执指向一份已不存在的规则集——这是特性，不是麻烦。

**它与同文件 `archive_previous()` 的实现直接矛盾**：`--write` 正是先把「正要被覆盖的」
manifest 追加进 `_data/manifest-history.jsonl`，`resolve_version()` 再按 `engine_version` 反查。
而 **ADR-0012 §6.1 在 2026-09-16 就记过这一条**，并实测过 5 条旧回执在四次重新固化后
仍可逐条解析。

**代价是可量的**：这句话让「该不该重新固化」看起来像一次有损操作，**于是没人敢固化** ——
上表三次改动都没固化，漂移就这么留了下来。

★ **我自己也照抄了它。** 我把这句话原样报给 Owner，当成一个真实的取舍
（「修 = 让旧回执指向一份不存在的规则集」）。两处能证伪它的原文
（`archive_previous()` 的 docstring、ADR-0012 §6.1）**我都没读**。
这是本轮我犯的错，形态与 §11.4 / §13.10 / §15.7 记的那几次完全一样：
**把一句读到的文本当成已核实的事实。** 已改正该提示并在代码注释里留痕。

### 17.5 改判：`manifest-history.jsonl` 由 `derived` 变 `primary`

§三 L2 原文把它与 `records.json` / `rules_raw.json` 同格，理由写
「**可复算**：源表在 PRD + 生成脚本 + 飞书可重拉」。

**该理由对这个文件为假。** 账本每行记的是那一次冻结时六个制品的真实 `sha256`，
而那些字节**没有第二份**：飞书重拉、生成脚本、源表都拿不回 2026-09-16 18:07 的
`rules-v1.json`。

而 `base/verify_base.py` 把它登记为 `class: "derived"` + `generator: engine_manifest.py`
+ 六个输入 —— **B 面因此绿**，因为 B 面只查「生成脚本在 L1 + 输入可追溯」，
**不查「跑出来是不是同一份」**。

§11.2 逐字预警过这个形态：

> 如果笼统要求全部可复算，结果只会是给不可复算的东西**编一个假的生成脚本**。

**这一条就是那个假脚本** —— 它躺在 `primary` 条目上方十行处没被认出来，
因为**它长得和邻居一模一样**。

**处置（不是改决定，是让台账与制品一致）**：§三 L2 拆出一行、`verify_base.py` 改判
`primary`，两处互相标出。

### 17.6 ★★ 改判解决的是判据，没有解决耐久性 —— 这一条要 Owner 定

`manifest-history.jsonl` **被 `.gitignore` 忽略，不在版本控制内**
（收在「追加型账本：只会增长，不需要 diff 与回滚」那一组）。

而 ADR-0012 §6.1 对 Owner 的承诺是：

> 「指向一份不存在的规则集」已经变成「指向历史里的一次快照」。
> 所以下一次迁移的公告成本从「回执作废」降为「回执指向历史」，可以做了。

**这个承诺目前只在本机成立。** 实测：

| 事实 | 值 |
|---|---|
| 账本条目 | 10 条 |
| 其中不同 `engine_version` | **8** |
| git 里能拿到的版本 | **1**（`30f10be717c09e9c`，即 `45d1810` 那次提交） |
| ★ **只在账本里、git 里没有的版本** | **7** |
| 这 7 个里有第二份副本的 | **1**（`f516c14c1a2284fb`，在 `_data/backup-batchD/` —— **该目录同样被忽略**） |
| 因此**全仓只有一份副本**的版本 | **6** |

★ 附带一个不好笑的巧合：唯一有第二份副本的那一版 `f516c14c1a2284fb`，
**正是 ADR-0012 §6.1 拿来做实测的那一版**（「现存 5 条回执全部指向 `f516c14c1a2284fb`」）。
那条实测成立，靠的是运气，不是设计。

**这不只是理论风险 —— 同一个目录里已经发生过一次。** `_data/receipts.LOSS.md`（**已入 L1**）
记录：2026-09-16 一次 `cp` 参数写反，真账本 5 条回执丢了 4 条，**不可恢复**。
当时逐条核查的不可恢复理由里，第一与最后一条是：

> - `git`：本目录不是仓库
> - 全仓搜索残留副本（`_data/backup-*/`、**`manifest-history.jsonl`**）：无

★ 注意最后一行：那次事故**已经把 `manifest-history.jsonl` 当成「可能有残留副本的地方」去搜过**。
**它是被当作存档用的，却没有被存档。**

而且那次事故之后加的三道机制（前缀哈希链 / 测试回执不得进生产账本 / `--status` 记行数）
**全部是「防重犯」，没有一道是「能恢复」**：哈希链能证明账本被动过，却证明不了内容是什么。
事故文档自己的结论是「**没有一道检查站在那一步上**」—— 对耐久性而言，今天仍然没有。

**为什么这要 Owner 定**：把该行从 L2 移进 L1，等于改掉 §三 对「追加型账本」**整行**的既有理由
（「只会增长，不需要 diff 与回滚」）。那是 ADR13-D7 的应用，不是开发者可以自行改的。
**本轮不动，只登记。**

| | 候选处置 | 代价 |
|---|---|---|
| **A**（推荐） | 该账本移入 L1（`git add`），此后每次 `--write` 连同 manifest 一起提交 | 每次固化多一个待提交文件；账本线性增长（当前 33 KB / 10 条，年量级仍很小） |
| B | 维持 L2，但每次 `--write` 按版本号另落一份快照到 L1（如 `_data/manifest-archive/<version>.json`） | 同样进 git，每版一个文件、可单独引用；代价是文件数增长 |
| C | 维持现状，只写进「加远端前必须一并重估」那一批 | 承诺继续只在本机成立；下一次误删仍不可恢复 |

**推荐 A**：最小、最直接命中「唯一副本」这个性质，且与 `receipts.LOSS.md` 的教训同向
—— 那次事故之所以不可恢复，正是因为账本没进版本控制。
