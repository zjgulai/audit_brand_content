- 状态：`accepted`（Owner 于 2026-09-17 经九道选择题逐条决定；**接受只代表设计决策已定，不代表已实现、已验收或可上生产** —— 见 `ADR/README.md` 规则 4）
- 日期：2026-09-17
- 决策者：Owner（D1–D9 全部由 Owner 选择，九条均采纳开发者推荐选项）
  开发者（分级的判据设计、`ContentUnit` 字段形状、同步契约的冲突语义）
- 依赖：ADR-0001（数据权威与双账本）· ADR-0002（记录级溯源与版本化）·
  ADR-0003（敏感样本分级准入，**`proposed`**）· ADR-0005（工具只补证据不替人过门）·
  ADR-0009（语境守卫独立成表 / 所有权分离）· ADR-0011（落地页内容获取的边界与节流）·
  ADR-0012（判定引擎产品化与处置分层）
- 触发：Owner 提出「先搭基座、等业务给 PRD 再做前后端联通」，并要求覆盖
  **多内容格式解析 / 需求文档治理 / 知识库 / skill** 四项。据此做了一次只读盘点。

> ★ 盘点过程中确认了一件**与规划无关、但改变排序**的事：
> **本目录不是 git 仓库**（`git rev-parse --show-toplevel` → `not a git repository`；
> `.git` 不存在，上级目录也没有；根目录无 README / 构建清单）。
> 也就是说 —— 14 个 ADR、161 项验收、291 条差分 0、四份验收脚本，
> **全部没有版本历史**。今天任何一次误改都不可回滚，
> 而「记录级溯源」正是 ADR-0002 的第一条地基。
>
> ★ 另一件在动手时才发现的事：**`git init` 这一刀本身会撞出安全问题**。
> 目录里同时存在真实凭据与浏览器会话数据（见 §三）。所以 D7/D8 不是「顺手加个
> `.gitignore`」，而是一条需要 Owner 单独拍板的入库规则。

## 一、决策

### D1 · 第一刀 = 建版本控制 + 冻结两个接口

顺序不是偏好问题。**基座里只有两处「不做完就会在 PRD 到来时返工」**，
其余三处已经立好，PRD 到位后只做装配：

| 面 | 契约 | 今天 | 会不会返工 |
|---|---|---|---|
| ① 进 | `ContentUnit` + 解析器 | 文本已通；落地页有抓取提取但**未接引擎**；图片/视频 0 | **会** —— `assess(text: str)` 的签名容不下三种新形态 |
| ② 判 | `judge(unit) → Verdict` | **已建成**（ADR-0012） | 不会，只差一层适配 |
| ③ 供 | 权威源 + 版本 + 4 类知识库 | 品线维度机制就绪但**零条规则声明**；规则为本地手工 JSON；4 类知识库只有 1 类有料 | **会** —— PRD 到来后业务与法务要改规则 |
| ④ 出 | 处置五层 DP0–DP4 + 回执 | **已建成**（ADR-0012） | 不会 |
| ⑤ 证 | 版本控制 + 验收 + 度量 | 4 份验收脚本齐备 | **会** —— 无版本历史则不可回溯 |

因此 B0 只做两件事：**立版本**、**冻结①②③三面里会返工的两处**。

### D2 · 飞书 Base 是规则与词表的唯一权威源，本地 JSON 是只读投影

- 方向**单向**：飞书 → 本地。本地不得回写权威源。
- 同步必须带**内容指纹**；指纹不一致而记录 id 相同 ⇒ **报错退出**，不静默合并、不取「较新者」。
- 依据：ADR-0001 已实测「飞书 API 无内容指纹、无 diff、无回放能力」，ADR-0009 已把
  「人写规则主 Base（app 只读）」与「app 维护机器词表 Base」分开。
- **本决定不新建 Base**：权威源已经存在 —— `_evidence/rulelib-live.json` 就是从飞书拉下的
  逐字快照（21 条规则，带 `record_id` 与全部字段）。B0 做的是把这次性拉取**固化成契约**。
- **投影仍入历史**（见 §三 L1）：正因为飞书没有 diff 与回放，
  本地副本的版本历史才是唯一能回答「上周那次判定用的是哪版规则」的地方。
  这不是冗余，是 ADR-0001 双账本在本层的具体含义。

### D3 · 图片与视频先只做「文本化」，不作语义判定

- 图片：OCR 取图内文字 + 合成人像标记检测；视频：字幕/ASR 转写 + 关键帧 OCR。
- 产出统一进 `ContentUnit.verdict_text`，**复用现有 21 条规则**，不新增判定机制。
- 理由：今天**没有图片/视频的标注集**，多模态直接判定的精度无法度量 ——
  那会把「判不了」伪装成结论，正是本项目从第一天起拒绝做的事。
- 代价已写进 §四：图内**非文字**的违规（画面暗示、构图）本决定覆盖不到。

### D4 · 4 类知识库从「措辞表达库」开始实例化

- 依据：存量 291 条里已现成提取出 60 个真实片段（`PMO/内容合规-阶段性复盘-20260916.md` §3.2），
  是四类中**唯一「今天就有料 + 直接提升引擎覆盖」**的一类。
- 其余三类（外部标准库 / 内部正负样本库 / 产品描述库）排在 D4 之后，不阻塞 B0/B1。

### D5 · 需求知识库的三条未决按「先记录不阻塞」收口

| 未决 | 处置 |
|---|---|
| `资源账号管理`（含密码，11 条） | **整体排除**（与 `research/kb/需求知识库-建设方案.md` 默认一致），理由写明：无脱敏方案前不纳管 |
| E/F/G/H 四条材料链接失效 | 记为**外部依赖**，不阻塞台账；等 Owner 补链接后单独补录 |
| 台账刷新节奏 | 定**定时**，且**排在谷时**（DeepSeek 官方线路峰时 ×2，见成本扫描结论） |

三条一律写进 `legal-decisions-v1.json · $decision_queue` 的书写位置，
不散落在方案文档里（该位置由 ADR-0012 · D12 收拢，本次沿用）。

### D6 · skill 做成 DSH 技能包，任何 agent 可按规程调用

- 不采用「只扩守衡工具集」两条腿：那会让规程散在两处，
  而「同一判据写两处就会漂移」正是本项目已复发三次的病（ADR-0007 → 0008 → 0009）。
- 技能包与守衡共用**同一条验收命令**，不共用两份实现。

### D7 · 仓库分三层，判据是「会不会被人改」，不是「大不大」

| 层 | 判据 | 处置 |
|---|---|---|
| **L1 入历史** | **人写的、会被改的、改了要能回滚的**；以及「权威源无 diff/无回放」时，唯一能答版本问题的本地投影 | `git add` |
| **L2 入盘不入历史** | **机器生成的、可复算的、内容寻址的、别人管的** | `.gitignore`，文件保留在盘 |
| **L3 永不入盘** | **凭据**与**会话数据** | 移出项目目录 |

→ 逐条清单见 §三。

### D8 · 凭据移出项目目录

`PMO/腾讯云-周健-SecretKey.csv`（92 字节，真实凭据）→ `~/.dsh/credentials/`（与既有
`shouheng-lark.json` 同处，目录权限 `700`、文件 `600`）。
**移出工作区，而不只是加 `.gitignore`** —— 工作目录本身可能被同步、备份、打包或分享。

### D9 · `ContentUnit` 采用双指纹

| 指纹 | 答什么问题 | 依据 |
|---|---|---|
| `raw_sha256` | 这条判定看的是**哪份原件** | 溯源需要；落地页会变 |
| `text_sha256` | **重跑能不能得到一样的结果** | ADR-0011 实测：原始 HTML 指纹 3/3 变化，提取后正文 3/3 一致 |

两者都要：前者是 ADR-0002 的记录级溯源要求，后者是 ADR-0005「没有 receipt 的判定不算发生过」的复现前提。

## 二、落地分期（B0 / B1 / B2）

| 期 | 内容 | Done（可验收） | 依赖 PRD |
|---|---|---|---|
| **B0 · 1 周** | 立版本 + 冻结 `ContentUnit` / `judge(unit)` + 规则单向同步 + `verify_base.py` | 五面各一条自证命令全绿；`git log` 有历史；任意文案与任意 URL 都能变成 unit 进 judge | 否 |
| **B1 · 2–3 周** | 文本 → 落地页 HTML → 图片 → 视频，逐个接进管道；每形态按法务口径各测三个指标 | 四种形态各有「获取成功率 / 识别完整度 / 处理耗时」三个数字 | 否 |
| **B2 · 2–3 周** | 4 类知识库实例化 + 需求治理三条未决收口 + skill 化 + 一次模拟端到端送审 | 10 条黄金问题全部可答；任意 agent 能按规程调起审查 | 否 |
| **之后** | **装配层**：卡片状态机 / 状态落多维表格 / 回调 / 审批 / 任务 | 才需要 PRD | **是** |

**范围边界（明确不做）**：不做前端（等 PRD）；不做「贴进来就告诉你能不能投」的机器人
（54.6% 落 CATCH-ALL，会把「不知道」说成「没问题」）；不让业务在卡片里直接改规则
（规则变更必须有单一权威实现）。

**周期账**：会议定 3 个月，当前第 1 周。B0+B1+B2 ≈ 6–7 周，余下 5–6 周给 PRD 到位后的
装配与真实试跑。B0 若拖成 3 周，后面余量即被吃掉。

> 「生成脚本 + 输入指纹」，就说明它被分错了层。

## 四、后果

### 4.1 得到什么

1. **可回滚**：14 个 ADR、161 项验收、四份验收脚本首次拥有版本历史。
2. **接口冻结**：B1/B2 的每一项能力都有确定的插入位置；PRD 到位后接的是装配层，不是重做。
3. **权威源单向**：业务与法务改规则不必经手开发者，且每次同步可被指纹检出漂移。
4. **凭据离开工作区**：目录被同步/备份/打包不再泄露。

### 4.2 **没有**得到什么（必须说清，否则会被当成已解决）

1. **L1/L2 分级不解决素材保密。** 它解决的是**体积**与**凭据/会话数据**。
   291 条真实广告文案与费用数据**仍会进历史** —— 因为它们就在 `PRD/内容治理需求文档.md`
   的「广告文案明细」表里，而该文档属于 L1。
   素材保密是 **ADR-0003（敏感样本分级准入，`proposed`）** 的事，本 ADR 不动它。
   ⇒ **推论：本仓库本轮不设远端。**设远端等于「开放外部输入」，依 `ADR/README.md` 规则 3
   须由 Owner 重新确认，且必须先结清 ADR-0003。
2. **D3 的文本化覆盖不到图内非文字违规**（画面暗示、构图、品牌调性），
   也不覆盖视频的音调、节奏、字幕与画面对不上的情形。
3. **`account-owners.csv` / `site-owners.csv` / `lark-visible-people.csv` 含真人 open_id。**
   本地无虞；**加远端前必须重估**（与第 1 条同批处理）。
4. **本地投影入历史 ≠ 权威源被版本化。** 飞书侧的改动历史仍然不可查；
   本地历史只能证明「某次同步时它长什么样」。
5. **飞书 `app_token` / `file_token`（Base 与文档的内部标识）会进历史。**
   实测：`tools/live_snapshot.py`（6 处）、`tools/kb_materials_lark.py`（15 处材料 token）、
   `tools/migrate_whitelist_to_lark.py`、`tools/migrate_vocab_to_lark.py`、
   `research/live/snapshot-*.json`（9 处）均含此类标识。
   它们**不是凭据**（token 本体在 `~/.dsh/credentials/`，已在项目外；拿不到
   `tenant_access_token` 就访问不了），且大部分已随飞书链接出现在 `PRD/内容治理需求文档.md`（同为 L1）。
   但它们是**内部资源标识**，与第 1 条同批处理：**设远端前必须一并重估**。
   ★ 提交前已跑内容级扫描：暂存区**无硬编码凭据** —— `SecretKey` / `api_key` / `password`
   的全部命中均可解释（minified JS 的库字符串、API 路径、或讨论凭据的说明性文字）。

## 六、异议留档（`ADR/README.md` 规则 5）

**异议一：D7 把 `records.json` 排除出历史，我不完全同意，但代价可接受。**

反对理由：`records.json` 是判定链的直接输入（`score.py:226` 读它），
把它移出历史意味着「上周跑的那版输入」不可回滚。

接受理由：它**可复算** —— 源表在 L1（`PRD/内容治理需求文档.md`）、脚本在 L1、
飞书可重拉，且产物自带指纹。为守住这条，
**B0.5 的 `verify_base.py` 必须包含一条检查：L2 的每个关键产物都能在 L1 里
找到它的「生成脚本 + 输入指纹」，找不到即红。** 若该检查做不到，本分级即失效，
D7 需重议。

**异议二：D3 的「先文本化」会让图片打样看起来覆盖了、实际只覆盖了一半。**

反对理由：会议明确要求打样覆盖「文字、图片、视频」三类。只做 OCR 的图片审查，
对「画面暗示功效」这类真实风险完全无感，却会因为跑出了数字而被当作已覆盖。

接受理由：替代方案（多模态直接判定）今天无法度量精度，代价更大。
**但必须让「覆盖到哪」显式可见**：B1 的图片/视频指标里要写清
「本数字只覆盖图内文字，不含画面语义」，并进 `boundary_statement.unknowns`。
不得只报「识别完整度 X%」而不写它的边界。

**异议三：九条决定全部采纳了开发者推荐选项，缺少对抗性检验。**

## 七、落地时发现：`.md` 文件被企业 DLP 透明加密加长 4096 字节（2026-09-17 · 已定位）

**发现方式**：执行 D1（`git init` 前的内容核对）时，`read` 工具拒绝两处合法 UTF-8 文件，
报 `binary file`。追查到底后确认：**不是文件内容坏了，也不是那个工具有 bug。**

### 7.1 最小复现（决定性的那一个）

同一目录、同一时刻、逐字节相同的内容，**只改扩展名**：

| 文件 | `st_size` | 实际读到 | 磁盘分配 | 差 |
|---|---:|---:|---:|---:|
| `/tmp/_repro.md` | 8118 | 4022 | 8192 | **+4096** |
| `/tmp/_repro.bin` | 4022 | 4022 | 4096 | 0 |
| `/tmp/_repro.txt` | 4022 | 4022 | 4096 | 0 |

**差值只跟扩展名有关 —— 与目录、内容、时刻都无关。** 这一条推翻了本节初稿的判断。

### 7.2 读数的分裂

| 取数方式 | 读数 | 为什么 |
|---|---:|---|
| `/usr/bin/stat` · `ls -l` | 真实 **+4096** | 直接读 `st_size` |
| `wc -c < 文件` · `dd if=文件` | 真实 **+4096** | 对普通文件走 `fstat`，**不实际读取** |
| `cat 文件 \| wc -c` · `python` · `mmap` · `cp` · `git blob` | **真实** | 真正读字节 |

多出的 4096 字节**确实被分配了**（`blocks` 由 8 涨到 16，即 8192 字节），
在全新文件上读出来是**全零**。

### 7.3 它会自己回来

- **原子替换可以临时修好**：读干净数据流 → 写临时文件 → `os.replace`。
  修完立即复验：271/271 全部一致，inode 已更换。
- **但 30 秒后复发，且 inode 再次更换。**
  受控实验（5 个文件，全程记录 inode）：

  | 时点 | `st_size` | 真实数据 | inode |
  |---|---:|---:|---:|
  | 修复前 | 19136 | 15040 | 11201472 |
  | 修复后立刻 | 15040 | 15040 | 11205660 |
  | **+30 秒** | **19136** | 15040 | **11205677** |

- ⇒ **不是一次性损坏，是一层介入在持续维护这个状态。**

### 7.4 影响

| 对象 | 是否受影响 |
|---|---|
| **文件内容** | **否** —— 所有真读字节的路径都得到完整、合法 UTF-8、语义完整的内容 |
| **git 仓库** | **否** —— `git add` 存入干净版本；提交后 `git status` **为空** |
| **判定引擎** | **否** —— 161/161 验收通过，读的就是这些文件 |
| **`read` 工具** | **是** —— 它按 `st_size` 读，读到 4096 字节尾部，遂判 `binary`。**它没有错。** |
| 任何按 `st_size` 预分配的消费者 | 是 |

**★ 更正本节初稿的一处过强判断。** 初稿把范围写成「只限本目录」，
并称之为「一条磁盘健康信号」。**这是错的** —— 7.1 的最小复现证明：
它在 `/tmp` 下同样成立，且只跟扩展名有关，与本目录、与磁盘健康都无关。
这段更正**保留在正文里而不删掉**，因为「先写下判断、再被自己的实验推翻」
这件事本身值得留痕 —— 它正是 B0.5「自证」要防的那类错误。

### 7.5 处置与遗留

- **修复无意义，已停手**：原子替换会在 30 秒内被撤销，且每次替换都换 inode。
  继续做只会制造 inode 抖动。已修复的 271 个文件**内容零改动**（逐文件 md5 前后对照，271/271 相同）。
- **不阻塞 B0**：内容、git、引擎三条都不受影响。
- **实际代价只有一条**：`read` / `edit` 工具在受影响的 `.md` 上会失败。
  绕行方式已验证可行 —— 用 `python3` 经 bash 读写（`read` 工具的判断依据是 `st_size`）。
### 7.6 这层介入是什么 —— **已定位（2026-09-17）**

**不是磁盘问题，是企业的数据防泄漏（DLP）透明加密。** 实测证据：

| 证据 | 值 |
|---|---|
| 已加载内核扩展 | **`com.tipray.trldKext (5.02)`** —— 天锐绿盾（TipRay） |
| 常驻进程 | `/usr/local/.trld/bin/tr_daemon`（多实例）、`TrTrayForMac.app`、`TrFinderSync.appex` |
| LaunchDaemons | `com.trld.tr_daemon` · `com.trld.tr_kext` · `com.trld.tr_userdog` |
| 端点安全系统扩展 | `com.kaspersky.kav.sysext`（Kaspersky，亦为活跃端点安全扩展） |
| 类型相关性 | 同一测试中 `.md` +4096、`.txt`/`.bin` +0 —— 与 DLP 按文档类型分类加密的行为一致 |

**机制**：DLP 对「文档类」文件做透明加密，加密元数据块占 4096 字节。
读文件时内核扩展对**被授权的进程**透明解密，于是：
`st_size` 显示密文长度（真实 +4096），而 `cat`/`python`/`git` 读到的是解密后的原文。

**这把本节的四条结论全部解释了**，且**推翻了「磁盘健康」这个初稿判断 —— 它已彻底撤回。**

### 7.7 对项目本身的三个后果

1. **D7「本轮不设远端」多了一条独立理由。** 原先的理由是 ADR-0003（敏感样本分级准入）未结清；
   现在多一条：**该目录处于企业 DLP 管控之下，向外部远端推送可能被策略阻断或构成数据外泄**。
   设远端前必须同时过这两关。
2. **`read` / `edit` 工具在本仓的 `.md` 上不可靠**（凡 `st_size` > 4096 者）。
   已验证的绕行：用 `python3` 经 bash 读写。**这不是工具 bug，不要报给它。**
3. **透明解密依赖进程被 DLP 授权。** 今天 `git`、`python`、引擎都在授权范围内（161/161 通过）。
   若日后换用户、换终端或换进程身份，**可能出现「同一命令昨天能读、今天读不了」** ——
   这类故障会伪装成「文件损坏」，届时先查 DLP 策略，不要先查文件。

## 九、B0.3 落地：`judge(unit)` 适配层（2026-09-17）

**交付物**：`base/judge_adapter.py`。自证 `--selftest` → **全绿，22 项检查 + 4 条反向对照**。

### 9.1 这一层存在的理由：引擎的边界声明里有一句话变成了假话

`skeleton/judge.py:220` 的 `unknowns` 里写死着一句（同一句还以机器可读形式出现在
`boundary_statement.not_covered_carriers`）：

> **未覆盖的载体**：本判定只看文本。图片、视频、**落地页正文**、A+ 详情页均不在输入内。
> 批次 C 已产出落地页正文的获取能力，但**尚未接入本引擎**。

在一个 `landing_page` unit 进判定时，**它逐字是假的** —— 那份判定的输入就是落地页正文。
而 `judge.py` 自己的 `_layer_note()` 已经立过「一句写死的免责声明迟早会变成假话」这条原则。

⇒ **D27 · 边界订正在适配层做，不在引擎里做。** 改 `judge.py` 是改引擎，且 161 项验收盯着它；
而 unit 知道自己是哪种载体，也只有它知道。订正动作进 `boundary_statement.$corrections`，
**留痕不静默**。订正**按载体分**：对广告文案引擎那句仍为真，**不动**。

实测对照（`python3 base/judge_adapter.py --boundary-report`）：

| | |
|---|---|
| 订正前 | 「…落地页正文…**尚未接入本引擎**」 |
| 订正后 | 「**载体：落地页正文——已接入，但只覆盖到文字那一层。**…**不含画面语义**，也抓不到 JS 运行时渲染出来的内容」 |
| `not_covered_carriers` | `['图片','视频','落地页正文','A+ 详情页']` → `['图片','视频','A+ 详情页']` |

### 9.2 `judge()` 的回执答不了「哪份原件」

引擎回执只存 `input_sha256`。这对广告够用（正文就是原件），对落地页不够 ——
同一段正文可以来自无数份 HTML（§8.1 三：raw 变 4/4 而正文变 0/4）。

**D28 · 适配层的回执加一个 `unit` 块**（双指纹 / 载体 / uri / 两个档位名 / 文本化边界），
**仍不含原文与片段**。实现上刻意**不重写** `obligations` —— 那是法务所有的契约字段，
抄第二份实现迟早不一致；改为让 `judge()` 照常生成完整回执（写临时路径），
本层补 `unit` 块后再经**生产闸门** `append_receipt()`（origin 检查 + 前缀哈希链）落账。

### 9.3 一条自证断言，与它抓到的一句假话

**J2 · 正文原样到达引擎**：`result["input"]["text_sha256"] == unit.fingerprint.text_sha256`，
且 `chars` 相等。引擎自己也算了一遍 `sha256`，**两个独立实现算出同一个数** ——
这是「unit 的正文没有被中间任何一层改写」的证明。427/427 通过。

**本层自己制造过一句假话**（记下来，因为它是本节最有价值的产出）：
第一版对「正文为空」只判 `not has_text`，于是它对**那 59 条 PLA 广告**也说
「本条落 DP0 的原因与 PLA 那 59 条不同」—— 而它自己就是其中一条。
**为了订正一句假话而写出的新句子，第一版就是假的。**
被本文件自己的断言抓到（[J3]「59 条 PLA 空文案不被告知『你与 PLA 那 59 条不同』」）。

修正后按**载体**分：`landing_page`/`structured_json`/`image`/`video` 的空正文是**取不到**；
`free_text` 是**调用方给的就是空的**；`ad_text` 是**结构上没有**（PLA）。
三者都走 DP0，性质与处置都不同 —— 而 D5 那条通知若只说「没有文本」，收件人无法行动。
