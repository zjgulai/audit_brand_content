### 1.1 「已经绿了」与「真的接通了」是两件事

`python3 tools/verify_coverage.py` 实测 `通过 661 项 · 不通过 0 项`。但那 661 项保证的是
「验算器文件存在，且 `subjects` 里的路径能在其源码中逐字查到」——**它不保证被验的东西
在生产链路上**。

本轮最有说服力的三个例子，全部是「自证全绿、生产断线」：

| 东西 | 自证 | 断在哪 |
|---|---|---|
| `due_at`（SLA 到期） | `verify_disposition_router` 60/60，独立复算 business-day | `base/orchestrator.py:479-483` 写回执时只取 `state/layer/release_status` 三个键；`contracts/receipt-v1.schema.json` 的 `disposition` 又是 `additionalProperties:false`，于是 `due_at` 进不了权威、API、界面 |
| 工作流耗时 | `duration_ms` 是 schema required，代码真测 | 报告模板不打印、接口不返回、指标模型不统计 |
| `semantic_judge` | `verify_semantic_judge` 有断言 | 生产传的是硬编码 `{"status":"untested"}` |

**这是本项目 §2.4.4 那个病的第四个实例：自证全绿只说明证过的形状是对的。**
所以本 ADR 的每一条验收都加一条**「活到终点」判据**——不只看部件自证，还要看它
在 `POST /submissions` 的真实响应里出现。

## 二 · 排期原则：先接线，再补链，最后才新建

七段里有三种不同的「缺」，代价差一个数量级：

| 类型 | 段 | 代价 | 为什么先/后 |
|---|---|---|---|
| **A 已经测了、只是没送出去** | 6 工作流耗时、5 回执耗时区块、1 图片进件的 env 入口 | 小：改动集中在已有代码的赋值与模板 | **先做**。不新增数据模型、不动判定逻辑，风险最低而用户可见收益最直接 |
| **B 部件齐了、缺组装** | 3 skill 加载器、7 知识库比对接生产 | 中：要新建 registry + 加载器，但被加载的东西已存在 | 次做。它能被 A 的读数验证（skill 跑多久、KB 比对花多少时间） |
| **C 根本没有** | 2 意图识别 | 大：要从数据模型开始，且要先定「识别错了怎么办」 | **最后**。它是唯一会改变判定输入形态的一段，必须在链路其余部分稳定后再做 |

- 不重开守衡（长期停令）。
- 不做部署（`PMO/implement/上线判断-GO-NOGO-20261026.md` 已判「技术侧 GO，卡在人 + 真实名单」，那是等委托方，不是等工程）。
- 不碰 `skill/` 那 37 个安装位副本（`.gitignore:43` 明确忽略；真源在 `agent-skills/`）。
- 不改判定规则内容（`rules-v1.json` 36 条不在本轮范围）。

## 三 · 执行票

编号接续表内最大号（T-450）。

### T-451 · 工作流耗时从「测了」到「读得出来」

**问题**：耗时已经写进回执，但用户与接口都看不到。

**做法**（三处，缺一处就还是读不出）：
1. `tools/audit/report_render.mjs` 的「执行回执」区块增加**耗时行**：总耗时 + 最慢的三步。
   ★ 单位与取整口径必须写进代码注释，并有一条断言钉住（不许这边写 `ms`、那边写 `s`）。
2. `api/review_api.py` 的案件详情返回里带 `workflow_timing`（总耗时、步骤数、最慢步骤名）。
3. `base/metrics_read_model.py` 增加第三个指标：**P50 / P95 工作流耗时**（分母是已出结论的案件数）。

**验收**（每条都要能说出什么变异让它红）：
- W1 报告文本里真的出现耗时行，且数值等于**步骤 `duration_ms` 求和**
  ★ **不许**用 `ended_at - started_at`。实测三次：`started_at` 与 `ended_at` **恒相等**
  （19:45:52Z == 19:45:52Z），因为 `base/orchestrator.py:54-55` 的 `_iso()` 精度只到**秒**，
  而整条链只跑 0.8–2.3 ms。用秒差会算出一个**恒为 0 的假读数** ——
  它长得像"测过了"，实际什么都没测。步骤是串行的（`:438-442` 五步顺序调用），
  所以求和合法；**将来若有并行步骤，这条判据必须重写**（注释里写明这点）。
- W2 最慢三步按 `duration_ms` 降序，取前三
- W3 案件详情接口的 `workflow_timing.total_ms` 与报告里的总耗时**逐字相同**（两个口径必须恒等）
- W4 指标的分母只数「已出结论」的案件（喂一条未出结论的 → 不许进分母）
- W5 ★ 反向对照：`steps` 为空 → 必须落 `untested` 并点名，**不许**报 `0 ms`
  （空步骤集与"0.0 ms 很快"长得一模一样，这正是 §2.4.1 那个形状）
- W6 ★ 反向对照：某一步的 `duration_ms` 缺失或为负 → `untested`，不许当成 0 参与求和

### T-452 · 图片进件接进生产（有 env 入口、默认仍关、**引擎不接**）

**问题**：`MEDIA_INGEST_ENABLED = False` 是模块常量，没有 env 入口。用户配了
`REVIEW_MEDIA_ROOTS` 也没用——能力建成却永远关着。

**★ 执行前查清的一件事，它改变了这一票的写法**：
`DEFAULT_OCR_ENGINE` 仍是 `host_vision`（macOS 专用），容器引擎 `rapidocr_ppocr_v6`
只是**注册**、没接线。而 `ocr_file()` 失败时**不抛异常**，只返回 `ok=False`；
`_build_image_unit` 已经会把失败落成 `parse_status=failed`（不会伪装成「审过了」）。

所以「把开关打开」的真实后果不是崩溃，而是**每张图都落 failed** ——
开了个什么都审不了的入口。委托方裁定：**只补 env 入口，不开引擎**。

**做法**：
- `REVIEW_MEDIA_INGEST` 读环境变量，默认仍 `False`（默认安全不变）。
- 取值只认 `1` / `true`（不分大小写），其余一律报错 ——
  ★ **胡话不许静默当关**：`REVIEW_MEDIA_INGEST=yes` 若被当成 False，
  「配了但没生效」与「没配」就长得一样（§2.4.1 那个形状）。
- 新增 `media_ingest_readiness()`：开关开了但引擎还是 `host_vision` 时，
  返回 `(False, 点名原因)`。生产装配在构造期把读数落到
  `settings.media_ingest_ready` / `media_ingest_readiness_note`。
  ★ **不 raise**：配错一个开关不该把「全站起不来」当代价。

**验收**：
- H2 不设变量 → 关（反向对照，默认不许变）
- H3 ★★ 设 `=1` → 真的打开（**改之前这条路根本不存在**）
- H5 ★★★ 打开但引擎是 `host_vision` → readiness 点名（不许静默）
- H6 关着时 readiness 通过（不误报）
- M1 生产装配里：开关开 + 引擎旧 → `media_ingest_ready=False` 且 note 含 `host_vision`
- M2 ★★ 配错开关**不阻断启动**（只记读数）
- A7 ★★ `=yes` 这种胡话必须报错并点名变量（不许静默当关）

### T-453 · skill 加载器与注册表

**问题**：`agent-skills/` 有 2 份规程，没有任何东西能加载它们。上游要求的
「skill 工作流」在本仓不存在。

**★ 执行时发现了一件比"没有加载器"更严重的事**：

回执里有 `skill_id` / `skill_version` / `skill_hash` 三个字段，而实测生产链路
**一个参数都没传** —— `base/submission_service.py` 调判定时只传了
`authority_query` 与 `kb_snapshot`。于是 `base/judge_entry.py:181-182` 的默认值生效：

    skill_id = "content-review"
    skill_version = "1"
    skill_hash = "local"      ← 这是个硬编码字面量

**"local" 比"没实现"更该修**：没有加载器只是缺功能，而它让回执**声称**
一个自己并不知道的版本 —— 回执读起来像"查过了"，实际什么都没查（§2.4.1 那个病）。

**做法**：
- 新建 `agent-skills/registry.json`：id / version / path / trigger_words / not_for。
- 新建 `base/skill_registry.py`：唯一加载点。**指纹 = 文件字节的 sha256**
  （不是 mtime、不是 size —— §2.1.1 说过那两个数会被"相等"骗过去）。
- `judge_entry` 的 `skill_version`/`skill_hash` 默认值改成 `None`（= 去注册表算）；
  取不到时落 `"untested"` 而**不是**编一个好看的默认值。
- `submission_service` **显式**传 `skill_id="content-review"`，不再靠默认值。

**验收**：
- B1 登记了但文件不在 → 红
- B2 ★★ 盘上有规程但没登记 → 红（**两个方向各自能红**，只查一个方向另一个永远绿）
- C1/C4 指纹 = 真实 sha256；加一个字节必须变
- D1 `judge_entry` 里不再有 `skill_hash="local"`
- D3 回执里的 `skill_hash` = 注册表算出的真指纹
- D7 ★★★ 生产链路**真的把 `skill_id` 传给了判定函数**（用 spy 观察入参）

**★ D6 → D7 的教训（这条比功能本身值得记）**：
D6 最初只断言「回执里的 skill_hash = 真指纹」。做变异时删掉生产链路那一行
`skill_id` —— **D6 照样全绿**，因为 `judge_entry` 的默认值恰好也是 `content-review`，
于是"没传"与"传了"产出同一个回执。

一个抓不住真实变异的判据等于没有。改成 D7（spy 观察**入参**）之后，
同一个变异立刻变红（`skill_id=None`）。**"结果对"不等于"过程对"。**

### T-454 · 知识库比对接进生产 + 补覆盖登记

**问题**：比对有两份真实现，都在分析侧，生产用不到；12 个 `kb_*` 工具不在覆盖登记表。

**做法**：
- 把 `base/change_detect.py` 的声明集合差集接进案件详情：同一个 SPU 两次送审时，
  判「同版 / 换版但声明未变 / 声明已变」。
- 12 个 `kb_*` 工具补进 `verifier-coverage.json`（**先**补登记，`verify_coverage` 的 E 段
  要求 `subjects` 里的文件要么已跟踪、要么标 `untracked`）。

**验收**：
- B1 三次比对的正例各一（同版 / 换版未变 / 已变），三值结论不许互相混
- B2 ★ 反向对照：两次完全相同的素材 → 必须判「同版」，不许因为时间不同就判「已变」
- B3 案件详情接口返回 `version_diff`，且与 `change_detect` 的结论逐字相同
- B4 `verify_coverage --controls` 全过（补登记后不许出现「提交后变红」）

### T-455 · 意图识别（最后做）

**问题**：全仓 0 行。上游 PRD 要求自动识别内容类型与阶段。

**做法**：先定**识别错了两件事怎么办**，再写代码：
- `content_type` / `content_stage` 现在是**调用方必填**（`base/contract.py:180-182`）。
  自动识别只能是**建议值**，不许覆盖调用方给的；两者不一致 → 落一条观察，不阻断。
- 识别器本身用规则（关键词 + 结构特征），不用模型——因为要能被反向对照。

**验收**：
- I1 调用方给了值 → 一律采信调用方的，识别结果只作观察（反向对照）
- I2 调用方没给 → 用识别值，并在响应里标明「这是推断的」
- I3 ★ 识别不出的内容 → `untested` 且点名，**不许**默认成某个类型
- I4 三条真实素材（图片/视频/纯文本）各一次，识别正确；外加一条故意错配的必须被记为不一致

## 四 · 次序与依赖

```
T-451（耗时读得出）── 无依赖，先做
   │
T-452（图片进件）──── 无依赖，可与 451 并行
   │
T-453（skill 加载器）─ 无依赖，但做完后 T-451 的耗时才说得清「这一步是哪个 skill」
   │
T-454（KB 比对）───── 依赖 T-453（比对结果要能指到是哪个 skill 比出来的）
   │
T-455（意图识别）──── 最后。它改变入参形态，必须在前面都稳定后做
```

**为什么 451 排第一**：它是唯一「数据已经在盘上、只是没人看」的一段。改动不碰判定逻辑，
风险最低，而它一旦通了，后面四票的耗时都会自动出现在同一条读数里——
等于给 T-453/454/455 免费装了一块表。

## 六 · 可证伪性（这份 ADR 自己怎么被推翻）

| 断言 | 什么让它红 |
|---|---|
| 「耗时测了但读不出」 | T-451 做完后，若报告里仍无耗时行或接口无 `workflow_timing` → 本句仍成立，说明没做成 |

★ 最后一条是本 ADR 的自我要求：**本节列出的每个「缺」，都应该在补上之后从本节删掉**，
而不是留成一份永远正确的清单。
