# 内容审查 Agent · 常犯坑点与硬约束 v1

这张表把本项目已经真实踩过（或有实测读数）的坑汇总成一张台账：一行一个坑，同一形状从多份材料收集到的已合并成一行，读数与出处写在「为什么错」「影响文件」两列里。用法：先用「坑 / 错误形状」辨认自己正处在哪一种，再照「约束」那句话做事；要判断它是否真的被拦住，只看「执行点」和「反向对照」两列——执行点必须指得出哪个文件的哪一段会红，反向对照必须说清喂什么坏样本会红、喂什么好样本会绿。

**这张表本身不是约束。** 表里的文字、约束句、状态都不会让任何检查变红；约束只在「执行点」列指出的代码/断言里。状态列的含义：`有执行点`＝指得出会红的断言或检查器；`部分`＝有执行点但覆盖不全，或另一侧仍然只有散文；`只有散文`＝规则只写在文档/注释/人格里，没有东西会因此变红；`未治理`＝已知缺口，连约束都还没有落地。写新行时，指不出执行点就写「无」，不许为了好看编一个——那正是本表第 6 行要防的事，也是第 7 行（验收索引≠执行验收）的同一个病。

> 状态与行号以 2026-10-18 盘上代码为准；代码改行号会漂，执行点优先认断言编号与函数名。反向对照一栏写「无」的，表示没有喂过坏样本/好样本，不代表它一定拦不住，只表示**没有证据**说它拦得住。
