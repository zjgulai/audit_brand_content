# 裁定 · 行 118「媒体能力全部走容器内跨平台模型，不使用宿主原生能力」

> 裁定日：2026-10-23 · 裁定人：编排会话（audit-multi-content-05）
> 触发：`tools/verify_media_portability.py` **如实红着**，f3 报「`base/media.py` 是否属生产路径
> 三处文档说法不一致，需要裁定」。裁定前它没有自行改绿 —— 这个停手是对的。

---

## 一、裁定

**行 118 的「不使用宿主原生能力」这半句，在今天的生产路径上
是**空真（vacuously true）**，不是已满足。**

具体三句：

1. **`base/media.py` 及其 OCR 链（`ocr_vision.m` / `build_ocr.sh`）不在生产路径上。**
   生产进件只接文本；媒体进件在入口就被拒。
2. **因此「生产用了宿主原生 OCR」这件事今天不成立** —— 不是因为我们做对了，
   是因为**生产根本没有媒体入口**。
3. **`verify_media_portability.py` 的红是准确的，不许改绿。** 它命中的 3 处是事实；
   它们「不在生产路径上」是另一件事，两者都要说出来。

> ★ 这条裁定的要害：**「今天不违规」与「今天做到了」是两件事。**
> 把前者的读数写成后者，就是本项目反复记的那个形状（§2.4.1「这句话比我的输入大吗」）。

## 二、证据（每条可复核）

### 2.1 生产进件只接文本 —— 行为级读数，不是读代码推的

```python
svc = SubmissionIngestor()
svc.prepare({
  "submission_id": "s1", "content_stage": "final_content",
  "entry_channel": "群消息", "content_type": "文本", "product_line": "吸奶器",
  "source": {"kind": "image", "uri": "inline:x"},
}, principal={"principal_id": "p", "tenant": "t1"})
```
```
SubmissionRejected: unsupported_source_kind:
  本轮只接文本载体 free_text/ad_text，收到 'image'
```

出处：`base/submission_service.py:33` `SUPPORTED_SOURCE_KINDS = frozenset({"free_text", "ad_text"})`
与 `:103` 的拒收分支。

★ 注意 `base/contract.py` 的 `SOURCE_KIND_DOMAIN` 里**是**有 `image` / `video` / `landing_page`
的 —— **契约允许，进件服务不收**。这两层不一致是**设计现状**，不是本裁定的对象。

### 2.2 传递依赖闭包：`api/` 的 24 个文件里没有 `media.py`

从 `api/**/*.py` 出发做 import 闭包（只跟 `base.*`），得到 24 个文件：

```
artifact_store / auth_session / authority_query / business_event_store / control_points /
decision_table / disposition_router / finding_store / judge_entry / orchestrator /
principal_directory / projection_store / projector / rbac / release_gate /
review_command_service / review_reducer / reviews_ledger / rule_judge / submission_service
```

**不含 `base/media.py`。**

第二跳也查了：`media.py` 唯一的 base 内引用者是 `base/text_stage.py:62`，
而 **`text_stage` 在全仓没有任何 import 者**（`grep` 全仓 0 命中）。

### 2.3 三处文档说法不一致 —— 属实，但**不是**「谁对谁错」

| 文档 | 说法 | 与裁定相关的部分 |
|---|---|---|
| PRD | 媒体属 P1 阶段 | 未说 `media.py` 今天在生产路径上 |
| Playbook | 媒体边界 §3.3.9 | 同上 |
| 技术解决方案 | `media_pipeline` 是组件 | 组件存在 ≠ 已装配 |

**裁定：三处都没说「今天已装配」。** 它们描述的是**目标形态**，而 2.1/2.2 描述的是**今天的装配**。
所以「三处不一致」这个提法本身要更正：它们**不矛盾**，是把「设计」与「实现」写在了不同文件里，
而没有人把「实现到哪一步」写下来。**缺的是那份实况，不是三处对齐。**

### 2.4 静态扫描的 3 处命中是真的

```
base/build_ocr.sh:12      -framework Foundation -framework Vision -framework AppKit
base/ocr_vision.m:23      VNRecognizeTextRequest *req = ...
base/ocr_vision.m:27      VNImageRequestHandler *h = ...
```

★ **我第一次自己扫时只命中了 1 处，而那 1 处还是 docstring 文本** ——
因为我只扫了 `*.py`，漏了 `.m` / `.sh`。是 f3 的验证器把我的读数纠正过来的。
记在这里，因为它正是「查通道不全就下结论」的又一次复现。

## 三、这条裁定**不**解决什么

1. **不解决未来**：只要生产真的接上媒体进件（`SUPPORTED_SOURCE_KINDS` 加入 `image`/`video`），
   今天这条空真立刻变成**真违规** —— 而**没有任何东西会提醒你**。
   → 要求：**打开媒体进件的那张票，必须同时处理行 118**。这条写进票清单。
2. **不解决容器那半**：行 118 还要求「在 Linux 容器内跑一次真实图片与视频，断言能产出结果」。
   今天**无对象**（无 docker daemon、镜像无引擎、素材 0 个）。**未测，不是通过。**
3. **不改 `verify_media_portability.py` 的红**：它继续红，且它的红是准确的。
   但它的结论行要加一句「不在生产路径上（见本裁定）」——**红要红得说清楚红的是什么。**
