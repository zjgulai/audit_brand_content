# 裁定 · nmem 知识图谱在本项目**刻意不建**（2026-10-27）

> 这份文档回答一个问题：**为什么我声明了 9 个对象类型、却一个实体都没有？**
> 答案不是「还没来得及」，是**刻意的，且已实测确认没有可行路径**。

---

## 一 · 事实：图谱是空的，而验证器曾经把它报成绿的

2026-10-27 实测（`nmem 0.10.108`，space `audit-multi-content`）：

```
声明的 9 个对象类型，实体数全部为 0：
  DECISIONRECORD 0 · VERIFIER 0 · FAILUREPATTERN 0 · SUBSYSTEM 0
  CONTRACT 0 · RELEASEGATE 0 · TICKET 0 · REDLINE 0 · INCIDENT 0

237 个实体 / 216 条关系 —— 全部在 default space，是别的工作的产物，与本项目无关

一条记忆的图谱邻域（决定性证据）：
  $ nmem graph expand b41c84fe-… --depth 1
  neighbors: []   edges: []   total_neighbors: 0
  → 写入的记忆与图谱**完全断开**，一条边都没有

extraction: {"enabled": false, "gate": "disabled", "active": false, "adjudicatesTypes": false}
```

**而 `verify_nmem.py` 的 N9 当时是 ✅。** 它断的是 `len(objectTypes) >= 9` ——
「词汇表里有没有」，不是「有没有东西按这个词汇被标出来」。

> ★ 这就是 `AGENTS.md` §2.4 点名的那个病，在**它自己的执行点里**又活了一次：
> 与当年 `cards.mjs` 的 `new RegExp('\b'+k+'\b').test(envSrc)` 一模一样 ——
> 一条 import 就能满足它。**名字出现过 ≠ 拦得住。**

## 二 · 三条候选路径，全部实测不通

| 候选 | 试验 | 结果 |
|---|---|---|
| `ontology.policy` | `observe` → `guide` | `extraction.gate` 仍是 `disabled` —— **policy 不是这道门** |
| `settings.agenticKgExtraction` | `false` → `true` | `extraction` 无变化 —— **也不是** |
| `settings.autoKGExtraction` | 本来就是 `true` | 它是**另一层**的开关；它一直开着，门一直关着 |
| `nmem entities create / add / new` | 三个都试 | 全部 `unrecognized subcommand` |
| `nmem entities` 全部子命令 | 逐个读 help | 只有 `aliases / repair-timestamps / repair-legacy-default-space / delete / merge` —— **全是读或改已有实体，没有建** |
| `ontology` 补丁字段白名单 | 喂非法字段读报错 | `objectTypes / linkTypes / openWorld / policy / seedFromDefault` —— **没有 extraction 项** |

两次试验后均已回滚：本体 9+8（rev=3），设置 41 键，差异只剩系统补的
`maxDailyBackgroundCostSource: None→'default'`。

**结论：`gate: "disabled"` 不是「配置没开」，是这个 space 的抽取能力没被启用，
而 CLI 里没有任何一条命令能启用它。** 这不是我这一轮能解决的事。

## 三 · 裁定：不做，并留下判据

**决定：本项目不建知识图谱。**

判据是硬的（`AGENTS.md` §2.4.1：否定结论的输入必须大于结论）：

本项目真正需要图谱去表达的三类关系，**已经有两份可验证的实现**：

| 需要的关系 | 现有实现 | 可验证性 |
|---|---|---|
| 谁验什么（验证器 → 被测主体） | `tools/verifier-coverage.json` | `verify_coverage.py` **661 项断言**，A–F 六段双向反证 |
| ADR 之间的取代链与状态 | `ADR/README.md` 的台账表 + `verify_adr_status.py` | 有执行点 |
| 票的依赖与阻塞 | `PMO/implement/执行票清单-*.md` | 人工可读 |

**再建一份不可验证的图谱，是净增负担，不是净增能力。**
这句话在 §2.4.2 的语汇里是：*一个没有人跑的检查器，和一句没有执行点的承诺是同一个形状。*
图谱当下正是那个形状 —— 词汇表写得很全，一条边都没有。

## 四 · 执行点：不许再把它报成绿的

`tools/verify_nmem.py` 的 N9 改成**两条互斥的合法状态**，两条都必须是**被声明的**：

| 状态 | 条件 | 判据 |
|---|---|---|
| **A 已播种** | 每个声明的对象类型都 ≥1 个实体 | `SEED_PENDING` 为空时生效；任一类型为 0 → **红** |
| **B 声明未播种** | `SEED_PENDING` 在，且本 space 在本体类型上**确实 0 个实体** | 若此时有实体 → **红**（声明过期了）。且声明的类型数必须与盘上一致 |

两条都不满足（声明了、有部分实体、又写着未播种）→ 红。

**结论行同步改口径**：不再输出「本体已生效」，改为
`本体 9 类已声明但**未播种**（实体 0 个，seed_pending：…）`。

反向对照（`--controls`，现为 8 项，新增 3 项）：

- **C6** seed_pending 声明了但库里其实有实体 → 必须红（证明「声明过期」这一支活着）
- **C7** 撤掉 seed_pending 后某个类型实体为 0 → 必须红
  （**改之前这条恒绿**，因为只查词汇表长度 —— 这是本次缺陷的原始形状）
- **C8** 合法状态 B（seed_pending + 零实体）→ 必须闭嘴（证明不会误报）

## 五 · 本裁定的失效条件

画在明处，避免这份文档变成免死金牌：

1. **nmem 提供了启用抽取的入口** —— 无论是 `nmem entities create`、
   `config settings` 里新增的键、还是 `ontology` 补丁新增的 extraction 字段。
   **判据**：能造出**一个**实体并让 `graph expand` 返回 ≥1 条边。
   做到之后必须撤掉 `SEED_PENDING` 并把 N9 切到状态 A，否则 C6 会红。
2. **项目出现一类只能靠多跳回答、且现有两份台账表达不了的问题** ——
   那说明上面的判据漏了一种需求，应当重新评估，而不是继续沿用本裁定。

## 七 · 更正（2026-10-27 同日）

### 我错在哪

上一节写「三条候选路径全部实测不通」，据此推出「CLI 里没有任何一条命令能启用抽取」。
**三行试验都是真的**，但结论跨大了：我查的是 `nmem` CLI 的子命令与 `settings` 键，
**没查 HTTP 路由**。而开关在 HTTP 路由上：

```
$ curl -s -X POST http://127.0.0.1:14242/settings/ontology/extraction \
       -H 'Content-Type: application/json' -d '{"enabled":true}'
{"store":{...},"extraction":{"enabled":true,"gate":"pass","active":true,"adjudicatesTypes":true}}
```

`disabled → pass`、`active` 由 `false` 变 `true`、`adjudicatesTypes` 也变 `true`。

**怎么找到的**：在 `web-dist` 的 `zh-Hant` 语言包里搜到一条事件标签
`ontologyExtractionToggled: 詞表引導擷取`，据此在 `nmem-server` 二进制里找到路由
`/settings/ontology/extraction`。也就是说，**证据一直在这台机器上**，
我上一轮的检索面（CLI `--help` + `config settings show`）不够宽。

### 现在的真实阻塞点（可指认）

门打开后我触发 `library extract` 两份材料，任务确实入队了，但服务端日志每分钟一行：

```
WARN nmem_server::scheduler_service::execution: Rate limit reached, deferring task
  task_type=source_extraction wait_reason=money_budget_daily wait_seconds=60
```

`money_budget_daily` —— **每日后台花费预算用尽**（`maxDailyBackgroundCostMicroUsd = 150000`，
即 $0.15/天）。所以：

| 层 | 状态 |
|---|---|
| 抽取能力 | ✅ 已开（gate=pass） |
| 任务队列 | ✅ 会入队 |
| 实际执行 | ⛔ 被 `money_budget_daily` 挡回 |
| 实体产出 | 仍为 0 —— **但原因变了** |

### 这份裁定的新状态

**「不做」这个结论暂时保留，但理由换掉了**：

- 旧理由：*做不了*（能力缺失）—— **错**。
- 新理由：*今天做不了*（预算），且**做与不做仍需重新判断** ——
  能力一旦可用，「图谱是否值得建」就回到 §三 那个权衡上，
  而那个权衡当时就承认过是弱论证（两份台账是给人读的表，不等于机器可多跳）。

### 失效条件收紧

原 §五第 1 条写「能造出一个实体并让 `graph expand` 返回 ≥1 条边」。
**这条判据仍然有效**，但要补一句：门已开，所以「造不出来」不再能归因于能力，
只能归因于预算或配置 —— **不许再把这两者混为一谈**（那是 §2.4.1 第 5 行
「一个会过期的读数，没有任何东西在它过期时变红」的同类）。

`tools/verify_nmem.py` 的 `SEED_PENDING.reason` 已同步改为新理由，
并用 C6（声明了 seed_pending 但库里有实体 → 必红）守着「预算放开后忘了撤声明」这条路。

  ├ 判定规则词表 / 白名单表 / 语境守卫表 / 豁免词字段

这恰好是我在路线 A 里手工列出的那批实体 —— **抽取器自己抽出来了**。

### 本裁定错在哪（三层，一层比一层深）

| 层 | 我写的 | 事实 |
|---|---|---|
| 1 | 「`gate=disabled`，**没有**启用路径」 | 路径在 HTTP 路由上（§七）。**否定结论比输入大** |
| 2 | 「就算能开，也要靠手工建 30 个实体」 | 抽取器能自己抽，且抽得对 |
| 3 | 「本项目不需要图谱，两份台账已够」 | **这条没有被证伪，但它从未被验证过** —— 它是我在「做不了」的前提下写的权衡，前提没了，权衡要重做 |

第 3 层最重要：**一个建立在错误前提上的判断，即使结论碰巧对，也不能留作依据。**
所以本裁定作废，图谱该不该继续建，回到开放问题。

### 补的那 4 条记忆，以及为什么它们有用

| 记忆 | 目标类型 | 写法关键 |
|---|---|---|
| `l2-10-verifier-inventory` | VERIFIER | 把每个 `verify_*.py` 当**实体**列成表，而不是在句子里提文件名 |
| `l2-11-release-gate-six-commands` | RELEASEGATE | 「上线闸门是一个实体，不是一句流程」—— **主语就是它** |
| `l2-12-three-redlines-detail` | REDLINE | 三条红线**逐条**给边界与执行点，不合并成一句 |
| `l2-13-shouheng-outage-incident` | INCIDENT | 一次**具体事故**的完整记录（日期/根因/代价/修法），不是抽象教训 |

`RELEASEGATE` 最难出（最后一个才出现，且只有 1 个）：LLM 抽取器容易把「上线流程」
归进 `PROCESS`/`SUBSYSTEM`。**要让它成为实体，必须在文本里给它一个独立的、可被指认的身份。**
