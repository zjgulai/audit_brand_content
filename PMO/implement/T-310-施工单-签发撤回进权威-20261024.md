### 关键一条：签发绑定字段在今天**没有生产者**

`_binding()` 要求 `case` 上有：`case_version`、`ir_id`、`ir_version`、`raw_sha256`、
`text_sha256`、`rule_snapshot{version,hash}`、`kb_snapshot{version,hash}`、
`used_authority_refs`、`conflict_table_version`、`frame_manifest_hash`、`keyframe_set_hash`、
`ocr_output_hash`、`asr_output_hash`、`model_config_hash`、`sampling_config_hash`
（`base/release_gate.py:134-195`）。

而 `review_reducer.initial_state()`（`:42-69`）里这些字段**一个都没有**。
`conflict_table_version` 更是**全仓只出现在 `release_gate.py` 自己**：

```bash
grep -rn "conflict_table_version" --include=*.py base/ api/ tools/
# → 只有 base/release_gate.py 的 9 处（定义、校验、失效比较），没有任何生产者
```

也就是说：**今天把 API 接到权威上，第一次签发就会抛 `SignatureError: case.raw_sha256 缺失`。**
这不是「接线」，是「先给绑定字段找来源」。

## 二 · 两个前置（票里没写，但绕不过去）

### 前置 A：绑定字段的来源必须逐条定，不能补默认值

补默认值 = 在裁定之前先做了一个裁定，而且会做出一个**看起来签过、其实什么都没绑**的签名。
每一条都要么有真实来源，要么**明确 fail closed**：

| 绑定字段 | 生产来源（本轮定） | 取不到时 |
|---|---|---|
| `case_version` | `state["version"]`（权威版本号） | 不可能缺 |
| `ir_id` / `ir_version` | `state["ir"]["ir_id"]` / `["ir_version"]` | 抛 `SignatureError` |
| `raw_sha256` | `state["content"]["fingerprint"]["raw_sha256"]` | 抛错（**不许**用 `sha256("")` 顶替） |
| `text_sha256` | 同上 `text_sha256` | 抛错 |
| `rule_snapshot_version` | `state["ir"]["coverage"]["rules_version"]["version"]` | 抛错 |
| `rule_snapshot_hash` | 同上 `["fingerprint"]`，必须 64 hex | 抛错 |
| `kb_snapshot_version` | `state["ir"]["kb_snapshot"]`（字符串） | 抛错 |
| `kb_snapshot_hash` | **新增**：`state["kb_snapshot_hash"]`，由 `SubmissionIngestor` 在判定时写入 | 抛错（见下） |
| `used_authority_refs` | `state["ir"]["findings"][*]["authority_ref"]` 去重 + `authority_state=ok` 的项，版本取 `state["authority_versions"]` | 空数组**合法**（文本件无外部依据时确实为空） |
| `conflict_table_version` | **新增**：`state["conflict_table_version"]`，取控制点表版本 `registry.table_version` | 抛错（不许写 `"unknown"`） |
| 六类媒体指纹 | 文本件：`state["media_fingerprints"]` 缺省为 `{}`；有媒体时逐类取 | 文本件允许缺省，**用一类一个的固定占位 hash**：`sha256(b"absent:<field>")`，且必须在签名里可复算 |

> ★ 最后一行是本单里**唯一一个允许「生成的默认值」**的地方，理由：判据要求字段是 64 hex，
> 而文本件确实没有媒体。占位值必须是**确定性、可复算、不等于任何真实指纹**的哈希，
> 并且要有一条断言：把 `absent` 改成 `not_available` 字符串 → `validate_signature` 必红。

**前置 A 的产出**：`base/release_binding.py`（新文件，约 90 行，纯函数，无 IO）。

### 前置 B：`kb_snapshot_hash` 与 `conflict_table_version` 必须先落进 ingest

`SubmissionIngestor.prepare()` 现在只写 `judgment` 与 `ir`（`base/submission_service.py:189-205`），
**不写**这两个字段。所以 T-310a 必须同时改 `submission_service.py` 与 `review_reducer._ingest_submission`，
否则后面所有签发都缺字段。

这两条字段的判定口径：
- `kb_snapshot_hash`：`ExternalStandardsAuthority` 的 `snapshot_id` 的 sha256。
  **如果一个 hash 都不是真 KB 的指纹，就不要签** —— 宁可 `untested`，不许签一个假绑定。
- `conflict_table_version`：`ControlPointRegistry().table_version`。
  它今天在 `judge_entry` 里**已经算过**（`base/judge_entry.py:124`），只是没进 `ir`。
  最小改动：把它写进 `ir["control_points_version"]` 旁边，命名 `conflict_table_version`
  （两者是同一个量，别造第二个口径 —— `AGENTS.md` §2.4.8）。

### T-310b · reducer 三条命令（1 天）

**改 `base/review_reducer.py`**，新增一个私有函数与三个分支：

```python
def _release(state, command, actor, payload, now):
    """release_sign / release_reject / release_revoke 的纯状态迁移。

    不消费 step-up（reducer 无 session store）、不验权限（那是 service 层的事）。
    只做：状态机合法性、签名结构校验、派生链、事件追加。
    """
```

三条命令的规则：

| 命令 | 前置状态 | 动作 | 拒绝码 |
|---|---|---|---|
| `release_sign` | `release.status ∈ (None, "pending_release")` 且 `state.status == "closed"` | 追加签名，`status="signed"`，`release_status="已放行"` | `invalid_transition` / `bad_signature` |
| `release_reject` | 同上 | 追加 `decision="rejected"` 的签名，`status="rejected"` | 同上 |
| `release_revoke` | `release.status == "signed"` | 只改状态 + 追加事件，**不追加签名** | `invalid_transition` |

三条共同要求：
1. `state["status"] == "closed"`（**未结案不许签发** —— 这是本单新加的守卫，理由见 §六 R2）；
2. 传入的 `signature` 必须 `validate_signature(sig) == []`；
3. `sig["derived_from"]` 必须等于上一条签名 id（首条为 `None`）；
4. `sig["case_version"]` 必须等于**当前** `state["version"]`（防签一个旧版本）。

**判据**：`tools/verify_release_persistence.py`（新，约 35 项）+ 现有 `verify_release_gate.py` 保持 rc=0。

## 四 · 落进 state 的确切形状

```json
"release": {
  "status": "signed",
  "release_status": "已放行",
  "signatures": [ { "signature_id": "...", "...": "27 个字段" } ],
  "events": [
    {"kind": "release_signed", "at": 1761..., "actor": "u_signer",
     "step_up_ref": "su-...", "reason": "..."}
  ],
  "active_job": null,
  "successor": null
}
```

**为什么不用新表**：`review_cases.state_json` 存的就是整块 state（`projection_store.py:149-155`），
所以加 `release` 字段**不需要 SQLite 迁移**，也不需要改 `SCHEMA_VERSION`。
这一点要在提交信息里写明，否则下一个人会去写一个没必要的 migration。

**为什么 `release` 放在 case aggregate 里、不另开 aggregate**：
- 签发状态与案件版本强耦合（`case_version` 是签名绑定字段），换 aggregate 就要维护跨聚合一致；
- `BusinessEventStore` 的 `execute()` 一次只能提交一个 `aggregate_id`（`:304-310`）；
- 现有 `Projector.catch_up()` 按 seq 顺序 apply，跨聚合的一致性没有额外保障。

## 六 · 红线（这张票不许做的事）

1. **不许给缺字段补默认值让签发「先跑通」。** 除 §二 表里点名的媒体占位 hash 外，一律 fail closed。
2. **不许把 `state["status"] == "closed"` 的守卫去掉。** 今天 `submit_review` 已经有
   「未裁决不许结案」的守卫（`review_reducer.py:331-352`）；签发再加一道「未结案不许签」，
   两道合起来才让「复核是一个真动作」这件事成立。少了这道，签发可以绕开复核。
3. **不许在 reducer 里调 session store。** reducer 是纯函数，测试与回放都依赖这一点。
4. **不许把 step-up 消费放在权限校验之前。** 否则无权限的人可以烧别人的 token。
5. **不许只改 `write_api.py` 的返回、不改 state。** 那正是这次要修的病。
