| 10 | 现有申诉断言全打在**开发装配**上 | `tools/verify_write_api.py:298-301` 调 `create_app()` 时**不传** `review_command_service` | 生产分支的申诉链**一条都没验过** |

### 第 3 条值得单独说

```python
self._seq = 0                      # :128
...
self._seq += 1                     # :139
appeal_id = "appeal-%d" % self._seq
```

这不是「重启会重复显示」，是**重启后新建的申诉会覆盖/混淆历史申诉**。
而 `verify_write_api.py` 每次新建 `AppealStore()` 都从 0 开始，所以它**恰好测不出这个缺陷**——
测试的构造方式正好复现了缺陷的触发条件，却因为每次都从空开始而看不见撞号。

> 判据：**一个 ID 生成器如果依赖进程生命周期，它就不是 ID。**
> 修法与 `draft_id` 同形：`"appeal-" + sha256({case_id, seq, appellant, opened_at})[:16]`（`base/review_reducer.py:104-124` 已有这个模式）。

## 四 · 落进 state 的确切形状

```json
"appeal_seq": 2,
"appeals": [
  {
    "appeal_id": "appeal-9f3c1a2b4d5e6f70",
    "case_id": "case-...",
    "tenant": "on_xxx",
    "appellant": "ou_xxx",
    "reason": "误判",
    "state": "paused_version_invalidated",
    "opened_at": "2026-10-24T07:00:00Z",
    "paused_at": "2026-10-25T01:00:00Z",
    "pause_reason": "version_invalidated",
    "migrated_at": null,
    "stale_at": null,
    "withdrawn_at": null,
    "withdraw_reason": null
  }
]
```

**四条设计决定及理由：**

1. **放进 case aggregate，不另开 aggregate。**
   理由与 T-310 §四 完全相同：`BusinessEventStore.execute()` 一次只提交一个 `aggregate_id`（`base/business_event_store.py:304-310`）；跨聚合一致性没有额外保障。

2. **不需要 SQLite 迁移。**
   `review_cases.state_json` 存整块 state（`base/projection_store.py:149-155`），投影是**整案替换**。
   加两个字段不改表、不升 `SCHEMA_VERSION`。这一点必须写进提交信息。

3. **`tenant` 必须写进每条申诉。**
   今天没有（§一 第 7 条），所以即使把所有东西接上，`GET /api/v1/appeals` 也查不到。
   这不是「顺手补字段」，是**这个接口今天唯一可能的过滤依据**。

4. **`appeal_id` 改成确定性哈希。**
   照 `draft_id` 的公式（`base/review_reducer.py:104-111`）：
   ```python
   "appeal-" + sha256(canonical({case_id, seq, appellant, opened_at}))[:16]
   ```
   `seq` 取 `state["appeal_seq"]`，同案单调递增、跨重启连续。

## 五 · 拆票

### T-311a · 五条 reducer 命令（1.5 天）

**改 `base/review_reducer.py`**（不新建文件：它需要 `_nonempty` / `_event` / `_hash` / `_iso`，
拆出去会产生循环 import —— 与 T-310b 同一个判断）：

```python
def _appeal(state, command, actor, payload, now):
    """appeal_open / _pause / _stale / _migrate / _withdraw 的纯状态迁移。

    不做租户校验（reducer 无 repo）、不查案件存在性（那是 API 层）。
    只做：五态迁移合法性、ID 生成、时间戳、事件追加。
    """
```

五条命令的状态机（**与今天 `AppealStore` 逐条等价，不许顺手改语义**）：

| 命令 | 前置状态 | 写入字段 | 拒绝码 |
|---|---|---|---|
| `appeal_open` | 任意（同案可多条） | 新记录，`state="open"` | `bad_appeal`（缺 case_id/appellant/reason） |
| `appeal_pause` | 该案所有 `state=="open"` 的条目 | `state="paused_version_invalidated"`、`pause_reason`、`paused_at` | 无（幂等：没有 open 条目时返回空数组，**不是错误**） |
| `appeal_stale` | `state=="paused_version_invalidated"` 且 `now - paused_at > days*86400` | `state="stale"`、`stale_at` | 无 |
| `appeal_migrate` | `state=="paused_version_invalidated"` 且 `actor == appellant` | `state="migrated"`、`migrated_at` | `not_original_appellant` / `not_paused` |
| `appeal_withdraw` | `state ∈ {open, paused_version_invalidated}` 且 `actor == appellant` 且 `reason` 非空 | `state="withdrawn"`、`withdrawn_at`、`withdraw_reason` | `missing_reason` / `not_original_appellant` / `terminal_state` |

**三条硬约束（每一对都有反向对照）：**

1. **只写该写的字段。** 每条命令只能改自己那几个键，业务字段（`reason`/`appellant`/`opened_at`/`case_id`）**一个都不许动**。这是 RL-12 ④，已有断言可复用（`tools/verify_write_api.py:123-136` 的 `assert_pause_field_discipline`），要**搬**到新验证器，不是复制。
2. **`pause` / `stale` 不关闭。** `state` 只能是 `paused_version_invalidated` / `stale`，**不许出现 `closed`**。反向对照：构造一个写 `closed` 的坏实现，必须红（`verify_write_api.py:191-205` 已有这条坏样本）。
3. **`migrate` 只能原申诉人做。** 拒绝码 `not_original_appellant`（403）。

## 六 · 红线（这张票不许做的事）

1. **不许让 `pause` / `stale` 改成 `closed`。** RL-12 的原话是「不自动关闭」（Playbook `:1171`）。这条已有坏样本，必须留。
2. **不许给申诉加「胜负结论」字段。** `appeal_result` 没有生产者（§三 D-311-2），造一个等于替产品裁定 `#84` 的分母口径。
3. **不许在 reducer 里查 repo / 校验租户。** reducer 是纯函数，回放依赖这一点。
4. **不许把 `mark_stale` 挂在 `GET /appeals` 上做「读时扫描」。** 读端点写状态会让「打开列表」变成一次写操作，且并发下会撞版本。
   触发点只能是 `maintain_once()`。
5. **不许删 `AppealStore`。** 开发装配与 C2 段都在用它；删了 `dev-up.sh` 与 `verify_write_api.py` 会一起红。
6. **不许把 `appeal.handle` 接成 migrate 的权限。** migrate 的动作主体是**原申诉人**，
   而 `appeal.handle` 是审核员能力 —— 接错会把「申诉人自己确认迁移」变成「审核员替他确认」。
