### 第 1 与第 3 条要单独说

原票把 T-312 写成「下线任务持久化 + 真实名单」，读起来像「东西都有，只是没存住」。

实际是：**东西在生产里一条都不存在**。`WRITE_PATHS` 那 7 条全是「对已有任务做迁移」，
没有任何一条能**造出一条任务**；而 `verify_takedown.py` 的 8 组断言（含 2026-10-24 补的通知链）
全打在纯函数上，所以 `#95–#101` 共 7 行可以是绿的，而生产里**连一个任务对象都产生不出来**。

这与 `PMO/上线Ticket清单-20261022.md` §〇 第二句是同一个形状：
「108/136 是命令退 0，不是判据成立」。

第 3 条同理：`TAKEDOWN_ALLOWLIST` 是空集这件事今天**完全不影响任何行为**，
因为路由根本没查这个能力。修名单写路径（T-314）之前，先把能力检查接上，
否则「名单有值」与「名单被读」两件事会一直分不清。

## 四 · 落进 state 的确切形状

```json
"takedown_seq": 1,
"takedown_tasks": [
  {
    "task_id": "td-3f2a9c1b8e7d6054",
    "case_id": "case-...",
    "tenant": "on_xxx",
    "product_line": "pump",
    "platform": "amazon_us",
    "trigger": "revoke",
    "reason": "revoke",
    "state": "pending",
    "assignee": "ou_xxx",
    "reviewers": ["ou_yyy"],
    "created_at": "2026-10-24T08:00:00+08:00",
    "history": [],
    "version": 0,
    "evidence": null,
    "waived": null
  }
]
```

**四条设计决定：**

1. **放进 case aggregate。** 理由与 T-310/T-311 相同（`BusinessEventStore.execute()` 一次一个 aggregate）。
   但注意：一条任务天生属于一个案件，所以**不需要跨案聚合**。

2. **不需要 SQLite 迁移。** 同样是 `state_json` 整体存。

3. **`task_id` 用确定性哈希**，不用自增：
   ```python
   "td-" + sha256(canonical({case_id, seq, trigger, created_at}))[:16]
   ```
   理由同 T-311 §一 第 3 条 —— 避免重启撞号。`seq` 取 `state["takedown_seq"]`。

4. **`version` 字段保留。** `api/write_api.py:683/708/728/755` 现在手工 `new["version"] = ... + 1`，
   接进 reducer 后由 reducer 统一递增（`state["version"]` 是案件版本，任务自己那一份是任务版本，
   **两个不同的量，不许合并** —— `AGENTS.md` §2.4.8）。

## 五 · 拆票

### T-312a · reducer 两条命令 + 字段补齐（1 天，可开工）

**改 `base/takedown.py`**：

- `new_task()` 增加 `trigger`、`reason` 两个必填关键字参数（§一 第 11 条）；
- 保持纯函数、无 IO。

**改 `base/review_reducer.py`**（追加，不新建文件）：

```python
def _takedown(state, command, actor, payload, now):
    """takedown_create / takedown_transition 的纯状态迁移。

    状态机合法性一律交给 base/takedown.check_transition() 判 ——
    不许在这里重写一份迁移表（两份表必然漂移）。
    """
```

| 命令 | 做什么 | 拒绝码 |
|---|---|---|
| `takedown_create` | 追加任务到 `state["takedown_tasks"]`，`state` 不变 | `bad_task`（缺 trigger/platform/assignee）｜`duplicate_task`（同 case 同 trigger 已有未完成任务） |
| `takedown_transition` | 调 `TD.check_transition()`，通过后替换该任务并写 `history` | 透传 `TD.TakedownError.code`（`E_TRANSITION` 等） |

**两条硬约束：**

1. **迁移表只有一份。** `_takedown` 必须 import `base.takedown.check_transition`，
   **不许**在 reducer 里复制 `TRANSITIONS`。反向对照：把 `TRANSITIONS` 里
   `failed → completed` 删掉，reducer 侧必须跟着拒（证明它真的在读那一份）。
2. **`takedown_create` 不做「已发布才建」的判断。** 那个判断在 `should_create_task()`，
   调用方（T-310c）先问它再发命令。reducer 只负责落盘 —— **判断与落盘分开，才验得清**。

**判据**：追加到**现有** `tools/verify_review_reducer.py`（它已覆盖九种命令），不新建验证器。

### T-312b · 能力检查 + actor（1 天，**blocked：等 T-314**）

**改 `api/write_api.py:663-760`**：

```python
def require_takedown(principal, task, capability="takedown.execute"):
    if not can_act(principal, capability, task):
        raise HTTPException(403, "无权执行下线动作")
```

- `start` / `complete` / `fail` / `retry` / `reassign` → `takedown.execute`
- `waive` → `takedown.waive`（**两把不同的钥匙，不许共用**）

**改 `base/takedown.py:408`**：`complete(task, evidence, *, actor, ...)` ——
`actor` 必填，写进 `task["completed_by"]`，并断言 `actor == task["assignee"] or can_act(...)`
（具体口径见下）。

**一个必须先想清的语义**：`#95` 说「任务只能由有权限的人回填完成」。
「有权限」是指 `takedown.execute` 名单里有他，还是指「他就是这个任务的 assignee」？
两者的区别在 reassign 之后：原 assignee 已不在名单里、新 assignee 在。
**建议口径**：`can_act(...) and (actor == task["assignee"] or actor 有 coordinator 角色)`，
即「有权限 **且** 是这个任务的负责人（或统筹可代填）」。这一条要写进代码注释，
否则下一个人会以为是纯能力判断。

## 六 · 红线（这张票不许做的事）

1. **不许自己造任务。** `takedown_create` 只有 `revoke` / `invalidated` 两个合法触发，
   触发点在 T-310 / T-317。在 T-312 里造触发点 = 第三个写者。
2. **不许把 `takedown.waive` 和 `takedown.execute` 合成一把钥匙。** `WAIVE` 是双人审批，
   `EXECUTE` 是单人执行；合起来等于让执行人给自己批豁免。
3. **不许在 reducer 里重写迁移表。** `check_transition()` 是唯一一份。
4. **不许给任务加 `deadline`。** `#96/#101` 与 `check_no_deadline()` 都盯着这一条
   （`base/takedown.py:297-308`）；加字段要连指标文案一起改，那是产品决策。
5. **不许让前端继续算年龄。** 这是 §2.4.8 的现成案例：后端 `bj_date()` 是唯一「今天」来源，
   前端 `Date.now()` 在跨时区/跨零点时会给出不同答案，而两者看起来都对。
6. **不许在 T-314 之前打开 `can_act`。** 名单空集 → 六条路由全 403。fail closed 是对的，
   但顺序错了会把「数据是假的」换成「点了就报错」，后者更难排查。

### 一处没人管的空缺：`published` 从哪来

`should_create_task(trigger=..., published=...)`（`base/takedown.py:116`）的核心输入是
**这条内容到底有没有发到平台上**。而案件 state 里**没有 `published` 字段**，
`ingest_submission` 也不写它：

```bash
# 按键名搜会得到两处无关命中 —— 两个都不是「这条内容发布了吗」：
#   base/backend_recovery.py:277  published = []        ← 备份流程的局部变量
#   api/review_api.py:152/434     published_at          ← 报告摘要的字段
grep -rn "published" --include=*.py base/ api/ | grep -v "base/takedown.py"

# 按语义搜，0 命中：
grep -rn "is_published\|was_published\|\"published\"\]" --include=*.py base/ api/
```

★ **这一条要特别记**：上面第一个命令返回非空，而结论是「没有这个事实」。
如果只贴那一条命令就当证据，读的人会以为有 6 处生产者 ——
这正是 `AGENTS.md` §2.4.1 那个形状（读数比它要描述的东西大）。
真正的判据是第二个命令，以及「`ingest_submission` 的 payload 里有没有它」
（`base/submission_service.py:189-205` 逐字段可核）。
