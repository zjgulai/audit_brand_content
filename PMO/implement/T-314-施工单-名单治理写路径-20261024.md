> **`#93` 现在 `untested` 是准确的，但它准确的**方式**是「映射对象选错了」——

> 而 `validate_grant_actors` 的两条断言在 `verify_rbac.py` 的 C8/C8b 里活着。
> 这意味着：**`#93` 的前一半今天就能转 passed，只要把映射指过去** ——

## 二 · 一个必须裁定的点（比技术问题更靠前）

| ID | 问题 | 为什么不能工程定 |
|---|---|---|
| **D-314-1** | 三主体（提案 / 执行 / 审批）是**三条独立 HTTP 请求**，还是**一次请求带三个身份**？ | `validate_grant_actors(proposer, executor, approver)` 一次收三个 principal。而 HTTP 世界里一个请求只有一个 session。两条路的产品含义完全不同：**三条请求** = 真异步流程（提案人等执行人、执行人等审批人，可能隔天）；**一条请求** = 一个人替三个人填名字（**那不是三权分立，是三个签名栏**） |

**本票的默认处置**（写下来是为了让后来者知道这是默认，不是裁定）：
按**三条独立请求**做，因为：
- `#93` 的原文要求「三方不同人」而 `validate_grant_actors` 是**在授予发生的那一刻**校验三方；
- 一条请求带三个名字，无法证明另外两个人真的在场 —— 那是「填表」不是「审批」。

**代价（必须写明）**：三条请求意味着 grant 需要**中间态**（`proposed → executed → approved`），
以及「提案过期」这条规则。本票按 `proposed → executed → approved` 三态做，
过期留给 `WV-` 台账式的外部裁定（同 `PMO/audit/waiver-v1.json` 的做法）。

## 三 · 落进 state 的确切形状

名单治理**不放进 case aggregate** —— 它与具体案件无关，是租户级配置。
但 `BusinessEventStore.execute()` 要求一个 `aggregate_id`（`base/business_event_store.py:304-310`）。
所以用**合成聚合 ID**：`"grants:" + tenant`。

```json
// aggregate_id = "grants:on_xxx"
{
  "case_id": "grants:on_xxx",
  "version": 3,
  "tenant": "on_xxx",
  "grants": [
    {
      "grant_id": "grant-8c3f2a9b1e7d6054",
      "capability": "takedown.execute",
      "user_id": "ou_yyy",
      "scope": {"tenant": "on_xxx", "product_lines": ["pump"]},
      "platform": "amazon_us",
      "reason": "该内容需人工下线，指定执行人",
      "state": "approved",
      "proposed_by": "ou_dp4",
      "proposed_at": "2026-10-24T08:00:00Z",
      "executed_by": "ou_it",
      "executed_at": "2026-10-24T09:10:00Z",
      "approved_by": "ou_coord",
      "approved_at": "2026-10-24T11:30:00Z",
      "revoked_by": null,
      "revoked_at": null,
      "revoke_reason": null,
      "history": [
        {"action": "propose", "actor": "ou_dp4", "at": "...", "from": null, "to": "proposed"},
        {"action": "execute", "actor": "ou_it", "at": "...", "from": "proposed", "to": "executed"},
        {"action": "approve", "actor": "ou_coord", "at": "...", "from": "executed", "to": "approved"}
      ]
    }
  ]
}
```

**五条设计决定：**

1. **`aggregate_type` 要新加一个值。** 现在是硬编码 `"review_case"`，
   **共 3 处**（复算，不是估）：`base/business_event_store.py:359`、`:380`、
   `base/review_reducer.py:130`（`_event()` 里）。
   要改成一个按 `aggregate_id` 前缀判的函数，三处都调它，
   否则投影层会把 `grants:` 当作案件写进 `review_cases` 表（`base/projection_store.py:149-155`）。
   **这是本票唯一的底层改动，也是最容易漏的一处** —— 漏第 130 行会让事件里的
   `aggregate_type` 与批次里的不一致，而**没有任何现有断言会抓到**。

2. **`history` 就是留痕四元。** 谁（`actor`）/ 何时（`at`）/ 改了什么（`from`→`to`）/
   依据（提案时写进 `reason`，执行/审批时写进 `history[].note`）。
   **不另建一张留痕表** —— 同一份数据两处存，必然漂移。

3. **`grant_id` 用确定性哈希**，不用自增（同 T-311/T-312 的理由）：
   ```python
   "grant-" + sha256(canonical({capability, user_id, scope, proposed_at}))[:16]
   ```

4. **`platform` 只对 `takedown.*` 有值。** 前端已经在发这个字段
   （`AdminGrantsPage.tsx:88` 的 `...(tab === "takedown" ? { platform } : {})`）。
   签发授权没有平台维度 —— 别为了「字段统一」给它补一个空值，
   那会让「不适用」与「漏填」长得一样。

5. **`revoked_*` 三个字段本票**只做结构，**不实现撤权动作** —— 那是 T-315。
   写成 `null` 而不是省略，是为了让 T-315 不必改 schema。

## 四 · 一个必须同时解决的底层问题：`TAKEDOWN_ALLOWLIST` 是常量

`base/rbac.py:80-83` 的名单是模块级 `frozenset`，`_takedown_allowed()` 直接读它。
授权一旦进了权威，`can_act()` 就必须能读到**当前有效名单**，否则：

- 授权写进去了，`can_act` 还是 `False`（名单常量没变）；
- 于是「授权成功」这件事**看起来成功、实际不生效** —— 第五次同一个病。

**改法（最小）**：`_takedown_allowed()` 增加一个**可注入的名单源**：

```python
# base/rbac.py
_ALLOWLIST_SOURCE = None      # None = 用模块常量（默认，开发装配与旧验证器不变）

def set_allowlist_source(fn):
    """生产启动时注入：() -> {capability: frozenset(principal_id)}。"""
    global _ALLOWLIST_SOURCE
    _ALLOWLIST_SOURCE = fn
```

生产在 `ProductionRuntime.start()` 之后注入一个读 `ProjectionStore` 的函数。

**为什么用注入而不是改签名**：`can_act(` 的真实调用点分布是
**生产 2 处 + `tools/verify_rbac.py` 28 处**（`grep -rn "can_act(" --include=*.py` 可复算）：

```
api/production_app.py:543   can_act(principal, capability, case)      ← reauth 动作校验
api/write_api.py:321        can_act(principal, "case.review", ...)    ← 复核动作
tools/verify_rbac.py        28 处                                     ← 断言与 mock 注入
base/release_gate.py        0 处（它自己用 principal["capabilities"]，见下）
```

> ★ 这里我第一版写的是「13 处调用点，其中 9 处是验证器」——**那是估的，不是数的**。
> 复算后是 2 + 28。写错的方向不重要，重要的是：**如果我按 13 去评估改动面，
> 会把一张 0.5 天的票估成 1.5 天**，而且会误以为「验证器是主要成本」。
> 实际成本恰恰相反 —— 生产只有 2 处，但**这 2 处里没有一处管 `release.*`**，
> 于是「签发授权写进名单」与「签发真的读名单」之间少一跳（见下）。

**不注入而是改签名，代价在哪**：那 28 处验证器断言全部是
`can_act(p, "takedown.execute", case) is True/False` 的形状，
改签名会让它们全部 `TypeError` —— 于是一张授权票变成一次 `verify_rbac.py` 重写。
注入 `_ALLOWLIST_SOURCE` 则**默认值保持模块常量**，28 处一行不动。

### ★ 顺带查出的第四处「两个口径」：`release.*` 的能力判定有两套

```python
# base/release_gate.py:302-311 —— 读 principal["capabilities"] 这个字段
if "release.sign" not in (principal.get("capabilities") or []):  raise SoDViolation
if "release.revoke" not in caps:                                 raise SoDViolation

# api/production_app.py:543 —— 读 rbac 的角色矩阵
if not can_act(principal, capability, case):                     raise HTTPException(403)
```

两条路**对同一件事给出不同答案**：`principal["capabilities"]` 是调用方给的字典字段，
而 `can_act()` 查的是 `_ROLE_CAPS` + `TAKEDOWN_ALLOWLIST`。一个每天鉴权的人
（`principal_directory`）如果 `capabilities` 字段被填错，`release_gate` 会放行而 `reauth` 会拒；
反过来也一样。

**本条不在 T-314 范围内修**（它属 T-310 的 `_binding`/`_authorize` 那一侧），
但它决定了 T-314 的一个设计选择：**授权名单只喂 `takedown.*`，不喂 `release.*`**。
理由：`release.*` 今天根本不读名单（它读 `capabilities` 字段），
现在把签发授权写进名单，会做出一个**看起来生效、实际没人读**的机制 —— 第六次同一个病。
签发授权的消费者要么是 T-310c 里改造后的 `_authorize`，要么什么都不做。
**本票只保证「名单写进去了、且 `takedown.*` 真读到了」，不替 `release.*` 造一个假消费者。**

**反向对照（这条必须有）**：注入一个恒返回空集的源 → `can_act(signer, "takedown.execute")` 必须 `False`；
注入含该 id 的源 → 必须 `True`。**两向都断言**，否则不知道它有没有真在读。

## 五 · 拆票

### T-314a · reducer 三条命令 + `aggregate_type` 分流（1 天）

**改 `base/review_reducer.py`**（追加）：

```python
def _grant(state, command, actor, payload, now):
    """grant_propose / grant_execute / grant_approve 的纯状态迁移。"""
```

| 命令 | 前置状态 | 动作 | 拒绝码 |
|---|---|---|---|
| `grant_propose` | 无该 `grant_id` | 新建，`state="proposed"`，写 `proposed_by/at` | `bad_grant`（缺 capability/user_id/scope/reason） |
| `grant_execute` | `state=="proposed"` 且 `actor != proposed_by` | `state="executed"`，写 `executed_by/at` | `not_proposed` / `same_actor` |
| `grant_approve` | `state=="executed"` 且 `actor ∉ {proposed_by, executed_by}` | `state="approved"`，写 `approved_by/at` | `not_executed` / `same_actor` |

**三条硬约束：**

1. **三方不同人这一条在 reducer 里也要有。** `validate_grant_actors()` 是**授予时的综合校验**，
   reducer 的是**逐步的**。两条不能互相替代：前者证明「三个都合格」，后者证明「不能一个人走完三步」。
2. **`reason` 必填且不可改写。** 后续命令不许动 `reason`（它是「依据」，改了就等于换了理由）。
3. **`history` 只追加，不重写。** 每条命令 `history.append(...)`，不许 `history[i] = ...`。

**改 `base/business_event_store.py`**：`aggregate_type` 按前缀判

```python
def _aggregate_type(aggregate_id):
    return "grant_registry" if aggregate_id.startswith("grants:") else "review_case"
```

两处硬编码（`:359`、`:381`）都改用它。

**改 `base/projection_store.py`**：`apply_batch()` 遇到 `aggregate_type == "grant_registry"` 时
写一张新表 `grant_registry(tenant, version, state_json)`，**不写** `review_cases`。
这需要 `SCHEMA_VERSION = 2` + 一个 migration —— **本票唯一一次 schema 升级**，
所以它必须有回滚办法（见 §七）。

### T-314b · 三条路由 + `validate_grant_actors` 接线（0.5 天）

### T-314c · 名单源注入（0.5 天）

**改 `base/rbac.py`**：加 `_ALLOWLIST_SOURCE` + `set_allowlist_source()`（§四）。
**改 `api/production_app.py`**：`ProductionRuntime.start()` 之后注入。

注入函数：

```python
def allowlist_source():
    out = {"takedown.execute": set(), "takedown.waive": set()}
    for tenant_state in projection.list_grant_registries():
        for g in tenant_state.get("grants") or []:
            if g.get("state") == "approved" and g.get("capability") in out:
                out[g["capability"]].add(g["user_id"])
    return {k: frozenset(v) for k, v in out.items()}
```

**注意一个业务事实**：`takedown.waive` 需要**两个人**（`base/takedown.py:218-227`）。
名单里只要有这两个人的 id 即可，不需要在这里判「够不够两个」——
那是 `check_waive()` 的事。**两处都判会让「名单里有 1 个人」与「豁免被拒」两个现象分不清**。

**★ 本子票只做 `takedown.*`，不做 `release.*`。**
理由见 §四 末尾：`release.*` 今天读的是 `principal["capabilities"]` 字段，
不是名单；把它写进名单会做出一个「看起来生效、实际没人读」的机制。
签发授权的消费者要等 T-310c 改造 `_authorize` 之后才有对象。

## 六 · 红线（这张票不许做的事）

1. **不许把三主体压成一条请求。** §二 D-314-1 已说明理由；压成一条 = 三个签名栏。
2. **不许在 `grant_propose` 就判定三方合格。** 那一刻执行人与审批人还没到场。
3. **不许给 `TAKEDOWN_ALLOWLIST` 加一份「默认维护者」。** 那是
   `PMO/上线Ticket清单-20261022.md` §七 T-91-follow 记过的第二次同类：
   「给它加一份空名单 = 制造第二个『注释说有维护者、实际没有』的假机制」。
4. **不许把授权写进 `TAKEDOWN_ALLOWLIST` 这个常量。** 常量是默认值，授权是数据；
   写进常量意味着「重启后授权消失」且「git diff 里有人的 id」。
5. **不许让前端按钮显隐当成校验。** 见 §五 T-314d 的反向对照。
6. **不许在 `grant_registry` 表里存个人身份信息。** 只存 `user_id`（`ou_xxx`）与 scope，
   不存姓名、邮箱、头像 —— `PMO/audit/waiver-v1.json` 那条「逐字 PII 不进公开仓」同样适用。
