## 二 · 前置与口径（开工前定死）

| 项 | 口径 | 依据 |
|---|---|---|
| 撤权是什么 | grant 记录的状态迁移 `approved → revoked`（**不是删除**），落 :534-535 三个占位字段 + history 追加 | 权威不可变；history 是 `{action, actor, at, from, to, note}`（:560-581 既有形状），四元留痕 spirit |
| 授权版本是什么 | **聚合 `state["version"]`**。每条命令统一 `version += 1`（reducer :859），撤权命令天然使版本递增 —— **不必另加字段** | 票面判据 ③ 的落点；变异 = 让撤权绕开统一 version+1 路径 |
| 谁能撤 | 需 `admin.grant.approve` 或 `admin.grant.execute` 能力 + 同租户（service 层判）；**actor ≠ 该 grant 的 user_id**（不许自己撤自己的授权，reducer 层判） | 三权分立精神（提案人不能执行，同理）；T-392（signer/revoker 拆分）不挡本票 —— 撤权 actor 用现有能力，角色重划留裁定门 |
| 名单覆盖面 | **本票只把 `release.sign` 纳入名单**。`release.revoke` 不入名单（signer 角色矩阵本含它，`base/rbac.py:59-60`） | #123 样本 (a)「撤权后对历史签发做撤回必须成功」成立的前提 —— 若 revoke 也入名单，撤权会误伤撤回 |
| 边界声明 | 纯靠 grant 拿 `release.revoke` 的人（`GRANT_CAPABILITIES` 授出的），被撤后撤回失效 = **预期**，写进验证器注释 | §一 最后一行的病：不写明，下一个人会当 bug 修 |
| 判定放哪 | 名单判定进 **rbac 层**（新 `can_sign_release(principal, case)`），`release_gate._authorize` **不加名单分支** | gate 是无 IO 纯内存模块，注入名单要多一条线；单一授权真相在 rbac（`_takedown_allowed` 机制 :146-172 就是按 capability 查 frozenset 表，直接容纳 release.sign） |

## 三 · 拆票

### T-315a · reducer 撤权命令（0.5 天，**与 T-310 并行**）

**改 `base/review_reducer.py`**：`GRANT_COMMANDS`（:449）扩 `grant_revoke`；
进 `_grant` 既有纯函数（target 查找复用 :546-549 样板）。

规则：

| 校验 | 拒绝码 |
|---|---|
| target 存在且 `state == "approved"` | `LedgerNotFound` / `LedgerConflict("grant_not_active")` |
| `actor != target["user_id"]`（不许自己撤自己） | `LedgerConflict("self_revoke")` |
| `reason` 非空（留痕四元之外必需） | `LedgerValidation("bad_revoke")` |
| 落 `revoked_by/revoked_at/revoke_reason` + `history.append({action:"revoke", ...})` | — |

幂等：reducer 层不做幂等键（既有分工），重复撤 → `LedgerConflict("grant_not_active")` 显式化；
跨重启重放由权威层 `(principal, tenant, idempotency_key) + request_sha256` 处理
（`business_event_store.py:328-345`）。**逐步 actor 校验进 reducer**（`_grant` docstring
:486-495 明确 `validate_grant_actors` 不能替代逐步校验）。

**判据**：追加进 `tools/verify_review_reducer.py`（纯函数语义）与 `tools/verify_grant_registry.py`
（P5 断言扩展：approved 撤权后 `can_act(该人, "takedown.execute")` 从 True 变回 False ——
名单自动收窄的机制性断言）。

### T-315b · 名单生效（1 天，**等 T-310c**）

**改 `base/rbac.py`**：名单机制从 `TAKEDOWN_CAPS` 泛化到 `release.sign` ——
新增名单本常量（两本名单同纪律，:77-79 注释按能力分本）、放宽 `_takedown_allowed:159-160`
的门槛（或并列 `_release_allowed`，实现取侵入小者）、`can_act:190` 加分支；
新公开函数 `can_sign_release(principal, case)` = SoD/case 可读性之外再加名单门槛。

**改 `api/production_app.py`**：`allowlist_source()`（:337-338）扩 `release.sign` key ——
撤权后 state != "approved" 自动出局，**无需任何同步代码**。

**改 `base/review_command_service.py`**：T-310c 的 `release_decision` 在 SoD 校验之后、
消费 step-up 之前插 `can_sign_release` 判定（顺序仍是 T-310 施工单的硬约束：
②权限 → ③消费 → ⑤execute，顺序反了 = 无权限者烧别人 token）。

**改 `base/release_gate.py`** —— **#123c，本票唯一的新判定点**：
`gate.revoke`（:375-393）加「撤回绑定原签发人」：取 `state["release"]["signatures"]` 最后一条，
`sig["signer_id"] == principal["id"]` 否则拒（新拒绝码 `not_original_signer`，异常映射 403）。
gate 改的是**判定函数**（保留类，`verify_release_gate.py` 不动仍有效），不是状态落点。

**边界钉住**：名单只盖 `release.sign`；`release.revoke` 不入名单 ——
变异「把 release.revoke 加进名单本」必须让 #123a 样本变红（证明这条边界不是靠巧合成立）。

## 四 · 落进 state 的确切形状

```json
{ "grant_id": "g-...", "capability": "release.sign", "user_id": "u_signer",
  "state": "revoked", "revoked_by": "u_admin", "revoked_at": 1761...,
  "revoke_reason": "调岗收回签发权",
  "history": [ {"action": "revoke", "actor": "u_admin", "at": 1761...,
                "from": "approved", "to": "revoked", "note": "调岗收回签发权"} ] }
```

**为什么放 grants 聚合不另开 aggregate**：撤权是 grant 记录的状态迁移，
`grants:<tenant>` 聚合已承载提案/执行/审批（T-314a），加一个命令不加一个聚合。

## 六 · 红线（这张票不许做的事）

1. **不许删除 grant 记录或重写 history**。撤权是迁移；history 只追加（T-314e M5 的同款守卫）。
2. **不许把 `release.revoke` 入名单。** 否则撤权误伤撤回，#123a 直接破（§二 口径 + M4 变异）。
3. **不许在 `release_gate` 里加名单源/IO。** gate 是无 IO 纯内存模块；单一授权真相在 rbac。
4. **不许让撤权需要被撤人同意。** 这是管理动作，不是双方协议。
5. **不许跳过「actor ≠ user_id」自撤校验。** 自己撤自己的授权 = 三权分立被绕开的最短路径。
6. **不许动 T-392。** signer/revoker 角色拆分是产品裁定门；本票撤权 actor 用现有能力，
   裁定落地后只换 actor 判定那一行，不动命令与名单机制。
