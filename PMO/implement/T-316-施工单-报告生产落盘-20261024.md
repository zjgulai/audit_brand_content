## 三 · ReportStore 的 ACL 必须改（真缺陷，不是接线）

`_default_authorize` 与 `base/rbac.py` 的 `can_read_content()` 是**两套权限模型**：

| | `report_store._default_authorize` | `rbac.can_read_content` |
|---|---|---|
| 字段名 | `principal["role"]` 单数 | `principal["roles"]` 复数 |
| 值的大小写 | `"DP3" "DP4" "IT"` 大写 | `dp3 dp4 it` 小写 |
| 判定方式 | 一条 `if/elif` 链，取第一个匹配 | 角色并集，任一授予即可 |
| IT 角色 | `role == "IT"` 落到 `return False`（未列出） | 显式 `IT_CAN_READ_CONTENT` 开关 |
| 与 `#133` 的关系 | 无关 | `verify_rbac.py` 的 12 组断言 |

**这不只是字段名不一致 —— 是「两套权限模型」。**
`rbac.can_read_content` 有角色并集语义（`verify_rbac.py` 的 C10「多角色并集：不得被第一个匹配角色短路」），
而 `_default_authorize` 的 if/elif 链**恰好是「第一个匹配角色短路」**的那种写法。

**修法有两个，必须选一个并写明理由：**

| 选项 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `ReportStore(authorize=...)` 传入生产自己的授权函数，`_default_authorize` 保留给验证器与旧调用 | 不动 `report_store.py` 的判据；`verify_report_store.py` 的 12 个夹具原样绿；生产用 `can_read_content(principal, case)` + 报告 ACL 的 `tenant` 比对 |
| **B** | 把 `_default_authorize` 改成读 `roles` + 复用 `rbac` | 改判据：`verify_report_store.py` 的夹具要全改（`role`→`roles`、大写→小写），且 `#56/#59` 的断言可能连带变 |

**推荐 A**，因为 `ReportStore.__init__` 已经留了 `authorize` 参数（`base/report_store.py:173`）——
那是给这件事准备的口子，不是偶然。

**但 A 有一个必须写清的后果**：报告的回读权限将由 **案件的 `can_read_content`** 决定，
而报告索引里那份 `acl`（`report_store.py:365`）只用于**留痕**，不再用于判定。
这一点要写在代码注释里，否则下一个人会以为 `acl` 还在生效 ——
`AGENTS.md` §2.4.1 那个病（「名字还在 ≠ 它还在起作用」）。

## 四 · `report_snapshot` 断链（真缺陷）

```
base/orchestrator.py:544        "report_snapshot": report_snapshot      ← 产出
base/judge_entry.py:144-154     返回字典里没有它                          ← 丢在这里
base/submission_service.py:196  payload["ir"] = ir                       ← 只取 ir
```

`grep -rn "report_snapshot" --include=*.py base/ api/ | grep -v orchestrator` → **0 命中**。

所以即使做完 §二 与 §三，提交链路仍然**拿不到**渲染输入。三处修法：

1. `judge_entry` 的返回字典加 `"report_snapshot": result.get("report_snapshot")`
   —— 一行，但它让 `judge_entry` 的返回契约多一个键，
   `tools/verify_orchestrator.py` 的 C4 段对七个顶层字段有断言（`:437` 记过「顶层 state 与
   obligations 根本不存在」的历史），要确认不会因此变红。
2. `submission_service.prepare()` 把 `report_snapshot` 放进 payload。
3. `review_reducer._ingest_submission()` 把它写进 state（与 `ir` 并列，
   **不是嵌在 `ir` 里** —— `report_render` 的入参是一个独立 snapshot，不是 IR 的一部分）。

**为什么 snapshot 要与 ir 并列存、不重算**：
`report_render.mjs` 的 `validateSnapshot()` 要求 `failure_kind_counts` / `unknown_bucket_counts` /
`evidence` / `unassessed` / `receipt` 五个键（`:111-203`），其中 `evidence` / `unassessed`
**判定时是空数组**（`orchestrator.py:511-512`），结案时才有内容。
如果结案时重算 snapshot，就会用「结案时的 evidence」渲染「判定时的报告」——
**报告的 IR 与 evidence 来自两个时刻**，那是 `AGENTS.md` §2.4.8 的典型。
正确做法：**判定时冻结 snapshot，结案时原样使用**。evidence 为空就渲染成「无」，
这与 `report_render` 的既有行为一致（`:255-261` 的 `asArray(...)`）。

> ★ 这是一条**产品含义的选择**，不只是技术选择：它决定了「报告反映的是判定那一刻，
> 还是结案那一刻」。本单按「判定那一刻」做，理由：报告的核心是**结论与依据**，
> 而结论在判定时就定了；结案只加人工裁决结果，那属于 `review.formal_reviews`，
> 不属于报告正文。**若产品要求报告含结案信息，本单 §六 的 T-316c 要重写。**

## 五 · 落进 state 的确切形状

```json
"report_snapshot": { "...": "判定时冻结的 renderReport 入参（五键）" },
"report": {
  "report_id": "rp8c3f2a9b1e7d605",
  "url": "https://.../reports/rp8c3f2a9b1e7d605.md",
  "path": "reports/rp8c3f2a9b1e7d605.md",
  "sha256": "...",
  "source_ir_id": "ir-...",
  "source_ir_version": "content-unit-v1",
  "source_ir_fingerprint": "...",
  "created_at": "2026-10-24T08:00:00Z",
  "published_at": "2026-10-24T09:12:00Z",
  "renderer": "report_render.mjs@v1"
}
```

**四条设计决定：**

1. **`report` 放 case aggregate**（同 T-310/311/312）。一条报告属于一个案件。
2. **`report_id` 由 `ReportStore` 算，不由 reducer 算。** 它是内容寻址
   （`report_store.py:275-277`），reducer 拿不到渲染文本。所以 reducer 只接受
   **已算好的** `report_id/url/sha256`，并校验格式。**这条边界不许模糊**：
   两边各算一次 = 两份公式必然漂移。
3. **`published_at` 与 `created_at` 分开。** `created_at` 是报告内容的时间戳（进 `report_id` 的哈希），
   `published_at` 是落盘时间（不进哈希）。合成一个会让「同内容重发」被算出不同 id。
4. **`report_snapshot` 不删。** 它是重签与重建的唯一来源（`ReportStore.rebuild` 需要 `ir`，
   而 `render_fn` 需要 snapshot）。删了就只剩 `.md` 文件，无法重建。

### T-316c · 渲染适配层（1 天）

新 `base/report_render_bridge.py`（约 60 行）：

```python
def render(snapshot) -> dict:
    """调 node 跑 report_render.mjs，超时 30s，返回 {ok, markdown, errors}。

    ★ 不在这里做任何校验 —— validateSnapshot 是渲染器自己的事。
```

三条硬约束：
1. **超时必须显式**（`subprocess.run(..., timeout=30)`）。没有超时的子进程调用在

### T-316e · 重签（0.5 天）

`POST /api/v1/reports/{id}/resign`：

**语义必须先说清**（今天的 `WRITE_PATHS` 只有路径名，没有语义）：
- 报告正文**不可变**（`report_store.py:328` 的 `immutable_conflict` 守着）；
- 「重签」= 生成一个**新的签名访问链接**，指向**同一份 .md**；
- 所以它不改 `report_id`、不改 `sha256`、不改文件，只产出一个带过期时间的签名 URL。

**因此它需要一套签名 URL 机制**，而全仓没有。两个选项：
- **A**：`url = static_base + "/reports/<id>.md?exp=<ts>&sig=<hmac>"` —— 但
  `_check_static_base` 拒绝带 query 的 base（`report_store.py:158`），且静态文件服务不做签名校验，
  这条路要改 nginx/应用侧。
- **B**：`url` 指向应用的一个转发端点 `/api/v1/reports/{id}/content?token=...`，
  但 `report_store._valid_url` 明确拒绝 URL 含 `/api/`（`:198`）。

**两条路都被现有判据挡住。** 这说明「重签」这个动作**在今天的契约里没有位置**。
→ 本票**不做重签**，把它标 `blocked`，并写清：需要先裁定「报告 URL 是否允许带签名参数」，
那会动 `_check_static_base` 与 `_valid_url` 两条判据（`#56/#59` 覆盖）。

> ★ 这是本单唯一一处**主动缩小范围**。写下来是因为：如果不写，T-316c 会把
> `/resign` 做成一个「返回一条不带签名的普通 URL」的东西 —— 那看起来能用，
> 实际没有任何访问控制，而**没有任何断言会红**。

## 七 · 红线（这张票不许做的事）

1. **不许在没裁定 D-316-1 前移植渲染器。** 两份实现必然漂移，而 7 行判据全挂在 Node 那份上。
2. **不许让报告失败回滚结案。** 结案是人的动作，报告是它的产物。产物生成失败，
   状态已经是 closed 了 —— 回滚等于抹掉一个人的判断（P7 就是这一条）。
3. **不许在结案时重算 snapshot。** §四 已说明：那会让报告的 IR 与 evidence 来自两个时刻。
4. **不许让 reducer 算 `report_id`。** 内容寻址的公式只有 `ReportStore` 一份。
5. **不许把 `/resign` 做成返回普通 URL。** §六 T-316e 已说明：那看起来能用、实际无访问控制。
6. **不许把报告 ACL 的 `acl` 字段当成还在生效。** §三 选项 A 之后它只是留痕。
