## 二 · 前置与口径（开工前定死）

| 项 | 口径 | 依据 |
|---|---|---|
| 重审输入 | `state["content"]` + **当前** `rule_snapshot` / `kb_snapshot`（正是 `_changes` 检出的五类变化中的两项） | 失效的原因就是要换快照；用旧快照重审 = 没审 |
| **不许重新走 submission 流程** | 不新建 ContentUnit、不动 `content.fingerprint`、`raw_sha256`/`text_sha256` 原样 | 单元身份不变（`raw_sha256` 是 unit_id 的输入）；重审是重判，不是重进件 |
| 旧 IR 保留 | **靠权威事件链**：每条命令的 `events[0].state` 是全量快照且不可变（`business_event_store.py:222-225`）—— 历史 batch 里的旧 IR 天然「在盘上且逐字节未变」；state 另加 `ir_prev` 指针（`{ir_id, ir_version}`）便于审计读取 | #98 判据 ②「仍在盘上且内容未被修改」由不可变事件链满足；「可查询」不是判据要求，指针是加分的审计便利 |
| job 生命周期 | `state["release"]["active_job"]` / `successor` —— **T-310 的 release 形状本来就预留了这两个键**（T-310 施工单 §四） | T-310 只做容器不搬 job（T-310 施工单 §九 明文「否则 T-310 会变成 T-317」）；本票就是那个「搬」 |
| 谁触发重审 | 服务层 `invalidate_if_due` 挂 `maintain_once()` 心跳（生产调用点 `api/production_app.py:357` 一带）—— **没有触发点的规则等于没有规则**（`mark_stale` 0 调用的教训） | `invalidate` 今天 0 生产调用；扫描频率与 `mark_appeals_stale` 同款（30s 心跳内生效） |
| 报告守卫怎么改 | `state["reports"]` 改为**追加列表**，`state["report"]` 保留为「最新一份」兼容读侧；`report_immutable` 守卫改为「同 id 幂等重放 / 不同 id 追加」 | 文件侧不用动：ReportStore 内容寻址 + index.jsonl 只追加（`report_store.py:229-239`），同案两个 report_id 天然共存，immutable_conflict 只在「同 id 不同字节」触发（:327-328/:345-351） |

## 三 · 拆票

### T-317a · reducer 重审命令（1 天，**等 T-310**）

**改 `base/review_reducer.py`**，四条新命令进 `state["release"]`：

| 命令 | 前置 | 动作 | 拒绝码 |
|---|---|---|---|
| `release_invalidate` | `release.status == "signed"` 且 `_changes` 非空 | 建 queued job（**job_id = sha256(case_id\|version\|change_set)[:16]**，确定性派生，禁 `now`） | `nothing_to_reaudit` |
| `release_job_start` | job queued | running；有前 job 未完 → 顶成 `successor`（沿用 gate :516-533 的继承语义） | `invalid_transition` |
| `release_job_complete` | job running | done；回 `pending_release`/「待放行」（继承 gate :525-532 两分支） | `invalid_transition` |
| `rejudge_apply` | job running | **携带 `expected_prev_ir_id` 乐观校验** → 写 `ir_prev = {ir_id, ir_version}` → 替换 `ir`/`report_snapshot`/`judgment` | `ir_moved`（并发重判）/ `bad_rejudge` |

**`_changes` 保持唯一一份纯函数**：`_changes`（release_gate:396-441）被 reducer 复用
（import 或搬移取侵入小者，施工时定并写注释），**不许复制第二份** —— 两份失效判据漂移
=「检不出失效」与「假失效」两种病交替出现，而且都长得像正常。

**判据**：追加 `verify_review_reducer.py`（纯函数段）+ 新 `tools/verify_reaudit_persistence.py`。

## 六 · 红线（这张票不许做的事）

1. **不许重新走 submission 流程。** 重审是重判，不是重进件；content fingerprint 不许变。
2. **不许删旧 IR / 旧报告文件。** 权威不可变；R2 是产物级判据。
3. **job_id 不许含 `now`。** 幂等重放会漂移（§一 第三行）。
4. **不许复制 `_changes` 第二份。** 失效判据漂移比没有判据更难查（§T-317a）。
5. **重审不许用旧快照。** `rule_snapshot`/`kb_snapshot` 必须取当前值 —— 失效的原因就是要换它们。
6. **不许在本票接飞书/通知外发。** 「重审完成」要不要通知、发给谁，走 T-313 的 emit 命令，
   本票只产事件，不自建通道。
