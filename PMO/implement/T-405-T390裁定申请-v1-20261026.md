## 一 · 不裁定会发生什么

### 1.1 桩在哪，以及它是「验过的」

```bash
$ sed -n '136,140p' base/judge_entry.py
    result = Orchestrator(
        rule_judge=rule_component,
        semantic_judge={"status": "untested", "findings": []},
        evidence=evidence_component,
```

`base/judge_entry.py` 共 197 行（`wc -l base/judge_entry.py`），桩在**第 138 行**。

这个桩**不是坏的，是故意留空的**，而且它被自证挡着：

```bash
$ python3 tools/verify_judge_entry.py | tail -3
✅ 12/12 全过
$ echo $?
0
```

其中 `R1` **直接依赖「语义层不产出任何东西」**才是绿的：

| 项 | 断言 | 接线后会怎样（实测） |
|---|---|---|
| `R1` | RuleJudge 空命中 → `findings == []` 且 `REVIEW` / `partial`，不许 `PASS` | **会红。** 复现：mock 掉 `RuleJudge.judge` 返回 `[]`，再给 `semantic_judge` 塞 1 条 candidate —— 今天 `findings==[] → True`（绿），接线后 `findings==[] → False`（**红**）。<br>★ 注意标签**没变**（两次都是 `REVIEW` / `partial`）—— 红的只有「finding 数」这一位。**这条断言是这处接线的探测点。** |
| `C4` | 图片画面语义未覆盖 → `partial` 永不 `PASS` | **仍绿。** 它靠的是 unit 的 `does_not_cover=["画面语义"]` + 三个空族，与桩无关（上一条实测里接线后 `coverage` 仍是 `partial`）。列出来是为了说明：**`partial` 有两个来源，别把两者混成一个** |

**所以「12/12 全过」不能读成「语义层没问题」。** 它读作：*今天没有任何东西会产出一条语义 finding，而这一点是被断言住的。*

同一件事还有一条更硬的执行点在 `tools/verify_engine_contract.py`：

```bash
$ python3 tools/verify_engine_contract.py 2>&1 | grep V56
  ✓ V56  ★ Q42=A 的判据：「P1/P2 零落点」是**量出来的** —— 判定路径上没有任何语义层调用
```

**V56 今天绿，正是因为它断言「判定路径上没有语义层」。** 它的注释写着：*「它红了的那一刻，正是回去改验收表那一行的时刻」*。
→ **接 P1 的那一刻，V56 必红。这是设计意图，不是 bug。** 谁做 T-405，就得同时改这一条，而改它的前提是知道口径（A 还是 B）——**这就是本裁定必须先到的原因之一。**

### 1.2 缺的具体是什么能力

这里必须把话说准。缺的**不是**「识别不出问题」，而是**「识别出来了也不能算数」**。

实测：把 291 条广告记录里**有正文**的 232 条全部走生产入口 `judge_unit`：

```bash
$ python3 - <<'PY'
import sys, json; sys.path.insert(0,'.')
from base import contract as C
from base.judge_entry import judge_unit
recs=json.load(open('research/governance/skeleton/_data/records.json'))
n=zero=0
for rec in recs:
    u=C.from_ad_record(rec)
    if not (u.get("text") or "").strip(): continue
    u["parse_status"]="ok"
    r=judge_unit(u, clock=lambda:1000)
    if r["run_state"]!="OK": continue
    n+=1; zero += (not r["findings"])
print("有正文 unit=%d，规则零命中=%d" % (n, zero))
PY
有正文 unit=232，规则零命中=98
```

**98 / 232 = 42.2%** 的真实文案，规则一条都没抓到。这 98 条里：

| 读数 | 值 | 复现 |
|---|---|---|
| 原表 `风险等级` | `合规·绿` 97 条 / `待复核·灰` 1 条 | 见 §七 命令 4 |
| 今天判定标签 | **`REVIEW` 98 条（100%）** | 同上 |
| 规则库规模 | 36 条规则 / 19 个 active 控制点 | `research/governance/skeleton/rules-v1.json` |

**结论一句话**：那 98 条里若有真问题，**今天没有任何一条链路能把它变成 BLOCK** —— 不是因为判错了，是因为**语义层不存在**。
这也是为什么「今天不违规」不能写成「今天做到了」（`裁定-R118` 同一句）。

> ⚠️ 一个必须同时说的反面：那 97 条标 `合规·绿` 的，**并不因此就是合规的**。原表的「绿」是**旧系统/人工**给的，
> 不是本引擎给的。本文不主张它们有问题，只指出：**今天的引擎对它们没有意见，而引擎没有意见这件事本身没有信息量。**

## 四 · 实测样本（真跑，不是构造）

### 4.0 探针做了什么

两件事分开做，因为**它们回答的问题不同**：

- **【桩】**：`judge_entry.judge_unit(unit)` —— 生产入口，语义是那个常量。
- **【A】/【B】**：同一个 `Orchestrator`，同样的 `rule_judge` / `evidence` / `coverage` / `authority_query`，
  **只把 `semantic_judge` 换成一个返回 1 条 finding 的函数**，`status` 分别取 `candidate` / `confirmed`。
  依据查询器用**生产真正在用的那个**（`SubmissionIngestor()._query()` → `ExternalStandardsAuthority`，
  快照 `external-stdlib-v1:b7c4ec0f7c158692`），不是 `judge_entry._local_authority_query` 那个恒 `untested` 的默认。

> 这一步很关键：若用默认查询器，`authority_state` 恒落 `missing`，L4 会走链 6（REVIEW）而不是链 7（BLOCK）——
> **读数会指向「语义不够格」，而真因是「依据查询器没接」**。这与 `AGENTS.md` §2.4.1 第 1 行同一个形状。

`semantic_judge` 是 `Orchestrator` 的注入点（`base/orchestrator.py:207/214/355`），**探针不需要改任何文件**。

### 5.2 接线的第一道真实障碍：两处契约不齐

## 六 · 为什么这不是一个工程决定

这一节必须写清楚，因为这个裁定看起来**很像**技术选型（三个方案各有工程量），**但它的对象不是技术**。

### 6.1 它决定的是「责任落在谁身上」

A/B/C 三者的技术差别是几十行代码，**它们的分歧点只有一句**：

| 选项 | 判错时的责任方 |
|---|---|
| A | 永远是**人**（机器最高只到「疑似」，转人工） |

**这不是工程能回答的问题。** 代码只能实现「谁负责」；它不能决定「谁应该负责」。
