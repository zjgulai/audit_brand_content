## 2 · ★ 一处**必须先说的偏差**：`signoff` 放在顶层，没有塞进每条样本

任务书给的关键约束是「加 `signoff` 不能改变 `fingerprint`」，理由是
`sample_fingerprint` 只算 `text`。**那个理由对单条指纹成立，对整套指纹不成立。**

| 口径 | 函数 | 算的是什么 | 加 signoff 到 sample 内会变吗 |
|---|---|---|---|
| 单条样本指纹 | `sample_fingerprint`（`verify_regression_set.py:133`） | `sha256(json({"text": ...}))` | **不会**（只吃 text） |
| **整套冻结指纹** | `set_fingerprint`（同文件 `:145`） | `sha256(json(samples))` —— **整个 sample 对象数组** | **会变** |

实测（加签之前，把 signoff 塞进 sample 内试算）：

```
python3 -c "
import json,sys,copy
sys.path.insert(0,'tools')
from verify_regression_set import set_fingerprint, FROZEN_SET_FINGERPRINT
S=json.load(open('research/governance/regression-set-v1.json',encoding='utf-8'))['samples']
S2=copy.deepcopy(S)
for s in S2: s['signoff']={'by':'X','at':'2026-10-26','basis':'y'}
print('冻结常量',FROZEN_SET_FINGERPRINT[:16])
print('塞进样本后',set_fingerprint(S2)[:16])
"
# 实测：冻结常量 538389f39bc4406d
#       塞进样本后 266135786eb11c48   ← 变了
```

于是两条硬性要求会**互相冲突**：

- 要求「GS-CHG-PIN 仍绿」；
- 要求「不许改 `tools/verify_regression_set.py`」（不在允许改动清单里），
  而 `FROZEN_SET_FINGERPRINT` 就写在该文件里。

**采取的解法**：把 `signoff` 做成**顶层按样本 id 索引的映射**，不碰任何 sample 对象。

```json
"signoff": {
  "GS-001": {"by": "法务", "at": "2026-10-26", "basis": "...", "kind_signed": "trap_negative", "attested_by": "..."},
  "...": "共 83 个键"
},
"signoff_meta": { "scope": "...", "待裁定": [ {...GS-011...} ] }
```

**这样做的三个好处，不只是「绕开指纹」**：

1. `samples` 数组**逐字节不变** → 冻结指纹**真的没变**（不是改常量迁就）；
2. 「法务签的那 83 条」与「冻结的那 83 条」是**同一批字节**，
   日后若有人改样本，签的与冻结的会同时是那一份，不会出现「签的是旧版」；
3. 不触碰 `FROZEN_SET_FINGERPRINT`，合法变更程序（改样本才要动常量）保持原样。

**代价（如实记）**：签署不在 sample 对象里，所以**任何只遍历 `samples` 的工具都看不到它**。
这正是为什么必须有 `tools/verify_regression_signoff.py` —— 没有它，
这个字段就是一份谁都读不到的表。

**差异证明**：

```
git diff --stat research/governance/regression-set-v1.json
# 实测：1 file changed, 613 insertions(+)   ← 纯新增，0 删除
```

## 4 · ★ GS-011 怎么处理的，以及需要你确认什么

### 4.1 事实（复述，便于对照）

| 项 | 值 |
|---|---|
| 样本 | `GS-011` `text = "FDA cleared medical device for home use"` |
| 标签 | `expected.kind = "should_hit"`（该拦） |
| 引擎实际 | `catch_all`，**零命中** |
| 规则侧 | `T6.1.regulatory-status` 的 `downgrade_band.keywords` 明文含 `FDA cleared`，`effect = auto_reject → auto_pass` |
| 既有的法务决定 | `$decision`：「**D2 · 法务 2026-09-16：放行**（同现即放行，确认维持原语义）」，依据 21 CFR 807.97 |
| D2 的确认状态 | `disposition-layers-v1.json` 的 `ratification_scope.legal_confirmed` 含 `D2` —— 即**法务已逐条确认过这条决定** |
| 时间关系 | 样本建集 **2026-10-22**，晚于 D2 **36 天** |

### 4.2 我采取的处置：**保守**，维持 `should_hit` + 记录冲突 + 标记待裁定

「全部通过」这四个字**没有说明** GS-011 的期望值该维持还是该改。
两种解读的后果完全不同，而**选哪一种都是替法务做决定** —— 所以不选。

落在盘上的三件事：

1. `GS-011` 的 `expected.kind` **仍是 `should_hit`**（未改一个字节）；
2. 它的 `signoff.basis` 里逐字写着「期望值维持，与 D2 冲突已记录，待单独裁定」；
3. `signoff_meta.待裁定` 里有一条**点名 GS-011** 的记录，含两种解读的后果与「需要谁确认什么」。

**为什么保守的那一侧是安全的**：若法务的真实意思是「改成 `correctly_exempted`」，
盘上现在的状态是**多留了一条待裁定**，改起来是一次有记录的变更；
反过来若我先改了、而法务的意思是「维持」，那就是**擅自改了法务签过字的期望值**，
并且会同时改变冻结指纹、`should_hit` 计数（9→8）与所有引用该计数的断言。
**「签了字但有一条与既有法务决定冲突」比「擅自改样本」安全** —— 这是任务书给的方向，我照做了。

### 4.3 两种解读的后果（写进盘，也写在这里）

| 若法务的意思是 | 要改什么 | 代价 / 风险 |
|---|---|---|
| **维持 `should_hit`** | 什么都不用改（当前状态） | 引擎继续按 D2 放行 `FDA cleared`，**样本永远与引擎不一致**；这条不一致会一直被当成「规则缺口」反复送审 —— 而它其实不是缺口，是样本过时 |
| **改成 `correctly_exempted`** | 改 `expected.kind` → 冻结指纹变 → **同一提交**里更新 `FROZEN_SET_FINGERPRINT` + changelog 条目 + 本执行点的 `PINNED_KIND` + 所有引用 `should_hit` 计数的断言与文档（`verify_regression_governance.py` 的说明、验收表第 85 行相关表述、申请文档 §2.1 的 9/21/49/4 分布） | 改变规则集语义。**引擎不需要改** —— D2 本来就让它放行；但「9 条 should_hit」这个读数会变成 8 条，凡抄过这个数的地方都要重算 |

> **为什么「引擎不需要改」**：`FDA cleared` 今天落 `catch_all` 不是因为规则缺口，
> 是因为它既没命中 `match.keywords`（那里面只有 `FDA approved/certified/认证/批准/通过`），
> 也没有 violation 可供 `downgrade_band` 豁免。若为了让样本变绿而去
> 把 `FDA cleared` 补进 `match.keywords`，它会**先命中再被豁免带拉回 `auto_pass`** ——
> 净效果仍是放行，只是多绕一圈。而那样做会让如实声明 510(k) cleared 的合规表述
> 在**没有豁免带生效的语境下**（例如只出现 `FDA-cleared` 的变体）面临被拦的风险。
> 21 CFR 807.97 禁止的是把 cleared 说成 approved，不是禁止说 cleared。

### 4.4 ★ 需要你确认的（**只有这一条**）

> **GS-011 的期望值：维持 `should_hit`，还是改成 `correctly_exempted`？**

- 选**维持** → 我什么都不用做，但这条不一致要继续挂在盘上（它已有记录，不会丢）；
- 选**改** → 我按 §4.3 右列一次性做完，并同步所有引用 9 条计数的断言与文档。

## 6 · ★ GS-011 当天晚些的改判（原「保守维持」已作废）

> **这一节是后加的。它推翻的不只是 §2 的结论，还包括本文档前半部分引用的两个读数**
> （`should_hit` 9 条 → 8 条；冻结指纹 `538389f3…` → `f3b0f91a…`）。
> 保留前半部分原文不动，是因为「当时为什么选保守」本身是一条该记的判断。

### 6.1 改判成什么

`GS-011` 的 `expected.kind`：`should_hit` → **`correctly_exempted`**。

### 6.2 判据（一句话）

> **逐条裁定 > 整体签署。**

- D2（法务 **2026-09-16**）把 `FDA cleared` 明文列进 `T6.1.regulatory-status` 的
  `downgrade_band.keywords`（`effect = auto_reject → auto_pass`，依据 21 CFR 807.97），
  并且 D2 在 `disposition-layers-v1.json` 的 `ratification_scope.legal_confirmed` 里
  —— 那是**法务逐条确认过**的。
- 本次「83 条全部阅读并签字通过」是**整体签署**。
- 两者冲突时**以逐条裁定为准**。口径已写进
  `regression-set-v1.json` 的 `signoff_meta["★ 整体签署与逐条标签的关系"]`。

### 6.3 一个必须实测的事实：引擎不需要改

```
$ python3 -c "…RuleJudge(text='FDA cleared medical device for home use')…"
[]                                    ← findings 为空
$ python3 -c "…judge_unit(...)…"
label: REVIEW | layer: DP3            ← 放行带已生效
```

也就是说：**引擎一直按法务的意思在放行，错的是样本标签。**
改的是记录，不是行为。

### 6.4 ★ 但这次改判没有修掉真正的缺陷

`downgrade_band` 是**文本级**生效 —— 关键词出现在同段文本任何位置即触发。规则自己的
`$decision` 里就写了这个例子：

> `FDA approved breast pump. FDA cleared.` → `auto_pass`

前半句是违规主张（`auto_reject`），后半句只要出现一句**事实正确**的
`FDA cleared`，**整段被放行**。

这是**独立的引擎缺陷**，不属于本次改判范围（它要改判定主链语义，属于 T-390 那类需要裁定的）。
已记在 `signoff_meta.待裁定` 的 `遗留` 字段里，并由
`verify_regression_signoff.py` 的 S7 断言「已裁定必须写遗留」——
**没写遗留会红**，防止下一个人只看到「标签改好了」。

### 6.6 两条判据自己踩过的坑（记下来，因为都是「判据在撒谎」的形状）

**其一：单条指纹不变，但集合指纹会变。**
任务书原话是「加 `signoff` 不改指纹，因为指纹只算 `text`」。这对**单条**成立
（`sample_fingerprint` 只哈希 `{"text": …}`），对**整套**不成立
（`set_fingerprint` 对整个 sample 对象数组做哈希）。实测把 `signoff` 放进 sample 内部
会让整套指纹从 `538389f3…` 变成 `266135786e…`。所以 `signoff` 做成了**顶层按 id 索引的映射**。

**其二：改判后，那条守着旧值的断言会正确地变红。**
`PINNED_KIND` 本意是「不许悄悄改标签」。改判后它仍守 `should_hit`，
于是**正确状态被判成红**。修法不是删断言，是**把「值」与「有没有人决定过」拆成两件事**：
现在的 S7 同时要求 ① 值等于已裁定值 ② changelog 里有一条提到 GS-011。
只改常量不写理由，照样红。
