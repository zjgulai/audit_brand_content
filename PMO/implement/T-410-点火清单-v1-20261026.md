### 0.1 🔴 P0：按现在的 `Dockerfile` 构建，容器**起不来**

`base/send_gateway.py:47` 有 `from tools.redact import redact`，而
`Dockerfile` 的 runtime 阶段只拷了 `tools/bj_time.py` 一个 Python 文件：


`tools/redact.py` 因此不在镜像里；`api/production_app.py` 在 `import` 期

补上 `tools/redact.py` 之后同一条命令 **rc=0**，装配、`/readyz` 七项、判定链路全部正常。

## 第 2 步 · 目录与权限

### 前置
- 五个宿主机目录已建好（见下表）。
- 容器内以 `audit`（uid 10001）运行（`Dockerfile:99-102`）。

### 六个断言（`ProductionSettings.__post_init__` + `ProductionRuntime.start()`）

| # | 断言 | 在哪一行 | 违反时报什么 |
|---|---|---|---|
| 1 | 路径不在仓库内（`repo == path or repo in path.parents`） | `production_app.py:252` | `<name>_inside_repository` |
| 2 | 七个路径**互不重叠**（相等、或任一是另一个的父目录） | `production_app.py:256-260` | `data_paths_overlap:<左>:<右>` |
| 3 | `frozen_projection_root` 必须**是目录** | `production_app.py:382` | `frozen_projection_missing` |
| 4 | 五个目录必须 `mode & 0o077 == 0`（即 0700 或更紧） | `production_app.py:367-370` | `data_permissions` |
| 5 | `principal_directory` 必须 `ready()`（非空、且每条有 `authz_version`） | `production_app.py:395-396` | `principal_directory_empty` / `principal_field` |
| 6 | writer lease 必须拿到 | `production_app.py:384` | `writer_lease_held` |

被 ④ 检查的五个目录是：`authority_root`、`review_projection_db.parent`、
`session_db.parent`、`access_log_path.parent`、`report_root`。

### 🔴 手工建目录时最容易踩的一条

`mkdir -p` 出来的目录是 **0755**（受 umask 影响）。而 `_ensure_private_dir()` 用的是
`path.mkdir(mode=0o700, exist_ok=True)` —— **目录已存在时 `mode` 不生效**。实测：

```
$ mkdir -m 755 /tmp/x && python3 -c "import os;os.makedirs('/tmp/x',mode=0o700,exist_ok=True)"
exists_ok 之后模式: 0o755
新建时模式: 0o700
```

所以宿主机上必须**显式 chmod**，否则容器起不来（`data_permissions`）。

### 命令

```bash
B=/opt/momcozy-audit-platform

# ① 建目录（一次性）
mkdir -p "$B"/data/{authority,projection,logs,db,reports-root} "$B"/config
# ② 显式收紧（★ 不能靠 mkdir 的默认）
chmod 700 "$B"/data/{authority,projection,logs,db,reports-root}
chmod 600 "$B"/.env.production
chmod 644 "$B"/config/principals.json     # 只读挂载，容器内不需要写

# ③ 核对
stat -f '%Sp %N' "$B"/data/* "$B"/config/principals.json 2>/dev/null \
  || stat -c '%A %n' "$B"/data/* "$B"/config/principals.json

# ④ 归属必须是容器 uid 10001（否则 audit 用户写不进去）
stat -c '%u:%g %n' "$B"/data/* 

# ⑤ 交叉检查：不重叠（就在宿主机上算，不启服务）
.venv/bin/python - <<'PY'
import os
paths = {
 "authority": "/data/authority", "frozen": "/data/projection",
 "projection_db": "/data/db/review.db", "session_db": "/data/db/session.db",
 "access_log": "/data/logs/access.jsonl", "principals": "/data/principals.json",
 "report_root": "/data/reports-root",
}
bad = []
ks = list(paths)
for i, a in enumerate(ks):
    for b in ks[i+1:]:
        pa, pb = paths[a], paths[b]
        if pa == pb or pa.startswith(pb + "/") or pb.startswith(pa + "/"):
            bad.append((a, b))
print("重叠:", bad or "无")
PY
```

### 这一步失败说明什么

| 现象 | 实际含义 |
|---|---|
| 容器 `Restarting`，日志尾 `SettingsError: data_permissions` | 宿主机目录权限不是 0700。**这条断言是故意的**：数据里有案件内容与审计日志。别用 `chmod 777` 绕过 —— 那等于把这个断言删掉 |

| `principal_field: authz_version` | 每条 principal 必须有 `authz_version`（生产装配是 `require_authz_version=True`）。开发夹具里常没有，照抄会卡在这里 |

### 前置

- `AUDIT_WEB_ROOT`：**未设**时默认 `/app/web_dist`（Dockerfile 把前端产物拷到这里）。
  ⚠️ 它**不经 `ProductionSettings`**、直接读 `os.environ`（`production_app.py:1135`），
  所以 `from_env` 的自检**不会**告诉你这个值对不对。

### 命令

```bash
cd /opt/momcozy-audit-platform

docker compose up -d --build
docker compose ps
curl -sS -o /dev/null -w 'healthz=%{http_code}\n' http://172.20.0.1:18000/healthz
curl -sS http://172.20.0.1:18000/readyz | python3 -m json.tool
```

### 期望输出

`docker compose ps` 的 `STATUS` 是 `Up … (healthy)`（healthcheck 打 `/healthz`，`start_period: 40s`，
所以**头 40 秒 `starting` 是正常的**）。

```
healthz=200
{
    "ready": true,
    "checks": {
        "config": true,
        "authority_chain": true,
        "projection_fresh": true,
        "session_db": true,
        "writer_lease": true,
        "data_permissions": true,
        "principal_directory": true
    },
    "error_code": null
}
```

七项各自对应什么（`production_app.py:576-584`）：

| 字段 | 真判据 | 常见 false 原因 |
|---|---|---|
| `config` | `settings is not None` | 永远 true（起不来就根本没这个对象） |
| `authority_chain` | `service.status()` 不抛异常 | 权威目录不可读、manifest 坏了 |
| `projection_fresh` | `status["status"] == "fresh"` | 投影落后于权威；**心跳 30s 一次**，启动瞬间可能短暂 false |
| `session_db` | `session_store.ready()` | session 库文件坏了/不可写 |
| `writer_lease` | `lease.acquired` 且 `assert_owner()` 不抛 | 被另一个进程抢了 |
| `data_permissions` | 四个目录模式 `& 0o077 == 0` | 见第 2 步 ④ |
| `principal_directory` | `directory.ready()` | 见第 2 步 ⑤ |

> ⚠️ `data_permissions` **只查四个目录**，不含 `report_root`。实测把 `report_root` 改成 0755，
> `/readyz` 仍然 `200` + 七项全 true。这不是遗漏而是既有的口径差 ——
> 但排障时要知道：**报告目录的权限问题不会出现在 `/readyz` 里。**

### 这一步失败说明什么

| 现象 | 说明什么 |
|---|---|
| `docker compose ps` 显示 `Restarting`，`curl` 得到 `Connection refused` | **服务在 import 期就死了**，不是业务错。`docker compose logs api \| tail -30` 会看到 `ModuleNotFoundError` 或 `SettingsError`。**这一种不要看 `/readyz`** —— 它没机会响应 |
| `/healthz` 200 但 `/readyz` **503** | 服务起来了、有某几项不满。`curl` 的 body 里 `checks` 会点名是哪一项，`error_code` 给码 |
| `/readyz` 三项 false（`authority_chain`/`projection_fresh`/`session_db`） | 典型是「刚启动、心跳还没跑完」。等 30–60 秒再看；仍 false 才是真问题 |
| `/readyz` 200 但 `curl /api/v1/me` 返回 503 `not_ready` | 不可能同时发生（`runtime.ready` 是 `ready` 的必要条件）。若真见到，说明中间有重启 |

> **实测的退出码语义**（这条对 compose 的 `restart: unless-stopped` 很重要）：
> 四类启动失败（缺 `principals.json` / 空 `principals` / 缺 frozen 目录 / 目录权限不对）
> **全部 `exit code = 3`**，日志尾都是 `ERROR: Application startup failed. Exiting.`。
> 非 0 → compose 会按 `unless-stopped` 反复重启，`docker compose ps` 会显示 `Restarting (3)`，
> **这本身就是一个精确的诊断信号**（3 = 应用层拒绝启动，不是 OOM、不是端口占用）。

## 第 4 步 · SPA 深链接

### 前置
- `AUDIT_WEB_ROOT`（或默认 `/app/web_dist`）**必须是一个存在的目录**。
  实测：目录不存在时 `/{full_path:path}` 路由**根本没注册**，
  于是 `/cases/x` 返回 `404 {"detail": "Not Found"}`（FastAPI 默认 404）。

### 四个必须验的 URL

```bash
H=http://172.20.0.1:18000

for p in /cases/x /queue /cases/x/deep/er /assets/index-SHM8DUNQ.js; do
  printf '%-32s ' "$p"
  curl -sS -o /dev/null -w '%{http_code}  %{content_type}\n' "$H$p"
done

# 深链接返回的必须是 index.html（比对 sha256 而不是「看起来像」）
staged=$(curl -sS "$H/cases/x" | shasum -a 256 | cut -d' ' -f1)
direct=$(shasum -a 256 /app/web_dist/index.html | cut -d' ' -f1)
echo "深链接=$staged"; echo "index =$direct"; [ "$staged" = "$direct" ] && echo SAME || echo DIFF
```

### 期望输出

```
/cases/x                         200  text/html; charset=utf-8
/queue                           200  text/html; charset=utf-8
/cases/x/deep/er                 200  text/html; charset=utf-8
/assets/index-SHM8DUNQ.js        200  text/javascript
深链接=<sha256>
index =<sha256>
SAME
```

### 这一步失败说明什么

| 现象 | 说明什么 |
|---|---|
| `/cases/x` → `404 {"detail":"Not Found"}` | **`AUDIT_WEB_ROOT` 指向的目录不存在**（或 `index.html` 不在那儿）。这是「路由没注册」，不是「路由写错了」 |
| `/cases/x` → 200 但 body 是后端 JSON | 说明 `/{full_path:path}` 被别人先注册了。检查是否有更早的 catch-all |
| `/assets/*.js` → 404 而 `/cases/x` → 200 | `index.html` 在、assets 不在 → **只拷了 index.html，没拷整个 dist** |
| `/assets/*.js` 返回 `text/html` | 目录穿越防护生效了但文件确实不存在，回落到 index。看文件名对不对得上 `dist` 里的 hash |

### 🔴 并且必须验这一条（0.2 的验证命令）

```bash
for p in /review-api/cases /review-api/me /review-api/reports /review-api/notifications; do
  printf '%-28s ' "$p"
  curl -sS -o /dev/null -w '%{http_code}  %{content_type}\n' "$H$p"
done
```

**期望**（前端能工作的前提）：

```
/review-api/cases          401  application/json
```

**实测现在是**：

```
/review-api/cases          200  text/html; charset=utf-8     ← 错
/review-api/me             200  text/html; charset=utf-8     ← 错
/review-api/reports        200  text/html; charset=utf-8     ← 错
/review-api/notifications  200  text/html; charset=utf-8     ← 错
```

判定口径很简单：**这几条必须是 `application/json`，状态码 401 或 200 都行。**
只要出现 `text/html` 就说明它落进了 SPA 回落 = 前端拿 HTML 当 JSON 解析。
唯一例外是 `/review-api/queue`（旧联调别名，返回 401 JSON）—— 它反而是对的。
**这条不一致本身就说明前缀是偶然工作，不是设计。**

## 第 5 步 · 报告静态路由

### 前置
- 有一条已发布的报告。没有就先用第 7 步之外的路径造一条（或等真实结案）。
- 签名相关四条依赖 `REVIEW_REPORT_LINK_SECRET`。

### 命令

```bash
H=http://172.20.0.1:18000
RID=<report_id>
JAR=/tmp/ca.jar

# 未登录
curl -sS -o /dev/null -w 'anon=%{http_code}\n' "$H/static/reports/$RID.md"

# 登录后读无签名链接
curl -sS -c $JAR -b $JAR -o /dev/null "$H/auth/login"   # 走完飞书扫码后
curl -sS -b $JAR -o /dev/null -w 'signed_in=%{http_code}\n' "$H/static/reports/$RID.md"

# 重签
CSRF=$(awk '$6=="csrf"{print $7}' $JAR)
curl -sS -b $JAR -H "Origin: https://ca.luteos.com" -H "X-CSRF-Token: $CSRF" \
     -H 'Idempotency-Key: resign-t410-1' -X POST \
     "$H/api/v1/reports/$RID/resign" | python3 -m json.tool

# 用签名 URL 读
curl -sS -b $JAR -o /dev/null -w 'with_sig=%{http_code}\n' "$H/static/reports/$RID.md?exp=...&sig=..."

# 改一个字符（篡改）
curl -sS -b $JAR -o /dev/null -w 'tampered=%{http_code}\n' "$H/static/reports/$RID.md?exp=...&sig=0..."
```

### 期望输出（全部实测过）

| 场景 | 状态码 | body |
|---|---|---|
| 未登录 | **401** | `{"code":"401","message":"缺少或无效 session",…}` |
| 已登录、无签名链接 | **200** | 报告 markdown 正文 |
| 已登录、带有效签名 | **200** | 同上 |
| 已登录、`sig` 改一个字符 | **403** | `{"code":"403","message":"链接无效",…}` |
| 已登录、`exp` 已过期 | **403** | `{"code":"403","message":"链接已过期，请申请重签",…}` |
| `report_id` 不存在 | **404** | `{"code":"404","message":"报告不存在",…}` |
| 未配签名密钥时 resign | **503** | `{"code":"503","message":"report_link_signing_unavailable: 服务端未配置签名密钥",…}` |

`resign` 成功时的 body（实测）：

```json
{
  "report_id": "rp233d17d146d78177",
  "url": "https://ca.example/static/reports/rp233d17d146d78177.md?exp=1792961645&sig=e7ffce…25a7",
  "exp": 1792961645,
  "ttl": 3600,
  "content_unchanged": true,
  "sha256": "67a04acc39dc82ede828f8e2b0b2a8a9d211c4cd22d5b3a58805dfc661ec9811"
}
```

**`content_unchanged: true` 且 `sha256` 与重签前一致** —— 这是 ADR-0017 的核心断言
（重签只签一条新链接，不动正文一个字节）。

### 这一步失败说明什么

| 现象 | 说明什么 |
|---|---|
| `/static/reports/*.md` 返回 **200 `text/html`** | 路由顺序错了：`/{full_path:path}` 抢先。`production_app.py:1075` 那条注释就是讲这个 |
| 未登录 401 但登录后 **404** | 报告索引里没有这条，或正文文件丢了（见 0.3）。两者**故意不区分**，防止这条路径变成 `report_id` 枚举器 |
| 登录后 **403 `链接无效`** | 三个可能：签名密钥变了（轮换后没配 `_PREV`）、`public_origin` 变了、URL 被截断。**不是**「报告坏了」 |
| `resign` **503** | 没配 `REVIEW_REPORT_LINK_SECRET`。这是设计好的降级，报告读写照常 |
| `resign` **500** | 落到 `raise HTTPException(500, "resign_failed: …")`，看 detail 是 `index_corrupt` 还是别的 |

## 第 6 步 · 重启后数据还在

### 命令

```bash
H=http://172.20.0.1:18000
```

### 期望输出

> ⚠️ `docker compose restart` **不会**重建容器，所以 0.3 那个问题在这一步**看不出来**。

> 那会把 `REVIEW_REPORT_ROOT`（匿名卷）一起丢掉。**这一步先别做**，

### 这一步失败说明什么

| 现象 | 说明什么 |
|---|---|
| 案件数变少 | `authority` 或 `projection` 没挂载/挂错了 → `docker inspect` 看 `Mounts` |

| 报告数变少 | **0.3 那个问题**。看 `docker inspect` 的 `Mounts` 里有没有 `reports-root` |

## 四 · 修法（本文不写代码，只列改哪一行）

### 4.1 `tools/redact.py` 进镜像（P0）

`Dockerfile` runtime 阶段，在 `COPY tools/bj_time.py ./tools/bj_time.py` 旁边加一行（或改成整目录）：

> 从 `api/` + `base/` 的源码里抽出所有 `from tools.X import`，逐个断言

> 必须红。

### 4.2 `/review-api` 前缀（P0）

两条路，二选一：

- **A（推荐，改构建）**：在 `Dockerfile` 的 `npm run build` 前注入
  `ENV VITE_REVIEW_API_BASE=/api/v1`。前端与后端同源同前缀，不需要反代。
  代价：要重建前端。
- **B（改反代）**：入口反代加 `location /review-api/ { proxy_pass http://172.20.0.1:18000/api/v1/; }`。
  代价：反代配置不在本仓库（`find . -iname '*nginx*'` → 空），改了也没有断言守着。

无论选哪条，都要**加一条断言**：`grep -c '/review-api' web/dist/assets/*.js` 必须为 0（选 A），
或「入口反代的配置副本入库 + 对拍」（选 B）。

### 4.3 `REVIEW_REPORT_ROOT` 挂载（P1）

`docker-compose.yml` 加一行（与 `/data/db` 同形状）：

```yaml
      - /opt/momcozy-audit-platform/data/reports-root:/data/reports-root
```

并同步 `Dockerfile` 的 `mkdir -p /data/…`（第 100 行，现在没有 `reports-root`）。

所以同样需要新断言：**`.env.production.example` 里每个 `REVIEW_*` 路径键，
必须被 compose 的某个 volume 覆盖**。

### 4.4 `reports-root` 进 `/readyz`（建议，非阻塞）

`data_permissions` 现在只查四个目录。加上 `report_root` 会让「报告目录权限不对」
在 `/readyz` 可见。**但这是口径变更**，会改掉现有 82 项里至少一条的语义（需先看 C31）。
至少要在注释里写明「`report_root` 不在 `/readyz` 覆盖范围内」，否则排障的人会以为它在。
