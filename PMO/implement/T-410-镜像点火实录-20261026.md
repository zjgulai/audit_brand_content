## 一 · Docker daemon：本机这条路不通，走了仓库外的既定替代

这一节不是主线，但必须记 —— 否则下一个人会以为是镜像的问题。

### 1.1 `colima start` 起不来（环境问题，非本仓库缺陷）

```bash
$ docker info --format '{{.ServerVersion}}'
Cannot connect to the Docker daemon at unix:///Users/lute/Project/Knowledge/.limacache/docker.sock. Is the docker daemon running?

$ colima status
level=fatal msg="colima is not running"
```

按委托方的说明在后台起了 `colima start`，等了 3 分钟以上仍失败。日志尾：

```
level=info msg="starting ..." context=vm
level=info msg="Using the existing instance `colima`"
level=fatal msg="failed to start usernet `user-v2`: cannot find executable path"
level=fatal msg="error starting vm: error at 'starting': exit status 1"
```

`cannot find executable path` = 本机 `os.Executable()` 被外部执行层干预，而 colima 的
usernet 启动路径必须 re-exec 自身。**这与本仓库无关**，是这台机器的既有约束。

### 1.2 改用仓库外已文档化的替代路径

`/Users/lute/Project/Knowledge/start-env.sh` 的注释里写着同一件事，并给了替代方案：
Lima VM + SSH 把 VM 内的 `docker.sock` 桥到宿主。

```bash
$ cd /Users/lute/Project/Knowledge && ./start-env.sh
...
错误: docker 桥建立失败
```

VM 起来了，但里面的 docker daemon 没起来。真因（`journalctl -u docker.service`）：

```
failed to load listeners: listen tcp 172.17.0.1:2375: bind: cannot assign requested address
```

`/etc/systemd/system/docker.service.d/10-fastgpt-tcp.conf` 要求 bind `172.17.0.1:2375`，
而 `docker0` 网桥不存在 —— **dockerd 起不来所以 docker0 建不出来，docker0 不存在所以 dockerd 起不来**。
先手工补网桥再起 daemon：

```bash
sudo ip link add docker0 type bridge
sudo ip addr add 172.17.0.1/16 dev docker0
sudo ip link set docker0 up
sudo systemctl start docker
$ docker info --format '{{.ServerVersion}} {{.Driver}}'
29.9.2 overlayfs
```

### 1.3 dockerd 不读 shell 的代理环境变量（这类坑值得单独记一条）

第一次真构建失败的报错**看起来像网络不通**：

```
failed to resolve reference "docker.io/library/node:22-bookworm-slim":
dial tcp 128.242.240.85:443: i/o timeout
```

而同一台 VM 里 `curl https://registry-1.docker.io/v2/` → **401（1.55s，正常响应）**。
差别在于：**shell 有 `http_proxy`，dockerd 没有** —— 它是 systemd 服务，不继承登录 shell 的 env。
给 service 加 drop-in 后镜像拉取正常。

> 判据顺序值得记住：**先分清是哪一类**。
> `curl` 通而 `docker pull` 不通 → 不是网络，是**代理没配到 daemon 上**。
> 这与「缺文件」的报错完全不像，不会混。

### 1.4 本机没有 buildx（只影响 `--progress` 这个开关）

宿主 docker CLI 29.8.1 没有 `cli-plugins/`，`docker build --progress=plain` 直接
`unknown flag: --progress`（退 125）。VM 里有 buildx，所以**最终构建走的是 buildx**：

```bash
$ (VM 内) docker compose version
Docker Compose version v5.6.1
```

## 二 · `docker compose config`

### 2.1 现状：失败，且失败信息精确

```bash
$ cd /Users/lute/Project/audit_multi_content
$ docker compose config
env file /opt/momcozy-audit-platform/.env.production not found:
stat /opt/momcozy-audit-platform/.env.production: no such file or directory
$ echo $?
1
```

### 2.2 它要什么、谁能满足它

`docker-compose.yml:40-41`：

```yaml
    env_file:
      - /opt/momcozy-audit-platform/.env.production
```

**这个绝对路径是有意的，不是笔误。** compose 文件第 35-39 行的注释写明了原因：
相对路径意味着「部署时得把 `.env.production` 复制进 repo/ 才能跑」，
那让凭据落进了 git 工作区 —— 虽然被 `.gitignore` 挡住，但「靠 ignore 保护」不是保护。

**但有一个 compose 的语义差要记下来**，它是这件事唯一的技术要点：

| 谁读 `env_file` | 影响 |
|---|---|
| **compose 客户端**（不是 daemon） | 该路径必须在**跑 compose 的那台机器**上存在且**可读** |
| 它不做的事 | 它**不**去 daemon 所在机器找这个文件 |

所以「把文件放到目标服务器 `/opt/...`」还不够 —— **跑 compose 的那个用户必须读得到它**。
本次实测撞到这一点：

```bash
$ (VM 内) docker compose config
open /opt/momcozy-audit-platform/.env.production: permission denied
```

因为该文件由 root 建、模式 `600`，而 compose 由 `lute` 跑。改成 `501:1000` + `0600` 后：

```bash
$ (VM 内) docker compose config
name: momcozy-audit
services:
  api:
    restart: unless-stopped
    container_name: momcozy-audit-api
$ echo $?
0
```

### 2.3 结论

**`docker compose config` 能通过，前提是那份 env 文件存在、模式 600、且属主是「跑 compose 的人」。**

- 需要哪个 env 文件：`/opt/momcozy-audit-platform/.env.production`
- 在哪：**目标服务器**（本机没有 `/opt`，实测 `touch /opt/.probe_write` → `Permission denied`）
- 上线时**谁来建**：部署 owner（T-323）。见 §七 第 1、2 条。
- **这不是可移植性缺陷**：绝对路径是为「凭据不进 git 工作区」付的代价，且 compose 注释里写明了。
  真要改也应该改「文件属主」，而不是把路径改回仓库内。

> ★ 本机想在没有 `/opt` 的情况下过静态校验，可以 `docker compose config --no-env-resolution`
> （实测 rc=0）。**但那只证明 YAML 语法对，不证明 env 齐全** —— 别拿它当通过。

### 4.3 ★ `/readyz` 的逐字 body

```json
{"ready":true,"checks":{"config":true,"authority_chain":true,"projection_fresh":true,"session_db":true,"writer_lease":true,"data_permissions":true,"principal_directory":true},"error_code":null}
```

`status=200`，`content_type=application/json`。**七项全 true，`error_code: null`。**

> 踩过一个假读数必须记：第一次 curl 得到 **502 且 body 为空**，看着像服务挂了。
> 真因是**我 shell 里的 `http_proxy=http://192.168.5.2:7890` 劫持了 loopback 请求**
> （`curl -v` 显示 `Connected to 192.168.5.2 port 7890` → `Operation timed out`）。
> `unset http_proxy https_proxy` 之后立刻 200。
> **「curl 回到 502」不等于「应用坏了」** —— 先看 `curl -v` 连的是谁。

**第 4 条是本票点名要验的那条**：`/api/v1/me` 未登录拿到 **401 JSON**，

```

index.html  sha256 = 73e6b6a8dab7516ae05e2e55e24dc7dcfa6221a04e9547561dc946a84b38a7b0
```

**第 5 条要分开看**：报告端点**注册在 SPA 兜底之前**，所以它赢了 ——
未登录 401 JSON、已登录 200 markdown。这是正确的注册顺序。

```
                                path=reports/rp2c095fe06d1ef9f3.md
```

### 5.1 `docker compose restart`（不重建容器）

| 项 | 重启前 | 重启后 |
|---|---|---|
| `/readyz` | 200, 七项全 true | **200, 七项全 true** |
| cases | n=1 `case-2c2a1a499dead653b86f` | **n=1 同一条** |
| `/api/v1/me`（带 session） | 200 `reviewer` / `on_t410probe` | **200 同一身份** |

**全部存活。** 这台机器上 `authority` / `projection` / `db` / `logs` 都是 bind mount，
所以 restart 不动数据 —— 与预期一致。

### 5.2 `docker compose down && docker compose up -d`（重建容器）

| 项 | down/up 前 | down/up 后 | 判定 |
|---|---|---|---|
| cases | n=1 | **n=1** | ✅ bind mount 生效 |
| authority 落盘 | 4 个 `cmd-*.json` | **4 个**（宿主机可见） | ✅ |
| `/readyz` | 七项全 true | **七项全 true** | ✅ |
| 报告**列表** | 1 条 `rp2c095fe06d1ef9f3` | **1 条仍在** | ⚠️ 见下 |
| 报告**正文** | 200 `text/markdown` | **🔴 404 `{"code":"404","message":"报告不存在"}`** | 🔴 |

### 5.3 ★ P1 实测结论：比清单里写的更糟

清单 §0.3 写的是「报告在 `compose down` 后**静默消失**」。
**实测不是「消失」，是「列表有、正文没有」** —— 这更难发现：

```
GET /api/v1/reports
→ 200 [{"report_id":"rp2c095fe06d1ef9f3","case_id":"case-2c2a1a499dead653b86f",
        "ir_id":"ir-3feb88a678f90e32","url":"https://ca.luteos.com/static/reports/rp2c095fe06d1ef9f3.md",
        "published_at":"2026-10-26T04:53:10Z"}]        ← 列表里有
GET /static/reports/rp2c095fe06d1ef9f3.md
→ 404 {"code":"404","message":"报告不存在"}              ← 正文没有
GET /readyz
→ 200 七项全 true                                       ← 没有任何东西会红
```

原因是**元数据与正文分两处存**：报告索引（`ir_id`、`published_at`）在 authority 里（走 bind mount，活下来），
正文与 `index.jsonl` 在 `report_root` 里（落在匿名卷，被丢掉）。
所以用户看到的不是「报告列表空了」，而是**「点进去说报告不存在」** —— 一个数据一致性问题。

### 5.4 机制：为什么 `reports-root` 会丢

三个证据逐条列出。

**① compose 的 5 个 volume 里没有它**（`docker-compose.yml:43-52`，逐行只有
`authority` / `projection` / `logs` / `principals.json` / `db`）。

**② 它落在 `Dockerfile` 的 `VOLUME ["/data"]` 之内 —— 而那是匿名卷**：

```bash
$ docker inspect momcozy-audit-api --format '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
volume /var/lib/docker/volumes/7531ba95…/_data -> /data        ← 匿名卷，覆盖整个 /data
bind /opt/momcozy-audit-platform/data/authority -> /data/authority
bind /opt/momcozy-audit-platform/data/db -> /data/db
bind /opt/momcozy-audit-platform/data/logs -> /data/logs
bind /opt/momcozy-audit-platform/config/principals.json -> /data/principals.json
bind /opt/momcozy-audit-platform/data/projection -> /data/projection
```

`/data/reports-root` **没有任何 bind 覆盖**，于是它落在那个匿名卷里。

**③ 匿名卷每次重建都换一个**，实测 id 变化：

```
重启前 /data 卷名：7531ba95a9e8ea94d0928076e4352fb77328fa97e783491df0cdaef0616d0efd
down/up 后：      3ad62138986dc5db6726486382eb26a9f5c5eac65da0d1ee10b56f1c3983ce58
（中间一次 restart 不变 —— 因为 restart 不重建容器）
```

**④ 宿主机上从来没有这个目录**（这是给上线的人看的判据）：

```bash
$ ls -d /opt/momcozy-audit-platform/data/reports-root
ls: cannot access '/opt/momcozy-audit-platform/data/reports-root': No such file or directory
$ ls /opt/momcozy-audit-platform/data/
authority  db  logs  projection          ← 没有 reports-root
```

### 5.5 为什么没人发现（这条比缺陷本身更值得记）

`/readyz` 的 `data_permissions` 只遍历**四个**目录（`production_app.py:555-560`）：

```python
for directory in (
    self.settings.authority_root,
    self.settings.review_projection_db.parent,
    self.settings.session_db.parent,
    self.settings.access_log_path.parent,
):
```

**不含 `report_root`**。所以「报告目录丢了 / 权限松了」这件事在 `/readyz` 里**完全不可见** ——
实测七项全 true 与报告 404 同时成立。

### 5.6 本次**不修**（按要求只取证）

修法是 `docker-compose.yml` 加一行 + `Dockerfile:117` 的 `mkdir` 补一个目录，两条都在 §七。
但改它会改变挂载拓扑，而本次任务只要求证明「能构建、能起来」+ 证实 P1。
**证据已齐，修法留给部署 owner，见 §七 第 3 条。**
