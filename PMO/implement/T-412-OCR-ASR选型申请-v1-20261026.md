## 一 · 现状：宿主 Vision 到底绑了什么

### 1.1 三样东西，各自的边界

| 文件 | 规模 | 作用 | 跨平台？ |
|---|---|---|---|
| `base/ocr_vision.m` | **114 行 / 5,057 字节** | OCR 主体的 ObjC 源码 | ❌ 依赖 `Vision.framework` `AppKit.framework` |
| `base/build_ocr.sh` | **36 行 / 1,551 字节** | 用 `clang` 编译出二进制 | ❌ 只认 `/Library/Developer/CommandLineTools/SDKs/MacOSX*.sdk` |
| `.tools/bin/ocr` | **53,584 字节** | 编好的 CLI（一次一进程 + `--serve` 常驻） | ❌ Mach-O **arm64**，动态链 macOS 系统框架 |

**`otool -L` 这一行是本文最硬的读数**：它不是「源码里 import 了什么」，是**这个二进制在运行时真的会去加载哪些库**。
`/System/Library/Frameworks/Vision.framework` 意味着：**换一台 Linux 机器，这个二进制连启动都做不到。**

### 1.2 三道绑定，一层比一层硬

| 层 | 绑定 | 换平台时的表现 |
|---|---|---|
| **编译期** | `build_ocr.sh` 写死 `-isysroot /Library/Developer/CommandLineTools/SDKs/$s.sdk`，且按 `MacOSX15.4 → 26.5 → 15 → 26 → MacOSX.sdk` 顺序试 | Linux 上没有这个目录 → **一个 SDK 都找不到** → 退 1 |
| **链接期** | `-framework Foundation -framework Vision -framework AppKit` | Linux 上无这三个 framework |
| **运行期** | `otool -L` 显示动态依赖 `Vision.framework` | 即使强行拷过去，**dyld 加载失败** |

本机实测的 SDK 列表（说明它不是「理论上绑」，而是**真的在按本机 SDK 路径找**）：

```bash
$ ls -d /Library/Developer/CommandLineTools/SDKs/*.sdk
MacOSX15.4.sdk  MacOSX26.5.sdk  MacOSX27.0.sdk  MacOSX.sdk -> MacOSX26.5.sdk
```

而 `build_ocr.sh` 的注释自己记了一件事：本机默认 SDK（`MacOSX27.0`）是**坏的**（`tapi error: malformed file ... unknown architecture arm64e.x1-macos`），所以脚本按顺序试几个 SDK 而不是写死一个。
→ **连 macOS 内部都已经是「试出来的」**，跨平台只会更脆。
