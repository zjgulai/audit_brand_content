## 二 · 为什么**不**改造 `verify_media_portability.py`

题面允许二选一。我选了**新建**，理由三条，第一条是判据层面的：

### 2.1 两者失败后要查的地方不同

| 红在哪 | 该去改什么 |
|---|---|
| `verify_media_portability` | `base/ocr_vision.m`（删/换宿主实现）、`SUPPORTED_SOURCE_KINDS`（进件） |
| `verify_media_selection` | ADR-0018 的表格、或 `MEDIA_PROVIDERS` 的某一行 |

合成一个退出码，红了之后第一件事是「先分辨是哪一类」——而两类之间**没有任何重叠**。
这与 `verify_secret_patterns` 不并进 DG 是同一条理由（AGENTS.md §2.1）：
**失败后要查的东西不同，就不能共用一个退出码。**

### 2.2 此刻最不该动的就是它

`verify_media_portability.py` 现在的读数是 `rc=0 · 3 命中 · vacuous_true`。
它的状态语义（`vacuous_true` / `must_fix` / `clean`）被 `--controls` 的 9 项
逐一钉住，也被 `PMO/audit/裁定-R118-媒体宿主原生-20261023.md` 引用为现场读数。
**在一个「空真」的读数上扩语义**，会让 10-23 那份裁定的引用失效 ——
而那份裁定的价值正是「当时读到的是这个」。

### 2.3 复用而不复制：`native_hits()` 直接调它

`verify_media_selection.py` 的 S7 需要「宿主原生命中数」。它**不复制扫描器**：

```python
sys.path.insert(0, str(ROOT / "tools"))
import verify_media_portability as P
return P.scan(P.collect())
```

两个分母各自漂移是本项目记过的病（`AGENTS.md` §2.4.8「同一个量有两个口径」）。
所以：**建新文件，但拿旧文件的读数**。

## 四 · 媒体进件今天不开，T-412 阻塞上线吗

**不阻塞。** 依据四条。

### 4.1 上线最小集里没有媒体

`PMO/implement/最终上线差距分析-v1-20261026.md` §五「上线准绪判断」是一张维度表：
核心写链 / 生产判定 / 部署 / 前端 / 待裁定。**OCR/ASR 不在任何一格里。**
它在 §2.1 差距表里挂着（GA-03 / GA-04），但结论段只点名
`T-323` + `T-320` + `T-321` + `T-401/402/403`。

`PMO/implement/T400段-ready收尾报告-20261026.md` §四 对 T-412 的
「拿不到会怎样」写的是「**媒体进件尚未打开**」——
即影响面是「P2 停在设计态」，不是「上线不能发生」。

### 4.2 进件在代码里真的是关的

```bash
$ grep -n "SUPPORTED_SOURCE_KINDS" base/submission_service.py
33:SUPPORTED_SOURCE_KINDS = frozenset({"free_text", "ad_text"})
```

`source.kind=image` 被 `unsupported_source_kind` 拒；`api/` 的 import 闭包不含
`base/media.py`。**所以即使本票一行没写，上线也不会因媒体受阻。**

### 4.3 本票引入的上线面风险为零（逐项）

| 风险 | 本票 | 结论 |
|---|---|---|
| 生产行为 | 未改 `ocr_file()` 路径 | 无变化 |
| 依赖 | 未改 `pyproject.toml` / `Dockerfile` / `uv.lock` | 无变化 |
| 仓体积 | `.onnx/.pt/.bin/.safetensors` tracked = **0** | 无变化 |
| 判定主链 | 未触碰 `api/` / `skeleton/` / `base/rule_judge.py` | 无变化 |
| 默认引擎 | 仍 `host_vision`（S6 断言） | 无变化 |

### 4.4 什么时候它**会**变成阻塞

T-412 本身永远不阻塞。**但「打开媒体进件」会立刻阻塞上线** —— 因为那一刻：

1. `SUPPORTED_SOURCE_KINDS` 加 `image` → 行 118 从空真翻成**真违规**
   （`verify_media_portability` 的 G2 退 1）；
2. 生产调 `ocr_file()` → `ensure_ocr()` → 在没有 macOS + CLT SDK 的容器里
   **直接抛异常**（`base/media.py:116` 的 `ensure_ocr` 只认本机 SDK 路径）。

正确顺序：**`T-118-follow` 先让 ADR §六.2 的四件事全部成立，再把 `image` 加进集合。**
反过来做，第 1 天就会在容器里得到 `ocr_build_failed`。

## 七 · 一条必须报告的事实：申请文档有一句过期了

`PMO/implement/T-412-OCR-ASR选型申请-v1-20261026.md` §2.4 写：

> 「docker 客户端在（`docker`/`colima`/`lima` 都有），**daemon 没起**。
> 所以「在 Linux 容器里跑一遍」这件事今天做不了」

**本次实测 daemon 可达**：

```bash
$ docker info >/dev/null 2>&1; echo "rc=$?"
rc=0
$ docker version --format '{{.Server.Os}}/{{.Server.Arch}}'
linux/arm64
```

于是「宿主二进制在容器里起不来」第一次有了**直接读数**（而不是靠 `otool -L` 推论）：

```bash
$ docker run --rm -i python:3.12-slim python3 -c '
import os,sys
d=sys.stdin.buffer.read(); open("/tmp/ocr","wb").write(d); os.chmod("/tmp/ocr",0o755)
print("magic=%s" % d[:4].hex())
try: os.execv("/tmp/ocr",["/tmp/ocr"])
except OSError as e: print("execv errno=%d %s" % (e.errno, os.strerror(e.errno)))
' < .tools/bin/ocr
magic=cffaedfe                       # Mach-O 64 魔数；容器只认 ELF
execv errno=8 Exec format error
```

**但「待测」这个状态没变** —— 卡点从 daemon 挪到了**素材**
（视频 0 / 音频 0、无人工标注真值）。这两件事必须分开说，
否则「等选型」会变成一个等不到的话。

> ★ 容器里还有一条实测值得记：`ldconfig -p | grep -c "libGL\.so"` → **0**。
> `python:3.12-slim` 没有 `libGL`，所以非 headless 的 `opencv-python` 会 import 失败。
> 这是选 `rapidocr`（依赖 `opencv-python-headless`）而不是
> `rapidocr-onnxruntime`（依赖 `opencv-python`）的一个**硬理由**，不是偏好。

## 八 · 给下一张票（T-118-follow）的交接

按顺序做，每步都有可核读数：

| # | 做什么 | 验收读数 |
|---|---|---|
| 1 | 备素材：真实中英文广告图（低清 + 旋转子集）、**视频、音频** | 视频/音频从 0 变 ≥1（`git ls-files` 口径，或声明的仓外目录） |
| 2 | 容器内装 `rapidocr==3.10.0` | `ContainerOcrProvider().probe()["ready"] == True` |
| 3 | 容器内真跑一张图 | `analyze()` 返回 `ok=True` 且 `lines` 非空 |
| 4 | **坐标系对拍**：同图两边跑，逐框比 y 重心 | 见 ADR §3.2 —— 翻错不报错，只能这样测 |
| 5 | 四项/五项读数存盘（TS-18/19） | `verify_media_model_lock.py` 的 M3 才有对象 |
| 6 | 改 `DEFAULT_OCR_ENGINE` → 容器引擎 | `verify_media_selection.py` 的 **S6 会红**，需同步改 S6 与 ADR（这是刻意的：接线必须是一次显式决策） |
| 7 | 移除宿主实现（`ocr_vision.m` / `build_ocr.sh`） | 宿主原生命中 3 → 0；此时 S7 也要同步改（**它当前挡的是「悄悄删」**） |
| 8 | `SUPPORTED_SOURCE_KINDS` 加 `image` | `verify_media_portability.py` 的 G2 从绿转红 → 说明它开始有对象了 |

★ **第 6/7/8 步都会让本票的断言变红，这是设计。** 那三步是「真接线」，
必须由人来改断言 —— 让「接线」这个动作**不可能悄悄发生**，正是 S6/S7 的全部意义。
