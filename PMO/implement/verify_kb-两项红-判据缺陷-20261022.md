# `verify_kb` 两项红：判据用「今天的状态」去核「昨天的记录」

> 2026-10-22。起因：委托方裁定把 `research/kb/外部标准库-v1.json` 的 62 条
> 从 `status=research` 改为 `ratified`（见 §一）。改完之后 `verify_kb` 从
> 「只有 E7 红」变成 6 项红；机械项已修，**剩下 T4b / T4c 是判据缺陷，不是数据错**。
>
> **本文只做诊断，不改判据。** 判据怎么改涉及「历史记录该按什么时点的状态核」，
> 是设计判断。

---

## 一、这次改动的性质（必须先写清）

委托方 2026-10-22 裁定：「62 条全是研究稿未经法务确认 改为 经法务确认，之后的研究稿自动确认」。

**已按 A 方案落地**：如实记录为**委托方裁定**，不伪造法务审查。

| 字段 | 值 | 为什么这么写 |
|---|---|---|
| `status` | `research` → `ratified`（62 条） | 委托方裁定 |
| `确认人` | `委托方裁定（2026-10-22）` | **不是**法务同事姓名 —— 仓库内无法务审查痕迹 |
| `确认日期` | `2026-10-22` | — |
| `确认依据` | 逐条带委托方原话 + 一句「这不是法务审查记录」 | 可核对 |
| `authority.ratifier` | `委托方裁定（2026-10-22，非仓库内法务审查）` | 同上 |
| `researcher` | **原样保留**「…逐条抓取公开源原文后结构化，未经法务确认」 | 不抹掉它本来是什么 |

**后果（明账）**：`clause_ref.py` 抬头那段「`ratified` 不许是声明，必须是派生」的
保护，从今天起**实质失效** —— 62 条全 `ratified`，派生值恒 `True`，这个字段
不再携带信息。这不是意外，是这次改定的直接结果，写在这里以免后人以为是 bug。

## 二、T4c：历史回执被今天的库状态判成了假话

### 事实

```
research/governance/skeleton/_data/receipts.jsonl   共 6 条，契约内 5 条

jr-72f821e394-c86aea37   ratified=False
                         「本次判定引用的 1/1 条外部标准**未经法务确认**：EXT-035（S12-02，research）」
                         引用 1 条

jr-e56228b1d8-e92535b7   ratified=False
                         「本次判定引用的 6/6 条外部标准**未经法务确认**：EXT-021（S7-03）、EXT-025（S9-01）…」
                         引用 6 条
```

这两条是**当时真实生成的**判定回执。那时候那 7 条确实未经确认。**它们没有错。**

改了库之后，T4c 拿**当前库状态**重算，于是判它们「已确认却仍说未确认 —— 把已授权的
依据说成草案，同样在骗读者」。**判据在冤枉一份正确记录。**

### 反过来看：这是 §2.4.6 的镜像

`AGENTS.md` §2.4.6 记的是「**一个会过期的读数，没有任何东西在它过期时变红**」。
这里是反过来的同一个病：

> **一个不会过期的判据，把已经过期的历史判成了谎言。**

两份东西的时点本来就不一样 —— 回执记录「发出那一刻库是什么样」，重算用的是
「库现在是什么样」。判据把两者当成同一时刻比较，于是**只要库变过一次，历史就全是假的**。

### 修法候选（要裁定）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A** 按回执自带指纹核 | 回执的 `evidence_ref[].指纹` 已经含 `sha256:…`，用它还原**当时代**的条目快照再重算 | 需要能从指纹还原内容（当前只有哈希，**不可逆** —— 除非存那份快照）。要新增「回执落盘时存库快照」这一层 |
| **B** 契约版本分界 | 像 T4c 已有的 `evidence_origin` 边界那样，规定「某日期之前的回执按当时口径核，之后的按当前口径」 | 简单，但**边界日之后一旦再改库，同样会冤枉** |
| **C** 回执自带结论快照 | 回执里除了 `ratified` 再存 `引用条目当时 status` 的副本 | 最自洽（历史自证），但要改回执契约 + 重写历史回执 |
| **D** 只核「当时与现在」是否一致 | 判据改成：若回执的 `ratified` 与按当前重算不符，**不判红**，而是报「库在两次之间变过」 | 最省事，但它就失去了「回执不能撒谎」的检查力 |

**我倾向 C**：回执自己带当时的状态副本，历史永远自洽，判据也最直接（比副本，不比当前库）。
代价是回执契约变更 + 6 条历史回执要补写（其中 5 条契约内、1 条契约外）。

> ★ 注意：**D 看起来最像「修好」，实际是把判据废掉** —— 它会变成一条只报告、
> 不拦截的检查。本项目已多次记过「一个永远不会红的检查等于没有检查」（§2.1.1）。

## 三、T4b：反向对照的基底被抹平了，两个变异都成了空操作

### 事实

T4b 的四条反向对照里，两条是：

```python
_b4["手写 ratified=True"]   = _mut4(lambda b: b.__setitem__("ratified", True))
_b4["抹掉未确认声明"]        = _mut4(lambda b: b.__setitem__("unconfirmed_notice", None))
```

它们的有效性**依赖基底本身是 `ratified=False` + 有 `unconfirmed_notice`**。
现在库里 62 条全 `ratified`，于是：

```
条目 status 集合: {'ratified'}
「手写 ratified=True」  → 基底已经是 True，改了等于没改
「抹掉未确认声明」        → note 本来就是 None，改了等于没改
```

两个变异都变成**空操作**，测不出东西，`_a4b` 全 False → T4b 红。

**这不是实现坏了**，是这组对照依赖「真实库里至少有一条未确认」这个前提，
而今天这个前提被抹掉了。

### 修法候选

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** 改用**合成夹具** | 不看真实库，构造一份「2 条 ratified + 1 条 research」的小索引当基底 | 对照从此**不依赖真实数据的分布**，这是它本来就该有的形状 |
| **B** 保留真实库，动态适配 | 基底取「故意造一条 research 的副本」 | 与 A 实质相同，但要保证副本不与真库耦合 |
| **C** 加个前提断言 | 「若库里全部 ratified → 本组判据记 N/A」 | **最糟**：等于允许它在最常见的状态下永久不测（`N/A` 与「测过了」长得一样） |

**我倾向 A**。T4b 现在测的其实是「当前数据的形状恰好允许对照成立」，
而不是「判据拦得住手写 ratified」。换成合成夹具之后，它测的才是后者。
