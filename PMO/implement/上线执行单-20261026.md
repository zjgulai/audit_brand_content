## 二 · 禁区（违反其中任何一条，本次上线作废重来）

1. **不许 `docker compose down -v`**。`-v` 会删卷。当前 `/data` 是匿名卷（见 §S3），
   未来 `report_root` 变成 bind 之后仍然不该用它。要停就 `stop`，要重建就 `down && up`。
2. **不许 `docker image prune` / `docker system prune`**。回滚全靠上一版镜像还在本地
   （回滚方案 §3）。镜像删了就没有回滚点。
3. **不许 `kill` / `pkill` 守护进程式的做法**。停容器只用 compose。
4. **不许把 `.env.production` 复制进仓库目录**。compose 的 `env_file` 写的是绝对路径
   `/opt/momcozy-audit-platform/.env.production`（`docker-compose.yml:40-41`），
   这个绝对路径是**有意**的：相对路径会让凭据落进 git 工作区。
5. **不许改 `docker-compose.yml` 的端口行**（`172.20.0.1:18000:8000`）。
   改成 `0.0.0.0` 等于绕过反代直接暴露公网；改成 `127.0.0.1` 会让容器里的反代连不上
   （`docker-compose.yml:22-31` 的注释解释了这两条）。
6. **不许在目标机上创建 `compose.override.yml`**。compose 会自动加载同目录下的
   `compose.override.yml`，而 `docker compose config` 的判据（§S2）读的是合并后的结果 ——
   一个残留的 override 会让「我看到的配置」和「它实际用的配置」不是一回事。

## 四 · S1 · 建数据目录并收紧权限

**谁**：R1
**前置**：S0 全绿。

### 为什么这一步不能靠 `mkdir -p` 的默认值

`mkdir -p` 出来的目录是 **0755**（受 umask 影响），而应用要求 `mode & 0o077 == 0`。
容器启动时会调 `_ensure_private_dir()`（`api/production_app.py:365-370`）：
它先 `mkdir(mode=0o700, exist_ok=True)`，**目录已存在时 `mode` 参数不生效**，然后读回真实模式，
`& 0o077 != 0` 就抛 `SettingsError("data_permissions")`。

实测（本文写作时，在仓内）：

```bash
.venv/bin/python -c "
import os, tempfile, pathlib
from api.production_app import ProductionRuntime, SettingsError
p = pathlib.Path(tempfile.mkdtemp())/'reports-root'; p.mkdir(); os.chmod(p, 0o755)
try: ProductionRuntime._ensure_private_dir(p)
except SettingsError as e: print('0755 →', e)
p.chmod(0o700); ProductionRuntime._ensure_private_dir(p); print('0700 → 通过')
"
```

```
0755 → data_permissions
0700 → 通过
```

**所以宿主机上必须显式 `chmod`。**

### 命令

```bash
. "$B/state/release.env"
mkdir -p "$B"/data/{authority,projection,logs,db,reports-root} "$B"/config
chmod 700 "$B"/data/authority "$B"/data/projection "$B"/data/logs "$B"/data/db "$B"/data/reports-root
$SUDO chown -R 10001:10001 "$B"/data
# principals.json 由 R2 在 S2 写；这里先建空文件占位，避免 bind mount 造出一个目录
: > "$B"/config/principals.json
chmod 644 "$B"/config/principals.json
```

### 逐字段核对

```bash
$SUDO stat -c '%a %u:%g %n' "$B"/data/* "$B"/config/principals.json
```

期望（**六行，按 glob 的字母序**）：

```
700 10001:10001 /opt/momcozy-audit-platform/data/authority
700 10001:10001 /opt/momcozy-audit-platform/data/db
700 10001:10001 /opt/momcozy-audit-platform/data/logs
700 10001:10001 /opt/momcozy-audit-platform/data/projection
700 10001:10001 /opt/momcozy-audit-platform/data/reports-root
644 <你的 uid>:<你的 gid> /opt/momcozy-audit-platform/config/principals.json
```

**判据只有两条**：

1. 前五行**必须**是 `700` 且属主 `10001:10001`（容器内 uid 10001 要写它们）。
2. 最后一行**必须**是 `644`，**属主是谁都行** —— 它只读挂载进容器
   （`docker-compose.yml:50` 的 `:ro`），容器内 uid 10001 靠 `644` 的「其他」位读它。
   写成 `600` 会让容器读不到 → `principal_directory_empty`；写成 `700`/目录同样不行。

### 失败时

| 现象 | 说明什么 |
|---|---|
| 某个目录 `755` 或 `775` | 上面的 `chmod` 漏了某个。容器起来后会以 `exit code 3` 反复重启，日志尾 `SettingsError: data_permissions` |
| 某个目录属主不是 `10001:10001` | 容器内以 uid 10001 跑（`Dockerfile:116`），写不进去。表现是启动时报 `data_permissions` 或写文件 `Permission denied` |
| `chown` 报 `Operation not permitted` | 你不是 root 且不是该文件属主。用 `$SUDO` |
| `stat` 报 `No such file` | `mkdir` 那行被改过或 `$B` 为空。`echo $B` 先看清楚 |

## 五 · S2 · 写 `.env.production`（**属主坑在这一步**）

**谁**：R2 提供值，R1 落盘并核对。
**前置**：S1 绿；R2 已从飞书开放平台拿到 `client_id` / `client_secret` / `tenant_key`。

### 坑的形状（实测，必须读懂再动手）

`env_file` 是**compose 客户端**读的，不是 daemon 读的。所以：

> **跑 compose 的那个用户必须读得到这个文件。**

2026-10-26 实测三种状态：

| 文件状态 | `docker compose config` |
|---|---|
| 文件不存在 | `env file ... not found: stat ...: no such file or directory`，rc=1 |
| `root:root 600`，compose 以非 root 跑 | `open ...: permission denied`，rc=1 |
| `501:1000 600`，compose 以 uid 501 跑 | **rc=0** |

**`chmod 600` 不够** —— 属主必须是「跑 compose 的那个人」。
而 `permission denied` 读起来很像「文件不存在」，这两件事要分清（本条已在 T-410 实录 §2.2 记过）。

### 命令

```bash
. "$B/state/release.env"
cd "$REPO"
cp .env.production.example "$B"/.env.production
```

然后用**编辑器**（不是 `sed`，值里可能有 `/` 和 `+`）逐项填：

```bash

```

## 六 · S3 · ★ 修 `report_root` 的挂载（**必须在第一次 `up` 之前**）

**谁**：R1 改，另一个人 review 这两处 diff（各 1~2 行）。
**前置**：S2 绿。
**注意**：本节**只给改法**。改代码这件事本身由另一个人做、另一个人看，而不是执行上线的人顺手改。

### 缺陷是什么（实测，不是推测）

`docker compose down && docker compose up -d` 之后：

```
GET /api/v1/reports        → 200，列表里那条还在（元数据在 authority，走 bind mount，活下来）
GET /static/reports/<id>.md → 404 {"code":"404","message":"报告不存在"}   ← 正文没了
GET /readyz                → 200，七项全 true                              ← 没有任何东西会红
```

机制两条，缺一条都不会发生：

1. `/data` 是 **匿名卷**（`Dockerfile:121` 的 `VOLUME ["/data"]`），
   compose 的 5 个 volume 里没有 `reports-root`（`docker-compose.yml:43-52`），
   于是 `/data/reports-root` 落在匿名卷里，**每次重建容器就换一个卷**。
2. `/readyz` 的 `data_permissions` 只遍历**四个**目录，**不含 `report_root`**
   （`api/production_app.py:554-560`）—— 所以这件事在 `/readyz` 里完全不可见。

> 顺带一条**必须分清**的：容器**启动**时会检查 `report_root`
> （`production_app.py:374-380` 的 `_ensure_private_dir` 循环里**有**它），
> 权限不对会 `exit code 3`。**运行中**的 `/readyz` 不查它。所以「起来了」不等于「目录一直是对的」。

### 为什么不能晚做

让改动生效（改 compose）需要 `up -d` **重建容器**，而重建正好会丢掉匿名卷里的报告正文。
**所以：先把挂载加上，再做第一次 `up`。** 上线之后再补，代价是「补之前产生的所有报告正文全部 404」。

> 同一个理由适用于**任何** `env_file` 改动：`docker compose restart` **不会**重读 `env_file`
> 里的新值（它重启的是同一个容器，环境变量是创建时注入的）。要改 env 就 `up -d`
> （= 重建），而要重建就必须先有 `reports-root` 的 bind mount。

### 改法一：`docker-compose.yml`（在 `data/db` 那行**后面**加两行）

```yaml
      - /opt/momcozy-audit-platform/data/db:/data/db
      # ★ 报告正文 + index.jsonl。必须有自己的 bind mount：
      #   /data 是匿名卷（Dockerfile 的 VOLUME），不加这一行，重建容器之后
      #   报告「列表还在、点开 404」，而 /readyz 仍是七项全 true。
      - /opt/momcozy-audit-platform/data/reports-root:/data/reports-root
```

改完这一节，`api.volumes` 应该是 **6 条** bind：authority / projection / logs /
principals.json（ro）/ db / reports-root。

### 改法二：`Dockerfile` 第 117 行（`mkdir` 补一个目录）

```dockerfile
RUN useradd --system --uid 10001 --create-home --shell /usr/sbin/nologin audit \
 && mkdir -p /data/authority /data/projection /data/logs /data/reports-root \
 && chown -R audit:audit /app /data
```

（`/data/db` 不在这里：它由 bind mount 提供，且 `_ensure_private_dir` 会建父目录。
`reports-root` 补上是为了让镜像自己就是完备的 —— 缺了它，容器里那个路径只能靠
「bind mount 时 docker 自动建挂载点」兜底，而那样建出来的是 `root:root`。）

### 宿主机同步（S1 已建过，这里只核对）

### S8.1 造一个验收探针 session

真实登录要人扫码，而下面的链路检查是机器跑。用容器内 Python 直接建一条 session
（走的是生产同一个 `SessionStore` 真身）：

```bash
. "$B/state/release.env"
$SUDO docker compose exec -T api python3 - <<'PY' | tee /tmp/probe.txt
import json, os, secrets
from base.auth_session import SessionStore

# ★ 三条路径全部从 env 推出来，不写死 —— 写死会让「传错 generation 文件」
#   这件事直接清空 sessions 表（auth_session.py:115-133），把所有人踢下线。
log_dir = os.path.dirname(os.environ["REVIEW_API_ACCESS_LOG"]) or "/data/logs"
gen = os.path.join(log_dir, "session-generation")
before = os.path.getsize(gen) if os.path.exists(gen) else None

doc = json.load(open(os.environ["REVIEW_PRINCIPAL_DIRECTORY"], encoding="utf-8"))
p = [r for r in doc["principals"] if "dp3" in (r.get("roles") or [])
     or "dp4" in (r.get("roles") or [])][0]
store = SessionStore(
    os.environ["REVIEW_API_SESSION_DB"],
    step_up_audit_path=os.path.join(log_dir, "step-up-audit.jsonl"),
    auth_audit_path=os.path.join(log_dir, "auth-audit.jsonl"),
    generation_file=gen)
after = os.path.getsize(gen) if os.path.exists(gen) else None
n_sessions = store._conn.execute("SELECT count(*) FROM sessions").fetchone()[0]
csrf = secrets.token_urlsafe(24)
sid = store.create_session(p["id"], tenant=p["tenant_id"], provider="feishu",
                           issuer="feishu", csrf_token=csrf,
                           authz_version=p["authz_version"])
store.close()
print("GEN_STABLE=%s" % (before == after))
print("SESSIONS_NOW=%d" % n_sessions)
print("SID=%s" % sid)
print("CSRF=%s" % csrf)
print("AS=%s" % p["id"])
print("AT=%s" % p["tenant_id"])
print("APL=%s" % (p.get("product_lines") or [""])[0])
PY
```

期望（**六行**，值不同）：

```
GEN_STABLE=True            ← ★ 必须是 True
SESSIONS_NOW=<数字>         ← ★ 必须与现有登录人数相当（不是 0，除非本来就没人登录）
SID=<43 个字符的 base64url>
CSRF=<32 个字符的 base64url>
AS=<principal id>
AT=<tenant_id>
APL=<品线>
```

**`GEN_STABLE` 是本步唯一的硬判据**。它是 `False` → 你在生成这条 session 的时候
**同时把 sessions 表清空了**（`base/auth_session.py:115-133`：DB 存在但 generation
表消失、或两边 generation 不一致，都会 `DELETE FROM sessions`）。
这时**所有人被踢下线**，且不会有人报错，只会觉得「怎么又要重新登录」。

`SESSIONS_NOW` 提供第二重判据：它必须是「这次插入**之前**的行数」。若它是 0 而此前
有人正常在用，说明表已经被清过。

> **这条命令为什么安全（在 `GEN_STABLE=True` 的前提下）**：它只往 session 表插一行。
> `SessionStore` 打开时会读 `/data/logs/session-generation`（路径由 `REVIEW_API_ACCESS_LOG`
> 的目录推出）与库里的 generation 比对；**一致就不动 sessions**。反过来 ——
> 如果你拿错了 DB 或 generation 文件，它会清空所有 session。所以上表的第一行
> 不是「顺便打印一个数」，它是**这条命令的安全证明**。

```bash
. /tmp/probe.txt   # 把 SID/CSRF/AS/AT/APL 读进 shell
AUTH="Cookie: __Host-session=$SID; csrf=$CSRF"
```

> ★ **为什么不用 `-b jar.txt`**：session cookie 叫 `__Host-session`
> （`production_app.py:129`），`__Host-` 前缀的 cookie 在 cookie jar 里带 `secure` 位，
> 而 curl **只在 https + 或 host 是 `localhost`/`127.0.0.1` 时才发它**。
> 上线的检查是打到 `http://172.20.0.1:18000`，实测（本文写作时）：
>
> | URL host | 用 `-b jar` 会不会带上 `__Host-session` |
> |---|---|
> | `127.0.0.1`（http） | **会** |
> | `localhost`（http） | **会** |
> | `172.20.0.1`（http） | **不会**（`COOKIE=<none>`） |
>
> 所以在目标机上做检查，**必须显式给 `Cookie` 头**（如上）。经过 https 反代
> （`https://ca.luteos.com`）时 `-b jar` 是正常的 —— 那是浏览器走的那条路。

| `report_body=404` | 报告正文没撑过重启。这不该发生 —— 立刻按回滚方案 §一 的 R7 判（报告正文 404） |

## 十四 · S11 · `down && up` 存活（**这一步才验得到 `report_root`**）

**谁**：R1
**前置**：S10 绿。**这一步会重建容器**，所以是最接近「将来某次部署」的演练。

```bash
. "$B/state/release.env"; . /tmp/probe.txt
AUTH="Cookie: __Host-session=$SID; csrf=$CSRF"
CASES_BEFORE=$(curl -sS "$H/api/v1/cases" -H "$AUTH" | python3 -c 'import json,sys;print(len(json.load(sys.stdin)))')
VOL_BEFORE=$($SUDO docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' momcozy-audit-api)
echo "before: cases=$CASES_BEFORE report=$RID data_volume=$VOL_BEFORE"

$SUDO docker compose down
$SUDO docker compose up -d
sleep 45

VOL_AFTER=$($SUDO docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' momcozy-audit-api)
echo "after : data_volume=$VOL_AFTER  (变了是正常的 —— /data 是匿名卷)"
curl -sS "$H/readyz" | python3 -c 'import json,sys;d=json.load(sys.stdin);print("readyz=",d["ready"],all(d["checks"].values()))'
curl -sS "$H/api/v1/cases"   -H "$AUTH" | python3 -c 'import json,sys;print("cases=",len(json.load(sys.stdin)))'
curl -sS "$H/api/v1/reports" -H "$AUTH" | python3 -c 'import json,sys;print("reports=",len(json.load(sys.stdin)))'
curl -sS -o /tmp/after.md -w 'report_body_after=%{http_code} %{content_type}\n' "$H/static/reports/$RID.md" -H "$AUTH"
$SUDO ls -l "$B/data/reports-root/reports/" | tail -3
```

### 逐字段期望（**这一组是本单最重要的判据**）

| 项 | 期望 | 不符说明什么 |
|---|---|---|
| `data_volume` 变了 | **允许变**（`/data` 是匿名卷） | 没变也不代表对，见下一条 |
| `readyz` | `True True` | 七项全 true **不代表报告没问题** —— 它不查 `report_root` |
| `cases=` | 与 `CASES_BEFORE` 相同 | 不同 → `authority` 挂载丢了 |
| `reports=` | 与 before 相同 | 不同 → 报告索引没了 |
| **`report_body_after`** | **`200 text/markdown; charset=utf-8`** | **`404` → §S3 的修法没生效** |
| `$B/data/reports-root/reports/` 里仍有 `<RID>.md` | 有，且非零字节 | 没有 → bind mount 没生效 |

**为什么必须跑这一步**：`restart` 不重建容器，所以匿名卷的问题在 S10 **完全看不出来**。
2026-10-26 实测：`down/up` 之后 `cases` 一条不少、`/readyz` 七项全 true，
**而报告正文 404**。

### 失败时

| 现象 | 说明什么 · 下一步 |
|---|---|
| `report_body_after=404` | ★ 立刻查 `$SUDO docker compose config \| grep -c 'source: /opt/momcozy-audit-platform'`。若是 5 → S3 没做。若是 6 但仍 404 → `$SUDO ls $B/data/reports-root/reports/`；空说明写路径不是这个目录，检查 `REVIEW_REPORT_ROOT` 是否为 `/data/reports-root`（拼错会写进匿名卷） |
| `reports=` 变了但 `report_body` 200 | 不可能同时。若真见到，先重跑一次两条命令，排除时序 |
| `cases=` 少了 | `$SUDO docker inspect momcozy-audit-api --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'`，逐条比对 §S6 的 6 行 |
| `up -d` 后 `Restarting (3)` | 见 §S6 失败表第一行。这次多发在上一步 `down` 之后目录权限被改过 |

## 十五 · S12 · 上线后的前 30 分钟看什么

**谁**：R3（持续看）；任何一条越线 → 按回滚方案 §一 的编号判断是否回滚。

**阈值只写在回滚方案 §一**，本节只给**怎么读出来**。在 S8/S9 用的**同一个 shell 会话**里跑
（`$CASE`/`$RID`/`$AUTH` 都还在；换会话就先 `. /tmp/probe.txt` 重新取）。

**每 5 分钟跑一次这一整块**（不是每分钟 —— 第 3、4 条数的是 5 分钟窗口，每分钟跑会重复计同一个窗口）：

```bash
. "$B/state/release.env"
echo "===== $(date -u +%H:%M:%SZ) ====="
# 1 容器状态与重启次数（判据 R1）
$SUDO docker inspect -f 'state={{.State.Status}} health={{.State.Health.Status}} restarts={{.RestartCount}} exit={{.State.ExitCode}}' momcozy-audit-api
# 2 七项（判据 R2）
curl -sS -o /tmp/rz.json -w 'readyz_http=%{http_code} ' "$H/readyz"
python3 -c 'import json;d=json.load(open("/tmp/rz.json"));print("ready=%s err=%r false=%r"%(d["ready"],d["error_code"],[k for k,v in d["checks"].items() if not v]))'
# 3 近 5 分钟**写端点**上的 5xx（判据 R3）
$SUDO docker compose logs --since 5m --no-log-prefix api 2>/dev/null \
  | grep -E '"(POST|PUT|PATCH|DELETE) /api/v1/' | grep -cE '" 5[0-9][0-9] '
# 4 近 5 分钟**写端点**上的 4xx，分两个码（判据 R4）
$SUDO docker compose logs --since 5m --no-log-prefix api 2>/dev/null \
  | grep -E '" 4[0-9][0-9] ' | grep -cE 'csrf_denied|origin_denied'
# 5 权威与报告在长（判据 R5）
echo "manifests=$($SUDO ls $B/data/authority/manifests | wc -l) events=$($SUDO ls $B/data/authority/events | wc -l)"
echo "report_md=$($SUDO find $B/data/reports-root/reports -maxdepth 1 -name '*.md' 2>/dev/null | wc -l)"
echo "index_lines=$($SUDO test -f $B/data/reports-root/reports/index.jsonl && $SUDO wc -l < $B/data/reports-root/reports/index.jsonl | tr -d ' ' || echo 0)"
# 6 磁盘（判据 R6）
df -h /opt | tail -1 | awk '{print "avail="$4" use="$5}'
```

### 每条的读法

| # | 读数 | 正常长什么样 | 异常长什么样（回滚方案 §一 的编号） |
|---|---|---|---|
| 1 | `state` / `health` / `restarts` / `exit` | `state=running health=healthy restarts=0 exit=0` | `restarts` 增长 → **R1**；`health=unhealthy` → **R1** |
| 2 | `readyz_http` / `ready` / `false=[...]` | `readyz_http=200 ready=True err=None false=[]` | `readyz_http=503` 或 `false=[...]` 非空 → **R2**（按 false 的具体项查表） |
| 3 | 写端点 5xx 条数 | `0` | ≥ 1 → **R3** |
| 4 | `csrf_denied` / `origin_denied` 条数 | `0` | ≥ 1 → **R4** |
| 5 | `manifests`=`events`、`report_md`/`index_lines` | 四数各自只增；`manifests == events` | 任何一个变小 → **R5**（数据丢了） |
| 6 | `avail` / `use` | `avail` > 10G 且 `use` < 90% | 越线 → **R6** |

**第 3、4 条为什么只数写端点**：读端点（`GET`）正常使用会持续产生 401
（未登录探测、SPA 试探），把 4xx 的**绝对值**当判据会天天误报。
`/healthz` 每 30 秒被 healthcheck 打一次，但它是 **200**，不进这两个计数。
