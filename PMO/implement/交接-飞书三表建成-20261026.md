## 2. 最重要的结论：两个公式必须降级，这是平台限制

若你之前基于「模板写了公式」做判断，那条判断需要更新。

按模板 §三 写了 `验收结论`（F30）与 `完成率`（M11）的公式，做了原语级实测：

| 原语 | 结果 |
|---|---|
| `COUNTA([关联子字段])` | ✅ 计数正确 |
| `TEXT([关联子字段])` | ⚠️ **只返回第一条**关联值 |
| `COUNTIF([关联子字段], 值)` | ❌ **恒返回 0**，无论值是否存在 |
| `SUMIF` / `ARRAYJOIN` / `TEXTJOIN` / `SEARCH` | ❌ 返回 null |
| `ISERROR(FIND(...))` | ❌ 返回恒定值，与 FIND 结果不自洽 |
| `BLANK()` | ❌ 函数不存在，整个公式返回 null |

**后果实测**：WBPM-0001/0002/0003 三条，证据分别为 {不通过,未测}、{未测}、{未测}，
公式一律输出 **`通过`**。这违反模板 §3.2 第 1 条（必验项缺记录 → 未测）
与 §7.6（未测不变通过）。

**处置**：
- `验收结论` → 单选（未测/部分通过/不通过/通过/证据冲突），94 条全填「未测」
- `完成率` → 文本，3 条全填「未确认范围」
- `进度健康度`／`延期天数`／`阻塞事项数` **保留为公式** —— 只依赖本表字段，
  实测正确，且行为级反向对照验过会随数据变化

取舍理由：宁可要一个手填、填的时候会被问「凭什么」的字段，
也不要一个会自己编出「通过」的公式。与本项目「会误报的检查器比没有更糟」同一条口径。

## 4. 已踩过的平台坑（照做会重复踩）

| 现象 | 真因 |
|---|---|
| 建表带 `fields` / `default_view_name` → `99992402 validation failed` | 只接受 `{"table":{"name":...}}` |
| 改字段名 `PATCH` → 404 | 字段更新是 `PUT` |
| 改字段名 PUT 只传 `field_name` → `99992402` | 必须同时带 `type`（及 `property`） |
| 表里多出「文本/单选/日期/附件」四列 | 平台自动建表的默认字段 |
| 主字段删不掉 → `1254046` | 主字段只能改名/改类型 |
| 主表多出 10 条空行 | 字段增删过程中平台补的空记录，需 `batch_delete` |

改主字段名的可行路径（唯一验过的一种）：把目标字段改成临时名 → 主字段改成目标名 →
批量把值从临时字段搬到主字段 → 删临时字段。
