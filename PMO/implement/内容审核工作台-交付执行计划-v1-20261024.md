## 一 · GOAL（目标与完成定义）

### 1.1 一句话目标

> **让一名真实的投放/审核人员，从登录开始，能把一份内容提交进系统、拿到机器判定、
> 在案件详情里逐条裁决、结案、生成不可变报告、完成签发放行；全程可审计、可回滚、
> 重启不丢数据，且每一步都有一条会红的断言守着。**

### 1.2 完成定义（DoD · 七条同时成立才算交付）

| # | 判据 | 执行点 |
|---|---|---|
| D1 | `verify_acceptance_run.py` → `failed=0`，且 `untested` 只剩 manual/unverifiable | `python3 tools/verify_acceptance_run.py` |
| D2 | `verify_acceptance_ratchet.py --run` → rc=0，`passed_floor` 与实测 `passed` 一致 | `python3 tools/verify_acceptance_ratchet.py --run` |
| D3 | 生产容器起来后 `/readyz` 七项 checks 全 true | `curl -s localhost:8000/readyz` |
| D4 | 真实飞书 OAuth 扫码登录成功，`/api/v1/me` 返回真实 `tenant_id`/`open_id` | `tools/verify_feishu_web_oauth_live.py` |
| D5 | 一条端到端样本走完「提交→判定→裁决→结案→报告→签发」，重启后状态仍在 | 新增端到端验收票 T-316 的断言 |
| D6 | 工作台 12 页在生产构建下全部可读写，无 501 占位（除已 waiver 项） | `web/scripts/check_production_bundle.mjs` + 逐页 CDP |
| D7 | 所有 waiver 项都在有效期内，到期有触发点 | `python3 tools/verify_waivers.py` |

### 1.3 三条不可协商的约束

1. **不许用「读数变绿」代替「能力建成」。** 一条判据若只可能绿或「未测」，它就不是判据
   （`#136` 的教训，见 `0d84ccd`）。
2. **不许在裁定前先做裁定。** 语义 BLOCK（T-121）、组合规则升级（`#29`）、品牌 T10 开启，
   都必须等委托方/法务书面结论；先补代码等于替人做决定。
3. **不许把断链固化进镜像。** 链路未通时不做部署发布（`D3 = C` 的原意）。

## 四 · 阶段划分与阶段门

> 阶段门的意思是：**上一阶段没过，下一阶段不开工**。不是为了排期好看，是因为
> 「链路未通就部署 = 把断链固化进镜像」这件事已经写进 `D3 = C` 的裁定里。

### P0 · 清场（0.5 天，无依赖，本会话可执行）

**目标**：让「仓库自己的读数」先干净。不干净的工作区会让后面每一次红都分不清是谁造成的。

| 出口判据 | 命令 |
|---|---|
| 文档可达性 rc=0（D/D2/E1 三项转绿） | `python3 tools/verify_doc_reachability.py` |
| 填充态 0 个 | `python3 tools/verify_depad.py`（**仅 macOS 宿主有效**，见 §七） |
| 工作区无「假 M」 | `git diff --numstat` 对三个 M 文件输出为空 |

### P1 · 工作台生产写链闭合（关键路径，8–14 人日）

**目标**：把 ⑥ 环节从「501 拦截 + 内存态」变成「持久化 + 可审计」。
这是**产品能不能用**的分水岭：做完之前，工作台只有「提交 + 初审」是可用的。

阶段门：**D5 端到端样本跑通**（提交→判定→裁决→结案→报告→签发→重启后仍在）。

### P2 · 点火（5–8 人日 + 外部等待）

**目标**：真实身份、真实容器、真实可达。
阶段门：`/readyz` 全绿 + 真实扫码登录 + `verify_feishu_web_oauth_live.py` rc=0。

### P3 · 能力补齐（按裁定与外部输入解锁）

多模态进件、前端技术栈四条红行、品牌 T10、组合升级、PASS 可达性。
**本阶段的票多数是 blocked**，解锁条件写在票里，不许提前开工。

### P4 · 签收与收官

人工签收、CI/hook 触发点、变异探针 survived 清零、136 项定格。

## 五 · 票号体系与状态机

- **票号**：`T-3xx`。与既有 `T-100..T-250` 不重叠（那批是 10-22 清单的票，仍然有效）。
- **状态**：`draft`（写得出来但判据没定）→ `ready`（判据可执行、依赖已清）→
  `in_progress` → `done`（有可复算读数）｜`blocked`（写明解锁条件与解锁人）｜`waived`（有到期日）。
- **`done` 的定义**：不是「代码写了」，是**那条验收判据从红变绿，并且有一个能让它再变红的变异**。
  这条沿用 `PMO/audit/变异探针审计-剩余5组43行-20261023.md` §〇 的口径。
- **`blocked` 必须写三件事**：缺什么、谁能给、给了之后第一步跑什么。写不出这三件 = 票没拆干净。

## 七 · 执行环境约束（实测，写给下一个人）

本计划第一次起草与 P0 执行发生在 Claude Desktop 的 Linux 沙盒里，通过 FUSE 挂载用户目录。
**以下五条是实测出来的环境事实，不是猜测**；把环境假红当成产品真红，是这份计划最想防的事：

| # | 现象 | 真因 | 怎么办 |
|---|---|---|---|
| E1 | `git status` 报 3 个 `M`，`git diff --numstat` 却是空的 | 宿主侧 +4096 填充：内容与 HEAD 逐字节相同，只有 `stat` 视图多 4096 | **不许「修」它**。宿主终端跑 `python3 tools/verify_depad.py --fix`（`cp` 往返 + sha256 断言） |
| E2 | `verify_depad.py` 在沙盒里报「扫描 7515 个文件 · 被填充 0」 | 它调的是 macOS `stat -f %z`；Linux 的 `stat -f` 是文件系统视图，格式串无效 | 该脚本**只在 macOS 宿主有效**。沙盒读数不许当结论 |
| E3 | `verify_acceptance_ratchet.py --run` 报 `passed=12 failed=111` | 沙盒里 `.venv/bin/python` 是 macOS 符号链接，指向不存在的解释器；系统 Python 无 `fastapi` | **这是环境假红**。必须在宿主用 `uv run` 或 `.venv/bin/python` 重跑 |
| E4 | `verify_coverage.py` 报 `verify_media_portability.py` 与 `base/ocr_vision.m` 脱钩 | 被填充的文件在沙盒视图里是二进制，`grep` 读不到正文 | 同上：宿主重跑；不要在沙盒里改这个验证器去「迁就」读数 |
| E5 | FUSE 挂载**可写不可删** | `rm` / `git checkout` 会报 `Operation not permitted` | 新建文件用 Write 工具；覆盖用编辑；**不要试图删除或回滚文件** |

> 结论：**沙盒适合写规格、拆票、跑纯离线文档检查；不适合跑依赖 venv 的验收集。**
> 所有 P1 及之后的票，执行与验收都在宿主终端完成。
