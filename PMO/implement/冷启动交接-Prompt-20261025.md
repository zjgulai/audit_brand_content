## 6. 已修的真缺陷，两类形状

### 6.1 「零件对、接线错」（四个）

rbac 名单源没注入、报告 ACL 读单数 `role`（真实 principal 是复数 `roles`）、
`report_root` 缺配置项、报告响应挂错层级（挂在 `outcome` 顶层，
而路由只取 `outcome["result"]`）。

它们**只在真实生产装配下暴露**，手工 `create_app()` 的验证器一个都抓不到。
`verify_stage_gate_d5.py` 就是为这一类建的：它走 `create_production_app()` +
`ProductionRuntime.start()`，不是手工拼装。**任何涉及生产装配的改动，都要跑它。**

### 6.2 「只在宿主上暴露」（两个，都已修）

这两个是重建 venv 之后才显形的，沙盒一直绿：

**① v1 投影库迁移崩溃**（`f1d8ba4`）
`_migrate` 把「全新库建表」与「v1 升级」写成同一个 `if version < 2:` 分支。
全新库（version=0）没问题；**任何 v1 老库升级**都撞 `table already exists`
→ `ProductionRuntime.start()` 抛错 → **服务起不来**。
沙盒验不出：所有验证器都用 version=0 的新库，新库永远走不到 v1 分支。
修法：按 `user_version` 分三段（`<1` 全量建 / `==1` 只补一张表 / `>=2` 不动）。
判据：C16 造一个**真的** v1 库来打（不是模拟 —— 模拟出来的结构总会恰好与实现一致）。

**② `close()` 未 checkpoint**（`da76e42`）
SQLite WAL 模式下最后一个写连接关闭时「通常」会清 `-wal`：Linux 清，macOS 不清。
而 `base/backend_recovery.py:300` 正是靠这个判「临时投影库有没有未落盘数据」，
于是 macOS 上判 `projection_sidecar_open` 退 2。
修法：`close()` 里先 `PRAGMA wal_checkpoint(TRUNCATE)` 再关（顺序不能反）。

### 6.3 一条关于「跨平台断言」的硬教训

②的判据我写了**三版**才对：

- v1「close() 后 `-wal` 不存在」→ Linux 上**恒真**（OS 帮忙删），
  变异「删掉 checkpoint」照样绿。
- v2「写入后非空、close 后为空」→ 后半仍靠 OS，还是绿。
- v3「用第二个连接挡住 OS 自动 checkpoint」→ 试了 plain / mode=ro /
  immutable / 写连接，**四种全失败**（Linux 上最后一个写连接关闭时一定 checkpoint）。
- **v4（落地）**：承认在 Linux 上做不到数值敏感，改成**结构判据** ——
  读 `close()` 源码，断言那行 checkpoint 存在**且**在 `conn.close()` 之前。

> **一个只在目标平台上才可能红的断言，在开发平台上永远绿，等于没有。**
> 遇到跨平台差异：要么把「平台帮忙」这个变量从实验里去掉（这次做不到），
> 要么补一条不依赖平台的**结构**判据，并且**在断言名字里写明它测不到什么** ——
> 别让它假装是绿的。

### 6.4 另一个坑：SPA fallback 吃路由

SPA fallback 是 `/{full_path:path}`，它会把 `/static/...` 吃掉并回落到 `index.html`，
**而且返回 200**。所以 D5-10b 断言的是正文内容（含 `# 内容审查报告`、
不含 `id=root`），不是状态码。**只断状态码的测试在这里是假的。**

## 8. 你的工作纪律

1. **改任何代码前，先跑对应验证器拿基线。** 没有基线就不知道是自己改坏的还是本来就坏。
2. **每条新断言都要能用变异证明它会红。** 写不出「什么变异让它变红」的断言，
   当场删掉或重写。上一轮有四处这样的假断言被抓出来，形状分别是：
   - 往 pydantic 模型里塞没声明的字段（被静默丢弃，测不到）；
   - 手搓一个输入去喂被测函数（证明不了生产写进去的是什么）；
   - 同一个判据写两遍（冗余的那一遍永远测不出东西）；
   - 断言依赖一个从未注册的路由（测的是一个不存在的对手）。
3. **改完某个子系统，跑到它的自证变绿。** 别攒着一起跑。
4. **区分「未测」与「通过」。** `rc=2` 不是绿。
5. **遇到真正需要用户决策的点，停下来问。** 不要替产品/法务裁定。
   目前已知需要裁定的是 §7 的第一条（签发字段来源）。
6. 沙盒里做**所有**文件改动，写 `.md` / `.sh` 时**优先用 `node -e`
   (`fs.writeFileSync`)**，其次 Python；**不要用 Write/Edit 工具**。
   这个 FUSE 挂载有三种已知异常，判据各不相同：

   | 异常 | 判据 | 后果 |
   |---|---|---|
   | null 字节污染 | `open(f,'rb').read().count(b'\x00') > 0` | Python 无法 parse（`source code string cannot contain null bytes`） |
   | +4096 填充 | `os.stat(f).st_size != len(open(f,'rb').read())` | `git add` 报 `short read while indexing`，**文件内容其实是对的** |
   | mtime 骗过缓存 | 源码对、运行行为旧 | `.pyc` / 模块缓存复用旧编译结果 |

   **第二种最容易误判**：`git add` 报错了，但 `git ls-files -s` 显示 blob 里内容齐全。
   别以为「add 失败 = 没进去」，先用
   `git cat-file -p <blob> | grep <你写的字符串>` 核实。
   绕法是 `rm` 掉再让 node 重写（`cp` 有时也行，有时不行）。
7. **`git` 操作在本挂载上不可靠，先读这段再动 git。**
   实测：`git commit` 会 Bus error 或**返回 0 但不落 ref**（提交看似成功、`git log` 没变化）。
   `git add` 中文路径文件会持续 `short read while indexing`。
   `git status` / `git diff --stat` 偶尔会**静默返回空**（看起来工作区干净，其实不是）。

   可疑时用这两个命令交叉核对，别信第一次读数：

   ```bash
   git --no-optional-locks diff --name-only HEAD
   git --no-optional-locks ls-files --others --exclude-standard
   ```

   确认要提交时的绕法：把 index 复制到 `/tmp`，用 `GIT_INDEX_FILE` 操作，
   然后 `git commit-tree` + 手工写 `.git/refs/heads/main`：

   ```bash
   cp .git/index /tmp/tmpidx && rm -f /tmp/tmpidx.lock
   TREE=$(GIT_INDEX_FILE=/tmp/tmpidx git write-tree)
   PARENT=$(git rev-parse HEAD)
   NEW=$(GIT_AUTHOR_NAME=... GIT_AUTHOR_EMAIL=... \
         GIT_COMMITTER_NAME=... GIT_COMMITTER_EMAIL=... \
         git commit-tree "$TREE" -p "$PARENT" -F /tmp/msg.txt)
   printf '%s\n' "$NEW" > .git/refs/heads/main
   cp /tmp/tmpidx .git/index
   ```

   中文路径文件 add 不进去时：用 Python 算 blob 写进 `.git/objects`，
   再 `git update-index --add --cacheinfo 100644,<sha>,<path>`。

8. **提交后要复跑，不要假设提交前绿就等于提交后绿。**

## 9. 沙盒与宿主的差异（会反复咬人，先看这里）

本项目有两个执行环境，**结论经常不同**。判定优先级：**宿主（macOS）为准**。

| 差异 | 沙盒（Linux） | 宿主（macOS） | 怎么办 |
|---|---|---|---|
| SQLite WAL 清理 | `close()` 后 OS 自动删 `-wal` | **不删** | 代码里显式 `wal_checkpoint`（已修，`da76e42`） |
| `.venv` | macOS 符号链接，不存在 | 真实 3.12 venv | 沙盒用系统解释器 + PYTHONPATH，**别动 `.venv`** |
| 验收读数 | 约 120（低几条） | **124**（地板） | 以宿主为准，沙盒低不是回归 |
| `python3` | 3.10（无 `tomllib`） | 3.12 | `tomllib` 缺失 = 跑错解释器，不是代码坏 |
| OCR 二进制 | `.tools/bin/ocr` 是 Mach-O，跑不了 | 能跑 | 沙盒 `#11` 恒未测 |
| Chrome | 无 | 有 | 沙盒 `#112`/`#116` 恒未测 |
| `stat` 大小 | 可能 +4096（填充态） | 正常 | 判据用 `len(open(f,'rb').read())`，不看 `stat` |
| 文件写入 | Python 写 `.md`/`.sh` 会出现 null 字节或填充 | 正常 | 优先 `node -e fs.writeFileSync`，改完核 null |
| `git` | `commit` 会 Bus error / 静默不落 ref | 正常 | 沙盒用 `GIT_INDEX_FILE` + `commit-tree` + 手写 ref |

> **最重要的一条**：沙盒里绿、宿主上红，不要先怀疑代码 —— 先问「这个判据
> 在沙盒里有没有可能红」。**一个在开发平台上恒真的断言，等于没有。**
> §6.3 里那条写了三版才对的判据，就是被这个问题逼出来的。
