## 1. 第一件事：清 pyc，然后摸状态

```bash
cd <仓库根>

# ① 清 pyc —— 这条不是例行公事，是硬性的
find . -name "__pycache__" -type d -not -path "./.git/*" -exec rm -rf {} +

# ② 看状态
git status --short
git log --oneline -1
```

**为什么必须先清 pyc**：这个仓库所在的文件系统（FUSE 挂载）**mtime 不可靠**。
上一个会话为此白查了三轮：源码明明改对了，运行时行为还是旧的，
`inspect.getsourcelines()` 读源码也是对的，但 `dis` 反汇编显示字节码是旧的。
`ls -la` 显示的 `.pyc` 时间戳是「刚刚」，Python 据此判定缓存比源码新而直接复用。
**现象是「源码明显对、运行行为明显错」时，第一动作就是删 pyc，不要去怀疑框架。**

## 8. 你的工作纪律

1. **改任何代码前，先跑对应验证器拿基线。** 没有基线就不知道是自己改坏的还是本来就坏。
2. **每条新断言都要能用变异证明它会红。** 写不出「什么变异让它变红」的断言，
   当场删掉或重写。上一轮有四处这样的假断言被抓出来，形状分别是：
   - 往 pydantic 模型里塞没声明的字段（被静默丢弃，测不到）；
   - 手搓一个输入去喂被测函数（证明不了生产写进去的是什么）；
   - 同一个判据写两遍（冗余的那一遍永远测不出东西）；
   - 断言依赖一个从未注册的路由（测的是一个不存在的对手）。
3. **改完某个子系统，跑到它的自证变绿。** 别攒着一起跑。
4. **区分「未测」与「通过」。** `rc=2` 不是绿。
5. **遇到真正需要用户决策的点，停下来问。** 不要替产品/法务裁定。
   目前已知需要裁定的是 §7 的第一条（签发字段来源）。
6. 沙盒里做**所有**文件改动，写 `.md` / `.sh` 时**优先用 `node -e`
   (`fs.writeFileSync`)**，其次 Python；**不要用 Write/Edit 工具**。
   这个 FUSE 挂载有三种已知异常，判据各不相同：

   | 异常 | 判据 | 后果 |
   |---|---|---|
   | null 字节污染 | `open(f,'rb').read().count(b'\x00') > 0` | Python 无法 parse（`source code string cannot contain null bytes`） |
   | +4096 填充 | `os.stat(f).st_size != len(open(f,'rb').read())` | `git add` 报 `short read while indexing`，**文件内容其实是对的** |
   | mtime 骗过缓存 | 源码对、运行行为旧 | `.pyc` / 模块缓存复用旧编译结果 |

   **第二种最容易误判**：`git add` 报错了，但 `git ls-files -s` 显示 blob 里内容齐全。
   别以为「add 失败 = 没进去」，先用
   `git cat-file -p <blob> | grep <你写的字符串>` 核实。
   绕法是 `rm` 掉再让 node 重写（`cp` 有时也行，有时不行）。
6. 沙盒里做**所有**文件改动都要用 Python 字符串替换或 shell heredoc，
   **不要用 Write/Edit 工具** —— 这个 FUSE 挂载会把它们写成二进制垃圾
   （实测写出过 4092 个 null 字节）。改完用
   `python3 -c "print(open(f,'rb').read().count(b'\x00'))"` 验证是 0。

**开始之前，先把你跑出来的读数贴给用户，然后问他要不要提交、要不要重建 venv。**
