## 〇 · 三句话，先记住

1. **回滚镜像 ≠ 回滚数据。** authority（权威）只追加、永不改写（`base/business_event_store.py`
   的 manifest 链）。换回旧镜像，权威里那些批次还在。**已经发生的事不会消失。**
2. **已经产生的签名 / 放行 / 下线动作是既成事实。** 它们躺在权威里，回滚镜像只是换掉
   「以后怎么处理」，不是「把过去撤掉」。要撤销一个放行，走业务上的撤回路径
   （`release-revoke`），不是回滚。
3. **有一类回滚会失败。** 如果上线后已经产生了**新版本才认识的批次**
   （通知 / 撤权 / 重审 job 那几类），旧镜像**建不出投影**（实测，见 §5.2）。
   这时回滚的形态不是「换镜像」，而是「换镜像 + 从备份恢复数据」。见 §5。

## 一 · 必须立刻回滚的读数（这是唯一一份阈值）

下面这几条是**当次**判据（刻意不写条数：加一条就会让数字型描述过期）。每条给出：怎么读、阈值、越线判给谁看、以及「读数本身可能骗人」的那一面。

> 采集脚本在**执行单 §S12**（每 5 分钟跑一次 —— 它的第 3、4 条数的是 5 分钟窗口，
> 每分钟跑会把同一个窗口重复计一遍）。本节只写阈值与含义。

### R1 · 容器在反复重启

**读法**

```bash
. /opt/momcozy-audit-platform/state/release.env
$SUDO docker inspect -f 'state={{.State.Status}} health={{.State.Health.Status}} restarts={{.RestartCount}} exit={{.State.ExitCode}}' momcozy-audit-api
```

**阈值：`restarts` 在 10 分钟内增长 ≥ 1。**

`RestartCount` 是累计值，不是「最近」。所以判据是**两次采样的差**，不是绝对值：

```bash
A=$($SUDO docker inspect -f '{{.RestartCount}}' momcozy-audit-api); sleep 600
B=$($SUDO docker inspect -f '{{.RestartCount}}' momcozy-audit-api)
echo "restarts_delta=$((B-A))"     # ≥1 → 回滚
```

**越线说明**：应用层在拒绝启动或崩溃。`exit=3` 是应用层拒绝（配置/权限/principals），
会一直重启且永远起不来；`exit=137` 是被 OOM killer 杀的；`exit=1` 是未捕获异常。
三种的下一步完全不同，但**都要先回滚再查**（`exit=3` 且配置没改过 → 一定是数据或挂载变了，
那正是回滚能救的）。

**读数会骗人的那一面**：`restart: unless-stopped` 会**无限**重试，
所以「它在动」和「它在工作」看起来都像 `Up`。必须看 `restarts` 的**增量**与 `health`。

### R2 · `/readyz` 不是七项全 true

**读法**

```bash
curl -sS -o /tmp/rz.json -w 'http=%{http_code}\n' "$H/readyz"
python3 -c 'import json;d=json.load(open("/tmp/rz.json"));print("ready=%s err=%r false=%r"%(d["ready"],d["error_code"],[k for k,v in d["checks"].items() if not v]))'
```

**阈值，按项分（不同项的含义差别极大，不许合并成一句「readyz 红了」）**：

| `false` 的项 | 阈值 | 含义 | 处置 |
|---|---|---|---|
| `writer_lease` | **只要出现就回滚** | 两个写者在抢同一份权威 = 数据可能被两个进程交错写。这是最危险的一类 | 立刻回滚 + 检查是否有第二个容器/进程 |
| `authority_chain` | **只要出现就回滚** | 权威 manifest 链读不通（损坏、文件被外部改动） | 立刻回滚，**不要**试图修文件 |
| `session_db` | **只要出现就回滚** | 所有人被踢下线 / 认证不可用 | 回滚 |
| `principal_directory` | **持续 > 2 分钟** | `principals.json` 读不出/形状不对 | 先看 §5.6 的「改文件即可」那一支；改完仍红 → 回滚 |
| `data_permissions` | **持续 > 2 分钟** | 某个目录不是 0700 | 先 `stat` 四个目录；改 `chmod` 后仍红 → 回滚 |
| `projection_fresh` | **持续 > 5 分钟** | 投影追不上权威 | 先等一轮心跳（30 秒一次）；5 分钟仍 false = `reconcile` 一直在失败 → 回滚 |
| `config` | 不必单独判 | 它恒 true（对象起不来就根本不存在） | — |

**为什么 `projection_fresh` 的阈值是 5 分钟而不是 30 秒**：心跳 30 秒一轮
（`api/production_app.py:621-627`），启动瞬间它**必然**短暂 false（投影还没 catch_up）。
30 秒就回滚 = 每次上线都会回滚一次。

**读数会骗人的那一面**（必须记，实测过）：`/readyz` 七项全 true **不代表报告没坏**。
`data_permissions` 只遍历四个目录（`api/production_app.py:554-560`），
**不含 `report_root`**。2026-10-26 实测的原始组合是：

```
GET /readyz                → 200 七项全 true
GET /api/v1/reports        → 200，列表里有那一条
GET /static/reports/<id>.md → 404
```

所以 R7（报告正文 404）**必须独立判**，不能靠 R2。

### R3 · 写端点上出现 5xx

**读法**

```bash
$SUDO docker compose logs --since 5m --no-log-prefix api 2>/dev/null \
  | grep -E 'POST /api/v1/(submissions|cases|appeals|takedown-tasks|reports|admin)' \
  | grep -cE '" 5[0-9][0-9] '
```

**阈值：5 分钟内 ≥ 1 条。**

**为什么是 1 条而不是一个比例**：这是**写**端点。一次 5xx 意味着一次业务写入的结果不确定
（可能已提交、可能没提交、可能提交了一半）。**不确定本身就是回滚理由** —— 让用户看到
「不知道成没成」比让用户看到「失败了」更糟。

**读数会骗人的那一面**：`docker compose logs` 默认只给 stdout/stderr，且**轮转由 docker 管**。
要确认「真的没 5xx」而不是「日志没拿到」，先跑一次 `docker compose logs --since 1m | wc -l`
确认非零。

### R4 · 写端点上 4xx 突然变多

**读法**：同 R3，把 `5` 换成 `4`，并**只看写端点**。

**阈值：5 分钟内写端点 4xx ≥ 20 条，且其中 ≥ 1 条是 `csrf_denied` 或 `origin_denied`。**

这两个码专门列出来，因为它们意味着**所有人**都在被拒（不是某个人权限不够）：

| 码 | 说明 | 为什么会全场发生 |
|---|---|---|
| `csrf_denied` | `X-CSRF-Token` 与 session 的 csrf 不匹配 | 反代改写/丢弃了 `csrf` cookie，或 `__Host-` 前缀在中间被剥掉 |
| `origin_denied` | `Origin` 头不等于 `REVIEW_PUBLIC_ORIGIN` | 反代改了 Host/Origin，或 `REVIEW_PUBLIC_ORIGIN` 填错 |

**读数会骗人的那一面**：正常使用会持续产生 401（未登录探测、SPA 探测）。
所以**不要看 4xx 的绝对值**，只看**写端点**上、只看这两个码。
实测基线：上线后 30 分钟内写端点的 `csrf_denied`/`origin_denied` 应当为 **0**。

### R5 · 数据只增不减，减少就是事故

**读法**

```bash
echo "manifests=$($SUDO ls $B/data/authority/manifests | wc -l)"
echo "events=$($SUDO ls $B/data/authority/events | wc -l)"
echo "report_md=$($SUDO find $B/data/reports-root/reports -maxdepth 1 -name '*.md' 2>/dev/null | wc -l)"
echo "index_lines=$($SUDO test -f $B/data/reports-root/reports/index.jsonl && $SUDO wc -l < $B/data/reports-root/reports/index.jsonl | tr -d ' ' || echo 0)"
```

**阈值：这四数中任何一个**比上一次采样小**。** 这是唯一判据。

**四个数之间不要求相等**，只要求各自单调不减：

| 关系 | 是否要求相等 | 说明 |
|---|---|---|
| `manifests` = `events` | **是**（正常状态下） | 每批 1 个 manifest + 1 个 event，成对产生。不相等且没有正在进行的写入 → 有半截状态 |
| `report_md` vs `index_lines` | **否** | 报告按内容寻址：同一份内容重复发布不会新增 `.md`，`index.jsonl` 也不重复追加（`base/report_store.py:441-452`）。两者可以不等 |

**唯一允许「变小」的例外**：你刚刚主动执行了「从备份恢复」（§5.3），那会让它们在恢复的瞬间
跳到备份里的值 —— 这个动作必须**事前**在 `$B/state/` 里留一行记录，否则下次采样会把它读成事故。

### R6 · 磁盘

**读法**：`df -h /opt | tail -1`

**阈值：`avail` < 10G，或 `use%` ≥ 90%。**

**为什么是 10G 而不是「满了才回滚」**：权威与报告都是**小文件、大量 inode**，
磁盘满时的表现是 `OSError: No space left on device` 出现在**写入中途**，
而 authority 的写入是「先写 staging 再 rename」（`base/artifact_store.py:155-175`），
所以不会写坏已有批次 —— 但会让**当前这一次**业务失败，且看起来像应用 bug。

### R7 · 报告正文 404（**与 R2 独立的一条**）

**读法**

```bash
. "$B/state/release.env"; . /tmp/probe.txt
curl -sS -o /dev/null -w 'report=%{http_code}\n' "$H/static/reports/$RID.md" \
  -H "Cookie: __Host-session=$SID; csrf=$CSRF"
```

**阈值：`report=404`，且同一时刻 `GET /api/v1/reports` 的列表里仍有这条 `report_id`。**

这个组合（**列表有、正文无**）意味着报告的元数据与正文分家了。2026-10-26 实测的成因是
`report_root` 落在匿名卷（执行单 §S3）。**上线时该缺陷已被修掉**（compose 加了
`reports-root` 的 bind mount），所以上线后再看到它，说明：

* 挂载没生效（`docker compose config | grep -c 'source: /opt/momcozy-audit-platform'` 应为 **6**）；或
* 有人以别的方式重建了容器而没带上那个 bind。

**处置**：这不是回滚镜像能救的（镜像没坏，是挂载形状坏了）。
走 §5.5「只修挂载」那一支。**但如果在 5 分钟内定位不到，就升级为 R1/R2 级并按 §3 回滚**
——因为「挂载形状不对」意味着所有数据的落点都不确定。

## 二 · 回滚前必须先做的三件事（约 3 分钟）

**顺序不能换。** 这三件事做完之前，**不许 `docker compose down`**。

```bash
. /opt/momcozy-audit-platform/state/release.env
# ★ 只取一次时间戳。取两次会在跨秒时得到两个不同目录名，
#   于是 mkdir 建的是一个、后面写的是另一个（`set -u` 下还会因为 SNAP 未定义直接退出）。
TS=$(date -u +%Y%m%dT%H%M%SZ)
SNAP="$B/state/rollback-$TS"
mkdir -p "$SNAP"
echo "SNAP=$SNAP"
```

### ① 定格现场（先把证据存下来，再动手）

```bash
{
  echo "# 回滚现场 $(date -u +%Y-%m-%dT%H:%M:%SZ)"
  echo "## docker compose ps"; $SUDO docker compose ps
  echo "## inspect"; $SUDO docker inspect momcozy-audit-api \
      -f 'status={{.State.Status}} exit={{.State.ExitCode}} restarts={{.RestartCount}} health={{.State.Health.Status}} image={{.Config.Image}} started={{.State.StartedAt}}'
  echo "## mounts"; $SUDO docker inspect momcozy-audit-api \
      --format '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
  echo "## readyz"; curl -sS "$H/readyz" 2>&1 | head -5
  echo "## 最后 200 行日志"; $SUDO docker compose logs --tail 200 --no-log-prefix api 2>&1
} | tee "$SNAP/snapshot.txt" >/dev/null
echo "snapshot -> $SNAP/snapshot.txt"
```

**为什么先做这件事**：回滚会重建容器，**旧容器的那份日志随容器一起消失**
（`docker compose down` 删容器；`up` 起的是新容器，日志从头开始）。
不做这一步，事后没人能回答「它为什么坏的」。

### ② 清点「已经发生的事实」

这一步决定 §5 走哪一支。**必须真跑，不能凭印象**。

```bash
# 权威里各类聚合各有多少条、最新 seq 是多少
$SUDO docker compose exec -T api python3 - <<'PY' | tee "$SNAP/authority-facts.txt"
import collections, json, os
root = "/data/authority"
c = collections.Counter()
for name in sorted(os.listdir(os.path.join(root, "events"))):
    if not name.endswith(".json"):
        continue
    b = json.load(open(os.path.join(root, "events", name), encoding="utf-8"))
    c[b.get("aggregate_type") or "review_case"] += 1
print("aggregate_type 分布:", dict(c))
print("总批次:", sum(c.values()))
PY
```

**逐字段期望与含义**：

| 输出 | 含义 | 影响 §5 的哪一支 |
|---|---|---|
| 只有 `review_case` | 只有案件批次 | **可以**回滚到任何旧镜像（实测，见 §5.2 场景 A） |
| 出现 `grant_registry` | 有名单治理批次 | 要看旧镜像有没有这个分支。`SCHEMA_VERSION=2` 那一版**有**（实测 `grep` 出 `agg_type == "grant_registry"`），更早的没有 |
| 出现 `notifications` | 有通知批次 | **`SCHEMA_VERSION=2` 一定建不出投影**（实测 `unknown_aggregate_type`，见 §5.2 场景 B） |

> ★ 这张表只是**初筛**。「能不能回滚到这个旧版本」的确定判据在 §5.2 末尾那条集合包含关系，
> 不要拿这张表当结论 —— 它只告诉你「有没有嫌疑」。

再清点这三件业务事实：

```bash
$SUDO docker compose exec -T api python3 - <<'PY' | tee "$SNAP/business-facts.txt"
import json, os
from base.business_event_store import BusinessEventStore
s = BusinessEventStore("/data/authority")     # 只读
for cid in s.aggregate_ids():
    if ":" in cid:            # grants: / notifications: 不是案件
        continue
    st = s.state(cid)
    rel = st.get("release") or {}
    if rel.get("signatures") or rel.get("status") not in (None, "pending_release"):
        print("RELEASE", cid, rel.get("status"), "sigs=%d" % len(rel.get("signatures") or []))
    if st.get("takedown_tasks"):
        for t in st["takedown_tasks"]:
            print("TAKEDOWN", cid, t.get("task_id"), t.get("state"))
PY
```

**这就是「已发生的事实」清单。** 把这份文件当作交接物 —— 回滚之后要拿它对用户解释。

### ③ 记住当前镜像，确认回滚目标还在本地

```bash
CURRENT_IMAGE=$($SUDO docker inspect -f '{{.Config.Image}}' momcozy-audit-api)
echo "CURRENT_IMAGE=$CURRENT_IMAGE"
$SUDO docker image ls --format '{{.Repository}}:{{.Tag}} {{.ID}} {{.CreatedSince}}' | grep momcozy-audit
```

**逐字段期望**：

| 项 | 期望 |
|---|---|
| `CURRENT_IMAGE` | 等于执行单 §S0 写进 `release.env` 的 `$AUDIT_IMAGE` |
| `docker image ls` | 至少**两行** `momcozy-audit:*`（当前这版 + 上一版） |

**回滚目标是谁**：`release.env` 里的 `PREV_IMAGE`。执行单 §S0 留了空值，
**如果它是空的，说明这是首次上线、没有上一版** —— 那时就不叫回滚，
叫「下线」（§6）。若是第二次及以后的部署，上线前必须把上一版的 tag 写进 `PREV_IMAGE`。

```bash
echo "PREV_IMAGE=${PREV_IMAGE:-<空 —— 没有可回滚的上一版>}"
[ -n "$PREV_IMAGE" ] && $SUDO docker image inspect "$PREV_IMAGE" --format 'ok {{.Id}}' || echo "MISSING"
```

`MISSING` → 你**没有**回滚点。不许假装有。走 §6。

## 三 · 回滚步骤（按时间顺序）

**前置**：§二 三件事已完成；`$PREV_IMAGE` 存在。

### 第 1 步 · 停（不是删）

```bash
. "$B/state/release.env"
$SUDO docker compose stop
```

期望：

```
 Container momcozy-audit-api  Stopped
```

**为什么 `stop` 而不是 `down`**：`stop` 保留容器与它的匿名卷（`/data`）。
`down` 会删容器，于是 `/data` 那个匿名卷失去唯一引用 —— 虽然它不会立刻被删，
但它再也不会被挂回来（每次 `up` 建新的）。`report_root` 现在是 bind mount，
所以业务数据在 `down` 之后仍然安全；**但 `/data` 下别的东西（比如未来的新目录）不安全**。
保守做法：`stop`。

**不要 `down -v`。** 那会删卷，`-v` 是唯一会真正删数据的开关。

### 第 2 步 · 备份当前状态（**回滚前，不是回滚后**）

> ★ **先看这一条**：`tools/review_backend_admin.py` **不在镜像里**
> （`.dockerignore` 整目录排除 `tools/`，`Dockerfile` 只拷了 5 个运行时文件）。
> 所以下面的命令**在宿主机上跑**，用仓库里那份。它只用标准库 + `base/`，
> 不需要 fastapi、不需要容器起来（实测：`python3 tools/review_backend_admin.py --help` rc=0，
> `backup` rc=0，`rebuild` rc=0）。

```bash
. "$B/state/release.env"
TS=$(date -u +%Y%m%dT%H%M%SZ)
cd "$REPO"
python3 tools/review_backend_admin.py backup \
  --authority "$B/data/authority" \
  --destination "$B/data/.backups/pre-rollback-$TS" \
  --audit-dir "$B/data/logs"
```

期望（单行 JSON，逐字段）：

```json
{"authority_seq": <数字>, "destination": "/opt/momcozy-audit-platform/data/.backups/pre-rollback-<TS>", "entries": <数字>, "ok": true, "operation": "backup"}
```

**逐字段判据**：

| 字段 | 期望 | 不符说明 |
|---|---|---|
| `ok` | `true` | `false` → 见下面的错误码表 |
| `authority_seq` | 等于 §二② 你数出来的「总批次」 | 不等 → 你备份的不是你以为的那份权威 |
| `entries` | ≥ `authority_seq` × 2（每批 1 个 manifest + 1 个 event） | 少了 → 有批次缺文件 |
| `destination` | 在 `$B/data/.backups/` 下 | 不在 → `--destination` 传错。★ **别指向 `/data/backups`**：那不在任何 bind mount 里，落在 `/data` 匿名卷，容器一重建就找不到了 |

```bash
$SUDO ls -l "$B/data/.backups/pre-rollback-$TS/" | head -5
python3 -m json.tool "$B/data/.backups/pre-rollback-$TS/backup-manifest.json" | head -20
```

期望：`backup-manifest.json` 的 `schema_version` 是 `"review-authority-backup/v1"`，
`authority.authority_seq` 与上面的 `authority_seq` 相同，
`excludes` 里明确列着 `session_db`、`projection_db`、`writer_lock` 等
（**这意味着备份不含 session 与投影** —— 见 §4.2 的后果）。

**跑这一步不需要停容器吗**：`BusinessEventStore` 在不带 `lease` 时是只读

上面第 1 步已经停过了，正好。

## 四 · 数据侧怎么办（**这一节是「回滚不是撤销」的落地**）

### 4.1 五个目录，回滚镜像会动到哪几个

| 宿主机路径 | 是什么 | 回滚镜像会影响它吗 | 说明 |
|---|---|---|---|
| `data/authority` | **权威**。不可变 command batch + manifest 链 | **不会** | 只追加。旧镜像启动时把整条链读一遍（`_load()`），读得懂就继续，读不懂就 `AuthorityCorrupt` |
| `data/projection` | SQLite 投影（派生数据） | **会（间接）** | 旧镜像可能因 `projection_schema_newer` 拒开（§5.4），或因遇到不认识的批次而追不平（§5.2）。**它是可删的** |
| `data/db` | `review.db`（同 projection）+ `session.db` | 投影同上；**session 不受版本影响** | session 表只加列不改语义（`base/auth_session.py:148-170`） |
| `data/logs` | `access.jsonl` / `auth-audit.jsonl` / `step-up-audit.jsonl` / `session-generation` | **不会** | 只追加。**`session-generation` 千万别动**：换了它 = 所有人被踢下线（`auth_session.py:98-138`） |
| `data/reports-root` | 报告正文 + `index.jsonl` | **不会** | 与镜像版本无关，只取决于挂载 |

**一句话**：回滚镜像换的是「怎么解释数据」，不是「数据是什么」。
authority、logs、reports-root 三个**只增不改**，所以回滚之后它们还在，**一条不少**。

### 4.2 备份里**没有**什么（必须知道，否则会以为「恢复备份 = 回到过去」）

`tools/review_backend_admin.py backup` 的 `excludes` 明确列着：

```
session_db, session_generation, step_up, projection_db,
sqlite_wal, sqlite_shm, writer_lock, staging, cache
```

后果三条：

1. **恢复备份不会恢复登录状态。** 所有人要重新扫码（`sessions_restored: false`，
   实测返回体里就是这个值）。这不是 bug，是设计：把 session 混进权威备份
   会让「恢复备份」变成「恢复别人的登录」。
2. **恢复备份会重建投影**（`projection_status: "fresh"`，实测）。所以 §5.3 那条路
   顺便解决了投影追不平的问题。
3. **恢复备份会回退权威本身。** 这一点最危险，见下。

### 4.3 「恢复权威备份」是真正的撤销 —— 它会**丢掉备份之后的所有写入**

2026-10-26 实测（本文写作时在仓内跑的，仓外临时目录）：

```console
$ python3 tools/review_backend_admin.py backup --authority <auth> --destination <bk>
{"authority_seq": 2, "destination": ".../bk", "entries": 4, "ok": true, "operation": "backup"}

$ python3 tools/review_backend_admin.py restore --backup <bk> \
    --authority-destination <不存在的目录> --projection-db <不存在的库>
{"audit_files_restored": [], "authority_seq": 2, "ok": true, "operation": "restore",
 "projection_status": "fresh", "sessions_restored": false}
```

两次约束（都是硬的，实测）：

| 约束 | 报错 | 含义 |
|---|---|---|
| 目标目录**必须不存在** | `{"error_code": "restore_destination_exists", "ok": false}` | 所以不能原地覆盖。要「把权威换回备份」= 先移走现场（重命名保留），再恢复到原路径 |
| 目标不能与投影/审计路径重叠 | `restore_targets_overlap` | — |

**并且**：如果你把权威恢复到备份点，**备份之后产生的那些业务写入就没了** ——
包括用户已经看到的「已结案」「已放行」。所以：

> **只有一种情况允许恢复权威备份**：权威链的真实性受损（§5.3 的 `AuthorityCorrupt`）。
> 「应用坏了」不许用恢复备份来修 —— 那是撤销，不是回滚。

### 4.4 尾部截断是**静默**的（实测，必须写下来）

权威链的完整性检查能抓到「中间少一批」，但**抓不到「最后几批被删掉」**：

```bash
# 造 3 批，删掉最后一批（manifest + event 成对删）
$ ... 
成对删掉最后一批 → 能读，seq = 2 （尾部静默截断！）
# 删中间一批：
删中间一批 → AuthorityCorrupt authority_sequence: 期望 2，实际 3
```

**这条的实践含义**：

1. **不要手工删权威文件**，哪怕「只是最后那一条」。它不会报错，会安静地少一条事实。
2. **备份是唯一能发现尾部截断的东西** —— 备份里记录的 `authority_seq` 与现场对不上时，
   要么有人删过，要么备份后新写过（正常）。对照 §二② 的清点。

## 五 · 回滚形态（按现场读数选一支，不要混）

> 标题刻意不写数字：这里的支数会随缺陷增减，而「写着四条的清单实际有六条」
> 会让读的人以为多出来的是别人随手加的（`AGENTS.md` §2.2 开头那条）。

### 5.1 判断树

```
回滚前先问：PREV_IMAGE 存在吗？
├─ 不存在 → §6 下线（不是回滚）
└─ 存在
   ├─ 只是报告正文 404（R7），/readyz 七项全 true → §5.5（只修挂载，不换镜像）
   ├─ 只是某个配置项不对（principals / 目录权限 / env 值）→ §5.6（改文件，不换镜像）
   └─ 真要换镜像
      ├─ 先做「旧镜像认不认识现场所有 aggregate_type」那一次检查（§5.2）
      │  ├─ 不认识（现场有 notifications）→ ★ §5.3（只能换镜像 + 恢复备份）
      │  └─ 认识
      │     ├─ 换镜像后 /readyz 200 → 完成，去 §七
      │     ├─ 503 且 projection_fresh=false → 先删投影重试一次（§5.2 末尾）
      │     │                                  仍 false → §5.3
      │     ├─ Restarting + projection_schema_newer → §5.4（删投影）
      │     └─ Restarting + AuthorityCorrupt → §5.3（从备份恢复）
```

### 5.2 旧镜像读不懂新批次（**实测**，这是最容易被忽略的一支）

**现象**：换回旧镜像后，`/readyz` 里 `projection_fresh=false`，日志里追平失败。
更坏的一种：容器能起来、`/readyz` 也可能短暂 true，直到有一天投影库被删/重建才暴露。

**实测（2026-10-26，本文写作时在仓内跑的）**：

```text
场景 A：权威里只有 review_case 批次（seq=1）
  旧镜像 SCHEMA_VERSION=2 从零重放 → 成功, applied_seq=1        ← 可以回滚

场景 B：权威里有一条 notifications 批次（v3 才有的聚合类型，seq=2）
  旧镜像从零重放 → 失败: ProjectionError unknown_aggregate_type
  → 对应现象：/readyz 里 projection_fresh=false
```

**机制**：投影写入按 `aggregate_type` 分流，`version 2` 的投影层只有
`review_case` / `grant_registry` 两个分支，遇到 `notifications` 走
`raise ProjectionError("unknown_aggregate_type")`；而且 v2 库里**根本没有**
`notifications` 表（实测：`v2 库里有没有 notifications 表: False`）。

**所以判断「能不能回滚到这个旧版本」的判据是一句话**：

> **权威里出现过的每一种 `aggregate_type`，旧镜像的投影层都必须认得。**

**怎么判**（回滚**之前**跑，30 秒）：

```bash
# 现场所有出现过的 aggregate_type
$SUDO docker compose exec -T api python3 -c '
import collections, json, os
c = collections.Counter()
for n in os.listdir("/data/authority/events"):
    if n.endswith(".json"):
        c[json.load(open("/data/authority/events/"+n, encoding="utf-8")).get("aggregate_type") or "review_case"] += 1
print(sorted(c))'

# 旧镜像的投影层认识哪些分支
$SUDO docker run --rm --entrypoint sh "$PREV_IMAGE" -c \
  'grep -o "agg_type == \"[a-z_]*\"" /app/base/projection_store.py | sort -u'
```

期望：

```
['grant_registry', 'notifications', 'review_case']     ← 现场
agg_type == "grant_registry"
agg_type == "review_case"                              ← 旧镜像
```

**左边的集合必须是右边的子集。** 不是 → 这一支走 §5.3。

### 5.3 换镜像 + 恢复备份（**只有权威受损，或必须回到旧版才能跑时才用**）

**代价明说**：备份点之后的业务写入**全部丢失**。这是**撤销**，不是回滚。

```bash
. "$B/state/release.env"
TS=$(date -u +%Y%m%dT%H%M%SZ)
$SUDO docker compose stop

# ① 把现场整体移走（不删 —— 它是最后一份证据）
$SUDO mv "$B/data/authority" "$B/data/authority.broken-$TS"
$SUDO mkdir -p "$B/data/authority" && $SUDO chmod 700 "$B/data/authority"
$SUDO chown 10001:10001 "$B/data/authority"

# ② 恢复到空目录（目标必须不存在）
cd "$REPO" && python3 tools/review_backend_admin.py restore \
  --backup "$B/data/.backups/<你要回到的那个点>" \
  --authority-destination "$B/data/authority" \
  --projection-db "$B/data/db/review.db.restored-$TS" \
  --audit-dir "$B/data/logs"
```

期望（逐字段）：

```json
{"audit_files_restored": ["access.jsonl", ...], "authority_seq": <备份点>, "ok": true,
 "operation": "restore", "projection_status": "fresh", "sessions_restored": false}
```

| 字段 | 判据 | 不符 |
|---|---|---|
| `ok` | `true` | `restore_destination_exists` → ① 没清干净；`authority_*_mismatch` → 备份本身坏了 |
| `authority_seq` | 等于 `backup-manifest.json` 里的 `authority.authority_seq` | 不等 → 备份不完整 |
| `projection_status` | `"fresh"` | 别的值 → 投影没建起来，但权威是好的（可后续 `rebuild`） |
| `sessions_restored` | `false` | 恒 false（备份 excludes session）。**所有人要重新登录** |

```bash
# ③ 换掉投影库（把恢复到的新库就位）
$SUDO mv "$B/data/db/review.db" "$B/data/db/review.db.pre-rollback-$TS" 2>/dev/null || true
$SUDO mv "$B/data/db/review.db.restored-$TS" "$B/data/db/review.db"
$SUDO chown 10001:10001 "$B/data/db/"*
$SUDO chmod 700 "$B/data/db"

# ④ 用旧镜像起
if [ -n "$SUDO" ]; then $SUDO env AUDIT_IMAGE="$PREV_IMAGE" docker compose up -d; else AUDIT_IMAGE="$PREV_IMAGE" docker compose up -d; fi
sleep 45
curl -sS -o /dev/null -w 'readyz=%{http_code}\n' "$H/readyz"
```

**`ok: false` 时的错误码对照**（`base/backend_recovery.py` 逐个点名）：

| `error_code` | 说明 | 下一步 |
|---|---|---|
| `restore_destination_exists` | 目标目录已存在 | 移到别处再试（① 做漏了） |
| `projection_destination_exists` | 投影库已存在 | `--projection-db` 指向一个新名字 |
| `restore_targets_overlap` | 权威/投影/审计路径互相包含 | 三个路径放进**不同**目录 |
| `authority_sequence` / `authority_chain` | 备份里的链本身坏了 | 换更早的一份备份 |
| `authority_object_missing` / `authority_object_hash` | 备份缺文件或内容被改 | 换更早的一份备份 |
| `restore_authority_mismatch` | 恢复后的 head 与 manifest 声明不符 | 备份损坏 |

### 5.4 投影库 schema 比旧代码新（**实测会拒，但投影是可删的**）

**实测（2026-10-26）**：

```
新镜像建库 user_version = 3
旧代码(SCHEMA_VERSION=2) 打开 v3 库 → ProjectionError: projection_schema_newer: 3
```

**为什么这不是灾难**：投影是**派生数据**。权威是真相源，投影随时可以从权威重建
（`base/projector.py` 的 `rebuild()`：先 `authority.head()` 校验整条链，再
`projection.reset()` 然后逐批重放，最后校验 `fresh`）。

```bash
. "$B/state/release.env"
$SUDO docker compose stop
$SUDO mv "$B/data/db/review.db" "$B/data/db/review.db.schema-v3-$(date -u +%Y%m%dT%H%M%SZ)"
$SUDO rm -f "$B/data/db/review.db-wal" "$B/data/db/review.db-shm"
if [ -n "$SUDO" ]; then $SUDO env AUDIT_IMAGE="$PREV_IMAGE" docker compose up -d; else AUDIT_IMAGE="$PREV_IMAGE" docker compose up -d; fi
sleep 45
```

**然后看是不是回到 §5.2 那个问题**：容器启动时 `Projector.catch_up()` 会从零重放，
如果权威里有旧镜像不认识的批次 → 又变成 `projection_fresh=false`。**那一支走 §5.3。**

**注意 `session.db` 不要删**：它是另一个文件（`REVIEW_API_SESSION_DB=/data/db/session.db`），
删了就所有人下线。

### 5.5 只修挂载（R7 专用，**不换镜像**）

**现象**：报告列表有、正文 404，而 `/readyz` 七项全 true。

```bash
. "$B/state/release.env"
# ① 先确认是不是挂载形状的问题
$SUDO docker compose config | grep -c 'source: /opt/momcozy-audit-platform'
```

**期望 `6`。** 得 `5` → `reports-root` 的 bind 丢了（有人回退了 `docker-compose.yml`）。

```bash
# ② 补回来（这一步要改仓库文件；执行单 §S3 给了逐行改法）
cd "$REPO" && git log --oneline -1 -- docker-compose.yml
grep -n 'reports-root' docker-compose.yml || echo "★ compose 里没有 reports-root"
```

没有 → 按执行单 §S3 的两处改法补上（`docker-compose.yml` 加一行挂载、
`Dockerfile` 的 `mkdir` 补一个目录），然后：

```bash
$SUDO stat -c '%a %u:%g %n' "$B/data/reports-root"     # 期望 700 10001:10001
$SUDO docker compose up -d     # 必须重建（up -d 才会重新按新配置建容器）
sleep 45
curl -sS -o /dev/null -w 'report=%{http_code}\n' "$H/static/reports/$RID.md" -H "Cookie: __Host-session=$SID; csrf=$CSRF"
```

**注意**：`up -d` 重建容器会把 `/data` 匿名卷换掉。**如果补挂载之前已经写过报告，
那些报告文件在被换掉的那个匿名卷里，找不回来了** —— 除非你还有备份。
这正是执行单要求「**必须在第一次 `up` 之前**加挂载」的原因。

**丢了怎么办**：报告正文可以由权威重建（`ReportStore.rebuild()` 用同一个 IR 重渲染，
content-addressed 的 `report_id` 会算出同一个）。这条路要逐案跑，属**运维手工**，
不在本方案的自动化范围里 —— 且它不保证逐字节相同（渲染器版本不同就不相同）。

### 5.6 只改配置（不换镜像、不动数据）

有些读数**不需要回滚**，改一个文件/一个环境变量就能好。判断标准：**数据与镜像都没问题**。

| 读数 | 改哪里 | 生效方式 | 注意 |
|---|---|---|---|
| `principal_directory=false` | `$B/config/principals.json`（形状见执行单 §S8.0） | **不用重启**，`PrincipalDirectory._refresh()` 比对 sha256 后自动重载 | `authz_version` 必须是**字符串**（实测：写成数字 → `principal_field: authz_version`） |
| `data_permissions=false` | 宿主机四个目录 `chmod 700` | 下一轮心跳（30 秒） | 不许 `chmod 777` 绕过 —— 那等于删掉这条断言 |
| `projection_fresh` 短暂 false | 什么也不改 | 等 30 秒 | 5 分钟仍 false 才是事故（§R2） |
| `REVIEW_TENANT_ALLOWLIST` 少了一个租户 | `.env.production` | ★ **必须 `up -d`**，`restart` 不重读 `env_file` | 改完 `docker compose config` 核对 |
| `resign` 恒 503 | `.env.production` 加 `REVIEW_REPORT_LINK_SECRET`（≥32 字节） | ★ 同上，`up -d` | 短于 32 字节会**拒绝启动**：`..._too_short（至少 32 字节）` |

## 六 · 没有回滚点时：下线（不是回滚）

`$PREV_IMAGE` 为空（首次上线）→ **没有可回去的状态**。这时唯一的动作是**下线**。

### 下线步骤

```bash
. "$B/state/release.env"
# ① 先做 §三 第 2 步的备份（必须）
# ② 停
$SUDO docker compose stop
# ③ 让反代停止转发（这一步在反代侧做，不在本仓库）
#    把反代里指向 172.20.0.1:18000 的那段 upstream 注释掉并 reload
```

### 对用户怎么解释（照这个说，别改）

> 内容审核工作台今天暂停对外服务。已提交的内容与已产生的结论都保留在系统里，不会丢。
> 恢复时间另行通知。

**为什么这句可以用**：authority 与 reports-root 都只增不改，`stop` 不动数据 ——
所以「已提交的内容与已产生的结论都保留」是**可核对的事实**（`$B/data/authority`
与 `$B/data/reports-root` 原样在盘上）。不要加「尽快恢复」这类时间承诺 —— 你手上没有这个信息。

### 下线之后**不要**做的事

| 不要 | 为什么 |
|---|---|
| `docker compose down` | 保留容器与 `/data` 匿名卷的引用。留着它，将来排查时 `docker inspect` 还能看到现场的挂载形状 |
| `docker image prune` | 那是将来唯一可能的回滚点 |
| 删 `$B/data/*` | — |

## 七 · 回归验证：怎么确认「真的回到上一个状态了」

**判据是「与哪个基线相等」，不是「看起来正常」。** 执行单 §S0 存了 `上线基线-*.txt`，
§S12 存了 `上线完成-*.txt`。回滚之后要拿这两份来比。

### 7.1 存量等价断言（G1–G6）

```bash
. "$B/state/release.env"
BASE=$(ls -t "$B"/state/上线基线-*.txt 2>/dev/null | head -1)
DONE=$(ls -t "$B"/state/上线完成-*.txt 2>/dev/null | head -1)
PREV_CFG=$(grep compose_config_sha256 "$BASE" | cut -d= -f2)
echo "PREV_CFG=$PREV_CFG"
```

| # | 断言 | 命令 | 期望 |
|---|---|---|---|
| **G1** | 镜像回到了 `$PREV_IMAGE` | `$SUDO docker inspect -f '{{.Config.Image}}' momcozy-audit-api` | 逐字等于 `$PREV_IMAGE` |
| **G2** | compose 配置回到了上线前的指纹 | `$SUDO docker compose config \| sha256sum \| cut -d' ' -f1` | ★ 见下面的警告 —— **只在与 `$PREV_CFG` 非空时比** |
| **G3** | 挂载形状回到了 6 条 | `$SUDO docker compose config \| grep -c 'source: /opt/momcozy-audit-platform'` | `6`（不是 5） |
| **G4** | 七项全 true | `curl -sS $H/readyz \| python3 -c 'import json,sys;d=json.load(sys.stdin);print(d["ready"],all(d["checks"].values()))'` | `True True` |
| **G5** | 权威一条不少 | `echo $($SUDO ls $B/data/authority/manifests \| wc -l)` | **等于回滚前 §二② 的「总批次」**（回滚不删数据） |
| **G6** | 报告正文读得出来 | `curl -sS -o /dev/null -w '%{http_code}' "$H/static/reports/$RID.md" -H "Cookie: __Host-session=$SID; csrf=$CSRF"` | **`200`** |

**关于 G2 的警告（不是可选的）**：上线时你**按执行单 §S3 改了 `docker-compose.yml`**
（加 `reports-root` 的挂载）。所以回滚**不应该**把 compose 配置退回改动前的指纹 ——
退回去就等于把 §S3 的修复丢了，下一轮又会出现「报告 404」。
**G2 的正确用法**：只在「上线**没有**改 compose」时与 `$PREV_CFG` 比。
本次上线改了 compose，所以 **G2 的期望是「与 `$PREV_CFG` 不同，且 G3 = 6」**。

> 这是本方案里唯一一处「不能简单地比指纹相等」的地方。写清楚是因为：
> 拿一个过期的期望值去比，会把**正确的回滚**读成失败，然后引发第二次回滚。

### 7.2 业务侧断言（G7–G9）

| # | 断言 | 命令 | 期望 |
|---|---|---|---|
| **G7** | 提交还能建案 | 执行单 §S8.2 的第 ① 条（用一个**新** `submission_id`） | `200` + `case_id` |
| **G8** | 领案 + 结案还能走完 | 执行单 §S8.2 的 ②③ | `200` / `version=3` / `status=closed` |
| **G9** | 新报告正文读得出 | 拿 G8 的新 `report_id` 跑执行单 §S9 的「已登录」那条 | `200 text/markdown`，第一行 `# 内容审查报告` |

**G7–G9 是必须做的** —— G1–G6 全部是「存量对」，它们证明不了「新的写入还能成功」。
一次只回滚了镜像、但把写入路径弄坏的回滚，在 G1–G6 上全绿。

### 7.3 对用户怎么解释（照这个说）

**回滚到上一版**：

> 系统已切回上一版。上一版期间产生的记录都还在（我们的记录只追加、不改写）。
> 今天新版本上线之后、切回之前做过的操作**仍然有效**，不会因为切回而消失。

**从备份恢复（§5.3）**：

> 系统已恢复到一个较早的一致状态。**这个状态之后产生的记录不再保留** ——
> 具体是哪些，我们会在核对后给你一份清单。

**为什么第二句必须说「不再保留」**：备份恢复是真的丢数据（§4.3）。含糊其辞会让对方
以为什么都没丢，然后在某天发现少了一批案件 —— 那时已经没人记得是这次回滚造成的。
