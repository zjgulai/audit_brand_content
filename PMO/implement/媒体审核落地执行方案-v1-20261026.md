## 三 · 票（按依赖顺序，每票带可执行判据）

### M0 · `T-420` 修 `_coverage_ir` 丢 `does_not_cover`（0.5d · 无依赖 · **先做**）

**改** `base/orchestrator.py` 的 `_coverage_ir()`：把 `does_not_cover` 加进重建白名单，
并从 `unit.textification.does_not_cover` 兜底（两边都要，因为 composer 与直接调用两条路）。

**判据**：

1. 新断言 `verify_orchestrator.py` **C16**：
   传一个 `does_not_cover` 非空的 unit → `ir.coverage.does_not_cover` 逐字相等。
2. **变异**：把那一行删掉 → C16 红。
3. 回归：`verify_coverage_composer` 26/26、`verify_orchestrator` 50/50 不变。

**为什么先做**：M1 之后每一张图片都会带 `does_not_cover`，
不修就是**每一张图片都在撒谎**。

### M1 · `T-421` 图片进件可用（宿主 Vision 路线）（2d）

**范围**：让 `POST /api/v1/submissions` 接受 `source.kind=image`，
走现有的 `media.judge_image_file` → `judge_entry` → 权威。

**改**：

- `base/submission_service.py`：`SUPPORTED_SOURCE_KINDS` 加 `image`；
  `_build_unit` 增加 image 分支（调 `media.image_file_row` + `row_to_unit`）；
  `content_type` 允许 `图片`。
- `api/write_api.py`：`SubmissionBody` 允许 image 载体（`uri` 或 `path`）。
- 归属：**「宿主原生」= 本机可用，不是生产可用**。这一票明确标注
  `deployment_scope: host_only`。

**判据**：

1. 端到端：提交一张真实广告图 → `GET /api/v1/cases` 出现案件 → `ir.coverage.modalities_evaluated == ["image"]`。
2. **边界**：`ir.coverage.does_not_cover` 含「画面语义」（依赖 M0）。
3. **反向对照**：`does_not_cover` 被清空的变异 → 红。
4. **不通过的形状**：OCR 失败时 `parse_status=failed` 且 `failure_kind` 落在四类之一，
   **不许产出一个「审过了」的 REVIEW**。
5. 宿主限定：`verify_media_portability` 的宿主原生命中数**仍是 3**（M1 不减少它）。

**⚠️ 这一票让行 118 从 `vacuous_true` 变成 **真违规**。**
所以 `M1` 只能在**内测/本机**存在，不能进生产镜像。这一点必须写在票面上。

### M2 · `T-422` 容器内 OCR 引擎接通（3d · 依赖 M1）

**这是 `ADR-0018` §六.2 的第 2–4 件事**，也是 `T-118-follow` 的实体。

**做**：

1. 镜像构建期装 `rapidocr==3.10.0`（权重随 wheel）→ `Dockerfile` 运行阶段。
2. 把 `DEFAULT_OCR_ENGINE` 从 `host_vision` 改 `rapidocr`。
3. 容器内真跑一张图 + **坐标系对拍**（`ADR-0018` §3.2：y 翻转错会让框上下颠倒而不报错）。
4. 删掉 3 处宿主原生命中（`build_ocr.sh` / `ocr_vision.m`），
   **或在 M1 仍需要它们时保留并说明**。
5. 行 118 从 `vacuous_true` → `passed`。

**判据**：

1. `verify_media_portability` 宿主原生命中 = **0**，且它在**容器内**跑（不是宿主）。
2. 容器内真跑：一张中英文图 → `ocr_file()` 返回非空 `text`，且 `chars > 0`。
3. **坐标系**：与 `ADR-0018` §3.2 的 golden 样本逐点对拍，误差 < 2px。
4. **变异**：去掉 y 翻转 → 坐标系断言红。
5. 行 118 映射：`verify_media_selection` 的 S8 不再红（它挡的是「没做却说 passed」）。

**顺序硬约束**：M2 不做完就打开生产进件 = 生产用宿主 Vision 且行 118 真违规。
**M1 与 M2 必须同时在或同时在不了生产。**

### M3 · `T-423` 图片画面语义（VLM 候选）（4d · 依赖 M2）

**PRD 要求**：`完整画面语义（构图/暗示功效/调性/模特状态）` ——
**部分做，由多模态模型给候选，永远转人工**。

**做**：

1. `base/multimodal_provider.py` 注册一个真实 provider（`SCENE_SEMANTICS`）。
   **口径必须先定**：走内网模型还是外部 API？外部 API 触发数据出境，
   须先过 `ADR-0003` 敏感样本分级。
2. `media.judge_image_file` 增加 `scene_semantics` 分支 → 产 **candidate finding**
   （`produced_by=multimodal`，状态 `candidate`，**不直接 confirmed**）。
3. 报告里画面语义单独成节，措辞必须是「候选，待人工确认」。

**判据**：

1. 一张有暗示功效的图 → 产出一条 `candidate`，`control_code` 落在画面语义族。
2. **它不能自己变成 confirmed**：变异「VLM 结果直接 confirmed」→ 红。
3. `does_not_cover` 里「画面语义」这一项**被移除**（因为这次真评了），
   但「模特状态」仍在 → `coverage_state` 仍是 `partial`。
4. `actual_egress_status` 记录真实出境状态；未授权时**一次都不许调**。

### M4 · `T-424` 视频字幕 + 内嵌文字（5d · 依赖 M2 + 素材）

**这一票的第一个阻塞不是代码，是素材。**

**前置（缺一即 blocked）**：

- 49 条视频广告的**视频文件**（Feishu 素材库 / Google / Meta 后台导出）。
- 一个**转写路线决定**：容器内 `faster-whisper`（`ADR-0018` 已选，权重构建期落盘）
  还是外部服务（出境，须过 ADR-0003）。
- 抽帧方案：`ffmpeg`（需进镜像）还是 AVFoundation（需写 ObjC，且又加宿主原生）。

**做**：

1. 抽帧器：按固定规则抽 N 帧（规则要可复现，不能「抽几帧看运气」）。
2. 关键帧 → 现有 OCR 通道（复用 M2 的引擎）。
3. 音轨 → ASR（`faster-whisper`）→ 带起止时间的片段。
4. 合成 `video` unit：`text_from_media` = 字幕 + 帧内文字，
   `covers` 逐项：字幕 ✅ / 内嵌文字 ✅ / 关键帧 ✅ / 音轨 ✅ / **完整画面语义 ⛔（M5）**。

**判据**（Playbook V1 逐字）：

1. `covers` 五项**逐项声明**，缺一项 → `from_media` 拒绝（已有强制）。
2. `ir.coverage.does_not_cover` 必须含「完整画面语义」→ `coverage_state=partial`。
3. 一个已知内容的视频 → 转写文本包含预期关键词（**需要人工标注真值**）。
4. **反例**：只有一个音轨、画面全黑的视频 → `covers` 里「关键帧」必须是 `not_applicable`，
   不许写成「已评」。

### M5 · `T-425` 视频画面语义 + 音画对齐（4d · 依赖 M3 + M4）

**PRD 要求**：`AV_ALIGNMENT`（字幕说 A、画面演示 B）—— 这是视频审核里最有价值的一条，
也是最难的一条。`multimodal_provider` 的 `MultimodalTask.required_media` 已经有闸门：
**没有 audio 的 provider 不许做 `av_alignment`**（2026-10-21 补的那条，起因是
`glm-5.3-flash` 在 27 家里 audio 是 0 家）。

**判据**：

1. 一个「字幕说 24h 保温、画面演示倒热水冒气」的样本 → 产出 `candidate` finding。
2. **无 audio 的 provider 请求 `av_alignment` → 必须拒**（不是返回空结果）。
3. `coverage_state` 仍是 `partial`（音画对齐永远只是候选）。

## 七 · 这份方案自己的可证伪性

- §1.1 / §1.2 每一行都带 `文件:行`，可逐条复核。
- §1.3 的缺陷可一行复现：

  ```bash
  python3 -c "
  from base.orchestrator import _coverage_ir
  out = _coverage_ir({coverage: {coverage_state:partial,modalities_evaluated:[image],
      rules_version:{version:r},control_points_applied:[H01],
      does_not_cover:[画面语义]}, coverage_state:partial}, {control_points:[H01]}, {})
  print(does_not_cover in out)"   # → False
  ```

- §三的每一票都有「变异 → 红」的判据，不是「跑通即通过」。
- **已知盲区**：本方案**没有执行点**。没有任何检查器会在「M2 没做完就打开生产进件」时变红 ——
  那需要一条断言检查「`SUPPORTED_SOURCE_KINDS` 含 image」与「`DEFAULT_OCR_ENGINE != host_vision`」
  **必须同时成立**。建议把这条写进 `verify_media_selection` 的 S9。**本方案提出它，但没实现它。**
