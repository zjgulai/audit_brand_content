## 一、票的排序原则

按「**不做它，会不会让别的事白做**」排，不按模块排。

- 一张票若**不满足**这个判据，它就不是 P0 —— 哪怕它很容易、很显眼。

- 每张票必须有：**改动路径 / 验证命令 / 期望退出码 / 回滚方式 / owner / 依赖 /
  是否需重启守衡**。缺一项就还是草稿。

## 七、一条被挡下来的建议（记下来，因为它越权了）

合成 agent 的交付里建议「为 `case_watch_tick` 加 launchd 任务或定时器」。
**这条被挡下，没有执行，也没有写进任何票。**

理由（三条，任一条成立就够）：

1. **它是机器级的常驻行为改变**，不是仓库内的一次提交。给它装定时器 = 在这台机器上
   留下一件重启后仍在跑的东西。这需要人明确批准，不是「顺手把文档里的命令跑一遍」。
2. **它违反 AGENTS.md §2.7 的形状**：本项目对「会让机器常驻改变」的动作已有先例 ——
   重启守衡必须走闸门且先问。加一个 launchd 任务比重启守衡更持久，不可能比它更松。
3. **它不在本任务的范围内**。用户要的是盘点、方案、tickets、ADR、执行与避让；
   给守护进程加定时器不属于其中任何一项。

> 同时记一句：PRD v2.0 优化稿 §4.1③（v1.2 无 §4.1）要的「超时升级」确实是缺口（`case_watch.py` 是纯扫描器，
   `tools/case_watch_tick.py` 是手动 CLI，全仓无调度）。**缺口是真的，但补法要人来定** ——
   可以是「接进已有守护进程的心跳」，也可以是「上 launchd」，甚至可以是「先不自动化」。
> 这是一道待决的题，不是一条待执行的命令。
