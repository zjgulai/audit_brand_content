## 〇 · 读法

| 字段 | 含义 |
|---|---|
| **状态** | `draft` 判据未定 / `ready` 可开工 / `in_progress` 在做 / `done` 有复算读数 / `blocked` 缺外部输入 / `waived` 有到期日 |
| **判据** | 必须是**一条能跑的命令 + 一个预期读数**。写「功能正常」等于没写 |

| **`done` 的附加条件** | 必须有一个能让它**再变红**的变异（`tools/mutprobe.py` 的 spec），否则只是「代码写了」 |

### 2026-10-24 · ★ 环境陷阱：FUSE 下陈旧 `.pyc` 让源码改动静默不生效

**这是本轮最难查的一个坑，写在这里因为它会再咬人。**

现象：`api/production_app.py` 的**源码**里，报告路由（842 行）明确在 SPA fallback
（880 行）之前；`inspect.getsourcelines()` 也这么读；但运行时 `app.routes` 里
SPA 排在报告**前面**，于是 `/static/reports/x.md` 被 SPA 吃掉、返回 index.html。
`dis` 反汇编证实：函数字节码里 SPA 的常量偏移 642 < 报告的 672 —— **字节码与源码不一致**。

排查过程（三次错误归因，都记下来）：

1. 先怀疑 Starlette 重排 `include_in_schema=False` 的路由 → 写纯 FastAPI 对照实验，
   **证伪**：先注册者优先，行为正常。
2. 再怀疑源码插入位置错（我确实曾把它插到 `return app` 之后）→ 重排一次，
   `grep -n` 与 `inspect.getsourcelines` 都显示顺序正确，**但运行时仍然反**。
3. 最后才想到缓存：`rm api/__pycache__/production_app.cpython-310.pyc` 之后
   字节码偏移立刻变成 596 < 670，问题消失。

**根因**：这个 FUSE 挂载的 **mtime 不可靠**。`ls -la` 显示 `.pyc` 是「刚刚 21:31」，
Python 据此判定「缓存比源码新」而直接复用 —— 而那份 pyc 其实是**更早**编译的。
本会话早前已记录过两种同族异常（Write/Edit 工具经 FUSE 写出 4092 个 null 字节、
`stat` size 带 +4096 填充），这是第三种：**内容没坏，但时间戳骗过了缓存**。

**处置**：凡改动 `api/` 或 `base/` 下的模块后运行验证器，先
`find . -name "__pycache__" -newer <你改的文件> -o -name "*.pyc" -newer <你改的文件>`
看一眼；现象是「源码明显对、运行行为明显错」时，**第一动作就该是删 pyc**，
而不是像我这样先花三轮去怀疑框架和源码。

**这类陷阱的一般形状**：一个「本该证明改动生效」的读数（这里是通过的验证器），
如果它读的是二手产物（pyc / 冻结 JSON / 内存旧对象），那么**改动不生效时它照样绿**。
判据必须读**一手来源**（源码字节、权威 state），或者读之前先强制失效缓存。
