## 二、根因(已逼近)

只读诊断结果:

| 探测 | 结果 |
|---|---|
| `mount` | `/` 卷 `/dev/disk3s1s1` 是 **apfs, sealed, read-only** |
| `/Users` 卷 | `/dev/disk3s5` 在 `/System/Volumes/Data`,可写,**无 read-only** |
| `xattr -l <file>` | **空**(无 quarantine,无 com.apple.*) |
| `ls -O <file>` | **无 uchg/schg/hidden flag** |
| `df -h` | 803 GB / 84 亿 inode 空闲 —— **不是容量问题** |

**根因假设**:APFS CoW 写时复制在某次 fs 操作下产生了 clone / snapshot,**stat 报告了"未刷新的快照视图"**,真实内容正确但 stat 多 4096。9a 与 6d 都撞,fb 已撞(v1 方案 17,441 B 污染),**说明是环境级问题,与具体写入路径无关**。

## 六、补充:源端也填充,且 `shasum` 也会撒谎(2026-10-17 20:26 实测)

落盘时发现 **`Brand_agent/` 源端的 76 个 caption(.txt)全部是填充态** ——
`stat`/`wc -c` 报 4,343 B,macOS `shasum -a 256` 读出的也是虚高版本,
而 **Python `open().read()` 读到真内容 247 B**(多出来的正好 4,096 B)。

**首版 `cp_scf_smoke.sh` 用 `shasum` 做校验,于是 76 个文件全部误报 `size_mismatch`**
—— 而 Python 逐字节比对 `153/153` 全等。这正是 §2.1.1 那句话的第二个现场:

> 判据必须比**内容**,不能比 `stat`/`shasum` 这类读数 —— 它们正是骗你的东西。

**修法**:`cp_scf_smoke.sh` 的 `sha256_of()` / `size_of()` 全部改用 Python 读真内容;
修正后幂等重跑 153/153 SKIP(sha match)。首轮误报日志原样保留为
`PMO/_logs/cp_cp.round1-falsepositive.jsonl`(不删,留审计轨迹)。
