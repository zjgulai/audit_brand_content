## 〇、先纠正三个前提

委托方提的六个问题各自成立，但它们不是并列的六件事。实测下来，其中三组是**同一个病**：

| 表面 | 实际 |
|---|---|
| Q1「负面样本不一定准」、Q2「品牌 KB 是否完整」 | 都是**知识输入**问题，且都栽在「读错了源 / 量错了对象」 |
| Q4「文件类型工作流是否完整」、Q6「要不要 intent skill」 | 都是**入口路由**问题，前者是接线缺口，后者是决策缺口 |
| Q5「要不要按类型选模型」 | 在样本量不足时是**伪问题**，它的答案被 Q1 的数据否定 |

而 Q3（KB 如何被高效调用）是串起它们的线：**KB 的组织方式决定了它能否被按阶段调用。**

### 三个必须更正的前提

**前提 1：不是「知识库不够全」，是「没有一套库被判定引擎读过」。**

盘上有四套互不引用的制品：

| # | 实体 | 规模 | 谁在消费 |
|---|---|---|---|
| ① | 需求台账 `research/kb/台账-v1.json` | 1160 条 | 只有 `verify_kb.py` 与黄金问题 |
| ② | 可执行规则 `research/governance/skeleton/rules-v1.json` | **26 条**（25 enabled） | 生产 `judge_copy` → `skeleton/judge.py` |
| ③ | 分类基准 `research/governance/rules-mece-migration-v1.json` | 638 条 | 只用于「规则归类评测」，**不进判定** |
| ④ | Momcozy 品牌资产包 `PMO/audit/momcozy-assets/` | 4 份 md + 155 条 manifest | **零消费者** |
| ⑤ | 外部标准 `research/kb/外部标准库-v1.json` | 62 条 / 17 来源 | `judge_evidence.mjs` 检索它，**但该文件零 importer** |

ADR-0015 已把 `rule_judge` 定为唯一判定引擎。所以真实口径是：**判定只吃 26 条规则**，
其余四套库一条判决都影响不了。**继续往库里加内容，不会改善任何一条判决。**

**前提 2：负面样本的问题不是「不一定准」，是「本地在读旧源」。**

详见 §一。一句话：云端 186 条真实记录，本地管线读的是一份 1.3 KB / 5 条的旧 dump。

**前提 3：品牌一致性不是「不完整」，是「不在系统里」。**

详见 §二。四个可重算读数：品牌控制点 **0**、空族 **4**、引擎品牌规则 **0**、七轴 BRAND **10**。

### 2.1 核心事实

| 检查 | 读数 | 复现 |
|---|---|---|
| 品牌控制点 | **0** | `python3 tools/kb_facts.py --check`（`brand_control_points`） |

| 视觉检查器 `check_image()` | 函数体 `pass`（自标「概念代码」） | `brand_consistency_controls.md` |

### 2.2 反直觉的发现：禁用词**不能**直接接进引擎

`brand_semantic_library.md` §1.3 的禁用词块，抬头逐字写着
**「绝对禁止出现在任何 Prompt 中的词」**——它约束的是 **AIGC 生成提示词**。

拿 232 条真实广告文案试跑（`research/governance/skeleton/_data/records.json`）：

| 词 | 命中率 | 真实语境 |
|---|---|---|
| `perfect` | **9.9%** | "Find Your **Perfect** Flow" |
| `must` | **7.8%** | "**Must**-Haves zum Stillen" |
| `hospital` | **6.0%** | "**Hospital**-Grade suction"（已由 T3.3/T7.1 管） |
| `ideal` | **5.6%** | "**ideal** for busy moms" |

直接接进去，品牌规则一上线就会被当噪声关掉。

另有一层口径错位：20 个词里 **17 个在引擎里完全不存在**，3 个（clinical/hospital/perfect）
只作别的规则子串且属医疗合规语境。**「零交集」不是引擎漏了品牌，是两者量的不是同一件事。**

### 2.3 已落地

新增三个缺口，全部可重算（E2 逐键验证）：

- **KB-GAP-20** 品牌控制点为空、引擎规则为 0
- **KB-GAP-21** 禁用词是「提示词约束」，实测 4 词误报 >5%，不得直接作为发布规则源
- **KB-GAP-22** 视觉检查器是概念代码；58 张风格锚定图不存在，且该 verifier 未登记进 §2.1 自证表

### 2.4 推荐方向

品牌判据**不从禁用词来，从 71 条品牌一致性样本的审核意见来**。
但这依赖 Q1 的样本治理（目前约 47 条可用、且未经业务确认）。

## 三、Q3｜知识库如何在不同审核阶段被高效调用

### 3.1 事实：不是效率低，是调用次数为 0

| 检查 | 读数 | 复现 |

### 3.2 按阶段的应然分工

| 阶段 | 该查哪套库 | 今天 |
|---|---|---|
| normalize | 不查（只归一） | ✅ 正确 |
| **judge** | 规则 26 条 + 外部条款 62 条 | ❌ 零调用 |
| **dispose** | 错题本 177 行 + 判例 40+47 | ❌ 零调用 |
| **output** | 措辞表达库（禁用/放行） | ❌ 零调用 |

### 3.3 推荐方案

**第一步只做一件事**：把 `judge_evidence.mjs` 接进判定那一跳，
并让「找不到证据」与「证据为空」在输出里长得不一样。

**关于「高效」，两个反直觉的点**：

1. **BM25 用 trigram 分词，查询词必须 ≥3 字才有真实相关性。**

   所以「提高 topK / 配额」是错的优化方向——应先确认 2 字词怎么处理。
2. **配额读数不可信**：日上限 1000，客户端实测记 41 次，服务端显示 292 次（多调用方共享）。
   在接线之前谈配额优化是空转。

## 五、Q5｜不同类型内容审查是否需要不同的 LLM

### 5.1 结论：现在是伪问题，但不是因为「一个模型够用」

实测：

| 事实 | 读数 |
|---|---|
| 全局单模型 | `deepseek-flash`，无按任务/按类型切换（`tools/agent/config.mjs`） |
| 多模态 VLM | **零实现**（图片走 macOS 本地 OCR，视频走空） |
| 同模型同天两遍 `unstable` | **16.92%**（阈值 2%） |
| gold 经人复核比例 | **3.1%（16/512）** |
| Q1 之后可直接用的样本 | **约 47 条** |
| 群回复延迟中位 | **32.3 秒**，P90 **83.9 秒**（PRD 要求 ≤5 秒） |

**在「同一模型跑两遍有 17% 不一致」的条件下做选型，等于用一把没校准的尺去量两把尺。**

### 5.2 反直觉的真问题

不是「不同类型用不同 LLM」，而是：

> **同一个位置要不要第二个模型做交叉复核？**

因为单模型抖动 16.92%，**换更强的模型不降方差，交叉复核才降方差。**

### 5.3 分层结论

| 层 | 谁来做 | 选型标准 | 现状 |
|---|---|---|---|
| L1 确定性 | `rule_judge`（26 条规则） | 不涉及模型 | ✅ ADR-0015 已定 |
| **L2 语义判定** | 模型 | **稳定性 > 能力** | 16.92% unstable，**不合格** |
| L3 成形/语域 | 模型 | 速度 + 语域 | 中位 32 秒，SLA 要求 5 秒 —— **超 6 倍** |
| L4 多模态 | VLM / ASR | **能力有无**，不是选型 | 零实现 |

**文件类型与模型选型没有因果关系**：图片要的是 OCR/VLM **能力**，视频要的是 ASR/抽帧**能力**，
这两件是「能力是否具备」，不是「模型好坏」。把它们混成「不同文件类型用不同 LLM」，
会做出一个「每个类型配一个模型、每个都不能用」的系统。

## 六、Q6｜intent 与 skill：要不要建

### 6.1 结论：不建新的，先把已有的 37 个救活

| 事实 | 读数 | 复现 |
|---|---|---|
| 有 intent 分类器吗 | **没有** | 四维靠人工填，`submission_router` 只做取值域校验 |
| 路由实际发生在哪 | **LLM 读 skill 的 description 自己匹配** | 提示词层，无真值可验 |
| `skill/` 下有多少 | **37 个，且 `git check-ignore` 对它返回 rc=1 —— 它根本没被忽略** | `git check-ignore -v skill/` → rc=1；`git add -n skill` → 220 个文件 |
| 这些 skill 引用的引擎 | `~/.dsh/Momcozy知识库/` —— **本机不存在** | `ls` → No such file or directory |
| 13 个中文审查 skill 装进运行环境了吗 | **一个都没有** | `ls ~/.dsh/skills/` |
| `agent-skills/`（入库的） | 2 个；`verify_skill.py` 跑「内容合规审查」**9 条里 4 条红** | `python3 tools/verify_skill.py` |

**你想「要不要建 skill」，而盘上已经有 37 个，一个都没在跑。建第 38 个只会让「不能用」的数量变成 38。**

### 6.2 推荐方案

| 步 | 做什么 | 为什么 |
|---|---|---|
| **1. intent 不要做 LLM 分类器** | 四维**先全部落盘**，再用它做路由 | 已经有 4 个正交维度，只是不落盘。再加一个 LLM 分类器，等于在有真值的地方又引入一个无真值的判断 |
| **2. intent 取值域必须是有限枚举** | 建议 5 个值，每个配输入契约 + 输出物 | 自由分类的 intent 无法被断言，等于没有 |
| **3. 37 个 skill 的处置** | 按文件类型的 3 个合并成一个 3 分支；引用仓外引擎的一律改成仓内路径或删除 | 37 个里有大量重复与不可执行项 |
| **4. 先让该入库的能「装上」** | 把自有的搬进 `agent-skills/`，查清装不进 `~/.dsh/skills/` 的原因 | 现在是「文件在、运行时装不上」，比「没有」更糟 |

### 6.3 一个必须先定的口径

★ **2026-10-21 更正（由并行会话 `fa` 实测发现，我原先写错了）**：
`.gitignore:39` 注册的是 **`skills/`（复数）**，而盘上这 37 个在 **`skill/`（单数）**。
`git check-ignore -v skill/` → **rc=1（没被忽略）**；`git add -n skill` → **220 个文件**。
