# 填充态（+4096）—— 环境特性与实测史

> **这是从 `AGENTS.md` §2.1 搬出来的**（2026-09-22）。搬走的原因只有一个：
> `AGENTS.md` 顶到了工作区指令预算（65536 字节），注入版**正在被截掉尾部** ——
> 而尾部是 §2.7 重启闸门。**内容一个字没删，只是换了地方。**
>
> 什么时候来读：要改 §2.1 那段、要新增一种「写盘方式」、或者 `verify_depad.py` 报了非 0。

**关于最后一行**（2026-09-18 实测）：本环境里**用 Python 写出的文件**，`stat` 报的大小会
比真实内容多 **4096 字节**，`read` 工具据此判成 `binary file` —— 正文一个字都读不出来。
内容本身是对的（`open().read()` 与 `shasum -a 256` 一致），是**视图不一致**，但后果
一样严重：**一个读不出来的文档，等于不存在。** 首次全仓库扫出 **332 个**（含本文件）。

**触发条件（实测矩阵，别记错）**：

| 写出方式 | 会不会被填充 |
|---|---|
| **Python**（`python3 -c` / 脚本 / `open(...,'wb')`） | ❌ **会** |
| **`python3 xxx.py > f`（Python 是产出方，重定向是 shell 做的）** | ❌ **会** —— 见下方 2026-09-22 实测 |
| Node（`node -e` / `.mjs`） | ✅ 不会 |
| **shell 自己的命令**（`printf` `cat` `dd` `cp`） | ✅ 不会 |
| **★ `sed` —— `-i` 与 `> f` 两种写法都算**（2026-09-22 实测） | ❌ **会**（只对 `.md` / `.sh`）—— 见下面「三次更正」 |
| DSH 的 `write` / `edit` 工具 | ✅ 不会 |
| **反向对照脚本用 Python 改真实数据**（改坏 → 跑一遍 → 改回来） | ❌ **会** —— 见下方 2026-09-21 实测 |

> ### ★ 2026-09-22 二次更正：上面这张表**漏了一整个维度 —— 后缀**
>
> 这张表读起来是「Python 写谁都会填充」，**这是错的**。实测矩阵（同一 23 字节内容，
> 每格**独立新建目录**、用**外部** `stat -f %z` 读、重复 3 次一致）：
>
> | 写出方式 | `.md` | `.sh` | `.json` `.txt` `.py` `.mjs` `.yml` `.csv` … |
> |---|---|---|---|
> | Python `open().write` | **4119** ❌ | **4119** ❌ | 23 ✅ |
> | shell `printf` / `cp` | 23 ✅ | 23 ✅ | 23 ✅ |
> | Node `writeFileSync` | 23 ✅ | — | 23 ✅ |
>
> 后缀**自成一维，而且只有这两个**：`.markdown` 23 ✅、`.bash` 23 ✅、`.zsh` 23 ✅ ——
> 只有 `.md` / `.sh` 命中。**与大小无关**：50000B 的 `.md` → 54096（+4096），同样 `.json` → 50000。
>
> 独立复现（2026-09-22 本轮，两方各自跑过、读数一致）：
>
> ```bash
> $ cd /tmp && mkdir padprobe && cd padprobe
> $ for ext in md sh json txt py; do python3 -c "open('a.$ext','w',encoding='utf-8').write('x'*23)"; \
>     printf '%-6s python写: stat=%s 真实=%s\n' ".$ext" "$(stat -f %z a.$ext)" "$(python3 -c "print(len(open('a.$ext',encoding='utf-8').read()))")"; done
> .md    python写: stat=4119 真实=23      ← 填充
> .sh    python写: stat=4119 真实=23      ← 填充
> .json  python写: stat=23 真实=23        ← 不填充
> .txt   python写: stat=23 真实=23
> .py    python写: stat=23 真实=23
> ```
>
> **为什么这条更正值得写进来**：本文件此前所有关于填充的事故（`PRD/feishu/*.md`、
> `lark_find.py readdoc > ….md`、`sed -i` 改文档）**恰好全是 `.md`** —— 所以一张缺了后缀
> 这一维的错表**一直没被拆穿**，而它会让下一个人把 `.json` 也当成危险物，
> 或者反过来以为「只要不是 Python 就安全」（Node 写 `.md` 确实安全，但那是因为**进程**，
> 不是因为后缀）。
>
> **代价很轻**：落盘配方不变（照抄下面那三步），只是现在知道**只有 `.md` / `.sh` 需要它**。
> ⚠️ 反过来说：`tools/verify_depad.py` 的 `EXTS` 里有 15 个后缀
> （`.py .mjs .js .cjs .ts .json .yml .yaml .txt .csv .tsv .toml .cfg .ini .html .css`）
> **按本矩阵永远不会命中填充**。那个扫描器**不是错**（它同时看「其他不一致」，
> 且后缀集合将来可能变宽），但**别把「扫出 0 个」当成「我没有填充问题」的证据** ——
> 真正在风险面上的只有 `.md` / `.sh`。

> ⚠️ **判据是「写这个文件的进程是不是 Python」，不是「谁做的重定向」。** 这一格是
> **2026-09-22 补的**，因为我按旧表的读法（「shell 重定向 → 安全」）去重拉上游文档：
>
> ```bash
> python3 tools/lark_find.py readdoc <token> > 'PRD/feishu/美国市场内容治理项目-一页纸计划书.md'

> #   verify_depad.py → 真实 6540B · stat 10636B

>
> 而**这条命令正是 `verify_prd_baseline.py` 红的时候自己打出来的那一条**
> 和 `PRD/feishu/README.md` §五 写的重拉步骤。也就是说：**照着文档做，就会做出一个
> `read` 工具打不开的文件**，而文档当时还写着「用 shell 重定向落盘」是安全的。
> 两处已经改掉了（见 §2.1 末条的「落盘配方」）。

> **「反向对照用 Python 改真实数据」这一格是 2026-09-21 补的，代价是一次真事故**：

> `PRD/feishu/内容审查Agent-PRD-v1.0.md` 改一个字节、跑一遍、再改回来。
> **sha256 完美复原**（`9254f5c7…` 一模一样）、新 verifier 全绿 ——
> 但那个文件已经进了填充态：
>
> ```

> python open().read()        →  14614     ← 索引 size_bytes 也是 14614
> ```
>
> 也就是说：**内容完好，而 `read` 工具已经读不出它了**。抓到它的是 `verify_depad.py`，
> 不是那个我刚写好的、专门看这份文件的新 verifier —— **因为新 verifier 比的是内容，
> 而这类损坏恰好不动内容**（它自己在 docstring 里写着这个盲区）。
>
> 两条规矩：**① 反向对照只在内存里做**（`judge()` 那种纯函数就是为此拆的）；
> **② 非要动盘就用 shell 的 `cp`；★ 不要用 `sed`（见下面「三次更正」）；事后跑一次 `verify_depad.py`。**

> ### ★ 2026-09-22 三次更正：**`sed` 也会填充，而这张表此前正推荐用 `sed` 动盘**
>
> 上面那句规矩的原文是「非要动盘就用 shell 的 `cp` / `sed`，别用 Python」。
> **`sed` 那一半是错的**，而它错的方式正是本文件反复在治的那一种：**照着文档做，
> 就会做出一个 `read` 工具打不开的文件。**
>
> 实测（每格独立新建目录、`printf` 造 21 字节、外部 `stat -f %z` 读、**重复 3 次一致**）：
>
> | 写法 | `.md` | `.sh` | `.json` `.txt` `.py` |
> |---|---|---|---|
> | `sed -i '' 's/x/y/' f.md` | **4117** ❌ | **4117** ❌ | 21 ✅ |
> | `sed 's/x/y/' f.md > out.md`（重定向） | **4117** ❌ | — | — |
> | `cp f.md out.md` | 21 ✅ | — | — |
> | `perl -pi -e 's/x/y/' f.md` | ~~21 ✅~~ **4196 ❌** | — | — |
>
> 后缀那一维与「二次更正」完全一致（**只有 `.md` / `.sh`**）；变的是**写者**那一维 ——
> 所以「判据是写这个文件的进程是不是 Python」**这句话本身也是错的**，
> 它只是恰好解释了此前所有事故。**别用「谁写的」推安全，用上面这张表。**

> ### ★★ 2026-09-22 四次更正：**`perl -pi` 那一格是错的 —— 填充会**延迟**出现，而上面那张表全是「写完立刻量」的**
>
> 上面表里 `perl -pi` 写 `.md` 记的是 **21 ✅（安全）**。**它是错的**，
> 而它错的方式正是本文件反复在治的那一种：**照着文档做，就会做出一个 `read` 打不开的文件。**
>
> 实测（2026-09-22，独立目录、`printf` 造 100 字节、外部 `stat -f %z` 读、**同一批文件隔 150 秒再量一次**）：
>
> | 写法 | 刚写完（T+0） | **150 秒后（T+150）** |
> |---|---|---|
> | `perl -i -pe 's/x/y/' f.md` | **100** ✅ | **4196** ❌（真实 100 + 4096） |
> | `python3 -c "open(...,'w').write(...)"` | **4196** ❌ | **4196** ❌ |
> | `cp src.md dst.md` | 100 ✅ | **100 ✅**（唯一一个两次都干净的） |
>
> **两个结论，缺一个都会再犯一次：**
>
> ① **`perl -pi` 写 `.md` 会填充** —— 与 `sed` 同类，**从「安全」那一栏挪走**。
>    真正安全的只有 **`cp`**、shell 自己的 `printf`/`cat`、Node 的 `writeFileSync`、
>    以及 DSH 的 `write` / `edit` 工具。
>
> ② ★ **更该记的是判据本身：填充是延迟出现的，所以「写完立刻量」这个读法会一致地骗人。**
>    上面那张表（以及本文件历次更正）用的都是「独立目录 + 外部 `stat` + **重复 3 次一致**」——
>    可那 3 次**全是立刻量的**，于是三次一致地读到干净的读数，
>    **一个错误的结论就这样通过了三次重复的检验**。
>    「重复」不构成证据，**只有换一个维度去量才构成** —— 这次的维度是**时间**。
>
> **它是怎么被发现的**：2026-09-22 用 `perl -i -ne` 把 §2.1 的一大段搬去别处，
> 拼完立刻量到 55,563（= 真实值，干净），据此认为安全；几分钟后 `read` 工具报
> **`binary file`**，`verify_depad.py` 报「AGENTS.md 真实 55563B · stat 59659B」。
> **抓到它的不是写那次替换的人，是那个常驻的扫描器** —— 这是它第二次抓同一个人。
>
> **判据（改成这一条）**：**不要用「刚写完的读数」判安全；要么等，要么直接跑**
> `python3 tools/verify_depad.py`。改动 `.md` / `.sh` 一律用 **DSH 的 `edit` / `write` 工具**；
> 非要用 shell，就用 **`cp`**（唯一实测两次都干净的），别用 `sed`，也别用 `perl -i`。
>
> **它是怎么被发现的**：2026-09-22 改 `ADR-0013` 与 `.ua/README.md` 时用
> `sed -i ''` 做了一次替换，紧接着 `read` 工具报 **`binary file`**，
> `verify_depad.py` 报「被填充 2 个 · ADR-0013 真实 134789B · stat 138885B」。
> **抓到它的不是写替换的那个人，是那个常驻的扫描器** —— 这正是 §2.1 表里
> `verify_depad.py` 那一行存在的理由。
>
> **修法**：`python3 tools/verify_depad.py --fix`（cp 往返 + sha256 前后比对 + 自动复验），
> 已跑过、内容一字未变。**改动 `.md` / `.sh` 一律用 DSH 的 `edit` / `write` 工具**，
> 需要批量替换时**先落临时文件再 `cp`**。
> ★ **2026-09-22 更正：这里原先写的是「或用 `perl -pi`（实测安全）」—— 那一半是错的**，
> 见上面「四次更正」：`perl -pi` 写 `.md` 同样会填充，只是**延迟**出现，
> 所以「写完立刻量」看不出来。**唯一两次都干净的是 `cp`。**

所以规矩是：**凡是 Python 脚本生成的文件，写完做一次 `cp → mv` 往返**
（`tools/feishu_index.py` 的 `depad()` 是现成实现，带 sha256 断言内容未变）。
改了任何 Python 生成器，跑一次 `python3 tools/verify_depad.py --fix` 即可 ——
那个检查器修完会自动复验。

**落盘配方（照抄这个，别只照抄「用 shell 重定向」）**：

```bash
python3 <产出者> ... > '<目标文件>'      # ① 落盘（产出者是 Python 就会进填充态，认了）
python3 tools/verify_depad.py --fix      # ② 去填充（cp 往返 + sha256 前后比对 + 自动复验）
python3 tools/verify_depad.py            # ③ 复验：必须「被填充 0 个」，退 0
```

三步都要。少了 ② 的后果是 **`read` 工具打不开这个文件，而 sha256 一切正常** ——
`verify_prd_baseline.py` 会全绿，因为它比的是内容（见下表上面那段本身的自述盲区）。

## ★★ 2026-10-22 定论：触发者是 **`Write` 工具**，不是 `Edit`

> **本节取代下面那一段「未复现」的记录。** 那段是我写错的：我用 `Edit` 做探针，
> 而 `Edit` 在**文件原本干净**时**不会**填充 —— 所以 27 次复现 0 次。
> 方向错了，不是现象不存在。

### 判据：哪种写法 × 哪种后缀

| 写入方式 | `.md` | `.ts` | `.txt` | `.json` |
|---|---|---|---|---|
| **`Write` 工具** | **+4096** ❌ | **+4096** ❌ | **+4096** ❌ | 0 ✅ |
| `Edit` 工具（文件原本干净） | 0 ✅ | 0 ✅ | 0 ✅ | 0 ✅ |
| `Edit` 工具（文件**已**被填充） | 保持 +4096 | 保持 +4096 | — | — |
| shell `printf` / `cp` | 0 ✅ | 0 ✅ | 0 ✅ | 0 ✅ |
| Python `open().write` | **+4096** ❌ | 0 ✅ | 0 ✅ | 0 ✅ |

**与文件大小无关**：20 字节就触发。

### 最小复现（自己跑一遍，30 秒）

```bash
# ① 用 Write 工具新建一个 20 字节的 .ts（内容随意，如 export const a = 1;）
# ② 立刻量：
stat -f %z x.ts                                    # → 4116
python3 -c "import os;print(os.path.getsize('x.ts'))"   # → 20
python3 -c "print(len(open('x.ts',encoding='utf-8').read()))"  # → 20
```

**实测报告（2026-10-22，本条作者亲验）**：`stat = 4116` / `getsize = 20` / `read = 20`，差 **4096**。

> ★ **`os.path.getsize` 与 `stat` 会给出两个不同的数** —— 这正是 §2.4.8
> 「同一个量有两个口径，而只有一个被看见」在本文件里的第二次出现
> （第一次是 `verify_agents_budget.py` 的 real vs stat）。
> `wc -c` 走的是前者，`stat -f %z` 走后者。

### 为什么旧矩阵一直没抓到

旧矩阵只测过 **Python `open().write`** / shell / Node `writeFileSync`，
**「哪个工具写的」这一维从来没被加进去**。而 `Write` 是 agent 最常用的写法之一 ——
所以这 4096 一直在发生，只是被记成了「后缀 `.md`/`.sh` 的问题」。

### 真实事故对照（都对得上）

| 文件 | 后缀 | 怎么写的 | 后果 |
|---|---|---|---|
| `tools/verify_shouheng_ops.py` | `.py` | Edit（在已被填充的文件上） | `verify_depad` 报出 |
| `web/vite.config.ts` | `.ts` | Edit（在已被填充的文件上） | `tsc` 报 `TS1490 File appears to be binary` |
| `web/src/api/auth-headers.ts` | `.ts` | **Write（新建）** | 第一次被 Node 当二进制读 |
| `web/src/data/taxonomyInternal.ts` | `.ts` | **Write（新建）** | 同上 |

**判据不变**：不管是哪个工具写的，**落盘后跑 `python3 tools/verify_depad.py` 是唯一可靠的判据** ——
它比 stat 与真实内容，不关心是谁写的。
