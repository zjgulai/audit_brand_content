## 三、P1：知识库

### 3.1 图片 / 视频完全不走知识库

`agent.mjs:464-469` 在媒体分支提前给 `reply` 赋值，而工具循环条件是 `reply === null`：

```js
if (mediaAuditGot && (mediaAuditGot.four_dim_audit || mediaAuditGot.judgment)) {
  reply = formatDirectAuditCardReply({ mediaGot: mediaAuditGot });
  ...
}
for (let iter = 0; reply === null && iter < config.llm.maxToolIters; iter++) { ... }
```

而 `feishu.mjs:571` 判 `image_judged` 时**必然**带 `judgment`，所以这条分支几乎必走。
→ **图片/视频审查一次 `judge_copy` 都不调，一次检索都不发。**

这与 `persona.mjs` 那条「每条内容合规结论必须能指到 `evidence_chain`」自相矛盾。

### 3.2 只传 URL / 文档链接时，检索拿到的是空串

`tools.mjs:709-710`：

```js
const body = String(text ?? '');
if (!body.trim() && !url && !doc_token && !fields) return { error: '文案为空，无法判定' };
```

带 `url` / `doc_token` 时不报错，但 `body` 仍是空串；`tools.mjs:746` 传给
`gatherEvidence(body, r, …)` 的**也是空串**，不是 python 侧抓取到的正文。
引擎零命中（`catch_all`）时 `probePhrases('')` 返回空 → `status:'untested'` → **一次检索都没发**。

### 3.3 `200 + 非 JSON` 被读成「库里没有」 —— 假阴性

`kb_client.mjs:383-390`：

```js
let body = null;
try { body = JSON.parse(txt); } catch { /* 非 JSON（ngrok 页面等） */ }
absorbQuota(body);
if (res.ok) return body ?? { _raw: txt.slice(0, 500) };
```

ngrok 隧道过期返回 **HTTP 200 + HTML 拦截页**（注释里明确提到这个场景）时：
`body===null` → `{_raw}` 不抛错 → `retrieve()` 里 `d?.hits` 为 undefined → `hits=[]` →
`judge_evidence.mjs:494` 判 `status = basis==='engine_matched' ? 'none' : 'probe_empty'`。

**`none` 且 `basis==='engine_matched'` 时 `may_assert_kb_absence=true`** ——
模型被授权对用户说「知识库里查不到」。而这次一次检索都没真的查成。

这恰好是 `judge_evidence.mjs:39-40` 自称「整套设计要防的唯一一件事」（假阴性结论）没防住的那条缝。

对比：网络层失败（`:370`）与 429（`:395`）都处理正确了，**唯独「200 但不是 JSON」这一支没有**。

### 3.4 其他

  注释写「不跨次缓存」，**没有实现**。知识库更新后守衡仍用旧缓存。

## 四、P1：超时与阻塞

### 4.1 `run_readonly_command` 的 15 秒超时形同虚设

`tools.mjs:586-590` 设 `timeout: budget`（默认 15_000），实测**有一条跑了 975 秒**：

```
[+166020.064s]    🔧 工具: run_readonly_command(975098ms) → ...
[+166020.070s]    💬 回复 1975 字，耗时 997632ms
```

**根因**：Node 的 `execFile` 超时只结束**直接子进程**，杀不掉抱着 stdout 的孙进程；
`promisify(execFile)` 等的是管道关闭，所以 promise 永不 resolve。

### 4.2 无总预算

| 层 | 超时 | 依据 |
|---|---|---|
| `llm.chat` 单次 | 120s | `llm.mjs:166` |
| `llm.chat` 尝试次数 | 4（1 + 3 重试） | `llm.mjs:216` |
| 工具循环轮数 | 6 | `config.mjs:149` |
| 知识库单请求 | 20s × 4 次 | `kb_client.mjs:347` |
| `judge_copy` 子进程 | 30s | `tools.mjs:734` |
| 图片判定子进程 | 180s | `image_judgment.mjs:29` |
| **单条消息总预算** | **无** | — |

理论最坏：6 轮 × 4 次 × 120s ≈ **48 分钟**；知识库 7 次串行 × 84.8s ≈ **10 分钟**，
且 `gatherEvidence` 在 `execFile` 之后单独 await，不受那 30s 约束。

### 4.3 无 in-process watchdog

`daemon-run.json` 心跳（`ws_daemon.mjs:638-640`）+ `verify_shouheng_ops.py:198` 的
`BEAT_MAX_MIN=12` **只报红，不重启**。`unhandledRejection` / `uncaughtException`
只计数并自报，**进程继续跑**（`ws_daemon.mjs:586-595, 619-620`），所以 launchd 也不会被触发。
