# 守衡 · 群历史发送者身份丢失修复记录

**日期**：2026-09-16
**发现方式**：守衡自己在群里指出来的 —— 它没有等我发现。
**性质**：信息在中间层被丢弃，导致守衡**自信地宣称自己做不到**。
**关联**：与《守衡-时间基准修复记录.md》同一轮排查；两份记录可对照看。

---

## 一、现象

时间缺陷修好后，用户问「我什么时候跟你说过话」。守衡的回答里有这段：

> **错误二，更严重：我把那两条消息说成是你发的，但我没有依据。**
> 群历史里用户消息只标「用户」两个字，不带 open_id。我根本分辨不出哪条是谁发的。
> 上一条我是顺着「这个群只有 3 个人」猜的，却写成了确定的事实。
>
> **所以你的问题，老实回答：我不知道。**

它同时纠正了自己**上一条**的问题（把用户消息说成是提问者发的，其实是猜的），
并主动提出「我不知道这是设计如此还是解析没做完，得看代码——你要我去查一下吗？」

### 这里有两件事值得分开说

1. **守衡做对了两件事**：一是拒绝在没依据时给确定答案；二是把自己前一条的**越权断言**主动撤回。
   这个"撤回"没人要求它做。
2. **它给出的理由是错的**：数据一直都在，是我们中间丢的。

---

## 二、根因：数据在工具层被丢掉

直接用接口验证（真接口，非推测）：

```
2026-09-16T04:39  type=user  id=ou_e5ada0b1c7a023c44e407c60ee8bd91b  @_user_1 我什么时候跟你说过话
2026-09-16T04:26  type=user  id=ou_e5ada0b1c7a023c44e407c60ee8bd91b  @_user_1 我是谁？
2026-09-16T03:12  type=user  id=ou_e5ada0b1c7a023c44e407c60ee8bd91b  @_user_1 你是谁？你能做什么？
...
用户消息：有 id 5 条 / id 为空 0 条
```

**群历史接口是返回 `sender.id` 的**，每条都有值。

但 `tools.mjs` 把它丢掉了：

```js
from: m.senderType === 'app' ? '守衡(你自己)' : (m.senderType === 'user' ? '用户' : m.senderType),
//                                                                  ↑ 这里直接写死
```

`feishu.mjs` 明明已经解析出了 `senderId`，工具层却把它压成了无差别的字面量「用户」。

### 这类缺陷为什么最难发现

守衡说「我分辨不出哪条是谁发的」，**这个说法在它那一侧完全成立** ——
它看到的就是 7 条一模一样的「用户」。它给出的结论听上去合理、措辞诚实、还主动声明了不确定性。

**唯一的破绽是它那句「我不知道这是设计如此还是解析没做完」** ——
它把自己的信息盲区正确地区分成了两种可能，并指出需要看代码才能判断。
这是一个我没想到它会有的动作：**它知道自己的"不知道"有不同类型。**

## 三、修复

### 1. `feishu.mjs`：新增 `resolveSender()`，把身份判定集中成一处

| 情况 | 输出 |
|---|---|
| `app` 消息 | `守衡(你自己)` |
| `user` + 成员表命中 | **真实姓名**（如「周健」） |
| `user` + 成员表未命中 | `用户(ou_xxx)` —— **退化为 open_id，不是「用户」** |
| `user` + 接口未给身份 | `用户(接口未返回发送者身份)` —— 如实说明 |

**原则：宁可显示 open_id，也不显示无法区分人的占位符。**
即使解析不出姓名，也要留下可比对的身份 —— 让「这两条是不是同一个人」仍然可判。

### 2. `listRecentMessages()` 自己保证成员表可用

```js
const map = memberMap ?? buildSenderMap((await listMembers(chatId))?.members);
```

### 3. 我在修这一步时**又犯了一次同样的错**

上面那行 `.members` 是错的 —— `listMembers()` 返回的是**数组**，不是 `{ members: [...] }`。

后果：`map` 永远为空 → 姓名永远解析不出 → 全部退化成 `用户(ou_…)`。
而 `?? ` 和 `?.` 让这次失败**完全没有声音**。

这正好是本次事故的同一个病根：**防御性地取错形状，会静默降级成"功能不存在"。**
改成显式判断并告警：

```js
const members = await listMembers(chatId);
if (!Array.isArray(members)) {
  console.warn(`[feishu] listMembers 返回的不是数组（${typeof members}），本次无法解析发送者姓名`);
  map = new Map();
} else { map = buildSenderMap(members); }
```

### 4. `tools.mjs`：透传 `from` 与 `senderOpenId`

工具描述也改成「每条带『谁发的』和北京时间」——
**工具的能力要写在描述里，否则模型不知道自己有这个能力，就不会去用。**

```
2026-09-15 22:53:45 星期二  [周健]        @_user_1 要脸吗？几次了
2026-09-16 10:57:08 星期三  [周健]        @_user_1 你是谁？
2026-09-16 11:12:47 星期三  [周健]        @_user_1 你是谁？你能做什么？
2026-09-16 12:26:20 星期三  [周健]        @_user_1 我是谁？
2026-09-16 12:39:35 星期三  [周健]        @_user_1 我什么时候跟你说过话
2026-09-16 12:39:52 星期三  [守衡(你自己)]
```

**全部用户消息都解析出了姓名**，包括守衡此前列为"不知道是谁"的那 6 条。

### 回归测试（第 8 组，4 条）

| 测试 | 防的是什么 |
|---|---|
| app / user 消息正确归类、不同成员可区分 | 基本解析正确性 |
| 成员表为空时退化为 open_id，**断言 `!/^用户$/`** | 直接锁死本次事故：占位符不许回来 |
| 接口未给身份时如实标注 | 防"假装成普通用户" |
| 真实群里用户消息必须解析出成员姓名 | 端到端验证成员表真的接上了 |

**全套：35 通过 / 0 失败**（含第 7 组时间基准 4 条）。

## 五、必须更正前一份记录里的一处说法

《守衡-时间基准修复记录.md》第一节我写过：

> 守衡答对了身份，但顺口报了两个错的时间。

**「答对了身份」这个说法不完整。** 我验证的是**当次消息**的身份解析
（`current_chat_info` 返回 `you_are_talking_to: 周健`，这条是对的），
但**没有验证历史消息的身份** —— 而那正是它出错的地方。

它把六条历史消息归给了提问者，**依据是"群里只有 3 个人"的推测**。
我当时读到「我读群历史能看到」就往下走了，没有追问「它凭什么知道那是同一个人」。

**教训**：一条回复里"对的部分"会掩护"错的部分"。
我核了它说对的（身份），没核它没说错的（历史归属）——而后者才是它的真实盲区。

## 六、遗留

1. **真实群聊复测已完成**（2026-09-16 12:42）：守衡第二轮**正确复述了发送者**，
   把 8 条消息全部归到「周健」名下，并主动撤回上一轮那个「我不知道」的结论。

   > ⚠️ **但这条验证本身有瑕疵，必须记下来**：
   > 那条 779 字的回复**结尾被截断了**（停在「这条也算那份记录里「未做」），
   > 原因是 `max_tokens=1600` 被思维链吃光、且 `finishReason` 从未被检查。
   > 也就是说：**我在用一条被截断的回复，去证明修复成功。**
   > 发送者部分（表格与前半段）确实是对的，结论仍成立；
   > 但「回复完整」这一层当时没有任何人验过 —— 包括我。
   > 详见 `守衡-回复截断修复记录.md`。

2. **群历史上限 50 条**：`listRecentMessages` 不分页，本群当前 40 条未触及该上限。
   群消息超过 50 条后，守衡将看不到更早的历史，而它不会知道自己漏了。
   **这是一个已知的、尚未处理的盲区。**
   （附带核实：工具层取回的正文与原始接口**逐字相同**（均 779 字），
   截断发生在模型生成阶段，不在读取阶段 —— 不要把它记成读取侧的问题。）
3. 最后一条用户消息（22:53「要脸吗？几次了」）出现在本群，早于当前这一轮。
   从时间线看它指向更早的失败尝试。我**没有**向用户核实这句话的来由，
   仅记录它存在，以及现在它有了明确的发送者和时间。
