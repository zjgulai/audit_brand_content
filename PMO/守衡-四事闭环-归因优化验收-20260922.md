## §1 Q1 · 一次断网，为什么连「断在哪一层」都答不出来

### 1.1 归因（三条，各自有读数）

**A1 「断在哪一层」不可分辨 —— 因为 `cause` 链根本没被读。**

现在证据只有群历史里那一条（逐字，`node -e` 读群历史取得）：

```
2026-09-22 15:32:16  守衡(你自己)
我这边调用模型失败了，没法回答这个问题。

失败原因：网络错误: fetch failed

（这是我的问题，不是你的输入有问题。）
```

这串字出自 `tools/agent/agent.mjs:341`，`${llmError}` 来自 `tools/agent/llm.mjs:83`：

```js
return { ok: false, error: `${isTimeout ? '请求超时' : '网络错误'}: ${e?.message ?? e}` };
```

而 Node 里 `fetch()` 失败抛的是一句**最外层**的话：`TypeError: fetch failed`。
真正的层在 `e.cause` 里，可能是：

| `cause.code` | 实际断在哪 |
|---|---|
| `ENOTFOUND` / `EAI_AGAIN` | DNS |
| `ECONNREFUSED` / `ECONNRESET` / `ETIMEDOUT` | TCP |
| `CERT_HAS_EXPIRED` / `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | TLS |
| `UND_ERR_CONNECT_TIMEOUT` / `UND_ERR_HEADERS_TIMEOUT` | undici 自己的超时 |

**这句 `网络错误: fetch failed` 是同一句话，覆盖了上表全部四种情况。** 于是 15:29 那次
到底是我这台的 DNS、还是出口、还是对端，今天**已经无法回答**（日志不留、cause 不存）。

> 区分它的代价：一次断网事故里，「DNS 挂了」和「对端 502」对下一步动作的含义完全不同 ——
> 前者要查本机/路由器，后者要查服务商状态页。而我们现在只有一句两者共用的话。

**A2 四次尝试的过程全部丢掉。**

`llm.mjs:58-85` 的循环是 `for (attempt = 0; attempt <= 3; attempt++)`，但 `catch` 分支**只在
`attempt === 3` 时返回**，前三次的 `e` 直接出了作用域。所以：

* 「这次一共失败了几次」只能从 `stats.calls` 反推（它在内存里，重启即归零）；
* 「第一次和最后一次的错是不是同一个」无从得知 —— 而**错在变**（比如 DNS 好了、TLS 又挂）
  恰恰是最有信息量的形态。

**A3 失败不留痕：那句话在盘上只存在于群里。**

三段复现，读数如下（本轮实跑）：

```bash
grep -c "调用模型失败" PMO/logs/ws_outbound.jsonl          # → 0   外发台账里没有
grep -o "调用模型失败" PMO/shouheng-state/sessions/*.json | wc -l   # → 0   会话记忆里没有
grep -c "网络错误\|fetch failed" PMO/logs/ws_daemon.log    # → 0   守护日志里没有
```

三个 0 各有各的原因，都得记住：

| 位置 | 为什么是 0 |
|---|---|
| 外发台账 | 台账 2026-09-22 15:3x 才有；15:32 那条是**旧代码**（PID 76921）发的 |
| 会话记忆 | `agent.mjs` 的 `llmError` 分支（`:340-342`）**直接 return，没有 `mem.append`** —— 正常回复分支有，失败分支没有 |
| 守护日志 | 日志的时间戳是 `stamp() = [+秒数]`（`ws_daemon.mjs:38`），**只有相对秒、没有绝对时刻**；而回复正文也只记长度（`💬 回复 N 字`），不记内容 |

后果是一条比「查不到」更坏的：**守衡自己事后想不起这件事**。如果她 15:40 问「你刚才为什么说答不了」，
守衡的会话里只有她 15:29 的问题和 15:42 的正常答复，中间那次失败**在它的记忆里不存在**。

**A4 没有补发：答不上，就是永远答不上。**

她问的是「有没有拉材料 + 给个链接」——一个**有确定答案**的问题（材料在盘上，链接今天补上了）。
但链路上没有任何东西记得「我欠她一条回答」：`verify_pending.py` 管的是**对方的承诺与我方的提问**，
不管**我方的失败**。于是 15:32 到 15:42 这十分钟里，缺口只存在于人的脑子里。

## §2 Q2 · 「它还在跑吗」为什么答不了，以及为什么 `ps` 本来就不该是判据

### 2.1 归因

本轮实测（`python3 tools/verify_shouheng_ops.py`，退 **2**）：

```
✅ E2  日志里出现过启动横幅 22 次
✅ E3  日志 1 分钟前还在写（心跳每 5 分钟一次 → 没卡死）
⚠ E1  跑不了 ps（PermissionError: [Errno 1] Operation not permitted: 'ps'）
       → 进程是否在跑【未测】，不等于「没在跑」。
⚠ 1 项未测 —— 这不是通过（退 2，与 §2.4.2 同口径）
```

**这个「未测」是真话，但它暴露的是选型错误，不是环境限制。** 两条：

1. **`ps` 是旁观者，launchd 才是持有者。** 这个进程的生命周期由
   `~/Library/LaunchAgents/com.shouheng.lark.plist` 的 `KeepAlive{SuccessfulExit:false}` 决定
   （`AGENTS.md` §2.7）。问「它还在跑吗」，最权威的答案是**launchd 怎么认为**，
   `ps` 只是碰巧能看到同一件事的另一只眼睛 —— 而这只眼睛在本沙箱里被蒙上了。
2. **「活着」有两层，原先只证了第二层。** ①进程存在；②事件循环还在转（没卡死）。
   E2/E3 用日志旁证了 ②，但 ① 一直是未测 —— 而 ① 恰恰是 §2.7 里「重启窗口会吃消息」
   那件事的前提。

**本轮实测：三条不需要 `ps` 的读数都拿得到。**

```bash
PID=$(pgrep -f 'ws_daemon\.mjs' | head -1)            # → 3971（pgrep 不被沙箱拦）
launchctl print gui/501/com.shouheng.lark | grep -E "state|pid"
#   state = running
#   pid = 3971
python3 -c "import os;os.kill(3971,0);print('存活探测 OK')"   # → 存活探测 OK
```

也就是说：**E1 今天本可以是绿的**，是判据自己把它按住了。

### 2.2 方案（E1 拆成四个子读数 + 一个纯函数）

| 判据 | 读什么 | 三态怎么分 |
|---|---|---|
| **E1a** | `launchctl print gui/501/com.shouheng.lark` → 解析 `state` 与 `pid` | 读到 `state=running` + pid → 继续；读到 `state` 非 running → **红**；命令本身跑不了 → **未测** |
| **E1b** | `pgrep -f ws_daemon\.mjs` 的输出**必须包含** E1a 那个 pid | 不包含 → **红**（「活着的那个 pid 不是守护进程」这件事必须报出来，不能被一句「进程在跑」盖住） |
| **E1c** | `os.kill(pid, 0)` | 抛 `ESRCH` → **红**（进程没了）；抛 `EPERM` → 说明权限受限但**进程存在**，算 ✅ 并在说明里写出来；其他异常 → **未测** |
| **E1d** | 新增 `PMO/shouheng-state/daemon-run.json`：daemon 启动时写一次 `{pid, startedAt, startedAtBj, lastBeatAt, events, handled, failed, llmCalls}`，**心跳每 5 分钟刷新 `lastBeatAt`** | 「运行了多久」= `now - startedAt`（**取代原先靠 `ps -o etime` 的那一格**）；`now - lastBeatAt > 12 分钟` → **红（卡死）**；文件不存在 → **未测** |
| **E1e** | 纯函数 `judge_liveness(pid_launchd, pgrep_out, kill_result, run_state, now)` → `(verdict, why)` | 好让反向对照**直接喂坏样本**，不碰真进程 |
| **E1f** | E1 的每一格都必须与 E2/E3 的日志旁证**说得通**（pid 变了而日志没有新一轮启动横幅 → 红） | 防「读到的活着」与「日志说的活着」是两件事 |

同时**保留** E2/E3（它们是独立来源的旁证），并新增：E1d 的状态文件由 daemon 写，
所以**它本身也要一条断言**：写它的那一行必须在 `ws_daemon.mjs` 里真的存在（§2.4：不许只留一个文件名）。

### 2.3 判据与执行点

## §4 Q4 · 62 条「逐字」：判据是齐的，缺的是跑；而且再跑一遍会毁掉上一遍的物证

### 4.1 归因

本轮实测（`python3 tools/verify_external.py --offline`，退 **2**）：

```
逐条核对：命中 62（已钉快照（今日 0 个来源被真抓 —— 上游本次未测）：
          可见正文 38 / 仅内嵌数据块 18；仓内钉住证据 6）  失配 0  不可复核 0  —— 共 62 条
⚠️  今日 0 个来源被真抓（--offline，或全部走了已钉快照）—— 未测：逐字命中只在快照上验过，
   没在上游验过。退 2，不是通过。
```

**先记它做对的地方**：这个检查器**已经**把「未测」与「通过」分开了（这正是 §2.4.2 记的那次
「第一次运行就把没测报成通过」的病，在同一个仓库的第二个检查器里被修掉了）。
所以 Q4 缺的不是判据，是**跑**，以及两个结构性的洞：

**A1 那 62 条命中里，有 6 条不是「今天的上游」。**
明细段逐条点名：`EXT-019…022`（S7，Meta）、`EXT-023/024`（S8，Meta）命中的是
`research/governance/_evidence/R1/meta-ad-*.md@2026-09-15` —— **仓内 09-15 的钉住件**，
因为「Meta 本机无匿名取法」（`KB-GAP-10`）。

> 所以「62 条逐字命中」这句话必须拆成两句才准确：
> **56 条**对今天 12:25 抓的快照命中；**6 条**只对 09-15 的钉住件命中，**上游最多证到 09-15**。
> 这是一次 §2.4.1 的自检（「这句话比我的输入大吗？」）—— 不拆开就是在替那 6 条多说 7 天。

**A2 跑第二遍会覆盖第一遍的物证。**

```python
# tools/verify_external.py:358
with open(path, "w", encoding="utf-8") as f:   # ← S{n}.txt 原地覆盖
```

今天 17 个快照文件的 mtime 全是 `12:25`，抬头写着 `fetched: 2026-09-22T12:25:16`。
**它们就是「12:25 那轮 62/0」这条结论的唯一物证。** 下一次 live 重抓会把它们原地改写 ——
于是：

* 上一轮**抓到的原文形态**没了（只剩这一轮）；
* 「上游改过没有」**在盘上永远问不出来** —— 因为没有任何东西在两轮之间做比较。

这正是 §2.4.2 那个病的第三个实例：**基线漂移有执行点（`prd_baseline.mjs`），外部标准库没有。**
PRD 那篇文改了会有人知道；而 FDA / Amazon / Meta 的政策页改了，**我们不会知道** ——
而这 62 条引文是要给法务当依据用的。

**A3 谁在上游改版后跑它？** 现在只有人手动。没有任何触发者。
