# 守衡 · 群回复卡片模版与语域规程（落地记录）

> 起因：「守衡在群内的回复格式很糟糕」。
> 本文记录这一轮做了什么、实测读数是什么、**哪些还没做**。
> 日期：2026-09-18。自证：`node tools/verify_cards.mjs`（253 项全过）。

---

## 一 · 先量一遍「糟糕」是什么意思

拿守衡真实发出去的 8 条群回复（`PMO/shouheng-state/sessions/chat_oc_*.json`）逐条量：

| 量什么 | 读数 |
|---|---|
| 回复长度 | 423 / 434 / 704 / 779 / 793 / 1045 / 1057 / 1312 —— **中位 786 字** |
| 含数据表的比例 | **42%**，而发送走 `msg_type=text` —— 表格在群里是一堆 `\|` |
| 同一条里重复的「边界声明」 | 最多 **5 条**，约占全文三分之一 |
| 「等于没答」的回复 | **2 条** |
| 工具调用耗时 | 最长一次 125 秒 / 14 次工具调用 / 输出 2675 字 |

两条「等于没答」的原文：

1. **434 字**：`我查了几轮还是没能得出可靠结论…我试过 list_files、list_files、list_files…`
   —— 连列 27 次工具名，把内部记录当内容发进了群。
2. **1312 字**：开头第一句是 `先处理我上一条：那条是故障输出，等于没答。`
   —— 守衡自己在群里更正上一条故障。

所以「格式糟糕」不是用词问题，是三件结构问题：**结论被埋、边界复读、内部记录外泄。**

## 二 · 卡片能力：不读文档，发真卡测

文档检索当时不可用，而卡片 JSON 里**任何一个元素不被接受，整张卡会被服务端整体拒绝**
（不是降级、不是忽略，是丢）。所以做法是：**一张卡只测一件事**，
往测试群发 10 张探针卡，每张的成败就是那个元素的读数。

读数落在 `PMO/logs/card_probe.jsonl`：

| 探针 | 元素 | 结果 |
|---|---|---|
| 1/7 | `header` + `subtitle` + `template` | ✅ 通过 |
| 2/7 | `markdown`（含标题/列表/引用/代码块） | ✅ 通过 |
| 3/7 | **原生 `table`** | ✅ 通过 |
| 4/7 | `column_set` 分栏 | ✅ 通过 |
| 5/7 | `collapsible_panel` 折叠 | ✅ 通过 |
| 6/7 | `note` 注脚 | ❌ **V2 已移除** |
| 7/7 | `action` 按钮容器 | ❌ **V2 已移除** |
| 8/10 | `column_set` + 灰底（替代注脚） | ✅ 通过 |
| 9/10 | 注脚退化成一行 markdown | ✅ 通过 |
| 10/10 | **按钮裸放 elements** | ✅ 通过 |

**两个否掉的元素本来是打算用在「边界声明」和「按钮」上的。**
按文档印象直接写进模版的话，表现是**守衡的回复凭空消失**——不是降级。

另外实测：官方的卡片校验入口 `cardkit.v1.card.create` 被权限挡住
（code=99991672，缺 `cardkit:card:write`），而且它的权限检查在 schema 校验**之前**，
所以拿不到 schema 诊断。**离线验卡这条路目前是堵的**，只能靠本地白名单 + 发群实测。

## 三 · 做了什么

### 3.1 十一个卡片类型（`tools/reply-cards/`）

| 文件 | 作用 |
|---|---|
| `cards.mjs` | 十一个构造器 + 子元素（表格/分栏/折叠/按钮/字段排）+ **V2 白名单校验器** |
| `registry.mjs` | 类型登记表（判据 / 字段 / 样例）+ 七条去 AI 味内容检查 + 降级渲染 |
| `index.mjs` | 公共出口 + `sendCard()`（卡片 → 纯文本降级链） |
| `cli.mjs` | `list` / `show` / `sample` / `validate` / `lint` / `send`（**发送必须带 `--confirm`**） |
| `contract.md` | 完整契约：白名单、配色语义、十一个类型的判据与反例、降级规则 |
| `README.md` | **给业务看的名片** |

十一个类型：`query-answer` · `data-table` · `correction` · `capability-boundary` ·
`find-nothing` · `cannot-read` · `receipt` · `turn-diff` · `evidence` · `alert` · `decision`

**类型不是拍脑袋列的，是从真实答错的那几条反推的：**

| 真实事件 | 对应的类型 |
|---|---|
| 连列 27 次工具名发进群 | `alert` + 「内部记录只进折叠区」 |
| 「10 次」→「11 次」，对方连问四遍 | `turn-diff`（今天没有任何机制处理这个） |
| 说「找不到」但不说找了哪里 | `find-nothing` 强制填 `paths` |
| 把「内容没有了」和「内容在我范围外」混成一句「我读不了」 | `cannot-read` 把三类拆开 |
| 把「**解析还没接上**」说成「我读不到 / 没权限」（附件类） | `cannot-read` 单列附件一条：**能力边界 ≠ 权限问题**。说错会让对方去申请权限、去找文件主人，全是白跑。★ 旧版这里写的是「按规矩不取 / 飞书禁止下载」—— 那条红线已于 **2026-10-17 废止**，下载是允许的；文本类附件会被抽取，图片/音视频/Office 的解析还没接上 |
| 边界声明重复五遍 | 「一个格，一行，没有就不写」 |

### 3.2 三条硬约束（写进模版，不靠模型自觉）

1. **结论在第一个格子里**（`verdict`，≤60 字）
2. **边界只写一行，没有就不写**（`boundary`，≤90 字）
3. **内部记录只进折叠区**（`collapsible_panel`）

### 3.3 语域规程（`agent-skills/守衡语域/SKILL.md`）

把 `Nanako0129/sepia` 的核心能力内化成项目级 skill，**只取能落到守衡身上的部分**：

- sepia 的**分层**思路（架构 → 语篇 → 表面）。对守衡翻译成：**结构 → 位置 → 用词**。
  主要药在结构层，不是词表层。
- sepia 的**职业文类检查表**（10 条）→ 挑出能字符串判真假的 6 条。
- sepia 的**中文标定**（HC3-Chinese，6,586 人 vs 6,586 ChatGPT）→ 具体数字与原产地都保留：
  连词密度 0.013 vs 0.036、语气词密度 0.016 vs 0.003、句长标准差 9.248 vs 6.729。
- sepia 的**反过度纠正规则** → 「单个『此外』不是 AI 味」「三顿号并列是规范」
  「句长本身方向相反，不是判据」。这一条最重要，抄词表不抄它就会把文本改成另一种机器腔。

**没有抄的**：小说叙事层（StoryScope 那 30 个特征）、英文词表、模型指纹表 —— 对群回复不适用。

## 四 · 一条诚实的读数（这轮最值钱的发现）

把七条内容级检查跑在守衡**真实发出去的 8 条群回复**上（5,544 字）：

| 命中 | 次数 |
|---|---|
| `internalLeak` 内部记录泄漏 | **1 次**（那条 434 字故障输出） |
| `hedgeStack` 模糊限定堆叠 | 8 次 |
| `chatbotResidue` / `conclusionTail` / `padding` / `connectorStack` / `ruleOfThree` | **0 次** |

**守衡说话不像 AI —— 它没有客服腔、没有结尾总结段、没有双音节填充、没有连词串珠。**

那句 434 字的故障输出，**通过了除 `internalLeak` 以外的全部检查**。
说明「读起来像不像 AI」和「该不该出现在群里」不是同一把尺，必须分开测。

**结论：模版是主药，去 AI 味的词表是安全网。**
如果这一轮只做了词表，守衡的回复会一字不改。

## 五 · 接入发送路径（2026-09-18 第二轮）

第一轮只做了模版，守衡仍发纯文本。第二轮把它接上了。

### 5.1 一个发现：三条硬约束此前没有执行点

写接入层时先 grep 了一遍 `VERDICT_MAX` / `BOUNDARY_MAX` / `MAX_SECTIONS`：

```
$ grep -rn "VERDICT_MAX\|BOUNDARY_MAX\|MAX_SECTIONS" tools/
tools/reply-cards/cards.mjs:70:export const VERDICT_MAX = 60;
tools/reply-cards/cards.mjs:72:export const BOUNDARY_MAX = 90;
tools/reply-cards/cards.mjs:74:export const MAX_SECTIONS = 3;
```

**只有定义行，没有任何引用。** 也就是「结论 ≤60 字」此前是一句**注释** ——
说明第一轮把约束**写进文档**、却没有**装到代码上**。
新层 `envelope.mjs` 是它们现在唯一的执行点，自证 J1 段会断言这件事。

### 5.2 模型不写卡片 JSON，只写「卡片块」

```
先正常写你的回答。

[[card:receipt]]
{"title":"已收到","verdict":"收到。"}
```

分界很清楚：**白名单、schema 2.0、V2 移除了什么，属于代码；「这条回答该长什么样」属于模型。**
让模型直接写 V2 JSON，等于每次推理都赌一遍白名单，赌输的代价是回复消失。

`envelope.mjs` 四件事：切块 → 执行上限 → 搬走内部记录 → 失败降级。

### 5.3 实测读数（不是设计意图）

**全链路、带工具**（`agent.handleMessage` 合成事件，两问）：

| 问 | 用了工具 | 得到 | 校验 | 公开格 |
|---|---|---|---|---|
| 本群里我发过的消息有几条？列明细 | `recent_messages` → `now`（17.2s） | 🃏 `data-table`（markdown · table(11行)） | ✅ | 干净 |
| 你能干什么？ | `recent_messages`（8.3s） | 🃏 `capability-boundary`（column_set 3栏 · 折叠区收起） | ✅ | 干净 |

**无工具、八问形态选择**（8 次调用）：卡片 **3** / 纯文本 **5** / 内部标记残留 **0** / 硬失败 **0**。

形态选择是**对的**：「在吗？」「收到我上一条了吗？」走纯文本，
「你能干什么」「找一下 PB-009」走卡片。**没有出现「每句话都套卡」**。

> 这两组读数的差别要说清楚：无工具那 8 次里，有些问本该先查再答
> （如「这个仓库有多少个 Python 脚本」），模型没有工具可调，只能凭印象答，
> 所以那组的**内容质量不作数** —— 只用来量「形态选择」和「有没有泄漏」。

### 5.4 11 张样例卡已发进测试群

```
$ node tools/reply-cards/cli.mjs send-all --confirm
✅ 11/11  mode=card
```

回读（`im.message.get`）：`msg_type=interactive`、`deleted=false`、标题完整。
**但这仍是「服务端收下了」，不是「你看着对不对」。**
回读的 body 是一段兜底占位（`请升级至最新版本客户端，以查看内容`），
所以**渲染效果只能由人眼确认**——这一步没有替代品。

### 5.5 一条被自证逮住的真缺口

第一版 `envelope.mjs` 在 JSON 解析失败时 `return null`，
于是 `[[card:receipt]]\n{"title":` 这种截断输出会**连标记带半截 JSON 原样发进群**。

自证 J2 段逮住了它（13 个用例逐条断言「文本里不许有 `[[card:`」）。
修法：只要看见标记就把整块剥干净；剥完没剩下可读的话，就发一句
「我这次没能把回答组织成卡片（<原因>）」。

**为什么这条必须机器断言**：标记被卡片渲染藏进折叠区时肉眼看不出，
但对方点开就看见了。这是全部约束里唯一一条人眼不可靠的。

### 5.6 发送兜底只能有一处

踩到的坑：`reply-cards/index.mjs` 的 `sendCard` 自带兜底，`agent/feishu.mjs`
新加的 `replyCard` 如果再兜一次，两处叠加的表现是**同一个回答在群里出现两次**。
所以 `feishu.replyCard()` 只尝试一次、失败如实返回，兜底统一由 `ws_daemon.replyTo` 做。
自证 L2 段会拦。

降级链：

```
有卡片 → reply 卡 ──失败──→ reply 纯文本（同一条引用里）
没有卡 → reply 纯文本 ──失败──→ sendMarkdown 补发
```

**卡片失败后也走 `reply` 而不是新发一条**：新发会断开引用关系，
群里看到的是一段悬空的话。**守住引用比守住卡片重要。**

### 5.7 生效状态

代码已改，但 **launchd 下的守衡进程（PID 81379）跑的还是旧代码** ——
Node 不热重载。要生效必须重启；重启时机由 Owner 定，不擅自中断在线的服务。
