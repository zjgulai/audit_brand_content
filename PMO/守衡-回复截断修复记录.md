# 守衡 · 回复截断修复记录

- **日期**：2026-09-16
- **发现者**：不是监控，是**逐字读了一条飞书消息的结尾**
- **严重度**：高。回答被腰斩，但日志记「✓ 已发送」，用户无从知道它是断的

---

## 一、事故现象

12:42:09 那条 779 字的回复，末尾是：

```
**怎么变好的：** 刚查时工具已经修好并重启了（记录里的 daemon PID 77963），
我重新读了一次历史，发送者字段就出来了。这条也算那份记录里「未做
```

停在「未做」。没有句号，没有收尾，**但守护进程日志写的是**：

```
[+ 79.666s]    💬 回复 779 字，耗时 14683ms
[+ 80.429s]    ✓ 已发送 om_x100b6595acd790a0b22876aeea4c8cb [reply]
```

用户看到一条断掉的回答，而他没有任何线索能判断这是「说完了」还是「断了」。

**这类故障的特征：发送成功率 100%，信息完整率不是。** 只盯错误码的监控永远发现不了它。

---

## 二、排查过程（三次假设，前两次都是错的）

### 假设 1：飞书 text 消息有长度上限 —— **错**

因为首条回复数是 779，很像撞到 800 的墙。实测：

| 发出 | 落库 | 一致 |
|---|---|---|
| 1000 字 | 1000 字 | ✅ |
| 2000 字 | 2000 字 | ✅ |
| 4000 字 | 4000 字 | ✅ |
| 8000 字 | 8000 字 | ✅ |

飞书能收 8000 字。**不是发送侧截的。**

> 附带教训：第一版探针脚本自己有 bug —— 它拿「落库长度」和「想要的长度」比，
> 但生成器可能多出 1 个字，于是 5000 字的探针报「落库 5001」。
> **超出请求长度的结果本身就证明没有截断**，而我差点把它读成截断证据。
> 正确的比法是：发出内容 vs 落库内容是否逐字相同。

### 假设 2：发送封装函数在切分时丢了后半段 —— **错**

`feishu.mjs` 有 `chunkText`，怀疑它切完只发了第一块，或静默丢了后续。
查下来切分逻辑没有丢块问题。

### 假设 3：模型输出被 `max_tokens` 截断，且 `finishReason` 被无视 —— **对**

```
llm.mjs:67   return { ok: true, message: choice.message, finishReason: choice.finish_reason, ... }
                                                                  ↑ 这个字段被返回了
agent.mjs    grep "finishReason"  →  0 个匹配
```

**`finishReason` 一路返回上来，然后被彻底丢弃。**

直接实测：

| max_tokens | finish | reasoning 用了 | 正文 | 结果 |
|---|---|---|---|---|
| 1600 | `length` | **1600（吃光）** | **0 字** | 全被思维链吃掉 |
| 4000 | `length` | **4000（吃光）** | **0 字** | 同上 |
| 8000 | `length` | 4775 | 5645 字 | 正文有了，仍被切 |

**关键机制：DeepSeek 的 `max_tokens` 同时覆盖思维链和正文**
（`usage.completion_tokens_details.reasoning_tokens`）。

配置值 `SHOUHENG_MAX_TOKENS` 默认 **1600**。这个数字看着像「够写 1600 字」，
实际上是「思维链 + 正文合计 1600 token」。思维链先写，写完就没正文了。

所以真正发生的是：**模型把全部额度花在思考上，然后正文被腰斩。**

## 三、修复

### 1. `tools/agent/truncate.mjs`（新增）—— 截断守卫

- `detectTruncation()`：**`finish_reason` 是权威信号，优先于任何文本启发式**。
  - `length` / `content_filter` / 其他非 `stop`、非 `tool_calls` 值 → 判为截断
  - 文本启发式兜底（防止 `finishReason` 哪天丢了就完全失明）：
    空回复、悬空标点、**未闭合的中文句子**、长文本无句末标点
- `annotateTruncation()`：把半句话回退到**最后一个完整句子**，再附明确说明
- 不误伤的边界：短回复（「好」「收到」）不报、表格/列表结尾不报、
  拉丁字母/数字/URL 结尾不报

### 2. `tools/agent/agent.mjs` —— 拿到回复就检查

```js
const cut = detectTruncation({ finishReason: r.finishReason, text: reply });
if (cut.cut) { /* 打警告 + 附加截断说明 */ }
```

返回值新增 `meta.truncated`，供守护进程与测试断言。

### 3. `tools/agent/config.mjs` —— 额度给足

`maxTokens` 默认 `1600` → `8000`（约 5 倍，覆盖实测 1918–4775 的思维链开销）。

### 4. 可见性（两个都不能少）

- `ws_daemon.mjs`：截断时日志打 `⚠️ 回复被长度上限截断`
- 启动横幅新增 `maxTokens` 一行 —— **这个值原本无处可见，正是它 1600 摆了那么久没人发现**

```
maxTurns                 = 24
maxTokens                = 8000     ← 新增
```

## 四、验证

### 单元/回归（第 9 组，5 条）

```
✅ finish_reason=length 必须被判为截断（哪怕正文看着像正常结尾）
✅ 回归：事故原文必须被拦住
✅ 悬空标点与空回复都要拦住
✅ 被截断的回复必须带出可见的截断标记，且不留在半句话上
✅ 配置的 maxTokens 必须留得下思维链（实测 1600 会被吃光）
```

其中「回归：事故原文必须被拦住」**逐字用了事故原文的结尾**，并且额外断言
**即使 `finishReason` 丢失也必须拦住** —— 不允许只依赖单一信号。

### 实盘（真模型，非 mock）

修复后同样的长回答请求：

```
当前 maxTokens = 8000
finishReason = stop        ← 正常收尾，不再是 length
reasoning    = 1918 tok    ← 思维链吃得下了
正文         = 826 字，以句号结尾
截断判定     = false
```

**那 1918 个 reasoning token，在旧的 1600 额度下会把整个预算吃光 —— 这就是腰斩的成因。**

### 全套

`通过 40 / 失败 0`（修复前 35，新增第 9 组 5 条）

### 现场清理

验证过程往群里发过 8 条探针消息（`[1][2][3]...` 和纯数字串），**已全部撤回**。
群里只留了 2 条「This message was recalled」占位 —— 那是正常撤回的痕迹。

## 五、这次暴露的更深问题：写代码的人和查代码的人是同一个

**上一轮我说过一句话：**

> 「守衡把话说到了『该去看代码』这一步，然后停住了，没去看。」

**这一轮我自己完全一样。** 我拿到 `finishReason` 的返回值、知道它存在、
甚至在自己的代码里看到了 `llm.mjs:67` 把它 return 出来 —— 然后没检查它。

三个 bug，同一个形状：

| # | bug | 表现 | 为什么没被发现 |
|---|---|---|---|
| 1 | `from: '用户'` 硬编码 | 身份信息丢失 | 输出看着「正常」，只是没有信息 |
| 2 | `?.members` 取错形状 | 姓名解析全挂 | 静默退化成 open_id，无报错 |
| 3 | `finishReason` 不检查 | 回复被腰斩 | 日志记「✓ 已发送」 |

**共同点：都是「静默降级」——代码没有崩，它只是安静地少做了该做的事。**

而且三次都是**读输出才发现的**，不是看错误码发现的。

**由此得到一条可执行的规矩：**
> 凡是「拿到了某个字段却不使用」，都要当成潜在缺陷对待，而不是当成正常写法。
> `finishReason`、`usage`、`sender.id`、`error.code` —— 这些字段存在是有原因的。

## 六、仍未解决

- **群历史只取 50 条、不分页**：本群当前 40 条还没碰到，但超过 50 条后守衡会
  看不到更早的历史，**而它不会知道自己漏了**。这是同一个「静默降级」家族的下一个成员。
- **截断后没有自动重试**：目前是「告知用户 + 建议接着说」，没有自动续写。
  更彻底的做法是检测到 `finish_reason=length` 时自动用更大额度重试一次。
