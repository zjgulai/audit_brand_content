# 守衡 · 时间基准缺陷修复记录

**日期**：2026-09-16
**触发场景**：用户在飞书群问「我是谁？」，守衡答对了身份，但顺口报了两个错的时间。
**性质**：静默型正确性缺陷 —— 不报错、不崩溃、日志干净，只是守衡对外说了错的时间。

---

## 一、现象

守衡在群里的原话（已从飞书接口取回原文，非日志推测）：

> 你在 **22:57** 和 **23:12** 各 @ 过我一次（问「你是谁？」「你是谁？你能做什么？」）

对照群历史接口返回的真实时间：

| 事件 | 真实时间（北京） | 守衡所说 | 偏差 |
|---|---|---|---|
| 用户第 1 次 @ | 2026-09-16 **10:57:08** | 22:57 | **+12h** |
| 用户第 2 次 @ | 2026-09-16 **11:12:47** | 23:12 | **+12h** |

两次偏差方向一致、幅度一致 —— 是**确定性错误**，不是随机口误。

> **⚠ 本节原有的一处说法已更正。**
> 这里原本写「守衡答对了身份，但顺口报了两个错的时间」——**「答对了身份」不完整**。
> 我只验证了**当次消息**的身份解析（那部分确实对），没有验证**历史消息**的归属，
> 而它当时正把六条历史消息**靠推测**归给了提问者。
> 详见《守衡-发送者身份修复记录.md》第五节。


---

## 二、根因

**同一轮对话里并存两种时间基准，逼模型自己做第二次换算。**

| 来源 | 修改前输出 | 基准 |
|---|---|---|
| `now` 工具 | `2026-09-16 12:28:35 星期三` | 北京 |
| `recent_messages` 工具 | `2026-09-16T03:12:48.165Z` | **UTC** |

`feishu.mjs:241` 写的是：

```js
at: new Date(Number(it.create_time)).toISOString(),   // ← UTC
```

模型拿到 `02:57:08.626Z` 后想换算成"本地时间"，结果算出了 `22:57`。

### 必须说清楚的一点：机制我并没有完全查实

我原以为是「模型把 UTC 减/加 8 小时」，但实测**不成立**：

- `02:57 UTC` 加 8 小时 = `10:57`（正确），减 8 = 前一天 `18:57`，都不是 `22:57`
- `22:57 - 02:57 = +20h`，`23:12 - 11:12 = +12h`（按北京时间算）

我逐一试过所有可能的格式化配置（`hour12:true/false`、`hourCycle:h11/h12`、`en-CA/en-US/zh-CN`），
**没有任何一个会产生 22:57** —— 全部正确输出 `10:57`。

所以：**错误是模型在换算环节产生的，不是我的格式化代码产生的**；但"为什么是 +12 而不是 ±8"我没有查实，
不再编一个听起来合理的解释。

这不影响修复的正确性 —— 修复的方向恰恰是**消除换算这一步**，而不是去猜模型怎么算错的。

## 三、修复

### 1. 新建 `tools/agent/timefmt.mjs`（时间的唯一定义处）

```js
beijingDateTime(input) → { beijing_time, date, time, weekday, timezone, iso, unix }
beijingString(input)   → '2026-09-16 12:26:20 星期三'
```

要点：

- 用 `formatToParts` 逐字段取值（`now` 工具原本的做法），跨 Node/ICU 构建结果确定
- 归一 `hour='24'` → `'00'`：`en-CA` + `hour12:false` 在午夜可能给出 `24`，不处理就会出现「24:05」
- 时区偏移用 `timeZoneName:'longOffset'` **实算**，不硬编码 `+8` —— 将来时区规则若变化会自己暴露，而不是继续悄悄算错
- 时间戳损坏时**返回 `(时间未知：...)` 而不抛异常**：一条坏消息不该把局部数据问题升级成功能故障

### 2. 两处调用点统一

- `feishu.mjs:241`：`toISOString()` → `beijingString(...)`
- `tools.mjs` `now`：删掉内联实现，改调 `beijingDateTime()`

**两份实现只要存在，就一定会再次漂移** —— 所以 `now` 的内联版本也一并删掉，不留副本。

## 四、验证

### 真实数据验证（真接口，非模拟）

修复后 `recent_messages` 对**同一个群**的输出：

```
2026-09-16 11:00:39 星期三   [守衡(你自己)]
2026-09-16 11:04:45 星期三   [守衡(你自己)]
2026-09-16 11:12:47 星期三   [用户]          ← 原被说成 23:12
2026-09-16 11:12:56 星期三   [守衡(你自己)]
2026-09-16 12:26:20 星期三   [用户]
2026-09-16 12:26:28 星期三   [守衡(你自己)]
```

全部为北京时间，与真实发送时刻一致，且 `now` 工具输出同一基准。

### 回归测试（第 7 组，4 条）

| 测试 | 防的是什么 |
|---|---|
| 输出不带 UTC 标识（`Z` / `T`） | 直接锁死这次的事故形态：**只要出现 UTC 的样子就算失败** |
| `now` 与 timefmt 同源、偏移实算 | 防两份实现再次漂移；顺带验证时区标注 |
| 午夜不产生 `24:xx` | 防 `hour='24'` 归一遗漏 |
| 时间戳损坏不抛异常 | 防局部数据问题升级成工具故障 |

**全套：31 通过 / 0 失败**（`tools/` 与仓库根目录两种运行位置各验一次）。

## 五、顺带修掉的一个测试自身缺陷

第 6 组的子进程启动写的是相对路径：

```js
"await import('./tools/agent/agent.mjs')"   // ← 相对 cwd
```

后果：这个测试**只在仓库根目录下运行才成立**。在 `tools/` 里运行会报
`ERR_MODULE_NOT_FOUND`（找不到 `tools/tools/agent/agent.mjs`），
而失败信息指向"产品起不来"，与真实原因（测试路径写错）完全无关 ——
**又是一个会把人带偏的失败信息**。

改为 `new URL('./agent/agent.mjs', import.meta.url).href`（绝对路径）：
子进程加载哪个文件是测试的固有属性，不该取决于你从哪敲的命令。

## 六、遗留与未验证

1. **模型端的 +12h 机制未查实**（见第二节）。修复消除了换算步骤，但没有解释模型当时具体怎么算的。
2. **未做真实群聊复测**：修复已加载（daemon 重启，PID 75474，长连接在线），
   但"守衡在新一轮对话里报时间正确"尚未实测 —— 需要群里再问一次才能确认端到端。
   我验证的是**工具输出层**（真接口、真数据），不是**模型复述层**。
3. 守衡仍会看到 `iso` 字段（UTC）。这是**有意保留**的：用于核对同一瞬间，且带 `Z` 标识不会引起歧义。
   若后续发现模型仍被它误导，可考虑移除。
