# 守衡 · 智能体架构说明

> 面向对象：未来接手这份代码的人，以及未来忘了细节的我。
> 最后更新：2026-09-16

## 一、守衡是什么

守衡是运行在飞书里的智能体。它的存在形态是**一个常驻进程**，通过飞书长连接接收事件、
调用大模型推理、必要时调用工具，然后把结果发回群里或私聊。

它不是「飞书机器人壳子 + 关键词回复」，也不是「把消息转发给某个 API」。
它是一个有记忆、有工具、能承认自己不知道的对话式智能体。

## 二、目录结构

```
tools/
├── ws_daemon.mjs          常驻入口：长连接 + 事件分发 + 发送回复 + 生命周期
├── run_shouheng.sh        启动器：运行时自动探测（给 launchd 用）
├── com.shouheng.lark.plist  launchd 守护配置
├── test_agent.mjs         离线测试套件（19 项，--live 可跑真实 LLM）
├── send_once.mjs          向群里发一条消息（运维用）
└── agent/
    ├── config.mjs         配置与凭据装载
    ├── persona.mjs        人格与系统提示
    ├── feishu.mjs         飞书能力封装（mention 还原 / markdown 转换 / 收发）
    ├── memory.mjs         记忆层（按会话隔离 + 压缩）
    ├── llm.mjs            DeepSeek 调用层（重试 / 用量统计）
    ├── tools.mjs          工具层（9 个只读工具）
    └── agent.mjs          推理内核（去重 / 串行 / 工具循环）
```

数据落在 `PMO/shouheng-state/`（记忆）与 `PMO/logs/`（日志、原始事件）。

## 三、一条消息的完整生命周期

```
飞书群 ──长连接──▶ ws_daemon.onMessage
                      │ ① 原始事件落盘 ws_events.jsonl
                      ▼
                   agent.handleMessage
                      │ ② 去重（seen-messages.json）
                      │ ③ mention 还原：@_user_1 → @李倩怡
                      │ ④ 群聊里没 @ 就跳过（避免刷屏）
                      │ ⑤ 取会话锁，载入该会话记忆
                      ▼
                   工具循环（最多 6 轮）
                      │ ⑥ 问 LLM，带 9 个工具的 schema
                      │ ⑦ LLM 要调工具 → 执行 → 结果回灌 → 再问
                      │ ⑧ LLM 给出最终答复 → 退出循环
                      ▼
                   ⑨ 压缩历史（超阈值时）→ 存盘
                      ▼
                   feishu.replyMarkdown ──▶ 飞书群
```

## 四、五个必须理解的设计决定

### 1. 为什么按「会话」隔离记忆
每个群一个文件、每个人私聊一个文件。群里的上下文不该泄漏到私聊，反之亦然。
键名：群聊 `chat_<chatId>`，私聊 `dm_<openId>`。

### 2. 为什么同一会话要串行（锁）
群里两条消息几乎同时到达时，两个处理流会同时读写同一个记忆文件，
后写的会覆盖先写的 —— 表现为「守衡忘了我刚说的话」。
`agent.mjs` 里的 `withLock` 按会话排队，代价是并发度降低，换来记忆不丢。

### 3. 为什么压缩切点这么讲究
LLM 的记忆不是纯文本流水，里面夹着 `assistant(tool_calls)` 和它对应的 `tool` 结果。
OpenAI 兼容协议要求这两者**必须成对且相邻**，从中间切开会让下一次请求直接被 API 拒绝（400）。

所以 `memory.compact()`：
- **按轮次定位切点**，不按条数（一轮可能含 1 个 user + 1 个 assistant + N 个 tool）
- 切点必须落在某个 `user` 消息之前
- 数够 `keepTurns` 轮后**原地停住**，让 cut 指向边界下标

> ⚠️ 这里踩过一个真实的坑：初版写成「数够了就 break，但 cut 仍在递减」，
> 结果 cut 一路退到 0 附近，把几乎整段历史都当待压缩内容，等于每轮只保留最后一条。
> 这个 bug 不会立刻报错，只会让守衡「记性突然变差」，极难发现。已在 `test_agent.mjs`
> 中固化为回归测试。

### 4. 为什么工具只有只读的
一个会主动往群里发消息、改文档的智能体，权限必须一次一点给。
现在 9 个工具全是只读（查时间、查群信息、查成员、读聊天记录、读工作区文件、跑只读命令）。
写类工具等业务场景明确后再逐个放开。

`run_readonly_command` 是唯一碰 shell 的工具，做了两层防护：
命令前缀白名单 + 拒绝管道/重定向/命令替换等元字符。

### 5. 为什么启动器要探测运行时
这台机器上**没有独立安装 node** —— PATH 里唯一的 node 是 Kimi.app 内置的运行时。
拿它做守护服务意味着「Kimi 一升级，守衡就死」。

`run_shouheng.sh` 按稳定性排序探测：环境变量指定 → 系统/包管理器 → nvm/fnm →
DSH Desktop 内置 Electron（以 `ELECTRON_RUN_AS_NODE=1` 当 node 用）→ PATH。
实测 DSH Electron 方案无窗口、无子进程、SIGTERM 干净退出，可用。

**将来若装了独立 node，无需改任何配置**，启动器会自动优先选它。

## 五、进程托管（launchd）

```bash
# 安装
cp tools/com.shouheng.lark.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/com.shouheng.lark.plist

# 查看状态
launchctl list | grep shouheng

# 重启（改完代码后用）
launchctl kickstart -k gui/$(id -u)/com.shouheng.lark

# 停用
launchctl unload -w ~/Library/LaunchAgents/com.shouheng.lark.plist
```

- `RunAtLoad` + `KeepAlive`：登录自启、崩溃自愈（实测 `kill -9` 后 3 秒内拉起）
- `ThrottleInterval=10`：防止疯狂重启刷爆日志
- 日志自轮转：daemon 每 5 分钟检查一次，超过 20MB 切成 `.log.1`

## 六、已知限制（诚实清单）

| 限制 | 说明 |
|---|---|
| 只处理文本消息 | 图片/文件/语音会明确回复「我读不了」，不装懂 |
| 长连接事件不排队 | 进程重启的几秒内到达的消息会丢。飞书长连接无落盘重放机制 |
| 记忆是单机的 | 存在本地文件，换机器不迁移 |
| 无写类工具 | 不能主动发消息、改文档、管群 |
| 无卡片交互 | `card.action.trigger` 已注册但只记日志，等业务场景 |
| 单进程 | 没有多实例/负载均衡，一台机器一份 |

## 七、怎么改

**改人格** → `agent/persona.mjs`
**加工具** → `agent/tools.mjs`，`register(名字, { scope, schema, run })`
**换模型** → 环境变量 `SHOUHENG_LLM_MODEL`（`deepseek-flash` / `deepseek-v4-pro`）
**调记忆长度** → `SHOUHENG_MAX_TURNS`
**限定只在某些群工作** → `SHOUHENG_ALLOWED_CHATS=oc_xxx,oc_yyy`

改完必须做两件事：
1. `node test_agent.mjs` —— 别让回归溜过去
2. `launchctl kickstart -k gui/$(id -u)/com.shouheng.lark` —— 让新代码生效
