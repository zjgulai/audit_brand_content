# 守衡 · 「查不到谁在说话」修复记录

**时间**：2026-09-16
**触发**：周健在群「内容治理-守衡Agent-测试」@守衡问「你是谁？你能做什么？」
**结论**：守衡回话了（704 字，7.97 秒），但**说不出对方叫什么**，只能输出 open_id。

---

## 一、真因

`getUserName(openId)` 走的是**通讯录单查**接口
（`contact.v3.user.get`，method_id 6925375841992245275），
而本应用未开通 `contact:contact.base:readonly` 等任一权限，返回：

```
code = 99991672
msg  = Access denied. One of the following scopes is required:
       [contact:contact.base:readonly, contact:contact.access_as_app,
        contact:contact.readonly, contact:contact.readonly_as_app]
```

**关键**：原实现是 `try { ... } catch { return null }` —— 把原因整个吃掉了。
上层只能看到「查不到」，于是把它解释成「此人不在可见范围」，
排查方向被带偏到「是不是权限范围没配」，而真实原因是**接口根本无权调用**。

## 二、为什么群成员接口是通的

同一时刻实测：

| 接口 | 结果 |
|---|---|
| `contact/v3/users/:id`（通讯录） | ❌ 99991672 缺权限 |
| `im/v1/chats/:chat_id/members`（群成员） | ✅ 正常，**且直接返回姓名** |
| `im/v1/chats/:chat_id`（群信息） | ✅ 正常 |

群成员列表用的是 `im:chat` 那套权限，本应用早就开通了。
**这是接口选错，不是权限缺失** —— 不需要去申请任何新权限。

实测结果（就是这一条定案的）：

```
· '刘华丽'  open_id=ou_af95e2a43871579692afbb25a529e77e
· '李倩怡'  open_id=ou_3eef3cc3fbecfdafa98cd74e608522c3
· '周健'    open_id=ou_e5ada0b1c7a023c44e407c60ee8bd91b   ← 就是发消息的人
```

## 三、改动

`getUserName(openId, chatId?)` 改成两级降级链：

1. **群成员列表**（已有权限）—— 带 `chatId` 时优先走这条，结果按群缓存
2. **通讯录单查**（需额外权限）—— 兜底，失败时如实返回原因

返回值从 `string | null` 改为 `{ name, source, reason }`：

| 字段 | 含义 |
|---|---|
| `source` | `chat_member` / `contact` / `none` —— 名字从哪条路来的 |
| `reason` | 失败原因原文（含错误码），不再静默 |

调用方同步更新：
- `agent.mjs` 传入 `chatId`，并把 `senderNameKnown` / `senderNameUnavailableReason`
  一并注入模型上下文 —— 查不到时明确告诉模型「这是占位符，别编称呼」
- `tools.mjs` 的 `lookup_user` 返回 `source`，失败时带 `hint: 不要猜测或编造称呼`

## 五、顺带挖出的三个同类缺陷

修这一个 bug 时做了全局排查（`grep "catch {}"`），又找到三处**静默吞异常**：

### 1. 去重表落盘失败被完全吞掉（`agent.mjs` flushSeen）

原为 `catch {}`，且**失败时仍清 `seenDirty`**。
后果：这个表决定「重启后是否重复回话」，它一旦静默丢失，
表现是守衡对同一条消息回两次，而日志里没有任何线索。

修复：失败不清 `seenDirty`（下次还会重试），首次失败报一条警告，
恢复后报一条恢复。采用「只报第一次」避免故障期间刷屏。

### 2. 状态目录被同名文件占位 → 整个进程起不来（`config.mjs`）

原为 import 期裸 `fs.mkdirSync(STATE_DIR, { recursive: true })`。
只要该路径被一个同名**文件**占住（残留、误创建、磁盘异常），
`mkdirSync` 抛 `EEXIST`，**进程在加载配置时就直接死掉**，
且报错指向 `config.mjs`，与真实原因（一个占了位的文件）毫无关系。

`memory.mjs` 里还有同一份拷贝（`SESS_DIR`）。

修复：抽出 `ensureDir()`，失败只警告不抛；写入点（`flushSeen`）自己补 mkdir。
「目录建不出来」不该阻止「读取配置」这件只读的事。

### 3. 测试自身的两个问题（已修）

- 测试文件里汇总行印在第 5 组之后，**报出的数字不含第 6 组** —— 一个会骗人的计数
- 第 6 组测试插在 `process.exit` 之后，是死代码，从未真正运行

另外：`sendTyping` / `recallMessage` 也有 `catch { return null }`，
但全局搜索确认**无任何调用点**（死代码），不属于真实风险，未改动。

## 六、回归测试

新增第 5 组（查名降级链，打**真接口**验权限边界）与第 6 组（落盘失败不静默）：

```
═══ 5. 查名字的降级链（真接口，验权限边界）═══
  ✅ 群成员接口可用（降级链的第一条路）
  ✅ 带 chatId 时，同群成员能查到真名（不需要通讯录权限）
  ✅ 不带 chatId 且通讯录无权限时，如实返回原因而不是静默 null
  ✅ lookup_user 工具能返回 source，并带上「别编称呼」的提示
  ✅ 查不到时，工具返回的提示明确禁止模型编造称呼
═══ 6. 去重表落盘失败不静默 ═══
  ✅ 写盘失败时不清 seenDirty，并打出一条警告
  ✅ 恢复可写后重新落盘，并报一次恢复
  ✅ 状态目录被同名文件占位时，进程仍能启动（不许 EEXIST/ENOTDIR 崩掉）

═══ 合计：通过 27 / 失败 0 ═══
```

第 5 组必须打真接口：假 mock 永远返回成功，测不出权限边界。
第 6 组的启动健壮性必须放**子进程**里测 —— 修复前那个场景会直接杀掉进程，
在本进程里测会把「产品起不来」误读成「测试没通过」。

测试自己通过 API 发现群（按群名匹配），不硬编码 chat_id ——
硬编码的 id 在换群后会静默失效，测试会假装通过。
