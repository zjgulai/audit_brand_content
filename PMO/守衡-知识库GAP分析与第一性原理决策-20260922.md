## 〇 · 第一性原理：先把"这个产品必须凭什么成立"写下来

不做类比、不看行业惯例，只问一句：**这个产品删掉什么就不能算存在？**

### 0.1 三条不可再分的公理（从 PRD 的验收条款倒推）

| # | 公理 | 从哪倒推出来（PRD 逐字） |
|---|---|---|
| **A1** | **每一条判定都能指回一条人类可读的依据** | §7.2「证据链：每条结论必须附原因 + **文档链接**」；§11「三态结论符合规范，**附原因和文档链接**」；§5.3 三个模板**每一个**都以「依据《文档名》第 X 条」结尾 |
| **A2** | **三态结论 + 每个状态都有它能被推翻的通道** | §5.3（PASS/REVIEW/BLOCK）+ §5.7（sign-off / 人工复核 / 重新提交） |
| **A3** | **准确率是硬指标，且必须有金标准** | §7.1（≥90% / BLOCK 精确率 ≥95% / PASS 误放率 ≤5%）+ §7.3「以**人工复核为金标准**」 |

### 0.2 ★ A1 展开 —— 这条公理直接决定了知识库**必须长成什么形状**

把 PRD §5.3 的三个示例拆开看，它们引用的是：

```
《合规措辞库 v1》第 3.2 条
《产品描述库-吸奶器》第 2.1 条
《广告法禁用语》第 1 条
《负面样本库-吸奶器》案例 07
《外部标准库-FDA》第 X 条
```

**五个引用里，四个带「第 N 条 / 案例 N」的条文号，一个带《库名-品线》的复合名。**

这不是笔误，是**证据链对知识库的形状要求**：

| 结论 | 依据 | 如果依据不是这个形状会怎样 |
|---|---|---|
| 一条判定要可被人工复核**采信** | 引用必须能**定位到一个条款/案例**，且那个人**当场打得开** | 引用一个 500 页 PDF，复核人在 §7.3 的金标准环节**无法在 SLA 内确认** |
| 一条判定要可被**申诉** | 申诉人必须能说「第 3.2 条不适用本次语境」 | 判据是 9 个关键词，申诉人无话可说 → 申诉退化成求情 |
| 一条判定要**随规则改动而失效** | 条款要有 ID 与版本 | 改一条描述性文字，所有引用过它的旧判定**静默失效** |

> **A1 的推论（本轮最关键的一句）：**
> **知识库不是"资料的仓库"，是"证据的可寻址空间"。**
> 一个存了 62 条外部标准的库，如果**没有条文号**，它对 A1 的贡献是 **0** ——
> 不是"少一点"，是**一条判定都支撑不了**。

### 0.3 由 A1–A3 推出的、知识库的四项不可省略的义务

| 义务 | 由哪条公理 | 一句话判据 |
|---|---|---|
| **O1 可寻址** | A1 | 每个条目有稳定 ID + 条文号；引用能落到它 |
| **O2 可背书** | A1+A3 | 每条有 `authority`（谁有权这么说）+ `ratified`（法务确认过没有） |
| **O3 可回填** | A3 | 人工复核结论能回流成新条目/新修正（§5.5「人工复核结论回流，更新记录」/ §5.9「知识库回流数量」） |
| **O4 可复算** | A3 | 覆盖/缺口/新鲜度是**算出来的**，不是写下来的 |

**下面全部 GAP，都是这四项义务之一没被履行。**

## 一 · 两个坐标系，先证明它们是 MECE 的

### 1.1 轴一：知识链条 L0–L11（**纵向，按"从资料到判定"的必经环节切**）

切分判据是**每一项的输入与输出都不同，且不可合并**：

| 层 | 环节 | 输入 → 输出 | 谁做 |
|---|---|---|---|
| L0 | **需求定义** | 业务口头/文档 → 可验收的条款 | 上游（李倩怡） |
| L1 | **源识别** | 世界 → 「哪些是权威源」清单 | 法务 + 研究 |
| L2 | **采集** | 权威源 → 原文落盘（带链接/日期/指纹） | 研究/工程 |
| L3 | **分类** | 原文 → 归入某一类，且**每一条都有家** | 业务 + 工程 |
| L4 | **结构化** | 原文 → 条款级条目（ID / 条文号 / 适用范围） | 研究起草 + 法务确认 |
| L5 | **机器可读** | 结构化条目 → 引擎/Agent 能调用的形式 | 工程 |
| L6 | **运行时调用** | 条目 → **一次判定真的引用了它** | Agent / 引擎 |
| L7 | **证据回链** | 判定 → 人类点得开的依据 | 工程 + 业务 |
| L8 | **评测** | 判定 + 金标准 → 准确率读数 | 测试 owner |
| L9 | **回流** | 人工结论 → 新条目 / 修正条目 | 业务 + 工程 |
| L10 | **治理** | 全链条 → 谁改、改了通知谁、旧判定怎么办 | Owner |
| L11 | **新鲜度** | 上游变化 → 我们知道 | 守护进程 |

**为什么这 12 层是 MECE 的**：每一层都有**独立的失败模式**，且**下层不能补救上层** ——
L6 再好也补不了 L4 的空缺（引用了不存在的条款）；L2 再全也补不了 L1 的错误（采集了不该信的那一份）。

> 因为那个方向的字段**根本不存在**，而一个不存在的字段没法被断言抓住。

> **验收器能给绿灯，而产品拿不出证据链。**（同形状的两次前科：`AGENTS.md` §2.4.1 的 bitable 读错字段、§2.4.2 的 sha256 零消费者。）
>

## 四 · 第一性原理决策：先定"形状"，再定"数量"

### 4.1 三个反直觉的推论

**推论一：不该先补"数量"，该先补"形状"。**
今天最容易被排进 W1 的动作是"收集四类知识库"（PRD §10 W1 逐字）。但如果 62 条已经存在的条目**形状不对**，
那么再收集 500 条，**形状还是不对** —— 只是让形状不对的东西多了 500 条。
→ **先做 L4（结构化），再做 L2（采集）**：把已有的 62 条改成"可被引用"的形状，是**照着一个已经在跑的模板批量套用**；
而采集 500 条新资料，是在**还不知道要什么形状**的前提下赌一次。

**推论二：不该等法务"确认完"，该让"未确认"本身成为一个可查询的状态。**
`ratified=0` 看起来是阻塞项。但 Kb2Agent 的反面教材（讨论稿 §5.5·5）正是**把所有风险转移到"人签字"上**，
而签字速度注定慢于业务变化。守衡已经在没人签字的情况下推进了整轮产出。
→ **正确做法**：判定照跑，**每条判定带 `ratified: false` 并显式声明"本条依据尚未经法务确认"**。
这既满足 A1（证据链完整），又不把产品挂在法务的队列上。**"未确认"是一个状态，不是一个禁令。**

**推论三：四类知识库不是"四个库"，是"四条可寻址的证据通道"。**
把它们当四个库，就会去数条数（今天数出来 62/117/3/5，然后沮丧）。
把它们当四条通道，判据就变成：**每条通道今天能不能支撑一次判定？**
→ 答案：**能支撑 0 条**（外部标准无条文号 / 样本表装的是审核意见 / 措辞库只有 3 条材料 / 产品库 5 条材料不可读）。
**这才是"知识库建设"真实的工作量口径。**

### 4.2 由此得到的排序（按"解除阻塞的杠杆率"排，不按"工作量"）
