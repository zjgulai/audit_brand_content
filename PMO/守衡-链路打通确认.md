> **`im.message.receive_v1` 从未随版本发布。**

- 应用 API 读到的 3 个已发布版本，事件类型并集里**没有任何 `im.*` 事件**，16 条全是云文档/云盘（`drive.*` / `wiki.*`）——那是创建应用时的预置包。

## 三、实施中发现并修复的 4 个真实缺陷

这部分比「做完了」更重要 —— 都是**不会立刻报错、只会让守衡悄悄变差**的那类问题。

### 缺陷 1：压缩切点 off-by-N（最严重）
`memory.compact()` 数够 `keepTurns` 轮后没有原地停住，`cut` 一路退到 0 附近，
把几乎整段历史都当待压缩内容 —— 等于每轮只保留最后一条消息。
**表现**：守衡「记性突然变差」，且不报任何错。
**修复**：数够即 `break`，让 cut 指向边界下标。已固化为回归测试。

### 缺陷 2：压缩会拆散 tool_calls 与其结果
按条数硬切会把 `assistant(tool_calls)` 和对应的 `tool` 结果分开。
OpenAI 兼容协议要求二者成对相邻，切开会让**下一次请求被 API 直接拒绝（400）**。
**修复**：改为按轮次定位切点，切点必须落在 `user` 消息之前。

### 缺陷 3：触发线与保留量耦合
`compact()` 的触发阈值硬绑在 `config.maxTurns` 上，调用方传 `keepTurns` 却不生效。
**发现方式**：测试报「本应发生压缩」却返回 false —— 一开始我以为是测试写错了，
查下去才发现是真设计缺陷。
**修复**：把 `keepTurns`（保留量）与 `triggerAt`（触发线）拆成两个独立参数。

### 缺陷 4：去重顺序错误
去重放在消息类型判断**之后**，导致非文本消息（图片/文件）绕过去重。
服务端重推时会对同一张图重复回话。
**修复**：去重提到最前。已加实测验证：第 1 次 `unsupported_type`，第 2 次 `duplicate`。
