|---|---|---|---|
| **E3** | 「`ws.start()` 成功 = 长连接握手成功」 | **`start()` 返回成功只是启动了重连循环**，不代表握手成功。必须看 SDK 的 `[ws] ws connect success` 或 TCP `ESTABLISHED` | 把「调用未抛错」当成「连接已建立」 |

## 2. ⛔→✅ 长连接「Connection failed」的完整诊断（v2 重写）

### 2.1 症状

控制台「事件配置 → 编辑订阅方式 → 选长连接 → **点保存**」时提示 `Connection failed`。

### 2.2 真实根因（官方 FAQ + 逐层实测）

> **飞书官方 FAQ**：使用事件订阅长连接方式，点击保存按钮时提示「应用未建立长连接」
> 回答：**订阅长连接前，需先确保已通过 SDK 在服务端/本地完成长连接的建立。**
> —— https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/event-card-faq

**即：飞书在「保存」那一刻会做一次在线客户端探测。探测不到 → 保存失败。**

**本项目当时失败的原因**：测试用的是一次性脚本（连上→等 100s→退出），
**用户点保存时，客户端已经退出**。验证完就把钥匙扔了。

### 2.3 逐层排除（全部实测，无推断）

| # | 检查项 | 实测命令 / 证据 | 判定 |
|---|---|---|---|
| 1 | 代理拦截 | `env \| grep -i proxy` 无、`scutil --proxy` 无 | ✅ 排除 |
| 2 | DNS | `msg-frontier.feishu.cn` → `59.36.45.11` / `113.96.128.67` … | ✅ 正常 |
| 3 | WS 端点 | `POST /callback/ws/endpoint` → `{"code":0,"URL":"wss://…"}` | ✅ 服务器正常下发 |
| 4 | 裸握手 | 直连 server 下发的 wss URL → `open` 事件触发，保持 20s 无异常 | ✅ |
| 5 | SDK 握手 | `[debug] [ws] ws connect success` | ✅ |
| 6 | TCP | `lsof` → `node(10352) 192.168.193.197:65453->59.42.248.103:443 ESTABLISHED` | ✅ |
| 7 | 心跳活性 | 运行 5.6min ≈ 3.7 个 90s 周期，`netstat` 发送 15800B / 接收 2515B | ✅ 非僵死 |
| 8 | 竞争客户端 | 仅 1 个（官方：同应用多客户端**只有随机一个**收到消息） | ✅ 无分流 |
| 9 | SDK 版本 | 1.74.0 **= `npm view` 最新版** | ✅ 非版本问题 |

**结论：网络层、连接层、SDK 全部健康。`Connection failed` 与这些无关。**

### 2.4 关键纠错：机器人不能给自己发消息

```
POST /im/v1/messages  receive_id = 机器人自己的 open_id
→ {"code": 230013, "msg": "Bot has NO availability to this user."}
```

**这意味着：任何「机器人自己发消息 → 期待自己收到事件」的测试都是无效的。**
v1 报告里那些「群内发消息 2 条 / 建群 / 被拉入群 → 0 事件」的动作，
**全部是机器人自己发起的**，因此**根本不会产生推送给它自己的事件**。
「0 事件」由此不能推出「事件列表为空」。

### 2.5 正确做法：常驻客户端

控制台保存长连接时要求**有一个在线客户端**。因此不能跑一次性脚本，
必须让客户端**常驻**：

```bash
cd tools
nohup node ws_daemon.mjs > ../PMO/logs/ws_daemon.log 2>&1 &
```

本项目的守护进程已确认**脱离会话**（`PPID=1 /sbin/launchd`），
不会因会话结束而被回收。

**状态**：控制台已保存成功（用户实测通过），长连接常驻在线。

### 2.6 仍未验证的一环：事件能否真正到达

**必须由真人触发**。原因见 2.4 —— 机器人自己的任何动作都不会回流事件。

已验证的无效测试（记录以免重犯）：

| 测试动作 | 为何无效 |
|---|---|
| 机器人往群里发消息 | 自己发的，不回流 |
| 机器人 @自己 发消息 | 同上，且飞书直接拒发（`230013`） |
| 机器人建群 / 被拉入群 | 均由机器人侧发起 |

**唯一有效测试**：真人在群里 @守衡，或真人单聊守衡。

### 2.7 第一次有效阴性：真人 @ 了，事件仍未到达

**2026-09-15 22:38:21**，群成员**周健**（`ou_e5ada0b1c7a023c44e407c60ee8bd91b`，真人账号）发出：


**但守护进程日志在 22:22:50 之后冻结 16 分钟，未收到任何事件。**

| 项 | 值 |
|---|---|
| 消息是否真实产生 | ✅ 是（API 读回，sender_type=`user`） |
| 是否自环（无效测试） | ❌ 否 —— **真人发出，本次测试有效** |
| 事件是否到达 | ❌ 未到达 |
| 同期 TCP 连接 | ✅ 仍 `ESTABLISHED`，socket 收发字节在增长 |

**排除项更新**：

| # | 怀疑 | 证据 | 判定 |
|---|---|---|---|
| 10 | 竞争客户端抢占 | `lsof` 全机扫描：仅 1 个 node 长连接；`Lark Helper`(PID 2104) 是桌面客户端非 bot | ✅ 排除 |
| 11 | 消息发送失败 | API 读回消息确实存在 | ✅ 排除 |
| 12 | 连接僵死 | 旧连接 socket 累计收 3294B，非零；连接全程 ESTABLISHED | ✅ 排除 |

**剩余嫌疑（需控制台核对，API 读不到配置）**：

| # | 嫌疑 | 如何确认 |
|---|---|---|
| **A** | **事件列表未真正保存** `im.message.receive_v1` | 控制台事件列表里逐个核对事件名 |
| **B** | 长连接建立在配置生效**之前**，未被登记为已订阅 | 已重建连接（见 2.8），待复测 |
| **C** | 应用未发布版本 | 控制台「版本管理与发布」 |
| **D** | 订阅方式存在冲突（曾配过 webhook 地址） | 确认订阅方式**仅**为长连接 |

> **API 侧无法自查**：`GET /application/v6/applications/{id}` 返回
> `99991672 Access denied ... [admin:app.info:readonly, application:application:self_manage]`。
> 事件订阅配置**只能由控制台人工核对**。

### 2.8 重建连接（配置生效后重新握手）

假设 B 成立：长连接若在「保存订阅方式」**之前**建立，飞书可能不将其登记为已订阅。
处理：**在配置保存之后重建连接**。

同时修正两个操作失误：

| 失误 | 现象 | 正确做法 |
|---|---|---|
| 用 `nohup ... &` 拉起守护进程 | `PPID` 非 1，会随会话回收（早期 `bash-3` 就这样被 SIGTERM 杀掉） | **双重 fork + `os.setsid()`**，使 `PPID=1`（launchd 收养） |
| 用 `setsid` 命令 | macOS **无此命令**（`command not found`） | macOS 用 Python `os.setsid()` |

## 4. 卡片能力实测（schema 2.0）

**支持**：`markdown`（含粗体/斜体/行内码/链接/有序列表/引用块）、`hr`、
`collapsible_panel`（折叠）、`column_set`（分栏）、`button`（顶层）、
`table`（原生表格）、`header`（彩色标题栏 + 副标题）

**不支持**（实测报错 `ErrCode: 200861`）：
- `note` 标签
- `action` 容器 —— schema 2.0 已废弃，按钮必须直接作为 element 挂在 `body.elements` 下

> 这条踩坑值得记：飞书官方文档里 button 的示例仍带 `action` 包裹，
> 但 schema 2.0 会直接拒绝。**`PATCH /im/v1/messages/{id}` 是原地更新的正确路径**
> （不是 `/content` 子路径），这是做「一张卡跑到完」的关键能力。

## 6. 我犯的两个错误（记在案）
