## 三 · 三条纪律，以及它们各自的执行点

按 `AGENTS.md` §2.4：「写进文档的每一个上限，必须能指出是哪一行代码在拦它。」

| 纪律 | 执行点 | 自证里那条能红的断言 |
|---|---|---|
| **① 留痕** | `withWrite()` 里 `logWrite(...)` 无条件 append `PMO/logs/lark_writes.jsonl` | B1 断言留痕**恰好追加一行**且 `result:'ok'`；B2 断言里面有**谁** |
| **② 回读** | 每个写函数 `step()` 自己读回来，`verifyReadback` 逐字段比；结果落 `readback` 三态 | B3 `mismatch`；B4 `untested`；A4 断言**不误报** |
| **③ 删除前快照** | `snapshotBefore(op, pre)` + 各删除/改动函数在发请求**之前**调用 | B6/B6b/B6c 断言 `batchDelete`/`appTable.delete`/`batchUpdate` **一次都没被调用** |

### 回读的三态，后两态不许说成成功

`consistent` / `mismatch` / `untested`。理由见 `AGENTS.md` §2.4.2：
**「接口返回 code=0」只证明请求发出去了，不证明数据落下来了。**
人设里也写了这一条（`persona.mjs` 能力边界那节第 1 点）。

### 删除是最大的一刀，所以搬走再砍

`deleteTable` 会把「表列表 + 全部字段定义 + 最多 500 条记录」一起搬进留痕；
`deleteRecords` / `updateRecords` 会把**将被删掉或覆盖的完整内容**搬进留痕。
搬不全就**拒绝执行**。

> **这是「搬是搬，砍是砍」的反面用法**：那条讲的是超长内容要搬不要截断；
> 这里是**砍之前先搬一份**。多花几 KB，换的是「删错了能重建」。

## 四 · 自证第一次运行就抓到两个真 bug

两个都不是测试写错，都是代码写错。两个都留在代码注释里了。

### (a) `{ records: found ?? [] }` —— 「读不到」被变成了「没有」

```js
const found = before.ok ? (before.data.records ?? []) : null;
const snap = snapshotBefore('delete_records', { records: found ?? [] , ... });
```

`found` 是 `null`（**读不到旧值**）时，`?? []` 把它变成了**空数组**，
而空数组在判定里是合法的「零条记录」→ 快照判定**通过** → **照删**。

**这是 `AGENTS.md` §2.4.1 那句话（未测 ≠ 没有）长在了防误删的护栏本身里面。**
修法两层：① `snapshotBefore` 要求 `pre.readable === true`，读不到一律不合格；
② 调用方在读不到时**先中止**，不再传空数组。

### (b) 留痕那一行用的是 `pre.ok`，而成功路径从没设过它

每次**成功**的写入，台账里记的都是 `result:'failed'`。
**一份会骗人的台账比没有台账更坏 —— 它会让人不再去看它。**
修法：成功与否**只判一次**（`okFlag`），留痕与返回值共用同一个布尔。

> 附带修掉的第三处：返回值里成功路径没有 `ok` 字段（`undefined`），
> 调用方分不清「成功」和「字段拼错了」。

## 六之二 · 破坏性操作是两段式的（2026-09-22 委托方第二次决定）

建完通道之后发现**我自己在里面留了一个 §2.4 意义上的缺**：

> `persona.mjs` 里写着「删除类操作动手前，先把要删什么说出来」——
> 而全仓**没有任何一行代码在拦它**。那是一句注释，不是约束。

就这一点问了一次，委托方选**两段式**：先说清楚要删什么、等对方在另一条消息里确认再删。

### 执行点：`judgeConfirm()`

纯函数，四种拒绝一种通过。**核心是第 3 条**：

| 情形 | 结论 |
|---|---|
| 没有待确认的 | `no_pending` |
| 提议超过 15 分钟 | `expired` |
| **同一条消息自我确认** | **`same_message`** ★ 这条是两段式的全部意义 |
| `messageId` 采不到 | `cannot_verify` ★ 未测不许当成通过（§2.4.1） |
| 另一条消息 + 未过期 | 放行 |

**为什么必须有「同一条消息」这条判据**：没有它，模型可以在**同一次推理**里
先调删除工具（提议）再调确认工具（确认）—— 两段式白做，
而**从外面看起来完全一样**。

### 落在哪

| 文件 | 是什么 |
|---|---|
| `lark_write.mjs` | `PENDING_FILE`（独立状态文件）/ `proposeDelete()` / `describeDelete()` / `judgeConfirm()` / `confirmDelete()` / `cancelDelete()` |
| `tools.mjs` | 新增 `lark_base_confirm_delete` · `lark_base_cancel_delete`；**三支删除的工具说明改成「只提议」** |
| `persona.mjs` | 能力边界那节第 2 条改成两段式的说法 |

**三支删除（`deleteTable` / `deleteField` / `deleteRecords`）在没带 `confirmed` 时
一律走 `proposeDelete()`，一个删除请求都不发。** `confirmed` **不在任何工具的参数表里** ——
只有 `confirmDelete()` 会传它。

### 两条与「数」有关的判据

- `describeDelete()` 数不出来时写 **「未测」**，**不许写成 0** ——
  0 读起来像「这列是空的，删了没事」（§2.4.1）。
- 确认之后**无论成败都清掉 pending**：留着的话，下一次任何人说一句「确认」都会重放它
  —— 那是把一次误触变成一条常设指令。

### 自证新增 D 段 11 项，且**把两条老测试撞红了**

D 段：`no_pending` / `expired` / **`same_message`** / **`cannot_verify`** / 正向放行 /
「未测不许写成 0」/ **三支删除不带 confirmed 时 `batchDelete`·`appTableField.delete`·
`appTable.delete` 一次都没调** / **同一条消息确认时 `batchDelete` 一次都没调** /
**另一条消息确认时 `batchDelete` 真的被调**（正向对照）/ 取消。

> ★ **B6/B7/B8/B6b/B8b 五条老测试当场变红** —— 因为它们调删除时没带 `confirmed`，
> 于是只能走到「提议」。**那不是回归，那是两段式真的接上了管道的证据**：
> 连测试都进不去删除路径了。已按新形状更新（补 `{ confirmed: true }`）。

### 定向破坏验证（§2.4.1）

| 破坏 | 实测 |
|---|---|
| 拿掉 `if (req === cur)` 那道判据 | 只有 **D3 / D9** 红；D5（正向对照）仍绿 |
| 让「采不到 messageId」放行 | 只有 **D4** 红；D5 仍绿 |

两次都 `cp` 复原，`sha256` 前后一致（`f2c80fb478570c39`）。

### 已知边界

- **`confirmed` 不是工具参数**，但这靠的是「`tools.mjs` 的 `run` 没把它透传」——
  它是一条**结构约束**，不是运行时检查。将来有人给删除工具加一个 `confirmed` 参数就会破。
- 提议状态按**会话**（`chat_id`）存，一份。同一个人在同一会话里连提两次，**后一次覆盖前一次**
  （返回值里有 `replaced_previous` 说明被顶掉的是哪一件事）。
