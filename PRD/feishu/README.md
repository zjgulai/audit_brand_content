# PRD/feishu · 上游飞书文档的只读基线

> **这个目录装什么**：从飞书拉下来的**上游权威文档的逐字原文**，以及它们的 token、时间与指纹。
> **不装什么**：任何本项目的判断、分析、结论。分析放 `PRD/PRD差异对照-*.md`，登记放 `research/kb/`。

---

## 一 · 为什么需要它

2026-09-21 之前，本项目对上游需求只有**一份 09-15 的提取件** `PRD/内容治理需求文档.md`，
而它**没有指纹、没有拉取时间之外的时间信息、也没有说明它对应的是哪一版**。
结果是 09-21 新 PRD 到手时，无法回答一个最基本的问题：

> 本地这份，和线上现在那份，是不是同一版？

答不出来，就只能靠记忆比 —— 而记忆比出来的差异**读起来和实测出来的一模一样**。
所以这个目录的作用只有一件：**让"上游现在是什么"变成可复核的读数，而不是印象。**

## 二 · 口径（三条硬约束）

### 1. 逐字原文，一个字都不改

`raw_content` 返回什么就存什么。**不重排、不补标题、不修标点、不合并空行。**
理由：一旦"整理"过，它就不再是基线，而是**第二份会漂的副本** ——
而漂掉的那一份读起来同样像一个结论（`legal-decisions-v1.json` V30d 的注释里记着这条纪律的由来）。

### 2. 只记"读到了什么、什么时候读的"，不记"它意味着什么"

`索引-v1.json` 里的字段只有：token / 标题 / 作者 / 建立与最后编辑时间 / 字数 / sha256 / 落盘字节数。
**没有"重要性""结论""待办"** —— 那些属于分析层，不属于基线层。

### 3. 飞书是权威，本地是只读投影（ADR-0001 / ADR-0013）

本地这份**永远是投影，不是源**。发现线上变了，动作是**重新拉取并记录新指纹**，
不是"在本地改一改让它对上"。改本地 = 制造第二份权威。

## 五 · 怎么用

```bash
cd /Users/lute/Project/audit_multi_content

# ★ 先跑这个：基线漂移检测（L1 结构 / L2 副本=指纹 / L3 上游=指纹）
python3 tools/verify_prd_baseline.py
#   退出码 0 = 三组全过（含 L3：上游此刻与指纹一致）
#         1 = 有红（L2 红 = 本地被改过；L3 红 = **上游改版了**）
#         2 = L3 **未测**（不联网/没凭据）—— 2 不是通过，别当绿用
python3 tools/verify_prd_baseline.py --controls   # 14 项离线反向对照：证明这些判据真会红
python3 tools/verify_prd_baseline.py --offline    # 只 L1+L2（退出码 2）

# 看基线台账（谁、什么时候、多少字、指纹）
python3 -c "import json;d=json.load(open('PRD/feishu/索引-v1.json'));print(d['fetched_at']);[print(x['file'],x['chars'],x['sha256'][:16],x['obj_edit_time_bj']) for x in d['docs']]"
```

**为什么要有 L3**：2026-09-21 11:51 上游在群里说这份 PRD「**我后续会基于评估重新修改**」，
守衡回她「改版后得重新拉一次基线并记新指纹」。而当时仓里**没有任何东西会在它改版时变红** ——
索引里的两个 sha256 全仓零消费者。`AGENTS.md` §2.4.2 记的就是这件事。
**落在 `tools/verify_prd_baseline.py`，它是那句对外承诺的执行点。**

**重新拉取（L3 红了才做）**：脚本会把该跑的命令直接打出来。要点三条：

1. **落盘的三步配方**（2026-09-22 更正 —— 原来说「用 shell 重定向落盘就不会被填充」
   **是错的**：`readdoc` 的产出方是 `python3`，重定向只是 shell 转手，文件照样进填充态，
   实测 `verify_depad.py` 报「真实 6540B · stat 10636B」）：

   ```bash
   python3 tools/lark_find.py readdoc <token> > 'PRD/feishu/<文件>'   # ① 落盘
   python3 tools/verify_depad.py --fix                                # ② 去填充（必做）
   python3 tools/verify_depad.py                                      # ③ 复验须「被填充 0 个」
   ```

   `readdoc` 自 2026-09-22 起**原样输出、不补换行**，所以 ① 出来的文件 sha256 与
   `raw_content` 逐字一致；在这个改动之前用 `print()` 会多一个 `\n`，
   于是**照文档跑出来的文件永远对不上索引**，B1/B2/B3 全红。
2. **别只改 sha256**，`chars` / `size_bytes` / `obj_edit_time_bj` 一起重记 ——
   只改一个数，等于把「变过」这件事压成一行，后人看不出变了什么。
   旧的读数写进该条的 `prev_fingerprints`，别丢。
3. **只写复现得出来的数**（AGENTS.md §2.2 第 1 条）：本轮我一度想记一个
   09-22 上午的「中间态指纹」，但它在仓里**找不到任何出处**，于是没写进去。

## 七 · 已知的环境陷阱（写在这里免得下一个人再踩）

**Python 写出的文件会被 `stat` 多报 4096 字节**，DSH 的 `read` 工具据此判成 `binary file`，
正文一个字都读不出来。内容本身是对的，是视图不一致（`AGENTS.md` §2.1）。

本目录的三份文件都做过 `cp → mv` 往返（带 sha256 断言"内容未变"）。
**自查**：`stat -f %z <文件>` 必须等于 `python3 -c "import os;print(os.path.getsize('<文件>'))"`。

**2026-09-21 又踩了一次，记下来**：为了验证 `verify_prd_baseline.py` 的 B1 会红，
我用 `Path.write_bytes()` 把 `内容审查Agent-PRD-v1.0.md` 改一个字节、跑一遍、再改回来。
**sha256 完美复原**、`verify_prd_baseline` 全绿 —— 但那个文件已经进了填充态：

```
ls -l / wc -c / stat -f %z  →  18710
python open().read()        →  14614     ← 索引 size_bytes 也是 14614（**那是当时那一版**；
                                            09-22 16:32:37 上游改版后已是 23452）
```

抓到它的是 `python3 tools/verify_depad.py`（`--fix` 修好，`cp` 往返带 sha256 断言）。
**教训两条**：① 反向对照只在内存里做（`--controls` 就是这么设计的，不动盘）；
② **非要动盘就用 shell，别用 Python；事后跑一次 `verify_depad.py`。**
详见 `AGENTS.md` §2.1 触发条件表里新加的那一行。
