## §1 · 分类体系（重写 §5.3.1）

### 1.1 原设计的三个问题

原 §5.3.1 规定「每个问题必须归入以下一个 issue_category」，枚举八项：
合规 / 消费者安全 / 品牌信任 / 经营风险 / 产品准确性 / 措辞表达 / 人物肖像与 AI / 其他。

**它有三个可以当场验证的问题：**

| # | 问题 | 证据 |
|---|---|---|
| **1** | **它悬空 —— 没有上游列可以对** | §5.4 **确实**有 `issue_category` 字段（说明写「必须使用 5.3.1 枚举」），所以「没有输入源」这个说法**不准确**。真正的问题是：**§6.5 的规则字段表里没有分类列** —— 也就是说那个 `issue_category` 是**模型每次临场填的**，无法断言「每个取值都在取值域内」。**一个没有上游列可以对的值，写错了没有任何东西会红** |
| **2** | **它内部自相矛盾** | §5.3.4 示例把「宝宝未坐安全座椅」归【消费者安全-**车内场景**】；而 §7.2 的「车内场景」行，**主要规则归属**写作「**法务合规红线 + 安全准确性**」。★ 注意后半句：**那一行本来就是跨两个归属的** —— 而 §5.3.1 规定「每个问题**必须归入一个**」。**这两句话不能同时成立** |
| **3** | **它对路由无用** | §9 写「REVIEW 自动转法务 / 医学 / 专家 / 北美」。而报告里给的是「**合规类问题：3 个**」—— 法务看到这个等于没收到信息。是哪类合规？FDA 器械宣称、FTC 广告实证、平台政策、肖像权？**路由键不携带路由所需的信息** |

> **一句话**：它是一个**有下游输出字段、但没有上游规则映射、也没有可验证来源**的标签枚举 ——
> **而且它不携带路由所需的信息。**
>
> ⚠️ **措辞更正**：我第一版写的是「没人引用的标签枚举」。**那句话过强了。**
> 准确的说法是：§5.4 **确实引用了它**（`issue_category` 字段，说明写「必须使用 5.3.1 枚举」），
> 缺的是**上游** —— §6.5 的规则字段表里没有分类列，
> 所以**没有任何东西能断言「每个取值都在取值域内」**。
> 有下游、无上游，不等于「没人用」。

### 1.2 新设计：三层，各答一个问题

```
第 1 层  审查控制族 → 控制点     答「这是一次什么审查动作」   ← 主轴
第 2 层  三轴（正交属性）         答「是什么 / 谁说了算 / 伤到什么」
第 3 层  双键（机器标识）         答「违反了哪条 / 凭哪条依据」
```

#### 第 1 层：七个审查控制族（**这是审查分类**）

| 控制族 | 答什么 | 复核人 |
|---|---|---|
| **宣称控制** | 这句话能不能说 | 法务 + 医学顾问 |
| **事实控制** | 这件事是不是真的 | 产品 + 专家 |
| **披露控制** | 该说的说了没有 | 法务 + 品牌 |
| **场景控制** | 画面这样做安不安全 | 医学顾问 + 北美 |
| **权利控制** | 能不能用这个人 / 这张脸 | 法务 |
| **渠道控制** | 这个平台允许吗 | 平台运营 + 法务 |
| **品牌控制** | 这个调性对不对 | 品牌 |

**为什么这七个是「审查动作」而不是「内容标签」**：
「宣称控制」的动作是**验实证材料**，「披露控制」是**查有没有披露**，「权利控制」是**查授权文件** ——
**每一个都有不同的判据、不同的复核人**。
而「车内场景」「睡眠场景」没有：它们只告诉你内容在讲什么，**不决定该做什么审查**。

> ★ **二级是强制项，且二级才是规则的挂载位置。**
> 例：`宣称控制 → 疾病治疗宣称（H01） / 催乳与通乳宣称（H02） / 临床与实验证据宣称（H03）…`

#### 第 2 层：三轴（**正交属性，不决定审查动作**）

| 轴 | 答什么 | 取值 | 维护人 |
|---|---|---|---|
| `scene_domain` | 在说什么 | 车内 / 睡眠 / 喂养 / 洗护 / 出行 / 居家 / 玩具 / 功效宣称 / 人物肖像与 AI / **其他** | 产品 |
| `authority_source` | 谁说了算 | 联邦法规 / 州法 / 平台政策 / 英国对照 / 品牌内规 + **机构**（FDA·FTC·Amazon…）| 法务 |
| `consequence` | 伤到什么 | 消费者安全 / 品牌信任 / 经营风险 / **建议级** | 业务 |

**三条轴都必须有「未知桶」，且未知桶必须显式登记、不许静默落进任何一个已知值：**

| 轴 | 未知桶 | 后果 |
|---|---|---|
| 控制族 | `未归类` | 强制转人工 |
| `scene_domain` | `其他` | 同上 |
| `authority_source` | `依据待定` | 同上 |
| `consequence` | `后果未知` | 同上 |

> **未知桶不是垃圾桶，它是有意义的信号** —— 它一多，就说明规则库或分类体系该补了。
> 关键在于：**它必须能被数出来**（否则垃圾堆积无人发现）。

#### 第 3 层：双键（机器标识）

| 键 | 答什么 | 取值 |
|---|---|---|
| `control_code` | 违反了哪个**控制点** | H/M/U/V 码 |
| `authority_ref` | 凭哪条**依据** | T 码 → 外部标准库条目 |

**为什么必须是两个键**：只有控制点，报告里写不出「违反了哪一条具体条款」。
而「通知里必须有具体条款」是我们对监管与平台政策的**设计性归纳**（见文末《依据索引》所列条目），
**不是经统计验证的「行业公认最低标准」** —— 该说法已撤回：盘上没有做过能支撑「公认/最低」的抽样测量。

#### 三个可执行的断言（**这是新分类体系对比旧八分类的唯一硬差别**）

| # | 断言 |
|---|---|
| **A1** | 每条问题**必须**带一个 `control_code`，带不出就显式标「未归类」并转人工 |
| **A2** | 每个轴取值**必须**在规则库该列的取值域内（写错字要能被检出）|
| **A3** | 人工结论的推翻率**按控制族分组统计** —— 某一族推翻率异常高，说明该族定义有问题 |

> 旧的八分类做不到这三条 —— **它没有上游列可以对，所以没有任何东西能验它**。

### 1.3 报告的统计口径

**按控制族汇总**（不是按八分类）：

```
【审查结论：BLOCK】共发现 4 处必须修改。
· 宣称控制：2 个　· 事实控制：1 个　· 场景控制：1 个
→ 查看完整问题清单与修改建议：<报告链接>
```

**报告详情里，每条问题给全五样**：控制点 · **依据条款** · 原文位置 · **原因** · 修改建议。
**外加一样**：`coverage_receipt`（覆盖证明）—— 报告要能回答「这次审到哪一层」。

> ⚠️ 我第一版这里写「四样」（漏了**原因**），与 §10.6 的报告契约不一致。**现已在源段直接统一。**

## §2 · 分层审查机制（重写 §6）

### 2.1 保留的部分

§6.1（设计背景）、§6.3（分层执行流程的漏斗结构）、§6.5（规则配置要求）**基本保留**，
但有三处必须改：

### 2.2 改动一：**判定必须按 `judge_type`（字面 / 语义）与检测层 `P0–P3` 分离**（重写 §6.2 的 P0 行）

**原设计**：P0 = 「规则引擎精确匹配 + 关键词黑名单」，「**无需大模型推理**，正则/关键词命中即输出 BLOCK」。

**它与 §11.1 的「`L4/L5` 漏报率 = 0」不能同时成立。** 具体漏在哪：

医疗功效宣称是 P0（§7.3 列了）。而下面这一类表述**不含任何可穷举的禁用词**：

> ⚠️ **举例假设，不是频次实测** —— 我第一版写「美国母婴内容里**最高频**的违规表述」，
> **那是断言，而盘上没有任何测量支撑它**（全仓搜 `boosts milk supply` 只命中本文件自己）。
> 下面四条是**形态示例**，用来演示「正则盖不住语义判断」这件事；**它们是不是最高频的，未核。**

```
boosts milk supply          pediatrician recommended
hospital-grade              FDA cleared（没 cleared 而这么写就是违规）
```

**这几条不含任何可穷举的"禁用词"。** 它们是**语义判断** ——
FDA 管这个叫 intended use（预期用途），认定靠整体印象，不靠词表。

**再看一层语种问题**：§7.3 的禁用词清单是**纯中文**（最 / 第一 / 最佳 / 100% / 纯天然），
而 §2.1 的范围是**美国市场**。英文里：

| 表达 | 中文词表会怎样 | 声称的美国要求 | 判据强度 |
|---|---|---|---|
| `Best Seller` | 命中「最佳」→ 误拦 | 亚马逊标识 | ⚠️ **待核**（未找到亚马逊政策原文）|
| `100% cotton` | 命中「100%」→ 误拦 | FTC 成分披露 | ⚠️ **待核**（全仓搜 `纺织品`/`成分披露` 零出处）|
| `first-time mom` | — | 品牌常态表达 | ⚠️ **待核** |
| `most loved` | 命中「最」→ 误拦 | 视有无优越性主张 | ⚠️ **待核** |

**照搬中文词表会误杀，不照搬就是零覆盖 —— 两个方向都错。**

> ★ **上表「声称的美国要求」那一列全部标了「待核」，这是刻意的。**
> 我第一版把它们写成了确定结论（「亚马逊**合法标识**」「FTC **法定成分披露**」），
> **而仓库里没有这些法源的任何原文。** 按本项目的规矩，
> **指不出条款位置的美国法判断，只能写「待法务确认」，不能写进表格当事实。**
>
> **这张表要成立，必须先有人补上第 3 列的可核原文。** 在那之前，它只能当「要问法务什么问题」的清单用。

**新设计：**

> ⚠️ **2026-10-18 术语更正：不存在「P0 子类」。**
> `P0–P3` 是**检测层**（`detected_by`：P0 正则/关键词 · P1 大模型语义 · P2 多模态 · P3 措辞建议），
> `L0–L5` 是**严重度**。两者不是一回事，**严禁用「P0-语义」这种写法** ——
> 它把「哪个检测层抓到」和「有多严重」压成了一个词，正是术语混用的源头。
> 依据：委托方 2026-10-17 定「P 是检测层，L 是严重度」；Playbook §1.1.1。

| 判定方式 | 判据 | 实现 | 例子 |
|---|---|---|---|
| **字面可判**（`judge_type=literal`） | 明确且字面可判 | 规则引擎（快、确定）| 具体禁用词、明确字号 |
| **需语义判断**（`judge_type=semantic`，检测层 **P1**） | 需整体印象判断 | **强制走模型语义判定**，且默认偏保守 | 医疗 intended use、**危险行为示范**、肖像授权 |

> ⚠️ **一处需要你定的取舍（本文件不替你定）**：
> 「危险行为示范」既是**法规问题**（联邦/州层面的儿童安全要求），也是**育儿建议问题**（AAP 的建议）。
> 本 PRD（v2.0 优化稿）§3.4 把它归入「**品牌内规层 · REVIEW**」（因为它依据的是 AAP 建议而非联邦法），
> 而这一节又把它列为**需语义判断（检测层 P1）**。**两者只能留一个。**
> ★ 注意：这里的「P1」只说明**由哪一层检测**，不表示严重度；它的严重度仍按 `L0–L5` 单独判定。
>
> 我的建议是**保持 §3.4 的归类（REVIEW）**，理由是依据强度：
> AAP 的建议不是法，把它当成「红线级（`L4/L5`）」会让「红线」这个词贬值。
> **但这需要与法务确认**，因为如果某条危险行为落在州法管辖内，它的严重度就应按 `L4/L5` 判、而不是按建议级。

且**规则按语种分库**（中/英各一套），**不是中英对照表**。

#### ⚠️ 关键补丁：**「模型说命中」≠「可以机器终结」**

上面那张表如果照字面读，会得到一个**危险的推论**：
P1 语义检测走模型 → 模型命中 → 状态被当成 BLOCK → 而 §4.2 说机器可终结 BLOCK
→ **语义模型可以绕过人工，直接拦截内容。**

**这条推论不成立，也必须被堵死**：按 Playbook 现合同，语义模型默认只出 `candidate`；
`candidate` 不贡献严重度、不能单独产生 BLOCK（它最多把结论拦在 REVIEW）。

**这条路必须堵死。** 补三条契约：

**① 每条 P0 规则必须声明「机结资格」，且默认关闭：**

```
machine_finalizable: false     ← 默认值，必须显式改成 true 才生效
```

**② 只有同时满足三条的 P0 规则才允许机器终结：**

| # | 条件 | 为什么 |
|---|---|---|
| **a** | 判据是**字面可判**（`judge_type=literal`，检测层 `P0`） | 结果可复现、可争论 |
| **b** | 依据能指出**具体条款**（`authority_ref` 非空） | 否则「凭什么拦」答不出来 |
| **c** | 该规则在**冻结回归集**上有已知表现 | 至少见过它的正例与负例 |

**三缺一 → 只能出「疑似」，转人工。**

**③ 语义类命中的输出不是 BLOCK，是「疑似需人看」：**

| 规则类型 | 模型命中后的输出 | 谁终结 |
|---|---|---|
| 字面规则（检测层 P0）+ 满足 a/b/c | **BLOCK** | 机器 ✅ |
| 语义检测（检测层 P1，任何情况）| **疑似 → 转人工** | 人 |
| 未声明 `machine_finalizable` | **疑似 → 转人工** | 人 |

**验收断言（可机验）：**

> ⚠️ **先说一处我第一版的漏洞**：a/b/c 三条准入条件我写在正文里，
> 但断言只检查了「字面类」和「默认 false」两条。
> **结果是：只把 `machine_finalizable` 改成 `true`、不动别的，就能拿到拦截权** ——
> 文档承诺了三道闸，代码只拦了一道。**下面把 a/b/c 逐条变成断言。**

| # | 断言 | 拦什么 |
|---|---|---|
| **A4** | 任何 `machine_finalizable=true` 的规则，其 **`judge_type` 必须为 `literal`**（检测层 `P0`） | 条件 a |
| **A5** | 任何由模型产出的命中，**不得**直接落 `BLOCK` —— 除非该规则的 `machine_finalizable` 为 true | 直通路径 |
| **A6** | 每条规则的 `machine_finalizable` **默认值为 `false`**（读不到这一列时按 false 处理，**不是按 true**）| 字段缺失 |
| **A7** | 任何 `machine_finalizable=true` 的规则，其 **`authority_ref` 必须可解析**（指向一条存在的依据条目，且该条目的 `条款位置` 非空）| 条件 b |
| **A8** | 任何 `machine_finalizable=true` 的规则，必须**在冻结回归集里有已登记的读数**（含规则版本 + 指纹 + 正例数 + 负例数）| 条件 c |
| **A9** | 每条 `machine_finalizable` 的**开权必须留痕**：谁批的、何时、依据哪次回归读数。**无留痕的 `true` 视为 `false`** | 谁能开这个权 |

> ⚠️ **2026-10-18 更正：原 E1–E4（回边 / `max_rounds` / 震荡检测）已移出阶段一现行规范。**
> 依据：委托方 2026-10-17 定「**不做回边，只留规格**」（决策溯源账 L10）；
> 2026-10-18 定「**第一阶段不开提前停**」（S-4）。
> 阶段一是 **pipeline：五步各跑一次、无回边、无轮次、无提前停**。
> E1–E4 全文保留在 **附录 F「未来能力（非阶段一）· 不进入验收」**，**不得**作为阶段一验收依据。
>
> 阶段一与流程形态相关的唯一断言是：
>
> | # | 断言 |
> |---|---|
> | **E0** | 五步（归一化→判定→处置→输出→评估）**各执行一次**，无回边、无轮次、无提前停；任一步跳过即视为实现缺陷 |

> ★ **A7/A8/A9 是这一组里最要紧的三条**，因为它们对应 a/b/c 里**真正难满足的**那三条。
> A6 防的是**字段缺失**，A7/A8/A9 防的是**只有一个布尔值**。
>
> ★ **A6 与 A9 的默认方向都是保守的（false）** —— 这是刻意的：
> **默认值的方向决定了失败时往哪边倒。**
> 读不到就当 false：后果是「该机结的转人工了」（慢，但不漏）。
> 读不到就当 true：后果是「模型拿到了拦截权」（快，但可能误拦且无人复核）。

> ★ **A6 是这三条里最容易做错的一条。**
> 「读不到就当 false」是**保守方向**；反之（读不到当 true）会让一次字段缺失
> 静默地把拦截权交给模型。**默认值的方向决定了失败时往哪边倒。**

### 2.3 改动二：**删除置信度分档，改为「证据状态 + 覆盖证明」**（重写 §6.6）

**原设计**：置信度 ≥0.90 直接出结论；0.70–0.89 出 REVIEW。

**三个问题：**

1. **`confidence` 这个数值在全文没有定义** —— §5.4 有个 `"confidence": 0.87` 字段，
   但没有一句话说它从哪来（模型自报？logprobs？校准后概率？）
2. **没有校准就没有意义** —— 要校准得有标注集，第一阶段没有
3. **它被用来决定要不要打扰法务**，而「0.87」和「0.70」对法务是同一个意思

**新设计 —— 三值证据状态：**

| 证据状态 | 含义 | 出口 |
|---|---|---|
| **命中确定** | 规则命中且判据明确 | 按最高严重度出状态 |
| **疑似需人看** | 有信号但不能定论 | 转人工 |
| **无确定命中** | **没有任何规则命中** —— 但**这还不是一种状态，是一种待判** | 靠**覆盖证明**再拆成两种，见下 |

> ⚠️ **命名更正**：我第一版把第三态叫「**未评估**」—— **那个名字是错的。**
> 它下面装着 `CLEAN-CANDIDATE`（**已评估**且干净），
> 于是「未评估」这一格里出现了一个「已评估」的东西 —— **状态语义自己矛盾。**
> 上位名必须是**中性的**（「无确定命中」/「未命中」），
> **「评没评过」是下一层靠覆盖证明回答的问题，不是这一层的名字。**

**「无确定命中」必须再拆成两种**（原设计把它们压成了一种）：

| | 含义 | 判据 | 处置 |
|---|---|---|---|
| **`CLEAN-CANDIDATE`** | **已评估且干净** —— 确实按某规则版本、对某些模态跑过了 | **有覆盖证明** | 可走业务自审，**但不自动发布** |
| **`UNASSESSED`** | **没有能力评估** —— 这个模态 / 这个规则域根本没跑 | **无覆盖证明** | 强制人工 + 进空白清单 |

**每个结论必须附带「覆盖证明」，至少四项：**

```
评过的模态      文本已评 / 图内文字已评 / 画面语义未评 / 音轨未评
规则版本        本次用的是哪一版规则（版本号 + 指纹）
适用控制点      七个控制族里，哪几个本次真的跑过
未跑的为什么    无能力 / 无规则 / 未接线
```

> **为什么这一项不能省**：没有它，
> **「审过了没问题」和「压根没审」在系统里长得一模一样。**
> 而这个形状**已经真实发生过一次**：291 条广告里 59 条（20.3%）是无文案格式，
> 其中 **55 条被渲染成了 `合规·绿 / 无需处理`**（另有 2 条落「待复核·灰」、2 条整行空白）——
> 「没有文本可判」被记成了「确认合规」。这 59 条近 7 天**在花 $15,747**。
>
> ★ **口径说明**：「55/59 变绿」与「59 条变绿」是两个数，**我第一版写成了后者**。
> 差的那 4 条说明**机制不是完全失效** —— 但它失效的方式正是最坏的那种：
> **大部分通过、少数被拦住，让整体看起来像是「跑过的」。**

### 2.4 改动三：**状态判定收敛为一张表**（重写 §6.3 的结论汇总与 §6.6 的判定）

**原设计**把判定散在三处：§6.3 的流程图（按层级）、§6.6 的置信度分档（按数值）、§11.1 的指标。
**三处各说一段，没有一张唯一的判定表。**

**新设计 —— 五条一起成立，缺一条就会退化：**

| # | 规则 |
|---|---|
| 1 | **唯一判定表决定状态** —— 只有一处能定 |
| 2 | **最高严重度给「状态下限」** —— 取该内容全部 `status=confirmed` 的 finding 的**最高 `severity`（`L0–L5`）**；命中 `L4/L5` 即为 BLOCK 档，**数量再少也不降级**。**注意三道前置**：`candidate` 不贡献严重度（L2-6a）；`authority_state` 不是 `ok` 时按 §3.3.6 三分法降级；`coverage_state = partial` 时永不 PASS（L1-6）。**不许写成「有 P0 就是 BLOCK」** —— `P` 只表示哪个检测层抓到的，不表示有多严重；一条 `P0` 正则命中可以是 `L2`，一条 `P2` 多模态命中可以是 `L5` |
| 3 | **任何数量不得降级状态** —— 数量只能升级或不变 |
| 4 | **特定共现可升级** —— 组合规则（如「场景名词 + 消除性动词 = 功效承诺」）有权上调 |
| 5 | **普通数量只影响呈现** —— 决定「群里出几句、详情放报告」，**不决定状态** |

> ★ **第 4 条不能省**：如果写成「状态由最高严重度决定」，组合规则就在**文字上被否掉了** ——
> 而它恰恰是抓新型表达的主要手段。

**并且删掉原 §6.6 末句**：「P0 层级规则不适用置信度分流，命中即 BLOCK，**置信度记为 1.0**」。
理由是它把不确定性藏了起来 —— 正则命中「最」会 BLOCK，
但「最」在「**最新**」「**最后**」「**Best Seller**」里都有。

### 2.5 一处行业依据的更正（改 §6.4）

§6.4 引用行业做法作为设计依据，其中写道「第一层快速拦截（关键词、规则引擎**和轻量模型**），……」，
并在另一句里写「先用正则匹配敏感词（**毫秒级响应**）」。

**这句话对文字成立，对本项目的主要场景不成立。** 原因是：

> 图片要 OCR 才有文字，视频要 ASR 才有字幕。**对图片和视频，"那个毫秒级的输入"根本不存在。**

而 §1.1 的业务量分布是：AI 平面素材每日产出、达人内容月均 100–200 条、广告二创月均约 500 条（高峰 3000 条）
—— **主要形态是图片和视频**。

**所以 §6.4 的行业依据应加一句限定**：
「该分层在**纯文本流**上成立；对图片/视频，第一层的前提是先做 OCR/ASR。
因此本项目的实施顺序是**先建归一化层（即 §1.2 提到的结构化中间表示，运行契约名 `ContentUnit v1`），再建分层**。」
（★ 上游没有「归一化层」这个概念 —— 它是本 PRD 新增的一层，定义见 Playbook §2 的 L1。）

## §3 · 知识库与规则体系（重写 §7）

### 3.1 原设计的核心问题

§7.1 定义了四类知识库（外部标准库 / 内部正负样本库 / 措辞表达库 / 产品描述库）。

**问题是：这四类不能回答「谁管的」。** 一条 FDA 法规和一条 Amazon 政策会同落「外部标准库」，
而它们的**复核人、条款引法、变更频率全不同**。

**实测的现状**：知识库不是「一个库缺材料」，而是**五条互不连接的入库通道**：

| 通道 | 条数 | 材料来自哪 | 出处字段指向 |
|---|---:|---|---|
| ① 外部标准库 | 62 | **直接网上调研** | 8 个外部网站（FDA/FTC/Amazon/Google/Meta/TikTok）|
| ② 规则库 | 50 | ①的投影（逐字节相同）| 同① |
| ③ 负面样本 | 183 | **飞书群「设计审核」扫描** | `来源` 183/183 全是该群 |
| ④ 材料收集 | 32 | **对接人手工提交**（**14 人**，实测去重）| 飞书节点 |
| ⑤ 主 Base 规则源 | 21 | **W1卖点表达边界 / 红绿灯 xlsx** | `依据来源` |

**交叉核验（两条都是空集）：**

```
材料收集的标题 ∩ 外部标准库的「来源文档」  = ∅
负面样本的「来源群」∩ 材料收集的标题      = ∅
```

> **不是「材料收上来了没蒸馏」—— 是外部标准库根本没从材料里长出来。**

### 3.2 新设计：按**权威来源**分层 + 一张来源登记表

**主轴改为权威来源**（废掉原四类作为主轴，四类降为副轴）：

| 层 | 内容 | 复核人 |
|---|---|---|
| **L-FED** 联邦法规 / 机构指南 | FTC · FDA · NHTSA | 法务 |
| **L-STATE** 州法 | 独留车内等 | 法务 |
| **L-PLAT** 平台政策 | Amazon · Google · Meta · TikTok | 平台运营 |
| **L-UK** 英国对照（**非美国法**）| ASA/CAP · MHRA | 法务（仅作对照）|
| **L-BRAND** 品牌内规 | 措辞库 · 设计常识 · 品牌规范 | 品牌 |
| **L-PROD** 产品事实 | 产品手册 · 卖点表 · 各站点 | 产品 |
| **L-CASE** 案例（正 / 负样本）| 设计审核判例 | 设计 + 品牌 |
| **L-TERM** 术语与本地化 | 中英对照 · 母婴常识 | 北美 + 专家 |

> ★ **L-UK 必须单列，不能混进 L-FED。**
> 现在那 12 条英国条目（MHRA 5 + ASA/CAP 7）被标成「英国（对照，非美国法）」，
> **这个标注是对的** —— 混进法规层会让判定引用一部不适用的法。

**每个权威层下必须有二级（机构）**，且实测这一级**已经建好了**：
`外部标准库` 的「法域」列三个取值与「来源机构」**一一对应、无交叉**。

### 3.3 来源登记表（**每条材料必填这五列**）

| 列 | 答什么 | 现状填充率 |
|---|---|---|
| **权威机构** | 谁说的 | 100% ✅ |
| **条款位置** | 去哪一页哪一段核 | **27%** ⚠️ |
| **出处链接** | 原文在哪 | **24%** ⚠️ |
| **复核方式** | 怎么判它对不对 | 新列 |
| **覆盖范围** | 它管哪几类判定 | 新列 |

> **实测的结论**：四条通道里，**只有「外部标准库」具备完整溯源三件套**（机构 + 条款位置 + 出处链接）。
> 其余三条要接进判定，**缺的正是这三样** —— 这就是蒸馏方案的实际工作量。

### 3.4 一票否决项必须**按权威来源拆开**（重写 §7.3）

> ⚠️ **本节的判据强度必须说清：下表「实际权威来源」那一列是判断，不是实测。**
>
> 实测的事实只有一条：**`FMVSS` / `Lanham` / `纺织品` 在全仓（除本文件外）零出处**。
> 也就是说 —— 下面这些法源归属**是我基于一般认知写的，仓库里没有可核的原文支撑。**
> **正确状态是「待法务逐条确认并给出条款位置」，不是「已验证」。**
> 同理，本节的行业标准引用（Santa Clara / WEF / FTC claim 分类法）在 `research/governance/R4-trust-and-safety-ops.md`
> 等处有逐字原文，那部分**是可核的**；而法条部分**不是**。

**原 §7.3 把七条并列**，而它们落在四个完全不同的位置：

| 原条目 | 实际权威来源 | 能不能叫「红线」 |
|---|---|---|
| 医疗功效宣称 | **FDA** 预期用途 + **FTC** 实证要求 | ✅ 是法（需语义判定）|

**必须单说的一条 ——「绝对化用语」的落位是错的**：

> 「最 / 第一 / 最佳」这张**词表**的形态（把超级形容词本身列为禁用词）**是中文广告法的做法**。
> 这个观察来自**词表本身的构成**（`最、第一、最佳、100%、纯天然` 是中文表述），
> 不来自任何美国法原文的比对。
>
> ⚠️ **下面两句是待法务确认的判断，不是实测：**
>
> | 判断 | 强度 |
> |---|---|
> | 美国法不禁超级形容词，管的是实证与虚假广告 | ⚠️ **待法务确认**（`Lanham` 全仓零出处，`§43(a)` 未能核实）|
> | `100% cotton` 在美国属 FTC 法定成分披露、写在标签上是合规义务 | ⚠️ **待法务确认**（`纺织品`/`成分披露` 全仓零出处）|
>
> **这两条是「结论的落位」依据，不是「结论」本身。**
>
> **结论**：正确落位是 **语义检测（检测层 P1）+ 依据改成 FTC 的实证要求**，
> 而不是字面词表（检测层 P0）+ 一份中文词表。
> 换句话说：**结论对（该拦），依据错（引错了法）。**
>
> ★ **盘上已经有人发现过这件事**：主 Base 规则源的 H05 写着
> 「（best/#1/No.1/最佳/最好等排名最高级**按 2026-09-09 口径放开**，海外广告允许，不再判险）」。
> **但规则行为仍在拦** —— 见 §4.4。

**新设计的 §7.3 结构：**

```
法规层（authority_source = L-FED / L-STATE；confirmed 且 authority_state=ok 且 severity ∈ {L4,L5} → BLOCK）
  ├─ 联邦法规：FDA 预期用途 · FTC 实证要求 · CPSC 产品安全
  └─ 州法：独留车内 · 肖像权（州州不同，需逐州登记）

平台政策层（authority_source = L-PLAT；按渠道适用；满足同一 L4/L5 + ok 条件才 BLOCK）
  └─ Amazon / Google / Meta / TikTok 各自的禁投项

品牌内规层（不 BLOCK，转人工）
  └─ AAP 建议类画面规范 · 品牌调性 · 措辞建议

待法务补依据（**暂不进判定链**）
  └─ AI 深度合成标识
```

>
> **上面每一条的具体条款引用（第几条、哪一页、生效日期），本文件不写。**
>
> 理由：那需要查原文逐条核对，是**法务的工作**，不是文档撰写者能凭记忆填的。

### 3.5 与引擎的接口（**新增一节**）

知识库最终要能供规则使用。三套编号必须先合一：

| 体系 | 在哪 | 条数 | 谁在读 |
|---|---|---|---|
| **H/M/U/V 码** | 主 Base「品线内容边界规则库」| **21** | ✅ **引擎正在读** |

## §4 · 人工复核与 sign-off（重写 §9）

### 4.1 四个必须补的机制

原 §9 只写了「REVIEW 转人、PASS 转 sign-off、BLOCK 返回修改」，**末句确实写了回流**
（「人工复核结论回流知识库，更新规则权重和正负样本」，§4 流程图末行同样写「发布 / 记录回流知识库」）。

**所以问题不是「没有环」，是「有环但没有转轴」** —— 那句回流承诺**没有任何数据通路支撑**：

- §10.1 的记录字段里**没有 `rule_id`，也没有 `risk_items`** —— **回流的输入不存在**
- 实测：70 条生产记录里，**人工复核人 0/70、复核结论 0/70、sign-off 人 0/70**
- 报告链接那列写的是「审查报告」四个字 —— **不是 URL**

> **一句话**：上游写了环，但环上那两个齿轮（附人工结论的记录、按规则维度的统计）**都还没造。**

| 字段 | 填充率 |
|---|---|
| 人工复核人 | **0 / 70** |
| 复核结论 | **0 / 70** |
| sign-off 人 | **0 / 70** |
| 送审版本 | **0 / 70** |

**70 条生产记录，人工环一个人都没填。** 报告链接那列写的是「审查报告」四个字 —— **不是 URL**。

**新设计，补四处：**

| # | 机制 | 解决什么 |
|---|---|---|
| **①** | **路由表**：依据来源 → 复核人 | 现在「转法务 / 医学 / 专家 / 北美」**谁判该转谁没定义** |
| **②** | **申诉通道** | 现在内容方唯一动作是「修改后重新提交」= **必须先认错** |
| **③** | **超时升级** | REVIEW 转出去之后专家不回会怎样？**没有任何一行在盯** |
| **④** | **版本一致性改为机器判** | 现在靠人工版本号 `"v1"`，见 4.3 |

### 4.2 路由表与申诉（对齐已有的处置五层）

处置分层已经建成并有法务确认，本 PRD 直接引用：

> ⚠️ **「终结」这个词在本文件里指三件不同的事，必须先分开** ——
> 我第一版把它们压成了一个「机器可否终结」，而那与源文件对不上：
>
> | 概念 | 答什么 | 源文件字段 |
> |---|---|---|
> | **① 可完成一次判定** | 机器能不能走完流程给出判定 | — |
> | **② 可终结处置** | 这一层的处置由谁结 | `can_finalize` |
> | **③ 可独立放行** | 机器能不能让内容上线 | `machine_may_finalize` + `human_must_see` |
>
> **源文件实读**（`disposition-layers-v1.json`）：
> `DP0 can_finalize=false` · **`DP1 can_finalize=true`** · `DP2 can_finalize=true`
> 而 mapping 侧 `auto_pass → DP1` 的 `machine_may_finalize=false`。
>
> **DP1 的 `can_finalize=true` 指的是「这一层的处置由这一层的人结」**
> （`who=文案提交人`），**不是**「机器可以结」。二者不矛盾 —— **是「谁结」不同。**

| 层 | 名字 | 谁接 | ② 处置由谁结 | ③ 机器可否独立放行 |
|---|---|---|---|---|
| DP0 | 不可判（无文案格式）| 投放侧 | 投放侧 | ❌ |
| DP1 | 业务自审 | 文案提交人 | **文案提交人** | ❌（机器退出）|
| DP2 | 工具预审 | 机器 | 机器 | ⚠️ **仅拦截方向**（放行待法务核准）|
| DP3 | 内容审核员复核 | 内容审核员 | 内容审核员 | ❌ |
| DP4 | 法务终审 | 法务 | 法务 | ❌ |

**对外标签（五个，对干系人）：**

| 标签 | 落在哪层 | 机器可否终结 |
|---|---|---|
| **BLOCK** | DP2 拦截 | ✅ **可**（唯一可机结的一档）|
| **REVIEW** | DP3；DP4 加「已升级法务」| ❌ |
| **未审查** | DP0 | ❌ |
| **待自决** | DP1（机器退出，责任回到提交人）| ❌ |
| **PASS** | DP1（覆盖证明 + 五条件全满时的干净结论；**附注口径 U8 待法务**）| ⚠️ **机器可输出标签，不可签发/放行**（见 4.5、Playbook §4.2.1）|

**申诉（已有机制，本 PRD 予以确认）：**
受理人是内容审核员（DP3），**2 个工作日**时限，回执编号即案件号，
撤销须附书面理由留痕，争议指向**规则本身**时才转法务（DP4）。

> ⚠️ **这套机制建成、但一条都没真发出去过。**

### 4.3 sign-off 的四项确认，改成机器可判

原 §9 让 sign-off 负责人确认四件事。其中三项保留，**一项必须改**：

| 原确认项 | 处理 |
|---|---|
| Agent 审查记录完整 | ✅ 保留（改为自动检查）|
| REVIEW 已有人工结论 | ✅ 保留 |
| BLOCK 已修改并重新提交 | ✅ 保留 |
| **发布版本与送审版本一致** | ⚠️ **改成内容指纹比对** |

**为什么必须改**：现在 `content_version` 是人工递增的 `"v1"`。
**这是唯一一道防「审 A 发 B」的闸门，而它靠人记。**
新设计用**双指纹**（原件指纹 + 正文指纹），机器直接比对。

### 4.4 一处生产环境正在发生的矛盾（**必须解决，不是设计问题**）

实测：`广告文案明细` 291 条里，**12 条**的 `命中原因` 写着：

> H05 虚假安全承诺（best/#1/No.1/最佳/最好等排名最高级**按 2026-09-09 口径放开**，海外广告允许，不再判险）

而它们的 `风险等级` **全部**是 `高危·红`，`处理状态` 全部 `待人工复核`。

96 份《内容审查报告》里有 **15 份**复述了这句「放开」，结论却是 **BLOCK**。

**规则文本声明它已放开，规则行为仍在拦。两端都在生产里，没有任何东西会红。**

**必须做的**：定一个口径（放开还是不放开），然后让规则文本与规则行为一致。
**这不是文档问题，是生产事故** —— 它意味着要么 12 条被误拦，要么规则库口径没生效。

### 4.5 一处待法务核准的源头冲突

回读处置分层的源文件，**两处打架**：

| 出处 | 原话 |
|---|---|
| DP2 层的说明 | 「机器的终结权是**单向**的……**机器不能独立放行一条内容**」|
| DP2 的映射 `auto_pass_with_note` | `machine_may_finalize: true`、`final_action: 附注放行` |

**且那一行的背书弱**：它的来源标注是「D1 之前的既有落点，法务 2026-09-16 未改动」——
**无编号**。而法务逐条确认的四条里，**只覆盖「允许机器独立拦截」**。

**本 PRD 采用更严的读法**（与 ADR-0005 约束 2 一致：Agent 永远不能把状态改成「无需处理」）：

> **机器唯一能独立终结的是 BLOCK。**「附注放行」（对外标签 `PASS`）**暂不作为机器可签发的动作**，
> 直到法务就这一档给出口径。

## §5 · 记录、统计与准确性（重写 §10–§11）

### 5.1 记录（改 §10.1）

原 §10.1 的记录字段**缺两样关键东西**，导致 §9 那句「回流知识库、更新规则权重」没有输入源：

| 缺什么 | 后果 |
|---|---|
| **`rule_id` / `control_code`** | 无法回答「这条规则被推翻过几次」|
| **`risk_items`（问题明细）** | 无法做案例回流 |

**新增必填字段：**

```
控制点 control_code        违反了哪个控制点
依据 authority_ref          凭哪条依据
问题明细 risk_items[]       每条含：控制点 · 位置 · 原因 · 依据链接 · 建议
覆盖证明 coverage_receipt   本次评过什么、没评什么
```

**另加一条**：§5.3.5 写「报告链接有效期 ≥ 30 天」，而 §10.1 写「记录保存 ≥ 1 年」。
**一年后复核时报告已打不开。**
**改为：报告链接有效期 ≥ 记录保存期**，且**结构化记录是唯一真相**，报告是它的渲染视图 —— 链接坏了能重建。

### 5.2 指标（重写 §11.1）

**原三个指标：**

| 原指标 | 问题 |
|---|---|
| 整体三态准确率 ≥ 90% | 若 PASS 占九成流量，**一个永远输出 PASS 的系统就是 90%**。不防退化 |
| BLOCK 精确率 ≥ 95% | **少 BLOCK 就能达标**；且对最高伤害层要求精确、放松召回 —— **方向反了** |
| `L4/L5` 漏报率 = 0 | 与「字面规则层无需大模型」互斥，做不到 |

**新设计 —— 四个可测数：**

| # | 读数 | 为什么是它 |
|---|---|---|
| **①** | **`L4/L5` 召回**（冻结回归集 + 抽检出的漏报）| 唯一防「漏」的指标 |
| **②** | **`L4/L5` 误判率**（**必须带样本量 n**）| 唯一防「误拦」的指标 |
| **③** | **未覆盖占比** | **唯一会随系统成长而变化的指标** —— 规则库空着时接近 100%，建起来后应下降 |
| **④** | **人工推翻率** | 所有人工结论里推翻机器的比例 |

**关于 ②**：小分母上的比率更抖。
**「2%（n=48）」和「2%（n=4）」是两个完全不同可信度的读数** —— 不带 n 的比率是假精度。

**关于 ④ 的分母口径**：**申诉的胜与败都进分母。**
否则统计里只剩「坐下来复核并改了结论」那部分，
**提了异议被驳回去的完全不在样本里** —— 这是幸存者偏差。

### 5.3 抽检（改 §10.3）

**原设计**：「每周抽检已 **PASS** 内容 ≥100 条或 5%」。

**问题**：四个数里 ② 的样本只在 **BLOCK** 那批里，而抽检只抽 PASS —— **② 永远没有样本。**

**改为分层抽检（与 Playbook §6.1 / 验收表 #81/#88 对齐）：**

```
非 BLOCK 四层（PASS / 待自决 / REVIEW / 未审查）各自独立抽样 → 查漏报（①）
BLOCK 层 100% 全量复核                                     → 查误报（②）
```

> ★ **为什么是四层而不是只抽 PASS**：漏报不只藏在「说没问题」里，
> 也藏在「说需要人看」（REVIEW）与「没审」（未审查）里；只抽 PASS 会让这三层的漏报永远没有样本。

### 5.4 覆盖率（**推翻 §10.2 的结论**）

原 §10.2 写「**不统计覆盖率**，因为需要人工登记应审总数，轻量跑不现实」。

**这个理由不成立。** 它以「群里 @Agent 的不可穷尽性」，推广到了**全部入口**。
而 §5.1 的方式二（多维表批量）和 §8.2 的入口**分母是可数的**。

**且现在有更硬的理由要测它**：本 PRD 的能力分级（§15）需要知道「浅档有多少」。
**放弃覆盖率，等于放弃了唯一能回答「漏了多少」的指标。**

### 5.5 金标准（新增）

| 来源 | 作用 |
|---|---|
| **在线回流**（人工复核 + 抽检）| 主力 |
| **最小冻结回归集**（几十条）| **规则改了之后，能在发布前回答「这次是变好还是变坏」** |

冻结回归集**必须含已知陷阱负样本**：`Best Seller` / `100% cotton` / `最新` / `first-time mom`。
**这些是误杀高发区**（见 §2.2 的语种问题）。

| 图片 / 视频 | **浅档** | 结论携带「审到哪一层」的声明 |

> **选自动映射的理由**：**映射表本身就是判据** ——
> 可以断言「每条输出的档位 ≡ 它的 `content_type` 查表所得」，不需要新能力，改档只改表。

### 6.3 逐档验收表

| 档 | 覆盖 | 必须达到 | 未达到时 |
|---|---|---|---|
| **深档** | 文字 / brief | ① 分类：控制族 → 控制点，二级完整<br>② 归一化：`ContentUnit`（**不是 IR**）+ 双指纹 + 覆盖声明；运行级 `ReviewIR` 为唯一真相<br>③ 判定按 `judge_type`（literal/semantic）+ `detected_by`（P0–P3）+ `severity`（L0–L5）三字段分离<br>④ 唯一判定表<br>⑤ 路由表 + 申诉 + 超时升级上线<br>⑥ 四个可测数有读数 | 红 |
| **浅档** | 图片 / 视频 | ① 图内文字（OCR）进同一套规则<br>② 画面语义出**候选**（不终结）<br>③ **输出里显式标注「未做区域级审计」** | 红 |

> ### ⚠️ 浅档的地板条款
>
> **浅档的结论里不能出现 PASS 而不带标注。**
>
> 浅档不是「没审」，是「审了、且说了审到哪一层」。
> **一个视频拿到浅档结论，必须能在输出里读出「区域级没审」，
> 而不是读到一句「未发现问题」。**
> 这两句话在群里长得一样，但是两回事。

### 8.2 已建成的输入契约：内容单元（ContentUnit）

**这是全项目最成熟的一层**，且它解决的是一个真问题：
**任意形态的内容 → 同一种可判、可溯、可复现的东西。**

| 契约要素 | 内容 | 为什么 |
|---|---|---|
| **12 个必填字段** | `contract_version` / `unit_id` / `content_key` / `source` / `fingerprint` / `normalization` / `composition` / `textification` / `text` / `has_text` / `routing` / `context` | — |
| **双指纹** | `raw_sha256`（看的是哪份原件）+ `text_sha256`（重跑能不能得到一样的数）| 实测：4 个页面各抓两次，**原件变 4/4、正文变 0/4** |
| **14 条不变量 H1–H14** | 含 H4「`text_sha256` 必须等于 `sha256(text)`」、H11「逐字可核」| 一个单元离开来源之后仍能自证 |
| **`source.kind` 封闭取值域** | `ad_text` / `free_text` / `landing_page` / `structured_json` / `image` / `video` | 加新形态要同时改契约、schema 与一条 builder |
| **`textification.covers` / `does_not_cover`** | **必填、刻意无默认值** | 理由原文：「一个默认的 `covers` 会让『只做了 OCR』看起来像『视频已审』」|

**`has_text` 是路由输入，不是判定输入。**

> ⚠️ **但它不是 DP0 的充分条件（我第一版把它当成了充分条件）**：
> `failed` / `empty` / `unsupported` **都会让 `has_text=false`**，
> 而它们的**原因与责任完全不同**（取不到 vs 取到了没内容 vs 这个形态没能力处理）。
>
> **正确的路由判据是两个字段合起来看：**
>
> | 判据 | 去哪个状态 | 责任 |
> |---|---|---|
> | `has_text=false` **且** `source.kind` 已知是「无文案格式」 | DP0 不可判 | 投放侧（该格式）|
> | `has_text=false` **且** `parse_status=failed` | 【未审查】+ `FAILED` | 投放侧（工具/素材问题）|
> | `has_text=false` **且** `parse_status=partial` | 可进判定（限已覆盖部分）| — |
> | `has_text=false` **且** 形态本层无能力（如视频→画面语义）| 【未审查】+ `UNTESTED` | 产品（能力缺口）|
>
> **存量 291 条里 59 条 `has_text=false`** —— 它们**全是** Google 产品广告（PLA），
> 属第一行（无文案格式）→ DP0。

### 8.3 真实缺口（按性质分，全部有实测出处）

**① 有但没接 —— 这条最要紧，因为它让「审过了」变成假的**

| 缺口 | 实测证据 |
|---|---|
| **图片 OCR 结果进不了判定语料** | `base/media.py:367` 定义了 `row_to_unit()`，**全仓零调用点**。实测 `source_kinds` = `{ad_text 291, landing_page 92, structured_json 44}` —— **427 个单元里没有一个是 image 或 video** |

> ★ **这一条的意义**：图片的 OCR 结果**已经能生产出来**（有 `ocr_vision.m`），
> 但**没有桥把它送进判定**。也就是说 —— **今天的「图片已审」是假的**：
> 要么根本没进链路，要么进了但用的是一个空正文的单元（同下面 ②）。
> **这就是「有但没接」比「完全没有」更危险的地方：它看起来像是做完了。**

**② 反而更隐蔽的一类 —— 失败被静默吞掉**

| 现象 | 实测 |
|---|---|
| 落地页解析异常**从不写回产出** | `tools/lp_extract.py:155` 把 `parse_error` 设在 **parser 对象**上，而 `analyze_html()` 的返回 dict **不含该键**，`main()` 也从不读它 |
| 结构化 JSON 解析失败**无法与「本来就没字段」区分** | `analyze_structured()` 在 json 异常或非 dict 时**静默 `return None`**；下游 `from_landing_page()` 收到 `None` 会给出一个**空正文单元**（`has_text=False`），失败原因在单元里**不可见** |

> ★ 这两条是同一个病：**「解析失败了」和「本来就没东西」长得一模一样。**
> 而单元层有个结构性理由让它更难修：**失败观测不产出单元**（`from_landing_page` 找不到成功记录直接 raise）。
> 所以「某类素材缺失」**在单元层没有表示**，只出现在报表层（`cannot_measure` / `not_measured` / `no_sample`）。

**③ 完全没有**

| 缺口 | 证据 |
|---|---|
| **视频素材通道** | 49 条视频广告（近 7 天 **$5,110**）的素材**一个字都没看过**；本机 **0 个视频文件**（`find *.mp4/*.mov/*.webm` = 0）|
| **画面语义** | `media.py` 图片单元的 `does_not_cover` 第一条即「**画面语义**：构图、画面暗示功效、品牌调性、模特状态」|
| **VLM / 多模态模型调用** | `base/` 与 `tools/` 无任何实现；图片通道走的是 **Apple Vision OCR**（`base/ocr_vision.m`）<br>★ **现状背景，不是阶段一目标路线**：阶段一生产形态已定为 Docker Compose + 容器内跨平台 OCR/ASR（Playbook TS-15/TS-16），本机 Vision 读数**不得沿用** |
| **Word / PDF 解析** | 源码 grep 无；`source.kind` 的 6 个取值里**也没有** document/file 形态 |
| **NAS 共享盘通道** | 无任何 NAS/SMB 代码；批量侧只有落地页 URL 一条链路（`tools/lp_fetch.py`）|
| **时间码 / 抽帧** | `video_stage()` 自报：本机无 ffmpeg、无 whisper，抽帧「AVFoundation 可做但要再写一层 ObjC/Swift」——**均为待办** |
| **「转 md 文档」这个产物形态** | 用户原话是「解析与提取**转化为 md 文档**」，而现有契约的产物是**纯文本 `text`**（归一化不动点），全仓**没有**把输入转成 .md 的实现 |

> ★ **最后一条要说清**：`md` 只出现在**文档/报告层**（`PMO/`、`agent-skills/`），
> 不是内容解析的产物。**这是用户原话与实现之间的一处语义差** —— 见 §10.4。

### 8.4 新增契约：解析失败与素材缺失必须是可读的

**上游没有这一层，而 8.3 的 ② 证明它必要。** 新增三条：

```
① 每个单元必须带 parse_status
     ok       正常解析
     partial  解析到了但覆盖不全（必须带 covers 说明缺什么）
     failed   解析失败（必须带 failure_kind 与失败原因）

② failure_kind 封闭取值域
     fetch_error      取不到（网络/权限）
     parse_error      取到了但解析不了（结构不符/格式异常）
     empty            取到了、解析了、但没有可判内容（★ 与上两种必须分开）
     unsupported      这个形态本层没有能力处理（如视频→画面语义）

③ 「素材缺失」必须能被数出来
     不允许「找不到就是没有」—— 缺失要落一条显式记录，否则缺口率无法统计
```

**判据（可机验）：**

| # | 断言 |
|---|---|
| **B1** | `parse_status = failed` 的单元**不得**进入判定（它没有可判内容）|
| **B1b** | `parse_status = partial` 的单元 **可以**进入判定，**但只在其已覆盖的部分上**；且不得产出 PASS，其结论必须带「覆盖不全」标记 |
| **B2** | `parse_status = failed` 的单元**不得**产出三态结论 —— 它只能落「未审查」 |
| **B3** | `failure_kind = empty`（取到了但没内容）与 `failed`（没取到）**必须能被分别数出来** |
| **B4** | 每次运行的报告里，四种 `failure_kind` 的**条数必须出现**（哪怕全是 0）|
| **B5** | `partial` 的单元，其 `coverage_receipt` **必须**列出「哪些模态/字段没覆盖到」；列不出就降为 `failed` |

> ⚠️ **B1 的第一版是错的，必须记下来。**
> 我原写「任何 `parse_status != ok` 都 `has_text = false`」——
> 那**等于让 `partial` 的已解析文本一个字都不进审查**，
> 而这与「浅档」「覆盖证明」的整个设计冲突（那套设计的目的恰恰是**让部分覆盖也能被审、只是标明覆盖面**）。
>
> **正确的三分：**
>
> | parse_status | 能不能进判定 | 能不能出 PASS |
> |---|---|---|
> | `ok` | ✅ 全量 | ✅ |
> | `partial` | ✅ **仅已覆盖部分** | ❌ **永不出 PASS**（必须带「覆盖不全」）|
> | `failed` | ❌ | ❌（只能落「未审查」）|
>
> **判据的形状**：不是「有缺就不许用」，而是「**用了就必须标明缺哪儿**」。

> ★ **B4 是防「静默归零」的那一条**：一个从不出现的字段和一个恒为 0 的字段，
> 读起来一样；只有强制出现在报告里，才能区分「没有失败」与「这一项没人统计」。

### 9.2 三个部件各自的职责（**这是本节的核心**）

用户原话里有三个名词，但它们的角色从未被定义过。**照实说清：**

| 部件 | **不是**什么 | **是**什么 | 证据 |
|---|---|---|---|
| **skill** | ❌ 不是可加载的运行单元 | ✅ **一份操作规程** —— 「任何 agent（或人）按这一页就能调起一次审查」 | `agent-skills/内容合规审查/SKILL.md`（138 行）：§一 何时用 · §二 30 秒命令 · §三 契约 9 个顶层键 · §四 DP0–DP4 五层表 · §五 六条失败形态 · §六 明确不做 · §七 回执 · §八 收工前 4 条自证 · §九 自腐检查 |
| **规则库** | ❌ 不是召回器 | ✅ **确定性判定 + 落层**：`score.Engine.assess()` 决定**命中**，`judge.resolve_layer()` 决定**落哪一层** | `assess()` 在 `score.py:406`；`resolve_layer()` 在 `judge.py:337`；次序 = 前置条件 → 落点 → 升级 |
| **知识库** | ❌ 今天**不是**证据源（未接线） | ✅ **应该是证据源**（设计上），产出「违反了哪一条具体条款」 | `judge_evidence.mjs` 已实现、未接线；回执账本里唯一带 `evidence_ref` 的一条来自 CLI 演练 |

> ### ⚠️ 一处必须先定的取舍
>
> **知识库到底是「证据检索」还是「裁决源」？**
>
> 本文档的建议是 **只作证据检索**，理由：
> 裁决权已经在规则库（确定性）与处置层（人）手里，
> **再给知识库一个裁决权，就等于引入第三个裁决者，而它没有严重度概念。**
>
> 且这与「机器仅可拦截、不可放行」一致：
> **知识库能提高「拦得准」，但不应单独产生「拦」这个动作。**

#### ⚠️ 但「只是补证据」还有一个必须定的方向：**补不到证据时怎么办**

**这是一个我刚发现的洞**：上面只说了「知识库不产生拦」，
**却没说「它该补的证据补不到时，那条已有的命中还算不算数」。**

三种情形，必须都有出口（**默认方向是 fail-closed，不是 fail-open**）：

| 情形 | 处置 | 为什么 |
|---|---|---|
| **找不到 `authority_ref`**（该控制点没有对应条款）| **转人工**，**不得**保留原命中的机结资格 | 「拦了但说不出凭哪条」= 无法复核，等于误拦 |
| **找到的条款互相冲突** | **转人工**，并**同时列出冲突的两条** | 冲突是规则库该修的信号，不是机器该裁的事 |
| **条款已过期**（版本超期）| **转人工**，并在回执里标明「依据版本已过期」 | 拿过期条款拦人，与引错法同族 |

> ★ **判据的形状**：**默认方向决定失败时往哪边倒。**
>
> | 方向 | 后果 |
> |---|---|
> | fail-open（补不到就当证据充分）| 机器**拦错了也没人知道** —— 与「机器仅可拦截」的初衷相反，因为拦截权本应建立在「说得出凭哪条」之上 |
> | **fail-closed（补不到就转人工）** | 慢，但**不会凭空产生一条无法复核的 BLOCK** |
>
> **本节取 fail-closed。** 这与 §2.2 的 A7（`authority_ref` 必须可解析）是同一条原则的两次落地：
> **「凭哪条」答不出来，就没有机结资格。**

### 9.3 循环体：每一个环节做什么

> ### ⚠️ 先说清一件事：**下面画的到底是 loop 还是 pipeline**
>
> 我第一版把它叫「loop 的循环体」，但那份图**每一步只跑一次、没有回边** ——
> **那是 pipeline，不是 loop。** 而「同一内容连续 2 轮无进展」这个停机条件，
> 在 pipeline 里**根本不可能发生**。这是自相矛盾。
>
> **两种形态要分清，因为性质和代价完全不同：**
>
> | | pipeline（单向）| loop（带回边）|
> |---|---|---|
> | 每一步 | 跑一次 | 可能重跑 |
> | 代价 | 可预测 | **不可预测**（回边可能不收敛）|
> | 需要什么 | 步骤清单 | 步骤清单 **+ 回边条件 + 最大轮次 + 收敛判据 + 震荡检测** |
> | 风险 | 无 | **震荡**（A 轮说补证据、B 轮说证据不足，来回横跳）|
>
> ### ✅ 已定（委托方 2026-10-17）：**第一阶段做 pipeline，预留一次回边**
>
> 这一条原本写的是「本文建议」—— 现在它**是决定，不是建议**。
> 决定内容：**每步跑一次；回边的规格先写好但不接线**（规格见下方）。
>
> 理由三条：
> ① 判定引擎今天是单次纯函数，加回边等于改引擎性质；
> ② 回边最大的价值是「证据不足时重新取证」，而**取证能力（§8）今天还不全** ——
>   先补齐能力，再加回路；
> ③ **不收敛的 loop 比没有 loop 更危险**：它会烧掉成本且产出不确定的结果。
>
> ★ **一处用词纪律（因为已定 pipeline，所以必须说清）**：
> 委托方原话是「loop 审计」，而**第一阶段实现的是 pipeline**。
> 因此在本文件里：
>
> | 说法 | 能不能用 |
> |---|---|
> | 「审计流程」「管线」「每个环节」| ✅ 可以 |
> | 「审计 loop」用来说**设计意图** | ✅ 可以，但**必须同句说明第一阶段是管线** |
> | 「审计 loop」用来说**实现完成了什么** | ❌ **不可以** —— 会让人以为有一圈在转 |
>
> **将来真要切成 loop，必须同时定这四样**（回边条件 / 最大轮次 / 收敛判据 / 震荡检测）——
> 下面已经写好规格，**照它做即可，不必重新设计**。

**当前没有循环，所以下面是设计，不是描述现状。** 逐条说明它对应哪个缺失。

```
步 1  预处理（定档）
        输入：内容单元（§8 契约）
        动作：定档（深档/浅档，按 content_type 自动映射，见 §6.2）
        产出：本次「要跑哪些控制点」的清单
        ★ 这一步的产出就是 §2.3 的「覆盖证明」

步 2  确定性判定（规则库）
        输入：单元的 text
        动作：Engine.assess() → 命中列表
        产出：hits[]（每条带 control_code + 位置 + 逐字片段）
        ★ 这一步已经建成，且是唯一有 α 实测的一步

步 3  证据补全（知识库）—— ⚠️ 未接线
        输入：hits[].control_code
        动作：按依据来源查条款位置 + 出处链接
        产出：每条命中带 authority_ref
        ★ 这就是 judge_evidence.mjs 要做的事，它已写好、没有调用者

步 4  语义判定（浅档）—— ⚠️ 未实现
        输入：图片 / 视频（经 §8.5 的通道）
        动作：多模态模型出候选
        产出：候选（**不是结论**，必须转人工）
        ★ 与 DP3 的定义一致：「机器给出的是候选与证据，不是结论」

步 5  合并与定状态
        输入：步 2–4 的全部产出
        动作：唯一判定表（§2.4 的五条）

```

> **回边规格与 E1–E4 已移出本节**，统一放在文末 **`## 附录 F · 未来能力（非阶段一 · 不进入验收）`**。
> 第一阶段只执行上面五步单向 pipeline：无回边、无轮次、无提前停。

### 9.4 停机条件（**用户工作流里没有定义，这是缺口③**）

| 条件 | 什么时候算 | 谁判 |
|---|---|---|
| **正常完成** | 清单里的每一个控制点都跑过（**不管有没有命中**）| 机器 |
| ~~**提前停（拦）**~~ | ⛔ **第一阶段不启用（预留）**：即使命中字面规则且满足机结三条件，也**跑完全部控制点**（Playbook §3.3.7 2026-10-18 改定）| — |
| **转人工** | 出现「疑似」、或出现「未覆盖」、或 `parse_status != ok` | 机器提出，人接 |
| **工具失败** | 抓取/解析/模型任一失败 | **不得静默跳过** —— 出口见下方专段 |
| ~~**无进展**~~ | ⛔ **第一阶段不启用（预留）**：pipeline 无回边时不存在「第二轮」，该条件不成立 | — |
| **超时** | 超过约定时限仍无人接（见 §4）| 升级到项目统筹 |

#### 工具失败的完整出口（**我第一版只写了「落 failure_kind」，那不是一个出口**）

**「记录下来了」不等于「有人管」。** 四件缺一不可：

| # | 要件 | 内容 |
|---|---|---|
| **1** | **状态** | 落 `FAILED`（工具失败）或 `UNTESTED`（没跑）—— **两者都不是三态标签，是运行状态** |
| **2** | **责任队列** | 进「工具失败队列」，**有负责人**（不是 `—`）|
| **3** | **重试与死信** | 重试上限 **3 次**；超限落死信，**且死信不能只写在日志里** |
| **4** | **人工接管** | 死信进人工队列，**与 REVIEW 同一条队列**（不能另开一条没人看的）|

> ★ 这四条的形状取自本项目已有的 `retry_queue.mjs`（`MAX_TRIES=5` / `WINDOW_MS=60min`），
> 但它有一个洞：**死信只在日志里说，没有队列、没有负责人。**
> **照搬它的参数，补上它缺的那一环：死信必须进队列。**

> ★ **「无进展」这一条是从 PolySafe 的反面学的**：
> 它的批次把 `error` 与 `review` 都算作终态，于是**全错的批进度条也能到 100%**。
> **跑完 ≠ 全部有结论** —— 我们的终态集合必须把失败与待人工**排除在「完成」之外**。

### 9.5 一处必须写清的架构事实

> ✅ **已裁定（委托方 2026-10-17，J1）：skill = 规程 + 唯一编排器 + 执行回执。**
> 即：SKILL.md 是**给人/agent 读的规程**；选择与排序由**唯一编排器**（`skill_registry`）负责，
> 按 `skill_id/version/sha256` 校验并产出**父子执行回执**（`skill_runs[]`）。
> 下面三选一是**起草时的背景讨论**，不是仍未决的选项。

**skill 不是「运行单元」，所以「谁选 skill」曾是一个未决问题。**

三种可能，当初需要定一个：

| 方案 | 含义 | 代价 |
|---|---|---|
| **A** 外部编排器选 | 由调用方（人 / 守衡 / 将来的编排服务）按场景挑一份 SKILL.md 执行 | 不需要新组件，但**「选对了没有」没有任何东西在验** |
| **B** 把 skill 变成可加载单元 | 定一个 `skill.json` 之类的契约，运行时真的读取 | 要改口径（今天 SKILL.md 是给人读的散文 + 可执行命令块）|
| **C** 不引入 skill 概念，只留规程文档 | 承认它是一份文档，编排逻辑写在别处 | 最小，但用户原话里的「skill」就没有落点 |

> **代价仍然成立**：无论哪种形态，**「用对了 skill 没有」必须能被回执验证**；
> 否则就是本项目已经栽过的那类坑（规则文本声明与规则行为不一致）。

## §10 · 输出层：从结论到群里那条回复（重写 §8）

> **上游 §8 只写了「Agent 回复三态结论、支持 @Agent、支持批量扫描」**，
> 没写「那条回复长什么样、谁决定它长什么样、写坏了怎么办」。
> 而本项目的输出层**已经建成且是全仓最成熟的一块** —— 本节主要是把它写进 PRD。

### 10.1 两个产物，一个源

| 产物 | 给谁看 | 地位 |
|---|---|---|
| **飞书卡片 / 文字** | 群里的人 | **渲染视图** |
| **报告** | 点进链接的人 | **渲染视图** |
| **结构化记录（运行级 `ReviewIR`）** | 机器 / 统计 / 复核 | ★ **唯一真相** |

> **为什么必须是这个关系**：链接会坏、有效期会过、群里那条会被刷走。
> 只要结构化记录在，任何视图都能重建。**反过来不成立。**

### 10.2 卡片机制：模型不写 JSON，只写一个「卡片块」

**这是本项目已经建成的机制，且它防的是一个很贵的坑。**

```
模型输出：一段自然语言 + 一行 [[card:类型]] + 一段 JSON
              ↓
envelope.mjs  extractCardBlock()   括号配对扫描（不是 indexOf('}')）
              ↓
enforceLimits()  超限内容搬进折叠区（**不丢字符**）
              ↓
scrubInternal()  公开格里出现内部标识 → **整段**搬进折叠区
              ↓
capSections()    顶层块数超上限 → 搬进折叠区
              ↓
toCardOrText()   返回 mode: card | text
```

| 要素 | 实测值 | 为什么是这样 |
|---|---|---|

### 10.4 一处语义差：用户说的「md 文档」与实现的「纯文本」

### 11.3 三类已记录的失败（本项目自有的教训，可直接当验收样本）

### 11.4 可借鉴的形状：`staleSince` 与 `recheckDue`

本项目在「重启闸门」那个子系统里已经解决过一次同类问题，
形状可以直接搬到「超时升级」：

| 要素 | 做法 |
|---|---|
| **判据** | `recheckDue(state, t)` —— 纯函数，`t` 可注入 |
| **留痕** | 跳过时写 `staleSince`（**第一次**跳过的时刻，重复跳过不刷新）|
| **触发** | 心跳里 `recheckDue(...)` 为真就叫一次 |
| **反面** | ★ **「冷却过期」本身不能当触发条件** —— 那会让检查从「三处触发」变成「每天 48 次」 |

> **对应到 §4.1 的「超时升级」**：
> 转出去时记 `pendingSince`；心跳里判断「超时且仍无人接」才升级；
> **重复检查不刷新时间戳**（否则永远不超时）。
> ★ 且必须有一条**反向断言**：「没有 `pendingSince` 就永远不许升级」——
> 否则会出现「凭空升级」，与「凭空挑一个群发收尾」是同一个病。

## 附录 F · 未来能力（非阶段一 · 不进入验收）

> ⚠️ **地位声明**：本附录记录的是**未来阶段**的设想（回边 / loop / 轮次 / 提前停 / 震荡检测）。

### F.1 回边规格（仅在将来开启 loop 时适用）

```
回边条件（三选一，且必须显式登记是哪一个）：
  a. 步 2 找不到 authority_ref，且该 hit 严重度 ≥ 高   → 重新取证
  b. 步 3 的候选与步 1 的命中冲突                      → 转人工（不是重跑）
  c. 覆盖证明显示某个控制点本该跑却没跑                → 补跑那个控制点

最大轮次     2（必须封顶 —— 一次回边，不允许无限）
收敛判据     两轮的「状态 + 命中集」完全一致 → 停
震荡检测     出现 A→B→A 的状态循环 → 立即停并转人工
```
