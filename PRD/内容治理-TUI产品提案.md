| **一句话** | 把「审核规则库 + 判定代理 + 人的签核」做成飞书里的一个**可留痕工作台**，而不是又一个会发消息的机器人 |

---

## 0. 先说清楚为什么不是「机器人自动判违规」

我手上这套东西的真实质量数据是：

| 指标 | 实测值 | 含义 |
|---|---|---|
| Precision（自动判定） | **0.970** | 判出去的 3% 是错的 |
| Recall | **0.962** | 3.8% 漏 |
| `CATCH-ALL` 命中率 | **54.6%** | **超过一半的广告落进「未命中任何规则」** |
| 豁免机制可达性 | **45/60 不可达** | 规则文本里写的「允许」，代码里没有住所 |

**「未命中」绝不等于「合规」** —— 这是设计文档 §5.1 的核心立场，也是本产品形态的第一约束。

> **因此：绝对不能做一个「贴进来就告诉你能不能用」的机器人。**
> 它会在 54.6% 的情况下把「我不知道」说成「没问题」，而这比不给结论更危险 ——
> 业务会拿它当背书。

**产品形态必须围绕「判定 + 存疑 + 人类签核」三件套设计。** 下面所有取舍都从这条推出来。

---

## 1. 产品定位

**守衡 = 内容治理的判定台。** 一个完整的 TUI（Text User Interface）形态，由三层构成：

```
┌─ 交互层：飞书 ──────────────────────────────────────────┐
│  卡片（状态机 · 原地更新）· 按钮 · 表单 · 折叠面板       │
│  群 / 单聊 · @ · 置顶 · 表情 · 定时推送 · 多维表格       │
├─ 判定层：守衡 Agent（DSH）──────────────────────────────┤
│  规则库执行 · 管辖归属 · 证据要求 · 一致性(α) · 错题本   │
│  多语言 · 引文核验 · 缺口登记 · 豁免可达性检查           │
├─ 状态层：多维表格 + 云文档 ─────────────────────────────┤
│  判定记录 · 签核留痕 · 版本 · 指标（α/盲区率/升级率）    │
│  规则库本体（带 permit 与依据）                          │
└─────────────────────────────────────────────────────────┘
```

**关键分工**：飞书管**交互与留痕**，Agent 管**判定与解释**，表格管**状态与指标**。
三者不互相渗透 —— 否则会退化成「所有东西都塞在卡片里」的一坨。

---

## 2. 核心闭环：一条广告的生命周期

**这张状态机是整个产品的骨架。** 每个状态都是一次卡片原地更新（`PATCH`），不是新消息。

```
 ① 采集            ② 判定            ③ 存疑            ④ 签核
┌────────┐      ┌─────────┐      ┌──────────┐      ┌──────────┐
│ 提交   │─────▶│ 守衡判定 │─────▶│ 举证责任  │─────▶│ 人工签核  │
│ 文案   │      │ 管辖+等级│      │ 倒置：问 │      │ 通过/驳回 │
└────────┘      └─────────┘      │ 而不是放 │      │ /改口径   │
     ▲                            └──────────┘      └──────────┘
     │                                  │                │
     │                                  ▼                ▼
     │                            ┌──────────────────────────┐
     └────────────────────────────│ ⑤ 回流：错题本 + 口径变更 │
                                  │ ⑥ 度量：α / 盲区率 / 召回 │
                                  └──────────────────────────┘
```

### 各状态的卡片形态

| 状态 | 卡片内容 | 可用动作 |
|---|---|---|
| **① 采集** | 提交表单（卡片 `form`）：文案正文 / 语种 / 品线 / 平台 / 投放地区 | 提交 |
| **② 判定** | 结论徽章（红/黄/灰/绿）+ **管辖叶子** + **证据要求** + 命中规则号 + 折叠的判定链 | 展开证据 · 我要复核 · 一键改写 |
| **③ 存疑** | **不藏「不知道」**：显式写「落进 CATCH-ALL，未命中任何规则」+ 为什么（新表达/新语种/规则边界不清） | 指派给谁 · 挂起 · 升级 |
| **④ 签核** | 三人名单（谁判的 / 谁签的 / 依据）+ 决定按钮 | 通过 · 驳回 · 改口径 · 转法务 |
| **⑤ 回流** | 本次决定对规则库的影响（新增/修改/废弃哪条） | 确认入库 |
| **⑥ 度量** | 周报卡：判定量 / 升级率 / α / 盲区率三维交叉表 | 订阅 · 下钻 |

### 为什么必须「举证责任倒置」

③ 不写「未发现问题」，而是写**「我判不了，请给证据」**。这一条来自行业四个体系 + 一个平台层的共同做法（设计文档 §5.1）。
**产品层面它的体现就是：默认不通过，而不是默认通过。**

## 3. 两条入口

| 入口 | 场景 | 为什么需要它 |
|---|---|---|
| **A. 群内工作台**（已有群） | 业务提问、边界争议、口径讨论 | 讨论**本身就是留痕**。口径是在争论里定的，不是在表单里定的 |
| **B. 单聊私有台** | 单条新文案的预检 | **广告文案是敏感资产。** 未投放的文案进群 = 泄露给所有人（含可能的外部成员） |

**B 不是 A 的附属，是刚需。** 群里有 3 人以上时，预检必须走私聊。

## 4. 能力映射：飞书给什么，我们补什么

### ✅ 飞书直接提供（已实测，见测试报告）

| 基础能力 | 产品用途 |
|---|---|
| 卡片 schema 2.0（markdown / table / 折叠 / 分栏 / button） | 判定结果的呈现，**原生表格直接放三维交叉表** |
| `PATCH /im/v1/messages/{id}` 原地更新 | **一张卡跑完整条生命周期**，不刷屏 |
| 多维表格（权限已开） | 判定记录表、规则库表、指标表 |
| 云文档 / Wiki / 云空间 | 规则库、错题本、标注指南的载体 |
| `@` 提及 / 置顶 / 表情 | 指派责任人 / 钉住争议 / 表情即确认 |
| 群 / 单聊隔离 | 公开讨论 vs 私有预检 |

### ⛔ 需要开权限

| 能力 | 缺什么 | 产品用途 | 优先级 |
|---|---|---|---|
| 通讯录 | `contact:contact.base:readonly` | @正确的人、按部门路由 | P1 |
| 任务 | `task:task:readwrite` | 待处置项派成飞书任务，自动催 | P1 |
| 日历 | `calendar:calendar:readonly` | 口径复盘会排期 | P2 |
| 审批 | `approval:approval` | 口径变更走审批（合规留痕） | P2 |
| 事件订阅 | `im.message.receive_v1` 等 | **所有交互的前提** | **P0** |

### 🔧 我们需要自己建

| 组件 | 为什么飞书给不了 |
|---|---|
| **判定引擎** | 规则库是我们的资产 |
| **管辖归属判据** | `pain relief` 归医疗管辖还是机器性能管辖，决定要什么证据 |
| **豁免可达性检查** | 「允许」必须可审计（这是 CONSULT-001 暴露的问题） |
| **一致性度量 α** | 飞书没有「标注一致性」概念 |
| **错题本 / 缺口登记** | 判定不了的case要有地方去 |
| **多语言构词表** | 英/德/法/西，且会长 |

## 5. 三个必须提前定的技术选择

| # | 选择 | 建议 | 理由 |
|---|---|---|---|
| **T1** | 交互状态放哪 | **多维表格**（不放内存、不放卡片） | 长连接会断、服务会重启；**卡片只是视图，状态必须在表里** |
| **T2** | 卡片原地更新的并发 | 每条记录带 `version` + 乐观锁 | 两人同时点按钮会互相覆盖。飞书不提供并发控制，必须自己加 |
| **T3** | 实时 vs 定时 | 判定实时；**指标定时** | 指标每次算代价高；且**谷时算**（DeepSeek 峰时 ×2 计费）。这条已由成本扫描验证过 |

> **T1 是最容易被做错的一条。** 状态放内存的机器人，重启即失忆；
> 状态放卡片的机器人，改不动历史。**必须先有表，再有卡。**

## 6. 分阶段落地

### P0（事件订阅配好后立刻可做，1–2 天）

- 单聊预检：贴文案 → 判定卡（结论 + 管辖 + 证据要求 + 折叠判定链）
- **显式输出「判不了」**：落 CATCH-ALL 时写清原因，不写「未发现问题」
- 判定记录写入多维表格（含版本、时间、判定人）

**验收**：在群里发一句 `Momcozy M5 Pain-Free Pump`，单聊回一张卡，
写着「T1.4 红 L4 / 对象未写出 / 需 X 证据」，并且**该卡可原地更新为已签核状态**。

### P1（1–2 周）

- 群内工作台：边界争议升级 → 指派 → 签核 → 回流错题本
- 卡片按钮回调（`card.action.trigger`）驱动的状态机
- 周报卡（定时推）

### P2（1 个月）

- 口径变更走飞书审批
- 规则库本体上 Wiki，带 `permit` 字段与依据（CONSULT-001 的修法）
- 多语言扩展 + 豁免可达性自动检查进 CI

### 不建议现在做

| 不做 | 为什么 |
|---|---|
| 自动判违规并直接拦截投放 | Precision 0.970 意味着 3% 误杀；且 54.6% 落 CATCH-ALL |
| 让业务自己在卡片里改规则 | 规则变更必须有单一权威实现，否则重演 §9-L4「同一判据写两处就会漂移」 |
| 做独立 App / 网页端 | 飞书已经是入口，再做一个只会分裂使用场景 |

## 7. 与 CONSULT-001 的关系

**CONSULT-001 不是产品的前置，是产品的第一个真实 case。**

它暴露的问题正好定义了 P2 的一个必做项：

> 规则文本里写「允许」，若没有代码承载，会在每次重建中被静默丢弃（本次丢了 30/44 条而无人察觉）。
> **产品必须让「许可」成为一个可查询、可审计的状态** —— 否则守衡给出的每一个「合规」结论都不可信。

**这就是为什么本提案把「豁免可达性检查」列为自建组件，而不是可选项。**
