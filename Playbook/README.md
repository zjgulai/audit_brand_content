### 三条必须一起读的补充

1. **「条件性 RATIFIED」不是修辞，它有具体缺口。**
   法务未签的那一半（PASS 档与状态语义）意味着：**机器可以输出 PASS 标签，
   但「PASS 该怎么附注」与「PASS 是否等于可发布」仍无法务裁定**
   （Playbook §7 的 U8）。所以本仓的硬约束是 **五标签全部止于「待放行」** ——
   这不是实现偷懒，是合同未闭合。

2. **判据数量是可复算的，别手抄。**
   ```bash
   python3 tools/verify_acceptance_index.py    # → 文档编号判据 134 / 已覆盖 134 / 未覆盖 0
   ```
   任何文档里出现的「134」都应带这条复现命令。手写的数字会漂移
   （本仓已发生过 347 → 134 的更正，见验收表头部注记）。

3. **`技术解决方案-v1.md` 的 DRAFT 状态与目录里的其它文件不同。**
   它不描述「应该做成什么样」，而描述「打算怎么做」—— 而那个做法被两轮审查否了。
   引用它时请引「模块↔判据映射」，**不要引它的实施步骤当作已批准计划**。

## 一 · 与其它权威文件的关系

```
上游飞书 docx（唯一权威，不在盘上）
        │  PRD：做什么、为谁做
        ▼
PRD/feishu/内容审查Agent-PRD-v1.0.md（快照）
        │
        ▼
Playbook v1.1（本目录）       ← 产品规格：做成什么样、凭什么说做完了
        │  134 条编号判据
        ├──────────────► PMO/audit/验收表-v3-*.md（136 项验收动作）
        └──────────────► 技术解决方案-v1.md（模块↔判据映射，DRAFT）
```

**冲突时以谁为准**：Playbook v1.1 自己写着「任何一条技术决策，如果和这份文件冲突，
**以这份文件为准**；任何一条验收标准，如果不能指回这里的某个判据，**它就不该进验收表**」。
上游 PRD 与 Playbook 冲突时，以上游 PRD 为准（它是需求源），Playbook 是实现口径。
