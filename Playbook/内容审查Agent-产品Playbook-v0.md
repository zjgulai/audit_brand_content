# 内容审查 Agent · 产品 Playbook v0

> **性质**：目标态定义 + 逐步判据 + 台账。**本文件不是 PRD，也不是实现方案。**
> **日期**：2026-10-17。
> **它回答**：这套东西最终长什么样、每一步做到什么算做到、现在缺哪几块。
> **它不回答**：为什么做这个项目（那是 PRD）、具体怎么编码（那是实现方案）。

---

## §0 · 这份文件怎么用

**一句话**：**把「做完」变成一个可以逐格核对的表。**

三个用法，按使用频率排：

| 场景 | 怎么用 |
|---|---|
| **每天** | 挑一个格子，做，然后在 §5 台账里划掉或记下新发现 |
| **评审** | 只看 §1 目标态 —— 它是唯一需要跟干系人对齐的部分 |
| **交接** | 读 §2 的判据列 —— 每一步做错了什么会红，接的人不用猜 |

**一条硬规矩（沿用于本项目）**：

> **写进本文件的每一个「完成」「已验证」「没问题」，必须能指出是谁在读它、读出来的数是什么。**
> 指不出来，就写「未测」。

## §1 · 目标态（终局形态）

### 1.1 一句话

**任意形态的营销内容进去，可执行的审查结论 + 可溯源的证据 + 可统计的读数出来。**

### 1.2 五个必须同时成立的条件

这五条是「做完」的定义，缺一条就是没做完。

| # | 条件 | 判据（怎么知道它成立了） |
|---|---|---|
| **甲** | **进得来** | 文本 / 图片 / 视频 / 链接 / brief 五种形态都能进链路，且每种都带**内容指纹** |
| **乙** | **判得准** | 每个结论都能指出**哪条规则**、**哪条外部依据**、**在原文哪个位置** |
| **丙** | **处置得住** | 每条内容都有明确的下一步负责人，且**转出去之后有回音或超时升级** |
| **丁** | **说得清** | 群里一句话 + 报告详情；**未审的部分明确说未审，不冒充已审** |
| **戊** | **改得动** | 规则改了之后，**能回答"这次是变好还是变坏"**（靠冻结回归集，不靠感觉） |

### 1.3 三条贯穿性的设计原则

**原则一：审查标签 ≠ 发布动作。这两件事必须分开，否则会互相污染。**

先把两个概念拆开：

| | 审查标签 | 发布动作 |
|---|---|---|
| **答什么** | 这次审查得出了什么 | 这条内容能不能上线 |
| **谁签发** | 机器（受限）/ 内容审核员 / 法务 | **人或流程**，机器**没有**这个权限 |
| **载体** | 报告上的一个标签 | 实际发布 |

**机器能签发什么，必须先看源头说了什么 —— 而源头在这里自相矛盾。**

我回读了 `research/governance/skeleton/disposition-layers-v1.json`（法务 2026-09-16）与
`ADR/ADR-0005` 约束 2，三处原文：

| 出处 | 原话 |
|---|---|
| DP2 层的 `$note` | 「机器的终结权是**单向**的。机器可以独立拦下一条内容……**但机器不能独立放行一条内容**」|
| DP2 映射的 `auto_pass_with_note` | `machine_may_finalize: true`、`human_must_see: true`、`final_action: 附注放行` |
| ADR-0005 约束 2 | 「Agent **不能**把记录状态改成 `无需处理`……只能**新增**字段。人的字段 Agent **只读**」|

**两处打架**：层级描述说机器只能单向（拦），而映射里「附注放行」也标了机器可终结。

**为什么「附注放行」那条的背书弱**：它的 `$decision` 写的是
「**D1 之前的既有落点**（法务 2026-09-16 未改动）」——**它没有 D 编号**。
法务逐条确认的只有 D1–D4，而 **D1 那一句只覆盖「允许机器独立拦截」**。

**本 Playbook 采用更严的读法（与 ADR-0005 约束 2 一致）：**

> **机器唯一能独立终结的方向是「拦截」。**
> 「附注放行」**暂不作为机器可签发的动作**，直到法务就这一档给出口径（见 §5 G13）。

| 对外标签 | 落在哪层 | 机器可否终结 | 依据状态 |
|---|---|---|---|
| **BLOCK** | DP2 拦截 | ✅ **可** | ✅ 法务已确认（D1）|
| **REVIEW** | DP3；DP4 加「已升级法务」 | ❌ | ✅ |
| **未审查** | DP0 | ❌ | ✅ |
| **待自决** | DP1（机器退出，责任回到提交人）| ❌ | ✅ |
| **PASS**（附注放行）| DP2 | ⚠️ **待法务核准** | ⚠️ **无 D 编号背书** |

> ★ **所以「PASS」在当前口径下不是机器产出**，它是一个**待核准**的档。
> 机器唯一能自己下的是 **BLOCK**；其余四档机器都是**退出或转人**，不是放行。
> 这不是保守，是照 ADR-0005 那条原话办：「绕过人的动作在系统层面不存在，不依赖自觉」。

**发布动作永远是人的事。** 系统无论产出哪个审查标签，**都不构成发布许可**
（★ 措辞更正：机器能签的只有 `BLOCK` 一个；写「机器无论签发哪个标签」会让人以为机器能签全部）。

**原则二：没命中 ≠ 安全；而「没命中」还要再拆一次。**

一条内容没有命中任何规则，**结论不是 PASS**。但「没命中」本身有两种，
必须靠**覆盖证明**区分（详见 §2 L2）：

| | 含义 | 处置 |
|---|---|---|
| **`UNASSESSED`** | **没能力评估** —— 这个模态 / 这个规则域根本没跑 | 强制人工 + 进空白清单 |
| **`CLEAN-CANDIDATE`** | **已评估且干净** —— 确实按某规则版本、对某些模态跑过了 | 可走 DP1，**但仍不自动发布** |

> 判据：`severity.py` 的 `L0` 写着「未覆盖 —— 不是「低风险」，是「不知道」。
> 查表会低估它」。
> ★ 两者**都不构成发布许可** —— 见原则一。

**原则三：判定表唯一；严重度给下限，数量只影响呈现。**

> ⚠️ **这一条是对最初设想的修正。** 原设想是「按照规则的 P0–Pn 的个数统计判断审核状态」。
> 实测证明这条会出事：现行 PRD §5.3.2（原写 §5.3.5；v1.2 的 REVIEW 节）规定「问题数 ≥3 就只出分类汇总」，
> 于是 1 个 P0（视频里宝宝未坐安全座椅）+ 2 个 P3（措辞建议）= 共 3 个问题 → 走汇总模式，
> **群里收到的是一句「合规类问题 1 个、措辞表达类问题 2 个」——最严重的那条被数量吞掉了。**

**正确形状，五条一起成立（缺一条就会退化成上面那个错误）：**

| # | 规则 | 作用 |
|---|---|---|
| 1 | **唯一判定表决定**状态 | 只有一处能定，不许第二处 |
| 2 | **最高严重度给「状态下限」** | 有 P0 就是 BLOCK 档，**数量再少也不降级** |
| 3 | **任何数量不得降级**状态 | 数量**只能升级或不变**，永远不能把 BLOCK 降成 REVIEW |
| 4 | **特定共现可升级** | 组合规则（如「场景名词 + 消除性动词 = 功效承诺」）**有权上调状态** |
| 5 | **普通数量只影响呈现** | 决定「群里出几句、详情放报告」——**不决定状态** |

> ★ 第 4 条不能省。本项目已有共现升级机制（`escalate_if` 的 `ESC-001`），
> 如果写成「状态由最高严重度决定」，组合规则在**文字上**就被否掉了 ——
> 而它恰恰是抓新型表达的主要手段。
> 正确的措辞是：**状态下限 = 最高严重度；共现可以把它抬得更高。**

## §2 · 五层工作流与逐步判据

每一层：**输入契约 / 输出契约 / 已建成什么 / 缺口 / 判据**。

### L1 · 归一化（进）

**输入**：文本 · 飞书文档链接 · 落地页 URL · 图片 · 视频 · brief · 广告记录
**输出**：**内容单元** —— 一段可判正文 + 双指纹 + 覆盖声明 + 来路

| 项 | 内容 |
|---|---|
| **已建成** | `base/contract.py` 的 `ContentUnit`：4 个构造器、**14 条不变量**、双指纹 |
| **双指纹为什么两个都要** | `raw_sha256` 答「看的是哪份原件」，`text_sha256` 答「重跑能不能得到一样的数」。实测：4 个页面各抓两次，**原件变了 4/4，正文一字没变 0/4** —— 合成就再也观测不到这件事 |
| **关键机制** | 每种形态必须显式声明 `covers` / `does_not_cover`（**刻意不设默认值**：默认值会让「只做了 OCR」看起来像「视频已审」）|
| **缺口** | ① **视频档管道是空的**（契约备好、实现没做）② **画面语义没有结构化表示** —— 现在只装文字，装不下「宝宝没坐安全座椅」这种画面断言<br>③ **图片 OCR 的桥没接线** —— `row_to_unit()`（`base/media.py:367`）**全仓零调用点**；实测 427 个单元里**没有一个是 image 或 video**<br>④ **解析失败会被静默吞掉** —— 落地页的 `parse_error` 设在 parser 对象上、返回 dict 不含它；结构化 JSON 解析失败**静默 return None**，下游拿到一个**空正文单元**，失败原因不可见<br>⑤ **Word/PDF 与 NAS 两个入口一行代码都没有**（而上游 §5.1 都列了）|

> ⚠️ **③ 比「完全没有」更危险**：OCR 结果**已经能生产出来**，但没有桥送进判定 ——
> 所以今天的「图片已审」是假的：**它看起来像是做完了。**
> **④ 是同一个病**：「解析失败了」与「本来就没东西」长得一模一样。
> 两者的修法都在 **PRD v2.0 优化稿 §8.4**（`parse_status` + `failure_kind` 封闭取值域 + 四条断言 B1–B4；v1.2 无 §8.4）。

**判据（做错了什么会红）**

| # | 判据 | 现状 |
|---|---|---|
| L1-1 | 每个内容单元都能复算出 `unit_id` | ✅ 已建成（H7）|
| L1-2 | 每个单元都声明了 `covers` **和** `does_not_cover`，且都不为空 | ✅ 已建成（不设默认值）|
| L1-3 | 位置字段能**点回原片**（时间码 / 区域），不是自然语言 | ❌ **缺** —— 这正是「画面语义结构化表示」要解决的 |
| L1-4 | 同一份内容的两次解析，正文指纹相同 | ✅ 已建成（归一化是不动点，H3）|

### L2 · 判定（判）

**双档，互不越界：**

| | 深档（确定性） | 浅档（语义） |
|---|---|---|
| **管什么** | 文本主张 | 画面语义 |
| **实现** | 规则引擎（21 条 + 主题树）| 多模态模型 |
| **输出** | 命中规则 + 位置 + 证据 | 候选 + 画面位置 + 依据或「未覆盖」 |
| **可否终结** | ✅ **仅拦截方向** | ❌ **只能出候选，永远转人工** |
| **已建成** | ✅ 全部；标注者一致性已测（叶子 **0.8345** / 等级 **0.9682**，均达标）| ❌ 无 |

#### ⚠️ L2 缺的那一环：**skill / 知识库 / loop**（2026-10-17 补）

上面那张表只写了「规则引擎 + 多模态模型」两个部件 ——
**而用户原始工作流里写的是「skill + 规则库 + 知识库 进行 loop 审计」，三个名词一个都没落。**

补齐后（完整定义见 **PRD §9**）：

| 部件 | **不是**什么 | **是**什么 |
|---|---|---|
| **skill** | ❌ 不是可加载的运行单元 | ✅ **一份操作规程** —— 「任何 agent 按这一页就能调起一次审查」（`agent-skills/内容合规审查/SKILL.md`）|
| **规则库** | ❌ 不是召回器 | ✅ **确定性判定 + 落层**：`Engine.assess()` 决定命中，`resolve_layer()` 决定落哪一层 |
| **知识库** | ❌ 今天不是证据源（**未接线**）| ✅ **应该是证据源**：产出「违反了哪一条具体条款」 |

**loop 的五轮**（⚠️ **是设计，不是现状** —— 仓库里今天**不存在**审计循环，
判定引擎是单次纯函数）：

```
轮 0  预处理    定档 + 产出「本轮要跑哪些控制点」的清单  ← 这就是「覆盖证明」
轮 1  确定性判定  规则库出 hits[]（带控制点 + 位置 + 逐字片段）  ✅ 已建成
轮 2  证据补全   按 control_code 查条款位置 + 出处链接           ⚠️ 已实现、未接线
轮 3  语义判定   多模态出候选（**不是结论**）                     ⚠️ 未实现
轮 4  合并定状态  唯一判定表出状态 + 路由 + 覆盖证明
```

**停机六条件**：正常完成（清单跑完）· 提前停（P0-字面且满足机结三条件）·
转人工 · 工具失败（**落 `failure_kind`，不得静默跳过**）· 无进展 · 超时升级。

> ★ **「工具失败」这一条是这一节最要紧的**：
> 一条内容因为模型超时而没被审，**今天它既不会报错，也不会进任何队列** —— 它会安静地不出现。
> **用户工作流里没有任何一环在管这件事。**

**三条合并规则：**
1. 深档命中优先，浅档不得推翻
2. 浅档产出**是证据不是结论**（这本来就是「人工复核」层的定义）
3. **两档都没命中的内容，必须再分一次** —— 见下

#### ⚠️ 「没命中」必须拆成两种，不能直接等同「未覆盖」

**这是一个必须修的过度保守**：我先前写「两档都没命中 = 未覆盖」，
但它把两种本质不同的情况压成了一种：

| | 含义 | 判据 | 处置 |
|---|---|---|---|
| **`CLEAN-CANDIDATE`** | **已评估且干净** —— 这次确实按某个规则版本、对某些模态跑过了，没发现问题 | 有**覆盖证明** | 仍**不自动发布**（机器无放行权），但可走 DP1 |
| **`UNASSESSED`** | **没有能力评估** —— 这个模态/这个规则域根本没跑 | 无覆盖证明 | 强制人工，且**进空白清单** |

**所以每个结论必须记录「本次实际评过什么」** —— 这就是**覆盖证明**（assessment receipt），
至少四项：

```
评过的模态     文本已评 / 图内文字已评 / 画面语义未评 / 音轨未评
规则版本       本次用的是哪一版规则（版本号 + 指纹）
适用控制点     七个控制族里，哪几个本次真的跑过、哪几个没跑
未跑的为什么   无能力（视频管道为空）/ 无规则（该叶子上无规则）/ 未接线
```

> **为什么不能省**：没有覆盖证明，
> **「审过了没问题」和「压根没审」在系统里长得一模一样** ——
> 而这是整个项目最安静的失效模式。
> 实测它已经发生过一次：291 条里 59 条无文案格式的记录，**其中 55 条**被渲染成了 `合规·绿 / 无需处理`。

> ★ **两者都不构成发布许可。** 系统无论给出哪个，都不等于「可以上线」——
> 见 §1.3 原则一：审查标签 ≠ 发布动作。

**⚠️ 一处必须修正的现行设计**：PRD §6.6 写「置信度 ≥0.90 直接输出结论（PASS / BLOCK）」。

两处问题：① 它让机器直接出 **PASS** —— 而按 ADR-0005 约束 2 与 §1.3 更严的读法，
**机器唯一可独立终结的是 BLOCK**；② 置信度这个数值在 PRD 里**没有定义、没有校准**，
却被写进准确率指标。

**建议删除置信度分档，改为三值证据状态**：

| 证据状态 | 含义 | 出口 |
|---|---|---|
| **命中确定** | 规则命中且判据明确 | 按最高严重度出状态（下限）|
| **疑似需人看** | 有信号但不能定论 | 转人工 |
| **未覆盖** | 拆成 `UNASSESSED` / `CLEAN-CANDIDATE` 两种（见上）| 见上表 |

**判据**

| # | 判据 | 现状 |
|---|---|---|
| L2-1 | 每个结论的三态 ≡ 判定表算出的值（唯一来源）| ❌ **缺** —— 现在判定散在三处（流程图 / 置信度分档 / 指标）|
| L2-2 | 「没命中」必须落成 `UNASSESSED` 或 `CLEAN-CANDIDATE` 之一，**不许合成一个空结论**；两者都不自动发布 | ❌ **缺** —— 覆盖证明尚未定义 |
| L2-2b | 每个结论都带**覆盖证明**（评过的模态 / 规则版本 / 适用控制点 / 未跑的为什么）| ❌ **缺** |
| L2-3 | P0 分字面类（正则可判）与语义类（强制走模型）| ❌ **缺** —— 现在 P0 全走正则，而「医疗宣称」这类靠正则盖不住 |
| L2-4 | 每个命中都能指出规则 + 外部依据 + 原文位置 | ⚠️ 深档可以，浅档缺位置契约 |

### L3 · 处置（置）

|---|---|---|---|

| DP1 | 业务自审 | 文案提交人 | ⚠️ **见下** |
| DP2 | 工具预审 | 机器 | ✅ **仅拦截方向** |
| DP3 | 内容审核员复核 | 内容审核员 | ❌ |
| DP4 | 法务终审 | 法务 | ❌ |

> 源文件 `DP1 can_finalize=true`，而我写成 ❌ —— **两处矛盾。**
> 真因是「终结」一词被压成了两件事：
>
> | 字段 | 值 | 含义 |
> |---|---|---|
> | `can_finalize` | **true** | 「**这一层的处置**由这一层结」—— `who=文案提交人`，**是「谁结」不同，不是「机器能结」** |
> | `machine_may_finalize` | **false** | 「机器不能终结」—— ✅ 与上面不矛盾 |
>
> **所以 DP1 的正确写法**：处置由**文案提交人**结；**机器不可终结**。

**对外五标签**（与 §1.3 原则一同源）：

| 对外标签 | 落在哪层 | 机器可否终结 |
|---|---|---|
| **BLOCK** | DP2 拦截 | ✅ **可**（唯一可机结的一档）|
| **REVIEW** | DP3；DP4 加「已升级法务」| ❌ |
| **未审查** | DP0 | ❌ |
| **待自决** | DP1（机器退出，责任回到提交人）| ❌ |
| **PASS** | DP2 附注放行 | ⚠️ **待法务核准**（见 §5 G13）|

> **为什么必须是五个而不是三个**：DP0 落不进三态里的任何一态。
> 而它今天是怎么显示的，有实测：存量 291 条里 **59 条（20.3%）**文本为空，
> **在花 $15,747** —— 它们被渲染成了 `合规·绿 / 无需处理`。
> 「没有文本可判」被记成了「确认合规」。
>
> ★ 另注意：**标签数（5）≠ 处置层数（5）** —— 两者不一一对应。
> `PASS` 与 `BLOCK` **同落 DP2**，`REVIEW` 跨 DP3/DP4。
> 把这两套数当成同一件事，就会得出「五层五态正好对应」的假结论。

**判据**

| # | 判据 | 现状 |
|---|---|---|
| L3-1 | 每条内容都有明确的下一层负责人 | ⚠️ 层有了，**路由表（依据来源 → 复核人）还没有** |
| L3-2 | 转出去之后，**没回音会升级** | ❌ **缺**（三级：转出 → 超时 → 升级项目统筹）|
| L3-3 | 被拦的人**有地方说话** | ⚠️ 机制已建成（2 工作日 SLA、案件号即回执号），**一条都没真发出去过** |
| L3-4 | 回执里不许出现「通过 / 已通过 / 无需处理 / 审批完成」 | ✅ 已建成（回执模板的 `must_not_say`）|

### L4 · 输出（出）

**已定**：群里**只出一句话结论 + 报告链接**，所有细节进报告。

**两个产物：**
- **报告**（给人看，渲染视图）
- **结构化记录**（机器读，**唯一真相**）—— 链接坏了还能重建

**判据**

| # | 判据 | 现状 |
|---|---|---|
| L4-1 | 群里不刷屏，且**P0 不可能被数量阈值吞掉** | ❌ 缺 —— 现行是「问题数 ≥3 就只出汇总」|
| L4-2 | 报告链接有效期 ≥ 记录保存期 | ❌ **矛盾** —— 报告 30 天 vs 记录 1 年，一年后复核时报告已打不开 |

### L5 · 评估（证）

**已定四个可测数**（替代原「整体准确率 ≥90%」）：

| # | 读数 | 为什么是它 |
|---|---|---|
| ① | **P0 召回** | 唯一防「漏」的指标 |
| ② | **P0 误判率**（**必须带样本量 n**）| 唯一防「误拦」的指标 |
| ③ | **未覆盖占比** | **唯一会随系统成长而变化的指标** —— 规则库空着时接近 100%，建起来后应下降 |
| ④ | **人工推翻率** | 所有人工结论里推翻机器的比例；**申诉胜与败都进分母**（否则是幸存者偏差）|

> **为什么淘汰「整体准确率 ≥90%」**：若 PASS 占九成流量，
> **一个永远输出 PASS 的系统就是 90%**。同一个数，两种完全相反的现实。

**金标准来源**：在线回流（人工复核 + 抽检）为主，**加一个最小冻结回归集**。
> 冻结回归集的作用：**规则改了之后，能在发布前回答「这次是变好还是变坏」**。
> 没有它，只能等群里出现误判。规模几十条即可，不是几百条 —— 但**必须含已知陷阱负样本**
> （`Best Seller` / `100% cotton` / `最新` / `first-time mom`），这些是误杀高发区。

**判据**

| # | 判据 | 现状 |
|---|---|---|
| L5-1 | 四个数都有来源，且**未测时显示未测** | ❌ **缺** |
| L5-2 | 抽检**分层**：PASS 层抽漏报 + BLOCK 层抽误报 | ❌ **缺** —— 现只抽 PASS，②永远没样本 |
| L5-3 | 冻结回归集存在，且规则变更时**必跑** | ❌ **缺** |

> ★ **L5-3 的现状补一句**：全仓**有**两个词表评测脚本（`tools/offline_replay.py`、`tools/heldout_test.py`），
> 但它们是**评测**不是**变更门** —— 规则改了没有任何东西强制跑它们。
> **缺的不是工具，是「谁跑它」** —— 这与 §5 G10 是同一件事。

## §3 · 三个必须钉死的机制

这三条是本次审计里发现的、**不做就会静默出错**的地方。

### 3.1 输入契约：显式提交单

**问题**：现行两条入口对「内容阶段」字段的处理不一致 ——
群里靠模型**猜**，多维表靠人**填**。猜错的后果是分叉的：brief 若被判成 final，
就会走 sign-off 路由 —— **而 brief 根本没有 sign-off 负责人**。

**做法**：一次提交 = 一张提交单。`内容阶段 / 品线 / 渠道` **三个必填**，
机器**只补不强猜**；没填就落「未覆盖」走人工，**不默认成 final**。

### 3.2 分类体系：**审查控制族**（主轴）+ 三轴（属性）+ 双键（机器标识）

**先把用户的质疑答清楚。** 原话：「审查的分类其实就是内容标签的分类，这个分类不对」。

**这个判断成立，而且比预想的更严重** —— 现行 §5.3.1 那套八分类**不是标签选错，是它悬空**：
**有下游输出字段（§5.4 的 `issue_category`），但没有上游规则映射** ——
§6.5 的规则字段表里没有分类列，所以**没有任何东西能断言「每个取值都在取值域内」**。
而 §7.2 的场景域是第三套清单，§3 的四个路由目标也没有映射表。
文档自己给出了矛盾答案：§5.3.4 示例把「未坐安全座椅」归「消费者安全」，§7.2 把同一场景归「P0 + P1 / 法务合规红线 + 安全准确性」。

**⚠️ 一处必须自我修正的地方**：我先前把 `三轴并置` 说成分类体系，**这个说法是错的**。
三轴里 `scene_domain`（车内/睡眠/喂养…）**本质仍是内容标签** —— 它答「在说什么」，
不答「审查动作是什么」。用户质疑的正是这件事，我差点用换名字的方式绕过去。

**正确的结构是三层，各答一个问题：**

```
第 1 层  审查控制族 → 控制点    答「这是一次什么审查动作」   ← 主轴，决定路由与判据
第 2 层  三轴（正交属性）        答「它是什么、谁说了算、伤到什么」  ← 不决定审查动作
第 3 层  双键（机器标识）        答「违反了哪条、凭哪条依据」   ← 可断言
```

#### 第 1 层：七个审查控制族（主轴）

| 控制族 | 答什么 | 由哪些现有类目归入（实测可覆盖 11/12）| 子类数 |
|---|---|---|---:|
| **宣称控制** | 这句话能不能说 | 合规与受监管宣称 + 证据与实质证明 | 15 |
| **事实控制** | 这件事是不是真的 | 商品信息与Listing准确性 + 母婴知识内容准确性 + 北美本地化与标签要求 | 23 |
| **披露控制** | 该说的说了没有 | 背书与披露透明 | 6 |
| **场景控制** | 画面这样做安不安全 | 产品安全与高危使用场景 | 2 |
| **权利控制** | 能不能用这个人/这张脸 | 权利、肖像、隐私与AI | 2 |
| **渠道控制** | 这个平台允许吗 | 平台与渠道政策 | 6 |
| **品牌控制** | 这个调性对不对 | 品牌信任与声誉 + 推广与价格透明 | 4 |

> **为什么这七个是「审查动作」而不是「内容标签」**：
> 「宣称控制」的动作是**验实证材料**；「披露控制」是**查有没有披露**；
> 「权利控制」是**查授权文件**。**每一个都有不同的判据和不同的复核人** ——
> 而「车内场景」「睡眠场景」没有：它们只是告诉你内容在讲什么。
>
> **实测依据**：`分类确认` 表 12 个一级、58 个子类（去【一级小计】行），
> 逐一归入上表**无遗漏**（11/12 被覆盖；剩 1 个是「未归类」，即空桶）。
>
> ⚠️ **诚实说明一处判据强度**：**「十二个一级归入七个控制族」这个分组是我归纳的，
> 不是盘上已经存在的结构。** 可复核的是「能做到无遗漏归类」这件事（脚本可复算）；
> 而「分成七个、叫这些名字」是判断，会随讨论变。
> 真正从盘上直接读出来的是**下一级的控制点**（H/M/U/V 码、`分类确认` 的 58 个子类），
> 那一层是数据，不是判断。

**每个控制族必须有二级（控制点）**，且**二级才是规则挂载的位置**：

```
宣称控制
  ├─ 疾病治疗宣称（H01）
  ├─ 催乳与通乳宣称（H02）
  ├─ 临床与实验证据宣称（H03）
  ├─ 绝对化与最高级用语（V02 → 见下方修正）
  └─ …（共 15 个）
```

#### 第 2 层：三轴（正交属性，**不决定审查动作**）

| 轴 | 答什么 | 取值域 | 谁负责维护 |
|---|---|---|---|
| `scene_domain` | 在说什么 | 场景域九项（车内/睡眠/喂养/洗护/出行/居家/玩具/功效/肖像）| 产品 |
| `authority_source` | 谁说了算 | 联邦法规 / 州法 / 平台政策 / 英国对照 / 品牌内规 + **机构**（FDA·FTC·Amazon…）| 法务 |
| `consequence` | 伤到什么 | 消费者安全 / 品牌信任 / 经营风险 / **建议级** | 业务 |

> **`authority_source` 的二级（机构）已经建好了** ——
> `外部标准库` 的「法域」列三个取值与「来源机构」**一一对应、无交叉**：
> `美国平台政策 → Amazon/Meta/Google/TikTok`、`联邦法规 → FDA/FTC`、`英国 → MHRA/ASA`。
> 这是唯一一处**二级已经存在**的轴。

#### 第 3 层：双键（机器标识）

```
control_code      违反了哪个控制点  ← H/M/U/V 码
authority_ref     凭哪条依据        ← T 码 → 外部标准库条目
```

**三条轴都要有「未知桶」，且未知桶必须显式登记、不许静默落进任何一个已知值：**

| 轴 | 未知桶 | 后果 |
|---|---|---|
| 控制族 | `未归类` | 强制转人工 |
| `scene_domain` | `其他` | 同上 |
| `authority_source` | `依据待定` | 同上 |
| `consequence` | `后果未知` | 同上 |

> **未知桶不是垃圾桶，它是有意义的信号** —— 未知桶一多，就说明规则库或分类体系该补了。
> 关键在于：**它必须能被数出来**（否则垃圾堆积无人发现）。

### 3.3 未覆盖的回退路径

```
规则库空着     → 未覆盖 → 人工
规则只覆盖中文 → 英文内容 → 未覆盖 → 人工
新场景 / 新平台政策 → 未覆盖 → 人工
```

**这三条路径必须长得和「审过了没问题」不一样。** —— 这是整个系统最安静的失效模式。

## §5 · 遗留台账（未定 / 未做）

> 每条：**是什么 / 为什么还卡着 / 谁来解**

### G12 部分结案（2026-10-17）

**原问题**：「v1.3 比 v1.2 少约 1,000 字，未核是精简还是删改。」

**结论：总量差由 6 张嵌入表完全解释。** 上游把 **6 张原生表改成了嵌入的电子表格**，
而嵌入表**不进 `raw_content`**。

> ⚠️ **这个结论的强度必须说清**：
> 它由**总字数**支撑（10,865 → 9,860 + 1,006 嵌入 = 10,866，差 +1），
> **不是逐段 / 逐单元格比对的结果。**
> 「总量差被完全解释」**不等于**「逐字恒等」—— 仍可能有一段被删、另一段被加而总量抵消。
> **要证明恒等，需要一次逐段差异（原生表 → 嵌入表 的单元格级比对），那件事没做。**

```
v1.2  raw_content        10,865 字
v1.3  raw_content         9,860 字
v1.3  嵌入表内容           1,006 字   ← raw_content 完全看不到
────────────────────────────────────
v1.3  全文合计           10,866 字
v1.2  全文合计           10,865 字    差 +1 字（一个空行）
```

**这 6 张表挂在哪：**

| 嵌在哪节 | 表的内容 |
|---|---|
| §5.2 审查能力 | **第一阶段的形态能力矩阵**（文字 / 图片 / 视频）|
| §10.2 日常统计指标 | 3 个指标定义 |
| §12 非功能需求 | 6 项要求 |
| §13 权限与安全 | 5 个角色权限 |
| §15 验收标准 | **9 行验收项** |
| §16 风险与依赖 | 4 行风险 |

**读法（任何人可复现）：**

```bash
# ① raw_content —— 看不到嵌入表
python3 tools/lark_find.py readdoc PXfBdjTwFokEQixtmTscqm7knNh

# ② blocks 接口 —— 找 block_type=30（嵌入表），取 sheet.token
#    形如 B1aUs2Vuah8YwjtwWO6cr5MFnUd_<sheet_id>
# ③ 再取该 sheet 的值
```

**★ 这条的真正价值不是「PRD 改了什么」，而是发现了本项目的一个方法缺陷：**

> **凡是「用 `raw_content` 读飞书文档」然后下结论的地方，都可能漏掉嵌入表。**
> `verify_prd_baseline.py` 的指纹就是这个接口算的 ——
> **上游把一张正文表换成嵌入表，指纹会变，但内容没变，
> 而我们读到的「正文」少了整整一节的内容。**

**已因此修正的结论（我此前说错的）：**

| 我说过 | 真相 |
|---|---|
| 「§15 验收标准：空标题」 | ❌ 有 9 行验收项，其中一行把「准确率整体≥90% / BLOCK 精确率≥95% / P0 漏报率=0」写进了验收 |
| 「§16 风险与依赖：空」 | ❌ 有 4 行风险 |
| 「§10.2 表丢了，标题下是散文」 | ❌ 有 3 个指标定义（且它统计的是「已审内容数」，**有分子没分母**）|
| 「§12/§13 通篇建议脱敏」 | ❌ §13 有完整 5 角色权限矩阵 |
| 「上游只打算做文字」 | ❌ §5.2 的矩阵明写图片 = OCR + 基础视觉、视频 = 字幕旁白 + 关键帧 + OCR |

**★ 这个缺口必须单独记，因为它是「判据写在了比数据粗一级的粒度上」的第四例。**
前三例：把「无标题」判成「权限拒绝」（75→7）· 把 668 条 API 地址当成文档节点 ·
覆盖矩阵拿叶子全名比前缀（25/26 零覆盖→0/26）。

### G12b 的执行点（**必须有，否则它只是登记**）

**这个缺陷的影响面不止 PRD**：全仓有 **4 处**读飞书 docx 正文的地方，
**全部只调 `raw_content`**，所以**全部看不到嵌入表**：

| 位置 | 用途 |
|---|---|
| `tools/lark_find.py:75,88` | `read` / `readdoc` —— 本项目最主要的读文档命令 |
| `tools/verify_prd_baseline.py:171` | **基线指纹核对**（就是它把 6 张表算成了「消失的 1000 字」）|
| `tools/feishu_index.py:573` | 可达资源索引 —— 索引里的 `extent.text` 是不完整的 |
| `tools/lark_probe.py:100` | 接口探测 |

**执行点（两条，缺一条都不算修）：**

| # | 做什么 | 怎么验它真的做了 |
|---|---|---|
| **①** | **立一个「完整文档视图」的取数入口**：`raw_content` **+ 递归取全部 `block_type=30` 的嵌入表** | 喂一份已知含嵌入表的文档（就用 PRD，6 张），断言取到的**字数 = raw_content 字数 + 嵌入表字数** |
| **②** | **反向对照**：喂一份**不含**嵌入表的文档，断言两条路径字数**相等** | 若相等这条恒真（即 ① 没生效），反向对照必须红 |

**谁会因此变红**：`verify_prd_baseline.py` 的 `C4 上游字数 = chars` ——
它比的是 `raw_content` 的字数，而**索引里记的 `chars` 也是 `raw_content` 算的**，
所以两边同时错、恒等、永远绿。**这正是本项目反复在治的那个形状：恒真的检查。**
修法不是改那个数，是**把索引的 `chars` 定义成「完整文档视图的字数」**，
这样嵌入表一被删或一被加，`C4` 就会响。

## §6 · 偏离台账（与最初目标 / 现行 PRD 的偏离）

> **偏离不是错误，是「和原来说的不一样了」——必须写下来，否则下一个人按原话做。**

| # | 原设想 / 现行 PRD | 实际 | 为什么改了 |
|---|---|---|---|
| **V1** | 「按 P0–Pn 的**个数**判断审核状态」 | 状态由**唯一判定表**出；最高严重度给**下限**、特定共现可**升级**、普通数量只影响**呈现** | 个数会把 P0 吞掉（实测：1 P0 + 2 P3 = 3 个 → 走汇总）|

| **V3** | PRD §6.6 置信度 ≥0.90 直接出 PASS | **发布动作永远由人**；**审查标签**里只有 `BLOCK` 机器可独立终结，`PASS`（附注放行）**待法务核准** | 置信度无定义、无校准；且源头「附注放行」无 D 编号背书，逐条确认的 D1 只覆盖「允许机器独立拦截」|
| **V4** | PRD §6.2「P0 用正则，无需大模型」 | P0 分字面 / 语义两类 | 与 §11.1「P0 漏报率 = 0」互斥：医疗宣称靠正则盖不住 |
| **V5** | PRD §7.3 七条一票否决 | 按权威来源拆四类，只有法规类叫红线 | 混了联邦法规、州法、平台政策、品牌建议四种东西 |

## §7 · 三个编号体系（**必须先合，否则后面全错**）

实测：仓库里并行着**三套互不接线的编号**。

| 体系 | 在哪 | 条数 | 谁在读 |
|---|---|---|---|
| **H/M/U/V 码** | 主 Base「品线内容边界规则库」| **21** | ✅ **引擎正在读** |
| **H/M/U/V 码**（另一子集）| 内容治理 Base「P0规则」表 | **17** | ❌ **全仓 0 引用** |
| **T 码** | 规则库 / 外部标准库的「关联规则」列 | 桥接列里出现 **19** 个（引擎叶子有 26 个，两者不等）| 桥梁（填充率 100%）|

> ★ 这里有个容易写错的数：**「引擎有 26 个叶子」≠「桥接列里有 26 个 T 码」**。
> 实测桥接列只出现 19 个（缺 `T2.1.2` 之外的若干、且 `T9` 完全不在桥接列里）。
> 写文档时把这两个数混为一谈，就会得出「桥接完整」的假结论。

**两条硬事实：**
1. **「P0 是什么」在盘上有四个答案，且至少两个互相矛盾：**

   | 出处 | 是什么 | 条数 |
   |---|---|---|
   | PRD §6.2 | 那一列叫「**典型规则**」—— 归纳性质 | **举例 5 个**（不是一个枚举）|
   | PRD §7.3 | 「一票否决项」—— 枚举性质 | **7 条** |
   | 内容治理 Base「P0规则」表 | 标 `优先级=P0` | **17 条** |
   | 老引擎 `rules-v1.json` | 标 `severity=L4 高危` | **11 条** |

   ★ **矛盾点在同一个 M03**：`P0规则` 表把它标 `P0 / 风险 High`，
   而引擎规则源「品线内容边界规则库」把它标「**审慎关注**」、`rules-v1.json` 标 `L2 审慎`。
   **一张表说它是红线，另一处说它是审慎关注 —— 两端都在盘上，没有任何东西会红。**
   （PRD §6.2 与 §7.3 之间也不一致：前者「典型规则」5 个举例里，
   不含 §7.3 的「危险行为示范 / 销量排名宣称 / AI 标识」三条。）
2. **V01–V06 只活在一张没有任何代码读的多维表里。**
   而 PRD §7.3 那七条里，**有四条（安全座椅 / 危险行为示范 / 未成年人出镜 / AI 合成标识）
   在引擎规则库和主题树里都是 0 次命中。**
   （★ 我先前写「五条」，多算了「肖像」—— 它是「未成年人出镜 / 隐私暴露」那条的组成部分，§7.3 没有单列它。）

**合并后的形状（已定）**：T 码挂外部依据，H/M/U/V 挂内部控制点，**一条问题同时带两个码**。
