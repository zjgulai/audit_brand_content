## §0 · 一页纸

**任意形态的营销内容进去，可执行的审查结论 + 可溯源的证据 + 可统计的读数出来。**

委托方原话的**归纳**（不是逐字引用）：
> 输入图片 / 链接 / 视频 / 文本 → 多模态解析成可判的东西 → 用 skill + 规则库 + 知识库审一遍
> → 按 P0–Pn 判审核状态（★ 用户原话；本 Playbook 把「严重度」统一记为 `L`，见 §1.1.1）→ 按模板出文字卡片或报告。

> **第一阶段运行与媒体形态（与 §4.5.5 TS-15 / TS-16 统一）**：Docker Compose 为阶段一**生产部署形态**；图片 / 视频的 OCR / ASR **全部运行于容器内跨平台模型**（不使用 macOS Vision / Speech 等宿主原生能力），既有基于 macOS + Vision/Speech 的本机实测读数**不得沿用**，必须在容器内模型上重做基线。

## §1 · 目标态

### 1.1 五个必须同时成立的条件

| # | 条件 | 判据（怎么知道它成立了） |
|---|---|---|
| **甲** | **进得来** | **四个维度**（内容形态 / 内容阶段 / 入口通道 / 来源种类）各自的全取值都能进链路，且都带内容指纹 —— 详见 §4.1 |
| **乙** | **判得准** | 每个结论都能指出**哪条控制点**、**哪条权威依据**、**在原文哪个位置** |
| **丙** | **处置得住** | 每条内容都有明确的下一步负责人，且**转出去之后有回音或超时升级** |
| **丁** | **说得清** | 群里一句话 + 报告详情；**未审的部分明确说未审，不冒充已审** |
| **戊** | **改得动** | 规则改了之后，**能回答「这次是变好还是变坏」** |

> ✅ **已定（委托方 2026-10-17）：外部与内部依据同等效力，但必须分类标注。**
>
> 「内部已批准」的判据是三条同时成立：**有版本 · 有批准人 · 有生效日**。
> 缺一条就只能算「内部说法」，不能当依据。
>
> ⚠️ **「乙」里的「权威依据」有两种，不是只有外部法规**：
> 外部法规 / 平台政策，**或**内部已批准的事实与品牌口径（如产品参数、品牌调性规则）。
> 要求「每结论必指外部法规」会把「事实控制」「品牌控制」两类逼成不可判。
> 判据的准确写法：**每个结论都指得出「它是凭哪一条权威说的」**，权威可以是外部也可以是内部**但必须是被批准的**。

### 1.1.1 两套刻度：`P` 是检测层，`L` 是严重度（**不是一回事**）

> ✅ **已定（委托方 2026-10-17）：P 是检测层，L 是严重度。**

| 刻度 | 答什么 | 取值 | 存在哪 |
|---|---|---|---|
| **`P0`–`P3`** | **这条是哪个检测层抓出来的** | `P0` 正则/关键词 · `P1` 大模型语义 · `P2` 多模态 · `P3` 措辞建议 | **Finding 的 `detected_by` 字段** |
| **`L0`–`L5`** | **这条有多严重** | `L0` 不知道 · `L1` 合规但受限 · `L2` 审慎 · `L3` 需修 · `L4` 高危 · `L5` 一次触顶 | **Finding 的 `severity` 字段** |

**两者互不推导：**

```
P0（正则抓到的）可以是 L5（极高危），也可以是 L2（审慎）
P2（多模态看出来的）可以是 L4（高危），也可以是 L1（合规但受限）
```

> ★ **这条必须写清楚的理由**：上游 PRD 里「P0」指的是**正则层**
> （「P0 规则引擎精确匹配，无需大模型推理」），
> 而原则三与 §6 指标里「P0」被当成**最高危**在用。**同一个词两个意思**，
> 直接导致实现者判断一条命中是 BLOCK 还是 REVIEW 时只能自己编。
>
> **本 Playbook 的裁定**：`P` 只表示**检测层**；**严重度一律用 `L`**；
> **凡说「严重」的场合一律写 `L4/L5`，不许再写 `P0`。**

### 1.2 三条不可让渡的原则

#### 原则一：审查标签 ≠ 发布放行

这两件事必须分开，**但分开的方式不是限制机器能说什么，而是限制「说了」意味着什么。**

| | 审查标签 | 发布放行 |
|---|---|---|
| **答什么** | 这次审查得出了什么 | 这条内容能不能上线 |
| **谁签发** | **机器可以下任何一档** | **永远由人做最后放行** |
| **载体** | 报告上的一个标签 | 实际发布 |
| **效力** | 对内容的判断 | 对发布的许可 |

**机器可以下全部五档：`BLOCK` / `REVIEW` / `未审查` / `待自决` / `PASS`。**
**但这五档没有一档等于放行。**

> **可机验的判据**：**不存在任何一条从「审查标签」直连「发布状态」的路径**。
> 五档全部停在「待放行」，必须有人签一次才动。

> **为什么这样分**：把限制加在「机器能说什么」上，会让机器在证据充分时也不敢说话；
> 把限制加在「说了算不算数」上，**机器的判断力可以放开，放行权仍然锁在人手里**。
> 前者是省事，后者才是可控。

#### 原则二：没命中 ≠ 安全，而且「没命中」还要再拆一次

一条内容没有命中任何规则，**结论不是 PASS**。但「没命中」本身有两种：

| | 含义 | 处置 |
|---|---|---|
| **`UNASSESSED`** | **没能力评估** —— 这个模态 / 这个规则域根本没跑 | 强制人工 + 进空白清单 |
| **`CLEAN-CANDIDATE`** | **已评估且干净** —— 确实按某规则版本、对某些模态跑过了 | 可进业务自审，**但仍是待放行** |

> 没有覆盖证明，**「审过了没问题」和「压根没审」在系统里长得一模一样** ——
> 这是整个产品最安静的失效模式。

#### 原则三：判定表唯一；严重度给下限，数量只影响呈现

> **这一条是对最初设想的修正。** 原设想是「按 P0–Pn 的个数统计判断状态」。
> **构造反例**（针对上游规则「问题数 ≥3 只出分类汇总」，不是生产样本）：
> 一条内容有 1 个 `L4/L5`（视频里宝宝未坐安全座椅）+ 2 个 `L1/L2`（措辞建议）= 3 个问题
> → 按该规则走汇总模式 → 群里只有「合规类 1 个、措辞类 2 个」，**最严重的那条被数量吞掉**。

**正确形状，六条一起成立：**

| # | 规则 |
|---|---|
| 1 | **唯一判定表决定状态**（只有一处能定）|
| 2 | **只有 `confirmed` 的 `L4/L5` 才有权给 BLOCK 下限** —— `candidate` 的命中不参与状态计算（见下）|
| 3 | **最高严重度给「状态下限」**：有已确认 `L4/L5` 就是 BLOCK 档，**数量再少也不降级** |
| 4 | **任何数量不得降级**：数量**只能升级或不变** |
| 5 | **特定共现可升级**：组合规则（如「场景名词 + 消除性动词 = 功效承诺」）**有权上调** |
| 6 | **普通数量只影响呈现**：决定「群里出几句、详情放报告」，**不决定状态** |

##### 第 2 条必须展开：`candidate` 与 `confirmed`

| finding 状态 | 谁能产生 | 参与状态计算？ | 出口 |
|---|---|---|---|
| **`confirmed`** | **`rule`（确定性规则）或 `human`（人确认）** | ✅ 参与，可按严重度给下限 | 按判定表出状态 |
| **`candidate`** | **只有 `semantic`（语义 / 多模态模型）** | ❌ 不贡献严重度，但**存在**可作为 REVIEW 门 | 只能作为 **REVIEW 的证据**，永不给 BLOCK 下限 |

> ⚠️ **「`confirmed` 只由深档产生」这个写法是错的（2026-10-17 更正）。**
> **`confirmed` 有三个合法来源**：① 规则直接判定（`produced_by=rule`）；
> ② **满足 C1–C4 的明确规则类语义判断**（`produced_by=semantic`，见 §3.3.4.1）；
> ③ 人确认（`produced_by=human`）。
> **区别在 `produced_by` 字段，不在 `status` 字段。**
> 语义模型**默认只能出候选**，只有同时满足 C1–C4 时才能直接确认。

> **为什么必须分开**：浅档产出的是「疑似」，它连「这条有多严重（L 级）」都还没确认。
> 允许候选直接给 BLOCK 下限，等于**用未确认的判断去触发最重的处置**，
> 而且它绕过了「浅档必须转人工」这条设计。
>
> **正确链**：浅档出 `candidate` → 转人工 → 人确认为 `confirmed` → **此时才进判定表**。
> 人工确认的那一步有记录，可追溯。

## §2 · 工作流：五步

内容从进来到出去，经过五步。**这是 pipeline，不是 loop** —— 每步恰好执行一次，**无回边**。

```
① 归一化（进）    任意形态 → ContentUnit v1（**不是 IR**）
② 判定（判）      内容单元 → findings（confirmed / candidate）
③ 处置（置）      findings → 状态 + 负责人 + 时限
④ 输出（出）      IR → md 渲染 → 群里一句话 + 报告
⑤ 评估（证）      运行数据 → 四个可测数
```

> **「步」不是「轮」**：第一阶段工作流始终**无回边**，没有「轮次」概念，每步恰好执行一次；人工复核或失效触发的重审是**新的独立 run**（产出新 `ReviewIR` 与新报告，不改旧记录），不构成流水线回边。
> 关于未来阶段回边的设想已移出正文，见文末「**未来附录 · 非阶段一 · 不进验收**」。

## §3 · 输入与运行契约

### 3.1 输入：四个正交维度（**不是一个「形态」清单**）

**v1 把它们混成了一个清单，导致「五种全覆盖」无法验收。现拆开：**

> ✅ **已定（委托方 2026-10-17）：第一阶段覆盖四条通道，Word/PDF 与 NAS 显式不做。**

| 维度 | 字段 | 取值域 | 第一阶段 | 答什么 |
|---|---|---|---|---|
| **内容形态** | `content_type` | 文本 / 图片 / 视频 / 文档 / 结构化记录 | 文本 ✅ · 图片 ✅ · 视频 ✅ · 文档 ⚠️（仅飞书文档）· 结构化记录 ✅ | **它是什么东西** |
| **内容阶段** | `content_stage` | `brief` / `final_content` | 两者都收 | **它处在什么阶段** |
| **入口通道** | `entry_channel` | 群消息 / 飞书文档链接 / 落地页 URL / 多维表批量 / **NAS** / **上传文件** | 前四条 ✅ · **NAS ⛔ unsupported** · **上传文件 ⛔ unsupported** | **它从哪儿进来** |
| **来源种类** | `source.kind` | 广告记录 / 自由文本 / 落地页 / 结构化 JSON / 图片 / 视频 / 文档 | 除 `文档` 外全支持 | **它的原始载体是什么** |

> ⚠️ **两个 `unsupported` 必须显式留在取值域里，不许从列表里删掉。**
> 删掉它 = 「这个通道不存在」；留着标 `unsupported` = 「知道它该有，现在没做」。
> 两者在报告里长得完全不同 —— 前者永远不会出现在「未审说明」里，后者会出现。
>
> **必然后果**：产品经理手里的 `.docx` brief 第一阶段进不来，得先贴成飞书文档或直接贴文字。
> 这是**已接受**的代价，不是遗漏。
>
> ✅ **NAS 单独确认（委托方 2026-10-17）：保留在需求里，标 `unsupported`，不划掉。**
> 理由：划掉 = 「它本来就不该在这个产品范围里」；标 `unsupported` = 「它该有，现在没做」。
> 两者的区别在报告里看得见 —— 前者永远不会出现在「未审说明」里，后者会出现。

> **`brief` 是阶段不是形态**；**「链接」是入口不是形态**。原 v1 把它们并列，是分类错误。

**覆盖判定**：四个维度**各自**的全取值都必须能进链路。
「进了 4 种形态」不等于「4 个维度都覆盖」—— 验收按维度分别断言。

#### 判据

| # | 判据 |
|---|---|
| **L1-0** | 四个维度的每个取值都能被**单独**提交并产出内容单元（逐个取值断言，不是抽样）|
| **L1-0b** | 未实现的取值必须**显式登记为 `unsupported`**，不是从列表里消失；**验收时对 unsupported 取值要做反向断言** —— 提交它必须**明确报出未支持**，不许静默跳过 |
| **L1-0c** | 「忘了做」与「决定不做」在验收结果里**必须长得不同**：前者报红，后者报 `unsupported`（不是通过，也不是红）|

### 3.2 归一化：内容单元（`ContentUnit`，**不是 IR**）

> ✅ **已定（委托方 2026-10-18）：运行级 `ReviewIR` 是唯一真相（见 §4.3）。**
> 本节产出的东西**不是 IR**，是一个**被引用的输入对象** —— 名字叫 `ContentUnit v1`。
> 上一版这里标题写「内容单元（IR）」，与 §4.3 的「结构化记录（IR）」**同词两义**，
> 导致 `source_ir_version` 到底指向哪一层无法回答（S-3）。现在只有一个 IR。

**输入**：任意维度组合的内容
**输出**：**`ContentUnit v1`** —— 可判正文 + 双指纹 + 覆盖声明 + 来路。

> ★ **它不叫 IR。** 唯一叫 IR 的是 §4.3 的 `ReviewIR`（运行级记录）。

| 项 | 要求 |
|---|---|
| **双指纹** | `raw_sha256`（哪份原件）+ `text_sha256`（能不能复算）。**两个都要** |
| **覆盖声明** | 每种形态**必须显式声明** `covers` / `does_not_cover`，**刻意不设默认值** |
| **失败必须可读** | 带 `parse_status`（`ok` / `partial` / `failed`）；`failed` 带 `failure_kind`（`fetch_error` / `parse_error` / `empty` / `unsupported`）|

#### 判据

| # | 判据 |
|---|---|
| **L1-1** | 每个内容单元都能复算出同一个单元标识 |
| **L1-2** | 每个单元都**显式声明** `covers` **和** `does_not_cover` 两个字段（**字段必须存在**；`does_not_cover` **可以是空数组**，表示「没有未覆盖的部分」）。**不许缺字段、不许给默认值** |
| **L1-3** | 位置字段能**点回原片**（视频时间码 / 图片区域），不是自然语言 |
| **L1-4a** | **确定性解析档**（纯文本、结构化字段）：同输入 + **同解析器版本**，两次解析正文指纹**必须相同** |
| **L1-4b** | **非确定性解析档**（OCR / VLM）：同输入 + 同模型版本 + 同采样配置，**多次解析的结论集合差集必须为空**（不要求逐字相同）|
| **L1-5** | `parse_status=failed` 的单元**不得**进入判定，只能落「未审查」 |
| **L1-6** | `parse_status=partial` 的单元**可以**进判定，但**只在其已覆盖部分上**，且**永不产出 PASS** |
| **L1-7** | `empty` 与 `failed` **必须能被分别数出来** |
| **L1-8** | 每次运行的报告里，四种 `failure_kind` 的**条数必须出现**（哪怕全是 0）|

> **L1-4 为什么改**：v1 写「两次解析正文指纹必须相同」——
> **对 OCR / VLM 不成立**。模型输出天然有抖动，用「逐字相同」验收会让这一条永远红，
> 或者逼着实现去伪造确定性。**限定版本 + 改用集合比较**才是这条真正想验的东西。

| `quote` | string | 逐字片段 |
| `produced_by` | enum | `rule` / `semantic` / `human` |
| `derived_from` | string \| null | append-only 的来源（见 §3.3.4.2）|
| `confirmed_by_rule_class` | bool | 仅 `semantic` 直接确认时必填 `true`（见 §3.3.4.1）|

> **`status` 决定它能不能参与状态计算**（原则三第 2 条）。

##### 3.3.4.1 合法组合：`produced_by` × `status`

**不是任意组合都合法。** 下表是白名单，表外组合一律拒收：

| `produced_by` | `candidate` | `confirmed` | `rejected` | **`superseded`** | 说明 |
|---|---|---|---|---|---|
| `rule` | ❌ | ✅ | ✅ | ✅ | 规则命中即确认 |
| `semantic` | ✅ | ✅ **仅限「明确规则类」**（C1–C4）| ✅ | ✅ | 见下方判定条件 |
| `human` | ❌ | ✅ | ✅ | ✅ | 人可直接新建、驳回、撤销 |

> ★ **`superseded` 是 append-only 的必需状态**：任何一条被新条目取代的 finding
> 都要标它，**`produced_by` 保持原值不变**。
> 上一版白名单漏了这一列，导致每次确认/驳回都被「表外一律拒收」挡死 —— 2026-10-17 修。

> ✅ **已定（委托方 2026-10-17）：明确规则类可直接确认。**

##### 「明确规则类」的判定条件（**四条同时满足，缺一条降为候选**）

> **为什么要有条件**：允许语义模型直接确认，等于让模型自己给自己背书。
> 只有在**判据本身是客观的、可外部复核的**时，这个背书才成立。
> 「明确规则类」不能是一句可以随口解释的话，它必须是**四条可机验的条件**。

| # | 条件 | 怎么验 |
|---|---|---|
| **C1** | 该 finding 挂的 `control_code` 在控制点主表里标 `judge_type = literal` | 查主表，不靠模型自述 |
| **C2** | 判定依据是**可枚举的视觉对象 + 可枚举的属性**（如「安全带」这一对象 + 「未扣合」这一状态），不是「氛围」「感觉」「调性」 | 输出必须给出结构化的 `object` + `attribute` 两个字段 |
| **C3** | 该 finding 的 `quote`（画面描述）能被**另一个模型或人**独立复核出同样结论 | 抽检：同一帧送第二个模型，结论一致率要能被统计 |
| **C4** | `location` 的 `bbox` 存在且非空 | 指不出画面哪一块，就不是明确规则 |

> **C2 是这条边界的核心**：「宝宝未坐安全座椅」满足 C2 —— 对象是「安全座椅」，属性是「未使用」。
> 「画面显得不够温馨」**不满足** —— 它没有可枚举的对象与属性，只能落候选。

##### 三条必须同时记下的限制

| # | 限制 | 为什么 |
|---|---|---|
| **M1** | 即使满足四条，仍需记录 `produced_by=semantic` 且 **`confirmed_by_rule_class=true`** | 报告里要能一眼分出「人确认的」与「模型按明确规则确认的」 |
| **M2** | C3 的一致率**必须被统计并公示**；低于阈值时该 `control_code` 自动降回「只能出候选」。**阈值不预先给定** —— 先跑一轮测出基线，再以基线定阈值（与 §6 指标目标线同一口径）。**在阈值定出来之前，该 `control_code` 的「明确规则类」开关默认关闭**，只能出候选 | 否则一次模型退化会把整类判断悄悄带偏；而凭空拍一个数等于没拦 |
| **M3** | 该能力**按 `control_code` 逐个开**，不是全局开关；**默认全部关闭** | 开一个点验一个点，不许「先全开再说」 |

> ⚠️ **这条改动直接放宽了「模型不能自己确认自己」这条原则**，代价是真实的：
> **画面类问题会绕过人工直接进入 BLOCK**。
> 兜底是 C1–C4 四条 + M1–M3 三条 —— 但这七条如果实现时打折，
> 就等于把最重的处置交给了一个没有人工复核的模型结论。
> **验收时必须逐条构造反例证明它们真的拦得住。**

##### 3.3.4.2 状态转换表

```
  （无 finding）
        │ rule 命中
        ▼
   confirmed ──────────────┐
        │ 人复核撤销        │
        ▼                  │
   rejected                │
                           │
  （无 finding）            │
        │ semantic 产出     │
        ▼                  │
   candidate               │
        │ 人确认            │
        ├──────────────────┘
        │ 人驳回
        ▼
   rejected
```

> ★ **2026-10-17 改为 append-only。**
>
> **精确说法（上一版写得自相矛盾，已更正）**：
>
> | 什么 | 能不能改 |
> |---|---|
> | `control_code` / `severity` / `location` / `quote` / `detected_by` / `produced_by` / `authority_ref` | **永不改** |
> | `status` | **只允许一次转换：→ `superseded`** —— 这是**标记它已被取代**，不是改写它的判断 |
>
> **所以「不可变」的准确含义是：一条 finding 的「判断内容」不可变；它只会被标记为「已被新条目取代」。**
> **所有实质状态变化（候选→确认、确认→撤销）一律新建一条**，用 `derived_from` 指回上一条。

| 动作 | 谁触发 | 产生什么 | 旧的那条 |
|---|---|---|---|
| 语义产出 | `semantic`（默认）| **新建** `candidate` | — |
| 规则命中 | `rule` | **新建** `confirmed` | — |
| 语义直接确认 | `semantic` + C1–C4 全满足 | **新建** `confirmed`，`confirmed_by_rule_class=true` | — |
| 人直接新建 | `human` | **新建** `confirmed` | — |
| **确认某候选** | `human` | **新建** `confirmed`，`derived_from=<candidate_id>` | 原候选标 `superseded` |
| **驳回某候选** | `human` | **新建** `rejected`，`derived_from=<candidate_id>` | 原候选标 `superseded` |
| **撤销某确认** | `human` | **新建** `rejected`，`derived_from=<confirmed_id>` | 原确认标 `superseded` |

**`status` 的完整取值**：`candidate` / `confirmed` / `rejected` / **`superseded`**。

| 状态 | 参与状态计算？ |
|---|---|
| `confirmed` | ✅ 是 |
| `candidate` | ✅ 作为 REVIEW 门（不贡献严重度）|
| `rejected` | ❌ 否 |
| `superseded` | ❌ 否（被新条目取代，历史保留）|

> **为什么必须 append-only**：
> ① **同一条 finding 不能既是被确认的候选、又是确认结果** —— 那样 `derived_from` 会指向自己；
> ② **历史要留**：报告要能回答「这条当初是机器看出来的，还是人提出来的」，原地改就抹掉了；
> ③ **可复算**：给定任一时刻的 finding 集合，结论必须唯一 —— 有 `superseded` 这个显式状态才能做到。

##### 3.3.4.3 人工确认/驳回的审计字段（**四个都必填**）

| 字段 | 说明 |
|---|---|
| `reviewer` | 谁做的这个判断（不是「系统」，必须是具体的人）|
| `reviewed_at` | 什么时刻 |
| `reason` | 为什么（自由文本，不许空）|
| `source_finding_id` | 从哪条 finding 转来的（`candidate → confirmed` 时指回原候选）|

> **为什么 `source_finding_id` 必填**：候选变确认之后，报告里仍要能回答
> 「它当初是机器看出来的，还是人自己提出来的」。
> 没有这个字段，两者在终稿里长得一模一样 —— 正是本产品最怕的那种「分不清」。

> **`rejected` 是终态，且不进状态计算。** 被驳回的候选不再算「有 candidate」，
> 这就是 §4.2.1 第 3 条和 L2-6b 里「candidate」的准确定义：
> **只算 `status=candidate` 的，`rejected` 的不算。**

##### 3.3.4.4 `location` 的三种形态（**画面位置必须可点回**）

> ✅ **已定（委托方 2026-10-17）：画面断言用「时间码 + 帧号 + 区域框」。**

| 内容形态 | `location` 必填字段 | 可省 |
|---|---|---|
| **文本** | `{char_start, char_end, quote}` | — |
| **图片** | `{image_id, bbox}` —— `bbox` 为 `[x1,y1,x2,y2]` 归一化到 0–1 | — |
| **视频** | `{video_id, time_start, time_end, frame_no, bbox, frame_thumb}` | `bbox`（全画面断言时可省）|

**视频位置的四条硬要求**：

| # | 要求 | 为什么 |
|---|---|---|
| **LOC-1** | `time_start` / `time_end` **必须**有，单位秒，精度到 0.1s | 没有时间码，审核员不知道去视频哪一段找 |
| **LOC-2** | `frame_no` **必须**有，且要能由时间码与抽帧参数**复算出来** | 帧号是唯一能把「模型看的是哪一帧」钉死的东西 |
| **LOC-3** | `bbox` 用归一化坐标 `[x1,y1,x2,y2]`（0–1，左上为原点）| 绝对像素会因分辨率不同而失效 |
| **LOC-4** | `frame_thumb` 指向该帧缩略图，**必须**可访问 | 审核员点一下就能看到模型看到的那一帧 |

> ⚠️ **为什么不接受自然语言描述**（如「约第 12 秒，宝宝坐在副驾」）：
> ① **无法校验** —— 没法断言它指对了位置；
> ② **无法复现** —— 同一条断言第二次跑，模型可能说「第 13 秒」，看起来像另一条；
> ③ **无法一键跳回** —— 审核员要自己拖进度条找。
>
> **代价**：抽帧时必须维护「帧号 ↔ 时间码」的对应表；模型输出要后处理成结构化坐标。
> **这是已接受的成本** —— 画面断言如果没有位置，它就只是一句意见，不是一条 finding。

> ★ **LOC-2 与 V5 是一对**：回执记抽帧参数（§3.4 V5），finding 记帧号（LOC-2）。
> **两者缺一，帧号就是个孤立的数字** —— 换个抽帧间隔，同一个帧号指的就是另一帧。

#### 3.3.5 覆盖证明（Coverage）

**先分清两件被压成一件事的东西**（2026-10-17 更正）：

| 状态 | 含义 | 结论怎么受影响 |
|---|---|---|
| **`coverage_missing`** | **四项里缺字段** —— 根本产不出覆盖证明 | 结论只能落 **`未审查`**（它连「我评了什么」都说不清）|
| **`coverage_partial`** | 四项齐全，但**「未跑的为什么」非空** —— 有模态/控制点没跑 | 可以出结论，但**永不 `PASS`**，必须标「覆盖不全」 |

> ⚠️ 原先写「缺一项则结论只能落 `UNASSESSED`」，把这两种混成一种。
> 差别在于：**前者是「我说不清我做了什么」，后者是「我说得清，但确实有一块没做」。**

至少四项：

```
评过的模态      文本已评 / 图内文字已评 / 画面语义未评 / 音轨未评
规则版本        本次用的是哪一版规则（版本号 + 指纹）
适用控制点      七个控制族里，哪几个本次真的跑过、哪几个没跑
未跑的为什么    无能力 / 无规则 / 未接线
```

#### 3.3.6 知识库失败路径（**v1 缺，新增**）

`authority_ref` 取不到时，**默认动作是降级，不是放行**：

> ✅ **已定（委托方 2026-10-17）：三分法，冲突单独升级。**

| 情形 | 结论怎么变 | 标记 | 去哪一层 |
|---|---|---|---|
| 查不到依据 | 降为 `REVIEW` | `依据缺失` | DP3 内容审核员 |
| 依据已过期 | 降为 `REVIEW` | `依据过期` | DP3 内容审核员 |
| 多条依据互相冲突 | 强制转人工 | `依据冲突` | **DP4 法务**（不是 DP3）|
| 依据可取且唯一 | 维持原状态 | — | 按判定表 |

> **冲突为什么单独升级到法务**：缺失是**数据问题**（库挂了、指针坏了），
> 过期是**维护问题**（该更新了），而冲突是**规则问题** —— 两条被批准的依据互相矛盾，
> 说明规则库本身需要人裁。把这三者压成一种，就会让「规则打架」这个最强信号
> 在报表上看起来像一次临时故障。**三者必须能分别数出来。**

> **为什么默认降级**：规则命中而依据拿不到，意味着**我说它违规但我拿不出条款**。
> 这时候继续 BLOCK，违反「每结论可指依据」；继续 PASS，等于无据放行。**只有转人是对的。**

#### 判据

| # | 判据 |
|---|---|
| **L2-1** | 每个结论的状态 ≡ 判定表算出的值（**唯一来源**）|
| **L2-2** | 「没命中」必须落成 `UNASSESSED` 或 `CLEAN-CANDIDATE` 之一，**不许合成空结论** |
| **L2-3** | 每个结论都带**覆盖证明**四项，缺一项即落 `UNASSESSED` |
| **L2-4** | **检测层必须记录**（`detected_by` ∈ P0/P1/P2/P3）；`P0` 层只做字面可判的部分（正则/关键词），语义类不得走 `P0` |
| **L2-5** | 每个 `confirmed` finding 都能指出控制点 + 权威依据 + 原文位置 |
| **L2-6a** | **`candidate` 不得贡献严重度**：移除全部 candidate 后，**状态不得变得更重**（BLOCK 不许因 candidate 产生）|
| **L2-6b** | **`candidate` 的「存在」可以作为 REVIEW 的门**：有 candidate 且无 confirmed 时，落 REVIEW 并标「有疑似待确认」|
| **L2-7** | 每次执行落一张回执，**字段符合 3.3.3 schema**（含 `skipped` 空数组）|
| **L2-8** | 依据查不到 / 过期 / 冲突时，结论**必须**降级或转人（按 3.3.6）|
| **L2-9** | 浅档产出**不得**单独构成结论 |

> ⚠️ **L2-6 原先写的是「删掉全部 candidate 后结论必须一模一样」—— 那条是错的，2026-10-17 更正。**
>
> 因为它与 §4.2.1 第 3 条（「有 `candidate` 遗留 → 不许 PASS」）直接矛盾：
> 删掉 candidate 之后，一条原本 REVIEW 的内容会变成 PASS，结论**必然变**。
>
> **正确的拆法是两件事，不是一个**：

> | 问题 | 答案 | 判据 |
|---|---|---|
> | candidate 能不能**把内容打重**？ | **不能** | L2-6a：删掉 candidate，状态不许变得更重 |
> | candidate 能不能**把内容拦在 REVIEW**？ | **能** | L2-6b：有 candidate 没 confirmed → REVIEW |

> 一句话：**candidate 可以是「往上走」的理由（转人），不能是「往下砸」的理由（BLOCK）。**

| **MC-3** | 该命中的 `authority_state = ok`（依据可取、未过期、无冲突） | 依据不齐时**必须跑完全程**，不能提前收工 |

> ⚠️ **第一阶段的实际行为**：三条**永远**按「任一不满足」处理 —— 即无论命中如何，都跑完五步。
> 所以这句话在第一阶段的读法是「**总是继续跑完五步**」，不是「有时可以停」。

> ★ **为什么必须定义**：上一版只写「满足机结条件」，**没说什么叫机结条件** ——
> 于是这条停机条件既写不出验收样本，也没法被实现。**一个不可判的停止条件，
> 实际上就是「看实现者高兴」。**

> ★ **为什么 MC-3 不能省**：依据缺失时提前停，等于**用一个拿不出条款的命中收工**。
> 这与 §3.3.6「依据缺失必须降级」直接冲突。

> **因此第一阶段要跟着关掉一整串东西**：轮次上限、收敛判据、震荡检测、回执里的轮次字段。
> **它们不是「先写着以后用」** —— 写进验收表就会变成「必须在没有回边的情况下也成立」的假要求。
>
> **已接受的代价**：证据不足时**不会自动重试**，只能靠人。
> 具体表现：依据缺失 → REVIEW（走 §3.3.6 的三分法），而不是「回去再找一次依据」。

### 4.2 对外五标签

| 标签 | 含义 | 机器可否下 | 等于放行？ |
|---|---|---|---|
| **BLOCK** | 有问题，必须拦 | ✅ | ❌ |
| **REVIEW** | 需要人看 | ✅ | ❌ |
| **未审查** | 没能力评 | ✅ | ❌ |
| **待自决** | 判断权交回提交人 | ✅ | ❌ |
| **PASS** | 本次审查在覆盖范围内未发现问题 | ✅ | ❌ **（待人工签）** |

#### 4.2.1 PASS 的成立资格（**五条同时满足，缺一条不许下 PASS**）

| # | 条件 | 为什么 |
|---|---|---|
| 1 | **覆盖证明四项齐全**（评过的模态 / 规则版本 / 适用控制点 / 未跑的为什么，且「未跑的为什么」必须为空） | 有任何一块没跑，就不是「审过了没问题」，是「没审到」 |
| 2 | **无 `confirmed` 命中** | 有确定命中就不可能是 PASS |
| 3 | **无 `candidate` 遗留** | 有疑似未定，正确标签是 REVIEW 不是 PASS |
| 4 | **无 `UNASSESSED`** | 有无法评估的部分，就不成立 |
| 5 | **无「依据缺失 / 依据过期 / 依据冲突」标记** | 依据不全时结论必须降级（§3.3.6）|

> **缺任何一条时都不许给 `PASS`** —— 但**落到哪个标签不是一律 `REVIEW`**，
> 由 §3.3.8 的唯一判定表决定：
> 覆盖证明缺失 → `未审查`；有候选/有依据问题 → `REVIEW`；有确定命中 → 按严重度。
>
> ⚠️ **原先写「缺任何一条时正确标签是 REVIEW」是错的**（2026-10-17 更正）：
> 那条与「覆盖证明缺失应落未审查」直接冲突。**PASS 的五个条件只回答「能不能给 PASS」，
> 不回答「不给 PASS 时该给什么」** —— 后者归判定表。
>
> ★ **这条是 2026-10-17 补的。** 此前 §1.2 原则一写「机器可以下 PASS」、
> §4.2 写「PASS = 这次审查没发现问题」，但**从没说清「什么条件下才够格」** ——
> 于是「没命中」在实现时最省事的做法就是直接给 PASS。
> **资格条件不定义，PASS 就会退化成「没跑也算过」**，那正是原则二要防的东西。

> **为什么五个不是三个**：DP0 落不进三态。**没有文本可判 ≠ 合规。**
>
> （问题背景：存量 291 条里 59 条文本为空，其中 **55 条落「合规·绿」、2 条灰、2 条空** ——
> **不是全部 59 条**。出处 `research/governance/01-内部证据-规则表现状审计.md:177`。
> ★ 这是**问题背景**，不是本规格的现状描述。）

> ★ **PASS 标签附注（U8）与「五标签 ≠ 放行」的边界**：
> ① **五标签 ≠ 放行（已定死）**：当上表五条必要条件同时满足时，**机器可以输出 `PASS` 审查标签，但机器绝不可签发/放行** —— `release_status` 仍恒为「待放行」，必须由授权签发人经 §4.4 放行门签发才改变发布状态；
> ② **U8 待法务裁定的范围**：仅限「机器输出 `PASS` 标签时，报告/消息中伴随的覆盖范围与免责声明附注怎么写、是否需要额外措辞约束」，**不改变「机器可输出 PASS 标签」与「机器不可签发」这两条已定边界**。
> **两者是两件事，不要合并成一个待决项。**

### 4.3 输出：三个产物

> ✅ **已定（委托方 2026-10-17）：报告落静态文档，IR 是源。**

| 产物 | 给谁看 | 地位 | 存续 |
|---|---|---|---|
| **`ReviewIR`（运行级结构化记录）** | 机器读 | **唯一真相** | 保留 **1 年**（D-4 已定）|
| **Markdown 报告** | 人读 | **渲染视图**（某版 IR 的静态快照）| 落盘，**与 IR 版本绑定** |
| **群里一句话** | 群里 | **渲染视图（极简）** | 不保存（可查报告）|

**三条规则：**

| # | 规则 | 为什么 |
|---|---|---|
| **R1** | 报告落盘时**必须记它渲染自哪个 `ReviewIR` 版本**（`source_ir_version` + 指纹）。**`source_ir_version` 只指向 `ReviewIR`**，不指向 `ContentUnit` | 没有这一行，报告就是一份不知来处的文档；指错层，报告就重建不出来 |
| **R2** | IR 变了 → **重新生成一份新报告**，旧报告**不改不删** | 「改一份旧报告」会让两份历史记录互相污染；重建才是对的 |
| **R3** | 报告链接指向**那份静态文件**，**不指向渲染服务** | 渲染服务挂了，历史报告还得能打开 |

> ★ **R2 是这个决定的关键代价**：同一份内容可能会留下多份报告（每重判一次一份）。
> 报告里必须写清「我是第几版」，否则人会拿旧版做判断。

#### 4.3.1 Markdown 渲染（**v1 缺，新增**）

**它是工作流里的一步，不是可选项。**

| 项 | 要求 |
|---|---|
| **生成时点** | 在 ③ 处置定出状态之后、④ 输出之前 |
| **输入** | 结构化记录（IR） |
| **输出** | 一份 md 文档 |
| **必带区块** | 结论 / 命中的 finding（逐条）/ 覆盖证明 / 依据清单 / 未审说明 |
| **一致性判据** | md 里每条结论、每个 finding 都能指回 IR 的 id |

> **U1（md 词表未定）不影响这一步成立** —— 区块结构可以定，
> 而**用词与排版**可以后定。**先把「有哪几块」定死，再谈「怎么措辞」。**

#### 4.3.2 群里消息模板（按标签分）

**每个标签必带字段不同**：

> ✅ **已定（委托方 2026-10-17）：每档带一句关键信息，其余进报告。**

**统一骨架**：`【标签】` + **一句本档特有的关键信息** + 报告链接。

| 标签 | 那一句带什么 | 为什么是它 |
|---|---|---|
| **BLOCK** | 最严重那条 finding 的**严重度（L4/L5）+ 控制点 + 逐字原文 + 位置** | 看到这句就能判断「拦得对不对」；**不带严重度**就满足不了验收第 8 项 |
| **REVIEW** | **为什么需要人看**（哪一类判断机器给不了） | 复核员据此知道要找谁、看什么 |
| **未审查** | **为什么没审**（无能力 / 无规则 / 未接线） | 不写这句，「没审」会被读成「审完了没问题」 |
| **待自决** | **要提交人决定什么** | 不写这句，提交人不知道该改哪儿 |
| **PASS** | **覆盖证明一句话**（评了哪些模态） | 不写这句，PASS 与「没跑」分不开 |

**统一规则：**

| # | 规则 |
|---|---|
| **MSG-1** | 每档**恰好一句**，不许多也不许少 —— 多一句就开始刷屏 |
| **MSG-2** | 那一句**必须能被机器生成**，不是模型自由发挥 |
| **MSG-3** | 其余内容一律进报告，群里不展开 |
| **MSG-4** | 有**并行义务**时（§3.3.8.1b），在那一句后追加一个短标记，如「· 另有 1 条疑似待确认」 |

> ⚠️ **2026-10-17 撞号更正**：本节原用 `M1–M4`，与 §3.3.4.1（明确规则类 C1–C4 的配套限制）**同号不同义**。
> 现改为 **`MSG-1`–`MSG-4`**；§3.3.4.1 的 `M1–M3` 保持不变。**判据编号必须全局唯一**。

> ★ **为什么每档带的不一样**：五个标签回答的是**五个不同的问题**。
> 用同一句模板套五个标签，必然有两档的信息被丢掉 —— 那正是「PASS 和没跑分不开」的成因。

> **「PASS 必带覆盖证明」是关键**：没有它，PASS 和「没跑」分不开。

#### 4.3.3 报告章节与必带字段

> ✅ **已定（委托方 2026-10-17）：定死区块标题与字段名，句子怎么写放开。**

**六个区块的标题必须逐字如下**（可机验）：

| # | 区块标题（逐字） | 块内字段（逐字） |
|---|---|---|
| 1 | `## 结论` | `状态` · `判定依据` · `放行状态`（固定值「待放行」）· `并行义务` |
| 2 | `## 命中的问题` | 每条：`控制点` · `严重度` · `确认状态` · `位置` · `原文` · `依据` |
| 3 | `## 覆盖证明` | `评过的模态` · `规则版本` · `适用控制点` · `未跑的为什么` |
| 4 | `## 依据清单` | 每条：`依据编号` · `来源类型`（外部/内部）· `出处` · `生效期` |
| 5 | `## 未审说明` | `未审部分` · `原因`（无能力/无规则/未接线）· `责任人` |

**两条格式规则：**

| # | 规则 |
|---|---|
| **F1** | 六块**必须全在**，内容为空时写「无」而不是省略整块 |
| **F2** | 字段名**逐字使用上表**，不许同义替换（不许把「命中的问题」写成「问题列表」）|

> ★ **F1 的理由**：省掉空块 = 「这块没内容」与「这块没做」长得一样。
> ★ **F2 的理由**：字段名一改，机器解析就断了；而报告是要被机器读回去做比对的。

> **句子的写法不作规定** —— 只要六块与字段齐备，那一句怎么组织由生成时决定。

| **L4-6** | 群里**永不**出现卡片标记的原始字符 |
| **L4-7** | md 报告的**六个区块齐全**，且每条结论都能指回 IR 的 id |
| **L4-8** | 群里消息**按标签带齐必带字段**（§4.3.2）|
| **L4-9** | **PASS 只在 §4.2.1 五条同时满足时出现**；缺任一条**只是不许给 PASS**，落哪一档由 §3.3.8 判定表决定 |

> **L4-2 为什么改**：v1 写「链接有效期 ≥ 记录保存期」。
> 但报告是**渲染视图** —— 既然 IR 是唯一真相，报告本来就**可以重建**。
> 要求链接活得和记录一样久，是在给一个可重建的东西提不该提的要求。
> 正确要求是「**保存期内可稳定重建**」。

## §4.4 放行门（**2026-10-18 委托方定，**RL-1**…RL-15**）

> ★ **这一节补的是 Playbook 自己的一个洞。** §1.2 原则一写「五档全部停在待放行，
> 必须有人签一次才动」，但全篇**没有定义**谁签、怎么签、签在哪、怎么撤 ——
> 「状态机 / 身份 / ACL / RBAC / 角色 / 权限」在 v1.1 里 0 命中。
> 按本文件 §1 自己的纪律（凡写「必须」都要能指出什么情况下会红），
> 那句话此前**是愿望，不是规格**。本节把它变成规格。

### 4.4.1 四个交互面的职责（**RL-1**）

| 面 | 职责 | **不做什么** |
|---|---|---|
| **飞书群** | 提交入口、结果通知 | 不做复核、不签发 |
| **Web 复核工作台** | 复核 / 法务 / 申诉 / **签发** / 队列 / 权限 | 不是唯一入口（群里也能提交）|
| **静态报告** | **不可变的详情存档** | 不做交互、不可编辑 |
| **多维表** | 批量入口 + **只读投影** | 禁止写 `release_status` / 发布状态 |

### 4.4.2 放行状态机（**RL-2**）

```
                  人签发
   待放行 ──────────────────→ 已放行 ──撤回──→ 已撤回
     ↑                          │                 │
     │       内容/依据/送审指纹变化（**RL-6**）        │
     └──────────────────────────┴─────────────────┘
                  人拒绝
   待放行 ──────────────────→ 已拒绝（修改后重新提交）
```

**每一次放行动作必须绑定四样东西**（缺一不许落盘）：
`内容版本` · `理由` · `操作者` · `时间`。

> ★ **「已放行」不是一个可以长期成立的结论，它是一个有输入前提的判断。**
> 前提变了它就失效 —— 这条是本节与「点一下就完事」的审批流最大的区别。

### 4.4.3 谁能签（**RL-3** / **RL-4** / **RL-5**）

| # | 规则 |
|---|---|
| **RL-3** | 签发权**按授权名单配置**，与「提交」「最终复核」职责**分离**。**不得签发自己提交或自己最终复核的案件**。撤回权**单独授权**，不随签发权自动获得 |
| **RL-4** | 授权名单的粒度是 **租户 + 品线** —— 不是全局一个人 |
| **RL-5** | 名单治理：**法务负责人提案，IT 管理员执行**；新增 / 扩大范围 / 授予或撤销 均需**另一名授权审批人双人确认**；**全变更留痕** |

> ★ **为什么「不得签自己复核的」要写进合同**：否则「两个人签」可以退化成一个人换个账号。
> 这条的可机验判据是：`signer_id ≠ submitter_id` **且** `signer_id ≠ final_reviewer_id`。

### 4.4.4 变化即失效（**RL-6**）

**五条任一变化 → 旧签发自动标 `已失效` → 回 `待放行` → 触发全量重审**：

| # | 触发源 | 具体比什么 |
|---|---|---|
| 1 | **内容指纹** | `raw_sha256` / `text_sha256` |
| 2 | **`rule_snapshot`** | 签发时钉住的规则库版本 |
| 3 | **`kb_snapshot`** | 签发时钉住的知识库版本 |
| 4 | **`authority_ref` 的实际版本集合** | 逐条依据的版本，不是只有集合本身 |
| 5 | **冲突表版本** | `conflict_table_version` |

> ★ **第 4 条容易被做错**：只比「引用了哪几条依据」不够 ——
> 同一条依据**内容改版但 id 不变**时，集合没变而依据变了。必须比**版本**。
>
> ★ **失效是自动的，且人工不能阻止。** 检测到上述任一变化即 `invalidated`，
> 随即自动触发全量重审（**RL-11**）。**没有任何「确认后再生效」的中间态** ——
> 那不是审慎，那是让一份过期结论继续带着有效的签。

**重审完成后才可重新签发。** 已拒绝的案件修改后**重新提交**（不是复用旧案件）。

### 4.4.5 重审怎么跑（**RL-10** / **RL-11** / **RL-14**）

| # | 规则 |
|---|---|
| **RL-11** | 失效后系统**立即**创建全量重审任务并**自动入队**，通知相关人员 —— **不等人工确认** |
| **RL-10** | **全量重审**：重跑全部适用控制点、模态提取、依据同步与判定，产出**新的 `ReviewIR` 与新报告**，**旧版本保留** |
| **RL-14** | **连续变化合并**：重审**未开始前**，连续变化合并进同一 job 并累积完整 `change_set`；job **开始后**再变化，当前 job 完成后**自动追加**一次新的全量重审。**不并行、不丢历史** |

> ★ **RL-14 防的是同一形状的第二次发生**：`AGENTS.md` §2.4.6 记过「跳过被当成重排」——
> 事件被冷却挡下后没有东西在冷却过期后补回来。这里同理：
> 一个正在跑的重审不能吞掉跑完之后才出现的变更。

### 4.4.6 失效与申诉（**RL-12**）

| 规则 |
|---|
| 旧版本的申诉**自动暂停**并标「版本失效」 |
| 全量重审后，由**原申诉人**确认是否迁移到新版本 |
| 旧申诉记录与材料**完整保留**，**不自动关闭、不自动迁移** |

### 4.4.7 已发布内容的下线（**RL-7** / **RL-8** / **RL-9** / **RL-13**）

**撤回或自动失效后生成「强制下线任务」**，通知投放侧 / 签发人 / 审核负责人。
**系统只跟踪任务，实际外部平台下线由有权限的人执行并回填 —— 不自动调用平台。**

| # | 规则 |
|---|---|
| **RL-8** | **不设硬时限。** 记录 `created` / `assigned` / `started` / `completed`，持续提醒、可见积压。**不得把「无期限」显示成「未超时」或「正常」** —— 指标显示**任务年龄**与**未完成数**，**不做超时判定** |
| **RL-9** | **回填最小证据**：`platform` + `executed_by` + `executed_at` 必填，且**至少**提供「平台回执号」或「可访问结果链接」之一；无回执/无链接的平台可用**截图**替代。**无证据不得 complete** |
| **RL-13** | 未完成任务**每日**提醒负责人 / 投放侧 / 审核负责人各一次；状态变化**立即**通知；仍**无硬截止时间** |

> ★ **RL-8 那句「不得把无期限显示成未超时」是这一组里最容易被做错的一条。**
> 一个没有截止日的任务，在绝大多数看板上会显示成「进行中（正常）」——
> 那是**用缺省值伪装成判断**。合同要求它显示**年龄**（已经挂了几天），
> 而不是显示一个「没有超时」的绿标。

### 4.4.8 规则变更入口（**RL-15**）

**阶段一：Web 只读**规则 / 控制点 / 路由。
修改**只在既有权威源完成**，再由系统**同步拉取**并**触发重审**。
**禁止 Web / API 直接写权威源。**

> ★ **为什么不在 Web 上做规则编辑**：规则一变，所有已签发案件同时失效（**RL-6**）。
> 让「改规则」发生在一个会留下 diff、会走评审的地方，是这条的唯一理由 ——
> 不是技术限制。

### 4.5.1 身份与访问（TS-1 / TS-11 / TS-13 / TS-20）

| # | 判据 |
|---|---|
| **TS-1** | 所有**写操作**（提交、复核、申诉、签发、撤回、豁免）都必须有**已认证的 `principal`**，且 `principal` 绑定 `tenant` + `open_id`。**开发/模拟身份在生产环境必须被拒绝**，不许「本地能过就上线」 |
| **TS-11** | Web 会话：`idle` 30 分钟、`absolute` 8 小时。**高风险动作（`sign` / `revoke`）在会话内仍需二次确认** —— 长会话不等于长期授权 |
| **TS-13** | 二次确认凭证：**5 分钟有效、只能消费一次、绑定 `actor + case + action`**。**不能跨案、不能跨动作复用** |

| **TS-20** | 撤权的影响范围：**历史签发继续有效**；撤权后**不能新签**；**原签发人仍可撤回自己的历史签发**，但需**一次性 SSO + 理由 + 审计** |

> ★ **TS-13 与 RL-3 是两条独立约束，缺一条另一个方向就恒真**：
> RL-3 管「**谁能签**」（身份与职责分离），TS-13 管「**这一次动作是不是他本人刚确认的**」。
> 只有 RL-3 时，一个被盗的会话可以签任何他有权的案子；只有 TS-13 时，同一人可以签自己复核的案子。

### 4.5.2 界面与无障碍（TS-9 / TS-12 / TS-14）

| # | 判据 |
|---|---|
| **TS-9** | 达到 **WCAG 2.2 AA**。**自动** `axe` 全页扫描 + **关键流程人工核验**（键盘可达 / 读屏 / 焦点顺序 / 对比度 / 目标尺寸 / 认证流程可访问性）。**两者缺一不算达标** —— 自动扫描抓不到「键盘走不通」这类问题 |
| **TS-12** | **仅支持桌面 Chrome 的最近两个主要版本**。**不承诺** Edge / Safari / 移动端全功能 —— 这个范围要**明写在界面上或交付说明里**，不许让用户以为到处都能用 |
| **TS-14** | 最小桌面视口 **1280×720**；更大视口自适应；**400% 缩放 / reflow 仍满足 AA** |

> ★ **为什么 TS-9 要求「自动 + 人工」两条都做**：`axe` 能查对比度和标签，
> **查不出「焦点跳到看不见的地方」**。只报自动扫描通过，等于用工具覆盖了一条它覆盖不了的风险 ——
> 这正是本文件 §6.1「未测不许说没问题」的同一个形状。

### 4.5.3 运行时、依赖与投影库（TS-2 / TS-3 / TS-4 / TS-5 / TS-6 / TS-7 / TS-8）

| # | 判据 |
|---|---|
| **TS-2** | 后端运行时为 **Python 3.12**。**全部既有 verifier 必须在 3.12 下全绿** —— 换运行时不是换一个版本号，是整套自证要重跑一遍 |
| **TS-3** | Python 依赖**锁定安装**（`pyproject.toml` + 锁文件）；**开发 / CI / 生产三处一致**；**禁止无锁安装** |
| **TS-4** | **投影库从 SQLite WAL 起步**，但**文件 + manifest 仍是唯一真相**。查询可以走投影库，**重建必须只依赖文件**。迁移到别的库的门槛按四项读数定：写锁等待、并发写者数、库体积、是否多主机 —— **阈值压测后锁，现在不预设** |

### 4.5.4 API 层（TS-10）

| # | 判据 |
|---|---|
| **TS-10** | 后端提供 **OpenAPI 3.1** 描述的装配层，承载 SSO / RBAC / 工作台读写 / 队列 / 申诉 / 签发。**判定仍由既有模块唯一计算，API 层不得重算任何状态** |

> ★ **「API 不得重算状态」是本条的核心。** 一个便利的 `GET /cases/{id}/status`
> 很自然会在服务层顺手算一遍 —— 那就出现了**第二个判定实现**，
> 直接违反 `L2-1a`（判定逻辑唯一）。可机验的判法：API 层不得 import 任何判定函数，
> 且同一案件经 API 读到的状态必须与 `decision_table` 的输出**逐字段相等**。

### 4.5.5 部署与媒体（TS-15 / TS-16）

| # | 判据 |
|---|---|
| **TS-15** | **阶段一生产部署形态**为**容器化编排**（Docker Compose，与 §0 一致），可复现；数据卷 **0700**；**健康检查与重启策略必须定义**；单写者约束不得因容器化而失效 |
| **TS-16** | 图片 / 视频的 OCR / ASR **全部使用容器内跨平台模型**，**不使用宿主操作系统的原生能力**（macOS Vision / Speech 等）；**既有 macOS + Vision/Speech 的本机实测读数不得沿用** |

> ⚠️ **TS-15 / TS-16 是本次改动里风险最高的两条，必须单独说清楚：**
>
> | 风险 | 说明 |
> |---|---|
> | **旧 macOS+Vision 读数不能沿用** | 既有的本机 OCR / ASR 实测读数**是在 macOS 原生能力（Vision / Speech）上跑出来的**。阶段一生产形态定为 Docker Compose + 容器内跨平台模型后，**那些旧读数一个都不能沿用** —— 准确率、时码、bbox、性能全部要在容器内模型上重做基线 |
> | **部署形态变了，守衡也要处理** | 现有飞书长连接跑在 `launchd` 下（见 `AGENTS.md` §2.7）。Docker Compose 作为阶段一生产形态时，飞书长连接与容器编排是共存还是迁移，须在部署门（DC-2）中锁定 |
> | **模型未选 = 多模态开发 NO-GO** | 在模型 / 许可证 / 隐私 / CPU-GPU / 准确率 / 时码 / bbox / 性能基线 / 回归门这些定完之前，**多模态相关开发不得开工** |
>
### 4.5.6 媒体算力与模型选型（TS-17 / TS-18 / TS-19 / TS-21）

> 详见下表；TS-22 / TS-23 见 §4.5.7。

| # | 判据 |
|---|---|
| **TS-17** | 阶段一**以 CPU 容器为主**，GPU **后评估**。通过队列与并发控制管理吞吐。**时延或准确率不足时必须给出显式读数并由人决策** —— **不预设 GPU 是默认答案** |
| **TS-18** | **OCR 首轮候选**：PaddleOCR（CPU 主选）+ Tesseract（基线）。用**真实中英文广告图**（含低清、旋转文本）评**许可证 / 准确率 / bbox / 时延**四项，**过门后才锁版本** |
| **TS-19** | **ASR 首轮候选**：faster-whisper（CPU 主选）+ Whisper 官方（基线）。评**中英 / 噪声 / 多人 / 长视频**四类语料下的 **license / WER 或 CER / segment 时间码 / latency / memory** 五项，**过门后才锁模型体积与版本** |
| **TS-21** | **阶段一不做 speaker diarization，不识别真实身份。** 只输出带起止时间的片段，多人**完整转写**，`speaker = unknown`。**不因无法区分说话人而丢内容** |

> ★ **TS-17 那句话要读准**：「不预设 GPU」不是「不用 GPU」，是**不许把「加 GPU」当成
> 性能不达标时的默认解法**。要求的是：不达标时先出读数（多慢、多不准、卡在哪个环节），
> 再由人决定是换模型、降范围还是加算力。
> **一个直接扩机器就绕过去的团队，测不出自己到底差在哪。**
>
### 4.5.7 通知、签发绑定与前端库（TS-22 / TS-23 / TS-24 / TS-25 / TS-26）

| # | 判据 |
|---|---|
| **TS-22** | **重审通知只在 Web 工作台内**（in-app inbox / unread / ack），**不主动发飞书、不发个人、不发群**。**必须能证明责任人可见**（inbox 条数 + 未读 + 已读回执）。**不许声称「已通知到人」** —— 系统只知道「已投递到 inbox 且已读」，不知道人有没有看 |
| **TS-24** | 签发还须绑定**四类媒体产物的独立指纹**：抽帧清单/关键帧（`frame_manifest_hash` / `keyframe_set_hash`）· OCR 结果（`ocr_output_hash`）· ASR 结果（`asr_output_hash`）· 模型与采样配置（`model_config_hash` / `sampling_config_hash`）。**任一变化 → 自动失效并触发全量重审**（同 RL-6）。「独立记录」的含义是：四类各自有独立指纹字段，**不许把四样只压成一个总指纹而省掉逐项字段** —— 否则改一样和改四样长得一样，分不出是哪一类导致的失效。**与 TS-27 的关系是「四类逐项 + 集合 root」并存、非互斥**：签发记录同时保存四类逐项独立指纹（管归因定位）与 TS-27 的 `media_fingerprints_root_hash`（管集合级完整比对） |
| **TS-23** | 每条 `signature`（`release_signatures`）记录必须执行**全字段绑定**（对齐 UIUX v1.3.1 §8.4）：<br>① **核心版本与内容九字段（子集）**：`case_version` · `ReviewIR`（`ir_id` + `ir_version`）· `raw_sha256` · `text_sha256` · `rule_snapshot`（version+hash）· `kb_snapshot`（version+hash）· `used_authority_refs[{ref_id,version}]` · `conflict_table_version` · `signature_version`；<br>② **媒体逐项指纹与集合 root**：`frame_manifest_hash` · `keyframe_set_hash` · `ocr_output_hash` · `asr_output_hash` · `model_config_hash` · `sampling_config_hash` · `media_fingerprints_root_hash`（见 TS-24 / TS-27）；<br>③ **签发身份与二次确认审计**：`signature_id` · `case_id` · `signer_id` · `signed_at` · `step_up_ref` · `decision` · `reason`。<br>**说明**：此前简写的「九字段」是全字段绑定的**核心版本子集**（与 RL-2 的最小审计四要素共同构成全字段的一部分），而非只绑九个字段；**全字段任一必填项缺失，该签发不成立** |
| **TS-25** | 前端服务端状态与表格：**TanStack Query**（缓存 / 失效 / 轮询 / 错误处理）+ **TanStack Table**（复杂表格 / 虚拟化）。版本按兼容矩阵后锁 |
| **TS-26** | **阶段一不做独立指标看板。** 案件 / 队列 / 报告页只显示必要计数、趋势摘要、以及「未测 / 样本不足」。**先保证指标合同（L5-1…L5-5）成立，再谈看板** —— 把指标做成看板而合同不成立，是拿图表替代读数 |
### 4.5.8 媒体指纹、会话存储、对象 ACL 与队列（TS-27 … TS-33）

| # | 判据 |
|---|---|
| **TS-27** | 媒体产物集合的指纹算法：**每项先做 RFC 8785 JCS 规范化字节 → UTF-8 canonical bytes → SHA-256**；集合按 **`kind` + `stable_id` 固定排序**后逐项取哈希，再对**有序清单**取 `media_fingerprints_root_hash`（root SHA-256）。**与 TS-24 的四类逐项独立指纹并存、非互斥**（逐项指纹用于失效归因，集合 root 用于整体一致性校验，两者同时落盘）。**跨语言复算必须一致**（Node / TypeScript / Python 各算一遍要逐字节相等）。**不自定义键序、不自定义浮点规则**。**措辞上不许叫「Merkle」或「不可篡改」** —— 它是排序后的确定性哈希摘要，不是 Merkle 树，也防不住有写权限的人重算 |
| **TS-28** | 会话存储：`session` 存**服务端 SQLite 投影库**，**cookie 里只有随机 session id**（不含身份、不含权限）。`step-up token` 同样**服务端存储**，`single-use` + `TTL` + `audit` |
| **TS-29** | **session 库与业务投影库是两个独立 SQLite 文件**：各自的 WAL、备份、清理、健康检查。**session 故障不得影响 IR / manifest 或业务投影**（构造 session 库损坏，断言业务读取仍正常） |
| **TS-30** | 对象级 ACL 按**职责 + 案件**最小权限：<br>· **提交人** —— 仅自己的案件<br>· **审核员 / 法务 / 签发人** —— 仅 `tenant + product_line` scope 内、且**被分派或待处理**的案件<br>· **项目统筹** —— 可见 scope 内全部<br>· **IT** —— 默认只见账号与运行元数据，**不见内容** |
| **TS-31** | 队列领取：审核员 / 法务可在 `tenant + product_line + role` 范围内看到并领取**未分配**案件。**领取必须是原子操作并形成独占 `assignment`** —— 其他人不可再操作该案件。反向对照：两个人并发领取同一案件，**必须只有一个人成功**，另一个收到明确失败（不是静默成功）|
| **TS-32** | **Session 库不备份。** 故障或恢复后**全部 session 与 step-up token 一律失效并重登** —— 不尝试恢复会话，因为一个被恢复的会话无法证明它在故障期间没被用过。**撤销审计写独立长期审计账本**（不随 session 库一起丢）|
| **TS-33** | **领取后空闲 30 分钟自动过期**，释放回角色队列。释放前**先保存草稿**。原审核员与新领取人**仅工作台通知**（同 TS-22，不发飞书）。实现上需要**心跳 / lease + 乐观锁** —— 不能靠「查一下有没有被领」再写，那是竞态 |


> ★ **TS-22 与 RL-13 不能混**：RL-13 说的是**已发布内容的强制下线任务**，
> 那个要每日提醒 + 状态变化通知（因为它是对外动作，漏了会出事）。
> TS-22 说的是**重审通知**，只在工作台内 —— 两者范围不同，别互相套用。
>
> ★ **TS-22 那句「不许声称已通知到人」是本条的价值所在。**
> 系统能证明的只有「投递了、读了」，证明不了「这个人知道了并处理了」。
> 把前者说成后者，就是本项目台账第 5 行（未测报绿）的同一个形状。

> ★ **TS-18 / TS-19 的「过门后才锁版本」是这两条的全部意义。** 先锁版本再测评，
> 等于把「候选」写成了「已选」—— 那正是本项目台账第 45 行（候选项目冒充成功案例）的形状。
> 注意：**PaddleOCR / Tesseract / faster-whisper / Whisper 现在都是候选，不是已选**。在四项读数出来之前，
> 任何文档都不许把它们写成「我们用的 OCR」。

> 这三条**不是判据，是前置约束** —— 它们没有「什么情况下会红」，
> 因为它们是「还没开始做」。写成判据会让验收表出现无法执行的条目。

## §6 · 评估：四个可测数（**每个都要成合同**）

**v1 只给了名字，不能做看板也不能验收。以下每一项都必须带齐七要素。**

### 6.1 指标定义

#### ① 高危（L4/L5）召回率

| 要素 | 值 |
|---|---|
| 分子 | 系统判为 `L4/L5`（`confirmed`）且人工确认也是 `L4/L5` 的条数 |
| 分母 | 人工确认为 `L4/L5` 的**全部**条数（含系统漏掉的）|
| 窗口 | 每个评估周期（默认自然月）|
| 抽样层 | **全部非 `L4/L5` 标签**：PASS / 待自决 / REVIEW / 未审查 **四层分别抽样**。★ 上一版只抽 PASS，漏掉了「系统判 REVIEW 但其实是 L4/L5」这一类 —— **漏报不只藏在「说没问题」里，也藏在「说需要人看」里** |
| 最低 n | 分母 < 30 时**显示「样本不足」**，不出比率 |
| 未测时 | 显示 **`未测`**，不是 0 |
| 目标线 | **待基线测量后设定**（第一次测量即基线，之后看趋势）|

#### ② 高危（L4/L5）误判率

| 要素 | 值 |
|---|---|
| 分子 | 系统判为 `L4/L5`、人工复核后**撤销**的条数。**未复核完的条目不计入分子也不计入分母**，单独报「已复核覆盖率」 |
| 分母 | 系统判为 `L4/L5` 的**全部**条数 |
| 窗口 | 同上 |
| 抽样层 | **BLOCK 层全量复核**。**未完成全量复核时，该指标显示「未测」+ 已复核占比**，不许用部分样本算出比率冒充全量 |
| 最低 n | **必须带 n 显示**（v1 已要求，保留）|
| 未测时 | `未测` |
| 目标线 | **待基线测量后设定**（第一次测量即基线，之后看趋势）|

#### ③ 未覆盖占比

| 要素 | 值 |
|---|---|

### 6.2 金标准

在线回流（人工复核 + 抽检）为主，**加一个最小冻结回归集**。

> ✅ **已定（委托方 2026-10-17）：50–100 条，规则变更必跑。**

**冻结回归集规格：**

| 项 | 值 |
|---|---|
| **规模** | 首次建 **50–100 条** |
| **必含** | 已知陷阱负样本：`Best Seller` / `100% cotton` / `最新` / `first-time mom`（误杀高发区） |

**它是变更门，不是评测脚本：**

| | 评测脚本 | 变更门 |
|---|---|---|
| 谁跑 | 想起来才跑 | **规则 PR 必须跑，不跑不许合** |
| 输出 | 一堆数 | **前后对比**（这次变好还是变坏）|
| 不跑会怎样 | 没人知道 | **变更被挡住** |

## §9 · 修订纪律

1. **改判据 = 改合同**，要说清改了什么、为什么、影响哪条验收。
2. **新增一条判据，必须同时能回答「什么情况下它会红」** —— 答不出来不许写进来。
3. **本文件不写「现状是什么」** —— 现状在 `PMO/`。唯一例外是**问题背景**，且必须标明「这是背景不是规格」。
4. **未定项必须留在 §7**，不许为了行文顺畅把它写成「已定」。
5. **改状态**（DRAFT → RATIFIED）需要 Owner + 审批人双签，并登记基线指纹。

## 未来附录 · 非阶段一 · 不进验收：回边（Loop）规格设想

> ⚠️ **地位声明**：本附录记录的是未来阶段「若开启回边（loop）」时的设计设想，**不属于第一阶段范围，不进入任何现行验收判据与测试**。第一阶段工作流（§2、§3.3.7）严格为**五步单向 pipeline、无回边**。
>
> 1. **为什么从正文移出**：2026-10-17 曾写「第一阶段不做回边，只留规格」，但「回边规格」当时并未写出完整定义（曾留下一处指向 §3.2 的悬空指针）；将其留在正文容易被误读为「规格已就绪」或「验收需预留轮次字段」。
> 2. **未来若要启用回边，必须先补齐的四项独立规格**（补齐并经评审签署前不得接线）：
>    - **进入与退出条件**：哪些「证据不足 / 补抽帧 / 补检索」情形允许触发同一次运行内的回边，哪些必须直接降级转人（§3.3.6）；
>    - **轮次上限（max rounds）**：单次运行的最大重入次数，防止无限循环与算力失控；
>    - **收敛判据（convergence）**：连续两轮 findings / 证据集合差集为空时的停止规则（对应 §3.3.7 第 6 条「无进展」预留项）；
>    - **震荡检测（oscillation）**：前后轮次结论在两态之间来回翻转时的强制熔断与转人规则。
> 3. **与第一阶段「人工/失效触发新 run」的区分**：第一阶段中，人工确认/驳回 finding 或五类失效输入变化所触发的全量重审，是**新的独立运行（新 `run_id`、新 `ReviewIR` 版本、新报告）**，旧记录原样保留不可改 —— 那是跨运行的版本演进，**不是**本附录所说的单次运行内回边。
