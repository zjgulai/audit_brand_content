# 内容审查 Agent · 产品 Playbook v1

> **这份文件是什么**：产品的**终局规格**。它不描述现状、不描述实现、不描述仓库里有什么。
> 它只回答一个问题 —— **做完之后，这个产品是什么样子、凭什么说它做完了。**
>
> **它怎么用**：从它倒推技术方案 → 前后端开发 → 测试 → 验收。
> 任何一条技术决策，如果和这份文件冲突，**以这份文件为准**；
> 任何一条验收标准，如果不能指回这里的某个判据，**它就不该进验收表**。
>
> **它不是什么**：不是项目周报、不是代码说明、不是历史审计记录。
> 这些内容在 `PMO/` 与 `research/` 下，与本文件无关。

---

## §0 · 一页纸

**任意形态的营销内容进去，可执行的审查结论 + 可溯源的证据 + 可统计的读数出来。**

用户实际说的一句话：*「把图片、链接、视频、文本交给它，它解析成可判的东西，用 skill + 规则库 + 知识库审一遍，按 P0–Pn 判状态，按模板出结论卡片或报告。」*

这份 Playbook 就是把这句口语，变成**可开发、可测试、可验收**的东西。

### 0.1 三层结构（先看这个，再看细节）

```
第 1 层  目标态      产品做完是什么样            §1
第 2 层  工作流      内容从进来到出去经过什么      §2
第 3 层  契约        每一段的输入输出与判据        §3
```

### 0.2 一条贯穿全篇的纪律

> **凡写「必须」的，都要能指出「什么情况下它会红」。**
> 指不出来的，是愿望，不是规格。

本文件每条要求后面都带一个**判据编号**（如 `L2-3`）。
验收时逐条跑，跑不过就是没做完 —— **没有「基本完成」这一档**。

## §1 · 目标态

### 1.1 五个必须同时成立的条件

这五条是「做完」的定义。**缺一条就是没做完**，不存在「主要功能已完成」。

| # | 条件 | 判据（怎么知道它成立了） |
|---|---|---|
| **甲** | **进得来** | 文本 / 图片 / 视频 / 链接 / brief **五种形态**都能进链路，每种都带内容指纹 |
| **乙** | **判得准** | 每个结论都能指出**哪条规则**、**哪条外部依据**、**在原文哪个位置** |
| **丙** | **处置得住** | 每条内容都有明确的下一步负责人，且**转出去之后有回音或超时升级** |
| **丁** | **说得清** | 群里一句话 + 报告详情；**未审的部分明确说未审，不冒充已审** |
| **戊** | **改得动** | 规则改了之后，**能回答「这次是变好还是变坏」** |

### 1.2 三条不可让渡的原则

#### 原则一：审查标签 ≠ 发布放行

这两件事必须分开，**但分开的方式不是限制机器能说什么，而是限制「说了」意味着什么。**

| | 审查标签 | 发布放行 |
|---|---|---|
| **答什么** | 这次审查得出了什么 | 这条内容能不能上线 |
| **谁签发** | **机器可以下任何一档** | **永远由人做最后放行** |
| **载体** | 报告上的一个标签 | 实际发布 |
| **效力** | 对内容的判断 | 对发布的许可 |

**机器可以下全部五档：`BLOCK` / `REVIEW` / `未审查` / `待自决` / `PASS`。**
**但这五档没有一档等于放行。** `PASS` 的含义是「这次审查没有发现问题」，
**不是**「可以上线」—— 后者只能由人给出。

> **这条的判据（可机验）**：
> 系统里**不存在**任何一条从「审查标签」直接连到「发布状态」的代码路径。
> 机器产出 `PASS` 之后，内容仍然停在「待放行」，必须有人签一次才动。

> **为什么这样分**：把限制加在「机器能说什么」上，会让机器在证据充分时也不敢说话，
> 把本该由它承担的判断推给人；而把限制加在「说了算不算数」上，
> **机器的判断力可以放开，放行权仍然锁在人手里**。
> 前者是省事，后者才是可控。

> ★ **2026-10-17 更正**：本节早先写的是「机器唯一能自行下的是 BLOCK」，
> **那个写法是错的** —— 它把「判断」和「放行」压成了一件事，用限制判断来达成限制放行。
> 委托方原话：「**机器人可以下任何状态，但最终都会由人做最后的放行**」。

#### 原则二：没命中 ≠ 安全，而且「没命中」还要再拆一次

一条内容没有命中任何规则，**结论不是 PASS**。但「没命中」本身有两种，
必须靠**覆盖证明**区分：

| | 含义 | 处置 |
|---|---|---|
| **`UNASSESSED`** | **没能力评估** —— 这个模态 / 这个规则域根本没跑 | 强制人工 + 进空白清单 |
| **`CLEAN-CANDIDATE`** | **已评估且干净** —— 确实按某规则版本、对某些模态跑过了 | 可进业务自审，**但仍不自动发布** |

> **为什么不能省**：没有覆盖证明，**「审过了没问题」和「压根没审」在系统里长得一模一样** ——
> 这是整个产品最安静的失效模式。

#### 原则三：判定表唯一；严重度给下限，数量只影响呈现

> **这一条是对最初设想的修正。** 原设想是「按 P0–Pn 的个数统计判断状态」。
> 实测证明这条会出事：一条内容有 1 个 P0（视频里宝宝未坐安全座椅）+ 2 个 P3（措辞建议），
> 共 3 个问题 → 走汇总模式 → **群里收到的是一句「合规类 1 个、措辞类 2 个」，
> 最严重的那条被数量吞掉了。**

**正确形状，五条一起成立：**

| # | 规则 | 作用 |
|---|---|---|
| 1 | **唯一判定表决定状态** | 只有一处能定 |
| 2 | **最高严重度给「状态下限」** | 有 P0 就是 BLOCK 档，**数量再少也不降级** |
| 3 | **任何数量不得降级** | 数量**只能升级或不变** |
| 4 | **特定共现可升级** | 组合规则（如「场景名词 + 消除性动词 = 功效承诺」）**有权上调** |
| 5 | **普通数量只影响呈现** | 决定「群里出几句、详情放报告」，**不决定状态** |

> 第 4 条不能省。组合规则是抓新型表达的主要手段；
> 若写成「状态由最高严重度决定」，它在文字上就被否掉了。
> 正确措辞：**状态下限 = 最高严重度；共现可以把它抬得更高。**

## §2 · 工作流：五段

内容从进来到出去，经过五段。每段都有**输入契约 / 输出契约 / 判据**。

```
① 归一化（进）  任意形态 → 可判的内容单元
② 判定（判）    内容单元 → 命中与证据
③ 处置（置）    命中与证据 → 谁在什么时限内做什么
④ 输出（出）    结论 → 群里一句话 + 报告
⑤ 评估（证）    运行数据 → 四个可测数
```

---

## §3 · 每段的契约与判据

### ① 归一化（进）

**输入**：文本 · 飞书文档链接 · 落地页 URL · 图片 · 视频 · brief · 广告记录
**输出**：**内容单元** —— 一段可判正文 + 双指纹 + 覆盖声明 + 来路

| 项 | 要求 |
|---|---|
| **双指纹** | `raw_sha256`（看的是哪份原件）+ `text_sha256`（重跑能不能得到一样的数）。**两个都要**：只留合成指纹，就再也观测不到「原件变了但正文没变」 |
| **覆盖声明** | 每种形态**必须显式声明** `covers` / `does_not_cover`，**刻意不设默认值** —— 默认值会让「只做了 OCR」看起来像「视频已审」 |
| **失败必须可读** | 每个单元带 `parse_status`（`ok` / `partial` / `failed`），`failed` 必须带 `failure_kind`：`fetch_error` / `parse_error` / `empty` / `unsupported` |

#### 判据

| # | 判据 |
|---|---|
| **L1-1** | 每个内容单元都能复算出同一个单元标识 |
| **L1-2** | 每个单元都声明了 `covers` **和** `does_not_cover`，且都不为空 |
| **L1-3** | 位置字段能**点回原片**（视频的时间码 / 图片的区域），不是自然语言 |
| **L1-4** | 同一份内容的两次解析，正文指纹**相同** |
| **L1-5** | `parse_status=failed` 的单元**不得**进入判定，只能落「未审查」 |
| **L1-6** | `parse_status=partial` 的单元**可以**进判定，但**只在其已覆盖部分上**，且**永不产出 PASS** |
| **L1-7** | `empty`（取到了没内容）与 `failed`（没取到）**必须能分别数出来** |
| **L1-8** | 每次运行的报告里，四种 `failure_kind` 的**条数必须出现**（哪怕全是 0）|

> **L1-7 与 L1-8 是防「静默归零」的两条。**
> 一个从不出现的字段和一个恒为 0 的字段，读起来一样；
> 只有强制出现在报告里，才能区分「没有失败」与「这一项没人统计」。

> ⚠️ **L1-6 的边界必须写死**：不是「有缺就不许用」，而是「**用了就必须标明缺哪儿**」。
> 一个更早的错误设计是「任何 `parse_status != ok` 都 `has_text = false`」——
> 那等于让 `partial` 的已解析文本**一个字都不进审查**，与「覆盖证明」的设计整个冲突。

### ② 判定（判）

**双档，互不越界：**

| | 深档（确定性） | 浅档（语义） |
|---|---|---|
| **管什么** | 文本主张 | 画面语义 |
| **实现** | 规则引擎 | 多模态模型 |
| **输出** | 命中规则 + 位置 + 证据 | 候选 + 画面位置 + 依据或「未覆盖」 |
| **可否终结** | ✅ **仅拦截方向** | ❌ **只能出候选，永远转人工** |

#### ②-1 三个部件的职责（**这是本节的核心**）

| 部件 | **不是**什么 | **是**什么 |
|---|---|---|
| **skill** | ❌ 不是可加载的运行单元 | ✅ **一份操作规程** —— 任何 agent 按这一页就能调起一次审查 |
| **规则库** | ❌ 不是召回器 | ✅ **确定性判定 + 落层**：决定命中，决定落哪一层 |
| **知识库** | ❌ 不是全文检索 | ✅ **证据源**：产出「违反了哪一条具体条款」 |

> **skill 的形态已定**：**规程 + 唯一编排器 + 执行回执**（委托方 2026-10-17）。
> - **规程**：每份 skill 是给人和 agent 读的书面规程
> - **唯一编排器**：只有一个入口选 skill、排顺序 —— 两处都能定，就会出现「按 A 想、按 B 发」
> - **执行回执**：每次执行落一张，记「用了哪个 skill / 哪条规则 / 命中什么」——
>   这是「用对了没有」唯一能被验的地方

#### ②-2 审计循环

```
轮 0  预处理    定档 + 产出「本轮要跑哪些控制点」的清单  ← 这就是「覆盖证明」
轮 1  确定性判定  规则库出 hits[]（带控制点 + 位置 + 逐字片段）
轮 2  证据补全   按控制点查条款位置 + 出处链接
轮 3  语义判定   多模态出候选（**不是结论**）
轮 4  合并定状态  唯一判定表出状态 + 路由 + 覆盖证明
```

**第一阶段实现 pipeline，预留一次回边**（委托方 2026-10-17 定）。

**停机条件六条**：

| # | 条件 | 第一阶段启用？ |
|---|---|---|
| 1 | 正常完成（清单跑完） | ✅ 启用 |
| 2 | 提前停（P0-字面且满足机结三条件） | ✅ 启用 |
| 3 | 转人工 | ✅ 启用 |
| 4 | 工具失败（落 `failure_kind`，不得静默跳过） | ✅ 启用 |
| 5 | 超时升级 | ✅ 启用 |
| 6 | 无进展（连续两轮无新命中） | ⚠️ **预留** —— pipeline 无回边时它不成立 |

> ★ **第 6 条必须标「预留」，不能算「已落」。**
> 一个只在设计里成立、实现中不触发的条件，写进验收表会让验收变成走过场。

> ★ **第 4 条是最要紧的一条**：
> 一条内容因为模型超时而没被审，**今天它既不会报错，也不会进任何队列** —— 它会安静地不出现。

#### ②-3 三条合并规则

1. 深档命中优先，浅档不得推翻
2. 浅档产出**是证据不是结论**（这本来就是「人工复核」层的定义）
3. **两档都没命中的内容，必须再分一次** —— `UNASSESSED` / `CLEAN-CANDIDATE`（见原则二）

#### 判据

| # | 判据 |
|---|---|
| **L2-1** | 每个结论的状态 ≡ 判定表算出的值（**唯一来源**）|
| **L2-2** | 「没命中」必须落成 `UNASSESSED` 或 `CLEAN-CANDIDATE` 之一，**不许合成一个空结论** |
| **L2-3** | 每个结论都带**覆盖证明**，至少四项：评过的模态 / 规则版本 / 适用控制点 / 未跑的为什么 |
| **L2-4** | P0 分**字面类**（正则可判）与**语义类**（强制走模型）—— 「医疗宣称」这类靠正则盖不住 |
| **L2-5** | 每个命中都能指出规则 + 外部依据 + 原文位置 |
| **L2-6** | 浅档产出**不得**单独构成结论，必须与深档结果合并后才出状态 |
| **L2-7** | 每次执行落一张**skill 回执**，可回答「这一轮用了哪些 skill、命中了什么」 |

> **L2-1 为什么重要**：状态如果散在三处（流程图 / 置信度分档 / 指标），
> 早晚会出现「按 A 算出 BLOCK、按 B 显示合规」。

> **关于「置信度」**：**不采用数值置信度。**
> 它在文档里没有定义、没有校准，却被写进准确率指标。
> 替代它的是**三值证据状态**：`命中确定` / `疑似需人看` / `未覆盖`。

### ③ 处置（置）

**五层处置，每层责任不同：**

| 层 | 名字 | 谁接 | 这一层由谁结 |
|---|---|---|---|
| DP0 | 不可判（无文案格式）| 投放侧 | 投放侧 |
| DP1 | 业务自审 | 文案提交人 | 文案提交人 |
| DP2 | 工具预审 | 机器 | 机器可下判断（**但不放行**）|
| DP3 | 内容审核员复核 | 内容审核员 | 内容审核员 |
| DP4 | 法务终审 | 法务 | 法务 |

> ★ **「这一层由谁结」与「能不能放行」是两个字段，不是一个。**
> DP1 的 `can_finalize=true` 指的是「**这一层的处置由这一层结**」（`who=文案提交人`），
> **不是**「机器能结」。而「放行」在**任何一层都不由机器给**。

**对外五标签（机器都可以下，没有一档等于放行）：**

| 对外标签 | 含义 | 机器可否下 | 是否等于放行 |
|---|---|---|---|
| **BLOCK** | 有问题，必须拦 | ✅ | ❌ |
| **REVIEW** | 需要人看 | ✅ | ❌ |
| **未审查** | 没能力评（模态/规则域缺失）| ✅ | ❌ |
| **待自决** | 判断权交回提交人 | ✅ | ❌ |
| **PASS** | 这次审查没发现问题 | ✅ | ❌ **（不放行，待人工签）** |

> **为什么必须是五个而不是三个**：DP0 落不进三态里的任何一态。
> **一条内容没有文本可判，不等于它合规** —— 把它显示成「合规」，
> 就是把「不知道」记成了「没问题」。
>
> （依据：存量 291 条里 59 条文本为空，其中 **55 条**被渲染成 `合规·绿`、
> 2 条灰、2 条空 —— **不是全部 59 条都落绿**。读数出处
> `research/governance/01-内部证据-规则表现状审计.md:177`。★ 这段是**问题背景**，不是本规格的现状描述。）

> ★ **标签数（5）≠ 处置层数（5）** —— 两者不一一对应。
> `PASS` 与 `BLOCK` **同落 DP2**，`REVIEW` 跨 DP3/DP4。

#### 判据

| # | 判据 |
|---|---|
| **L3-1** | 每条内容都有明确的下一层负责人（**路由表**：依据来源 → 复核人）|
| **L3-2** | 转出去之后，**没回音会升级**（三级：转出 → 超时 → 升级项目统筹）|
| **L3-3** | 被拦的人**有地方说话**（申诉通道 + 案件号即回执号）|
| **L3-4** | 回执里不许出现「通过 / 已通过 / 无需处理 / 审批完成」 |
| **L3-5** | **机器可下全部五档，但不存在任何一条从「审查标签」直连「发布状态」的路径**；五档全部停在「待放行」 |

### ④ 输出（出）

**群里只出一句话结论 + 报告链接**，所有细节进报告。

**两个产物：**
- **报告**（给人看，渲染视图）
- **结构化记录**（机器读，**唯一真相**）—— 链接坏了还能重建

#### 判据

| # | 判据 |
|---|---|
| **L4-1** | 群里不刷屏，且 **P0 不可能被数量阈值吞掉** |
| **L4-2** | 报告链接有效期 **≥** 记录保存期 |
| **L4-3** | 输出无 AI 味（**七条机械判据，可机验**：模板腔 / 结论尾巴 / 填充语 / 堆叠对冲 / 三段式排比 / 连接词堆叠 / 内部实现泄漏）|
| **L4-4** | 卡片被拒时**降级为纯文本**，不是消失 |
| **L4-5** | 超限内容**搬走、不丢**（搬是搬，砍是砍）|
| **L4-6** | 群里**永不**出现卡片标记的原始字符 |

> **L4-2 的现状矛盾**：报告 30 天 vs 记录 1 年 —— 一年后复核时报告已打不开。

### ⑤ 评估（证）

**四个可测数**（替代「整体准确率 ≥90%」）：

| # | 读数 | 为什么是它 |
|---|---|---|
| ① | **P0 召回** | 唯一防「漏」的指标 |
| ② | **P0 误判率**（**必须带样本量 n**）| 唯一防「误拦」的指标 |
| ③ | **未覆盖占比** | **唯一会随系统成长而变化的指标** —— 规则库空着时接近 100%，建起来后应下降 |
| ④ | **人工推翻率** | 所有人工结论里推翻机器的比例；**申诉胜与败都进分母** |

> **为什么淘汰「整体准确率 ≥90%」**：若 PASS 占九成流量，
> **一个永远输出 PASS 的系统就是 90%**。同一个数，两种完全相反的现实。

**金标准来源**：在线回流（人工复核 + 抽检）为主，**加一个最小冻结回归集**。
> 冻结回归集的作用：**规则改了之后，能在发布前回答「这次是变好还是变坏」**。
> 规模几十条即可，**但必须含已知陷阱负样本**（`Best Seller` / `100% cotton` / `最新` / `first-time mom`）—— 这些是误杀高发区。

#### 判据

| # | 判据 |
|---|---|
| **L5-1** | 四个数都有来源，且**未测时显示未测**（不是 0，不是空白）|
| **L5-2** | 抽检**分层**：PASS 层抽漏报 + BLOCK 层抽误报 |
| **L5-3** | 冻结回归集存在，且**规则变更时必跑**（是变更门，不是评测脚本）|

## §4 · 两个必须钉死的输入机制

### 4.1 提交单：三个字段必填

**问题**：两条入口对「内容阶段」的处理不一致 —— 群里靠模型**猜**，多维表靠人**填**。
猜错的后果是分叉的：brief 若被判成 final，就会走签核路由 —— **而 brief 根本没有签核负责人**。

**做法**：一次提交 = 一张提交单。`内容阶段 / 品线 / 渠道` **三个必填**，
机器**只补不强猜**；没填就落「未覆盖」走人工，**不默认成 final**。

### 4.2 分类体系：控制族（主轴）+ 三轴（属性）+ 双键（标识）

**用户的质疑**：*「审查的分类其实就是内容标签的分类，这个分类不对。」*

这个判断成立。现行的八分类不是标签选错，是**它悬空**：
有下游输出字段，**但没有上游规则映射** —— 没有任何东西能断言「每个取值都在取值域内」。

**正确的结构是三层，各答一个问题：**

```
第 1 层  审查控制族 → 控制点    答「这是一次什么审查动作」   ← 主轴，决定路由与判据
第 2 层  三轴（正交属性）        答「它是什么、谁说了算、伤到什么」  ← 不决定审查动作
第 3 层  双键（机器标识）        答「违反了哪条、凭哪条依据」   ← 可断言
```

#### 第一层：七个审查控制族（主轴）

| 控制族 | 答什么 | 子类数 |
|---|---|---:|
| **宣称控制** | 这句话能不能说 | 15 |
| **事实控制** | 这件事是不是真的 | 23 |
| **披露控制** | 该说的说了没有 | 6 |
| **场景控制** | 画面这样做安不安全 | 2 |
| **权利控制** | 能不能用这个人/这张脸 | 2 |
| **渠道控制** | 这个平台允许吗 | 6 |
| **品牌控制** | 这个调性对不对 | 4 |

> **为什么这七个是「审查动作」而不是「内容标签」**：
> 「宣称控制」的动作是**验实证材料**；「披露控制」是**查有没有披露**；
> 「权利控制」是**查授权文件**。**每一个都有不同的判据和不同的复核人** ——
> 而「车内场景」「睡眠场景」没有：它们只告诉你内容在讲什么。

**每个控制族必须有二级（控制点），二级才是规则挂载的位置。**

#### 第二层：三轴（正交属性）

| 轴 | 答什么 | 取值域 | 谁维护 |
|---|---|---|---|
| `scene_domain` | 在说什么 | 车内/睡眠/喂养/洗护/出行/居家/玩具/功效/肖像 | 产品 |
| `authority_source` | 谁说了算 | 联邦法规 / 州法 / 平台政策 / 英国对照 / 品牌内规 | 法务 |
| `consequence` | 伤到什么 | 消费者安全 / 品牌信任 / 经营风险 / 建议级 | 业务 |

> ⚠️ **三轴不是分类体系**。`scene_domain` 本质仍是内容标签 —— 它答「在说什么」，
> 不答「审查动作是什么」。用户质疑的正是这件事，不能用换名字的方式绕过去。

#### 第三层：双键（机器标识）

```
control_code      违反了哪个控制点
authority_ref     凭哪条依据
```

**三条轴都要有「未知桶」，且必须显式登记：**

| 轴 | 未知桶 | 后果 |
|---|---|---|
| 控制族 | `未归类` | 强制转人工 |
| `scene_domain` | `其他` | 同上 |
| `authority_source` | `依据待定` | 同上 |
| `consequence` | `后果未知` | 同上 |

> **未知桶不是垃圾桶，它是有意义的信号** —— 未知桶一多，说明规则库或分类体系该补了。
> 关键在于：**它必须能被数出来**。

### 4.3 未覆盖的回退路径

```
规则库空着        → 未覆盖 → 人工
规则只覆盖中文    → 英文内容 → 未覆盖 → 人工
新场景 / 新平台政策 → 未覆盖 → 人工
```

**这三条路径必须长得和「审过了没问题」不一样。**

## §7 · 这份文件的修订纪律
