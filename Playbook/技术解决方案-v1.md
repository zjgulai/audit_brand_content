## §1bis · 两份内部契约（2026-10-18 补：S-1 与 S-2 的落点）

> 这两份契约是**技术方案内部的数据合同**，不改变 Playbook 里任何产品可见的字段
> （Finding schema 见 Playbook §3.3.4，一个字段都没动）。它们存在的唯一原因，
> 是 §8 的两条阻断门要求「生产者写什么、消费者收什么」必须写死，
> 否则依赖成环与「报告要数 unsupported 却没有源」都只能靠实现者当场猜。

### §1bis.1 DraftFinding → ValidatedFinding（对应 **S-1**）

**问题**：`rule_judge` 写出带 `confirmed` 的 finding，但 `finding_store` 的准入
（L2-5 三要素合取）要求 `authority_state`，而 `authority_state` 只能由 `evidence_sync`
算出来，`evidence_sync` 又声明「不产 finding」—— **三者互相等，谁都不动**。

**三段式**（每一段只有一个写者，缺一段或跳一段都算违约）：

| 段 | 谁写 | 内容 | 谁读 |
|---|---|---|---|
| ① `DraftFinding` | `rule_judge` / `semantic_judge` | Playbook §3.3.4 的全部字段，**但 `authority_state` / `rule_conflict` 必须缺省**（不许填占位值） | `evidence_sync` |
| ② enrich | `evidence_sync` | 在**判定步内**作为具名子阶段：算 `authority_state`、`rule_conflict`，钉住 `rule_snapshot` / `kb_snapshot` | — |
| ③ `ValidatedFinding` | `evidence_sync` 落盘 | ① 的全部字段 + `authority_state` + `rule_conflict` + 两个快照 | `finding_store`（只收这个）→ `decision_table`（只读这个） |

**三条不变量**（每条都要有反向对照，见 §1bis.3）：

- **DF-1**：`DraftFinding` 直接进 `finding_store` 必须被拒 —— 判据是
  「`authority_state` 字段**不存在**」，而不是「值等于 `untested`」。
  后者是一个合法状态（依据未同步到），前者是「还没算过」。**两者长得像，含义相反。**
- **DF-2**：`ValidatedFinding` 的 `status=confirmed` 而 `authority_state` 缺失 → 拒收。
  `candidate` / `rejected` / `superseded` 不要求 `authority_state`（它们不进判定链）。
- **DF-3**：`decision_table` 的输入里出现 `DraftFinding` → 违约，不许降级处理。

**为什么不是「让 evidence_sync 产 finding」**：那会让 finding 有两个生产者，
`derived_from` 的来源就不再唯一，§3.3.4.2 的 append-only 无法维护。
evidence_sync 写的是**同一个 finding 的后续版本**，不是新 finding。

### §1bis.2 Attempt：unsupported 计数的唯一来源（对应 **S-2**）

**问题**：`submission_router` 对 `unsupported` 直接拒绝且不产 IR，
但 Playbook **L1-7 / L1-8** 要求报告里出现四种 `failure_kind` 的条数（哪怕全是 0），
验收第 9 项还构造了 `unsupported=1` 断言计数可见 —— **没有东西记过它，数不出来。**

**Attempt 契约**（`contract_suite` 定义 `attempt-v1`，`submission_router` 是唯一写者）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `attempt_id` | string | ✅ | 一次入口提交的稳定 id |
| `submission_id` | string | ✅ | 同一次用户提交可含多次 attempt（重试） |
| `entered_at` | timestamp | ✅ | 进入入口的时刻 |
| `outcome` | enum | ✅ | `accepted` / `rejected_unsupported` / `failed` |
| `failure_kind` | enum? | — | `accepted` 时缺省；否则必填，取值与 Playbook L1-7 的四值一致 |
| `reason` | string | ✅ | 人或机器可读的原因；**不许写「其他」「未知错误」这类无信息词** |
| `ir_id` | string? | — | `accepted` 时必填；其余必须不存在 |
| `receipt_id` | string? | — | 走完流程才有；`rejected_unsupported` 必须不存在 |

**恒等式**（这是 L1-7 能被验收的唯一依据）：

```
Σ attempt(outcome=accepted) + Σ attempt(rejected_unsupported) + Σ attempt(failed)
    == 入口提交总数
Σ attempt(failure_kind=k) for k in 四种   ==  L1-7 报告里那一行
```

**为什么 `run_record` 顶不了这个位置**：它只覆盖 **spawn 之后**的 worker attempt。
`unsupported` 死在 `submission_router`，**从来没进过 worker**，所以 run_record 里
一条都不会有 —— 而那正是最需要计数的一类（「我们根本没能力审」）。

> 一条方法论上的备注（AGENTS.md §2.4.1 第 4 行）：**「计数为 0」和「没有计数源」
> 在报告上必须长得不一样。** Attempt 读不出时，L1-7 那一行显示「未测」，
> 不许显示 0。执行点见 §1bis.3 的 R-3。

### §1bis.2b 落盘与身份语义（**与 Playbook §3.3.4.2 逐字对齐**）

> ⚠️ **本节第一版写错过，留在这里说明为什么改。**
> 第一版写「后续状态变更沿用同一个 `finding_id`，`(finding_id, revision)` 才是行标识」——
> 那是**与 Playbook 相反的**。§3.3.4.2 原文：「所有实质状态变化（候选→确认、确认→撤销）
> **一律新建一条**，用 `derived_from` 指回上一条」；验收 16 明确断言「两条相同 `finding_id`
> 必须拒绝」。我当时凭「append-only 应该是一个对象多个版本」这个**通用直觉**写下去，
> 而没回头读那 30 行表 —— 这是本项目最反复的形状：**说得比读过的多。**

**正确语义（三层，别混）：**

| 阶段 | 在盘上吗 | `finding_id` |
|---|---|---|
| `DraftFinding` | **不在**。只在判定步的内存里（judge → evidence_sync），进程崩溃即丢，**从未分配 id** | **无** |
| `ValidatedFinding` | **首次落盘**，这也是**第一次**分配 `finding_id` | **新分配** |
| 后续实质状态变化（候选→确认、确认→撤销、驳回） | **新建一条**，**新分配 `finding_id`**，`derived_from = <旧 id>`；旧条**只改一个字段**：`status → superseded`，`produced_by` 保持原值 | **新的** |

**「不可变」的准确含义**（§3.3.4.2 原文）：一条 finding 的**判断内容**永不改
（`control_code`/`severity`/`location`/`quote`/`detected_by`/`produced_by`/`authority_ref`）；
唯一允许的变化是 `status → superseded`（标记它被取代，不是改写它的判断）。

**所以 Draft → Validated 与 append-only 不冲突**：
Draft **从来没进过 store**，`ValidatedFinding` 是**这个 finding 的第一行**。
「新建条目」这件事只发生在**后续状态变化**上，而那已经是 ValidatedFinding 之后的事了。

**三条反向对照**（验收 16 / 23 / 26 的口径，逐条对齐）：

| # | 断言 | 反向对照 |
|---|---|---|
| **ID-1** | 两条 finding 的 `finding_id` 相同 → **拒绝**（验收 16）| 喂一对同 id 的两条 → 必须红 |
| **ID-2** | 旧条目在状态变化后，除 `status` 外**一个字段都不许变**，且 `produced_by` 保持原值（验收 26）| 改一个 `severity` → 必须红 |
| **ID-3** | 新条目必须存在，且 `derived_from` 指回旧 id（验收 23/26）| `derived_from` 悬空或指向自己 → 必须红 |
| **ID-4** | `DraftFinding` 出现在 store 的任何一次写入里 → 拒绝（**它本该从未落盘**）| 喂一条 Draft → 必须红 |

## §1ter · 八条架构/持久化门的设计裁定（2026-10-18）

> **这一节回答 §8 里 8 条「可机械修」的门。** 它给出的是**设计裁定**，不是实现 ——

### §1ter.1 A-1：`report_renderer` 不许读活数据

**裁定**：渲染器的**唯一输入**是 `RenderSnapshot`（`render-snapshot-v1`），由
`orchestrator` 在 output 步**冻结**后交给它。`RenderSnapshot` 内含：

```
render_snapshot:
  ir_id, ir_version            # 冻结的 ReviewIR 标识
  findings[]                   # 冻结副本（只读）
  decision{state, external_label, layer, obligations, max_sev}
  coverage{missing|partial|full, 四项证明}
  metrics_snapshot{...}        # 渲染那一刻的四指标读数（含 n / 未测标记）
  control_points_version
  frozen_at
```

**规则**：`report_renderer` 的函数签名里**不许出现** `finding_store` / `decision_table` /
`coverage_composer` / `metrics_read_model` 的句柄或连接。它只接一个 `RenderSnapshot`。

**为什么**：R2 要求「IR 变了才生成新报告，旧报告不改不删」。若渲染器现读活数据，
同一份 IR 在不同时刻会渲出不同报告 —— **R2 恒真变成了偶然**。

**执行点**：`tools/audit/report_render.mjs` 的模块依赖白名单（只允许 `RenderSnapshot` 一种入参），
配一条反向对照：给渲染器塞一个会变的 store → 必须报「违规依赖」而不是照渲。

### §1ter.2 A-2：归一化只在一处（**normalizer**）

**裁定**：`normalizer` 是唯一实现，**在 worker 内**跑（即 orchestrator 第①步）。
`submission_router` **不做归一化**，只做四维取值校验与 unsupported 拒绝；
`job_dispatcher` 只 spawn，不碰内容。

**架构图改法**（与 §1 原图冲突，以本节为准）：

```
submission_router  ──→  job_dispatcher  ──→  orchestrator ①normalize
   (校验/拒绝)            (spawn + run_record)      ↑ normalizer 只在这里被调用
```

**为什么是「worker 内」而不是「deriving 之前」**：`parse_status` / `failure_kind` 是 IR 的字段，
必须先有 IR 才能记；而 worker 崩溃/超时也要能留下 `run_record`。归一化放 worker 内，崩溃时
`job_dispatcher` 仍能写「failed」，不会出现「既没有 IR 也没有 run_record」的空洞。

**执行点**：全仓 `normalize(` 调用点的静态断言 —— 只允许出现在 `base/orchestrator.py` 与
`base/contract.py`（后者是被调用的实现）。反向对照：在 `submission_router` 里加一处调用 → 必须红。

### §1ter.3 A-3：routing 拆表，主表守住 9 字段

**裁定**：`control_point_registry` 产出**两张**、**各自独立版本**的表：

| 表 | 内容 | 版本字段 |
|---|---|---|
| **控制点主表** | Playbook §5.3.1 的 **9 个字段**，一个不多 | `table_version` |
| **处置路由表** | `control_code → {owner, layer, due, escalation, appeal}` | `routing_version` |

**为什么不塞一起**：§5.3.1 是**交付物合同**（L6-1 逐字段断言它）。塞进 routing 之后，
`judge_type` 与 `owner` 同层，一条规则的路由变了就要升整表版本 —— 而路由是**组织信息**
（谁负责），控制点是**判定信息**（判什么）。两者的变更频率与审批人都不一样。

**两表如何对齐**：`disposition_router` 同时读两张，并断言
**routing 表的 control_code 集合 == 主表的 active 集合**（L3-1「无空洞」的唯一判据）。
任一方向缺一条 → 红。

**执行点**：`research/governance/control-points-v1.json`（9 字段）+
`research/governance/routing-v1.json`（5 字段）+ `verify_control_points.py` 的集合恒等断言。

### §1ter.4 A-4：C3 的唯一执行者

**裁定**：`rule_class_registry` 是 **C3 的唯一执行者**（此前它只「调度/统计」，没人真跑）。

它负责四件事，缺一件 C3 就不成立：

| # | 做什么 | 触发 |
|---|---|---|
| 1 | 按 `control_code` **抽样**（开启期每 N 条抽 1 条，N 由基线定） | 每次该 control_code 产出 confirmed |
| 2 | 把同一帧送**第二模型**（与主模型不同 id） | 抽样命中 |
| 3 | 统计**一致率**并公示 | 每个统计窗口（默认自然日） |
| 4 | 一致率 < 阈值 → 该 `control_code` **自动降回 candidate**，写审计行 | 统计出结果时 |

**≥30 样本是硬下限**：样本 < 30 时一致率显示「样本不足」+ n，**不许给比率、不许据此降级**
（与 L5-5 同一口径）。

**执行点**：`base/rule_class_registry.py` 的 `run_c3_sample()` + `contract_suite` 的
`c3-sample-v1`（含 `control_code / sample_n / agree_n / agreement / below_threshold / action`）。
反向对照：喂 n=29 → 必须「样本不足」；喂 agreement 低于阈值 → 必须降级并留审计行。

### §1ter.5 P-1：跨产物原子提交

> ⚠️ **本节第一版写错了一次，改了两轮才成立。**
> 第一版写序是「所有产物写 `*.tmp` → rename `manifest.json` → 删 `*.tmp`」——
> **产物从来没有被提升成最终路径**。于是提交之后只有两种可能：manifest 指向最终名而文件不存在，
> 或者指向 tmp 名而第 5 步把它们删掉。**一个连自己的例子都跑不通的设计。**
> 第二版补了 fsync 与对账，但没发现这个洞 —— 补丁加在了错误的骨架上。

**目标**：一次运行的全部产物，要么**全部可见**，要么**全不可见**，不存在中间态被读成成功。

#### 正确的写序（内容寻址 + 最后一步才可见）

```
① 每个产物写进 <root>/staging/<run_id>/<name>.tmp，逐文件 fsync(fd)
② 每个产物 rename 到它的最终**不可变**路径，逐次 fsync 所在目录：
     blobs/<sha256>            # 内容寻址，同名即同内容，天然幂等
     ir/<ir_id>.json
     receipts/<receipt_id>.json
     reports/<report_id>.md
   ★ 到这一步产物已在最终位置，但**还不能被消费** —— 没有任何东西指向它们
③ 写 <root>/manifests/<run_id>.json.tmp（entries 列**最终路径 + sha256**），fsync 文件
④ fsync manifests/ 目录
⑤ rename manifests/<run_id>.json.tmp → manifests/<run_id>.json   ← **唯一的可见提交点**
⑥ fsync manifests/ 目录
⑦ 删 staging/<run_id>/（已无用）
```

**关键点（第一版就是漏在这里）**：第②步的 rename 是**内容寻址对象的常规写入方式**
（同 sha256 的对象覆写是等价的，不违反不可变）；**可见性**由第⑤步统一决定。
所以「提交」= manifest 出现，「回滚」= 删掉第②步写的东西（或干脆留着当垃圾回收）。

#### 三条前置条件（不满足则机制不成立，启动时断言）

| # | 条件 | 断言 |
|---|---|---|
| 1 | **同一文件系统** —— `rename` 只在同 fs 内原子 | 比对 `st_dev`；不同则**拒绝启动**，不许降级成 copy |
| 2 | staging / blobs / manifests 都在仓外本地盘 `~/.dsh/audit-data` | 路径前缀断言；网络盘（NFS/SMB）不支持 rename 原子性 |
| 3 | **单写者** —— 同一 `run_id` 同时只有一个提交者 | 锁文件；两个 manifest 争同一个 rename 目标是未定义行为 |

#### 崩溃恢复（四态穷举，没有第五种被当成成功）

| 盘上状态 | 判定 | 动作 |
|---|---|---|
| manifest 存在，entries 全部存在且 sha256 对得上 | `committed` | 正常消费 |
| manifest 存在，**任一 entry 缺/哈希不符** | `orphan` | **报 ERROR**，不降级成「部分成功」，不自动补写 |
| 无 manifest，staging 里有 `.tmp` | `uncommitted` | 删（可安全重跑）|
| 无 manifest，但有没人引用的 blob（内容寻址） | `garbage` | 记入 `gc-candidates`，**不立即删**（可能另一 run 正在写）|

> **为什么「manifest 存在」就够**：rename 是原子的，所以「manifest 可见」与
> 「它列出的全部产物都已落盘」是**同一件事**，不是两个判断。这是整个设计成立的全部理由；
> 一旦把可见性拆成两个判断，就退回到「文件和清单可能不一致」。

#### 执行点与崩溃样本

`base/artifact_store.py` + `verify_atomic_commit.py`，注入六种故障点，逐个断言恢复判定：

| 故障注入 | 期望 |
|---|---|
| ① 写 staging 一半时 kill | `uncommitted`；重跑成功 |
| ② rename 到 blobs 一半时 kill | `uncommitted`；已 rename 的成为 `garbage`，**不许被消费** |
| ③ 写 manifest.tmp 时 kill | `uncommitted`；产物全部在最终位置但**不可见**（正确） |
| ④ rename manifest 前 kill | 同上；这是「已写完但没提交」的边界 |
| ⑤ rename manifest 后、删 staging 前 kill | `committed`；staging 残留无害 |
| ⑥ 提交后删掉一个 blob 再启动 | `orphan` + ERROR（**这是数据损坏，不是「未提交」**）|

反向对照：把第②步整个去掉（只 rename manifest）→ **必须红** —— 这正是第一版的 bug。

### §1ter.6 P-2：hash 链的措辞降格（**不加外部锚定**）

**裁定**：把「不可变审计」这个说法**降为「防误改的完整性链」**，并明写它防不住什么。

| 它防得住 | 它防不住 |
|---|---|
| 单个 JSONL 行被误改（前缀 hash 对不上）| 有本机写权限的人**整套重写**（重算整条链）|
| 追加写被截断 | **回滚**到旧快照 |
| 乱序/漏写 | 恶意伪造（无签名、无外部时间戳）|

**为什么不加外部锚定**：锚定要么上公链（合规、成本、且客户原文的 hash 上公链本身是个新问题），
要么上第三方时间戳服务（引入外部依赖与凭据）。**在单机 + 内部审计的定位下，收益不值这个代价。**
所以选择**说清楚它是什么**，而不是加一层看起来更硬的东西。

**如果日后审计要求真·不可变**：唯一的正确做法是「签名 + 外部可信时间戳」，
那是一次独立的合规决策，不是这里能顺手加的。

**执行点**：`AGENTS.md` 措辞 + **现存断言**「全仓不许出现『不可变审计』这几个字」（除本节与降格说明），否则红；`base/artifact_store.py` 是**未来实现落点（无代码）**，其 docstring **不得当执行点**；无现存断言的子项标「待建」。

### §1ter.7 G-2：外发 outbox（**不做 exactly-once 的承诺**）

> ⚠️ **本节第一版声称能防「卡片超时降级导致双发」，那个说法是错的，已改。**
> 第一版把幂等键定成 `run_id + 目标 + 内容 hash`。可是「卡片」与「降级文本」
> **内容不同、hash 就不同、键也不同** —— 两次发送会被当成两件不同的事，**照样双发**。
> 一个为防双发而设计的键，在它要防的那条路径上失效了。

**先承认一件做不到的事**：飞书的发送接口**不提供幂等键，也不提供「按 idempotency key 查询是否已发」**。
所以「恰好一次」在当前接口下**不可能保证** —— 只能选一边：

| 策略 | 崩溃时（发出去了但记账前崩） | 代价 |
|---|---|---|
| **at-most-once** | 不重发 | **可能丢一条消息**（群里什么都没收到）|
| **at-least-once** | 重发 | **可能重复一条**（群里收到两次）|

**本项目的选择：按来源分档**（这是产品判断，不是实现细节）：

| 来源 | 选哪边 | 为什么 |
|---|---|---|
| `reply`（回答某人的提问） | **at-most-once** | 重复回答比没回答更糟：对方会以为自己问了两遍 |
| `proactive-baseline` / `proactive-pending`（告警/提醒） | **at-least-once** | 漏报比重复更糟：告警没收到等于没有告警 |
| `resend` | at-most-once | 它本身就是一次重试，再重试就是三发 |

**于是「幂等键」的正确形态是 `logical_delivery_id`**：一次**逻辑投递**的 id，
**卡片与它的降级文本共用同一个**（因为它们是同一句话的两种形态，不是两句话）。
`logical_delivery_id = run_id + ':' + 目标 + ':' + 标签档位`，**不含正文 hash**。

**outbox 只补三件现有台账没有的**：

| 缺什么 | 补什么 |
|---|---|
| 意图先落盘 | 发之前写 `pending` 行（带 `logical_delivery_id`），拿到 `message_id` 后补成 `sent` |
| 超时对账 | `pending` 超时 → **按上表分档处理**，并标 `unknown`（不许标成「已发送」）|
| 形态合流 | 卡片与降级文本共用同一个 `logical_delivery_id`，第二次发送前先查这个 id 是否已有 `sent` 行 |

**保留不动**：`SOURCES` 封闭集合、`foldInto` 的「只有 daemon 写会话」、`alreadySaid` 的正文去重
—— 那三条是 2026-09-22 两次真实误答之后定的，不在本次改动范围。

**执行点**：`tools/agent/outbound.mjs` 加 `beginSend()` / `confirmSend()` / `reconcilePending()`，
配四条反向对照：同一 `logical_delivery_id` 发两次 → 只发一次；**卡片 + 降级文本两个变体 → 只发一次**
（这条专门守第一版的 bug）；`reply` 来源 `pending` 崩溃重启 → **不重发**（at-most-once）；
`proactive-*` 来源同样情形 → **重发**（at-least-once）。

### §1ter.8 G-3：入站 durable inbox

**裁定**：长连接收到事件后**先落盘再处理**，三段：

```
飞书长连接 → [1] 追加 events-inbox.jsonl（fsync）  ← 唯一的「收到」证据
           → [2] 按 event_id 去重，写处理游标 cursor.json
           → [3] 交给回复循环
```

- **去重键**：飞书的 `event_id`。重复投递（长连接重连后的补发）只处理一次。
- **游标**：处理完成后更新 `cursor.json`；重启时从游标之后继续，**不从头重放**
  （重放会让群里收到旧消息的重复回答）。
- **与重启闸门的关系**：`AGENTS.md` §2.7 的重启窗口问题**不会因此消失** ——
  inbox 只保证「已经推进来的事件不丢」，**进程不在时推进不来的那些仍然会丢**。
  这条要写进 §2.7 的说明里，不许把它读成「重启无损」。

**执行点**：`tools/agent/inbox.mjs` + 反向对照：同一 `event_id` 投两次 → 只处理一次；
处理到一半 kill → 重启后从游标续，不重复回答。

## §6 · 设计期核验发现的问题（**必须先读**）

从六维设计到收敛，核验共抓出以下问题。**前 6 条是 critical，不修不能开工。**

### [critical] L1-7/L1-8/L6-5：报告级计数没有模块负责

- **位置**：维度1 metrics_evaluator；维度2 report_renderer；维度3 report-renderer；维度4 report_render；维度6 output-renderer
- **问题**：L1-8 明文要求「每次运行的报告里，四种 failure_kind 的条数必须出现（哪怕全是 0）」；L6-5 要求未知桶计数「在报告里出现」；L1-7 要求 empty 与 failed 可分别数出。全方案只有 metrics_evaluator 在 criterion_refs 里认领 L1-8/L6-5，但它的职责是算四指标、生成 metrics/<period>.json，明确不写报告；五个报告渲染模块没有一个认领 L1-7/L1-8/L6-5。维度3 的 D11-report-v1 自己写明「L1-8 的四种 failure_kind 计数、L6-5 的未知桶计数也没有区块；方案同见 open questions」。结果这三条判据在报告上没有落点，验收取不到读数。
- **修法**：指定唯一报告渲染模块（report_renderer 或 output-renderer）负责把 failure_kind 计数与未知桶计数写入报告（新增区块或明确扩展 F1/F2），由 metrics 模块提供计数；为 L1-7/L1-8/L6-5 各加报告级断言，含全 0、未知桶为 0 的样本。

### [critical] L2-7：回执 schema 至少四套，写入者与字段表互相冲突

- **位置**：维度1 job_dispatcher/ARCH-08；维度3 D07-receipt-v1/receipt-ledger；维度4 D04/audit_schema/orchestrator；维度6 orchestrator
- **问题**：L2-7「每次执行落一张回执，字段符合 3.3.3」被 job_dispatcher、pipeline_orchestrator、artifact_store、receipt-ledger、orchestrator、rule_engine_bridge 等重复认领，但回执定义互斥：维度4 D04 在 11 字段外要求 obligations/invariant_violation/error/disposition/control_points_ran/control_points_skipped/ir_ref/video_sampling/models_used/code_version/decision_chain；维度3 D07 要求 control_points_run/control_points_version/obligations/invariant_violation/frame_sampling/models_used/origin；维度1 ARCH-08 另造 dispatcher 外层 run_record（error_kind）；维度6 只写 11 字段。字段名（run/ran）、control_points_version 与 origin 的有无、ERROR 回执由内层还是外层写都不一致，同一 job 可能产出两张回执。
- **修法**：由 contracts-suite 唯一拥有回执 schema、orchestrator 唯一写入；dispatcher 的 run_record 定义为独立 artifact，不冒充回执；合并两份扩展字段表并去重，把 L2-7 只挂这两个 owner。

### [critical] L1-0/L1-1/L1-2：IR 契约三套并存（冻结 v1 / 升 v2 / 套信封）

- **位置**：维度3 contracts-suite/content-unit-adapter（D01/D02）；维度4 audit_ingest/contract（D22）；维度6 review-ir（D-10）；维度1 ir_normalizer；维度2 normalizer
- **问题**：同一批 IR 判据有三种互斥落法：维度3 新建 contracts/ 与 content-unit-v2，同时声明 base/content-unit-v1.schema.json 与 base/contract.py 冻结不改；维度4 D22 把 base/contract.py 从 v1 升到 v2；维度6 D-10 不重写 base/contract.py，改用「扩一层信封」。六七个归一化模块都认领 L1-0~L1-2，却对「哪个 schema 是真值、unit_id/text_sha256/covers 写在哪一层」没有共识；artifact_store 还在 criterion_refs 里认领 L1-1，但它只负责存储、不计算 unit_id。任何一条验收只能对一套成立。
- **修法**：先裁定唯一 IR 契约 owner 与迁移策略（新 v2 包或 envelope 二选一），其余维度只保留 adapter；在契约里写死唯一真相；L1-0/L1-1/L1-2 只挂一个 owner，并从 artifact_store 等存储模块移除认领。

#### 8.1a **53 个辅助 ID 的缺口（明着留 open，不并入 B-2）**

> ★ **B-2 关闭的只是「86 条正式编号判据各有一个 owner」这一件事。**

|---|---|---|
| **存在性** | 验收表引用了 53 个、Playbook 里 0 个 | 没有登记表，也没有「这个标签从哪来」的指针 |

### 8.10 D-4 的落地规格（**媒体 24h · IR 1 年 · 报告长期**）

> ✅ **已定（委托方 2026-10-17）。**

| 数据 | 留存 | 到期动作 |
|---|---|---|
| **媒体**（帧 / OCR 图 / 抽出的字节） | **24 小时** | **删除**，但删除前必须已落指纹 |
| **IR**（正文 + 双指纹 + 覆盖声明 + 来路） | **1 年**（随案件） | 随案件归档 |
| **报告**（静态 md） | **长期** | 不删（可从 IR 重建，删了也能造） |

**三条必须同时成立的判据：**

| # | 判据 | 为什么 |
|---|---|---|
| **RT-1** | 媒体删除**之前**，其指纹（sha256）必须已写进 IR | 否则「这条内容当时长什么样」永久不可考 |
| **RT-2** | 媒体删除必须**留痕**（删了什么、什么时候、按哪条规则） | 「没删」与「删了没记」长得一样 |
| **RT-3** | 一年后复审时，**必须能从 IR 回答「当时评了什么、结论是什么、依据是什么」**，即使媒体已删 | 这是 IR 保留 1 年的唯一理由 |

> ⚠️ **RT-3 的代价要说清**：媒体 24h 后删，**一年后无法回看原帧**。
> 审核员只能看到「当时这条 finding 的位置是 12.3–12.8 秒、bbox 在这里、quote 是这个」，
> **看不到那一帧的图**。要回看必须重新取一次（如果原件还在）。
> **这是用「不留客户数据」换「复核时看不到原图」的取舍，是刻意的。**

> ★ **与 D-2 的关系**：报告长期 ≠ 媒体长期。**报告里不含媒体二进制**，
> 只含文字与 `frame_thumb` 的**指针**——而那个指针 24h 后失效。这是已知且接受的。

### 8.11 D-5 的落地规格（**统一 2 个工作日**）

> ✅ **已定（委托方 2026-10-17）：统一 2 个工作日，不分严重度。**

| **SLA-2** | 超时升级**必须落一条可查的记录**（什么时候、升给谁、因为超时） | 没记录 = 没人知道自己被升级了 |
| **SLA-3** | **升级不等于关案** —— 升级后案件仍在原负责人手上，只是被更多人看到 | 否则「升级」会变成「甩锅」 |

> ⚠️ **统一阈值有一个已知的代价，必须写明**：
> **BLOCK 类内容拖 2 个工作日才升级，可能已经上线了。**
> 这不是靠 SLA 解决的 —— 它靠的是「机器可以自己下 BLOCK，且不存在从标签直连发布的路径」（原则一）。
> **SLA 管的是「人什么时候来看」，不是「风险什么时候被拦住」。**

> ★ **D-5 与 §8.1 G-1（人工放行门）不是一回事**：
> D-5 管「复核超时」；G-1 管「谁有权批准发布」。**二者都缺，但缺的不是同一样东西。**

### 8.12 D-6 的落地规格（**单独一张冲突表**）

> ✅ **已定（委托方 2026-10-17）：冲突关系单独成表，`evidence_sync` 查表，不靠推理判冲突。**

**表结构**（`research/governance/authority-conflicts-v1.json`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `conflict_id` | string | 唯一标识 |
| `ref_a` / `ref_b` | string | 冲突的两条依据（`authority_ref` 的 id）|
| `nature` | enum | `直接矛盾` / `范围重叠` / `时效冲突` / `法域不同` |
| `resolution` | enum | `未裁` / `以 A 为准` / `以 B 为准` / `按场景分别适用` |
| `resolved_by` | string \| null | 谁裁的（**必须是人**，未裁时为 null）|
| `resolved_at` | date \| null | 何时裁的 |
| `version` | string | 本表版本 |

**四条判据：**

| # | 判据 | 为什么 |
|---|---|---|
| **CF-1** | `any_authority_conflict` **只能来自查表**，不许由代码临时推断 | 否则不可复现：同样两条依据，今天判冲突明天不判 |
| **CF-2** | 表里 `resolution = 未裁` 的冲突**仍然算冲突**（走 REVIEW/DP4） | 「还没裁」不等于「不冲突」—— 它恰恰是最该转法务的状态 |
| **CF-3** | 每条冲突必须能**分别数出来**（按 `nature` 分组） | 「规则打架」这个信号必须可见；否则它会被当成普通故障 |
| **CF-4** | 依据变更时**必须检查冲突表是否过期**（`ref_a`/`ref_b` 指向的依据已改版则报警） | 否则表会变成一份过期名单 |

> ⚠️ **这张表最大的风险不是漏报，是没人维护。**
> 一张空的冲突表会让 `any_authority_conflict` 永远为 false —— **等于判定链里的一个分支永远不触发**。
> 所以 CF-3 是必须的：**报告里要把「本月冲突数为 0」写出来**，
> 才能区分「确实没有冲突」与「这张表没人管」。
