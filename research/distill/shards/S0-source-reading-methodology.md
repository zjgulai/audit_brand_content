## 一、结论先行

这个仓库是一套**带 AI 精读大型源码仓库的方法论**，四个阶段、三份模板、一个零依赖文风扫描器、29 条踩坑记录。它解决的问题可以收束成一句话，作者自己写在 README 里：

```48:48:source-reading-methodology/README.md
**让每一个技术论断都可回溯到源码的具体行。**
```

它值得为本项目所用的理由如下。本项目此前的调研产出（`research/star-lists-audit-report.md`，521 行）是**论断级**的，例如「`constraints.yaml` 把阈值外部化」。论断级产出有一个结构性弱点：读者无法自己验证，而 AI 辅助读码时幻觉几乎必然发生，它会根据文件名推测实现、根据常见模式补全细节、把注释当成代码行为陈述。作者对后果的表述很直接：

```17:17:source-reading-methodology/METHODOLOGY.md
这套方法论的核心是用一件事同时解决两个问题：**让每一个技术论断都可回溯到源码的具体行**。可回溯迫使你真的读到那一行，也让读者能自己验证。
```

**已经发生的事实验证了这个担忧。** 在派活之前核对前一份报告的路径时，至少三处路径claim 与真实代码树不符：

| 前一份报告写的 | 实际位置 |
|---|---|
| `ad-review-agent/decision_engine.py` | `ad-review-agent/src/agents/decision_engine.py` |
| `ad-review-agent/rules_loader.py` | `ad-review-agent/src/rules_loader.py` |
| `cbi/backend/src/rules/ruleBasedReview.js` | **该文件不存在**，需重新定位 |

三处都是路径与位置层面的偏差，不涉及结论对错。它们说明的是同一件事：**论断级产出的错误无法被读者发现**，因为读者手里没有可跳转的锚点锚点。

## 二、内核：可回溯如何同时解决两个问题

方法论自称用一件事解决两个问题：读了很多却没留下结构化理解，以及产出看起来很专业但掺了编造。可回溯是那个「一件事」。

它把可回溯落成八条**作废级**铁律。作废级的含义是违反的稿件直接作废，修改都不做：

```135:143:source-reading-methodology/METHODOLOGY.md
违反的稿件直接作废，不是修改，是作废。七条：

1. 每一处源码引用、每一个行号、每一个类型名与函数名，动笔前用读文件工具实读核实。禁止凭印象写、禁止根据文件名推测、禁止照抄大纲里的候选行号
2. **代码块必须与源文件逐字节一致**。保留原始缩进、属性宏、注释、空行。禁止转译、禁止美化、禁止删属性、禁止写「示意代码」或「简化版」
3. 找不到某个机制的实现，明确写出来：`未找到对应实现，检索关键词为 X、Y、Z`。不许编一个看起来合理的实现
4. 源码里没明说、由你推断的结论，显式标注为推断
5. 引用注释原文时说明这是注释，不要把注释内容当成代码行为陈述
6. 数字（行数、文件数、枚举变体个数）必须实际统计过。统一用 `splitlines()` 口径，避免末行换行符造成的 off-by-one
7. 引用符号链接时引真实文件。`CLAUDE.md -> AGENTS.md` 这种情况引 `AGENTS.md`，否则同一份材料在不同章节里会出现两个名字
```

**第 4 条与第 5 条对本项目价值最高。** 本项目要判断的很多问题，源码给出的答案是「这里没有实现」或者「这只是注释里的一句话」。前一份报告在四处 README 上都发现了文档与代码不符，第 4 条把这类发现从失败变成了交付物。

## 三、四阶段，以及「别过度应用」

````60:71:source-reading-methodology/README.md
## 四个阶段

产出物分层，每一层的输入是上一层的输出。不要跳级。

```
阶段一  语料准备      锁版本、备对比语料、建检索脚本
   ↓
阶段二  大纲          回答「这门课要解答哪一个问题」+ 逐章源码锚点
   ↓
阶段三  章节书稿      八段结构，每处论断带行号，机器校验
   ↓
阶段四  成书          编成一本带封面封底的 HTML 书，可读、可查、可传
````

紧接着它自己划了适用边界，这一节决定了本项目要采用哪几段：

```12:22:source-reading-methodology/SKILL.md
## 第一步：先定规模，别过度应用

问清产出形态再动手。四阶段全流程很重，小任务不需要。

| 用户要什么 | 走哪些 |
|---|---|
| 读懂某个模块、回答一个机制问题 | 只用零幻觉引用纪律，不建大纲不做课页 |
| 一篇架构分析、一份技术文档 | 阶段一 + 阶段三 |
| 一门课、一个系列、多篇连载 | 四阶段全走，并建校验器 |

不确定就问：产出是给自己看还是给别人看，要不要交互演示，篇数大概多少。
```

按这张表，本项目的产出形态是「一份技术文档」，对应**阶段一 + 阶段三**。阶段二（大纲）与阶段四（成书）服务于「一门课」，本项目不产出课程，因此不采用成书构建器与课页规范。

有一件事阶段一要求、本项目此前的调研**没有做**：锁版本锚点。方法论把它的缺失后果写得很具体：

```60:64:source-reading-methodology/METHODOLOGY.md
**只读一个仓库读不出设计决策。** 你会把作者的选择当成唯一解，因为你没见过别的解法。

至少准备一个同类项目做对照。理想情况是三个，覆盖不同语言和不同取舍。四个项目的实践里，对比语料贡献了最有价值的那部分内容：同一个问题的两种答案各自付出了什么代价。

对比语料也要锁版本，路径写进关键路径表。
```

本项目手里有 11 个同类项目的本地快照，对比语料是充足的，缺的是版本锚点。抓取时间 2026-09-15，各仓库内部 commit 未逐一记录，这是一个已知缺口，见第六节。

## 四、投入产出比最高的那件事：机器校验

作者对它的评价没有保留：

```306:306:source-reading-methodology/METHODOLOGY.md
**这是这套方法论里投入产出比最高的一件事。** 人工复核十万字的行号不现实，必须写脚本。
```

校验三件事，第三件来自一次真实事故：

```312:316:source-reading-methodology/METHODOLOGY.md
1. **代码块与源文件逐字节比对**。以内容为准、行号为辅：把引用块按省略标记切成连续段，要求每段在源文件里能找到完全连续的匹配。拼不上就判 FABRICATION。行号错了可以自动校正
2. **文风禁忌扫描**。把上一节那份禁忌清单写成正则，交付前自动过一遍。扫描要跳过代码块和行内代码，否则源码里的字符会被误判
3. **引用密度下限**。防止一种很隐蔽的作弊：删掉引用让校验变绿

第三条来自真实事故。某章初稿 56 处引用带若干报错，交付时只剩 22 处、全部通过，作者把报错的引用删掉了。**校验器只报「现有引用是否正确」，不报「该有的引用是否还在」，这个缺口必须补上。**
```

第三件事直接决定了本项目的派活方式。**「删引用让校验变绿」在并行生产里是必然发生的偏差**，因为子 Agent 面对校验失败的局部最优解就是删掉那条引用。所以校验器必须有密度下限，而且这项要写进派活规范里提前堵。

有一条判据细节值得单独抄出来，它展示了「判据放宽一毫米，盲区扩大一平方公里」：

```86:88:source-reading-methodology/PITFALLS.md
**根因**：省略标记的判据写成了「整行是注释且含 `...`」。源码里 `/// Returns ... within a \`bash -lc "..."\` or` 这种正常的文档注释被当成了省略标记，于是这几行既不参与逐字节比对，也不参与行号推算。判据宽一分，校验盲区就大一片：落在这类行里的内容可以随便编，校验器不看。

**对策**：判据收紧成「整行是注释，且注释符号后面紧接着就是 `...`」。
```

本项目的 `research/distill/verify_citations.py` 直接采用了收紧后的判据，并额外区分了 `LINE_DRIFT`（内容真实、行号偏差，可自动校正）与 `FABRICATION`（内容找不到，作废级）。作者提的「行号错了可以自动校正」正是把两者分开的理由：行号漂移是运维问题，编造内容是可信度问题，前者可以修，后者只能作废。

## 五、并行生产：派活必须给全四样

```332:339:source-reading-methodology/METHODOLOGY.md
三十章逐章写完要很久，可以派并行子 Agent，每个负责一章。前提是规范足够硬，规范里每一处含糊都会变成三十份不同的理解。

### 派活时必须给的东西

- 完整的写作规范（一个文件，不要口头补充）
- 那一章的大纲条目
- 全部语料的绝对路径，包括对比语料。**不要凭印象说某个语料不在本地**，先确认再说，否则子 Agent 会绕开它
- 校验命令，以及「必须全绿才算交付」
```

本项目按这四样派活，对应关系：

| 方法论要求 | 本项目的落实 |
|---|---|
| 写作规范（一个文件） | `research/distill/00-写作规范.md` |
| 大纲条目 | `research/distill/01-大纲.md` 的对应分片节，含**已实读核实的候选锚点** |
| 绝对路径 | 语料根 `/Users/lute/Project/audit_multi_content/research/repos/`，11 个仓库逐一确认存在后才写进大纲 |
| 校验命令 | `verify_citations.py` + `style_scan.py`，两条都要 0 命中 |

第三样在本项目上有一次真实的预判拦截。派活前核对时发现，前一份报告说 `research/repos/` 有 8 个仓库，实际有 11 个，且它列为 P0 的 `crossborder-image-agent-New-` 在本地目录里叫 `cbi`。**如果按前一份报告的路径派活，子 Agent 会绕开这个价值排第二的仓库**，这正是方法论警告的那种事故。

派活之前先建校验器、并跑通一个样例，本项目照做了，自测覆盖五类故障（编造、路径错、区间不符、行号漂移、密度不足），五类都被正确抓出。

## 六、这套方法论的局限，以及本项目的已知缺口

1. **它假定产出的读者会去核对行号。** 本项目的第一读者是要做设计决策的人，不一定逐行跳转。因此本项目在卡片里加了「证据强度」字段（已实读核实 / 仅注释说明 / 推断 / README 声称但代码中未找到），让不跳转的读者也能判断每条结论的可信度。这是对本方法论的扩展，不是替代。
2. **版本锚点在本项目只完成了一半。** 各仓库有本地快照与抓取日期（2026-09-15），但只有 `source-reading-methodology` 记录到了 commit（`f45f579`）。其余仓库多数是从 tarball 解包的，没有 `.git`，无法取 commit。补全方式是从 GitHub API 取各仓库当时的 HEAD，这项工作尚未做。
3. **它的文风禁忌是为中文技术书稿定的。** 本项目直接沿用了十二条中的绝大部分，并额外加了一条「空话迁移」禁令：禁止在迁移建议里写「可以参考」「有一定参考价值」这类没有落到字段名的表述。理由与本项目产出形态有关，卡片的价值全部在「迁到 Momcozy 长什么样」这一段。
4. **它对「对比」的要求比本项目原计划高。** 它要求横向对比必须说清另一侧为什么可以没有、或用别的东西补上了，禁止写成功能清单对照。本项目的大纲把「每个分片至少一组横向对比」列为必填。

## 七、对本项目的直接启示

有一句话值得单独摘出来，它解释了为什么本项目的知识库要横跨 11 个仓库：

```50:52:source-reading-methodology/README.md
可回溯迫使你真的读到那一行，也让读者能自己验证。AI 辅助读码时幻觉几乎必然发生，它会根据文件名推测实现、根据常见模式补全细节、把注释当成代码行为陈述。一旦掺进去，整份成果的可信度就是零，因为读者无法分辨哪句是真的。

这套方法论里所有的规则，都是为了守住这一条。落到版面上是这样：
```

**前一份报告的四处文档不可信，与本项目的目标直接相关。** 本项目要做的是内容审计，核心动作是「判断一份材料声称的东西有没有证据支撑」。而这次调研在四个仓库上都遇到了同一种现象：README 声称实现了某能力，代码里查不到。这与广告场景的「有 claim 但无 substantiation」在结构上完全同构。

因此本项目采用的判定形态（来自 `sinyard/contract_review/risks.py` 的「有 A 但缺 B」）在这套方法论上得到了独立印证：**声称与证据的分离，是一个可以跨领域复用的审计原语。**
