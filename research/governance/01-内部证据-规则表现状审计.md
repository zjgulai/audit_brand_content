# 内部证据：现有规则库的可执行性审计

> 本文不是读文档写的判断，而是**把 `PRD/内容治理需求文档.md` 当数据集跑出来的结果**。
> 复跑命令：
> ```
> python3 research/governance/audit_rule_table.py     # 规则表层（21 条）
> python3 research/governance/audit_records.py        # 记录层（291 条）
> ```
> 机器可读结果：`research/governance/_evidence/rule_table_audit.json`、`record_audit.json`
> 审计日期：2026-09-15

---

## 结论先行

**现有 21 条规则表是一份「文档」，不是一份「可执行规则库」。两者的证据是：把它自带的正则跑在 291 条真实记录上，只能复现 13.8% 的人工判定，72.3% 一条都复现不出来，而且它从不多报一条。**

这意味着团队现在的判定能力**不在规则表里**。规则表记录了「我们关心哪些风险」，但真正做判断的是别的东西——三维度上看是人工的隐性知识，加上一张只存在于 `命中片段` 自由文本里的**多语种词表**。

这直接解释了团队的困惑「规则库应该如何来定义」：**他们困惑的不是分类维度选哪几个，而是「规则」这个词现在同时指两样东西——一份给人看的政策文档，和一套给机器执行的判定逻辑。这两样东西已经分家了。**

## 一、规则表层（21 条）

### 1.1 结构

12 列，21 行，列数无错位：
`规则编号 | 边界类型 | 适用产品 | 风险等级 | 检测关键词 | 边界内容 | 判断方式 | 依据来源 | 启用状态 | 正则表达式 | 豁免词 | 触发原因`

### 1.3 豁免词与正则互相打架

`M01` 的正则 `\b(silent|noiseless|whisper.?quiet)\b` **会命中它自己的豁免词 `silent mode`**。也就是说按正则在跑，`silent mode`（应当放行）与 `silent`（应当判黄）会被同等对待，豁免只能靠人。

其余 4 条带豁免词的规则（H01 / H02 / H06 / H07）没有这个问题，但**它们的豁免词清一色是英文与中文，没有一条小语种**。而 H06 的豁免词 `FDA cleared / FDA-cleared / FDA registered / FDA 注册` 恰好会被 H06 自己的正则 `\bFDA\s+(approved|certified)\b` 放过——这一条是对的。

### 1.4 编号族不是一个分类轴

| 前缀 | (边界类型, 风险等级) | 是否单一 |
|---|---|---|
| H | (严格限制红线, 高危) ×9 | ✓ |
| **M** | **(审慎关注, 审慎) ×6 与 (人工复核, 审慎) ×1** | **✗ 多义** |
| U | (人工复核, 待复核) ×4 | ✓ |
| 安全词 | (安全词白名单, 合规) ×1 | ✓ |

`M05` 的边界类型是「人工复核」但风险等级是「审慎」，与其余 6 条 M 规则（审慎关注 / 审慎）不同。**M 这个前缀因此同时编码了「审慎关注」和「人工复核」两个不同的轴**，机器无法从前缀推出处置动作。

### 1.5 「适用产品」字段是失效的

21 条规则全填 `W1、M5、M6、M9、Air1`。但同一份 PRD 的「风险文案改写建议库」里实际出现的型号是：

|---|---:|---|
| W1 | 13 | ✓ |
| **S12 Pro** | **5** | **✗** |
| M9 | 4 | ✓ |
| M5 Smart | 3 | （写作 `M5`） |
| Air 1 | 3 | （写作 `Air1`） |

| **V1 Pro** | **1** | **✗** |

**S12 Pro 与 V1 Pro 有改写建议、却没有规则覆盖。** 且 `M5` / `M5 Smart`、`Air1` / `Air 1` 两种写法混用，字段值没有受控词表。

### 2.1 可复现性：规则表复现不了自己的判定

### 2.2 多语种词表存在，但在错的地方

把 291 条记录里 `命中片段` 字段解析成 `（规则编号, 命中词）` 对，共 **270 对**。逐对检查它能否被该规则自带的 `检测关键词` 解释：

```
能被规则自带关键词解释的：167  (61.9%)
不能解释的：              103  (38.1%)
```

**规则表 21 条的 `检测关键词` 里，带变音符的拉丁字符数量为 0。** 一条都没有。而人工实际在用的命中词包括：

| 次数 | 命中词 | 语种 | 所属规则 |
|---:|---|---|---|
| 18 | `schmerzfrei` | 德 | H07 无痛 |
| 11 | `hospital-grade` | 英（连字符写法） | M05 |
| 8 | `sans douleur` | 法 | H07 |
| 8 | `whisper-quiet` | 英（连字符写法） | M01 |
| 6 | `strong suction` | 英（短语写法） | M02 |
| 4 | `indolore` | 意 | H07 |
| 4 | `augmente la production de lait` | 法 | H02 |
| 4 | `silencieux` | 法 | M01 |
| 3 | `silenciosa` / `silencioso` | 西 | M01 |
| 2 | `sin dolor` | 西 | H07 |
| 2 | `mehr milch` | 德 | H02 |
| 2 | `cicha` | 意 | M01 |
| 2 | `succión potente` | 西 | M02 |
| 1 | `qualité hospitalière` | 法 | M05 |
| 1 | `krankenhaus` | 德 | U03 |

**结论**：运营层已经是 5 语种（英/德/法/西/意），规则表层是 2 语种（英/中）。**这张多语种词表现存于 3 位 Copywriter 的脑子里和 `命中片段` 的自由文本里，规则表里没有。** 这是规则库里价值最高、也最容易随人流失的部分。

同一现象的另一面：`hospital-grade`（记录里的写法）与 `hospital grade`（规则里的写法）、`whisper-quiet` 与 `whisper quiet`、`strong suction`（记录）与 `super strong`（规则）——**连英文内部都存在书写形态的漂移，而规则表用空格分词，没有归一化层。**

### 2.3 覆盖缺口被呈现为「合规」

| 项 | 数量 | 占比 |
|---|---:|---:|
| 有 `Primary Text` | 232/291 | 79.7% |
| 有 `Headline` | 232/291 | 79.7% |
| 有 `落地页URL` | 204/291 | 70.1% |
| **两者皆无（引擎看不到任何文案）** | **59/291** | **20.3%** |

这 59 条的广告类型全部是 `产品广告`，风险等级分布是 **绿 55 / 灰 2 / 空 2**。也就是说：**引擎看不到的素材，默认落在「合规·绿」。**

这正是 `research/distill/cross-cutting-findings.md` 第 11 节记录的反模式——「降级链把『无法分析』呈现成『没有问题』」——在本项目现网正在发生。区别只是这里的降级发生在数据采集层，而不是模型层。

其中只有 2 条被显式标注：
```
命中片段: EMPTY:<文案为空/非文本广告>
命中规则: EMPTY
修改建议: 导出表无文本文案（多为图片/视频/自适应素材），需到广告后台人工查看素材本体
处理状态: 待人工复核
```
**这两条的处理方式是对的**（降级为灰、给出下一步动作）。问题是同样的处理没有覆盖另外 57 条。

另外 `广告类型` 字段显示：图片需求开发广告 83 + 视频需求开发广告 31 + 自适应视频广告 6 = **120 条（41%）是图片/视频形态**。这些记录有文本的，引擎审的是文案文字；没有文本的，引擎什么都没审。**素材本体（画面、字幕、口播）不在任何一条记录的覆盖范围内。**

### 2.4 问责链在数据上是断的

PRD 原文：

> 目前无法强制卡死「审查完才能上线」的系统节点，因此需要 GTM 严格把控，且必须执行此流程。**如果上线后依然出问题，则通过审查记录明确问责。**

而 291 条记录里：

| 字段 | 填写数 | 比例 |
|---|---:|---:|
| `风险等级` | 289/291 | 99.3% |
| `处理状态` | 289/291 | 99.3% |
| `命中规则` | 132/291 | 45.4% |
| `命中片段` | 132/291 | 45.4% |
| `修改建议` | 132/291 | 45.4% |
| `命中原因` | 130/291 | 44.7% |
| **`检查人`** | **0/291** | **0.0%** |

**没有任何一条记录有检查人。** 132 条非绿记录的处理状态**全部**是 `待人工复核`，157 条绿记录全部是 `无需处理`——**没有任何一条记录处在「已复核 / 已处置 / 已上线」的终态。**

也就是说：
- 「通过审查记录明确问责」这条兜底机制，**目前没有数据支撑**。真出问题时，无法回答「这条素材当时是谁签的字」。
- 无法区分「人工看过了，同意 Agent 的判断」与「人工还没看」。这两个状态在数据上完全相同。

`处理状态` 只有两个取值（`无需处理` / `待人工复核`），49 条记录里 `风险等级` 与 `命中规则` 自洽性检查发现 4 条异常（2 条标灰但命中规则写 `EMPTY`，2 条等级为空）。

### 2.5 规则负载极度不均衡

238 次规则命中（多命中记录重复计入）的分布：

| 规则 | 命中 | 累计占比 |
|---|---:|---:|
| H07 无痛承诺 | 51 | 21% |
| M03 数据/社会证明 | 38 | 37% |
| H02 催乳增产 | 34 | 51% |
| M01 静音夸大 | 18 | 59% |
| U03 医院场景 | 17 | 66% |
| M07 效率/漏奶/奶流 | 16 | 73% |
| M05 等级背书 | 15 | 79% |
| U01 IBCLC 头衔 | 15 | **86%** |

**前 8 条规则承担 86% 的命中量。** 而从未命中的有 6 条：

```
H01（医疗功效，72 个关键词，全表最长）
H03（临床背书）
H06（FDA 表述）
H08（竞品对比）
U02（保险，已停用 —— 停用是合理的）
安全词（白名单，本来就不该产生违规，合理）
```

**9 条 H 类红线规则里有 4 条（H01/H03/H06/H08）在 291 条真实记录中零命中。** 两种解释，必须区分：
- (a) 这四类风险真的没发生 —— 那它们是低概率但高后果，属于必须保留但资源投入应下调

**现有字段无法区分 (a) 与 (b)。** 这正是「错题本」要解决的第一件事。

### 2.6 规则重叠：一条命中被记两次

命中 ≥2 条规则的记录 69 条 / 291。高频共现组合：

| 组合 | 共现次数 | 解读 |
|---|---:|---|
| H07 + M03 | 17 | 无痛承诺与销量声称常同现 |
| **M05 + U03** | **15** | **M05 共命中 15 次，与 U03 完全重合 → 每次 M05 命中，U03 也命中** |
| H02 + M03 | 9 | |
| M03 + M05 | 8 | |
| M03 + U03 | 8 | |
| H02 + M01 | 8 | |

`M05`（等级背书：`hospital grade / medical grade`）与 `U03`（医院/NICU 场景：`hospital / NICU`）是**同一个触发词家族的两条规则**。业务上 M05 问「有没有等级认证」，U03 问「有没有临床适用性文件」——是两个不同的问题，但**触发条件完全相同**。这在规则工程里叫**触发条件冗余**：改一个词表要改两处，且两条规则会同时进人工队列，制造双份工作量。

### 2.7 命中片段已经是一个证据记录，但没有结构

`命中片段` 的实际形态：

```
H07:sans douleur
M03:bestseller / H07:schmerzfrei
H02:more milk / M03:best-selling / U03:hospital / M05:hospital-grade / M07:smoother milk flow
H04:ob-gyn recommended / M03:trusted by 6m / U01:ibclc
H02:faster let-down,support faster let-down / H05:perfect pump / M07:improve milk flow
H07:say goodbye to cold, painful / U04:painful pumping
```

它已经在编码 `（规则编号, 命中词）` 这个二元组，用的分隔符是 `/` 与 `,`。**这是一条结构化的证据记录被写成了字符串。** 拆开它就是现成的 `evidence[]` 数组，每个元素是 `{ruleId, matchedTerm, text, span}`——只缺字符位置。

`H07:say goodbye to cold, painful / U04:painful pumping` 这条还展示了一件事：U04 的描述写「与 goodbye/no more/not anymore/relieve 等消除性表述连用**应升级** H01/H07」。**这条升级逻辑写在散文里，由人工执行，规则表里没有对应的字段或表达式。**

## 三、这些发现如何回答团队的四个问题

| 团队的问题 | 这份审计给出的答案 |
|---|---|
| 规则库按「国家 × 品类 × 平台 × 内容类型」定义？ | **这四个都不是当前的主要矛盾。** 当前最大的两个隐藏维度是**语种**（38.1% 的命中在规则表里没有词）与**内容模态**（20.3% 的记录引擎看不到）。而且「维度」不该是规则的分类轴——见 R1/R3 分片 |
| 怎么萃取？需要「错题本」还是「规则库」？ | 「错题本」已经存在了，它就是这 291 条记录，只是**缺三个字段**（见下） |
| 严重等级？ | 现有四档（高危/审慎/待复核/合规）与编号族 **M 是多义的**，且四档之间没有升级/降级规则 |
| 要是没有呢？怎么办？ | 现在就是「规则不全也不一定对」的状态。审计给出了它具体长什么样：正则层 13.8% 复现率、6 条规则零命中、20.3% 记录不可见 |

### 错题本缺的三个字段（这是全篇最可执行的一条）

现有 27 列**没有任何一列**承载以下三件事：

1. **false positive**（Agent 判违规、人工判定合规）
   现在 `处理状态` 只有 `无需处理` / `待人工复核`。人工推翻 Agent 的结论无处可记。
   **没有这个方向，规则只会越加越严，召回率上升、准确率下降，最后人工复核队列爆掉。**

2. **false negative**（Agent 未判、人工补判违规）
   现在绿记录是终态，人工在绿记录里发现的问题无处可记。
   **这是 H01/H03/H06/H08 零命中的 (a)/(b) 判别器。**

3. **规则出处**（这条判定依据哪条规则、这条规则从哪个案例长出来）
   现在 `依据来源` 只写「W1卖点表达边界（品线反馈2026-09-10 T4）」或「红绿灯.xlsx 规则库」。**没有一条规则能追到具体的错题。**

这三件事同时缺失，导致规则库**只能单向生长**：只能加规则，不能改规则、不能删规则、不能证明一条规则是对的。
