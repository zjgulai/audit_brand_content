## 2. 三个缺陷：修好了，以及为什么修法不是我以为的那个

### 2.1 白名单对判定**没有任何运行时影响** —— 但「接上」不是正确答案

原状（盘点实测）：

```
vocab.py:64-65   提供 pass_of()
grep pass_of     全仓无消费者
score.py:127     只看 downgrade_of()
score.py:439     仍在打印「放行带 8 词次」
```

3 条 `target=auto_pass` 的规则（`T6.1.regulatory-status` / `T2.2.quiet-claim` /
`T2.2.suction-claim`）的**降级带全是空的** —— 它们的词落在 `pass_bands` 里，
而那两条 `→ auto_pass` 分支因此**不可达**。

**我第一版的修法是错的**：我写的是「把 `pass_of` 接到 `assess` 里」。
那等于把「哪条带」这个判断留在代码里。正确的问题是：**谁有权决定落点？**

答案在 ADR-0008 §三 的分工表里 ——「降级后的处置等级 ✅ 法务定义 ❌ 开发者」。
而方向**早就写在规则文件里了**：`downgrade_band.effect` 的箭头右侧。
`"auto_reject → auto_pass"` 这个字符串就是法务的声明。

> **修法**：按 `band_target(rule)` 选带。代码读声明，不复述声明。
> **副作用**：法务改一个字符串就能改处置等级，不需要开发者改代码、不需要发版。

**修完在存量 291 条上触发 0 次。** 没有一条记录同时含判险词与放行词。
所以这条修复**无法被存量语料验证** —— 用构造用例做的正对照：

| 输入 | 结果 |
|---|---|
| `FDA approved and FDA cleared breast pump` | `T6.1` `auto_reject` → **`auto_pass`** |
| `Whisper quiet motor, with a quiet mode` | `T2.2.quiet` `manual_review` → **`auto_pass`** |
| `FDA cleared wearable breast pump`（只有豁免词） | 零命中 → CATCH-ALL（**不是**「合规」） |

> ★ **需要法务裁定**（ADR-0012 §4.2）：第一行里「FDA approved」本身是错误宣称，
> 即便同段文字也出现了正确的「FDA cleared」。规则现在声明的效果就是放行。
> 若不认可，把该规则的 `effect` 改成 `auto_reject → manual_review` 即可。

### 2.2 三份 JSON 没有版本号 —— 「这条判定是哪版规则算的」今天答得了

| 原状 | 现在 |
|---|---|
| 只有 `"$schema_version": "rules-v1"`（**结构**版本名，改内容不变） | `engine_version` = 四个制品 sha256 的确定性折叠 |
| 时间戳 / 哈希 / `generated_at` 全零命中 | `engine-manifest.json` 逐制品记录 `sha256` + 字节数 + 结构计量 |
| `rules-v1.json` 顶层连 `source` 块都没有 | 上游引用单独存，且**标注为声明不是证明** |
| 本目录不是 git 仓库，外部兜底也没有 | `--check` 不一致即硬失败 exit 1 |

实测（验收 V11）：改 `rules-v1.json` 里一个 `severity` 值 →
`engine_version` 由 `f516c14c1a2284fb` 变为 `f45a2bbfb39051c5`；`--check` exit=1；
同内容重算稳定。

**★ 一个我自己漏掉的另一半**：第一版只有数据指纹。**改一行 `judge.py`，`engine_version` 纹丝不动** ——
而契约的形状、聚合的次序、边界声明的措辞全在代码里。ADR-0005 约束 5 列的字段清单
本来就把两者分开写了（`rule_snapshot_sha256` **与** `agent_version`），是我只做了一半。

现在：`engine_version = f516c14c1a2284fb`（数据）· `code_version = 392ed34e34f86ad8`（6 个 .py）。
两者都进回执，**不合并** —— 合并之后就再也分不出「是规则变了还是代码变了」。

**★ 另一件踩到的事**：开发期的验证调用把三条记录写进了正式账本，
**而账本当时没有任何字段能把它们标出来**。回执现已带 `origin`（`cli`/`batch`/`shouheng`）。
已写入的三条**保留并补记 `origin=dev-batchA`**，不删除 —— 删审计记录比留一条标注过的更坏。

★ **一个刻意的区分**：`sha256(本地文件)` 是**证明**（每次重算）；
「`whitelist-v1.json` 来自 `snapshot-20260916T050845Z.json`」是**声明**（没有任何东西校验过）。
两者混在一个字段里，等于把声明洗成证明。所以 manifest 把它们分开存，
`upstream.integrity = "declared"`，且**不参与** `engine_version`。

### 2.3 命中位置被算出来又丢掉 —— 恢复它时踩到一个静默陷阱

```
score.py:92      _find_literal 返回 (i, i+len(term_lower))
score.py:101-102 if _find_literal(...): found.append(kw)     ← 区间在这里被扔
score.py:110     return [f"re:{pat}"], "pattern"             ← 正则只回占位符
```

后果有两个，都直接打到「能否定位到具体位置」：

```
原文   Painlessly pump with high efficiency
旧输出 matched = ['painlessly', 'painless']
       → 原文里根本没有 `painless`（只有 `Painlessly`）
       → 下游拿它回原文搜，**搜不到，而且不会知道自己搜错了**
```

**恢复位置时踩到的陷阱**：匹配在 `text.lower()` 上做，切片在原文上做。
`'İ'.lower()` 是 **2 个字符** —— 小写串的下标与原文下标不再一一对应，
用小写串偏移切原文会**静默切错**，不抛异常，只给一个看起来合理的错片段。

> **处置**：先判等长。等长走恒等映射；不等长回原文重搜；
> **再失败就报 `position: null` 并给出成因**。
> 宁可少报位置，不可错报位置 —— 错位置比没位置更坏，因为它看起来是对的。

实测（验收 V2）：构造用例的 13 处命中、存量语料的 355 处命中，
**片段不变量违反 0 处，定位失败 0 处**。

### 3.2 「本可降级、因词形没补全而成了红线」—— 现在看得见了

```
"… does not treat any disease"  →  T1.1  manual_review   downgraded=True
"… does not cure  any disease"  →  T1.1  auto_reject     downgraded=False
```

**差一个词，从「降级」变成「红线」。** 原因不是规则错：
`does not cure` 在 `context-guards-v1.json` 里是 `status=pending` / `wired=false`，
而 `cannot cure` 是 active。**词表里有这个词 ≠ 它在生效。**

对法务来说，这两条是**两个完全不同的问题**，处置也不同：
前者改文案，后者补词表。旧输出把它们渲染成一模一样的一行 —— 差距就这样消失了。

新契约把它变成果名条目：

```
▸ T1.1.medical-cure  [H01]  L4  auto_reject → auto_reject
    命中原文 @18..22  'cure'  ← 词干 'cure'
    ⚠ 未接线守卫 'does not cure'（status=pending，若接线效果为 (未声明落点)）
       成因：同族已接线（does not treat）—— 词形未补全
```

**但要说清它今天有多少用**：43 条未接线守卫里，只有 **2 条**在存量语料中出现过
（`soulage les engorgements` 4 条、`suction settings` 2 条），
且这两条的**目标规则都没有同时命中**。所以在本语料上，它一次都没改变结论。

> ★ 这个「0」是**语料属性，不是功能属性** —— 存量 289/291 是吸奶器、以 en 为主。
> 换成德语或法语新文案，43 条里的德语/法语条目的暴露面会完全不同。

### 3.3 四条词走错了通道 —— 而且现在才修得动

| 词 | 目标规则 | 问题 |
|---|---|---|

## 5. 本批次做不到的事（七条）

1. **品线维度：机制已就绪，规则数据未填。** 26 条规则里没有一条声明 `product_lines`，
   所以今天传任何品线都不产生过滤。**但这不是「不支持」** —— `Engine.rules_for()`
   已按声明过滤；法务给一条规则加上 `product_lines: ["吸奶器"]`，过滤立刻生效
   （验收 V17c/V17d 用注入声明证明了机制是活的）。
   规则侧口径：不写或写空数组 = 适用全部品线（默认，向后兼容）。
   ★ 这个区分是刻意的：「机制不存在」与「机制存在但你没填」长得一样，
   但前者永远不可能生效，后者只差一次数据录入。让调用方看得见区别，是本条的要点。
2. **未接入落地页正文。** 批次 C 已产出获取与提取能力，通路未建。
   落地页天然带地区/语言属性，而规则库没有这两个维度。
3. **未覆盖图片 / 视频 / A+ 详情页。** 只看文本。
4. **未覆盖地区/平台差异。** 同一条英文文案在 US 与 DE 的合规结论可能不同，
   本引擎给出的是同一个结果 —— 因为它没有地区维度。
5. **零命中的三种成因不区分**（新表达 / 新语种 / 规则边界不清）。
   CATCH-ALL 只答「未覆盖」，不答「为什么没覆盖」。
6. **`evaluability = manual_only` 的 5 条规则仍然报出命中**，只是被升级到 L4。
   机器在这 5 条上不可采信 —— 报出来是为了让法务看见，不是为了让它判。

## 9. 一条把 Q2 的问法本身推翻的实测

**问题原样**：「catch_all（零命中）159 条落 DP3 人工复核，还是 DP4 法务终审？」

测完发现两个选项建立在同一个错误前提上 —— 那 159 条不是同一类东西：

```
$ 逐条看 catch_all 的文本长度
  完全空文本：59 条（37.1% of catch_all）
  有文案：    100 条
```

再往下钻一层，那 59 条**全部**是同一种广告格式：

| 广告类型 | 有文本 | 空文本 | 近 7 天费用（空文本） |
|---|---|---|---|
| **产品广告**（Google PLA / 商品 Feed） | 0 | **55** | **$15,747** |
| 图片需求开发广告 | 83 | 0 | — |
| 自适应搜索广告 | 84 | 0 | — |
| 视频需求开发广告 | 31 | 0 | — |
| 自适应视频广告 | 6 | 0 | — |
| 加大型动态搜索广告 | 3 | 0 | — |
| （广告类型为空） | 25 | 4 | $0 |

PLA 是商品 Feed 广告，本来就没有 Primary Text / Headline。

### 9.1 这条实测同时改掉了三个数字

| 指标 | 修正前 | 修正后 | 差在哪 |
|---|---|---|---|
| 空白清单压力（规则缺口候选） | 159 条 · **54.6%** | **100 条 · 34.4%** | 差 59 条结构上不可判的记录 |

## 10. ESC-003 的立论被自己的实测推翻

**问题原样**：「ESC-003（跨一级主题共现 → 法务）要不要启用？它是本表里唯一会主动给法务加单的规则。」

测量分两步，第二步才是关键：

| 步骤 | 结果 |
|---|---|
| 触发面：「≥2 个不同一级主题」 | 291 条中 **28 条（9.6%）** |
| 其中本来就已经落 DP4 的（ESC-001/002） | **23 条** |
| **纯新增法务单** | **5 条**（DP4 31 → 36，+16%） |

成本很低（+5 单）。**但它抓错了东西。** 实测的跨主题组合：

```
T2+T3+T7 ×12 · T2+T3 ×5 · T2+T5 ×4 · T2+T7 ×3 · T3+T7 ×2 · T2+T8 ×1 · T5+T7 ×1
```

纯新增的 5 条样例：

- `More Milk（T2.1.1）+ 28% faster（T2.3.1）+ Don't Miss（T8.1）`
- `Momcozy Official | S12 Pro Quick | On Sale | Best-Value`

这些是「效果声明 + 促销紧迫性」的**普通多主题广告**，不是新表达模式。
原立论说「跨主题共现通常是新表达模式」—— 实测说明：**一条广告同时说效果和打折就会触发它**，
那不是规则空白信号，是「广告通常不止说一件事」。

★ 所以关闭它的理由不是成本，是**代理指标与它声称测量的东西不相关**。
若将来确实要「机器主动找空白」，正确的形状是规则**显式声明**要升级
（ESC-001 已经是这个形状），而不是由主题计数推断。

## 11. 两个「L」：一个只有把输出打出来才看得见的冲突

改 ID 之前，同一份判定结果里长这样：

```
verdict.severity = "L4"      ← 规则的风险等级（severity.py 的 L0–L5 六档）
verdict.layer.id  = "L2"      ← 处置层（谁必须处置它）
```

**两者语义相反**：severity=L4 是「这条规则最危险」，layer=L2 是「机器可以自己拦」——
而一条 severity=L4 的红线规则产出的**正是** layer=L2。

| 若下游把字段取错 | 后果 |
|---|---|
| 把 `L4` 当成 layer | 以为法务已经看过这条 |
| 把 `L2` 当成 severity | 以为风险很低 |

★ 这是一个**读代码看不出来、只有把完整输出打出来才撞上**的冲突：
两个字段在源码里相隔 400 行，各自都有正确的注释。
而「字段都叫 L、数字还不一样」这种事，只有在**同一份产物**里并排出现时才成立。

处置：层级 ID 改 `DP1–DP4`（新增 `DP0`），风险等级 `L0–L5` **一字未动**
（它来自设计文档 §4.2.1 的六档校准，写进 26 条规则，改它才是贵的那个）。
`DP` 前缀在本项目全部制品中实测出现 **0 次**。

## 12. FDA 两个词的实测代价是 0 —— 正因如此更不能按代价判

```
$ 在 291 条里数 `FDA registered` / `FDA 注册`
  命中：0 条
```

于是「维持同带」与「移出放行带」在**账面上完全等价**。
但两者说的是不同对象：

| 词 | 指的是 | 能否独立复核 |
|---|---|---|
| `FDA cleared` | 510(k) 实质性等同 —— **器械层**状态 | 可查 K 号 |
| `FDA registered` | establishment registration —— **企业/设施层**状态 | 可查注册号 |

FDA 的注册与列名数据库声明写明：注册**不表示**对该机构或其器械的批准、许可或授权
（并见 21 CFR 807.97）。D2 放行的理由是「作者写出了 `cleared`，说明他分得清
approved 与 cleared」——而「同一段里写了 FDA 注册」证明不了这件事。

**构造正对照**（存量碰不到，所以必须构造）：

| 输入 | 改前 | 改后 |
|---|---|---|
| `FDA approved … FDA cleared.` | auto_pass | **auto_pass**（D2 逐字未变） |
| `FDA approved … FDA registered facility.` | auto_pass | **manual_review**（收紧） |
| `FDA approved … FDA 注册.` | auto_pass | **manual_review** |
| `FDA approved. FDA cleared. FDA registered.` | auto_pass | **manual_review**（降级优先，保守） |

★ 需要点明的一处张力：D3（同一天）把 `FDA 注册` 迁**进**白名单表，D9 让它回到**降级通道**。
这不是推翻 —— D3 修的是「登记在哪张表」，D9 定的是「它该在哪个通道」。
叠加后：词仍在白名单表（可独立复核为真），通道是降级。
**只看 D3 的 diff 会以为它被放行了；只看 D9 的 diff 会以为 D3 被撤销了。**

## 13. 一个「跑一次对、跑两次错」的同步工具

D11 执行飞书同步时踩到的，不是词表问题，是**工具问题**：

```
第一次运行：  ✅ 写入 85 行 / 30 行 / 4 行       ← 完全正确
第二次运行：  ✅ 写入 85 行 / 30 行 / 4 行       ← 输出一模一样，而表里每行变成两份
验证脚本：    ✅ 飞书 89 条 · 字段不符 0          ← 它比的是**集合**
```

实测后果：守卫表 **174 行**（85 词）、白名单表 **56 行**（30 词）、说明表 8 行（4 行）。

两条缺陷必须同时存在才构成这个形状：

1. `migrate_vocab_to_lark.py` 用 `batch_create` —— 那是**追加**，不是替换；
2. `verify_vocab_lark.py` 用 `{词: 字段 for r in fetch(...)}` 建索引 ——
   **同一个词的第二行被静默覆盖**，于是重复在验证里不存在。

★ 合起来的效果是：**工具宣称的「已同步」在第二次运行时无法被它自己的工具证伪。**
而业务看的就是行数 —— 逐词比对一致的表，在飞书里是一张每行都有两份的表。

已修两处并重建：

| 修法 | 位置 |
|---|---|
| 非空表**拒绝**写入，重建必须显式 `--force` | `write_rows()` 的前置闸门 |
| 数行数、列重复词、**让重复导致验证失败** | `verify_vocab_lark.py` |

```
$ python3 tools/migrate_vocab_to_lark.py --apply --force
   ✅ 写入 85 行（写前 0 行）· 30 行 · 4 行
$ python3 tools/verify_vocab_lark.py
   本地 85 词 ｜ 飞书 85 行（唯一 85 词）· 重复行 0 词 · 仅本地有 0 · 仅飞书有 0 · 字段不符 0
   结论：✅ 飞书与本地逐词一致（回读值，非写入返回码）
```

## 16. 取证：一个地址有据可用，一个只有名字

| 人 | 角色 | 飞书 open_id | 怎么来的 |
|---|---|---|---|
| **Roxie（余玉珊）** | 广告账号负责人（12 个账号，含空账号那一桶） | `ou_dd3f9a2e…d6149a` | KB 快照的人员字段：`creative__平面_日常需求看板.json · records[4].fields.需求人[0]`，同一 id 另见 4 个文件（创意支持_项目需求 / 视频_日常需求看板 / 国庆前后_考勤值班计划）|

★ **一个容易搞错的点：open_id 是应用内标识。** 换个应用读同一个人会得到另一个值，
所以「从别处抄来的 open_id」不能直接用。Roxie 这个之所以可用，是因为那份 KB 快照
**由本应用自己读的**（`tools/kb_snapshot.py`，identity 写明 `app: 守衡`）。
这一点如果搞错，表现是「表填好了、发送静默失败」—— 又一个「看起来在用」的状态。

★ 想按邮箱现查 Rikka 也不行：应用缺 `contact:user.id:readonly`，`batch_get_id` 实测返回
`99991672`。所以她的地址只能由人来给（Q16），而**表里写的是「（未定）」+ 指向 Q16，不是留空** ——
留空与「已备好」在文件里长得一模一样。

## 20. 这一批我自己犯的两个错（都写进 ADR §七 16–17）

1. **四条「反向对照」是假的，而它们全绿。** `_o_e = _tmp_owners(...)` —— 那个函数没有返回值，
   于是 `--owners` 永远拿到生产表，四条对照跑的全是正面路径。跑出来 `exit 0` 时我第一反应
   是「工具没改对」，查下去才发现是**对照自己在偷懒**。现在输入与写入分成两行，写错就红。
2. **V36d 曾是一条恒真检查**，而它守的正是「未映射即硬失败」这个最关键的行为：
   原判据 `(a and b) or c` 里 `c` 就是 `退出码 == 0`。它从未红过，**恰恰因为要防的事从未被造出来过**。
   反向对照现在用临时账本 + 临时映射表真造条件。

## 26. 姓名不是地址：把「看不见」证明成结论，而不是当成结论

Owner 对 Q16 的回答是一行「她的名字是：林建纯」。名字我早就有了，缺的一直是 `open_id`。
于是本轮做的事情只有一件：**把「按姓名找人」的通道逐条走到尽头**，然后
把「找不到」这件事本身变成可复验的结论。

八条通道的实测结果：

| 通道 | 结果 |
|---|---|
| `contact/v3/users`（列成员） | `99991672` 缺 `contact:contact.base:readonly` |
| `contact/v3/departments/0/children` | `99991672` 同上 |
| `contact/v3/users/{open_id}`（id → 姓名） | `99991672` 同上 |
| `contact/v3/users/batch_get_id`（邮箱 → id） | `99991672` 同上 |
| `search/v1/user`（按姓名搜人） | `99991634` 需 user token |
| `im/v1/chats` | 仅 1 个群、3 人（刘华丽 / 李倩怡 / 周健），不含她 |
| `created_by` / `last_modified_by` | 响应里**恒为 null**（字段不可用） |
| `drive/v1/metas` 的 `owner_id` | 只有 id、没有姓名，无法反查 |
| **人员字段（bitable `type=11`）** | ✅ 唯一同时给出 姓名 + 邮箱 + open_id 的通道 |

于是有了 `tools/lark_people.py`：它做**值形状**扫描（不猜字段类型），从 8 个底座 41 张表
5042 条记录里采集出 **35 人**字典（`_data/lark-visible-people.csv`，带采集时间与 app id）。
她不在其中 —— 她只出现在**文本**字段（材料收集表「来源人」= 林建纯（Rikka）），而文本字段没有 id。

```
$ python3 tools/lark_people.py --find 林建纯
可见人员字典：35 人 · 底座 8 · 数据表 41 · 记录 5042
阳性对照：✅ 锚点 余玉珊 可解析，字典 35 人
❌ 本应用看不见 林建纯（退出码 2）

$ python3 tools/lark_people.py --find 余玉珊      # 阳性对照：同一条命令能找到人
✅ 可送达：余玉珊 → r***@rootglobal.net · ou_dd3f9a2e…
```

★ **这一对的写法是关键**：只有「找不到」是结论，「找得到」是它的前提。
`resolve()` 在字典为空时**无论调用方传什么**都返回 `unverifiable` —— 阴性结论不许建立在空输入上。
（原因见 ADR §七 22：我上一轮用恒为 null 的字段扫了 6000+ 条记录报「零命中」。）

★ 还有一句必须写清：**「本应用看不见」不等于「此人不可送达」**。飞书里当然有她的 open_id；
缺的是应用侧读取权限，或一次可观测信号。前者可修，后者才是结论。四条可修的路在 Q17。

顺带暴露的第二个缺口：`www.amazon.de`（`/dp/B0G1MW5TB6`，1 条 URL）那一行责任人写的是**「（未定）」**。
D19 只定了「广告账号 → Roxie、独立站 → Rikka」，亚马逊站内商品页两边都不完全对口。
现在没有发现指向它，所以不阻塞；但它是一行**没有主**的路由目标，记 Q18。

## 28. 「暂不填」落地：把待办改造成决定

Q17 的四条路里 Owner 选了 **D（暂不填，站点侧只记录、不送达）**，落成 **D23**。
执行的重点不在「不动表」，而在**改语义** —— `（未定）` 原来是「等一个人填」，现在是「已决定不填」。

| 位置 | 改成什么 |
|---|---|
| `site-owners.csv` 10 行备注 | 「按决定留空（Q16 → Q17 → D23）」+ 穷举与工具出处 |
| `整改路由-页面侧.csv` 4 行 | 「★ 不可送达（**已决定，非待办**）……」 |

（dB 42 vs 48、认证词 CE vs FDA）**不会被任何人收到** —— 价值只剩「记录在案」。
同时写明 `$reversible`：填上地址即自动恢复送达（`deliverable` 只看地址形状），
