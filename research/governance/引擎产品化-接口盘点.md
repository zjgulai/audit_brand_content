## 三、版本与指纹：今天能不能回答「这条判定是哪版规则算出来的」

### 3.1 三个 JSON 里有什么 【实测】

| 文件 | 版本类字段 | 行 |
|---|---|---|
| `rules-v1.json` | `"$schema_version": "rules-v1"` | `2` |
| `whitelist-v1.json` | `"$schema_version": "whitelist-v1"`；另有顶层 `source` 块，含 `snapshot` 文件名 | `2`、`23` |
| `context-guards-v1.json` | `"$schema_version": "context-guards-v1"`；另有顶层 `source` 块 | `2`、`35` |

- **`$schema_version` 是结构版本名，不是内容版本**；三份都不是 `-v2`，改内容不会改这个字符串。**【推断】**
- **三份都没有时间戳、内容哈希、`generated_at`、`revision`**：`grep -i -E '"(version|timestamp|generated_at|hash|sha256|fingerprint|content_hash|updated_at|built_at)"'` 对三份文件**零命中**。
- `rules-v1.json` **顶层连 `source` 块都没有**（`grep '^  "source"'` 空）；文件内 29 处 `source` 全是规则级 `source_legacy`（26）+ `source_citation`（1）。其 `$note` 自述：「本文件是手工维护的判定源，score.py 只读不写」。

### 3.2 指纹存在，但停在上游 【实测】

`research/live/LATEST.json`：`"boundary_rules": { "read_count": 21, "api_total": 21, "content_sha256": "2a1a219a7e76b459…" }`；计算逻辑在 `tools/live_snapshot.py:100-112`（「内容指纹：只取 fields + record_id，按键排序后哈希」→ `hashlib.sha256`）。
**但三份本地判定 JSON 里没有任何 `content_sha256`。** 本地判定文件与飞书快照之间**只有 `whitelist`/`context-guards` 里的 snapshot 文件名（弱引用），`rules-v1.json` 连这个都没有**。

### 3.3 项目自己的要求 vs 现状

- `ADR-0002:53` 要求知识单元带 `snapshot_sha256`；`:61`「**必须带快照指纹。** 没有 `snapshot_sha256` 的知识单元**不得进入任何报告或 Agent 的判定依据**」。
- `ADR-0005` 约束 5 要求 receipt：`run_id` / `input_sha256` / `rule_snapshot_sha256` / `agent_version` / `model`，并写明「**没有 receipt 的判定不算发生过。**」
- **`score.py` 的产物里当前一项都没有。**【实测】

### 3.4 「同输入重跑结果逐字一致」—— **满足** 【实测】

`python3 score.py` → md5 `8da081c00df962ef85a5f8c69dd9ed74`（2644 字节），两次 `diff` 为空；`--json` → md5 `c6c969e7bf36e4f22ad7f23241ba0a69`（3406 字节），两次 `diff` 为空。无随机/时间依赖：`grep -E 'random|shuffle|time\.|datetime|now\(\)|uuid'` 对 `score.py`/`vocab.py`/`severity.py` **零命中**。字典序依赖已处理（`score.py:127` `sorted(vocab.downgrade_of(...))`、`276-277` `sorted()`、`364`、`424`）。

**结论：可复现性成立，可追溯性不成立。** 今天能答「结果一模一样」，**不能**答「这是哪版规则算出来的」——无版本号、无指纹，且**本目录不是 git 仓库**（`git rev-parse` → `fatal: not a git repository`），连外部兜底都没有。**【实测】**

### 5.2 `catch_all` 的结构与语义（`rules-v1.json:1256-1268`）【实测】

```json
"catch_all": {
  "rule_key": "CATCH-ALL-01", "topic": "L0", "topic_label": "未覆盖",
  "modality": "escalate", "severity": "L0", "disposition": "manual_review",
  "evaluability": "n/a", "trigger": "no_rule_matched",
  "reason": "未命中 ≠ 合规。不拆 `未覆盖` 与 `合规`，盲区率在数学上不可观测。",
  "evidence": "设计文档 §5.1 / §B（…）；NIST AI RMF MEASURE 3.2；Ofcom Step 2",
  "$note": "★ 这是 P0-1 的落地实现。它与「命中了但结论是通过」的责任归属完全不同。"
}
```
- **语义**：不是规则，是一条**兜底通道**；`trigger: "no_rule_matched"`。
- **实现方式**：`Engine` 只在构造时存下它（`score.py:143`），判定时**不使用** —— `assess` 直接用 `len(hits)==0`（`score.py:206`）。`CATCH-ALL-01`/`severity:"L0"`/`disposition:"manual_review"` **从不进入 `Hit`**。
- `severity.py:112-115` 有专门 catch-all 告诫文本，但其 `is_catch_all` 是 keyword-only 参数，`score.py:319` 只传两个位置参数 → **`caveats` 里永远不会有 `catch_all:…`**。
- `report` 输出 `CATCH-ALL 命中 159 条（54.6%）`，并打印「这些是**未覆盖**，不是合规」（`score.py:356-357`）。

### 5.3 有没有定义 disposition → 人工程序的对应关系？

**没有。**【实测】

- 全仓检索 `业务自审` / `工具预审` / `法务终审`（限 `*.md *.py *.json *.csv`，排除 `node_modules`、`_evidence`）：**零命中**。检索 `分层判定|人工程序|四道|审核流程` 于 `ADR/*.md` 与 `skeleton/*.md`：**零命中**。
- ADR 对 `disposition` 的提及全是**通道语义**，不是「谁来做」：`ADR-0008:73`「接线校验：豁免目标须落在 `effect→auto_pass` 的带里」；`ADR-0009:65-66` 把词分到 `auto_pass` 带 / `manual_review` 带。
- 最接近的人工程序定义在 **ADR-0005**，但那是 **Agent 输出侧的三值建议**，不是 disposition 映射：`ADR-0005:46` `suggestion: 直接发布 | 转人工 | 需修改     # 建议，不是决定`；`:60-65` 约束 2 规定 Agent **不能**改状态为 `无需处理`，只能新增 `agent_suggestion`/`agent_evidence`/`agent_unknowns`，人的字段（`处理状态`/`检查人`/`修改建议`）**只读**；`:74-75` 约束 3 规定未命中时「分流建议**不得是**『直接发布』，只能是『转人工』」。
- 需求侧只有一句粗粒度流程：`PRD/内容治理需求文档.md:20`「**核心解法**：建立 **"AI Agent初筛 + 北美人工复核"** 的内容审查机制」—— **两段，不是四段**，且未与 `auto_reject/manual_review/auto_pass` 建立映射。

**结论：`disposition` 目前只有「机器通道」语义（放行/降级/拒绝），没有「业务自审 / 工具预审 / 人工复核 / 法务终审」的分层定义。这一层完全缺失。**


## 三件最容易搞错的事

**1. `Engine.assess()` 根本不碰记录结构 —— 容易以为整个引擎都绑死在快照上。**
`score.py:179` 的签名就是 `assess(self, text: str)`，全仓调用点（`249`、`314`）传的都是 `rec_text(r)` 的结果。**绑死快照的是 `report()`/`audit_channel()`/`rec_text()`（`score.py:232-233,251,318,325,397`），不是引擎。** 产品化的主要工作量在**输出契约**，不在解耦数据源。

**2. 「白名单独立成表」已做完，但白名单今天对判定没有任何影响 —— 两层之间断线了。**
`vocab.py:96` 老实地把 active 白名单词装进 `V.pass_bands`，`score.py:439` 还把它打印出来（「放行带 8 词次」），但 `Engine.assess` 只调 `downgrade_of()`（`score.py:127`），`pass_of()`（`vocab.py:64`）**零调用者**。实测 `assess("FDA cleared wearable breast pump")` 返回 **0 条命中**（该规则关键词是 `FDA approved`/`FDA certified`，`fda cleared` 只在 `pass_bands` 里）。所以 `score.py:197-200` 那两条 `→ auto_pass` 分支目前**不可达**。看到「放行带 8 词次」极易以为放行在生效。

**3. 否定句会误报，且结论取决于一个 `status` 字段 —— 差一个词，从「降级」变「红线」。**
实测同句式：`"… does not treat any disease"` → `T1.1.medical-cure` `disposition=manual_review`，`downgraded=True`，`downgrade_terms=['does not treat']`；而 `"… does not cure any disease"` → 同规则 `disposition=auto_reject`，`downgraded=False`。原因：`load_vocab` 只装 `status == "active"` 的守卫（`vocab.py:82`），而 `does not cure` 在 `context-guards-v1.json:265` 是 `pending`/`wired: false`（同表 `can't cure` 在 `:133` 是 active）。**词表里有这个词 ≠ 它在生效** —— 这正是 `context-guards-v1.json` 的 G5 不变量提醒的事（「wired=false 的守卫不计入失败，但必须逐条给出 wire_gap 成因」），该表 `stats` 自述 89 条守卫中 46 条已接线、43 条未接线。
