## 2. 规则库怎么定义

### 2.1 三层结构总览

**[判断] 规则库由三层构成，不是四个维度的乘积：**

```
┌─────────────────────────────────────────────────────────────┐
│  第三层：风险级（Risk Tier）                                  │
│  GARM 风险框架的 4 级 + 2 个扩展档；由 severity × exposure 查表得  │
│  ★ 它不参与"规则存不存在"，它决定"命中之后怎么办"              │
└─────────────────────────────────────────────────────────────┘
                            ▲
                            │ 挂载
┌─────────────────────────────────────────────────────────────┐
│  第二层：正交属性（Orthogonal Attributes）                    │
│  ┌──────────┬──────────┬──────────┬──────────┬──────────┐   │
│  │ 平台      │ 辖区      │ 语种      │ 内容形态  │ 渠道      │   │
│  │ platform │ jurisdiction│ language│ form     │ channel  │   │
│  └──────────┴──────────┴──────────┴──────────┴──────────┘   │
│  互相正交、可独立取值、可缺省（null = 不关心这一维）           │
│  ★ 它们是"属性"不是"分区键"——不物化乘积                       │
└─────────────────────────────────────────────────────────────┘
                            ▲
                            │ 引用
┌─────────────────────────────────────────────────────────────┐
│  第一层：主题分类（Aboutness Taxonomy）                       │
│  一套树：医疗功效 / 效果数据 / 背书 / 对比 / 安全 / 促销 …     │
│  规则挂到主题节点上，沿树继承                                  │
│  ★ 规则的"身份"在这里，不在作用域里                            │
└─────────────────────────────────────────────────────────────┘
```

**三层各自的职责**（这是整个设计的核心，务必区分）：

| 层 | 回答什么问题 | 变化频率 | 谁维护 |
|---|---|---|---|
| **主题分类** | **这条规则在说什么？** | 低（半年一次） | 规则库负责人 |
| **正交属性** | **它在什么情况下适用？** | 高（每进一个新市场/平台就变） | 运营 + 规则库负责人 |
| **风险级** | **命中之后怎么办？** | 中（每季度校准） | 合规负责人 |

**[判断] 这三层必须分开的原因**：它们的**变化频率差一个数量级**。作用域（第二层）每进一个新国家就变，主题（第一层）半年才动一次。如果混在一张表里，**每次扩区都要复制规则行** —— 这正是原方案 `适用产品` 写死 5 个型号所暴露的问题的组织版本。

### 2.2 第一层：主题分类

#### 2.2.1 现有 21 条规则的主题归类

**[判断]** 现有规则已经隐含了一套主题分类（编号前缀 H / M / U），只是没有被显式建模：

| 现有前缀 | 主题 | 条数 | 说明 |
|---|---|---:|---|
| **H** | 高风险声明类 | 9 | H01 医疗功效 / H02 增产 / H03 临床背书 / H04 专家背书 / H05 绝对化安全 / H06 认证表述 / H07 疼痛功效 / H08 竞品对比 / H09 智能仿生 |
| **M** | 中性表述类 | 7 | M01 静音 / M02 吸力 / M03 效果数据 / M04 促销话术 / M05 等级背书 / M06 模糊对比 / M07 效率漏奶 |
| **U** | 待核实类 | 4 | U01 顾问头衔 / U02 保险 / U03 医院场景 / U04 疼痛场景 |
| 其他 | 白名单 | 1 | 安全词 |

**[判断] 这个前缀分类是有效的，但有一处问题：H/M/U 混合了两个不同的切分依据。**

- H 和 M 按**严重度**分（红线 vs 审慎）；
- U 按**判定确定性**分（需人工核实）。

这是**两个轴**混进了一个轴。按 §2.1 的三层结构，正确做法是：

```
主题分类（第一层）应该只按"在说什么"分：
  T1 医疗功效声明
  T2 效果/功效数据声明
  T3 权威背书
  T4 比较性声明
  T5 绝对化表述
  T6 认证与资质表述
  T7 场景与人群表述
  T8 促销与紧迫性
  T9 产品参数表述

严重度（第三层）独立表达：L0–L5
判定确定性（规则元数据）独立表达：evaluability
```

**[判断] 映射关系**（现有规则 → 新主题分类），这一步是把现有资产接进新模型：

| 新主题 | 现有规则 | 主题定义 |
|---|---|---|
| **T1 医疗功效声明** | H01, U04 | 声称治疗/治愈/诊断/预防疾病，或描述病理性场景 |
| **T2 效果与数据声明** | H02, M03, M07 | 声称产品带来可量化的生理/性能结果 |
| **T3 权威背书** | H03, H04, U01 | 引用临床、专家、机构、认证作为可信度来源 |
| **T4 比较性声明** | H08, M06 | 与竞品或行业基准的对比 |
| **T5 绝对化表述** | H05, M01, M02 | 无上限的形容（最/零/完全/所有） |
| **T6 认证与资质** | H06, M05, U02, U03 | 对监管状态、等级、报销资质的陈述 |
| **T7 智能与仿生宣称** | H09 | 声称系统具备识别/模拟/闭环能力 |
| **T8 促销与紧迫性** | M04 | 限时、稀缺、催促 |
| **T9 产品参数** | （安全词） | 客观可测的结构/性能参数 |

> **注**：T9 对应现有的「安全词白名单」。**它是一个主题，不是一张白名单**。这个改动很重要 —— 它让「为什么这些词是安全的」变成一个可回答的问题（因为它们属于「客观可测参数」这个主题），而不是一份凭经验收集的清单。

#### 2.2.2 主题树的形状

**[判断]** 主题分类是一棵树，深度建议 **2–3 层**（不用更深）：

```
T2 效果与数据声明
├── T2.1 生理结果声明（→ 人体结果，需临床级证据）
│   ├── T2.1.1 奶量提升
│   └── T2.1.2 疼痛缓解
├── T2.2 机器性能声明（→ 产品测试即可）
│   ├── T2.2.1 效率/速度
│   └── T2.2.2 吸力/档位
└── T2.3 数据来源声明（→ 关于"证据本身"的声明）
    ├── T2.3.1 未标注来源
    └── T2.3.2 来源不可复核
```

**[判断] T2 拆成 T2.1 / T2.2 是整个设计里最重要的一次拆分**，依据是本文 §2.5 实测到的 `28.2%` 问题：

> 同一个 `28.2%`，在 5 个产品上被用来支撑**三种不同量纲的声称**：泵送效率（机器）、泵送速度（机器）、奶量产出（人体生理结果）。而它们的证据要求**完全不同**：
> - 机器指标 → 产品测试数据即可（不需 RCT）
> - **人体生理结果 → FTC HPCG 2022 p.13 要求 RCT**
>
> 写成同一个数字，属于 FTC HPCG 2022 Example 18 的同类问题：**测试对象与声称对象不匹配**。

**现有规则库无法表达这个区别** —— 因为 H02 把 `increase milk supply` 和 `improve pumping efficiency` 放在**同一条规则**里，共用一个严重度。R5 曾建议「H02 增加『声称对象』子字段」，本质就是这个拆分。

#### 2.2.3 主题分类的行业对照

| 体系 | 顶层数 | 深度 | 对本文的用法 |
|---|---:|---:|---|
| **IAB Tech Lab Content Taxonomy 3.1** | 37 | 4 | **主题分类的参照系**（R6） |
| Meta Community Standards | 27 | 1（平铺） | 证明「平铺」可行，但只适合少量条款（R1 §2.1） |
| GARM Brand Suitability | 11 | 1 | **风险级的参照系**，不用于主题（R6） |
| 现有 H/M/U | 3 | 1 | 有效但混合了两个轴，需重组 |

**[判断]** 建议不直接采用 IAB 的 37 个顶层 —— 它面向**广告投放环境**（aboutness of content），颗粒度与审核规则不匹配。**采用它的结构（树 + 正交属性），不采用它的节点。**

### 2.3 第二层：正交属性

#### 2.3.1 五个正交属性

| 属性 | 取值 | 缺省语义 | 现状 |
|---|---|---|---|
| **`platform`** 平台 | Google / Meta / Amazon / TikTok / 官网 / 独立站 … | `*` = 全平台 | 已有（记录表的 `平台` 列） |
| **`jurisdiction`** 辖区 | ISO 3166-1 国家码 + `GLOBAL` + 次国家级（`US-CO`） | `GLOBAL` | 已有但取值不规范（`欧洲DE` 与 `DE` 并存） |
| **`language`** 语种 | ISO 639-1 | `*` = 全语种 | 已有（`文案语种`）**但规则侧完全空缺** |
| **`form`** 内容形态 | `text` / `image` / `video` / `landing_page` / `listing` / `ad_copy` | `*` | **缺失** |
| **`channel`** 渠道 | `paid` / `organic` / `owned_site` / `marketplace` | `*` | **缺失**（用 `平台` 兼职） |

#### 2.3.2 三条设计规则
**规则 1：正交属性不物化乘积。**

IAB 的原文是决定性的：

> **[原文]**（R6 引用 IAB `implementation.md`）
> 风险级「encoded in an **orthogonal vector** accordingly, allowing 'risk' to be associated with a 'topic' **dynamically**」

**[判断]** 「orthogonal vector」（正交向量）这个用词是有意的：**属性是附加的、独立的，不是相乘的**。四维笛卡尔积的 5 产品 × 8 国家 × 3 平台 × 4 内容类型 = 480 个格子，而实际每条规则只关心其中一两个 —— **用乘积存储稀疏矩阵是经典的存储反模式**（R3 §11.2 理由 1）。

**规则 2：允许 `null`（未指定）。**

SPECIAL 项目（H2020）的五元组授权模型明确允许元素为 `null` —— 其 Example 1 里 `storage` 位就是 `null`（R3 §11.2）。**[判断] 笛卡尔积模型无法表达「这一维我不关心」**，这是它最致命的表达力缺陷。

**规则 3：互斥性用显式约束，不靠维度天然正交。**

「内容形态 = 视频」在「平台 = 小红书」上无意义。**[判断]** 这类约束**必须在属性层显式声明**，而不是指望维度之间天然不冲突。ODRL 的 `xone`（有且仅有一个满足）与 `andSequence` 正是为这类约束准备的。

#### 2.3.3 辖区属性：为什么它特殊

**[判断] 辖区与其他四个属性有一个本质区别：它会改变规则的身份。**

R1 §4.7 的发现是决定性的 —— Google 的规则**名字里就带辖区**：

```
Update to Gambling and Games Policy: Global (August 2026)
Update to Gambling and Games Policy: Colorado, USA (June 2026)
Update to Gambling and Games Policy: France (June 2026)
Update to Gambling and Games Policy: Ireland (May 2026)
```

**[判断]** 这不是命名习惯，是因为「Gambling: France」与「Gambling: Global」**是两条会被分别修订、分别失效的规则**。

R3 给的旁证更锐利：**DPV（W3C 社区组最终报告）处理「同一概念在 N 国有 N 套规定」的做法，是给每个辖区一个独立命名空间（ISO 3166-2），而不是给概念加 `jurisdiction` 字段。**

**所以辖区的处理是双轨的**：

| 情形 | 做法 | 例子 |
|---|---|---|
| 规则的**结论**因辖区不同 | **拆成两条规则**，辖区进 `rule_key` | `T1.medical-claim.US` / `T1.medical-claim.UK` |
| 规则的**适用范围**覆盖多个辖区 | 用一个 **辖区组**（`EU` / `GLOBAL`） | `T2.2.1.efficiency.EU` |

**四条可直接搬运的规则**（R1 §4.7 原样给出）：

1. **辖区是规则身份的一部分** —— 规则 ID 构造为 `<主题>.<辖区>`，而不是 `规则 { jurisdiction: 属性 }`
2. **必须存在 `GLOBAL` 这个取值**，与具体国家并列（Meta 的 `Global restrictions` 报表、Google 的 `…: Global` 条目都证实）
3. **辖区可以是次国家层级**（`Colorado, USA`、`Alberta, Canada`）
4. **辖区差异的成因要写出来** —— Google 写 `to align with the current regulatory landscape`，即变更理由必须指向一个外部法律事件

#### 2.3.4 ★ 实证补充：真实系统里，这五个属性各自住在哪（R7-W2 §4）

**[判断] 上面五个属性是「设计上应该怎么建模」的答案。R7-W2 另外做了一件事：横剖真实系统，看这些维度**实际住在哪里**。结论对委托方有直接影响 —— 因为「结构上应该建模成属性」与「真实系统把它放在哪」不是一回事。**

**① 四维笛卡尔积在真实系统里不存在；唯一接近二维矩阵的样本只有两轴。**

最强的采用者是 **Stripe** 的 `Jurisdiction-specific prohibited businesses`：对 Indonesia 与 Thailand 使用显式图例 `(Prohibited = P, Restricted = R)`，**轴是「法域 × 业务类型」，单元格值是「处置」**。

> **[判断]** 同一条业务在两国可以取值相反（`Domestic charter air travel` 在 Indonesia = P、在 Thailand = R）。**这是全份证据里唯一的二维判定矩阵，而它只有两轴** —— 不是四轴，也不是笛卡尔积。

> **★ R7-W2 明确记录：未找到任何「国家 × 违规类型」矩阵。** 「四维笛卡尔积」是**客户设想的形态**，不是行业既有形态。这不否定本文 §2 的三层模型（它本来就不主张物化乘积，见 §2.3.2 规则 1），但**它意味着委托方无法从任何同行那里抄到四维结构**。

**② 「国家」在真实系统里的位置是「文档伺服层」与「正文限定词」，不是规则模型的字段。**

六种表达形态按结构化程度排序（R7-W2 §4.1）：

| 形态 | 采用者 | 结构化程度 |
|---|---|---|
| 法域子树 | Stripe（11 个法域节点） | 最高 |
| 「处置强度 → 国家集合」两列表 | Google | 高 |
| `See ISO-3166-1-alpha-3` 外键 | IAB | 高 |
| 正文散句 | Meta、**TikTok（14 处）** | 低 |
| URL 分区但正文无标记 | TikTok | 低 |
| **法域完全移出规则树** | **YouTube（12 个政策文件地区关键词命中 = 0）** | — |

> **[判断] 最尖锐的一条**：**「作用域在 URL/分区上」≠「作用域在规则模型里」。** 连最结构化的 Stripe 都在两种形态之间摇摆 —— 它同时用法域子树**和**行内法域指针（`Specific prohibitions apply in India, United Arab Emirates, and Thailand`）。

> **[判断] 委托方可以直接用的一个判据**：本文 §2.3.3 说「辖区会改变规则的身份」，这仍然成立；但**不要因此认为辖区必须是一个独立字段** —— 真实系统里它常常是**文档的伺服维度**（同一规则的不同辖区版本分开托管），而不是数据库的一列。**两种做法都可行，选择取决于委托方是否需要跨辖区做统计**（若需要按国家聚合命中率，就必须是字段；若只需要正确执行，目录分区即可）。

**③ 「内容类型」不是规则判定维度 —— 未找到任何「模态 × 违规类型」判定矩阵。**

> **[原文]**（Google，**四模态写在判定句的主语位置**）
> `Text, images, audio, or video that can be interpreted as suggesting sexual intent`

> **[判断] Google 的做法是「一条标准覆盖四模态」，不是「四套标准」。** Amazon DSP 则是让模态决定**可用的过滤维度**（app vs streaming TV/audio）—— 也是**能力开关**，不是**判定阈值**。

> **★ 对委托方的直接含义**：本文 §2.3.1 的 `form` 属性**仍然需要存在**（因为委托方确实要问「这条规则管不管落地页」），但**不要指望为每个模态设不同的违规阈值** —— **没有行业先例**。R7-W2 的措辞是：若客户确实需要按模态给不同阈值，**这是客户特有的需求缺口，无行业先例可引**。

**④ 「平台」与「品类」不是两根独立轴；「品类」在四家系统里有三个名字、三种后果。**

| 系统 | 品类叫什么 | 后果 |
|---|---|---|
| Amazon Ads | `category` | **投放时申报的判定输入** |
| Google | `industry` | **申请制，决定资格** |
| Meta | `Special Ad Category` | **限制定向工具** |
| Stripe | `business type` | **决定准入路径：硬墙 / 加流程 / 人工通道** |

> **[判断] 共同规律是「品类 → 准入路径」，不是「品类 → 判定阈值」。** 这条对委托方有实质影响：**母婴品类在平台侧的作用是决定「你能怎么投」，而不是「你的文案能被判多严重」** —— 后者才是委托方关心的，而**它不在平台政策里，在法源里**。这解释了为什么 §2 的三层模型把 `topic` 与 `severity` 分开。

**⑤ 一条关于本文方法论的诚实说明**：「最小团队规模」这一列，R7-W2 **五个方案全部未找到任何一手人数证据**。可用的只有复杂度代理指标（Meta 27 节 ≈780 条 / IAB 704 节点 / Stripe 11 法域节点 / DAPRECO 966 条）。**因此 R7-W2 的建议是「从方案 (a) 起步 + 监控三条触发信号」，而不是「一次选对方案」。** 本文采纳这个立场。

### 2.6 ★ 「平台」维度的真实后果：三巨头的 strike 模型结构不同（R7-W1 §1.8.5 / §1.9.5 / §1.13.5）

**[判断] 这一节回答一个具体问题：为什么 `platform` 必须是一个维度？** 因为它不只改变「什么算违规」，还改变**「违规如何累计」** —— 同样的违规次数，在三家平台上后果完全不同。

**三家的官方规则逐字对照**：

| 平台 | 计数模型 | 逐字原文 |
|---|---|---|
| **Meta** | **账号级累计池**（跨政策共用） | `One strike: You'll get a warning since this is your first strike.` / `Two to six strikes: You'll be restricted from specific features, like posting in groups, for a limited amount of time.` / `Seven strikes: You'll get a one-day restriction from creating…` |
| **Google Ads** | **逐政策配额**（各政策独立计数） | `You will receive a maximum of 3 strikes per policy on your Google Ads account.` |
| **YouTube** | **同一 90 天窗口内计数**，且有唯一「培训消警告」机制 | `To have this warning expire after 90 days, you can take an optional policy training. However, if your content violates the same policy within that 90 day window, the warning may not expire…` |

**[判断] 三条操作性含义：**

1. **Meta 的池是共享的，Google 的不是。** 在 Meta 下，历史上任何一次违规都在消耗同一个配额；在 Google 下，**违规 A 政策不消耗 B 政策的配额**。所以「已经攒了几次」这个问题，在 Meta 上是**账号级单一数字**，在 Google 上是**每政策一个数字**。
2. **YouTube 是唯一给出「消除机制」的。** 90 天窗口 + 可选政策培训 → 警告失效。**这意味着 YouTube 的 strike 是需要主动运营的**（完成培训即可降低存量风险），而 Meta 与 Google 的没有等价机制。
3. **三家的骨架相同（警告 → 限制 → 封禁），但计数规则不同** —— 所以**「违规次数」不是一个可以跨平台相加的量**。规则库里 `platform` 字段如果只用来标「这条规则属于哪个平台」，会丢掉这层差异。

**落地建议**：`platform` 属性之外，另建一张**平台后果模型表**（平台 → 计数单位 → 配额数 → 窗口长度 → 消除机制），作为规则库的**附属维表**：

```
platform_consequence_model:
  platform      : Google Ads / Meta / YouTube / TikTok / Amazon
  counting_unit : 账号级累计池 | 逐政策配额 | 窗口内计数
  quota         : 3 | 7 | …（各政策独立或共用）
  window_days   : 90 | 无
  remediation   : 政策培训可消警告 | 无 | 申诉
```

> **[判断] 这张表的用途不是判定内容，而是判定「处置紧迫度」** —— 它喂给 §4.3 的 `exposure`：**同样一条 L3 违规，在「账号级累计池且已攒 6 次」时应当升级为紧急，在「逐政策配额且该政策首次」时可以是常规。** 这是 `exposure` 的一个新输入，且**零采集成本**（平台后台可见）。

### 3.1 来源分类学与优先级

**[判断] 一条审核规则可能来自八个地方，可信度与更新频率差异极大：**

| 来源 | 可信度 | 更新频率 | 萃取成本 | 可否自动化 | 现有规则中的例子 |
|---|---|---|---|---|---|
| **S1 法源**（法规/判决/执法） | 最高（有强制力） | 低（年度级） | 高（需法务） | 部分 | H01/H02/H05/H06/H07 的法源部分 |
| **S2 平台政策** | 高（不遵守会被下架） | **高（季度级）** | 中 | 可（有 changelog 可爬） | R1 的五家政策库 |
| **S3 平台实际判例**（申诉结果/拒登通知） | 高（是执行事实） | 高 | 低 | 可（有 API/回填） | **当前空缺** |
| **S4 竞品对标** | 中（是参考不是依据） | 中 | 中 | 部分 | R5 §7.5 的五种边界规避手法 |
| **S5 客户投诉/差评** | 中（暴露痛点，不定义合规） | 高 | 低 | 可 | **当前空缺** |
| **S6 内部专家经验** | 中（快但不可复核） | — | 低 | 否 | **现有 21 条的主要来源** |
| **S7 数据挖掘**（从标注反推） | 中（需验证） | — | 高 | 可 | **当前空缺** |
| **S8 品牌自定调性** | 低（无外部强制力） | 低 | 低 | 否 | M04 压力话术等 |

> **★ 两处必须声明的事实（R8-W1 §1.1、§3.4）**：
>
> **(a) 「可信度」这一列是本文的定性判断，不是行业既有实现。** R8-W1 穷尽检索后确认：**没有任何真实系统把「来源可信度」建模成字段**。NIST SP 800-30 把「识别信息来源」列为正式任务（`TASK 1-4`，分 internal / external），但**只分类、不打分**；GitHub 的 `versions: fpt: '*'` 是**适用范围**字段，不是可信度。**所以委托方若采纳此列，是在自建一个标准里没有的字段** —— 这是可以做的，但要知道它没有外部依据。
>
> **(b) 法源有滞后，规则库因此需要第三个状态。** 依据（`_evidence/R8/eu-aiact-art6-eurlex.txt`）：
> > **[原文]** EU AI Act 第 6(1) 条 `Done at Brussels, 13 June 2024`，但同条 `shall apply from 2 August 2027`
>
> **= 38 个月的间隔。** DSA 同样：2022-11-16 通过 → 2024-02-17 适用（15 个月）。
>
> **[判断] 委托方现有 12 字段只有二值的 `启用状态`，无法表达「已通过但尚未适用」。** 这是 schema 的一处真实缺口 —— **规则必须有第三态**：
> ```
> rule_state ∈ { 已生效, 已通过未适用, 已废止 }
>     # 二值的「启用/停用」无法表达「已通过未适用」
>     # 后果：法源类规则要么提前误拦，要么上线时才补，两者都有成本
> ```
> 已并入 §3.5 的字段设计。

**[判断] 冲突时的优先级 —— 这不是本文的发明，平台自己已经声明了：**

**R1 §4.6 的 M7 发现是行业共识级的**：三家平台用**几乎相同的语言**独立声明了同一条原则：

> **[原文]** Meta：`we endeavor to restrict access to the content **only in the jurisdiction where it is alleged to be unlawful** and do not impose any other penalties or feature restrictions`
> **[原文]** TikTok：`we seek to restrict access to the content **only in the jurisdiction where it is alleged to be unlawful**`（**与 Meta 逐字相同**）
> **[原文]** YouTube：`We may remove content for reasons other than Community Guidelines violations. For example, a first-party privacy complaint or a court order. **In these cases, your channel won't get a strike.**`

**[判断] 三条结论：**

1. **法律性移除与平台违规是两套管道** —— 后果不同（一个不处罚、一个计 strike）、地域范围不同（一个只屏蔽指认违法的辖区、一个全球）。
2. **必须放在规则库的两个不同字段** —— 否则会把「某国法律不允许」误记成「品牌违规」，**污染规则库的统计与升格计数**。
3. **优先级：S1 法源 > S2 平台政策 > S8 品牌调性**，但当 S1 与 S2 冲突时**不取高**，而是**两条都执行、分别记录**（因为它们的**后果**不同，不是**结论**不同）。

**映射到 R3 的冲突三原则**（R3 §11.2 的修正是重要的）：

| 维度 | 优先级方向 | 依据 |
|---|---|---|
| `jurisdiction` | **上位优先**（国家法规 > 平台政策 > 品牌调性） | lex superior |
| `platform` | **具体优先**（平台具体条款 > 通用政策） | lex specialis |
| 时间 | **新法优先** | lex posterior |

> **⚠️ R3 的重要修正**：**不要用「越具体越优先」这个流行说法**。LegalRuleML 明确警告 lex specialis 不一定适用（`a more specific article from a local council regulation might not override a less specific constitutional norm`）。**正确做法是在作用域上为每个维度分别声明优先级方向。**

#### 3.1.1 ★ 补充：「谁压谁」的真实答案是两个排序，不是一个（R8-W1 §2）

**[判断] 委托方问「这几类互相冲突时谁压谁」，这个问题隐含假设存在**一个**全序。R8-W1 逐字取证后得到的答案是：**存在两个，且二者不矛盾，必须分开建模。**

**第一层：立法层（谁的话更算数）** —— 四个来源独立声明：

> **[原文]**（GitHub Terms of Service）`Except to the extent applicable law provides otherwise, this Agreement … are governed by the federal laws of the United States…`
>
> **[原文]**（Amazon Ads Policies，**最强的一条**）`Our policies aren't legal advice. It's your responsibility to consult with legal counsel…`
>
> **[原文]**（GitHub ToS，同层冲突的裁决规则）`If those additional terms conflict with this Agreement, the more specific terms apply`
>
> **[原文]**（PyPI AUP，无法裁决时的兜底）`We will interpret our policies and resolve disputes in favor of protecting users as a whole`

**第二层：裁决层（谁说了算）** —— 平台保留单方裁量：

> **[原文]**（Amazon AHR）`Amazon reserves the right to… at its sole discretion`
> **[原文]**（PyPI）`in our sole discretion`

**[判断] 两层的含义完全不同，混为一谈会导致错误的行动：**

| 层 | 排序 | 对委托方的行动含义 |
|---|---|---|
| **立法层** | 法源 > 平台政策 > 品牌调性 | 决定**规则怎么写**：法源类规则不得被平台政策或品牌调性覆盖 |
| **裁决层** | 平台 > 一切（单方裁量） | 决定**怎么申诉**：**不能对平台引用位阶**（说「我符合欧盟法所以你不该下架我」无效） |

> **★ 这是对申诉策略的一条硬约束（R8-W1 §2.2）**：对平台的申诉材料里，**引用规则位阶是无效的**。唯一有效的论证形式是「根因已消除」——依据 `_evidence/R1/amazon-appeal-questionnaire-reinstate-G201623610.md` 的逐字要求：
> `look for the root causes` / `specific actions … dates of changes, or documentation`

**另附一条位置信号**：GitHub AUP 把 `Compliance with Laws and Regulations` 编为 **§1**，且 §2 的首项又是 `is unlawful or promotes unlawful activities` —— **法源在同一份 AUP 里出现两次，分别承担「义务条款」（你可以做什么）与「禁令条款」（你不可以做什么）两种职能**。这说明**法源不是一个来源类，而是两种**，在规则库里应当有区分。

**[判断] 未找到完整全序**：R8-W1 在 AMO / AWS AUP / npm ToS / Shopify / npm-disputes 中检索 `precedence|priorit|conflict|supersede` **全部 0 命中**。所以「全网有一个统一优先级」是错的 —— **多数系统根本没有声明冲突优先级，只有少数声明了局部规则。**

### 3.2 「错题本」与「规则库」的关系

**[判断] 这是委托方问得最准的一个问题。答案需要先澄清一个误解：**

| 常见理解 | 正确理解 |
|---|---|
| 错题本 = 记录判错的案例 | **错题本 = 记录「判定与真相的偏差」+「规则自身的缺陷」** |
| 规则库和错题本是两个东西 | **错题本是规则库的输入管道，不是它的附属品** |
| 先有规则库，再有错题本 | **在没有规则库时，错题本可以先生成**（本文已生成 143 条） |

#### 3.2.1 九个体系怎么处理「规则本体 vs 案例」

| 体系 | 规则本体 | 案例库 | 二者关系 |
|---|---|---|---|
| **判例法传统** | 从判决中提炼 | 判决书 | 案例是规则的**来源** |
| **LegalRuleML** | `PrescriptiveStatement` | **无案例建模元素** | **不解决** —— 见下方更正 |
| **EU Cellar（法规 ← 判例）** | 法规条款（CELEX） | 判例（224 个判例 CELEX） | **引用网络**：4,966 条三元组 / 6,465 条引用边，精度到「句」 |
| **Meta × Oversight Board** | 政策条款 | 个案决定 + **四个处置码** | 案例**回写**规则（R4 §1.2） |
| **DSA Transparency Database** | 平台政策 | **法定结构化错题本**（16 个法定数据点） | 案例**被监管方定期审视** |
| **OPA / Rego** | `policy` | `opa test` 的测试用例 | 测试用例**守护**规则不退化 |
| **软件工程的 bug tracker** | 代码 | issue + regression test | 缺陷**转化为**回归用例 |
| **Gab Hate Corpus 手册** | 标注规范 | `Notes` 列（记录编码困难） | 手册**下一版**的输入 |
| **Andrew Ng error analysis** | 模型/规则 | 错误样本分桶 | 错误**指向**下一个改进点 |
| **本文的错题本** | 规则库 | `EB-NNNN` + `EB-RNNN` | 双向：错题 → 规则修订 → 回归门守护 |

> **★ 一处必须注意的细节**（R4 §1.5）：Gab Hate Corpus 的 `Notes` 列收集的是**「判定者遇到的困难」**，不只是「判错的案例」：
> **[原文]** `make notes about difficult cases and difficulties you had in coding, as we will use these contributions to refine and improve later versions of this manual.`
>
> **[判断]** 这是一个重要的设计提示：**「我不确定」本身是一条有价值的记录**，而不是需要隐藏的失败。

> **★ 更正（R8-W3 §1.3.3）：LegalRuleML 并没有 `CaseLaw` 概念。**
> **[判断]** 本表早期版本曾把 LegalRuleML 列为「案例分开建模」，这是错的。对 `_evidence/R3/raw/legalruleml-core-spec.txt`（7,391 行）做**字节级检索**：
> - `CaseLaw` → **0 命中**
> - `isCase` → **0 命中**
> - `ConstitutiveStatement` → 18 命中
> - `Case` → 6 命中，但**全部不是元素**：其中 1 处是 `refIDSystemName="European Case Law Identifier"`（欧洲判例标识符，属于 `LegalReference` 的**引用标识体系**），其余是 `UpperCamelCase` / `lowerCamelCase` 的命名法说明与 §6.2 的示例标题 `Case 18/96, Bologna Tribunal, Imola Section`。
>
> **所以 LegalRuleML 是「引用判例」而不是「把判例建成可推理对象」** —— 它给出 `LegalReference` 去指向判例，但不提供承载判例内容的元素。
>
> **修正后的结论反而更强**：**「规则库 + 案例库」的双库结构，在规则建模标准里是空的。** 现有标准只覆盖 `PrescriptiveStatement`（规定性）与 `ConstitutiveStatement`（构成性）两类陈述，**没有一个标准把「个案判定」建模成一等公民**。委托方要的双库结构**必须自建**，无法继承任何标准——这是一个负面结论，但它是可据以决策的负面结论。
>
> 需要澄清的一点：判例法传统那行（`案例是规则的来源`）**不受此更正影响**，因为它是法学传统的描述，不是任何标准的元素清单。

> **★ 新增（R8-W3 §1.3.1）：双库结构有一个正在 PROD 运行的官方实例 —— 欧盟 Cellar 的「法规 ← 判例」引用网络。**
>
> **[判断]** 上一条更正说「双库结构在标准里是空的」，但**在真实系统里不是空的**。R8-W3 从 `_evidence/R3/raw/gdpr-cellar-gdpr-subset.rdf` 实测出：
>
> | 指标 | 实测值 |
> |---|---|
> | `owl:Axiom` 三元组 | **4,966** |
> | `cdm:work_cited_by_work` 引用边 | **6,465** |
> | 判例 CELEX 标识 | **224** |
> | 被引条款片段 | **693** |
>
> **关键在引用的粒度与工作流**：
> > **[原文]**（片段级引用样本）`fragment_citing_source = N 159` → `fragment_cited_target = A82P2SNT1`
> >
> > 即 **判例第 159 段 → GDPR 第 82 条第 2 款第 1 句**，**引用精确到「句」**。
> >
> > **[原文]**（工作流）`workflow: CASELAW_METADATA_UPDATE; rules: caselaw-legacy-20250930-0; environment: PROD`
> >
> > **判例库有独立于成文法的更新流水线，且工作流本身带版本号。**
>
> **★ 这推出一个对本文错题本设计的硬要求**：
>
> ```
> # 错题必须引用到「规则的哪一条哪一款」，而不是「H07」
> errorbook.related_rule_ref ∈ { 规则 ID + 片段定位符 }
>     # 例：H02#claim_clause_2  而非  H02
> ```
>
> **[判断] 这不是过度设计 —— 它恰好能表达本文已实测出的真实冲突。** 错误的错题本里，一条错题挂在 `H02` 上，看不出问题出在 H02 的哪一句话；而**本文 §3.6 实测的 `EB-R010` 冲突正是片段级的**：`H02` 与 `M07` 共享 `improve pumping efficiency` 这一措辞但严重度不同 —— **文件级看无冲突，片段级看才是冲突**。**只有把引用粒度降到片段，这类冲突才可被发现和统计。**

### 3.3 五个环：规则的自迭代管道

**[判断] 规则库的自迭代是五个环，不是一次性工程**（R4 §7.1）：

| 环 | 节奏 | 输入 → 输出 | 责任 |
|---|---|---|---|
| **环 5 外部扫描** | 双周 | 平台政策/法规/竞品/客诉 → **风险信号卡** | 调研/合规。**目前完全空缺** |
| **环 1 规则生产** | 月度 | 草案 + 抽样内容 + **≥2 个候选划线方案**（每方案必附「会删/会留」样例）→ enforcement guideline | 规则库负责人 |
| **环 2 回归门** | **每次变更前强制** | golden set（每规则 ≥1 正例 + ≥1 反例 + ≥1 对抗样本）→ PASS/FAIL，**FAIL 不许发布** | 独立于环 1 |
| **环 3 运行取证** | 每日 | 内容 → 四格记录 + **判定路径**落库 | 系统 |
| **环 4 误差分析与回写** | 周会 + 月报 + 季盘点 | 四格 + 抽样人审 → 错误分桶 + **处置码台账** → 回环 1 | 合规负责人 |

**两条硬约束**：

1. **环 1 与环 4 负责人不能同一人** —— 依据 NIST AI RMF MEASURE 1.3 + Santa Clara Principles 的「未参与初判」要求。
2. **环 2 不可特批绕过**。

#### 3.3.1 ★ 同行里唯一可抄的完整原型（R6 新发现）

**[判断] 「同行怎么做」这个问题，查遍四家 A 股跨境电商上市公司 2025 年报 + 安克三年年报，只有一份可抄的样板。**

**为什么其他人的年报里查不到**（R6 §2.7）：

| 公司 | 「广告」出现次数 | 「内容审核」出现次数 | 原因 |
|---|---:|---:|---|
| 安克创新（2023/2024/2025 三年） | **0 / 0 / 0** | 0 | 广告是**成本项**，不进风险因素 |
| 致欧科技 | — | 0 | 披露了 AIGC 规模化生产，未披露审核 |
| 华凯易佰 | — | 0 | 披露 AI 生成广告创意，未提审核 |
| **PDD Holdings（Temu 母公司）20-F** | **大量** | — | **广告是它的收入项**（卖的广告要审），所以有整段广告法风险披露 |

> **[判断] 这条结论本身很重要：不能把「查不到」当成「没人做」。**
> **广告/内容合规只在「广告是收入」时才进年报风险因素。** 委托方是成本侧买方，所以同行披露里注定查不到。

**唯一可抄的样板：赛维时代（301381.SZ）2025 年报 P24**

描述的是一个「基于大模型的侵权检测平台」，其结构与本文设计的规则生产管道**高度同构**：

| 赛维时代的做法 | 对应本文的哪一环 |
|---|---|
| 多模态输入（图像 / 文本 / 设计元素） | **环 3 运行取证**（但**覆盖多模态**，委托方当前只覆盖文本） |
| 风险知识库 | **§2 主题分类** |
| **按平台分区的**侵权案例知识库 | **§3.2 错题本** —— 注意它**按平台分区**，印证了 §2.3 的平台正交属性 |
| 自动评级 | **§4 严重等级** |
| 上架前**前置筛查** + 在售**持续监控** | 两个时点，委托方只有前者 |
| **高检出率与低误报率双指标** | **§4.4 度量** —— 它同时报两个方向，不是单一准确率 |

> **[判断] 这份披露最值得注意的一点是「按平台分区的案例知识库」。**
> 一家做跨境多平台的公司，其案例库的组织方式**就是按平台分区** —— 这是对本文 §2.3「平台是正交属性」的独立旁证，且来自同行而非标准组织。

**第二条可抄的（同构但赛道不同）：安克创新 P61 供应商 ESG**

`128 检查项 / 量化扣分制 / 四级风险分级 / 等级 → 处置映射`

> **[判断] 安克做的是供应商审核，不是内容审核，但它的结构完全可以平移**：**检查项清单 → 量化打分 → 风险分级 → 等级决定处置**。这正是本文 §4.3 的 `severity × exposure → 处置` 的同一个逻辑。

> **[判断] 环 5 是全空缺，而它恰恰是最容易做的。** R1 已经证明平台政策的变更历史是**公开可爬的** —— Google Ads 的 changelog 是五家里最强的（R1 §7.2），Meta 有 `Restrictions by country` 报表，TikTok 是版本化发布。**这一环不需要新能力，只需要一个双周例程。**

### 3.4 标注指南：规则从文本到可执行的关键一步

**[判断] 工业界把这一步叫 `enforcement guidelines`**，YouTube 官方定义逐字（R4 §2.1）：

> **[原文]** `enforcement guidelines (detailed explanation of what makes content violative)`

**而且官方承认这一步要花几个月**：

> **[原文]** `we begin revising the guidelines so that they can be accurately interpreted across the larger, more diverse set of moderators. **This process can take a few months.**`

**[判断] 这句话里藏着一条关键顺序：先对齐人，再对齐机器。** 修订指南的目的是让**更多、更多样的审核员**能一致地解释它 —— 也就是说，**在自动化之前，先要证明人类能一致**。

**这条顺序对委托方直接适用**：现在 21 条规则全部标注「自动可检测」，但**没有任何证据表明两个人读这 21 条会得出同样的结论**。而度量这事的方法只有一个：**一致性检验**（见 §4.4）。

### 3.5 规则的字段设计

**[判断] 规则库需要 5 张表，不是 1 张表 12 列**（R3 §11.6 给出完整 schema，此处给结构）：

| 表 | 职责 | 关键字段 |
|---|---|---|
| **`scope_node`** | 作用域节点 | `scope_id` / `parent_scope_id` / `dimension` / `value` |
| **`rule`** | 规则本体 | `rule_key` / `revision_id` / `guid` / `modality` / `severity` / `disposition` / `scope_id`（外键）/ `evaluability` / `effective_from` / `effective_to` / `priority` / `authority` / `source_refs`（N:M） |
| **`constraint`** | 判定条件 | `constraint_id` / `left_operand` / `operator` / `right_operand` |
| **`detector`** | 检测器实现 | `detector_id` / `type`（regex/keyword/model）/ `pattern` / `version` |
| **`rule_set`** | 规则集级声明 | `hit_policy` / `conflict_strategy` / `fallback_disposition` / `applies_to_assets` |

**三个必须理解的字段设计**：

**(a) 规则 ID 要三个不是一个**：
- `rule_key` —— WORK 层，**永不变、永不复用、可读**（`T1.medical-claim.US`）
- `revision_id` —— EXPRESSION 层，可变（`R2026.09.1`）
- `guid` —— 无语义主键

> 依据 Akoma Ntoso 三原则 `MEANINGFULNESS` / `PERMANENCE` / `INVARIANCE` + Cedar 原话 `identifiers that are guaranteed unique and never reused`（R3 §10.3）

**(b) `modality` 与 `severity` 与 `disposition` 必须分开** —— 现有的 `边界类型` 一列混了三个概念：

| 概念 | 取值 | 现有规则中的混入 |
|---|---|---|
| `modality` | `forbid` / `obligation` / `permission` | H 族=forbid，U 族实为 obligation |
| `severity` | L0–L5 | 与 modality 混在一起 |
| `disposition` | `reject` / `human_review` / `rewrite_required` / `pass` / `downgrade` | **M05（审慎即止）与 U01（待复核）的差别在这里，不在严重度** |

**(c) `evaluability` 必须是三值，且允许「无法自动判定」**：

```
evaluability ∈ { automatic, assistive, manual_only }
```

> **[判断] 现在 21/21 填「自动可检测」是不真实的。** R4 给的旁证很有力：**Meta 在最难类别（Hateful Conduct）的主动发现率也只有 66.40%，Spam 才 99.60%**。一个 21 条规则、无度量基础的体系声称 100% 自动可检测，在数量级上不可能。

#### ★ 3.5.1 一处内部矛盾：`自动可检测` 与 U 族定义不能同时成立

**[判断] R6 指出一个必须进验收清单的内部矛盾**（R6 §6.5）：

> **21/21 条规则 `判断方式` 全部填「自动可检测」，同时 U 族（U01–U04）的定义是「人工复核灰规则」——两者不能同时成立。**

遍历 21 条规则的 `边界类型` 与 `风险等级`：

| 族 | `边界类型` | `风险等级` | 声称的 `判断方式` | 矛盾 |
|---|---|---|---|---|
| H01–H09 | 严格限制红线 | 高危 | 自动可检测 | 可接受（红线规则通常是模式匹配） |
| M01–M04, M06, M07 | 审慎关注 | 审慎 | 自动可检测 | 可接受 |
| **M05** | **人工复核** | 审慎 | **自动可检测** | **✗ 边界类型自称「人工复核」，却声称自动可检测** |
| **U01–U04** | **人工复核** | 待复核 | **自动可检测** | **✗ 同上，四条** |

**[判断] 这是一个数据自洽性问题，不是判断错误。** 它意味着：**规则表同时表达了两件互相冲突的事** —— 边界类型说「这需要人」，判断方式说「机器能做」。

**行业侧的解法是拆成三个正交字段**（R6 §6.5）：

```
detection_mode      ∈ { rule_based, model_score, human_only }   # 怎么检测
operating_point     # 仅当 detection_mode = model_score 时必填，对应 evaluation.py 的 --level
escalation_criteria # 什么情况下从自动升级到人工
```

**[判断] 这个拆法比现有的「判断方式」单字段强在三处**：

1. **`detection_mode` 允许 `human_only`** —— 现有表里没有这个取值，所以 U 族被迫填「自动可检测」；
2. **`operating_point` 把「宁可错拦/宁可放过」变成一个显式参数** —— 这正是 §4.1.1 的发现；
3. **`escalation_criteria` 让「升级到人工」成为一个可声明的条件**，而不是散落在各规则的豁免词里。

**[判断] 回看 U04 的现状，这个拆法的价值立刻显现**：U04 的定义是「疼痛/堵奶场景化名词表述：需人工判定是痛点场景描述还是功效承诺；**与 goodbye/no more/not anymore/relieve 等消除性表述连用应升级 H01/H07**」。

**最后半句就是 `escalation_criteria`！** 它已经存在，只是被写在了 `触发原因` 这一自由文本列里，而不是一个结构化字段。**这是「现有资产里已有正确答案、只是没被建模」的典型例子。**

### 3.6 21 条规则写死「适用产品」的修法

**[判断] 这是新模型收益最直接的一处。**

现状：21 条规则的 `适用产品` 全部写死 `W1、M5、M6、M9、Air1`。

**问题有三层**：

1. **型号是客体（Asset），不是作用域** —— ODRL 里「涉及哪些资产」是 `Rule.target`，「适用于资产集合里的哪些成员」是 `AssetCollection.refinement`。**型号列表是 `target` 的取值**。
2. **硬编码列表会导致新产品上市时静默失效** —— Air2 上市时如果没人改这 21 行，**Air2 的内容不会被任何规则覆盖**，而由于没有兜底规则，它会**静默通过**。这是 OPA Style Guide 描述的 fail-open 的**组织版本**。
3. **它掩盖了「规则是否真的对所有型号都一样」这个未经验证的问题** —— 21 条全填同一个值，有两种可能：(a) 确实一样；(b) **填表时批量粘贴的**。从 `判断方式` 也是 21/21 同一个值看，(b) 的可能性不低。

**修法（三选一，按推荐度）**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 集合引用** | `applies_to_assets: @product_line.pump` | **推荐**。新产品加入产品线时自动覆盖。依据 ODRL `AssetCollection` + `source` 属性 |
| ② 显式声明未覆盖即异常 | 兜底规则：任何不在任何规则作用域内的资产 → 人工复核 | 好，且是 §5 的必要组成 |
| ③ CI 检查 | 规则集的资产覆盖集与产品主数据做 diff | 工程化最佳，成本最高 |

**并且**：把 `applies_to_assets` 设为**必填且不允许从别的行继承**，对「与规则集默认值相同」的规则打 `inherited: true` 标记，使它**在审计时可见** —— 「这条规则的适用范围是继承来的，从未被单独确认过」。

## 4. 严重等级

### 4.1 行业参照系：GARM

**[判断] 风险分级的行业标准是 GARM（Global Alliance for Responsible Media）**，由 IAB Tech Lab 承载（R6 逐字核实）：

| 项 | 内容 |
|---|---|
| **类别数** | **11 类**（IAB 新闻稿 2020-10-28 列出原名） |
| **等级数** | **4 级**：`Floor` / `High` / `Medium` / `Low` |
| **聚合规则** | **11 类中取最高档** |
| **实际标注集** | IAB 官方 GitHub `Brand-Suitability-Test-Benchmarks`（Zefr 捐赠，**5,330 条 YouTube 人类标注**）实际用 **5 档**：`minimal` / `low` / `medium` / `high` / `floor` |

> **⚠️ GARM 现状**：WFA 官网保留 **2024-08-09** 声明原文：
> **[原文]** `Today we announce that GARM will discontinue its activities.`
> 但同页仍写：`GARM's toolset includes the Brand Safety Floor and the Adjacency Standards Framework`
>
> **[判断]** GARM 组织已解散，但**其框架仍在被 IAB Tech Lab 承载和使用**（标注集、taxonomy 仍在 GitHub 上）。**采用其分级结构是安全的，引用其"现行标准"地位则需谨慎。**

**[判断] GARM 对本文最大的启示是它的「Floor」概念**：

- `Floor` 不是「最严重」，而是**「绝不容忍的下限」** —— 它是一条**阈值线**，不是一档程度。
- 这解释了为什么标注集里用 5 档而框架是 4 级：**`Floor` 与 `High` 不是连续的**。

**这个结构对委托方直接适用**：现有四档里，「高危·红」同时承担了「很严重」与「绝对不行」两种含义。

#### 4.1.1 ★ 行业标准自带一个可运行的度量脚本（R6 新发现）

**[判断] 这是本次调研里最可操作的一个发现。** IAB Tech Lab 官方 GitHub 仓库 `IABTechLab/Brand-Suitability-Test-Benchmarks`（Zefr 捐赠，Apache-2.0）里有一份 `evaluation.py`，它给出了「严重等级如何变成可度量指标」的完整答案：

| 环节 | 官方做法 |
|---|---|
| **标签** | 5 档序数：`minimal` < `low` < `medium` < `high` < `floor` |
| **聚合** | **11 类中取最高档**（`overall_severity = max(per_category_severity)`） |
| **二值化** | 在 `--level` 指定的**操作点**上切成「高 / 非高」 |
| **指标** | 预测是 0–1 分数 → **Average Precision**；预测是标签 → **Balanced Accuracy** |
| **为什么不用准确率** | 类别不平衡。Balanced Accuracy 对不平衡稳健 |

**[判断] 三个可以直接搬进本文设计的点：**

1. **「操作点」（operating point）必须是一个显式参数，不是隐含的。** 同一条规则在「宁可错拦」与「宁可放过」两种操作点上，评价结果完全不同。**现在 21 条规则没有任何地方声明它工作在哪个操作点上。**
2. **聚合用 `max` 而不是平均** —— 这与本文 §4.4.2 的元规则（取最差不取平均）**方向一致但用途不同**：`max` 用于**单条内容的多类别聚合**，取最差用于**多规则的系统可靠性聚合**。两者都要。
3. **标签必须显式包含「无风险」底档** —— 官方标注集是 5 档，最底是 `minimal` 而非「无标签」。**这与本文 §5.1「未命中 ≠ 合规」是同一个设计原则的两处体现。**

**[判断] ★ 最重要的一句：委托方的 291 条在跑记录，已经具备跑这个评测的全部输入。**

现有字段 `风险等级 | 命中规则 | 命中片段 | 修改建议 | 检查人` 已经够算 Balanced Accuracy。**只差两个字段**：

```
overall_severity   # = max(per_category_severity)，GARM 一致的聚合结果
status             # 待复核 / 已确认（即本文 §4.2 的「复核状态」）
```

**这两个字段都在本文 §6 的 P0 清单里。** 也就是说：**做完 P0-2 与 P0-3，就能立刻跑行业标准的评测脚本，而不是从零设计度量体系。**

### 4.2 六档设计

**[判断] 现有四档不够，缺两档，且两档有语义问题。**

| 现有档位 | 诊断 | 处置 |
|---|---|---|
| `高危·红` | 语义清晰，但**缺少「谁来决定」和「扣多少」** | 保留为 **L4**，补 `处置权限` 与 `处罚梯度` |
| `审慎·黄` | 语义清晰 | 保留为 **L3** |
| `待复核·灰` | ⚠️ **这是「过程状态」不是「风险等级」** —— 它和 U 族重叠，且**把过程状态混进风险等级，会导致「待复核」的内容永远停在待复核**（没人定义它复核完应该变成哪一档） | **移出**，改为独立的 `复核状态` 字段 |
| `合规·绿` | ⚠️ **语义重载**：同时表示「确认合规」与「规则没覆盖到」 | **拆成 L0 与 L1** |

#### 4.2.1 六档定义

| 新档 | 含义 | 默认处置 | 一致性门槛 | 处置权限 | 依据 |
|---|---|---|---|---|---|
| **L0 未覆盖** | 无规则命中，且**不能确认为合规** | **转人工 + 必填『未覆盖原因』**；**禁止自动放行** | 不适用（本身即「不知道」） | 一线 + 合规负责人 | NIST AI RMF MEASURE 3.2；Ofcom Step 2；R4 §6.1 兜底条款 |
| **L1 合规** | 明确判定合规 | 自动放行 | α ≥ .667 | 自动 | Krippendorff Rec. iii |
| **L2 待复核** | 规则命中但结论不确定 | 转人工 | 不设一致性门槛；改看**转人工率**与**处理时延** | 一线 | 原创 |
| **L3 审慎** | 命中审慎类规则，需限定表达 | 要求改写后放行 / 限制投放 | α ≥ .667 | 一线 + 合规负责人 | Krippendorff Rec. iii |
| **L4 高危** | 命中红线规则 | 拦截 + 合规确认 + 记录 | **α ≥ .800** | **合规负责人 + 法务** | Krippendorff（`decision criteria have to be set far higher`） |
| **L5 例外/降级** | 内容本身可保留，但需限制 | **保留但限制渠道/受众/地区** | α ≥ .800 | 合规负责人 | TikTok 例外处理（`Make it ineligible for the FYF` / `Add a warning screen` / `Add a context label`） |

#### 4.2.2 六档与 GARM 五档的对照

**[判断] 本文的六档不是重新发明，是 GARM 五档 + 一档扩展。** 对应关系：

| 本文 | GARM 序数档 | 说明 |
|---|---|---|
| L0 未覆盖 | *（GARM 无对应）* | **★ 这是本文的一处扩展**。GARM 面向「已分类内容的风险评估」，不处理「分类体系本身没覆盖」。工业界用 DSA Art 17 的自由文本字段补这一位（R4 §5.3.3） |
| L1 合规 | `minimal` | 无风险底档 |
| L2 待复核 | *（非风险档）* | **过程状态**，不参与序数 |
| L3 审慎 | `low` / `medium` | 需限定表达 |
| L4 高危 | `high` | 红线 |
| **L5 例外/降级** | **`floor`** | **★ `floor` 是阈值线，不是程度档** —— 它是「绝不容忍的下限」。本文把它用作「保留但限制」是因为 TikTok 的例外处理正是这个语义（降级而非放行） |

> **⚠️ 一处必须交代的错位**：GARM 的 `floor` 语义是「**这条内容绝不能出现在品牌旁边**」（淘汰），而本文 L5 的语义是「**内容可保留但需限制**」（降级）。**两者方向相反。**
>
> **[判断]** 因此本文**不声称 L5 等于 GARM `floor`**。正确做法是：
> - **GARM `floor` 对应本文 L4 的「最严重子档」**（绝不容忍）
> - **L5 是 GARM 框架之外的独立档**，来源是 TikTok 的例外处理机制
>
> 这一处错位之所以要写明，是因为它影响 §4.3 的 `severity × exposure` 计算：**`floor` 级内容不应参与暴露量加权 —— 它是硬阈值，不是程度。**

#### 4.2.3 三条关键改动为什么不能省

| 改动 | 不做的后果 |
|---|---|
| **拆出 `L0 未覆盖`** | **盲区率永远不可测**，规则库永远看起来「很干净」。实测：291 条里 159 条未命中（54.6%），**它们当前全部显示为「合规·绿」，无法区分「确认合规」与「没覆盖到」** |
| **移出 `L2 待复核` 到独立字段** | **复核完的内容无处可去**，必然积压。实测：132 条挂「待人工复核」，且 `风险等级 × 处理状态` **完全对角**（见 §4.5） |
| **新增 `L5 例外/降级`** | **所有非黑即白的判断被迫二选一** → 要么推高 FP（误拦），要么推高 FN（漏放）。对委托方，L5 对应「**可以投但限制渠道/受众/地区**」 |

### 4.3 等级是算出来的：severity × exposure

**[判断] 这是对现有四档最实质的一处改进，而且零采集成本。**

**依据**（NIST AI RMF）：

> **[原文]** `risk is a function of 1) the negative impact, or magnitude of harm … and 2) the likelihood of occurrence`

**[判断] 现有四档只编码了第一个因子。** 一条「高危」命中一次（低暴露）与命中 300 次（高暴露），风险完全不同。

**而 PRD 里已经有三个字段没有参与定级**：

| 已有字段 | 作为 exposure 的代理 |
|---|---|
| `近7天展示` | 触达规模 |
| `近7天点击` | 实际交互规模 |
| `近7天费用USD` | 商业投入规模（≈ 若被下架的损失） |

**定级公式**：

```
severity   ∈ {L1..L5}                      # 伤害的量级（规则固有属性）
exposure   = f(近7天展示, 近7天点击, 费用)   # 伤害的概率代理（内容固有属性）
risk_score = severity × exposure 分档       # 决定处置优先级与响应时效
```

**[判断] 三个直接收益**：

1. 把「高危但只投了 3 次」和「高危且投了 20 万次展示」分开；
2. **处置时效可以分层** —— 高暴露的高危内容应当小时级响应，低暴露的可以日级；
3. **它是 FP 成本计量的基础** —— 误拦一条高暴露文案的损失，与误拦一条低暴露的，差几个数量级。

**实测验证**：本文 §4.5 的 132 条待复核记录，近 7 天花费 **$19,913.24，占全表 $43,060.59 的 46.2%** —— 这就是**暴露量的真实分布**，而它当前完全不参与定级。

---

#### 4.3.1 ★ 修正：不是乘法，是查表（R8-W3 §2.1.5）

**[判断] 上一版的 `severity × exposure` 用乘法合成，这是错的，应改为查表。**

**依据**（NIST SP 800-30 Rev.1，`_evidence/R8/nist-sp800-30r1.txt` L4883–4896，`TABLE I-2: ASSESSMENT SCALE – LEVEL OF RISK (COMBINATION OF LIKELIHOOD AND IMPACT)`）：

| Likelihood ↓ / Impact → | Very Low | Low | Moderate | High | Very High |
|---|---|---|---|---|---|
| **Very High** | Very Low | Low | Moderate | High | Very High |
| **High** | Very Low | Low | Moderate | High | Very High |
| **Moderate** | Very Low | Low | Moderate | **Moderate** | **High** |
| **Low** | Very Low | Low | Low | Low | Moderate |
| **Very Low** | Very Low | Very Low | Very Low | Low | Low |

**这张官方矩阵直接证伪了乘法**，有三处：

1. **两个因子不等权。** `High likelihood × Moderate impact = Moderate`，但 `Moderate likelihood × High impact = High`。乘法下两者都是「中×高」= 同级，**矩阵下不等** —— **impact 的权重高于 likelihood**。
2. **低概率行会封顶。** `Low likelihood` 一行的最高值是 `Moderate`（即使 impact 是 `Very High`）；`Very Low likelihood` 一行**最高只到 `Low`**。乘法不会产生这种封顶效应。
3. **乘法会系统性高估低曝光内容。** 一条 L5（最高伤害）但曝光极低的内容，乘法会给出「L5 × 低 = 中高」的结论，而矩阵给出 `Low`。

**[判断] 这对委托方的实际后果**：委托方是**成本侧买方**，「高危但几乎没投」的内容大量存在（§4.5 已实测：132 条待复核中有相当比例低花费）。**乘法会把这些内容排到不该有的优先级上，挤占真正高暴露风险的处理资源。**

**落地写法**：

```
risk_level = NIST_TABLE_I2[ likelihood_bin(exposure), impact_bin(severity) ]
# 不是 severity × exposure 的算术积
# likelihood_bin 由 exposure 分箱得到（几档，见 §4.3.2）
# impact_bin 由 severity 映射得到（L1..L5 → Very Low..Very High）
```

---

#### 4.3.2 ★ 修正：`exposure` 只覆盖了三维中的一维（R8-W3 §2.2.1(b)）

**[判断] 上一版把 `exposure` 定义为「触达规模」，这只是严重性的一个子维度。** DSA 逐字要求三个子维度。

**依据**（DSA Recital (79)，`_evidence/R8/dsa-art34-eurlex.txt` L373）：

> **[原文]** `In determining the significance of potential negative effects and impacts, providers should consider the severity of the potential impact and the probability of all such systemic risks. For example, they could assess whether the potential negative impact` **`can affect a large number of persons`**`, its potential` **`irreversibility`**`, or` **`how difficult it is to remedy and restore the situation prevailing prior to the potential impact`**`.`

**三个子维度对照委托方现状**：

| DSA 子维度 | 含义 | 委托方现状 |
|---|---|---|
| `can affect a large number of persons` | 触达人数 | **已可用**（`近7天展示/点击/费用`） |
| `potential irreversibility` | 不可逆性 | **无字段** |
| `how difficult it is to remedy and restore` | 补救难度 | **无字段** |

**[判断] 后两维正是「平台封号风险 ≠ 某国罚款风险」的技术答案。** 两者的差别不在**大小**，而在**可逆性**与**补救难度**：

| 后果类型 | 不可逆性 | 补救难度 |
|---|---|---|
| 平台封号 / Listing 下架 | **低**（可申诉、可重上） | 中（有申诉流程，§3.2 的 `EB` 记录即证据） |
| 某国监管罚款 / 强制召回 | **高**（罚款不可退） | **高**（无申诉对象） |
| 品牌声誉损伤 | **中高**（已触达的受众无法收回） | **高** |

**落地建议（P1）**：`exposure` 不要坍缩成一个数，**保留三维**：

```
exposure = {
  reach:          # 触达人数（已有数据）
  irreversibility:# 不可逆性：枚举 {可撤回, 部分可撤, 不可撤}
  remediability:  # 补救难度：枚举 {有申诉通道, 需人工交涉, 不可补救}
}
# 三者不合成标量，直接作为 NIST 矩阵 impact 档的辅助判据
```

**[判断] 为什么不要合成标量**：NIST `TABLE H-4` 的第四列就叫 `Maximum Impact` —— 官方做法是**取最差**，不是求平均。把「不可逆但触达小」与「可逆但触达大」平均成一个中间值，会同时丢掉两个风险信号。

**[判断] 关于「监管后果与商业后果如何合成」**：两者在**对象**（监管方 vs 平台/消费者）、**层级**（法人 vs 内容）、**时间常数**（罚款即时 vs 声誉滞后）三个维度上**不可通约**。因此**不合并成一个标量**，而是**输出后果向量 + 取最差**（依据同 `TABLE H-4` 的 `Maximum Impact` 列）。

#### 4.3.3 一条附带发现：规则库本身是一份可从轻处置的合规资产

**[原文]**（AWS Acceptable Use Policy，`_evidence/R7/aws-aup.txt` L285）：

> `When determining whether there has been a violation of this Policy, we may consider your ability and willingness to comply with this Policy, including the policies and processes you have in place to prevent or identify and remove any prohibited content or activity.`

**[判断] 这条把「规则库」从内部工具提升为对外可举证的合规资产。** 平台在判断是否违规时，**会看你有没有流程**。所以规则库的商业理由不只是「降低误拦率」——**它本身是一份在违规争议中可援引的从轻情节**。

**建议写入 §6 的商业理由，并在向管理层汇报时使用这个论证**：建规则库的收益不只体现在运营指标上，还体现在**一旦发生平台争议时的抗辩能力**上。

### 4.4 等级怎么校准

**[判断] 校准的方法只有一个：一致性检验。而指标的选择有一个必须纠正的地方。**

#### 4.4.1 指标选择：用 α 不用 κ；α 与 Balanced Accuracy 分工

**R4 给出的依据是决定性的**：

> **[原文]**（Krippendorff 2004）
> `Cohen's (1960) κ … should be rejected as these measures are incompatible with reliability concerns in content analysis`

**原因**：κ 只能处理**两个编码者**，而审核场景是多人、多批次、有缺失值的。

**阈值**（Krippendorff Rec. iii）：

| α | 结论 |
|---|---|
| α ≥ **.800** | 可靠，可用于高危档 |
| α ≥ **.667** | 可用于探索性结论 |
| α < .667 | 不可用 |

> **★ 关键设计**：**阈值应按错误代价分档** —— Krippendorff 原文：`An acceptable level of agreement … must be chosen depending on the costs of drawing invalid conclusions`。
> **这直接推出「高危档需要更高的一致性门槛」**（本文 §4.2.1 的 α ≥ .800）。

**★ 两个不同层次的度量：α 管「人对不对齐」，Balanced Accuracy 管「机器对不对」**

**[判断] 这两个指标回答不同的问题，不能互相替代：**

| | **Krippendorff's α** | **Balanced Accuracy / Average Precision** |
|---|---|---|
| 问的问题 | **两个人**判得一样吗 | **机器**判得对吗 |
| 基准 | 人工之间的一致性 | 人工标注作为真值 |
| 用途 | 证明「规则是可被一致解释的」 | 证明「规则跑得准」 |
| 来自 | Krippendorff 2004（本文 §4.4.1） | IAB `evaluation.py`（本文 §4.1.1） |
| **何时用** | **先做**，否则机器的"准"没有意义 | **后做**，α 达标之后 |

**[判断] 顺序不能颠倒**，依据是本文 §3.4 引用 YouTube 的原话 —— 修订 enforcement guidelines 的目的是让**更多、更多样的审核员**能一致地解释它，即**先对齐人，再对齐机器**。

**如果 α 不达标（< .667）就先去调机器，结果会是**：机器拟合了一组本身就不一致的判断，**指标好看但不可复现**。

**操作点的声明方式**（IAB `evaluation.py` 的 `--level`）：

```
operating_point: high     # 在 "high" 档二值化 → 报「高危及以上」的 Balanced Accuracy
```

**[判断] 对委托方，建议对 L4（高危）与 L3（审慎）分别报两个操作点的结果**：

| 操作点 | 含义 | 该操作点上的错误代价 |
|---|---|---|
| `--level high` | 只关心「高危及以上」判对没有 | **漏放代价高**（FN 是合规风险） |
| `--level medium` | 把「审慎」也纳入阳性 | **误拦代价高**（FP 是业务损失） |

**同一套规则在两个操作点上的表现会显著不同 —— 而现在 21 条规则没有任何地方声明它工作在哪个操作点上。**

#### 4.4.2 元规则：取最差那条，不取平均

> **[原文]**（Krippendorff 2004）
> `the reliability of each variable should be measured and **the smallest among them should be taken as the reliability of the whole system**`

**[判断]** 这意味着度量报告**必须逐规则列出并标出最差那条**，不能报一个整体数字。**取平均会掩盖最差的规则** —— 而最差的规则才是风险所在。

#### 4.4.3 校准节奏

| 周期 | 动作 |
|---|---|
| **周** | 复核积压清理 + 处置码台账更新 |
| **月** | 逐规则算 α，**标出最差那条**；误差分桶（PAIR 七类） |
| **季** | **重新校准等级** —— 用本季的 FP/FN 数据检验「L3/L4 的划分是否仍然合理」 |

### 4.5 现状实测：等级从未被校准

**[判断] 这是本文最有力的一个实测结论。**

`audit_records_deep.py` 对 291 条记录做 `风险等级 × 处理状态` 交叉表：

| 风险等级 ＼ 处理状态 | 无需处理 | 待人工复核 | 小计 |
|---|---:|---:|---:|
| 合规·绿 | **157** | 0 | 157 |
| 高危·红 | 0 | **91** | 91 |
| 审慎·黄 | 0 | **30** | 30 |
| 待复核·灰 | 0 | **11** | 11 |
| （空） | 0 | 0 | 2 |
| **合计** | **157** | **132** | **291** |

**[判断] 这张表完全对角。**

含义不是「分类整齐」，而是：

1. `处理状态` 是 `风险等级` 的**函数**，零独立信息；
2. **291 条里没有任何一条**呈现「机器判红 → 人工改判绿」或「机器判绿 → 人工发现红」；
3. **这套判定还没有经历过第一次人工校准。**

**旁证**：`检查人` 列**存在但非空率 0.0%** —— 从未有人填写过。

**资金敞口**：132 条待复核记录近 7 天花费 **$19,913.24**，占全表的 **46.2%**。**规则把这笔钱标为「需要人确认」，而在确认之前，它一直在花。**

### 4.6 现有四档的直接处置建议

| 现有档位 | 处置 | 迁移动作 |
|---|---|---|
| `高危·红` | → **L4** | 补 `处置权限`（合规+法务）；接入 `exposure` |
| `审慎·黄` | → **L3** | 接入 `exposure` |
| `待复核·灰` | → **移出风险等级**，改为 `复核状态` 字段 | 取值：`待复核` / `已复核-维持` / `已复核-升级` / `已复核-降级` / `已复核-放行` / `已复核-规则待修` |
| `合规·绿` | → **拆成 `covered+L1` 与 `uncovered`** | 未命中的先落 `coverage_state = uncovered`（不是 `L0`），由兜底规则转人工或按 §5.2 的条件自动确认 |

#### 4.6.1 ★ 补充：漏了一条升级轴 —— 配合度（R8-W2 §1.7）

**[判断] 本文的等级全部由内容属性决定，但平台侧的升级判据里还有一条与内容无关的轴：处置过程中的配合度。**

**依据**（Mozilla AMO Add-on Policies §8.1 `Policy Enforcement`，`_evidence/R7/amo-addon-policies.txt`）：

> **[原文]** `Mozilla may attempt to contact the add-on's developer(s) and provide a reasonable time frame for the problems to be corrected before a block is deployed. If an add-on appears to intentionally or repeatedly violate the policies, or its developers have proven` **`unreachable, unresponsive, or uncooperative`**`, blocking may be immediate.`

**[判断] 三个词 —— `unreachable` / `unresponsive` / `uncooperative` —— 与「故意或反复违规」并列，是同等的立即封禁理由。**

**含义拆解**：

| | 内容侧（本文已建） | 过程侧（本文未建） |
|---|---|---|
| 判据 | 这条内容有多危险 | **你在被指出后怎么反应** |
| 后果 | 内容级 / 可见性级 / 账号级 | **直接跳到账号级（`blocking may be immediate`）** |
| 委托方现状 | 有（`风险等级`） | **无任何字段** |

> **[判断] 为什么这对委托方特别重要**：委托方是**成本侧买方**，风险主要来自平台侧的账号级后果（封号、Listing 下架），而不是内容本身被删。**而平台在决定是否直接封禁时，会看你的响应行为** —— 这与 §4.3.3 的 AWS AUP 条款是同一逻辑的两个侧面：**AWS 看「你有哪些流程」，Mozilla 看「你回不回话」。**

**落地建议（P1）**：新增一个与 `severity` 正交的过程字段：

```
response_state ∈ { 未触发, 已响应-配合, 已响应-异议, 逾期未响应, 无法联系 }
    # 与内容等级正交：内容 L5 + 配合 = 走常规申诉；内容 L2 + 不配合 = 可升到账号级
    # 触发条件：收到平台通知 / 申诉窗口开启 / 超期
```

> **[判断] 注意这与 §3.1.1 的申诉结论是一回事**：对平台申诉时不能引用位阶，只能主张「根因已消除」—— 而「响应及时 + 根因已消除」正好就是这个字段要记录的东西。**它把「申诉」从一次性的临场发挥，变成一个可审计的状态机。**

## 5. 空白怎么处理（「要是没有呢？」）

### 5.1 核心原则：未命中 ≠ 合规

**[判断] 这是整份设计里最重要的一句话。**

现状是：**规则没命中就是「合规·绿」**。这意味着：

| 情形 | 现在的显示 | 应该的显示 |
|---|---|---|
| 规则检查过，确认合规 | 合规·绿 | **L1 合规** |
| **没有任何规则覆盖这个情形** | **合规·绿** ← 错 | **L0 未覆盖** |
| 新品类/新语种/新平台的表达 | **合规·绿** ← 错 | **L0 未覆盖** |

**[判断] 后果**：**盲区率在数学上不可观测。** 因为「没覆盖到」与「确认合规」在数据模型里是同一个值。

R4 的原文判断（§5.4）：

> **[原文]**（本文引用 R4 的表述）
> 必须存在一个第三态的判定结果 `未覆盖`（既不是"合规"也不是"违规"）。**如果系统的输出只有"命中/未命中"，盲区率在数学上不可观测。**

### 5.2 空白的三条处置路径

**[判断] 空白不是一个状态，是三个状态，处置完全不同：**

| 情形 | 处置 | 依据 |
|---|---|---|
| **① 有兜底规则，覆盖了但结论是「不知道」** | 落 **L0 未覆盖** → 转人工 + 必填 `未覆盖原因` | NIST MEASURE 3.2；Ofcom Step 2 |
| **② 语种/形态不在规则覆盖内** | 落 **L0** 且 `未覆盖原因 = 新语种/新平台` → 进入规则生产队列 | 本文 §2.5.4 实测（小语种覆盖 0%） |
| **③ 检测器异常**（正则编译失败/上游超时/字段缺失） | **独立通道**，**不并入 L0** | Cedar skip-on-error 论证 |

#### 5.2.1 为什么「检测器异常」必须独立

**[判断] Cedar 的论证在这里是决定性的**：

> **[原文]**（R3 §5.2.2 引用 Cedar 文档）
> `an application that was working fine with 100 policies might suddenly start denying all requests if the 101st policy has an error`

**[判断] 对委托方的直接含义**：**如果检测器异常直接落到「高危」，那么一次正则写错会让全量内容被拒。**

而委托方**没有强制卡点**（PRD 明确写「目前无法强制卡死『审查完才能上线』的系统节点」），后果是**业务绕过审核流程** —— 这比漏放更危险。

**所以三条通道必须分开**：

```
命中规则        → 按规则 disposition 处置
未命中（兜底）   → L0 未覆盖 → 转人工
检测器异常      → ERROR 通道 → 告警 + 该条降级为人工，不自动判任何等级
```

### 5.3 兜底规则必须显式写在规则库里

**[判断] 本文建议新增第 22 条规则（数值上）：**

```
rule_key:      CATCH-ALL-01
modality:      obligation
severity:      （不适用 —— 它不是风险等级，是默认路径）
disposition:   human_review
scope:         root（全局）
condition:     无（catch-all）
statement:     "凡未被任何规则显式判为拒绝、且未被安全词白名单显式判为通过的内容，
                一律置为 L0『未覆盖』，转人工确认，并必填『未覆盖原因』。"
evaluability:  automatic
```

**[判断] 这条规则必须显式写在规则库里，不能硬编码在引擎里。** R3 §10.2 给了六体系零例外的证据：

| 体系 | 不写兜底会怎样 |
|---|---|
| **Cedar** | 硬编码 default-deny |
| **OPA** | `default` 不写则结论是 **`undefined`（第三态）** 而非 `false` |
| **ODRL** | 不写 `conflict` 默认 **`invalid`（整份 Policy 作废）** |
| **DMN** | 默认 `UNIQUE` 且**禁止重叠** |
| **OPA complete definition** | 多值**直接报错** |
| **XACML** | 无默认，必须显式选 combining algorithm |

> **六个体系，零个选择「静默挑一条」。**

### 5.4 「已知未覆盖清单」是合法且必要的

**[判断] 「规则写不完/覆盖不全」不是一个需要隐藏的状态，行业里有正式做法。**

| 做法 | 出处 |
|---|---|
| **DSA Art 17 的自由文本字段** | 平台发现现有分类描述不了判定理由时可自由文本提交，**监管方定期看，出现重复模式就升级为正式分类**（R4 §5.3.3） |
| **Gab Hate Corpus 手册的 `Notes` 列** | 明确收集「编码困难」（见 §3.2.1） |
| **Ofcom Step 2** | `Identify whether there are any additional characteristics or functionalities … not in the … Profiles, which could increase the risk` |
| **NIST MEASURE 3.2** | 唯一直击「度量手段尚不存在」的条文 |

**[判断] 本文的 `未覆盖原因` 字段（枚举：`新表达方式`/`新语种`/`新品类`/`新平台`/`规则边界不清`/`其他`）就是「已知未覆盖清单」的最小实现。** 它已经在生成的错题本 CSV 里。

### 5.5 「不确定」如何被表达成一个可存储的状态

**[判断] 这是委托方问题的最后一半：「怎么处理」的前提是「怎么存」。**

| 不确定的类型 | 存储方式 | 字段 |
|---|---|---|
| **规则没覆盖** | `coverage_state = 未覆盖` | + `未覆盖原因` |
| **规则覆盖了但我不敢定** | `Agent判定等级 = L2 待复核` | + `复核状态` |
| **两个人判得不一样** | 一致性指标下降 | `复判人` 非空 + α 计算 |
| **这条内容是新的、没见过的** | `未覆盖原因 = 新表达方式` | 进入规则生产队列 |
| **检测器本身出错了** | `ERROR` 通道 | 独立字段，**不污染等级** |

**[判断] 五个状态，五种存法。** 现状是**五种全部落成「合规·绿」或「待人工复核」两个值** —— 这就是「要是没有呢」这个问题在数据模型层面的答案。

#### 5.5.1 ★ 修正：`未覆盖` 不能寄生在 `severity` 里（R8-W3 §3.4.1）

**[判断] 上一版把「规则没覆盖」写成 `Agent判定等级 = L0 未覆盖`，这是把两个正交的量塞进了一个字段。应拆出独立的 `coverage_state` 字段。**

**依据**（NIST SP 800-30 Rev.1 的 CAUTIONARY NOTE，`_evidence/R8/nist-sp800-30r1.txt`）：

> **[原文]** `… must ultimately be assigned to one bin` —— 官方明确要求：**用于定级的标度必须是「每个样本都能落进某一档」的封闭标度。**

**[判断] 「未覆盖」不是一个严重程度。** 它与严重程度正交：

| | **规则覆盖了** | **规则没覆盖** |
|---|---|---|
| **内容看起来危险** | 正常定级 L1–L5 | `coverage_state = 未覆盖`，**等级未知**（不是 L0） |
| **内容看起来安全** | L1 | `coverage_state = 未覆盖`，**等级未知**（不是 L1） |

**四种组合都存在，而「L0」这一个值无法表达它们。** 把「未覆盖」编码成等级枚举的成员，会产生两个具体错误：

1. **它污染一致性系数**。α 的分母会把「未覆盖」当成一个判定结果参与计算 —— 但「未覆盖」不是判定，是**缺失**。这会让 α 虚高（两个人都不认识这条内容，会显示为「一致」）。
2. **它让「未覆盖」无法与「已知的高危」排序**。业务上「未覆盖」的处置优先级可能**高于** `L2 待复核`（因为它是完全的盲区），但作为枚举里最小的档，它会被排到最后。

**落地字段设计**：

```
coverage_state ∈ { covered, uncovered, partially_covered }
    # 与 severity 正交，独立字段
    # uncovered 时 severity 必须为 NULL，不得填 L0

severity ∈ { L1..L5 } | NULL
    # NULL 仅当 coverage_state = uncovered
```

**实测含义**：本文 §4.5 的「132 条待复核」里，**有多少其实是 `uncovered` 而不是「待复核」，是当前无法区分的** —— 因为现有表只有「待人工复核」一个值（§5.5 首表）。**拆出 `coverage_state` 后，这个数字才第一次可测。**

### 5.6 行业对「无规则时怎么办」的官方立场

**[判断] 官方答案不是「先拦着」。** R4 给出了三条法域的同一结构：

> **[原文]**（NIST AI RMF §5.2）
> `After completing the MAP function, Framework users should have sufficient contextual knowledge about AI system impacts to inform an initial go/no-go decision`

> **[原文]**（NIST AI RMF §1.2.1）
> `The inability to appropriately measure AI risks does not imply that an AI system necessarily poses either a high or low risk`

> **[原文]**（COM(2000)1 §6.2）
> `The absence of scientific proof … should not be used to justify inaction`

**[判断] 三条证据合起来说的是**：**「测不出来」不等于「高风险」，也不等于「可以不动」—— 它意味着「需要先做评估，再决定」。**

**三条法域的同构要求**：

| 法域 | 条款 | 要求 |
|---|---|---|
| EU AI Act | Art 9(2) | 全生命周期风险管理 |
| EU DSA | Art 34(1) | 风险评估（**至少每年一次**） |
| UK OSA | s.9(4) | 部署/变更前评估 |

**[判断] 所以对「要是没有呢」的完整回答是**：

1. **短期（现在）**：未命中 → **L0 未覆盖** → 转人工。**成本是人工量，不是风险。**
2. **中期（月）**：把重复出现的未覆盖原因**聚类**，升级为新规则。**这是规则库的主要增长方式。**
3. **长期（季）**：用**加权交叉表**看盲区（见 §5.7）。

**[判断] R4 穷尽检索后确认：「规则库覆盖率」没有标准定义。**

> ### ★ 8.0.1 α 首次实测完成（本文 §3.4「先对齐人」的前置条件已达成）
>

## 附录 C：引文的机械核验结果（`audit_citation_fidelity.py`）

本文与 6 个分片合计 **426 条引文**，已全部机械回查：每条引文被拉伸为整语料搜索，命中即记录**文件、字节偏移、原文上下文**；`EXACT` 表示逐字节命中。

> **一句话结论**：**424 条可判定引文中，无一条是凭空编造。** 有 1 条**行号标注错了 2 行**（已定位到原文），2 条含中文夹注未核验（已标出），其余全部在证据中逐字存在。
>
> **但达到这个结论的过程本身暴露了核验工具的两个严重缺陷 —— 见 C.2 与 C.4。**

### C.1 判定分类

| 判定 | 含义 | 处置 |
|---|---|---|
| `EXACT` / `TIGHT` / `PREFIX` / `MULTI` | 逐字命中（容差递增） | 通过 |
| `PARTIAL` | 主段命中，尾段是中文夹注 | 通过（夹注已标出） |
| `UNDECIDED` | 候选预算被截断且未命中 | **≠ 未命中**，须加大预算或人工 |
| `MISS` | 整语料找不到该连续字符串 | **必须人工看** |
| `NOT_QUOTE` | 去掉 markdown 链接后只剩几字符，本就不是引文 | 不算 MISS |
| **`SELF_REF`（本文新增）** | **命中来自工具自身产物**（自己证明自己） | **一律不算通过，见 C.2** |
| **`WRAP`（本文新增）** | **原文被折行/分栏切开，引者用空格拼成一行** | **须改写标注，见 C.3** |

### C.2 ⚠️ 最严重的一处：核验工具**自己证明自己**

**这是本轮发现的、比引文出错严重得多的缺陷 —— 它在核验工具内部，且制造「假通过」。**

`Table H-2 or Organization-defined` 这条在**任何真实证据文件里都不存在**。但工具曾把它判为 **`EXACT`**。原因是命中文件为：

```
match.file = _evidence/_citation_fidelity_misses.md   ← 工具自己上一轮写出的「未命中报告」
offset     = 504
```

**该引文正是被这份报告原样抄录的**（`grep -c` = **6**，与它报出的 6 条 MISS 一一对应）。链条是：

```
第 1 轮：真实语料里找不到 → 写入 _citation_fidelity_misses.md（记为 MISS）
第 2 轮：把该报告也当语料 → 在里面找到了自己 → 判 EXACT（通过）
```

**`_KNOWN_MISLABELS.md`、`_citation_fidelity_report.json`、`_integrity_report.json` 同样含逐字引文，同样构成污染源。** 这类缺陷的特征是：

- **越跑越「干净」** —— 未命中的引文被报告抄一遍，下一轮就「核验通过」；
- **自我强化** —— 报告越长，假通过越多；
- **在人类审阅时看不出来** —— 报告里明晃晃写着「EXACT + 命中文件」，看起来比 MISS 更可信。

**修正后重跑的对比（同一语料、同一输入）**：

| 判定 | 修复前 | 修复后 | 说明 |
|---|---:|---:|---|
| `EXACT` | 347 | **269** | **−78 条全是假通过** |
| `MISS` | 0 | **83** | 其中 **45 条**经穷尽归因确认**只存在于工具产物里**（见 C.6） |

**已修**（两处，互为冗余）：

1. `walk_evidence()` 排除 `_evidence/` **顶层**的 4 个产物文件名（`_is_self_artifact()`）。**只排除顶层**——`R1/raw/_body_*.md` 等 **427 个**下划线开头的文件是**真实证据**，必须留在语料内（已用 10 条单元用例正反验证）。
2. 判定处加**运行时断言**：只要 `match.file` 落在产物集内，一律钉成 `SELF_REF`，即使排除逻辑被改坏也不算通过。

> **由此得到本项目最值得外传的一条方法学结论**：
> **核验工具的产物绝不可进入它自己的语料。**
> 任何「证据卫生」工具都必须回答：**我写出的报告，会不会在下一轮变成我的证据？**
> 与 C.5 的假阴性、C.4 的标记形态问题同源 —— **机械核验的失效模式几乎全是「静默地变得过于宽松」。**

### C.3 唯一真实存疑的引文：不是编造，是**折行被拼平**

`Table H-2 or Organization-defined` 在 6 处出现，**还原污染后**整语料精确搜索 **0 命中**。逐字节回查确认：

- **确有原文**，在 `_evidence/R8/nist-sp800-30r1.txt` **L4813–4820**（TABLE H-4 模板的列头），引文所标的行号**准确**；
- 但原文是一个 PDF 表格单元格，**被折成三行**：

  ```
  Table H-2
  or
  Organization-
  defined
  ```

- 引者把三行**用空格拼成一行**。把空白与换行归一化后，该串在源文件中命中 **2 次**。

**这条判定仍是有效的保真度不合格，只是原因不是编造而是渲染失真**：读者按「同文件 L4813–4820」去核，在源文件里**搜不到**他看到的那个字符串。**正确写法**是保留换行，或写成 `Table H-2 / or / Organization-defined（原文三行）`。

> **C.3 的含义超出这一条**：**PDF 提取件里「表格单元格」会被折行，散文引文不会。**
> 本项目证据库的主体正是 PDF 提取件（NIST SP 800-30、GDPR、FTC、DSM 等），
> 所以**凡引自表的引文，都必须按「不可跨行拼接」处理**。
