## 三、怎么用

```bash
cd /Users/lute/Project/audit_multi_content

# 全流程（只读源系统，写飞书需显式 --apply）
python3 tools/kb_snapshot.py                  # ① 拉快照
python3 tools/kb_analyze.py                   # ② 结构分析
python3 tools/kb_build.py                     # ③ 生成台账
python3 tools/kb_index.py                     # ④ 索引本地资产
python3 tools/kb_evidence.py                  # ⑤ 需求→证据
python3 tools/kb_query.py --md                # ⑥ 查询手册（生成物）
python3 tools/kb_gaps.py                      # ⑦ 缺口登记表（生成物）
python3 tools/kb_facts.py                     # ⑧ README 事实块（生成物）
python3 tools/verify_kb.py                    # ⑨ 验收（C1–C10 / D1,D3 / E1–E5）

# 落飞书（有副作用，需显式确认）
python3 tools/migrate_kb_to_lark.py --apply
python3 tools/migrate_kb_to_lark.py --roundtrip   # 回读比对
python3 tools/kb_materials_lark.py --apply

# 直接问问题
python3 tools/kb_query.py 2      # 哪些需求逾期了
python3 tools/kb_query.py 8      # 哪些需求有证据、哪些零证据
```

**改口径的正确姿势**：改 `schema-v1.json` → 重跑 `kb_build.py` → 重跑 `verify_kb.py`。
不要直接改台账 JSON，那会让指纹失配，`load.py` 会当场拒绝装载。

**不要手改三个生成物**：`查询手册.md`、`缺口-v1.json`、README 的事实块 ——
它们由脚本重算，手改会被 E4/E5 逐字比对抓住（反向对照见 ADR-0013 §十四）。

## 四、这份知识库**做不到**的事（显式声明，不是遗漏）

> ★ **本节不复述数字。** 每一条都指向 `缺口-v1.json` 里的编号，量由
> `tools/kb_facts.py` 重算 —— 散文里的数字会腐烂，指针不会。
> 检查：`python3 tools/verify_kb.py`（E1/E2/E5）。

1. **算不出「卡在同一状态超过 N 天」。** 〔缺口:D1〕源系统只有当前状态，
   没有状态变更时间戳；用「提交日期至今」代替会把「一直没开始」和「做到一半
   停住」混为一谈。**另有四个疑似「开始时间」字段，语义未确认**〔缺口:D2〕——
   未确认前不得用于判据，否则会把「排期没到」算成「卡住了」。

2. **逾期率不能外推。** 只有少数记录有计划完成日期，「逾期 N 条」是那个子集里
   的事实，不是全部需求的事实。**基准日取快照日**（见 §一 事实表）：
   逾期是数据的属性，不是提问时刻的属性。

3. **「产出物为空」≠「没有产出物」。** 可能只是没填。这张表回答的是**可追溯性**。

4. **材料收得多，读得到的少。** 材料收集表只记「链接」，不记「这条链接我到底
   读不读得到」—— 于是「收集了 N 条」会变成错觉。**实测可读性见 §一 事实表
   最后一行**〔缺口:D3〕。

5. **品线字段有未归一的取值**（PSEO 的 `品类` 字段里写着一句话）〔缺口:D4〕，
   未归一的取值不参与任何品线口径的统计。

6. **三张空壳表**〔缺口:D5〕有表无内容，而空壳表会被当成「已覆盖的领域」。

7. **不判断需求该不该做。** 知识库只呈现事实与缺口（ADR-0005）。

**完整的缺口清单（8 条，五类）在 `缺口-v1.json`**：每条带编号、影响哪条黄金问题、
量、责任人、状态与复算命令。**「已登记」这句话现在指得出落点** ——
B3.0 之前它只是散文里的四个字。
