## 1. 指标一：内容获取成功率 —— 它不是站点属性

### 1.1 成对的两个数字

| 轮次 | 节流策略 | 成功 | 成功率 |
|---|---|---:|---:|
| 第一遍 | 只有同域名 1.2s 间隔，**无全局节流** | 28 / 92 | **30.4%** |
| 续抓 | 全局 6s 间隔 + 快速失败 | 64 / 64 | **100%** |
| **合计** | | **92 / 92** | **100%** |

**同一个站点、同一批 URL、同一份 User-Agent，唯一变量是节流策略。**

第一遍在第 28 个 URL 处被拦，之后 63 个 URL 全部返回 HTTP 429，
内容是 Cloudflare 的 `Verifying your connection...` 机器人验证页
（原始响应已存 `_evidence/…/raw/`）。

根因：**限制按来源 IP 施加**，而「同域名间隔」在跨域名时形同虚设 ——
`au` / `ca` / `de` / `es` / `fr` / `uk` 各自等 1.2s，出门却是同一个 IP，
实际速率是域名数的倍数。约 40 次请求后触发防护。

> **这条结论决定了怎么读任何一份「内容获取成功率」：
> 它是「获取策略 × 站点防护」的联合结果，不是站点的属性。**
> 只报一个数会同时冤枉站点、掩盖真问题。

### 1.2 分域名与分类型（最终口径）

10 个域名、4 类页面，**每一档都是 100%**：

| 域名 | 成功/分母 | | 页面类型 | 成功/分母 |
|---|---:|---|---|---:|
| `momcozy.com` | 41/41 | | 产品页 product | 48/48 |
| `ca.momcozy.com` | 12/12 | | 博客/其他 other | 24/24 |
| `de.momcozy.com` | 12/12 | | 集合页 collection | 13/13 |
| `uk.momcozy.com` | 8/8 | | 营销页 page | 7/7 |
| `fr` / `es` / `eu` / `au` / `pl` | 5/4/4/3/2 | | | |
| `www.amazon.de` | 1/1 | | | |

**Amazon 那 1 条抽查过**：正文 40,422 字符、标题 `Momcozy M5 Breast Pump : Amazon.de`、
无 captcha 字样。它是真的抓到了，不是反爬页被误判为成功。

### 1.3 一处被这轮推翻的判断（留档）

续抓途中 `es.momcozy.com` 的产品页返回 HTTP 500、`.js` 端点返回 429 挑战，
一度判断为「与速率无关的持续错误」。**续抓完成后该域名产品页全部 200。**

> 500 也是限流的副作用。教训：**在限流未完全冷却时观察到的「站点错误」，
> 先假定是自己的问题。**

## 2. 指标二：页面/素材识别完整度

**六类要素的达成率（分母 = 92 个成功页面）：**

| 要素 | 达成 | 覆盖率 | 说明 |
|---|---:|---:|---|
| `title` | 92 | 100% | |
| `body_text` | 92 | 100% | 正文 ≥ 200 字符 |
| `images` | 92 | 100% | 共 **23,745 张**图，其中 **90.2%** 有非空 `alt` |
| `claims` | 90 | 97.8% | 2 页零声明，见下 |
| `links` | 92 | 100% | 共 **21,524** 条站内链接 |
| `locale_signals` | 92 | 100% | hreflang / currency / lang |

**完整度均值 0.996，中位 1.000，90/92 六类齐全。**

**两项例外值得单说**：`de.momcozy.com/pages/breast-pump` 与
`…/breast-pump-winter-sale-in-europe` 是**纯图营销页** ——
各 127 张图、正文仅约 7,100 字符、**文本声明为零**。
这不是抓取失败，是这两页确实没有可判定的文本。
**对法务的意义**：文字审查覆盖不到它们，只能靠图片审查。

**声明密度（含该类的页面数 / 92）：**

| 类别 | 页面数 | 占比 | 例 |
|---|---:|---:|---|

| `absolute` 绝对化用语 | 86 | 93.5% | `Best` · `No.1` · `100%` · `perfect` |
| `certification` 认证 | 81 | 88.0% | `FDA` · `CE` · `GREENGUARD` · `BPA-free` |
| `comparative` 比较性 | 57 | 62.0% | `vs` · `World's First` · `Award-Winning` |
| `medical` 医疗相关 | 40 | 43.5% | `Hospital-Grade` · `therapeutic` |
| `health` 健康功效 | 36 | 39.1% | `Pain-Free` · `boost milk` |

> ⚠️ **上表是「页面上出现了这些词形」的清单，不是「这些表述有问题」的结论。**

**正文体量**：92 页共 **2,352,386** 字符，中位 **24,809** 字符/页

## 3. 指标三：处理耗时

| 路径 | n | P50 | P90 | P95 | max |
|---|---:|---:|---:|---:|---:|
| HTML 页面 | 92 | **2,181 ms** | 5,236 ms | 6,251 ms | 12,462 ms |
| 结构化端点（`.js`） | 44 | **377 ms** | 1,377 ms | 2,496 ms | 5,178 ms |

**结构化端点体积中位数是 HTML 的 1/64.4，耗时是 1/5.8。**

**但有一个反直觉的发现，必须写下来**：结构化端点的
`description` 字段**中位长度为 0 字符** —— 44 个商品里绝大多数这个字段是空的，
营销文案在 HTML 的其它位置。

> 所以：**结构化端点适合做「变更检测」的指针**（快、小、稳），
> **不适合做「内容审查」的来源**（拿不到文案）。
> 这不影响它作为监测能力的备选路径 —— 但选它之前必须知道它能给什么。

**抓取总墙钟 711.3 秒**（第一遍 245.5s + 续抓 465.8s）。
续抓过程中自适应节流从 6.0s 收敛回 2.0s，说明 6s 是偏保守的起步值。

## 4. 顺带发现的两类不一致（法务验证表之外的，但直接相关）

法务文档里两句话促成了这部分：

> 上线后持续监测：……有没有法务未看到的风险
> 整改与闭环：一个地方发现的风险，其他版本、页面和渠道是否同步整改

### 4.1 表 A · 广告文案 vs 落地页

**93 条广告**同时具备广告文案与已抓取的落地页正文，可比对。

| 项 | 读数 |
|---|---:|
| 至少一项广告声明未在落地页出现 | **33 条** |
| 其中广告本身已命中规则 | **29 条** |

出现最多的缺失声明：`Award-Winning`（5×）· `Pain-Free`（5×）· `280mmHg`（4×）·
`Perfect`（3×）· `World's First`（2×）· `Hospital Grade`（2×）。

> **口径修正留档**：第一版用严格子串匹配，报 42 条；逐条复核发现
> **假阳性率 20%**（广告写 `45dB`、页面写 `45 dB`；广告写 `300 mmHg`、页面写 `300mmHg`）。
> 加规范化后为 **33 条**。两个数都留在 `一致性分析.json` 里。
> **不做这一步，就会把「写法差异」当成「内容缺失」报给法务。**

**这是事实，不是结论。** 「广告有、页面无」是否构成问题、要不要整改，由法务判断。

### 4.2 表 B · 跨 locale 版本一致性

这批 URL 里有 **9 个产品横跨 2–9 个地区站**，是现成的跨版本测试集。
数字类声明跨语言应当一致（翻译会变，参数不会）。实测 **4 个产品不一致**：

| 产品 | 不一致项 | 各地区取值 |
|---|---|---|
| `momcozy-mobile-flow` | `dB` | CA/DE/EU/UK = **42**；US = **48**；FR = 42 **与** 48 都有 |
| `wellness-1 (W1)` | 认证词 | DE/ES/UK = **CE**；US/FR = **FDA** |
| `v1-pro` | `mmHg` | CA/DE/US = **300**；UK = **288 与 300** |
| `s12-pro` | `mmHg` | DE = **292, 295**；US = **292** |

**同一产品在不同地区站自报不同参数/认证**，正是法务「跨页面、跨版本整改闭环」
要防的情形。**此处同样只呈现差异，不下判断。**

### 4.3 一条改实现口径的发现：内容指纹不能建在原始 HTML 上

验收器 V4 抽检重抓时，**3/3 的页面原始 HTML 指纹都变了**。查清了原因：

```
旧: <script id="__st">var __st={"a":65928953919,…,"reqid":"339c19df-…-1789545921",…
新: <script id="__st">var __st={"a":65928953919,…,"reqid":"06e9eaf8-…-1789548441",…
```

差异只有 9–14 行，全部是 **Shopify 内嵌的每次请求唯一 `reqid`** 与埋点脚本。
页面内容本身没变（字节数 990,837 → 990,837）。

**于是做了一次对照实验：**

| 指纹建立在 | 结果 |
|---|---|
| 原始 HTML 的 sha256 | **3/3 变化** —— 不可用 |
| **提取后正文**的 sha256 | **3/3 逐字节一致** —— 可用 |

> **结论（直接改 ADR-0002 的实现口径）**：
> **内容指纹必须建立在「提取后的正文」上，不能建立在原始响应上。**
> 对原始 HTML 做哈希会把「每次请求都不同的追踪 ID」误判成「内容变了」，
> 于是「这条需求/这个页面还是不是同一个」这个问题**永远答不了**。
> 这个坑不测就发现不了 —— 因为所有页面看起来都「变了」。

`verify_landing.py` 的 V4 现在**同时测两种指纹并分别报告**，
把这个区别固化成了验收项。

## 5. 本批次**做不到**的事（显式声明，不是遗漏）

1. **这 92 个页面 ≠ 公司对外发布的全部内容。** 它们只是 291 条在投广告所指向的落地页。
   **覆盖率本批次未测**，不能由它推断「官网没有别的问题」。
2. **不能回答「多久会被再次拦住」。** 只跑了一轮，且 6s 是通过值而非稳健水位。
   要回答它需要一次跨小时的持续速率实验 —— **那不该拿生产站点做**。
3. **反爬之外的 JS 渲染内容抓不到。** 本批次用标准库 `html.parser` 解析静态 HTML。
   实测正文中位 24,809 字符说明主要文案在静态层，但**轮播/弹窗/延迟加载的内容会漏**。
   页面正文里混有视频播放器 UI 文本（`PlayMuteUnmuteShare…`）这类噪声，未做清洗。
4. **`claims` 是词形清单，不是判定。** 本批次不回答任何「是否合规」。
5. **只测了一次快照。** 没有变更检测、没有定时化 —— 「持续监测」是另一件事。
6. **广告侧比对只覆盖 93/204 条。** 广告文案字段（`Primary Text`/`Headline`）
   本身填充不全，不是抓取问题。
7. **图片只统计了数量和 alt，没有看内容。** 法务 PRD 要求跑图片素材，
   那需要视觉能力，本批次没有。

## 7. 对下一批次（A · 判定引擎产品化）的三条输入

1. **判定引擎的输入契约必须显式化。** 本批次产出的是**落地页正文**，
   这是引擎此前从未处理过的内容类型（此前只吃广告文案的 `Primary Text`/`Headline`）。

   但引擎目前把 `_find_literal` 算出的 `(start, end)` 丢掉了。
3. **别把「抓取成功」当成「可以开始监测」。** §5 第 2、5 条是硬边界。
