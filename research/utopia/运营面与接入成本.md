## 0. 口径：这份报告怎么区分「设计」与「代码」

Utopia 的文档体系是它最突出的工程特征，也是最容易读错的地方。`docs/design/README.md:3-8` 自己写明了规矩：

> "`docs/design/` says what the system does today, one file per domain. … `docs/decisions/` says why: each record is history, written once and never rewritten."

**但这条规矩本身在这份检出里已经裂开**。三条硬证据：

1. `docs/design/README.md:105-106` 把 **0044 与 0045 标成 `proposed`**（"the code is not yet on `dev`"），而同一天（2026-09-23）HEAD 上已经躺着 `0063_extraction_reads_only_the_open_graph.sql`（0044 决定 2 的落地）、`0064_a_time_mention_is_resolved_against_its_document.sql`（0045）和 `0074_an_errata_agent_reviews_the_typed_graph.sql`（0044 决定 7）。`0044` 自己的状态行（`docs/decisions/0044-*.md:3`）写的是 "cut 1 built … cut 2 in progress … **the errata agent (cut 6) built**"——**同一份仓库里，索引表比它索引的记录旧**。
2. `docs/design/ontology.md:14-17` 写 "typed facts will come only from alignment（**0044 cut 2, not built**）… A base extracted today holds open statements and name facts and **no typed facts**"，而 `crates/utopia-store/src/materialize.rs` 是一整个已实现的模块，文件头写 "绑上的签名下的开放陈述算成类型化事实（0044 决定 3 的第三、四片，见 0067、0068）"，且被 `crates/utopia-server/src/phrase_alignment.rs:562` 真实调用。
3. `docs/decisions/0014-*.md:3` 写 "**`can_write` is still hard-coded `false`**, so a `write` scope changes nothing yet"，而 `crates/utopia-server/src/api/mcp.rs:107-110` 已经把 `can_write` 算成 `auth.can_write() && kb_role >= Editor`。`docs/design/access-and-audit.md:73-74` 自己把这条列为 open question："check the code before relying on either."

**所以本报告的口径是**：凡涉及「有什么」，一律以 `crates/` 与 `migrations/` 的 grep 为准；凡引用 `docs/`，只当作**意图**与**理由**，并在每处标明它是否被代码证实或证伪。这条对「接入成本评估」至关重要——Utopia 的文档会让人高估它的完成度。

## 1. 数据源与连接器

### 1.1 文件格式：代码里真实存在的解析器

唯一入口是 `crates/utopia-ingest/src/lib.rs` 的 `parse(filename, bytes)`（`:303`），它先看**文件头**再看扩展名（`:316-317` "魔数探测优先于扩展名（扩展名可能撒谎）"）。

| 格式 | 实现 | 证据 |
|---|---|---|
| **PDF** | `parsers::pdf`（`pdf_extract`，失败回退到**外部进程 `pdftotext`**） | `parsers.rs:59`；`lib.rs:320-331` |
| **DOCX** | `parsers::docx` | `lib.rs:332` |
| **XLSX / XLS / ODS** | `parsers::spreadsheet`（calamine，每 sheet 前 2000 行） | `parsers.rs:532`；`lib.rs:333` |
| **PPTX** | `parsers::pptx` | `lib.rs:334` |
| **HTML / HTM** | `html::page_to_markdown`（Readability + Markdown 转换 + 表格按 DOM 重建） | `parsers.rs:580`；`html.rs` 605 行 |
| **CSV / TSV** | `parsers::csv_text`（前 10,000 行，`flexible`） | `parsers.rs:584` |
| **MD / JSON / YAML / XML / LOG / TXT 及一切未识别文本** | `parsers::plain_text`，chardetng 探测编码 | `parsers.rs:10`（"覆盖 GBK/GB18030/BIG5 等中文常见编码"） |
| **图片**（png/jpg/jpeg/gif/bmp/tif/tiff/webp/heic/heif） | 不解析，返回 `NeedsReader(Reader::Ocr)` | `lib.rs:242-244, 260-265` |
| **录音**（mp3/wav/m4a/flac/ogg/oga/opus/aac/amr/wma） | 不解析，返回 `NeedsReader(Reader::Transcribe)` | `lib.rs:245-247, 266-271` |
| **视频**（mp4/mov/mkv/avi/webm/m4v/wmv） | **明确拒收** `Unreadable("Video files are not read yet; upload its audio track or a transcript")` | `lib.rs:248, 272-276` |
| **二进制**（老式 .doc、压缩包、可执行文件） | 拒收，不当文本解码 | `lib.rs:285-298, 340-344` |

一个值得注意的细节：`lib.rs:280-284` 的 `looks_binary` 判定要求「**开头夹着 NUL 而且不是合法 UTF-8**」两条同时成立——因为 PDF 文本层抄出来的正文会夹 NUL 但合法（#611），而 GBK 不是合法 UTF-8 但不夹 NUL。这是被真实数据打磨过的痕迹。

### 1.2 活连接器：14 种枚举，9 种真会拉取

`SourceKind` 枚举在 `crates/utopia-core/src/models.rs:269-286`，共 **14 个变体**：

```
Folder, Url, Rss, GithubIssues, JiraIssues, S3, AzureBlob, Gcs, Webdav,
Notion, Api, Custom, Memory, Upload
```

`creatable_by_hand()`（`:302-304`）排除 `Memory` 与 `Upload` → **界面上可建 12 种**。分派在 `crates/utopia-server/src/ingest_sources.rs:80-95`，注释写明"按枚举穷举：加一种来源就得在这里决定它怎么同步，编译器不放过漏掉的那一支"：

| 种类 | 同步实现 | 拉取 |
|---|---|---|
| `url` | `sync_urls` | ✅ HTTP GET 列表 |
| `rss` | `sync_rss` | ✅ 见 §1.4 |
| `custom` | `sync_custom`（`?since=` RFC3339 增量） | ✅ |
| `github_issues` | `sync_github_issues` | ✅ 见 §1.3 |
| `jira_issues` | `sync_jira_issues` | ✅ 见 §1.3 |
| `s3` / `azure_blob` / `gcs` | `sync_object_storage` | ✅（object_store crate） |
| `webdav` | `sync_webdav` | ✅ |
| `notion` | `sync_notion` | ✅ |
| **`folder` / `api` / `memory` / `upload`** | `Ok(SyncStats::default())` | ❌ **被动容器，无拉取语义** |

即：**代码里真实存在的「活连接器」是 9 种**（url / rss / custom / github_issues / jira_issues / s3 / azure_blob / gcs / webdav / notion 中 notion 与 webdav 各算一种，共 10 个分支，其中 3 个对象存储合并为一个分支）。

凭据处理：`SOURCE_SECRET_KEYS`（`models.rs:229-236`）点名六个键——`auth_header`、`token`、`password`、`secret_access_key`、`account_key`、`service_account_key`——`Source::without_secrets()` 从任何回给客户端的响应里剥掉。ADR-0013 §127 记着这条的来由："Until now only `auth_header` was stripped … The object-storage, WebDAV and Notion keys went out to every viewer."

### 1.3 增量重同步与「历史交接」（ADR-0013）

这是 Utopia 连接器设计里最实质的一条，且**确实落地了**。

`ingest_sources.rs:70-75`：

```rust
let since = match kind {
    Some(SourceKind::Custom | SourceKind::GithubIssues | SourceKind::JiraIssues) => {
        utopia_store::sources::last_successful_sync_start(&state.pool, source_id).await?
    }
    _ => None,
};
```

**只有这三种走 `since`**；url / rss / s3 / webdav / notion 每轮全量比对（靠 `external_key` + sha256 去重，不靠时间窗）。

ADR-0013 §1 的核心决定（`docs/decisions/0013-*.md:23-27`）：

> "**One ticket is one document, and the body carries the history.** … a heading, dated declarative sentences (`Currently Closed.`, `Resolved on 2011-07-19.`), a `## History` list of `date — who changed Field: A → B` … **Sentences with dates, never key-value pairs**: `Opened by X on 2026-08-18` extracts to a fact with `valid_from`; `created_at: 2026-08-18` leaves the model to guess."

代码证实：`crates/utopia-server/src/github_issues.rs:113` 有 `pub fn render(issue, comments, events) -> String`（纯函数、无网络，所以可测），`:158` 写 `out.push_str("\n## History\n\n")`。Jira 侧 `jira_issues.rs:160` 同形，`:218-239` 把 `changelog.histories` 渲染成同一节。

GitHub 的具体形态在 `ingest_sources.rs:736-745` 的文档注释里说得很直白：

> "工单与评论走**仓库级 + `since`**（一次分页取全），事件走**逐工单**——不是不一致，是 `issues/events` 不支持 `since` 且会被 PR 事件淹没，拿真实仓库一跑就发现状态变更史悄悄空了。"

Jira 的三个坑记在 ADR-0013 §3（`:37-42`）：时间是 `2026-08-24T11:11:52.944+0000`（偏移量没冒号、不是 RFC3339）、增量没有 `since` 要走 JQL `updated >= "…"`、`fields` 必须显式列出（省略 `comment` 就没有评论）。代码里 `jira_issues.rs:270` 是 JQL 构造，`:299` 是 `expand=changelog`，`jira_issues.rs:360` 的测试断言 `q.contains("updated >= \"2026-08-30 12:34\"")`。

**身份与版本**在 `ingest_item_with_outcome`（`ingest_sources.rs:240-360`）里：
- 主判定按 `external_key`，找不到时按文件名认领历史文档并补键（`:259-278`）
- 内容相同（sha256 一致）→ `Unchanged`，不动管道
- 已删除的文档重新出现 → 先 `restore` + 重建索引 + `settle_derivations`，写一行 `document.restored` 审计（`via: "sync"`），再比内容（`:280-305`）
- 内容变了 → `replace_content_and_enqueue_processing`，旧版本入 `document_versions`
- **同内容换路径** → `Moved`，只改 location **不重跑管道**（`:325-333`）——这是"换了前缀但内容没变时，`ingest_item` 会认成「搬家」而不是新增"（`:1034-1035`）
- 库里已有同内容 → `Conflict` 被吞成幂等结果（`:355-359`）

时间精度：ADR-0013 §6 原决定"截到天"，**2026-09-14 修订（#691）改为写到秒**——"the GitHub and Jira connectors now write `2026-08-18T16:18:27Z`, and the extractor reads it back at second precision"（`0013-*.md:67-70`）。

截断有明确上限且**会说**：`MAX_NEW_PER_SYNC = 200`（`ingest_sources.rs:19`），RSS 在途 `RSS_MAX_INFLIGHT = 25`（`:21`）。ADR-0013 §5："When the fetched count is below `total`, a warning says this round covered a slice, otherwise 'sync complete' misleads."

### 1.4 RSS：观察不是文档

`docs/decisions/0023-rss-observations-are-not-documents.md` 的模型在代码里体现为 `migrations/0032_rss_full_content.sql` 的 `rss_full_content_entries` 表，`entry_kind IN ('baseline','candidate','no_source')`，带 `activation_generation`。

`ingest_sources.rs:596-601` 把 feed 解析器的 id 生成器**打桩成返回空串**，理由是真实注释：

> "feed-rs normally synthesizes missing entry IDs from link + title (or a random UUID). Neither is an application-level stable identity. Leave missing IDs empty so rss_entry_key can use only the stable article URL."

正文补全走 `crate::http_fetch::get(..., Reach::Operator, ...)`，`Reach::Content` 与 `Reach::Operator` 是两种信任级（`http_fetch.rs:10-13`）——`Content` 那一路会拒内网地址、逐跳重检重定向、拒绝 https→http 降级。

**没有 GUID 也没有文章链接的条目会被跳过**（`ingest_sources.rs:610` 的 `rss_entry_key(entry, article_url.as_deref())?`，返回 `None` 就 `filter_map` 掉）。

## 2. 检索

### 2.1 三件套：内嵌 Tantivy + pgvector + RRF

**全文**在 `crates/utopia-search/src/lib.rs`（223 行）：内嵌 Tantivy 0.26 + `tantivy-jieba`，**单索引多 KB**（`:2` "kb_id 作过滤字段；chunk 正文在 Postgres，索引里只存 id 映射"）。检索**不走 `QueryParser`**：

> `lib.rs:125-126`："查询用与索引完全一致的 jieba analyzer 切词后按 OR 组合——不能走 QueryParser：CJK 整句会被当成短语查询（要求词连续出现），召回归零。"

**向量**在 `crates/utopia-store/src/vector_index.rs`：列是无维的 `embedding vector`（`migrations/0002_ingest.sql:101`），**HNSW 索引由任务建**（`JOB_KIND = "build_vector_index"`），因为"维度跟着工作区选的嵌入模型走，迁移跑的时候还不知道"（`vector_index.rs:1-6`）。三条读路径规矩写在 `:13-19`，其中第 3 条是实测出来的：

> "**`hnsw.iterative_scan = relaxed_order`.** HNSW 先取 `ef_search` 个候选再过 WHERE；一张按 kb 分租的表上，小库的行在候选里占不到几个，`LIMIT 10` 会回三行甚至零行（**实测 1 万行的库在 6 万行的表上：关着回 3/24，开着回满**）。"

`MAX_DIMS = 2000`（`:41`），超过就永不建索引、走精确扫描——注释点名 `text-embedding-3-large` 是 3072 维。

**融合**在 `retrieval.rs` + `rrf_fuse`（`utopia-search/src/lib.rs:174-185`，k=60）。`crates/utopia-server/src/retrieval.rs` 的 `hybrid()`：

- 两路**并行**（`tokio::join!`，不是 `try_join!`），BM25 在 `spawn_blocking` 上——`:15-18` 解释："两路从前还串着：BM25 跑完才去调嵌入端点，嵌入回来才查向量，而嵌入是一次网络往返、整个函数最贵的一项，跟 BM25 毫无依赖。并起来之后延迟是两路取大，不是相加。"
- 每路召回 `RECALL_PER_CHANNEL = 24`（`:22`）
- RRF 之后再按 `as_of` 过滤、最后 `truncate(top_k)`——`candidate_limit = lists.iter().map(Vec::len).sum()`，注释："newer hits must not consume a historical query's limit"
- 通道顺序钉死（`channel_lists`）："BM25 恒在第一位，向量有就在第二位。顺序钉死、不看谁先回来"

### 2.2 降级是静默的，但只在模型这一侧

`retrieval.rs:66-71`：

> "没配嵌入模型、嵌入请求失败、回了空，都是 `Ok(None)`：检索照常，只剩 BM25——这就是模块头说的静默降级。**向量查询本身失败仍是 `Err`：那是库的事，不是模型的事，吞掉会把坏库伪装成没配模型。**"

### 2.3 记录轴（`as_of`）在检索上只做了一半——代码自己写明了

`retrieval.rs:4-9`，这是这份代码里最诚实的一段注释之一：

> "**`as_of` 只在向量与取块这两处是完整的**（0019 开放问题②）。Tantivy 的索引只有"现在"一个版本：重解析会把文档的块整批换掉，旧版本不在索引里。所以，带时刻检索时，BM25 找回来的东西**是对的**（随后按当时的活性过滤），但它找不回当时有、如今已被顶掉的那些块——**召回缺一角，命中不会出错**。"

### 2.4 查询时的「分块出处」：证据层完整，检索层缺失

这是任务明确要问的一条，答案分两层，**必须分开说**。

**检索层的返回结构里没有出处。** `ChunkView`（`crates/utopia-core/src/models.rs:436-442`）只有五个字段：

```rust
pub struct ChunkView { id, document_id, seq, text, filename }
```

`POST /api/v1/kbs/{id}/search` 直接返回 `{"results": chunks}`（`search_routes.rs:38`）。MCP 的 `search_chunks` 的 `structuredContent` 同样只有 `chunk_id / document_id / seq / filename / text / truncated`（`tools.rs:208-220`）。**`origin` / `origin_model` / `anchor` 一列都不在里面。**

**证据层是完整的。** `chunks` 表上有三列（`migrations/0058_a_chunk_says_where_its_words_came_from.sql`）：

```sql
ALTER TABLE chunks
    ADD COLUMN origin TEXT NOT NULL DEFAULT 'stated'
        CHECK (origin IN ('stated', 'ocr', 'transcribed', 'described')),
    ADD COLUMN origin_model TEXT,
    ADD COLUMN anchor JSONB;
```

并且有一个**形状随来源而变的 CHECK 约束**（同文件）：

```sql
ALTER TABLE chunks ADD CONSTRAINT chunks_anchor_matches_origin CHECK (
    (origin = 'stated' AND anchor IS NULL AND origin_model IS NULL)
    OR (origin = 'ocr' AND anchor ? 'page')
    OR (origin = 'transcribed' AND anchor ? 'start_ms' AND anchor ? 'end_ms' AND anchor ? 'speaker')
    OR (origin = 'described' AND anchor IS NOT NULL)
);
```

`crates/utopia-ingest/src/provenance.rs:3-5` 说清了为什么这四档必须分开：

> "这四种不是同等的证据：前三种是「原话，照读」，人能对着页面或录音核对；第四种是模型对一张图的转述，没有原话可对。"

锚点的生成逻辑在 `reading.rs`：扫描件按页分段（`mineru.rs`），一页一段，块切好之后把它盖住的那几个区域的框**并成外接矩形**写进 `anchor.bbox`；录音整段一段，块的锚点取它盖住那几句的**最早开始、最晚结束和出现过的说话人**（`reading.rs:60-98`）。

**但查询时谁能看到出处？**

| 路径 | 带 origin/anchor？ | 证据 |
|---|---|---|
| `POST /kbs/{id}/search` | ❌ | `search_routes.rs:38`（`ChunkView`） |
| MCP `search_chunks` | ❌ | `tools.rs:208-220` |
| MCP `get_document` | ❌ | `tools.rs` 用 `chunks_in_document` → `ChunkView`（`documents.rs:1716-1728`） |
| MCP `changes` | ✅ 只有 `quote_origin` | `tools.rs:627` |
| `GET /kbs/{id}/facts/{fid}/evidence` | ✅ **完整**（quote / origin / origin_model / anchor / doc_version / stale / document_deleted） | `models.rs:994-1024`（`EvidenceView`）；`graph_routes.rs:451` |
| 文档查看器 `chunks_full` | ✅ | `documents.rs:1539-1551`（`ChunkFull`） |
| RDF 导出 | ✅ | ADR-0020 |

**结论**：`docs/design/chat-and-mcp.md:23-25` 说 "MCP results carry `structuredContent` with ledger UUIDs and **each evidence row's origin**" ——**这一句只对 `changes` 成立**。一个只走 `search_chunks` 的 MCP agent，无法分辨它引用的这句话是原文写的、OCR 认出来的、还是模型看图描述出来的。这对「证据链回到条款原文」的需求是实质缺口（见 §8(d)）。

（Web 侧倒是有的：`web/src/pages/DocViewer.tsx:116-119` 用 `originLabel` / `originHint` 在分块上打标签。）

## 3. HTTP API 面

### 3.3 认证模型

**会话**：JWT HS256，HttpOnly Cookie `utopia_token`（同时接受 `Authorization: Bearer`），TTL **7 天**，口令 Argon2（`crates/utopia-server/src/auth.rs:20-21, 29-45, 110-140`）。`Secure` 由 `X-Forwarded-Proto` 推（`behind_tls`，`:66-74`），可用 `UTOPIA_COOKIE_SECURE=true` 强制。`clear_auth_cookie` 的属性必须与签发时一致——`:87-90` 记着踩过的坑："只给名字的话 path 会退化成当前请求路径…cookie 留在浏览器里，人以为自己登出了。"

**个人令牌**（`migrations/0017_personal_tokens.sql`）：前缀 `utp_pat_`，**SHA-256 哈希存**（不是 argon2，理由见 `tokens.rs:48-56`：高熵随机串 + 校验是热路径要走唯一索引），`scope IN ('read','write')` 默认 read，`kb_ids` 可空（空=该人能进的全部），`expires_at`（界面默认 90 天），`last_used_at`，**撤销不删行**（`revoked_at` 留痕）。第 0017 号迁移的注释把「为什么存法与来源 token 不同」写得很清楚：

> "**爆炸半径不同，所以存法不同。** 那一条（`sources.ingest_token` 明文）的理由是「DB 失守时文档本体早已泄露，哈希化没有额外收益」，而它成立是因为 ingest_token 只能**往里推文档**。这一把不一样：它经 `query_data` 能读出 Utopia 之外的生产库。"

**这里有一个对集成方最关键的限制**：**个人令牌只能用在 MCP 端点上**。

```

crates/utopia-server/src/api/mcp_tests.rs:240,338,396   (测试)
（生产代码只有 mcp.rs:94 一处）
```

会话提取器 `AuthUser`（`auth.rs:113-140`）**只解 JWT**，不认个人令牌。所以「拿一把长期钥匙去调 `/chat` 或 `/search`」这条路不存在——要么用 7 天过期、不可撤销的 JWT，要么走 MCP。

**RBAC**：`Role { Viewer, Editor, Admin, Owner }`（`models.rs:55-60`）+ `users.is_admin`。核心守卫是 `utopia_store::access::require_kb(pool, user, kb_id, min_role)`（`access.rs:83`）。我在路由层数出的角色分布：

### 4.1 MCP 服务端：一个端点，12 个工具

`crates/utopia-server/src/api/mcp.rs`（265 行）实现 Streamable HTTP MCP：

```
POST /api/v1/kbs/{kb_id}/mcp

```

关键设计决定写在文件头 `:1-18`：

> "**传输选 Streamable HTTP 不选 stdio** … **每个 POST 都重新认证一次。** 规范允许把一次握手的结果沿用整条连接，而 0014 那条纪律说得很清楚：『校验 scope 要在每个工具入口，不在握手。`revoked_at` 中途被写上时必须立刻生效。』这里做成无状态之后，那条性质是白得的——**没有「连接」这个东西可以被信任**。"
> "**响应用 `application/json` 而不是 SSE。**"

### 4.2 细粒度权限控制在 MCP 上是怎么做的

答案：**两道收窄，粒度是「库 × 读/写」，没有更细的**。

`mcp.rs:71-112` 的 `authorize()`：

```rust
/// 认证 + 授权。**两道，不是一道。**
/// 令牌说「这是谁、这枚钥匙够到哪几个库」；`require_kb` 说「这个人在这个库里是什么角色」。
/// 前者只收窄，后者才是权限——一枚 scope 全开的令牌落在一个 viewer 手上，仍旧只是 viewer。
```

具体四步（`:89-111`）：
1. `Bearer` 取出 → `tokens::authenticate` → 得 `user_id / token_id / scope / kb_ids`
2. `auth.covers(kb_id)` 不过 → 403（令牌限定的库之外够不着）
3. `accounts::find_user_by_id` → 停用立即生效
4. `access::require_kb(..., Role::Viewer)` → 角色守卫，**与网页端走同一个函数，一行没改**

有效写权限（`:105-110`）：

```rust
/// **收窄两次。** 令牌勾了 write 只是没把写排除掉；能不能写，问的是这个人
/// 在这个库里的角色——一枚 scope 全开的令牌落在 viewer 手上仍旧只能读
let can_write = auth.can_write()
    && utopia_store::access::kb_role(&state.pool, &user, &kb).await?
        .is_some_and(|role| role >= Role::Editor);
```

**能力边界要说清楚**：
- ✅ 令牌级：限定到哪几个 `kb_ids`
- ✅ 令牌级：`read` / `write` 两档 scope
- ✅ 角色级：viewer / editor / admin / owner
- ✅ 工具级：写工具单独一张白名单（`WRITABLE`）
- ❌ **没有按工具勾选的白名单**——不存在「这把令牌只能用 `search_chunks` 不能用 `changes`」
- ❌ **没有字段级/行级权限**
- ❌ **没有速率限制、没有配额**
- ❌ 也没有「机器身份」：`migrations/0017` 明确拒绝了机器令牌（"机器身份要引入第三套授权模型，而且 `audit_events.actor_id` 会多出一类「不是任何人做的」记录"）

### 4.3 Agent 循环：rig runner + hooks

`crates/utopia-server/src/api/agent.rs:1-14`：

> "从前 `chat.rs` 里手写着一个 1,100 行的循环，每个策略问题都落成它里面的又一个分支… 这里把循环换成 rig 的：工具是 `DynamicTool`，策略是钩子，终止是**结构性的**——**一轮对话在调过至少一个工具之前不能结束。**"

政策清单（`docs/design/chat-and-mcp.md:9-19` 与代码对应）：
- 首轮 `tool_choice: required`，直到某个工具跑过
- `no_evidence_needed` 是「这题不用查」的**诚实出口**（`agent.rs:36-42`）——"不是每个问题都关于库里的数据，而强迫模型对「你好」跑一次检索是另一种错"
- `MUST_CALL` 兜底句（`:44-49`），**没有 DONE 出口**
- 空回复重问**一次**（`EMPTY_REPLY_RETRY`，`:53-62`），第二次还空才报错
- 工具预算用尽后仍尝试调工具 → `FINAL_TOOL_CALL` 错误（`:71`）
- 终答上限 `MAX_FINAL_ANSWER_BYTES = 1024 * 1024`（`:70`）
- 降级到一次性 RAG **只在首个带工具请求返回 400/422 时**（`chat-and-mcp.md:17-19`）

**聊天侧的工具集**比 MCP 多：`tools_schema(can_write, data_source_names)`（`chat.rs:61-135`）= 11 个基础 + `query_data`（仅当有挂载数据源，`:63-98`）+ `remember`（`can_write && REMEMBER_ENABLED`，`:99-135`）→ **最多 13 个**。`REMEMBER_ENABLED: bool = true`（`chat.rs:49`）留作拉闸开关，理由注释写得很实在：

> "它那时会把一句话直接变成图上一条活边，实测里「记住 Acme 把总部搬到了深圳」落成的是一条**空谓词、0.9 置信**的边… 这个开关留着，是为了下次再发现「工具会悄悄改图」时有地方立刻拉闸——**宁可没有这个工具，也不要一个会悄悄改图的工具。**"

**参数守卫** `check_call`（`chat.rs:152-200`）：JSON 合法性 + 必填项 + schema 里写了 `format: uuid` 的格式。空串与 null 都算没给（"`{"query": ""}` 检索出来的东西与问题无关，而它同样会显示成一条正常的轨迹"）。MCP 侧共用同一把尺（`mcp.rs:221-227`），注释："与聊天共用参数守卫：缺少 query 不能变成一次成功的空搜索。"

## 5. 治理、审核队列与审计台账

### 5.1 审计台账：写什么、何时写、只增怎么保证

**表结构**（`migrations/0007_audit.sql`）：

```sql
CREATE TABLE audit_events (
    id, kb_id, actor_id, action TEXT NOT NULL, target_kind TEXT NOT NULL,
    target_id, detail JSONB NOT NULL DEFAULT '{}', created_at,
    client_ip, user_agent, actor_label
);
```

三处非显然的设计，注释都写了理由：
- **`kb_id` 与 `actor_id` 是裸 UUID，没有外键**："台账不该依赖它所记录的对象存活：kb_id 若级联删除，删掉一个知识库就删掉了它的全部审计记录——包括刚刚写下的那条 `kb.deleted`，**删除是最需要留痕的动作，却成了唯一不留痕的**。"
- **`client_ip` / `user_agent`**："ISO 27001 A.8.15 要求日志覆盖 Where / How…没有它，一个账号被盗用后的所有活动看起来与本人操作毫无差别。"
- **`actor_label`** 是操作者邮箱快照——"用户停用时行会留下，但 LEFT JOIN users 取不到名字，界面只剩一串 UUID。"

**写什么**：全仓只有一个 `INSERT`（`crates/utopia-store/src/audit.rs:73`）。动作名是**自由字符串，没有 enum、没有常量表**。我在代码里数出 **66 个不同的 action 字面量**，分族如下：

| 族 | 动作 |
|---|---|
| 审核/合并 | `review.merge`、`review.keep`、`merge.manual`、`merge.revert` |
| 事实 | `fact.confirm`、`fact.reject`、`fact.close`、`fact.time_corrected`、`fact.nod_confirmed`、`fact.nod_rejected` |
| 冲突 | `conflict.close_old`、`conflict.keep_both`、`conflict.reject_new` |
| 对齐/勘误 | `alignment.phrase_decided`、`alignment.kind_word_decided`、`alignment.rule_decided`、`alignment.materialized`、`errata.reviewed`、`errata.decided` |
| 本体/规则/映射 | `ontology.*`（8 个）、`rule.created\|updated\|deleted`、`mapping.written\|revised\|decided` |
| 库/来源/文档 | `kb.updated\|deleted\|exported\|member_set\|member_removed`、`source.*`、`document.deleted\|restored\|purged` |
| 身份与工具 | `auth.*`、`token.issued\|revoked`、`user.deactivated\|reactivated`、**`mcp.tool_called`** |
| 引擎 | `graph.rebuild`、`inference.materialized`、`jobs.requeued`、`consistency.checked`、`violation.decided`、`defect.decided` |

**何时写**：业务动作提交之后，由路由/任务层各写一行，且**一律 `let _ =`**。`audit.rs:1-2` 明说：

> "审计日志：谁在何时对什么做了什么。纯审计——只记录与展示，不承载回滚等衍生功能。**记录失败绝不影响业务操作（调用方一律 `let _ =`）。**"

**两个后果必须点出来**：① 台账不在业务事务里，记的是「试过」不是「成功过」；② 记录失败是**静默**的——没有告警、没有重试、没有计数器。

**只增怎么保证——三层，强度递减**：

1. **触发器**（`0007_audit.sql:48-62`）：
```sql
CREATE FUNCTION audit_events_immutable() RETURNS trigger AS $$
BEGIN
    RAISE EXCEPTION 'audit_events is append-only (attempted %)', TG_OP
        USING HINT = 'Audit records cannot be modified or deleted.';
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER audit_events_no_update_delete
    BEFORE UPDATE OR DELETE ON audit_events FOR EACH ROW EXECUTE FUNCTION audit_events_immutable();
-- TRUNCATE 不触发行级触发器，单独挡一道，否则一句 TRUNCATE 就绕过了上面全部。
CREATE TRIGGER audit_events_no_truncate
    BEFORE TRUNCATE ON audit_events FOR EACH STATEMENT EXECUTE FUNCTION audit_events_immutable();
```
注释自认边界："**它挡不住 superuser**——那个身份可以 DROP TRIGGER 或 ALTER TABLE ... DISABLE TRIGGER 之后从容修改。所以这一层的作用是把门槛从「顺手就能改」抬到「必须先动 DDL」."

2. **权限**（`0010_least_privilege_role.sql:28`）：`REVOKE UPDATE, DELETE, TRUNCATE ON audit_events FROM utopia_app;` —— **但这是可选的，且默认没启用**（角色不存在整段跳过；连接串在 `.env.example` 里是注释掉的）。**默认部署里这一层不存在。**

3. **哈希链**：**不存在。** `0007_audit.sql:9` 与 `:43` 两处提到它（"这也是哈希链的前提"、"要让蓄意篡改也无所遁形，得靠后续的哈希链"），但

```
$ grep -rn "prev_hash\|chain_hash\|哈希链" --include=*.rs --include=*.sql --include=*.md .
（只命中 0007 自身的这两行注释）
```
**没有列、没有代码、没有校验。**

**一处真实的台账缺口**：来源对账的批量清理不写审计。`crates/utopia-server/src/api/sources_routes.rs:275-285` 的 `cleanup_missing` 循环调 `documents::delete(...)`，然后**一行 `audit::record` 都没有**。而逐条删除路由（`documents_routes.rs:460-473`）是写的。ADR-0022 说的「删除是一个事件」在台账上**只对单条删除成立**。

### 5.2 人的裁决怎么记，理由去哪，是否回灌

**理由有自己的一列**：`migrations/0038_a_decision_records_why.sql:8`

```sql
ALTER TABLE resolution_reviews ADD COLUMN rationale TEXT;
```

迁移注释把「为什么要这一列」写得很清楚：

> "`reason` 一列早就有，但它记的是这一对**为什么被排进队列**… 人拍板时想的那句话——"同一个地址" "一个是子公司"——没有地方落。于是裁决器和治理 agent 读先例时只看得见结果，看不见依据：**一次错误的合并会被当成"这类该合"的证据，错误洗成政策。**"

请求侧是 `rationale: Option<String>`（`review_routes.rs:309-310`），空白转 NULL（`resolution.rs:1619`）。

**理由同时进台账，而且台账才是被读的那份**：`review_routes.rs:355` 写 `json!({ "left": l, "right": r, "score": score, "why": body.rationale })`；读路径是 `governance.rs:75` 的 `NULLIF(detail->>'why', '') AS why`。

**反证**：`resolution_reviews.rationale` 这一列**生产代码从不读**——grep 全仓，读它的只有测试（`crates/utopia-store/tests/a_decision_records_why.rs:133,213`）。

**覆盖比文档窄**。`docs/design/governance.md:17-19` 说 "Every human decision is a ledger event with an actor … and may carry a `rationale`"，但代码里只有 **ADR-0026 点名的四条重复对路径**带 why（`review_routes.rs:355, 421, 567, 726`）。`fact.confirm` / `fact.reject` / `conflict.*` / `merge.revert` 只写事实三元组快照，**没有 why**（`review_routes.rs:599-608, 623-632, 283-298, 659-668`）。

**是否回灌以调优抽取？——没有。** 理由的唯一消费者是把话拼进提示词：

`crates/utopia-store/src/governance.rs:188-235` 的 `render_lines`，`because` 闭包拼 `; they wrote: "{w}"`，而且**只挂在 same-pair / same-name / revert 三种先例上**；类型对习惯刻意不带理由（`:217-224` 只输出 counts）。调用点只有两个：`crates/utopia-server/src/governance.rs:368`、`crates/utopia-server/src/adjudication.rs:166-167`。

**没有任何一行**把理由变成规则、改阈值、或反哺抽取器。`docs/design/governance.md:130` 自己承认："The agreement rate split by `via` now that the sample is gone: **nothing computes it**."

**更根本的一层**：Utopia 现在的抽取是**开放抽取**，它既不读本体也不读先例。`crates/utopia-extract/src/lib.rs:3-5`：

> "开放抽取（`open`）是唯一的抽取契约（0044 决定 2）：**模型用文档自己的话写陈述，不读本体、不算日期。**"

`docs/design/extraction.md:13-16`：

> "One call per chunk, at temperature 0, with the document's filename, the things already accepted earlier in the document, the document's opening (its first 1,500 characters, #680) and the chunk text. **No ontology, no document date, no request for dates.**"

所以「人的裁决反哺抽取」在这套架构里**不是一个还没做的功能，而是一个被设计排除的东西**——本体与人的先例都在**抽取之后**的「对齐」阶段起作用，而且作用的对象是**消歧裁决器**（判断两个名字是不是同一个实体），不是抽取器。这对「喂进法规 + 内部规则 + 正负样本，让它越来越准」的期待是釜底抽薪的一条。

### 5.3 "每个审核队列都被治理"（ADR-0043）在结构上是什么意思——以及代码里有没有

**文档说的**（`0043-every-review-queue-is-governed.md:3`，状态行逐字）：

### 5.4 删除与清除

**0022（删除是一个事件，可撤销）**：`documents.deleted_at` 墓碑 + `document_deletions` 表（`invalidated_facts UUID[]` / `superseded_chunks UUID[]` 两份名单 + `reverted_at`）。核心注释：

> "**什么内容都不清**——内容留到显式的 purge（另一条路，未做）；只作废「每条出处都已删除」的事实；这次作废了哪些事实、打标了哪些分块记在 `document_deletions` 里，撤销、同步复活、同内容重传复活都从那里原路读回，**不多不少**。"

撤销（`documents.rs:1108-1207` 的 `restore_tx`）只复活名单里那两份，末尾 `UPDATE document_deletions SET reverted_at = now()`。

**0023（清除是终局）**：`documents.purged_at`。**不可撤销**——`restore_tx` 一查 `purged_at IS NOT NULL` 就报 `Conflict("The document's content was purged; there is nothing to restore")`；全仓只有一处 `SET purged_at`，**没有任何路径把它置回 NULL**。purge 要 `Role::Admin`（`documents_routes.rs:517`），restore 只要 `Editor`（`:490`）。原文 blob 只交出**没人再引用的**那个指纹。

**保险丝**（`migrations/0037` + `crates/utopia-server/src/governance.rs:1019-1020`）：`FUSE_WINDOW_DAYS = 7`、`FUSE_REVERTS = 2`。七天内人撤回 agent 的自动合并两次 → 关掉 `governance` 开关、发 `governance.tripped` 告警、写一行 **actor 为 NULL** 的 `kb.updated`。窗口基准是 `governance_since`（"只数这次打开之后的撤回——人重新打开时，之前那两次不再算，**否则一开就再跳**"）。

### 5.5 执行闸门（0027）

`crates/utopia-store/src/execution_gate.rs:1-12`：

> "合并在图里撤得回… **撤不回的是它活着那几天离开图的东西**——推理据它推出的派生、据它开出的违规与告警、进了导出的三元组、带引用给出去的答案。**撤销还原的是图，不是图被读进去的那个世界。**"
> "这里问的只有一件事：**这一次合并会不会立刻把什么送出图外**。会，就留给人，把握再高也不动手。**只管合并**：分开撤起来不费什么，下一次合并就是撤销。"

实现是纯函数 `hold(&Impact) -> Option<Hold>`（`:97-108`），优先级 `contradictions > derived > answered`，`Display` 输出 `contradiction CEO of` / `derived 2` / `answered 1`，直接接在 `escalate_impact|` 后面。**三处共用同一个闸门**：`utopia-server/src/governance.rs:515-537`、`adjudication.rs:329-336`、`errata.rs:479-495`。还前置给模型当工具看（第二层 `consequences`，`governance.rs:766-782`）。

> "一个库上可以连着好几个 agent，而**它们共用同一个人的身份**。"

链路：`mcp.rs:239` `via_token: Some(auth.token_id)` → `tools.rs:705-720` job payload 的 `proposed_token` → `pending.rs:171,190` 落库。

**一处不一致值得点名**：`Uuid::nil()` 与 `actor_id IS NULL` 两套「机器行」写法并存——`main.rs:430`、`main.rs:519`、`errata.rs:100` 用 `Uuid::nil()` 当 actor，而 `review_summary.rs:156` 的自动口径是 `(e.actor_id IS NULL) AS automatic`。**`nil` 既不是 NULL 也不是真人**，按后者统计会把它算成「人办的」。

## 6. 部署与运维

### 6.1 最小可用足迹：2 个容器

| | `db` | `app` |
|---|---|---|
| 镜像 | `${UTOPIA_DB_IMAGE:-pgvector/pgvector:pg16}` | `${UTOPIA_IMAGE:-ghcr.io/deeplethe/utopia:0.1.0-rc5}` |
| 端口 | 宿主 `${UTOPIA_DB_BIND:-127.0.0.1:1517}` → 容器 5432 | `"1516:1516"`（**绑所有宿主接口**） |
| 卷 | `dbdata:/var/lib/postgresql/data` + `./docker/init-app-role.sh` | `./data:/app/data` |
| 健康检查 | `pg_isready`，5s/3s×10 | 无 |

`app` 用 `depends_on: db: condition: service_healthy`。README 承诺的一条命令是 `docker compose --profile app up -d`（`README.md:82`）。

**注意一处不一致**：`docker-compose.yml:46` 默认镜像是 `0.1.0-rc5`，而 `.env.example:41` 注释里写的是 `ghcr.io/deeplethe/utopia:0.1.0`。compose 自己的注释解释了为什么钉 rc："撤掉一个版本时必须连它一起改——0.1.0 撤了，现在指向 rc。"

**没有任何资源限制、也没有 `restart:` 策略**（`grep -c "restart:" docker-compose.yml` = 0）——**主机重启后容器不会自愈**。

### 6.2 LLM 要求

**只支持 OpenAI 兼容协议**，没有 Anthropic 原生客户端。硬编码 `/chat/completions` 与 `/embeddings`，鉴权一律 `bearer_auth`。`crates/utopia-llm/src/lib.rs:1-2`：

> "utopia-llm: OpenAI 兼容协议的薄客户端。一套代码适配 DeepSeek / Qwen(DashScope 兼容模式) / GLM / OpenAI / Ollama / vLLM。"

**模型配置在数据库里，不在环境变量里**：`llm_settings` 表按 workspace 分行，字段 `chat_base_url / chat_api_key / chat_model` 与 `embed_base_url / embed_api_key / embed_model / embed_dim`（`models.rs:445-467`），key 落库前 AES-256-GCM 封印。UI 在「管理 → 模型」，带五组预设（`web/src/pages/Settings.tsx:836-870`），含 **Ollama（`http://localhost:11434/v1`，chat `qwen2.5:7b` / embed `bge-m3`）**。

**维度是动态的**，不固定。决定性的一行：

```rust
// crates/utopia-store/src/documents.rs:1636
crate::vector_index::request(pool, crate::vector_index::Target::Chunks, first.len())
```

`llm_settings.embed_dim` 只被存下和返回，**不参与强校验**。超过 `MAX_DIMS = 2000` 就不建索引（`text-embedding-3-large` 的 3072 维走精确扫描）。

`GET /api/v1/workspaces/{id}/settings/test` 对 embed 会"试算一条并返回维度"（`{"dim": v[0].len()}`，`settings_routes.rs:233-238`）——这是配模型时最有用的一个端点。

### 6.3 硬外部依赖

- **Postgres 16 + pgvector，仅此一个扩展**。全仓唯一的 `CREATE EXTENSION` 是 `CREATE EXTENSION IF NOT EXISTS vector;`（`migrations/0001_core.sql:3`）。**没有 pg_trgm**。
- **全文检索内嵌**（Tantivy），**作业队列是一张表**，**没有 Redis**。README 原话：*"One Rust binary and one Postgres. Full-text search is embedded in the binary, vectors go in pgvector, and the job queue is a table: nothing else to run."*（`README.md:53`）
- **外部二进制**：`pdftotext`——PDF 回退路径。`docker/Dockerfile:27` 装了 `poppler-utils poppler-data`；**源码运行时会依赖宿主机有它**（CI 里也专门 `apt-get install`，并设 `UTOPIA_TEST_REQUIRE_PDFTOTEXT=1`）。
- **S3 不是必需**，只是可选来源类型。
- **运行时联网**：① 远端 LLM（换本地 Ollama/vLLM 可消除）；② 来源连接器同步；③ **浏览器侧**——`web/index.html` 从 `fonts.googleapis.com` 加载字体（内网部署时唯一一处静默的外部请求，会退化成系统字体）。

### 6.4 离线 / 内网能力

README 两处宣称（`README.md:27` "It deploys offline"；`:59` "so the whole system can run air-gapped"）。**没有「离线模式」开关**——降级全靠「某一项配置为空」。

为离线而做的实现：
- 五个本体包 gzip **内嵌二进制**，`crates/utopia-server/packs/README.md:5` 写明理由："**为什么内嵌而不是运行时下载**：README 承诺整套系统可以运行在完全离线的内网环境"
- 内置产品文档随包（`web/src/pages/Docs.tsx:1` "随应用打包（私有部署离线可用）"）
- 分块用的 cl100k 词表随 crate 内嵌

**断网会坏什么**：① 没有本地模型 → 抽取、消歧、裁决、问数全停（此时系统变成「能存能搜、不能抽取」）；② 扫描件/图片需要工作区的 MinerU（`llm_settings.ocr_*`），没配时文档停在 `failed` 并记 `reader_needed` + 发 `document.needs_reader` 告警；③ 全部来源同步停；④ 网页字体。**数据库、检索、图谱读写、台账完全不依赖网络。**

### 6.5 磁盘上存什么（`data/` 目录）

| 路径 | 内容 | 写它的代码 |
|---|---|---|
| `data/files/{sha256}` | **原始文件字节**，内容寻址、去重、不可变 | `LocalBlobStore::new(data_dir.join("files"))`（`state.rs:54`；`blob.rs:6`） |
| `data/index/` | **Tantivy 全文索引** | `SearchIndex::open(&cfg.data_dir.join("index"))`（`main.rs:140-142`） |
| `data/secret.key` | **AES-256-GCM 封印钥匙**，64 位十六进制，unix 下 0600 | `secret_key_file()`，首启生成（`main.rs:651-669`） |

**其余全在 Postgres**：图谱、作业队列、审计台账、`deployment_settings`（含自动生成的 JWT 密钥）、`llm_settings`。**没有配置文件落盘**。

compose 注释写明了不挂卷的后果（`docker-compose.yml:72-74`）：

> "原始文件（files/）与全文索引（index/）。不挂出来的话，容器一重建它们就没了，而库里的 `documents` 记录还在——**引用全断且不报错**。备份 = 这个目录 + 数据库。"

索引有自愈：库里有分块而索引为空时自动重建，**失败只告警不阻断启动**（`main.rs:337-383`）。

### 6.6 备份 / 恢复

**今天实际存在的**：`crates/utopia-cli/` 是一个真在 workspace 里的可执行 crate（`Cargo.toml:5` 的 members 里有它；`bin name = "utopia"`；`main.rs` 1076 行、13 个测试）。`backup` 与 `restore` **均已实现**：`pg_dump -Fc` + 可选打包 `data/`（不含 `secret.key`），产出含 `manifest.json`（`schema_version`、`utopia_version`、`created_at`、sha256 校验和）的单个 tar.gz；`restore` 拒绝 `schema_version > CURRENT`，旧版仅告警；支持 `--dry-run / --force / --yes`。`CURRENT_SCHEMA_VERSION: u32 = 73` **是迁移文件个数**，且有守卫测试按目录数比对。

**但有一半还停在提案层，三个硬证据**：
1. `.roadmap-proposals/backup-restore.md:122`："This proposal does **not** ship the docker image change — it lands the binary first, the image second."
2. 镜像里**没有** `pg_dump`/`pg_restore`，也没有 `utopia` 这个二进制——`docker/Dockerfile` 只 `COPY --from=build /src/target/release/utopia-server`。
3. `main.rs:130` 的 `--help` 文案还写着过期的东西：`"restore  Restore from a tarball produced by \`utopia backup\`. (TODO: stubbed in this PR.)"` ——而 `run_restore`（`:488`）实际已实现。**帮助文本在骗人**，`README.md:116` 的路线图也仍是 `- [ ] **Enterprise**: OIDC SSO, backup and restore commands…`（OIDC 同样已落地）。

**迁移纯前滚、无回滚——三处逐字证据**：
- 机制：`crates/utopia-store/src/db.rs:30-32` 全体就一句 `sqlx::migrate!("../../migrations").run(pool).await?;`。**不用 refinery，无 down 目录，无 `.down.sql`。**
- README：`README.md:120` "the database schema evolves between versions and **migrations only roll forward, with no rollback**"
- CONTRIBUTING：`CONTRIBUTING.md:109` "`migrations/` rolls forward by number"

唯一能当「回退」用的是整包 `restore`，而它自己只认不高于当前的 schema。

**另一处细节**：`ls migrations/` 有 73 个文件，编号从 0001 到 0074，**0071 缺号**（没有对应文件）。这不影响运行，但说明编号是被有意保留给某个被撤回/改名/占位的迁移——对一个把迁移当契约的项目，缺号本身是一处应当有说明而不存在的空白。

### 6.7 CI 与安全态势

CI（`.github/workflows/ci.yml`）：`push: [main, dev]` + 所有 PR，`permissions: contents: read`。六个 job：`lint`（fmt + clippy `-D warnings`）、`test`（起 pgvector/pg16 service + 装 poppler + `cargo run -p utopia-store --example migrate` + `cargo test --workspace`，带 `UTOPIA_TEST_REQUIRE_DB=1` / `UTOPIA_TEST_REQUIRE_PDFTOTEXT=1`——**测试不许静默跳过**）、`build`、`backend`（汇总闸门，分支保护按这个名字）、`migrations`（查编号重复 + `sqlx migrate run` **跑两遍**：全新库 + 重放）、`web`（`pnpm test` + `pnpm build`）。

`release.yml` 的冒烟测试值得一记：先 `load: true` 构建 → 起 pg + app → 轮询 `/api/v1/health` 核对 `"status":"ok"`（注释说明为什么不能只看 200："请求 /health 会拿到 200 的 index.html，看着像通过"）→ 再 POST `/api/v1/auth/register` 检查返回带 token → **冒烟过了才 `push: true`**。

`SECURITY.md:5-6` 的性质声明：

> "Utopia is at v0.1. Below are the **known, unresolved** limits — not a vulnerability report, but **the places the design has not reached yet**."

**没有一句直白的 "not production ready"**。最接近的是 README：`README.md:120` "Utopia is still at **v0.1** … Pin a specific version with `UTOPIA_IMAGE` in production, and back up the database along with the `data` directory before upgrading."；`README.md:122` "Please read SECURITY.md before exposing it to the public internet."

已做（`SECURITY.md:20-44`）：凭据 AES-256-GCM 封印、钥匙不进库；JWT 密钥首启由 CSPRNG 生成 32 字节存库（**无部署共用默认值**）；cookie 按 `X-Forwarded-Proto` 自动打 `Secure`；**数据库端口只绑回环**；可选受限运行角色；数据源只到达被显式授权的工作区；问数三层只读闸（解析白名单 + 只读事务 + 强制行数上限）；账号停用不删除；口令 argon2。

**运维上最该注意的一处自相矛盾**：数据库端口被刻意绑回环，但 `app` 的 `ports: ["1516:1516"]` 绑的是**所有宿主接口**（不是 `127.0.0.1:1516:1516`），而默认 `UTOPIA_OPEN_REGISTRATION=true`、**第一个注册的人自动成为系统管理员**。README 却让人直接 `http://localhost:1516` 注册。一个照 README 做、把机器放在公网的人，会在几分钟内得到一个别人当管理员的部署。

## 8. 接入成本评估

前提：以下按「一个团队要拿 Utopia 做法规/标准 + 内部规则的合规审查知识底座」评估。所有结论都基于 §1–§7 的证据。

### (a) 把它跑起来：**低，1–2 人日**

这是 Utopia 最扎实的一面，名副其实。

- 一条命令：`docker compose --profile app up -d`，两个容器，1516 + 1517 两个端口，**一个 Postgres 依赖，无 Redis / 无对象存储 / 无外部搜索**。
- 迁移自动跑，JWT 密钥与封印钥匙首启自动生成。**严格说没有「必需」的环境变量**（`AppConfig::default()` 每一项都有默认值），生产要改的只有 `UTOPIA_DB_PASSWORD` 与 `UTOPIA_IMAGE`（钉版本）。
- 模型在 UI 里配（管理 → 模型），有 Ollama 预设，**真能全离线**。
- 三个必须当场处理的坑（都能在半小时内处理完，但不处理会出事）：
  1. **`app` 端口绑所有接口 + 开放注册 + 第一个注册者即管理员**。上公网前必须 `UTOPIA_OPEN_REGISTRATION=false`，或把端口改成 `127.0.0.1:1516:1516`。
  2. **备份今天得自己做**：`utopia-cli` 的 `backup`/`restore` 已实现，但**镜像里没有这个二进制也没有 `pg_*` 工具**。可行方案是 `pg_dump` + `tar data/`（**`data/secret.key` 必须一起备份**，否则封印的凭据全解不开），外加自己写恢复流程。
  3. **迁移纯前滚**：升级前必须整库 + 数据目录快照。没有 down 路径，`restore` 又拒绝更新的 schema，所以**回滚只能是「恢复快照」，不能是「降级镜像」**。
- 风险等级：低。但 `v0.1` 且 README 明确说 schema 会在版本间演进——**每次升级都要当作一次有数据风险的操作**。

### (b) 灌一个「法规/标准 + 内部规则 + 正负样本」的语料：**高，且比看起来高得多**

这是最需要说清楚的一段，因为 Utopia 的文档会让人严重高估这里。

**格式与传输层：便宜。**
- PDF / DOCX / PPTX / XLSX / XLS / ODS / CSV / MD / HTML 都直接吃；**扫描件 PDF 与图片需要额外配一个 MinerU 实例**（`llm_settings.ocr_*`），录音需要会标说话人的转写服务。法规扫描件很常见——**这一项要先算进去**。
- 语料规模不大时（几千份以内），走 `/kbs/{id}/documents` 上传或 `custom` 来源推送（带 `ingest_token`）都行。上限 100 MiB/文件、每轮同步 `MAX_NEW_PER_SYNC = 200`。

**本体层：要把期望调对。**
- **抽取不读本体**（`utopia-extract/src/lib.rs:3-5`、`extraction.md:13-16`）。所以你写多好的「法规实体类型体系」，都**不会**让抽取更准——抽取只是把文档用**它自己的话**写成开放陈述（subject / 短语 / object / 限定词 / 时间词）。
- 本体在**抽取之后**起作用，经由一条叫「对齐」的流水线：类别词绑到类、短语签名绑到属性（两次投票必须一致）、绑上的陈述才算成「类型化事实」（`materialize.rs`）。**这些绑定大多数要人裁**——两票不一致的进 `alignment` 队列（12 个队列之一）。
- 实操含义：**「法规条文 → 结构化规则」这一步没有捷径，它是一条有人的审核队列的长流水线**。ADR-0044 自己的状态行说 cut 2「in progress」，而 `docs/design/ontology.md` 甚至还说它 not built（见 §0）——**这条流水线在动，但显然还没稳定**。
- 冷启动有五个内嵌本体包（schema.org、W3C Org、PROV-O、FOAF、IOF Core）。**没有一个法律/合规向的包**，README 是挂了个 issue 链接让人「ask for your industry」。

**内部规则层：要看你想让它做什么。**
- 想要「规则读某类实体的属性、超过阈值就判成某类」——**有**，`/kbs/{id}/rules` + `RulesPanel`，ADR-0021/0032，规则是声明式结构化数据（"everything a person authors is structured, so the page shows what runs"，`0034-*.md:5`）。
- 想要「规则命中就自动发飞书 / 开工单 / 发邮件」——**没有**。ADR-0034 的 actions 零代码，0050 还退回到文档层（§4.5）。**Utopia 今天没有任何对外副作用能力。**

**正负样本反哺：这条期望要直接删掉。**
- 人写的裁决理由（`rationale`）只做一件事：拼进**消歧裁决器**的提示词当先例（`governance.rs:188-235`，两个调用点）。**它不改抽取、不改阈值、不生成规则。**
- `docs/design/governance.md:130` 自认："nothing computes it."
- 而且只有四条重复对路径带理由；`fact.confirm/reject`、冲突裁决、合并撤销都**不带**。
- 另外：`resolution_reviews.rationale` 这一列**生产代码根本不读**（只有测试读）——理由的实际载体是台账的 `detail.why`。

**结论**：把语料灌进去（能搜、能问答、能图谱）成本中等；**让它的输出「符合内部规则且随正负样本变准」不是配置工作，是要在这套代码上做二次开发的工作**。

### (c) 从现有飞书机器人调用它：**中等，有一条硬约束会决定架构**

**硬约束一：没有飞书连接器。**§1.5 已逐条验证（README 路线图、ADR-0013 状态行、`docs/design/sources.md` 的 "Proposed and not built"、以及 `crates/` 与 `migrations/` 里零命中）。**飞书文档不能作为来源同步进来**——如果你们的法规/内部规则本来沉淀在飞书文档里，第一步就得自己做导出（注意 §7 提到的红线约束在这个项目语境下不适用，但你们自己可能有同等约束）。好消息是连接器框架是现成可插的，ADR-0013 给了完整开工清单。

**硬约束二：Utopia 不会主动推任何东西。**没有 webhook、没有 action、没有邮件出口；告警只到浏览器（SSE）。**所以「法规变更 → 飞书自动通知」这个方向，Utopia 侧没有落点。** 可行的形态只有拉模式：你的飞书 bot 定时问，或者你们自己写一个旁路服务，读 Utopia 的台账/告警再决定推不推。

**可用的调用面有两条，选哪条决定了很多事**：

| | 走 MCP | 走 REST `/chat` |
|---|---|---|
| 端点 | `POST /api/v1/kbs/{kb_id}/mcp` | `POST /api/v1/kbs/{kb_id}/chat` |
| 认证 | **个人令牌 `utp_pat_`**（长期、可撤销、可限库、可限读/写） | **JWT**（7 天过期、**不可撤销**） |
| 会话要求 | 无（无状态，每次 POST 重新认证） | 有（Cookie/Bearer JWT） |
| 能力 | 12 个工具（11 读 + 1 写），**没有 `query_data`** | 最多 13 个工具（含 `query_data` 与 `remember`），有流式与引用编号 |
| 适合 | **服务端到服务端集成（你们的场景）** | 前端/人机对话 |

**结论：正确的接法是让飞书 bot 做 MCP 客户端。** 具体工作量与要点：
- 建库 → 建个人令牌（`/account/tokens`，scope=read，勾上目标库，默认 90 天）→ 明文只显示一次，要当场存进你们的密钥管理。
- 实现 MCP 的 `initialize` / `tools/list` / `tools/call` 三个方法（JSON-RPC 2.0，`2025-06-18`）。注意：**响应是 `application/json`，不是 SSE**，比常见 MCP HTTP 客户端假设的简单。
- 用 `search_chunks` 找条款 → `get_document` 拿全文 → `entity_facts` / `paths_between` / `timeline` 做实体与时间推理 → 组装答案回飞书。
- **没有速率限制、没有配额**，所以节流得你自己做。而且**每次工具调用都是一次独立的模型/DB 往返**，飞书那条 3 秒响应窗口会很紧——建议 bot 侧先回「正在查」，再异步补发。
- **审计天然是通的**：每次调用落一行 `mcp.tool_called`（actor = 令牌持有人，`target_id` = token_id，`detail.tool` = 工具名）。但注意 `let _ =`——**记账失败是静默的**，不能拿它当合规证据的唯一依赖。

**如果你们必须用 REST `/chat`**：得接受 7 天 JWT。JWT 存库外加定期重登，或自己在前置代理里做令牌交换——两者都是在绕过认证模型，不是它支持的做法。

### (d) 保住到原文条款的证据链：**目前能做，但要走三跳，且有一处实质缺口**

**做得到的部分**（这是 Utopia 真正的差异化，也确实实现了）：

1. **`facts` 行从不原地更新**。修正 = 新行 `supersedes` 旧行并作废旧的；撤回 = 作废。两个时间轴都在：`valid_from/valid_to`（世界轴，什么时候**是**真的）+ `recorded_at/invalidated_at`（记录轴，我们什么时候**认为**它是真的）。
2. **每条事实带证据行**：`fact_evidence (fact_id, chunk_id NOT NULL, quote, proposed_predicate, quote_start, quote_end)`——引文与它在 chunk 里的字符偏移都在服务端算好。
3. **每个 chunk 带来源**：`origin`（stated / ocr / transcribed / described）+ `origin_model` + `anchor`（页 + 框 / 起止毫秒 + 说话人），**且 anchor 的形状按 origin 有 CHECK 约束**（§2.4）。`provenance.rs:3-5` 说得对：这四档不是同等证据。
4. **`origin = 'described'` 的事实不能单独关掉一条正确的旧事实**，只会开一个 `described_evidence` 冲突交给人（`ledger.md`），置信度也被压到审核阈值以下。
5. **RDF 导出是明确的对外读契约**（ADR-0020）：每条事实是 `rdf:Statement`，带两个时钟、置信度、证据（含 origin）、限定词与 PROV-O 到文档/规则的谱系；当前成立的三元组再额外写一遍。`web/src/docs/mcp.md` 明确："**RDF export is the supported machine-readable read contract** … Ordinary `/api/v1` UI response shapes are **not** a compatibility promise."
6. **删除与清除分得很清**：删除是墓碑（可撤销、可 `as_of` 回看），清除是终局（`purged_at` 无法置回 NULL，且使 `external_key` 让出身份）。

**实质缺口一：检索路径不携带出处（§2.4）。**
`/search`、MCP `search_chunks`、MCP `get_document` 返回的 `ChunkView` **没有 `origin`/`anchor`**。所以一个走 MCP 的 agent 可以给你一句引文和 `document_id`，但**无法告诉你这句话是原文写的、OCR 认出来的、还是模型看图转述的**——而 ADR-0040 的整个立论就是"这四种不是同等的证据"。
补齐路径：
- 拿到 `fact_id` 后调 `GET /api/v1/kbs/{id}/facts/{fact_id}/evidence`（`EvidenceView` 字段最全，含 `stale` / `document_deleted` / `doc_version`），或走 RDF 导出；
- 或 MCP `changes`（每条带 `quote_origin`）；
- 或在 `search_chunks` 的 `structuredContent` 上自己加字段——但注意 `web/src/docs/mcp.md` 写明了：**移除或改名已文档化的 `structuredContent` 字段需要一条决策记录**，新增字段则可以（"clients should tolerate additional fields"）。所以**加字段是被允许的方向，改字段不是**。

**实质缺口二：没有 `chunk_id → 条款原文` 的一跳。**
`web/src/docs/mcp.md` 结尾自己列了未完成项（引 #564）："The export does not yet include conflict/review state"。而 `docs/design/chat-and-mcp.md:72` 的 "Proposed and not built" 里明写：**"The read-contract gaps: conflict and review state, chunk identity behind a quote."**
也就是说：**「一条引文对应哪个 chunk、哪个字符区间」这件事在对外契约上是空的**。在内部 `fact_evidence.quote_start/quote_end` 有，但没有一条文档化的外读路径把它交出来。

**结论**：做「事实 → 引文 → 文档 → 版本」的四跳链路，Utopia 今天是支持的（第 4 跳用 REST evidence 端点或 RDF 导出）。做「**引文 → 具体字符区间 → 条款编号**」这一跳，得你们自己在外部把 chunk 与法条结构对齐——Utopia 不认识「第 12 条第 3 款」这种结构，它只知道 chunk 的 `seq` 和字符偏移。

### (e) 一句话总结与建议

**值得用的部分**：部署、摄入（含中文编码、表格、扫描件）、内嵌全文 + 向量混合检索、双时间轴台账、RDF 导出、MCP 服务端。这几块是**真的做完了、而且做得很细**——代码里的那些注释（HNSW 的 `iterative_scan` 实测、CJK 不能用 QueryParser、`looks_binary` 的两条判据、`clear_auth_cookie` 的 path）说明它经受过真实数据的打磨。

**不要期待的部分**（这几条建议在立项文档里明写）：
1. **没有飞书连接器**（要自己写，框架现成）。
2. **Utopia 不会主动推任何东西**（action 零代码）。
3. **人的裁决不反哺抽取，也不生成规则**——只做消歧的先例。
4. **「每个审核队列都被治理」是 ADR 而非代码**：今天只有重复对一个队列有 agent，其余靠人。
5. **迁移纯前滚，备份要自己做**（工具在，镜像里没有）。
6. **`v0.1`，且 docs 的完成度普遍高于代码**——§0 那三处不一致不是孤例，**任何一条来自 `docs/` 的结论都必须回代码验证一遍**。

**建议的接入顺序**：先只做 (a) + 一个走 MCP 的只读飞书问答 bot，用真实语料把检索质量与中文分块质量压出来；确认真实问答可用之后，再决定要不要投入 (b) 那条有人的对齐流水线。**不要把 (b) 和 (c) 并行开工**——(b) 的产出形态（开放陈述 vs 类型化事实）会随 0044 cut 2 的落地而变，`0046-*.md:37-40` 自己就把这条列为「现在不做应用层」的第一个理由："**The layer an app would read is in motion.** Extraction writes only the open graph (#736), and typed facts come from alignment, whose cuts are landing as this is written (#751, #752, #753, #754). **The first applications would be written against a model being replaced underneath them, and the cost of that lands on whoever wrote them.**"
